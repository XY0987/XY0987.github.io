从脚本到 CLI：Node 命令行工具开发基础

发表于2026|更新于2026|工程化
|字数总计:2.1k|阅读时长:7分钟

前言：前面我们把模块系统、包管理、构建工具都过了一遍。这一阶段目标很明确：把 Node 从「会写一点脚本」提升到「能开发工程化工具」。换句话说，从「跑一个 node xxx.js」进化到「写一个能 npm install -g 全局使用的命令行工具」。这一篇先打地基，把一个 CLI 工具最底层的运行机制讲清楚。

一个 CLI 工具的本质是什么

很多人觉得脚手架、命令行工具很神秘，其实拆开看非常简单：

一个 CLI 工具 = 一个普通的 Node.js 程序 + 一份「命令名到入口文件」的映射。

你平时敲的 vite、eslint、vue、create-vite，本质都是 Node 脚本。区别只在于：它们通过 package.json 的 bin 字段，把一个命令名注册到了系统的可执行路径里，所以你能在任意目录直接敲命令，而不用写 node ./node_modules/.../cli.js。

理解了这一点，开发 CLI 就没有心理负担了：先把功能用普通 Node 代码写出来，再处理「怎么让它变成一个命令」。

最小可运行的 CLI

我们从零做一个最小的 CLI，叫 mycli。

mkdir mycli && cd mycli
npm init -y

新建入口文件 bin/index.js：

#!/usr/bin/env node

console.log('hello from mycli')
console.log('参数:', process.argv.slice(2))

这里的第一行 #!/usr/bin/env node 叫 shebang，它告诉操作系统：这个文件要用 node 来执行，而不是当 shell 脚本跑。少了这一行，全局命令在类 Unix 系统上会直接报错。

然后在 package.json 里加上 bin 字段：

{
  "name": "mycli",
  "version": "1.0.0",
  "type": "module",
  "bin": {
    "mycli": "bin/index.js"
  }
}

bin 的含义是：注册一个叫 mycli 的命令，它指向 bin/index.js。如果命令名和 name 一样，也可以简写成 "bin": "bin/index.js"。

用 npm link 本地调试

工具还没发布到 npm，怎么本地测试？答案是 npm link：

# 在 mycli 项目根目录执行
npm link

npm link 会在全局 node_modules 里创建一个指向当前项目的符号链接，并把 bin 注册的命令挂到全局。完成后，在任意目录都能直接敲：

mycli hello world
# 输出:
# hello from mycli
# 参数: [ 'hello', 'world' ]

调试完想取消链接：

npm unlink -g mycli

坑点：在类 Unix 系统上，如果 npm link 后提示 permission denied，通常是 bin/index.js 没有执行权限。手动补一下 chmod +x bin/index.js 即可。不过实际发布时，npm 会在安装阶段自动处理可执行权限，本地用 npm link 偶尔需要手动补。

process.argv：最原始的参数获取

process.argv 是 Node 提供的原始命令行参数数组。它的结构固定：

process.argv[0]  →  node 可执行文件路径
process.argv[1]  →  当前脚本路径
process.argv[2]  →  第一个真正的用户参数
...

所以拿用户参数时永远要 slice(2)：

const args = process.argv.slice(2)
// mycli build --watch  →  ['build', '--watch']

你可以手写解析逻辑，但很快就会发现痛点：要处理 --name=foo 和 --name foo 两种写法、要处理 -abc 这种合并短选项、要生成 --help、要做必填校验……这些都是重复劳动。所以实际项目里几乎不会裸用 process.argv，而是交给 commander、cac、yargs 这类参数解析库。这部分下一篇专门讲，这里只要知道：**process.argv 是地基，参数解析库是地基上的房子**。

CLI 里 ESM 和 CJS 怎么选

CLI 工具同样要面对模块格式的选择。模块系统的差异在前面《JavaScript 模块格式与运行时差异》和《exports 条件导出与双包陷阱》两篇里讲得很细了，这里只给 CLI 场景下的结论：

场景 建议
全新 CLI 工具 优先 ESM（"type": "module"），生态已经普遍支持
依赖里有只支持 ESM 的包 优先 ESM，或者用打包器把依赖一起处理进发布产物
需要兼容很老的 Node 运行环境 才考虑 CJS

这里有个很现实的驱动力：现在 CLI 生态里大量高频工具（execa、chalk、ora、@clack/prompts 等）的新版本都是 ESM-only 的。如果你完全手写 CJS 入口，要么被迫用 await import() 动态导入，要么只能锁在旧版本。

但这不代表所有 CLI 都只能直接发布 ESM。工程上还有一个常见思路：源码用 ESM / TypeScript 写，发布时用 tsup、unbuild 这类打包器生成最终产物。这样内部可以放心使用 ESM-only 依赖，外部则根据目标环境输出 ESM、CJS，甚至单文件 CLI。我的建议是：新 CLI 优先按 ESM 思路设计；如果有兼容诉求，就把模块格式问题交给构建层解决。

用 TypeScript 写 CLI

实际工程里，CLI 工具基本都用 TypeScript 写，好处是参数类型、配置对象都有提示和检查。但 Node 不能直接跑 .ts，所以分两个阶段：

  • 开发期：用 tsx 免编译直接跑 TS（tsx watch 当热重载用）。
  • 发布期：用 tsup 把 TS 打包成 JS 产物，再发到 npm。

这两个工具在《库构建与脚本运行工具链：tsx、tsup、unbuild》里讲过，这里直接给 CLI 的最小配置。

package.json：

{
  "name": "mycli",
  "version": "1.0.0",
  "type": "module",
  "bin": {
    "mycli": "dist/index.js"
  },
  "files": ["dist"],
  "scripts": {
    "dev": "tsx src/index.ts",
    "build": "tsup src/index.ts --format esm --clean"
  }
}

src/index.ts：

#!/usr/bin/env node

const args: string[] = process.argv.slice(2)
console.log('mycli 收到参数:', args)

注意：bin 指向的是构建产物 dist/index.js，不是源码 src/index.ts。用户安装后跑的永远是编译后的 JS。

坑点：用 tsup 打包 CLI 时，shebang（#!/usr/bin/env node）要写在源码入口的第一行，tsup 会保留它。如果产物丢了 shebang，全局命令就跑不起来——这是发布后最常见的「装上了但敲命令没反应」的原因。

这一阶段会用到的工具链全景

为了不在后面的篇章里迷路，先建立整体印象。开发一个工程化 CLI，常用工具按职责分类大概是这样：

运行/构建    tsx（跑 TS）          tsup / unbuild（出包）
参数解析    commander / cac / yargs
交互输入    prompts / @clack/prompts
日志体验    ora（loading）        kolorist / picocolors（颜色）
子进程      execa（执行命令、装依赖）
文件/模板   node:fs / node:path   ejs（模板渲染）
远程模板    giget / degit
职责 代表工具 解决什么
跑 TS 脚本 tsx 免编译直接执行 TS
构建发布包 tsup / unbuild 把 TS 打成可发布产物
参数解析 commander / cac / yargs 命令、选项、help
交互输入 prompts / @clack/prompts 问答式收集用户输入
日志美化 ora / kolorist loading 动画、彩色输出
子进程 execa 执行外部命令、自动装依赖
文件操作 node:fs / node:path 复制模板、生成文件
远程模板 giget / degit 从 GitHub 拉模板

后面每一篇会挑其中一两块深入。你不需要一上来全记住，知道「遇到某类需求该往哪个工具找」就够了。

我的实战建议

  1. 别把 CLI 想得太玄。先用普通 Node 代码把功能跑通，最后再加 bin 映射变成命令。
  2. 新项目直接用 ESM + TypeScript，开发期 tsx、发布期 tsup，这套组合现在是主流。
  3. npm link 是本地调试的核心手段，养成「写完就 link 上真机敲一遍」的习惯，能提前发现 shebang、权限、产物路径这类问题。
  4. 参数解析、交互、日志这些都有成熟库，不要重复造轮子，把精力放在工具本身的逻辑上。

小结

  1. CLI 工具的本质是「普通 Node 程序 + bin 命令映射」，没有魔法。
  2. 入口文件第一行要写 shebang #!/usr/bin/env node，否则全局命令跑不起来。
  3. package.json 的 bin 字段把命令名映射到入口文件，发布后用户即可直接敲命令。
  4. 本地用 npm link 注册全局命令调试，npm unlink -g 取消。
  5. process.argv.slice(2) 拿原始参数，但实际项目交给参数解析库处理。
  6. 新 CLI 优先 ESM + TypeScript，开发期用 tsx，发布期用 tsup，bin 指向构建产物而非源码。
