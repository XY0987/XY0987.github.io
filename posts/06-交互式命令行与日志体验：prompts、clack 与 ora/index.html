交互式命令行与日志体验：prompts、clack 与 ora

发表于2026|更新于2026|工程化
|字数总计:3.4k|阅读时长:13分钟

前言：上一篇解决了「用户敲命令传参数」。但好用的脚手架往往不止接受参数，还会主动问你：项目名叫啥？用哪个框架？要不要 TypeScript？这就是交互式命令行。这一篇先讲底层原理：手写问答、彩色输出、loading 动画到底是怎么实现的；再讲怎么用 prompts / @clack/prompts / ora 把体验做专业。一个工具好不好用，交互和日志体验占一大半。

参数式 vs 交互式

先想清楚两种输入方式的边界：

方式 例子 适合场景
参数式 mycli create app -t vue 已知所有选项、追求脚本化/自动化
交互式 mycli create 然后逐步问答 新手、选项多、想要引导式体验

成熟工具通常两者都支持：你给了参数就用参数，没给的部分再交互式询问。比如 npm create vite@latest，直接回车会一步步问，带上参数则跳过对应步骤。这是体验最好的做法，后面架构篇会讲怎么把两者揉到一起。

这里先专注交互式怎么做。当前主流是两个库：prompts 和 @clack/prompts。

如果不用库，底层怎么做

交互式 CLI 看起来很神奇，但底层其实还是三件事：读用户输入、控制终端输出、用特殊字符改变显示效果。

最简单的问答可以直接用 Node 内置的 readline/promises：

import { createInterface } from 'node:readline/promises'
import { stdin as input, stdout as output } from 'node:process'

const rl = createInterface({ input, output })

const projectName = await rl.question('项目名称？')
const framework = await rl.question('使用哪个框架？')

rl.close()

console.log({ projectName, framework })

这已经能完成最基础的「问一句，等用户输入一句」。但 readline.question() 有个限制：它是按行读取的，用户敲完 Enter 之后你才拿到结果。如果要做选择列表、方向键移动、默认值、多选，就要进入更底层的按键监听。

一个最小的选择列表大概是这样：

import readline from 'node:readline'
import { stdin, stdout } from 'node:process'

const choices = ['Vue', 'React', 'Svelte']
let selected = 0
let renderedLines = 0

readline.emitKeypressEvents(stdin)

if (stdin.isTTY) {
  // 只有真实终端才支持 raw mode；管道输入时不要进入交互式选择模式
  stdin.setRawMode(true)
}

stdout.write('\x1b[?25l') // 隐藏光标

function render() {
  if (renderedLines > 0) {
    readline.moveCursor(stdout, 0, -renderedLines)
  }

  readline.cursorTo(stdout, 0)
  readline.clearScreenDown(stdout)

  const lines = [
    '选择框架：',
    ...choices.map((choice, index) => {
      return `${index === selected ? '>' : ' '} ${choice}`
    }),
    '',
    '使用 ↑/↓ 移动，Enter 确认',
  ]

  stdout.write(`${lines.join('\n')}\n`)
  renderedLines = lines.length
}

function cleanup() {
  stdout.write('\x1b[?25h') // 恢复光标

  if (stdin.isTTY) {
    stdin.setRawMode(false)
  }

  stdin.pause()
}

render()

stdin.on('keypress', (input, key) => {
  if (key.name === 'up') {
    selected = (selected - 1 + choices.length) % choices.length
    render()
  }

  if (key.name === 'down') {
    selected = (selected + 1) % choices.length
    render()
  }

  if (key.name === 'return') {
    cleanup()
    console.log(`你选择了：${choices[selected]}`)
  }

  if (key.ctrl && key.name === 'c') {
    cleanup()
    process.exit(1)
  }
})

这里有几个关键点：

  1. stdin.setRawMode(true) 之后，终端不再等用户按 Enter 才把输入交给程序，而是每个按键都会触发事件。
  2. 选择列表不是凭空「滚动」的，而是程序记录当前选中项，然后通过 readline.cursorTo() 和 readline.clearScreenDown() 清掉当前 prompt 区域，再重新渲染一遍。
  3. 这里用的是局部清屏，不一定每次都清掉整个屏幕。成熟库会尽量只重绘 prompt 这一小块区域，避免把用户上面的日志也冲掉。
  4. Ctrl+C、隐藏/恢复光标、退出时还原 raw mode 都要自己处理，否则终端状态很容易被搞乱。

对应到 render() 里的代码，流程是这样的：

readline.moveCursor(stdout, 0, -renderedLines)
readline.cursorTo(stdout, 0)
readline.clearScreenDown(stdout)

moveCursor() 是把终端里的文本光标往上移动，回到上一次 prompt 开始的位置；cursorTo(stdout, 0) 是把光标放到当前行行首；clearScreenDown() 是从这个位置开始，清掉下面的旧内容。清完以后再 stdout.write() 输出新的列表，看起来就像选项在上下移动。

confirm、password、multiselect 本质上也是这套机制的变体：confirm 监听 y/n 或左右方向键；password 读取真实按键但不回显原字符，或者只回显 *；multiselect 维护一个选中集合，用空格切换选项。也就是说，交互库不是魔法，它主要是在帮你稳定地处理键盘事件、状态管理和终端重绘。

彩色输出也不是终端真的理解了「红色」这个 JavaScript 概念，而是输出了 ANSI 转义序列：

const red = (text) => `\x1b[31m${text}\x1b[0m`
const green = (text) => `\x1b[32m${text}\x1b[0m`
const dim = (text) => `\x1b[2m${text}\x1b[0m`

console.log(green('创建成功'))
console.log(red('创建失败'))
console.log(dim('这是一条次要提示'))

\x1b[31m 表示切到红色，\x1b[32m 表示切到绿色，\x1b[0m 表示重置样式。至于十六进制颜色，并不是直接把 #ff0000 原样丢给终端，而是库把它转换成终端能理解的 ANSI 颜色能力，比如 256 色或者 True Color 的 38;2;r;g;b 格式。日常 CLI 里通常用红、绿、灰、加粗这些基础样式就够了。

loading 动画也是同一个思路：不是终端里真的有一个动画组件，而是不断在同一行重写内容：

const frames = ['-', '\\', '|', '/']
let index = 0

const timer = setInterval(() => {
  const frame = frames[index % frames.length]
  process.stdout.write(`\r${frame} 正在安装依赖...`)
  index++
}, 80)

setTimeout(() => {
  clearInterval(timer)
  process.stdout.write('\r依赖安装完成\n')
}, 1200)

这里的关键是 \r：它会把光标移回当前行开头，下一次输出就能覆盖上一帧。更复杂的场景还会用 ANSI 指令清除当前行、隐藏光标、移动光标。ora、clack 这类库做的，就是把这些细碎的终端控制封装成稳定 API。

所以我的建议是：理解原理可以手写，正式项目尽量用库。终端交互最麻烦的不是能不能跑，而是各种边界：用户按 Ctrl+C、终端不支持颜色、CI 环境没有 TTY、Windows 和 macOS 表现不一致、输出被日志系统收集时动画变成乱码。这些都不值得在每个 CLI 项目里重复踩坑。

prompts：轻量经典

prompts 是一个轻量、API 直观的交互库，用得很广。

npm i prompts

import prompts from 'prompts'

const response = await prompts([
  {
    type: 'text',
    name: 'projectName',
    message: '项目名称？',
    initial: 'my-app',
  },
  {
    type: 'select',
    name: 'framework',
    message: '选择框架',
    choices: [
      { title: 'Vue', value: 'vue' },
      { title: 'React', value: 'react' },
      { title: 'Svelte', value: 'svelte' },
    ],
  },
  {
    type: 'confirm',
    name: 'useTs',
    message: '使用 TypeScript？',
    initial: true,
  },
])

console.log(response)
// { projectName: 'my-app', framework: 'vue', useTs: true }

prompts 接收一个问题数组，按顺序逐个问，最后把所有答案收集成一个对象。常用 type：text、select、multiselect、confirm、number、password。

坑点：prompts 在用户按 Ctrl+C 取消时，不会抛错，而是返回已收集到的部分结果（未回答的字段直接缺失）。所以不能假设 response 里字段一定齐全，要么用 onCancel 回调统一处理，要么在后续代码里判空。这是新手最常忽略的地方——用户中途取消，程序却拿着半截数据继续跑。

const onCancel = () => {
  console.log('已取消')
  process.exit(1)
}

const response = await prompts(questions, { onCancel })

@clack/prompts：现代、好看、取消处理更优雅

@clack/prompts 是近几年很流行的交互库，Astro、SvelteKit 等项目在用。它的卖点是默认样式漂亮（带连贯的边框线、符号），而且取消处理设计得更清晰。当前版本是 1.x。

npm i @clack/prompts

import {
  intro,
  outro,
  text,
  select,
  confirm,
  isCancel,
  cancel,
} from '@clack/prompts'

intro('create-my-app')

const projectName = await text({
  message: '项目名称？',
  placeholder: 'my-app',
  validate(value) {
    if (value.length === 0) return '名称不能为空'
  },
})

// clack 取消时返回一个 symbol，用 isCancel 判断
if (isCancel(projectName)) {
  cancel('操作已取消')
  process.exit(0)
}

const framework = await select({
  message: '选择框架',
  options: [
    { value: 'vue', label: 'Vue', hint: '推荐' },
    { value: 'react', label: 'React' },
    { value: 'svelte', label: 'Svelte' },
  ],
})

const useTs = await confirm({ message: '使用 TypeScript？' })

outro('搞定，开始创建项目')

@clack/prompts 的几个关键设计：

  • intro / outro 用来框住整个交互流程的开始和结束，视觉上更连贯；
  • 每个 prompt 取消时返回一个 symbol，要用 isCancel() 判断，再用 cancel() 输出统一的取消提示。这比 prompts 的「静默返回部分结果」更不容易出错；
  • 内置 spinner，不用再单独装 ora。

如果嫌每个 prompt 都判 isCancel 麻烦，clack 提供了 group 把一组问题打包，并用一个统一的 onCancel 处理取消：

import { group, text, select, confirm, cancel } from '@clack/prompts'

const project = await group(
  {
    name: () => text({ message: '项目名称？' }),
    framework: () =>
      select({
        message: '框架？',
        options: [
          { value: 'vue', label: 'Vue' },
          { value: 'react', label: 'React' },
        ],
      }),
    useTs: () => confirm({ message: '使用 TypeScript？' }),
  },
  {
    onCancel: () => {
      cancel('操作已取消')
      process.exit(0)
    },
  },
)

console.log(project) // { name, framework, useTs }

prompts vs clack 怎么选

维度 prompts @clack/prompts
默认样式 朴素 精致（带边框连线）
取消处理 静默返回部分结果，需自己防御 isCancel 显式判断，更安全
spinner 需配合 ora 内置
体积 很小 小
风格 一次性传问题数组 逐个 await 或 group

我的判断：

  1. 想要现代、好看、取消处理省心：选 @clack/prompts，新工具我现在默认用它。
  2. 极致轻量、或已有 prompts 代码：prompts 也完全够用，注意处理取消即可。

ora：让长任务有 loading 反馈

交互拿到答案后，往往要执行耗时操作：装依赖、拉模板、初始化 git。这时候终端干等着没反应，用户会以为卡死了。ora 提供转圈 loading 动画。

npm i ora

import ora from 'ora'

const spinner = ora('正在安装依赖...').start()

try {
  await installDeps() // 你的耗时操作
  spinner.succeed('依赖安装完成')
} catch (err) {
  spinner.fail('依赖安装失败')
  throw err
}

ora 的常用方法：start() 开始转圈、succeed() 变成成功的对勾、fail() 变成失败的叉、stop() 直接停。中途还能改文案 spinner.text = '...'。

如果你用的是 @clack/prompts，它自带 spinner，就不用额外引 ora：

import { spinner } from '@clack/prompts'

const s = spinner()
s.start('正在安装依赖')
await installDeps()
s.stop('依赖安装完成')

彩色输出：kolorist 与 picocolors

最后是颜色。红色报错、绿色成功、灰色次要信息，能极大提升日志可读性。早年大家用 chalk，现在更轻量的选择是 picocolors 和 kolorist。

picocolors（极小、API 是函数链）：

import pc from 'picocolors'

console.log(pc.green('✔ 创建成功'))
console.log(pc.red('✖ 出错了'))
console.log(pc.dim('提示：可以用 --help 查看用法'))
console.log(pc.bold(pc.cyan('mycli')))

kolorist（按需导入具名函数，Vite 系常用）：

import { green, red, dim, bold, cyan } from 'kolorist'

console.log(green('✔ 创建成功'))
console.log(red('✖ 出错了'))
console.log(`${bold(cyan('mycli'))} ${dim('v1.0.0')}`)

两者都很小、都够用，区别只是导入风格。chalk 功能也强，但新版是 ESM-only 且体积相对大，纯做颜色的话 picocolors / kolorist 更轻。

一个体验细节：颜色和 emoji 不要滥用。终端日志的核心是「让人快速看懂状态」，红绿区分成功失败、灰色弱化次要信息，就已经够专业了。满屏花花绿绿反而干扰阅读。

一个串起来的小例子

把交互、loading、颜色串成一个迷你「创建项目」流程：

import { intro, outro, text, confirm, spinner, isCancel, cancel } from '@clack/prompts'
import { green, dim } from 'kolorist'

intro('create-my-app')

const name = await text({ message: '项目名称？', placeholder: 'my-app' })
if (isCancel(name)) {
  cancel('已取消')
  process.exit(0)
}

const install = await confirm({ message: '现在安装依赖？' })

const s = spinner()
s.start('正在创建项目')
await new Promise((r) => setTimeout(r, 800)) // 模拟生成文件
s.stop('项目文件已生成')

if (install) {
  const s2 = spinner()
  s2.start('正在安装依赖')
  await new Promise((r) => setTimeout(r, 1200)) // 模拟装依赖
  s2.stop('依赖安装完成')
}

outro(green(`完成！`) + dim(` cd ${name} && npm run dev`))

跑起来你会发现，这已经和 npm create vite 的体验很接近了。脚手架的「专业感」很大程度就来自这套交互 + loading + 颜色的组合。

小结

  1. 参数式适合自动化，交互式适合引导，成熟工具两者都支持：有参数用参数，缺的再问。
  2. prompts 轻量经典，但取消时静默返回部分结果，必须用 onCancel 或判空防御。
  3. @clack/prompts 样式现代、用 isCancel 显式处理取消、自带 spinner，是我现在的默认选择。
  4. clack 的 group 能把一组问题打包并统一处理取消，省去逐个判断。
  5. ora 给长任务加 loading 动画，start/succeed/fail 反馈状态；用 clack 则直接用内置 spinner。
  6. 彩色输出用轻量的 picocolors 或 kolorist，红绿区分成败即可，不要滥用颜色和 emoji。
