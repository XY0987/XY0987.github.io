CLI 参数解析：commander、yargs 与 cac 对比

发表于2026|更新于2026|工程化
|字数总计:2.7k|阅读时长:10分钟

前言：上一篇我们用 process.argv.slice(2) 拿到了原始参数，也提到裸解析参数很痛苦。这一篇就把参数解析这件事讲透：为什么不要手写、commander/yargs/cac 三个主流库各自什么风格、命令和选项怎么设计、最后怎么选。

为什么不要手写参数解析

上一篇我们已经知道，CLI 参数本质上都来自 process.argv.slice(2)。比如：

mycli create my-app --template vue -f --port 3000
mycli build --watch
mycli --help
mycli --version

拿到的原始数组大概是这样：

const args = ['create', 'my-app', '--template', 'vue', '-f', '--port', '3000']

如果只是做一个内部脚本，完全可以先手写一个最小版解析器：

function parseArgs(args) {
  const result = {
    command: args[0],
    positionals: [],
    options: {}
  }

  for (let i = 1; i < args.length; i++) {
    const arg = args[i]

    if (arg.startsWith('--')) {
      const [key, value] = arg.slice(2).split('=')

      if (value !== undefined) {
        result.options[key] = value
      } else if (args[i + 1] && !args[i + 1].startsWith('-')) {
        result.options[key] = args[i + 1]
        i++
      } else {
        result.options[key] = true
      }
    } else if (arg.startsWith('-')) {
      result.options[arg.slice(1)] = true
    } else {
      result.positionals.push(arg)
    }
  }

  return result
}

console.log(parseArgs(process.argv.slice(2)))

运行一下：

node cli.js create my-app --template vue -f --port 3000

输出大概是：

{
  command: 'create',
  positionals: ['my-app'],
  options: {
    template: 'vue',
    f: true,
    port: '3000'
  }
}

这个版本已经能处理 --template vue、--port=3000、-f 这些常见写法。到这里你会发现，参数解析的底层原理并不神秘：无非就是遍历字符串数组，把命令、位置参数和选项拆出来。

但问题也很快来了。一个稍微正经的 CLI，要正确处理这些细节：

  1. 区分命令（create、build）和选项（--template）；
  2. 选项的两种写法 --port 3000 和 --port=3000；
  3. 短选项 -f 以及合并写法 -rf；
  4. 布尔选项（--watch 不带值）和带值选项的区别；
  5. 必填参数校验、默认值；
  6. 自动生成 --help 和 --version。

这些全是重复且容易出错的逻辑。手写解析适合用来理解原理，或者应付非常简单的内部脚本；一旦要做给别人用的 CLI，我的建议就很直接：参数解析交给成熟的第三方库。下面三个是当前最主流的选择。

commander：最广泛使用的方案

commander 是 Node 生态里最老牌、用得最广的参数解析库，Vue CLI、很多大型工具都用它。风格是链式 + 声明式。

npm i commander

// bin/index.js
#!/usr/bin/env node
import { Command } from 'commander'

const program = new Command()

program
  .name('mycli')
  .description('一个示例脚手架')
  .version('1.0.0')

program
  .command('create <project-name>')      // <> 表示必填参数
  .description('创建一个新项目')
  .option('-t, --template <name>', '模板名称', 'vue') // 第三个参数是默认值
  .option('-f, --force', '目标目录存在时强制覆盖')
  .action((projectName, options) => {
    console.log('项目名:', projectName)
    console.log('模板:', options.template)
    console.log('强制覆盖:', !!options.force)
  })

program.parse()

跑一下：

node bin/index.js create my-app --template react -f
# 项目名: my-app
# 模板: react
# 强制覆盖: true

commander 的特点：

  • API 稳定、文档全、遇到问题搜得到答案；
  • <arg> 是必填参数，[arg] 是可选参数，option 里 <value> 表示该选项需要带值；
  • 自动生成 --help 和 --version，不用手写。

它的缺点是相对「重」一点，但对绝大多数工具来说完全够用，也最不容易踩坑。

cac：轻量、零依赖

cac 的定位是轻量、零依赖、单文件，Vite、unocss 等 UnJS/Vite 生态项目用得多。它的 API 和 commander 很像，但更简洁。

npm i cac

#!/usr/bin/env node
import cac from 'cac'

const cli = cac('mycli')

cli
  .command('create <project-name>', '创建一个新项目')
  .option('-t, --template <name>', '模板名称', { default: 'vue' })
  .option('-f, --force', '目标目录存在时强制覆盖')
  .action((projectName, options) => {
    console.log('项目名:', projectName)
    console.log('模板:', options.template)
    console.log('强制覆盖:', !!options.force)
  })

cli.help()        // 启用 -h / --help
cli.version('1.0.0') // 启用 -v / --version
cli.parse()

跑法和上面一样。cac 官方说核心就 4 个 API：cli.option、cli.version、cli.help、cli.parse，确实非常好上手。

几个细节：

  • 选项默认值写在第三个参数的 { default: 'vue' } 里，这点和 commander 不同；
  • cli.help() 和 cli.version() 要显式调用才会启用对应能力；
  • 零依赖，对追求体积、不想引入大依赖树的工具很友好。

yargs：功能最全、最重

yargs 是功能最全的一个，校验、命令组织、中间件、自动补全都有，适合复杂 CLI。代价是 API 更繁、体积更大。

npm i yargs

#!/usr/bin/env node
import yargs from 'yargs'
import { hideBin } from 'yargs/helpers'

yargs(hideBin(process.argv))
  .scriptName('mycli')
  .command(
    'create <projectName>',
    '创建一个新项目',
    (y) =>
      y
        .positional('projectName', { describe: '项目名', type: 'string' })
        .option('template', {
          alias: 't',
          describe: '模板名称',
          default: 'vue',
          type: 'string',
        })
        .option('force', { alias: 'f', type: 'boolean' }),
    (argv) => {
      console.log('项目名:', argv.projectName)
      console.log('模板:', argv.template)
      console.log('强制覆盖:', !!argv.force)
    },
  )
  .help()
  .parse()

注意 hideBin(process.argv) 这个细节：它帮你去掉前两个（node 路径、脚本路径），等价于 process.argv.slice(2)，是 yargs 的标准写法。

yargs 的命令定义把「参数声明」和「处理函数」分开写，结构清晰但啰嗦。它的强项是内置的参数校验和类型系统，如果你的 CLI 选项特别多、校验逻辑复杂，yargs 能省不少事。

三者对比与选型

维度 commander cac yargs
风格 链式声明 链式声明，更简洁 配置式，最详细
依赖 少 零依赖 较多
体积 中 小 大
学习成本 低 最低 中高
内置校验 基础 基础 强
生态典型 Vue CLI 等 Vite/UnJS 系 复杂 CLI 工具

我的判断：

  1. 大多数工具、想稳：选 commander。文档最全、社区最大、出问题最好查。
  2. 追求轻量、Vite 风格项目：选 cac。零依赖、API 极简，体积敏感时首选。
  3. 选项极多、需要强校验：选 yargs。它的校验和类型系统在复杂场景能省事。

对刚开始做 CLI 的人，我建议直接上 commander 或 cac，不要纠结。三者都能完成同样的事，切换成本也不高。

多个命令与多级子命令

实际脚手架往往有多个顶层命令（create、add、info）。严格说，它们都是挂在 mycli 这个根命令下面的命令，不是 mycli project create 这种多级子命令。这里用 cac 写一个稍完整的骨架，体会一下结构：

#!/usr/bin/env node
import cac from 'cac'

const cli = cac('mycli')

cli
  .command('create <name>', '创建项目')
  .option('-t, --template <t>', '模板', { default: 'vue' })
  .action((name, options) => {
    console.log(`创建项目 ${name}，使用模板 ${options.template}`)
  })

cli
  .command('add <plugin>', '为项目添加插件')
  .action((plugin) => {
    console.log(`添加插件 ${plugin}`)
  })

cli
  .command('info', '打印环境信息')
  .action(() => {
    console.log('Node 版本:', process.version)
    console.log('平台:', process.platform)
  })

// 没有匹配到任何命令时，输出帮助
cli.command('').action(() => cli.outputHelp())

cli.help()
cli.version('1.0.0')
cli.parse()

node bin/index.js create my-app -t react
node bin/index.js add router
node bin/index.js info
node bin/index.js --help

真正的多级子命令，通常是把一组相关能力收在同一个命令空间下面，比如：

mycli project create my-app
mycli project list
mycli plugin add router

这种结构的重点不只是命令变长了，而是 help 也要分层：mycli --help 只展示 project、plugin 这种顶层命令组；输入 mycli project --help 时，才展示 create、list 这些子命令以及它们自己的参数。

用 commander 写这种层级会更直观，因为它的 Command 可以继续挂子命令：

#!/usr/bin/env node
import { Command } from 'commander'

const program = new Command()

program
  .name('mycli')
  .description('一个示例脚手架')
  .version('1.0.0')

const project = program
  .command('project')
  .description('项目相关命令')

project
  .command('create <name>')
  .description('创建项目')
  .option('-t, --template <t>', '模板', 'vue')
  .action((name, options) => {
    console.log(`创建项目 ${name}，使用模板 ${options.template}`)
  })

project
  .command('list')
  .description('查看项目列表')
  .action(() => {
    console.log('项目列表')
  })

program.parse()

对应的 help 入口是分层的：

node bin/index.js --help
# 这里能看到 project 这个顶层命令组

node bin/index.js project --help
# 这里才会看到 create、list 这些子命令

node bin/index.js project create my-app -t react

cac 文档里说的 subcommands，更接近 mycli create、mycli build 这种单层的 git-like 命令。它没有像 commander 这样显式的命令树 API。如果想在 cac 里做 project create 这种多级结构，一般要把 project 当成一个命令，再在它的 action 里自己解析后续参数，或者拆成多个 CLI 实例手动分发。能做，但分层 help 就需要自己补，不如 commander 直接。

我的理解是：顶层命令适合数量少、语义很清晰的工具，比如 create、build、info；多级子命令适合能力越来越多之后做分组，比如 project create、project list、plugin add。否则所有命令都堆在第一层，CLI 会越来越像一个没有目录的文件夹。

坑点：命令的位置参数顺序和必填/可选标记要和 action 回调的形参对应。create <name> 的 name 会作为 action 的第一个参数传入，最后一个参数永远是解析出来的 options 对象。如果发现 options 拿到的是字符串而不是对象，多半是形参错位了。

小结

  1. 不要手写参数解析，命令/选项/help/校验这些重复逻辑交给库。
  2. commander 最主流、最稳，文档社区最全，是通用首选。
  3. cac 零依赖、API 极简（只有 4 个核心方法），适合轻量和 Vite 风格项目。
  4. yargs 功能最全、校验最强，适合选项多、校验复杂的大型 CLI，代价是更重。
  5. 三者都支持常规命令、选项、默认值、自动 help；如果需要真正的多级命令树和分层 help，commander 或 yargs 更合适。
  6. action 回调里，位置参数按声明顺序传入，最后一个参数固定是 options 对象。
