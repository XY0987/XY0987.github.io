Vue 3 baseHandlers 源码解析：get 和 set 如何连接 track 与 trigger

发表于2026|更新于2026|Vue框架及周边库
|字数总计:3.8k|阅读时长:15分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：上一篇看了 reactive 如何创建 Proxy。这一篇继续往下走，看普通对象和数组的代理拦截器 baseHandlers。我的理解是，baseHandlers 是响应式系统真正“接管对象读写”的地方：读属性时连接 track，写属性时连接 trigger。

先给结论

baseHandlers.ts 主要处理四类代理行为：

拦截器 对应操作 核心动作
get state.foo 读取属性、收集 GET 依赖、处理 ref 解包和深层懒代理
set state.foo = 1 判断新增还是修改，触发 ADD 或 SET 更新
deleteProperty delete state.foo 删除成功后触发 DELETE 更新
has / ownKeys 'foo' in state / Object.keys(state) 收集 HAS 或 ITERATE 类型依赖

如果把 reactive.ts 理解为“创建代理对象”，那 baseHandlers.ts 就是“代理对象具体怎么工作”。

一张图看懂 baseHandlers 的位置

reactive(obj)
  │
  ▼
new Proxy(obj, mutableHandlers)
  │
  ├─ get  ─────────► track(target, GET, key)
  │                    │
  │                    └─ 记录当前 active effect
  │
  ├─ set  ─────────► trigger(target, ADD/SET, key)
  │                    │
  │                    └─ 找到依赖并重新调度 effect
  │
  ├─ deleteProperty ─► trigger(target, DELETE, key)
  │
  ├─ has ───────────► track(target, HAS, key)
  │
  └─ ownKeys ───────► track(target, ITERATE, ITERATE_KEY)

这也是 Vue 响应式系统的核心闭环：

  1. effect 执行时读取响应式属性。
  2. get 拦截读取，调用 track 记录依赖。
  3. 后续修改属性。
  4. set 拦截写入，调用 trigger 找到依赖。
  5. 对应 effect 重新执行。

get：读取属性时发生了什么

get 是整个 handler 里最重要的函数。它不只是返回属性值，还顺手完成内部标记读取、数组方法增强、依赖收集、ref 解包和深层懒代理。

  get(target: Target, key: string | symbol, receiver: object): any {
    if (key === ReactiveFlags.SKIP) return target[ReactiveFlags.SKIP]

    const isReadonly = this._isReadonly,
      isShallow = this._isShallow

    // 1. 先处理 Vue 内部标记字段。
    // 这些读取用于 isReactive/isReadonly/isShallow/toRaw 等工具函数，
    // 只返回代理状态，不应该进入普通属性读取和依赖收集流程。
    if (key === ReactiveFlags.IS_REACTIVE) {
      return !isReadonly
    } else if (key === ReactiveFlags.IS_READONLY) {
      return isReadonly
    } else if (key === ReactiveFlags.IS_SHALLOW) {
      return isShallow
    } else if (key === ReactiveFlags.RAW) {
      if (
        receiver ===
          (isReadonly
            ? isShallow
              ? shallowReadonlyMap
              : readonlyMap
            : isShallow
              ? shallowReactiveMap
              : reactiveMap
          ).get(target) ||
        // receiver is not the reactive proxy, but has the same prototype
        // this means the receiver is a user proxy of the reactive proxy
        Object.getPrototypeOf(target) === Object.getPrototypeOf(receiver)
      ) {
        return target
      }
      // early return undefined
      return
    }

    const targetIsArray = isArray(target)

    if (!isReadonly) {
      let fn: Function | undefined
      // 2. 数组的一些方法需要特殊改写。
      // 例如 includes/indexOf 需要兼容原始对象与代理对象，push/pop 等会暂停依赖追踪，避免 length 递归触发。
      if (targetIsArray && (fn = arrayInstrumentations[key])) {
        return fn
      }
      if (key === 'hasOwnProperty') {
        return hasOwnProperty
      }
    }

    // 3. 真正读取属性值。Reflect.get 保留了 getter 中 this 指向 receiver 的语义。
    const res = Reflect.get(
      target,
      key,
      // if this is a proxy wrapping a ref, return methods using the raw ref
      // as receiver so that we don't have to call `toRaw` on the ref in all
      // its class methods
      isRef(target) ? target : receiver,
    )

    // 4. 过滤不需要追踪的 key，避免无意义的依赖记录。
    if (isSymbol(key) ? builtInSymbols.has(key) : isNonTrackableKeys(key)) {
      return res
    }

    // 5. 非 readonly 读取才需要收集依赖；readonly 只做只读保护，不建立更新关系。
    if (!isReadonly) {
      track(target, TrackOpTypes.GET, key)
    }

    // 6. shallow 模式只代理第一层，直接返回原始属性值。
    if (isShallow) {
      return res
    }

    if (isRef(res)) {
      // ref unwrapping - skip unwrap for Array + integer key.
      // 普通对象属性上的 ref 会自动解包；数组按索引访问时不解包，避免破坏数组元素的一致性。
      return targetIsArray && isIntegerKey(key) ? res : res.value
    }

    if (isObject(res)) {
      // 7. 深层响应式是“懒代理”：只有读取到嵌套对象时，才继续转成 reactive/readonly。
      // 这样避免初始化时递归遍历整棵对象树。
      return isReadonly ? readonly(res) : reactive(res)
    }

    return res
  }

我把 get 拆成七步：

步骤 目的
处理内部标记 支持 isReactive、isReadonly、toRaw 等工具函数
数组方法增强 修正数组方法在代理对象下的行为
Reflect.get 保持原生 getter 和原型链语义
过滤不追踪 key 避免内部字段和内建 Symbol 污染依赖
调用 track 把当前正在执行的 effect 记录到当前属性上
shallow 判断 浅层响应式不继续处理嵌套值
ref 解包 / 懒代理 普通对象属性自动解包 ref，嵌套对象按需转代理

这里最核心的一句是：

    // 5. 非 readonly 读取才需要收集依赖；readonly 只做只读保护，不建立更新关系。
    if (!isReadonly) {
      track(target, TrackOpTypes.GET, key)
    }

只要在 effect 里读取了 state.count，就会走到这里，最终把当前正在运行的 effect 和 target.count 建立关系。

为什么 readonly 不收集 GET 依赖

get 中有一个判断：只有 !isReadonly 时才调用 track。

这看起来可能有点反直觉：readonly(reactive(obj)) 读取时不是也能响应变化吗？关键在于它的内部结构。

readonly(reactive(obj)) 是在 reactive 代理外面再包一层 readonly 代理。读取 readonly 外层时，最终仍会读到内层 reactive 代理，所以依赖收集发生在内层 reactive 的 get 上。readonly 自己只负责只读语义，不重复建立依赖关系。

我的理解是，这样可以避免 readonly 层制造额外依赖，让“状态变化”和“只读保护”两个职责保持分离。

数组为什么要特殊处理

数组比普通对象复杂，主要有两个问题。

第一个问题是身份比较。比如数组里存的是原始对象，但你用代理对象去 includes，也应该尽量得到符合直觉的结果。

  includes(...args: unknown[]) {
    return searchProxy(this, 'includes', args)
  },

  indexOf(...args: unknown[]) {
    return searchProxy(this, 'indexOf', args)
  },

  join(separator?: string) {
    return reactiveReadArray(this).join(separator)
  },

  // keys() iterator only reads `length`, no optimization required

  lastIndexOf(...args: unknown[]) {
    return searchProxy(this, 'lastIndexOf', args)
  },

searchProxy 会先用原参数查一次，查不到时再把代理参数转成原始值查一次：

// instrument identity-sensitive methods to account for reactive proxies
function searchProxy(
  self: unknown[],
  method: keyof Array<any>,
  args: unknown[],
) {
  const arr = toRaw(self) as any
  track(arr, TrackOpTypes.ITERATE, ARRAY_ITERATE_KEY)
  // we run the method using the original args first (which may be reactive)
  const res = arr[method](...args)

  // if that didn't work, run it again using raw values.
  if ((res === -1 || res === false) && isProxy(args[0])) {
    args[0] = toRaw(args[0])
    return arr[method](...args)
  }

  return res
}

第二个问题是 length。像 push、pop、splice 这类方法会读写 length，如果在操作过程中错误地追踪了 length，容易造成不必要的重复触发，甚至递归循环。

// instrument length-altering mutation methods to avoid length being tracked
// which leads to infinite loops in some cases (#2137)
function noTracking(
  self: unknown[],
  method: keyof Array<any>,
  args: unknown[] = [],
) {
  pauseTracking()
  startBatch()
  const res = (toRaw(self) as any)[method].apply(self, args)
  endBatch()
  resetTracking()
  return res
}

所以 baseHandlers 在 get 阶段会优先返回增强后的数组方法：

    if (!isReadonly) {
      let fn: Function | undefined
      // 2. 数组的一些方法需要特殊改写。
      // 例如 includes/indexOf 需要兼容原始对象与代理对象，push/pop 等会暂停依赖追踪，避免 length 递归触发。
      if (targetIsArray && (fn = arrayInstrumentations[key])) {
        return fn
      }
      if (key === 'hasOwnProperty') {
        return hasOwnProperty
      }
    }

这就是为什么数组在响应式系统里经常需要单独处理：数组既是对象，又有很多会隐式读写索引和 length 的内建方法。

ref 解包和深层懒代理

get 还有两个很重要的行为：ref 自动解包和嵌套对象懒代理。

    if (isRef(res)) {
      // ref unwrapping - skip unwrap for Array + integer key.
      // 普通对象属性上的 ref 会自动解包；数组按索引访问时不解包，避免破坏数组元素的一致性。
      return targetIsArray && isIntegerKey(key) ? res : res.value
    }

    if (isObject(res)) {
      // 7. 深层响应式是“懒代理”：只有读取到嵌套对象时，才继续转成 reactive/readonly。
      // 这样避免初始化时递归遍历整棵对象树。
      return isReadonly ? readonly(res) : reactive(res)
    }

看一个例子：

const state = reactive({
  count: ref(1),
  nested: { foo: 1 },
})

state.count // 1，普通对象属性上的 ref 会自动解包
state.nested // 读取到 nested 时，nested 才会被转成 reactive

这里的设计很实用：

  • 对普通对象来说，state.count 比 state.count.value 更符合直觉。
  • 对数组来说，arr[0] 如果是 ref，不自动解包，避免数组元素类型不稳定。
  • 对嵌套对象来说，只有访问到才代理，避免初始化时深度递归。

set：写属性时如何触发更新

看完 get，再看 set。如果说 get 负责 track，那 set 就负责 trigger。

  set(
    target: Record<string | symbol, unknown>,
    key: string | symbol,
    value: unknown,
    receiver: object,
  ): boolean {
    let oldValue = target[key]
    if (!this._isShallow) {
      const isOldValueReadonly = isReadonly(oldValue)
      if (!isShallow(value) && !isReadonly(value)) {
        // 深层响应式下比较新旧值时使用原始对象，避免代理对象与原始对象混用导致误判。
        oldValue = toRaw(oldValue)
        value = toRaw(value)
      }
      // 普通对象属性原本是 ref，且新值不是 ref 时，不替换整个 ref，
      // 而是写入 oldValue.value。这就是 reactive 对象里 ref 属性可以直接赋值的原因。
      // 数组索引上的 ref 不做这个解包赋值，保持数组元素语义稳定。
      if (!isArray(target) && isRef(oldValue) && !isRef(value)) {
        if (isOldValueReadonly) {
          if (__DEV__) {
            warn(
              `Set operation on key "${String(key)}" failed: target is readonly.`,
              target[key],
            )
          }
          return true
        } else {
          oldValue.value = value
          return true
        }
      }
    } else {
      // in shallow mode, objects are set as-is regardless of reactive or not
    }

    // 区分新增属性和修改已有属性，后续会触发不同类型的依赖。
    // 对数组来说，超过当前 length 的整数 key 才算新增索引。
    const hadKey =
      isArray(target) && isIntegerKey(key)
        ? Number(key) < target.length
        : hasOwn(target, key)
    const result = Reflect.set(
      target,
      key,
      value,
      isRef(target) ? target : receiver,
    )
    // don't trigger if target is something up in the prototype chain of original
    // 只在 receiver 对应的原始对象就是当前 target 时触发，避免原型链上的 setter 造成重复触发。
    if (target === toRaw(receiver)) {
      if (!hadKey) {
        trigger(target, TriggerOpTypes.ADD, key, value)
      } else if (hasChanged(value, oldValue)) {
        trigger(target, TriggerOpTypes.SET, key, value, oldValue)
      }
    }
    return result
  }

这段逻辑重点有三个。

第一，比较新旧值时会尽量转成原始对象。这样可以避免代理对象和原始对象混在一起导致 hasChanged 判断不准确。

第二，普通对象属性里如果原本是 ref，新值不是 ref，会写到 oldValue.value 上，而不是替换整个 ref。

const state = reactive({ count: ref(1) })

state.count = 2
// 等价于：内部写 oldValue.value = 2

第三，Vue 会区分新增和修改：

场景 触发类型
原来没有这个 key TriggerOpTypes.ADD
原来有这个 key，且值变化了 TriggerOpTypes.SET
原来有这个 key，但值没变 不触发

这个区分会影响后续 trigger 到底要通知哪些依赖。比如新增属性不仅影响这个属性本身，还可能影响 Object.keys、for...in 这类依赖“键集合”的逻辑。

delete、in 和 Object.keys 也要响应式

响应式不只关心 state.foo 和 state.foo = 1，还要关心删除、判断属性是否存在、枚举 key。

  deleteProperty(
    target: Record<string | symbol, unknown>,
    key: string | symbol,
  ): boolean {
    // 只有删除真实存在的属性并且删除成功，才需要通知依赖。
    const hadKey = hasOwn(target, key)
    const oldValue = target[key]
    const result = Reflect.deleteProperty(target, key)
    if (result && hadKey) {
      trigger(target, TriggerOpTypes.DELETE, key, undefined, oldValue)
    }
    return result
  }

  has(target: Record<string | symbol, unknown>, key: string | symbol): boolean {
    // `key in proxy` 会进入 has 拦截，需要收集 HAS 类型依赖。
    // 后续新增/删除这个 key 时，依赖该判断的 effect 才会更新。
    const result = Reflect.has(target, key)
    if (!isSymbol(key) || !builtInSymbols.has(key)) {
      track(target, TrackOpTypes.HAS, key)
    }
    return result
  }

  ownKeys(target: Record<string | symbol, unknown>): (string | symbol)[] {
    // Object.keys/for...in 等枚举操作依赖的是“键集合”。
    // 对数组来说键集合变化通常体现为 length 变化；普通对象则使用 ITERATE_KEY 作为统一依赖 key。
    track(
      target,
      TrackOpTypes.ITERATE,
      isArray(target) ? 'length' : ITERATE_KEY,
    )
    return Reflect.ownKeys(target)
  }

举个例子：

const state = reactive({ foo: 1 })

effect(() => {
  console.log('foo' in state)
})

delete state.foo

这里 effect 里不是读取 state.foo，而是在判断 'foo' in state。所以它收集的是 HAS 类型依赖，删除属性时触发 DELETE，最终这个 effect 也应该重新执行。

再看枚举：

const state = reactive({ foo: 1 })

effect(() => {
  console.log(Object.keys(state))
})

state.bar = 2

Object.keys(state) 依赖的是整个 key 集合，不是某个具体 key。所以它会通过 ownKeys 收集 ITERATE 类型依赖。新增 bar 时触发 ADD，后续 trigger 会额外通知 ITERATE_KEY 对应的依赖。

trigger 里的处理可以看到这一点：

      // also run for iteration key on ADD | DELETE | Map.SET
      switch (type) {
        case TriggerOpTypes.ADD:
          if (!targetIsArray) {
            run(depsMap.get(ITERATE_KEY))
            if (isMap(target)) {
              run(depsMap.get(MAP_KEY_ITERATE_KEY))
            }
          } else if (isArrayIndex) {
            // new index added to array -> length changes
            run(depsMap.get('length'))
          }
          break
        case TriggerOpTypes.DELETE:
          if (!targetIsArray) {
            run(depsMap.get(ITERATE_KEY))
            if (isMap(target)) {
              run(depsMap.get(MAP_KEY_ITERATE_KEY))
            }
          }
          break
        case TriggerOpTypes.SET:
          if (isMap(target)) {
            run(depsMap.get(ITERATE_KEY))
          }
          break
      }

这也是为什么 Vue 要区分 GET、HAS、ITERATE、ADD、SET、DELETE：不同操作影响的依赖范围不同。

readonly handler 做了什么

readonly 的读逻辑复用 BaseReactiveHandler.get，但写和删除会被拦截。

class ReadonlyReactiveHandler extends BaseReactiveHandler {
  constructor(isShallow = false) {
    super(true, isShallow)
  }

  set(target: object, key: string | symbol) {
    // readonly 代理允许读取并参与依赖追踪，但写入会被拦截。
    // 这里返回 true 是为了避免严格模式下抛出 TypeError，同时在开发环境给出警告。
    if (__DEV__) {
      warn(
        `Set operation on key "${String(key)}" failed: target is readonly.`,
        target,
      )
    }
    return true
  }

  deleteProperty(target: object, key: string | symbol) {
    // readonly 对删除属性也只告警不执行，保持只读语义。
    if (__DEV__) {
      warn(
        `Delete operation on key "${String(key)}" failed: target is readonly.`,
        target,
      )
    }
    return true
  }
}

这里有一个细节：set 和 deleteProperty 返回的是 true。这不是说写入成功了，而是告诉 JavaScript 引擎“代理拦截器执行完成”。开发环境下 Vue 会给出警告，生产环境下则静默阻止写入。

四组 handler 对应四种响应式模式

最后看导出：

// 四组 handler 对应 reactive.ts 中的四个 WeakMap 缓存：
// mutable/readonly 决定能否写入，shallow 决定是否只处理第一层。
export const mutableHandlers: ProxyHandler<object> =
  /*@__PURE__*/ new MutableReactiveHandler()

export const readonlyHandlers: ProxyHandler<object> =
  /*@__PURE__*/ new ReadonlyReactiveHandler()

export const shallowReactiveHandlers: MutableReactiveHandler =
  /*@__PURE__*/ new MutableReactiveHandler(true)

// Props handlers are special in the sense that it should not unwrap top-level
// refs (in order to allow refs to be explicitly passed down), but should
// retain the reactivity of the normal readonly object.
export const shallowReadonlyHandlers: ReadonlyReactiveHandler =
  /*@__PURE__*/ new ReadonlyReactiveHandler(true)

它们刚好对应上一篇里 reactive.ts 的四类入口：

API handler 特点
reactive mutableHandlers 深层响应式，可写
readonly readonlyHandlers 深层只读，不可写
shallowReactive shallowReactiveHandlers 仅第一层响应式，可写
shallowReadonly shallowReadonlyHandlers 仅第一层只读，不可写

所以 reactive.ts 和 baseHandlers.ts 是配套看的：前者负责选择 handler，后者负责具体拦截行为。

小结

  1. baseHandlers 是普通对象和数组响应式代理的核心拦截器。
  2. get 负责读取属性、收集 GET 依赖、处理数组增强、ref 解包和深层懒代理。
  3. set 负责判断新增还是修改，并触发 ADD 或 SET 更新。
  4. deleteProperty、has、ownKeys 分别覆盖删除、属性存在性判断和 key 枚举场景。
  5. Vue 区分多种追踪和触发类型，是为了精确通知真正受影响的 effect。

读完 baseHandlers.ts 后，下一步就可以进入 dep.ts。因为 baseHandlers 只是调用了 track 和 trigger，而依赖到底怎么存、怎么找、怎么批量通知，答案都在 dep.ts 和 effect.ts 里。
