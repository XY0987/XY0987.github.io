package exports 条件导出与双包陷阱

发表于2026|更新于2026|工程化
|字数总计:2.8k|阅读时长:11分钟

前言：exports 是现代 npm 包设计里非常关键的字段。它能让包入口更清晰，也能限制外部访问内部文件。但如果 ESM/CJS 双产物设计不好，就容易踩到 Dual Package Hazard，也就是双包陷阱。

main、module、exports 各自解决什么

main

main 是传统 Node.js 入口：

{
  "main": "./dist/index.cjs"
}

它表达的是：当用户 require('pkg') 时，默认加载哪个文件。

缺点是只能描述一个主入口，没法很好表达子路径和不同环境。

module

module 常被打包工具当作 ESM 入口：

{
  "module": "./dist/index.js"
}

但它不是 Node.js 官方包入口标准字段。很多库以前会同时写：

{
  "main": "./dist/index.cjs",
  "module": "./dist/index.js"
}

这能照顾部分打包工具，但语义不够精确。

exports

exports 是现代入口声明方式：

{
  "exports": {
    ".": "./dist/index.js",
    "./package.json": "./package.json"
  }
}

它的价值有三个：

  1. 明确公共 API；
  2. 支持子路径导出；
  3. 支持条件导出。

Node.js 官方文档明确说明：如果同时存在 exports 和 main，exports 优先级更高。

exports 会封住未声明的内部路径

以前用户可能这样导入：

import util from 'some-pkg/dist/internal/util.js'

如果包新增：

{
  "exports": {
    ".": "./dist/index.js"
  }
}

这个内部路径就不能再被访问，可能报：

ERR_PACKAGE_PATH_NOT_EXPORTED

所以给已有包新增 exports 可能是破坏性变更。库作者要谨慎，最好把过去被用户依赖的公开路径都补进去。

{
  "exports": {
    ".": "./dist/index.js",
    "./utils": "./dist/utils.js"
  }
}

条件导出怎么写

条件导出允许根据使用方式或运行环境返回不同文件。

{
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs",
      "default": "./dist/index.js"
    }
  }
}

含义大概是：

条件 加载文件
types TypeScript 类型入口
import ESM 方式加载
require CJS 方式加载
default 默认兜底

要注意：条件顺序是有意义的。一般更具体的条件放前面，default 放最后。

常见条件有哪些

Node.js 官方支持的常见条件包括：

条件 含义
node Node.js 环境
import 通过 import 或 import() 加载
require 通过 require() 加载
default 默认兜底

社区和工具链里还常见：

条件 含义 谁会识别
types TypeScript 类型系统使用 TypeScript
browser 浏览器环境入口 打包器（Vite / Webpack / Rollup 等）
development 开发环境入口 打包器
production 生产环境入口 打包器

这里要特别注意：browser / development / production 都不是 Node.js 默认识别的条件——它们由打包器实现，Node 原生解析时会直接跳过（除非显式传 node --conditions=development）。所以别以为把 production 写进 exports，node app.js 就会自动切到生产入口；这套「按环境切文件」的能力，通常只有在 Vite / Webpack 打包时才生效。真正被 Node 内置识别的只有 node、node-addons、import、require、default 这几个。

我建议 types 放在最前，default 放在最后。

{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "browser": "./dist/index.browser.js",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs",
      "default": "./dist/index.js"
    }
  }
}

子路径导出要保持风格统一

可以这样：

{
  "exports": {
    ".": "./dist/index.js",
    "./react": "./dist/react.js",
    "./vue": "./dist/vue.js"
  }
}

用户导入：

import { Button } from 'pkg/react'

也可以带扩展名：

{
  "exports": {
    "./react.js": "./dist/react.js"
  }
}

我的建议是：**选择一种风格并保持一致，不要同时暴露 ./react 和 ./react.js**。否则同一个模块可能有多个导入路径，长期维护会变乱。

什么是双包陷阱

双包陷阱，也就是 Dual Package Hazard，通常发生在一个包同时提供 ESM 和 CJS 两套入口时：

{
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}

看起来很完美：ESM 用户拿 ESM，CJS 用户拿 CJS。

问题是：如果同一个应用里，某些地方通过 import 加载这个包，另一些地方通过 require 加载这个包，Node.js 可能会加载两份不同模块实例。

import -> ./dist/index.js   -> 实例 A
require -> ./dist/index.cjs -> 实例 B

如果包里有状态，就麻烦了。

let count = 0

export function increase() {
  count += 1
  return count
}

ESM 和 CJS 各自维护一份 count，你以为是同一个包，实际上状态被拆成两份。

怎么规避双包陷阱

方案一：尽量让包无状态

最稳的方式是让包导出纯函数、类型、常量，不维护模块级可变状态。

export function add(a: number, b: number) {
  return a + b
}

无状态包即使被加载两份，风险也小很多。

方案二：只发布一种模块格式

如果用户群体允许，新包可以只发布 ESM：

{
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "default": "./dist/index.js"
    }
  }
}

这样最清晰，但老 CJS 项目使用成本会变高。

方案三：CJS 包装 ESM 或共享同一份实现

如果必须双产物，尽量让两种入口共享同一份核心实现，避免各自维护状态。

src/core.ts
  ├── dist/index.js   ESM 包装
  └── dist/index.cjs  CJS 包装

重点是不要在两个入口里分别初始化状态。

方案四：文档明确推荐一种导入方式

有时候工程上不能完全避免，但可以通过文档降低混用概率。

推荐在新项目中使用 ESM：

import { createClient } from 'pkg'

CommonJS 项目请使用：

const { createClient } = require('pkg')

types 要和入口对应

双产物包还要注意类型入口。

简单包可以：

{
  "types": "./dist/index.d.ts"
}

更推荐放到 exports：

{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}

如果有子路径，也要给子路径配类型：

{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./react": {
      "types": "./dist/react.d.ts",
      "import": "./dist/react.js"
    }
  }
}

我的包入口配置建议

应用项目

应用项目不发布给别人用，重点是运行稳定：

{
  "type": "module",
  "private": true
}

不需要复杂 exports。

内部工具库

如果团队 Node.js 环境比较新，可以优先 ESM：

{
  "type": "module",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "default": "./dist/index.js"
    }
  }
}

面向外部用户的库

要看用户群体。若必须兼容 CJS，再考虑双产物，但要认真处理双包陷阱。

Node 模块解析算法：一次 import 到底发生了什么

前面讲的 exports、条件导出、双包陷阱，本质都是在影响同一件事——Node.js 拿到一个模块标识符（specifier）后，怎么把它变成磁盘上的一个具体文件。这个过程叫模块解析（module resolution）。把它串成一条完整链路，前面的字段才不再是零散的知识点。

首先，Node 会根据 specifier 的形态分成三类：

import x from 'lodash'          → 裸标识符（bare specifier）→ 走 node_modules 查找
import x from './utils.js'      → 相对路径 → 相对当前文件解析
import x from '/abs/utils.js'   → 绝对路径 / file: URL → 直接定位

相对/绝对路径比较简单，重点是裸标识符的解析流程。以 import { debounce } from 'lodash-es/function' 为例，Node 大致这样走：

1. 拆分：包名 = lodash-es
2. 从当前文件所在目录开始，逐级向上找 node_modules：
   ./node_modules/lodash-es → ../node_modules/lodash-es → ... 一直到根
3. 找到这个包后，读它的 package.json
4. 有 "exports" 字段吗？
   ├─ 有：只认 exports 声明的路径。按当前场景匹配条件
   │      （import / require / node / types / default...），
   │      解析出目标文件；exports 没声明的子路径 → 直接拒绝
   └─ 没有：走传统解析——用 main / 子路径拼文件 / index.js，
          并按扩展名规则补全
5. 得到最终文件，按它的模块格式（ESM/CJS，见上一篇的判定规则）加载

这里有几个最容易踩坑、也最能体现前面字段作用的点：

  • exports 是一道「封闭闸门」。一旦包声明了 exports，就只有它显式列出的路径能被引入。哪怕 node_modules/pkg/internal/util.js 文件真实存在，import 'pkg/internal/util.js' 也会失败——这是设计如此，用来锁定包的公共 API。
  • ESM 下扩展名不会自动补全。CJS 里 require('./utils') 能自动试 .js/.json/index.js；但原生 ESM 里 import './utils' 必须写全 ./utils.js（这也是为什么很多 TS 项目要开 moduleResolution: "Bundler" 或写 .js 后缀）。
  • 条件匹配是「短路」的：按 exports 里声明的顺序，命中第一个匹配的条件就返回，所以 types 要放前面、default 放最后。

常见解析报错怎么读

解析失败时 Node 抛的错误码是有规律的，对着下面这张表基本能秒定位：

报错 含义 通常的修法
ERR_MODULE_NOT_FOUND 路径根本没找到（常见于 ESM 少写扩展名、或包没装） 补全 .js 后缀；确认依赖已安装
ERR_PACKAGE_PATH_NOT_EXPORTED 包有 exports，但你 import 的子路径没被声明 改用 exports 声明的公共路径；或给包提 issue 让它导出
ERR_UNSUPPORTED_DIR_IMPORT ESM 下 import 了一个目录（想吃 index.js 的老习惯） 写全到具体文件，或让包用 exports 声明目录入口
ERR_REQUIRE_ESM 用 require() 加载了纯 ESM 包 改用 import/动态 import()，或升级 Node 22+（已支持 require ESM）

记住一条排查主线：报错里只要出现 EXPORTED 字样，问题几乎一定在目标包的 exports 字段上（是封装限制，不是文件不存在）；出现 NOT_FOUND，才多半是路径/扩展名/依赖安装的问题。 区分这两类，能省掉大量瞎猜。

小结

  1. main 是传统单入口，module 常被打包工具使用，exports 是现代包入口声明方式。
  2. exports 会限制未声明路径访问，给老包新增时可能是破坏性变更。
  3. 条件导出可以区分 import、require、node、browser、types 等入口。
  4. 双包陷阱的核心风险是 ESM 和 CJS 加载出两份模块实例。
  5. 库项目要谨慎设计入口，优先保持无状态、入口清晰、类型声明完整。
  6. 模块解析算法把这些字段串起来：裸标识符逐级向上找 node_modules → 有 exports 就只认它声明的路径并按条件短路匹配，没有才走传统 main/index 解析；EXPORTS/NOT_FOUND 两类报错分别对应「封装限制」和「路径问题」。
