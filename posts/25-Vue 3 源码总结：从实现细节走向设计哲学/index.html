Vue 3 源码总结：从实现细节走向设计哲学

发表于2026|更新于2026|Vue框架及周边库
|字数总计:3.7k|阅读时长:12分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：源码读到最后，最值得沉淀的不是”哪个函数调了哪个函数”，而是”为什么 Vue 在这几条岔路上选了这一条，又付出了什么代价”。代码会变、版本会迭代、优化策略也会演进，但取舍和约束会留下来。这篇是整条主线的收尾，只讲取舍，不讲流程。

先给结论

读完一整条主线后，我对 Vue 3 设计哲学的判断不在”声明式”和”分层”这种通用词上——这些放到 React上也成立。Vue 真正独有的取舍是下面这几条：

  1. Vue 是渐进式框架：让用户自己决定要把多少能力交给框架，从 @vue/reactivity 到 SFC 是一条连续光谱。
  2. Vue 走的是编译器与运行时的中间路线：不是纯 VDOM，也不是纯编译；用 PatchFlags / Block Tree 让两者协作。
  3. Vue 把用户心智当作 API 的第一约束：.value、async update、SFC 这些”看起来更麻烦”的设计，都是在保护可预测性。
  4. Vue 给每条默认路径都留了逃生口：shallow、raw、createRenderer、独立 reactivity 包、render function。
  5. Vue 的每一个优化都有标价：响应式的代理代价、调度的同步直觉代价、SFC 的工具链代价。哲学的厚度来自取舍，不是来自正确。

一句话概括：

Vue 不追求”一种最好的实现”，而是在多条岔路之间走一条显式的中间路线，并把代价告诉你。

哲学一：渐进式不是口号，是一条连续光谱

很多框架都会自称”渐进式”，但 Vue 把这件事真正落实在了包结构上。同一套响应式能力，可以以四种深度被使用：

使用深度 入口 典型场景
只要响应式 @vue/reactivity 自建小框架、Node.js 中做依赖追踪
要响应式 + 渲染 @vue/runtime-core + 自定义 createRenderer Canvas/原生/小程序渲染
要完整运行时 vue 运行时构建 CDN 引入、动态模板
要完整工具链 vue + compiler-sfc 大型工程、SFC、TS、SSR

reactivity 包是完全独立可用的：

export {
  ref,
  shallowRef,
  isRef,
  toRef,
  toValue,
  toRefs,
  unref,
  proxyRefs,
  customRef,
  triggerRef,

这条光谱让”渐进式”成为可验证的事实——不是文档口号。它带来的设计哲学是：

框架能力应该可以被部分采用，而不是只能整体接受。

对比 React：你很难只用 React 的 reconciler，不要 JSX，不要 hooks。Vue 把每一层都拆成了独立 npm 包，用户可以从最薄一层开始，逐层叠加。

代价也很明确：包之间需要稳定的内部协议（RendererOptions、ComponentInternalInstance、PatchFlags），任何一层重构都要顾及下游使用方。这是 Vue 内部 RFC 流程比 React 重的根因之一。

哲学二：声明式的本质，是把变化收敛到数据层

写 Vue 时我们写的是状态：

<template>
  <button @click="count++">{{ count }}</button>
</template>

没有手动找 DOM，没有手动重渲染。这种”语法简单”的表象之下，是响应式系统维护的一个事实：谁在运行时读过某个数据，谁就订阅这个数据。

// 当前正在执行并允许收集依赖的订阅者。
// ReactiveEffect.run / refreshComputed 会在执行用户函数前设置它，track 会读取它来建立依赖关系。
export let activeSub: Subscriber | undefined

声明式的深层价值不是 Proxy，也不是 VDOM，而是：

不要让用户描述”更新步骤”，让用户描述”状态和结果的关系”。

这一点 React 的函数组件也做到了，但 Vue 选了不同的路径——React 通过”重新执行整个函数”来表达关系，Vue 通过”细粒度依赖图”来表达关系。前者心智简单但需要 useMemo 救场，后者写起来更接近普通赋值，但需要 Proxy 在背后维护图。

两条路都是声明式，但响应粒度的位置完全不同。Vue 选择把粒度推到数据本身，这是它整套架构的起点。

哲学三：编译器和运行时的中间路线

这一条是 Vue 3 最有原创性的设计。

纯运行时框架（早期 React）：所有判断都在更新时进行，模板是不透明的。代价是 diff 工作量大。

纯编译型框架（Svelte）：所有更新逻辑都在编译期生成，运行时极薄。代价是无法处理”运行时才知道结构”的场景。

Vue 3 的选择：让编译器给运行时打小抄——这就是 PatchFlags 和 Block Tree。

PatchFlags：编译器告诉运行时”哪里是动态的”

export enum PatchFlags {
  /**
   * Indicates an element with dynamic textContent (children fast path)
   */
  TEXT = 1,

  /**
   * Indicates an element with dynamic class binding.
   */
  CLASS = 1 << 1,

  /**
   * Indicates an element with dynamic style
   * The compiler pre-compiles static string styles into static objects
   * + detects and hoists inline static objects
   * e.g. `style="color: red"` and `:style="{ color: 'red' }"` both get hoisted
   * as:
   * ```js
   * const style = { color: 'red' }
   * render() { return e('div', { style }) }
   * ```
   */
  STYLE = 1 << 2,

  /**
   * Indicates an element that has non-class/style dynamic props.
   * Can also be on a component that has any dynamic props (includes
   * class/style). when this flag is present, the vnode also has a dynamicProps
   * array that contains the keys of the props that may change so the runtime
   * can diff them faster (without having to worry about removed props)
   */
  PROPS = 1 << 3,

模板里 <div class="static" :title="x">{{ y }}</div> 编译后会带上 TEXT | PROPS 这样的标记。运行时拿到 VNode 时已经知道”这个节点只有文本和 props 是动态的”，可以跳过 class/style/children 的全量 diff。

Block Tree：把动态节点从树里抽出来排成一队

export function openBlock(disableTracking = false): void {
  blockStack.push((currentBlock = disableTracking ? null : []))
}

export function closeBlock(): void {
  blockStack.pop()
  currentBlock = blockStack[blockStack.length - 1] || null
}

编译器在 render 函数里插入 openBlock()，编译进去的所有动态子节点会被收集到当前 block 的 dynamicChildren 数组中，跨越层级，扁平存储。更新时根本不需要递归整棵 VNode 树：

    if (dynamicChildren) {
      // block tree 优化路径：只 patch 编译器收集到的动态子节点。
      patchBlockChildren(
        n1.dynamicChildren!,
        dynamicChildren,
        el,
        parentComponent,
        parentSuspense,
        resolveChildrenNamespace(n2, namespace),
        slotScopeIds,
      )

这是 Vue 3 相比 Vue 2 渲染层最大的飞跃：diff 不再以树为单位，而是以”模板内可能变化的节点序列”为单位。

哲学落点

PatchFlags + Block Tree 的本质是一种协议：编译器和运行时不是单向调用，而是约定一份共享数据结构，让两边都减少工作。

这条中间路线的代价也很显式：

  • 一旦用户写 render function 或来自外部的 VNode，整棵 block 退化成 BAIL 模式，所有优化失效。
  • 编译器输出和运行时实现强耦合，两者必须同版本演进。

单层最简的方案往往不是最优解。让构建期和运行期协作，但要有清晰的协议作边界——这是 Vue 3 最值得学习的架构判断。构建期和运行时各有擅长的事情，好的框架应该让它们互相补位。

哲学四：用户心智是 API 的第一约束

Vue 里有几个”看起来更麻烦”的设计，长期被社区争议，但都是为了保护用户心智的可预测性。

.value：明确读写边界

const count = ref(0)
count.value++ // 显式读写

vs Vue 2 的 data 自动 unwrap，写起来更顺。但 .value 换来了：

  • 函数边界稳定：ref 传进函数还是 ref，不会因为解构变成 snapshot。
  • 类型系统清晰：TS 能区分”响应式引用”和”普通值”。
  • 工具链可识别：compiler-sfc 的 ref sugar 之所以可被静态识别，靠的就是 .value 这个标记。

scheduler 的异步批量

count++; count++ 不会触发两次更新——同一个微任务窗口里同步状态变化合并成一次：

export function queueJob(job: SchedulerJob): void {
  // 同一个 job 在同一轮 flush 中只允许入队一次。
  if (!(job.flags! & SchedulerJobFlags.QUEUED)) {
    const jobId = getId(job)
    const lastJob = queue[queue.length - 1]
    if (
      !lastJob ||
      // fast path when the job id is larger than the tail
      (!(job.flags! & SchedulerJobFlags.PRE) && jobId >= getId(lastJob))
    ) {
      queue.push(job)
    } else {
      queue.splice(findInsertionIndex(jobId), 0, job)
    }

    job.flags! |= SchedulerJobFlags.QUEUED

    queueFlush()
  }
}

function queueFlush() {
  if (!currentFlushPromise) {
    // 通过 Promise 微任务异步 flush，实现同一轮同步状态变更的批量更新。
    currentFlushPromise = resolvedPromise.then(flushJobs)
  }
}

代价是同步直觉被打破：改完数据立刻读 DOM，拿到的是旧值，必须 await nextTick()。Vue 用一个明确的概念（nextTick）来交换”批量合并”的稳定性，而不是为了直观让两次 count++ 触发两次更新。

Composition API 与 Options API 共存

这是 Vue 3 最有政治意味的设计决策。Vue 没有像 React 强推 hooks 那样强迫迁移，而是让两套 API 同时活着、互相兼容。代价是文档要讲两套、维护要顾两套；收益是 Vue 2 的存量项目升级 3.x 时心智成本极低。

哲学落点

API 不是函数签名，是用户理解系统的方式。ref.value 这种”看起来多余”的设计，本质上是在定义用户和框架之间的契约。

读源码时如果只盯着实现优化，会错过 API 设计真正在保护的东西。反过来想：这个实现保护了怎样的心智？让用户少关心了什么？又刻意暴露了什么？

哲学五：默认路径要顺滑，逃生口要明确

成熟框架的标志，是常规场景能一路走到底，复杂场景也有清晰的出口。Vue 的默认路径：

state -> render -> VNode -> patch -> DOM

但每一段路上都留了显式的逃生口：

当默认路径不合适 Vue 给的逃生口 这个逃生口在保护什么
不希望对象被深代理 markRaw / shallowReactive / shallowRef 性能、第三方对象兼容、DOM 节点
想自己控制副作用时机 watch 的 flush / effect scheduler SSR、测试、外部异步系统集成
想跨平台渲染 createRenderer(options) Canvas、原生、小程序
不想用模板 render function / JSX 高度动态结构、TS 友好
想做 SSR server-renderer + hydration 首屏性能、SEO
只用响应式 独立 @vue/reactivity 包 嵌入到非 Vue 项目 
// runtime-dom 给 runtime-core 注入浏览器平台能力：
// nodeOps 负责增删查改 DOM 节点，patchProp 负责更新 class/style/event/attribute 等属性。
const rendererOptions = /*@__PURE__*/ extend({ patchProp }, nodeOps)

export function createRenderer<
  HostNode = RendererNode,
  HostElement = RendererElement,
>(options: RendererOptions<HostNode, HostElement>): Renderer<HostElement> {
  return baseCreateRenderer<HostNode, HostElement>(options)
}

createRenderer 是这一条哲学最干净的体现——平台能力被收成一个 options 对象，逃生口不是隐藏选项，而是公开 API。

默认路径太弱，普通用户被迫学高级特性；逃生口太隐蔽，高级用户撞墙。Vue 在两端都没偷懒。

哲学六：每一个优化都有标价

这一条是我整个源码阅读最深的体会，也是最容易被”框架优秀”叙事掩盖的部分：Vue 的每一个聪明设计，都付出了具体代价。

设计 收益 代价
Proxy 替代 Object.defineProperty 支持新增属性、Map/Set、数组下标 不支持 IE，Proxy 自身有性能 overhead
Block Tree 跳过静态节点 更新时间几乎只和动态节点数相关 一旦走非编译器生成路径就 BAIL，全部失效
scheduler 异步批量 同一轮状态合并成一次更新 改完数据立刻读 DOM 拿不到新值，需要 nextTick
.value 显式 类型清晰、边界稳定 写起来啰嗦，社区反复讨论
SFC 单文件组件 模板/逻辑/样式聚合，工具链强 必须有 build step，不能裸 HTML 用
Composition + Options 共存 迁移友好 文档/维护双倍，新手需要选边
reactivity 独立包 渐进式落地 内部协议必须长期稳定，重构受限

这张表里没有一个设计是”白嫖”的。哲学不是”Vue 的选择都很对”，而是 Vue 知道自己付了什么代价、并且明确告诉你这个代价。

举例：readonly 不会为了和 reactive 共享代理而破坏写保护；keyed diff 追求最少移动，但前提是 key 能正确表达节点身份；hydration 文本不一致时告警并修正而不是假装没事——这些都是优化让位于语义。

性能优化的真正纪律，不是”做到极致”，而是”在不破坏用户能理解的规则前提下，少做事”。

读 Vue 源码到底训练了什么

很多源码导读会以”如何实现一个 mini-vue”作为收尾。我倾向于不那样收。模仿一个简化版 Vue 训练的是 API 调用熟练度，而读完整 Vue 真正能训练的是另外几样：

第一，识别岔路口。看到一段实现，能问出”这里本可以走另一条路，为什么没走？”——比如为什么 ref 不做自动 unwrap、为什么 scheduler 不用同步 flush、为什么 reactivity 不绑定到组件。

第二，识别协议。框架内部的协议比函数签名重要——PatchFlags 是编译器和运行时的协议，RendererOptions 是 core 和平台的协议，ComponentInternalInstance 是 setup 和 render 的协议。好的系统是协议清晰的系统，不是函数封装好的系统。

第三，识别代价。任何”优秀设计”都伴随代价。源码里能找到代价的位置：BAIL 分支、__DEV__ 分支、各种 // edge case 注释、shallow* 系列的存在。这些”丑陋的角落”才是真实工程的样子。

第四，识别边界。哪些事情 Vue 选择不做？比如不做细粒度组件级编译（这是 Solid 的方向），不做完全无 VDOM（这是 Svelte 的方向），不强推 Composition API（这是 React hooks 的方向）。理解一个框架不做什么，比理解它做了什么更难。

小结

  1. Vue 是渐进式框架：能力分层成可独立采用的包，从 reactivity 到 SFC 是连续光谱。
  2. Vue 走的是编译器+运行时的中间路线：PatchFlags 和 Block Tree 是这条路线的核心协议。
  3. Vue 把用户心智契约放在 API 第一位：.value 和 async update 不是缺陷，是有意识的边界设计。
  4. Vue 给每条默认路径都留了显式逃生口：createRenderer、shallow*、server-renderer 都是公开 API 而非内部细节。
  5. Vue 的每一个优化都有标价：哲学的厚度来自取舍，不是来自正确。读源码真正要沉淀的，是识别岔路、协议、代价和边界的能力。
