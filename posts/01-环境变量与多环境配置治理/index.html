环境变量与多环境配置治理

发表于2026|更新于2026|工程化
|字数总计:1.5k|阅读时长:5分钟

前言：环境变量看起来只是几个 .env 文件，但它直接影响接口地址、构建产物、功能开关和安全边界。很多线上事故不是代码逻辑错了，而是环境配置用错了。

先区分两类配置

前端项目里的配置大致分两类。

构建时配置

构建时就确定，打进产物里：

console.log(import.meta.env.VITE_API_BASE_URL)

比如：

  • API 基础地址；
  • CDN 地址；
  • 应用环境标识；
  • 是否开启某个实验功能。

这类配置一旦构建完成，就固定在静态资源里。要修改，通常需要重新构建。

运行时配置

应用启动后再读取，不一定打进构建产物：

const config = await fetch('/config.json').then((res) => res.json())

比如：

  • 部署后动态切换后端地址；
  • 不同租户配置；
  • 灰度开关；
  • 运行时注入的版本信息。

我的建议是：普通前端应用先用构建时配置，确实需要同一份产物部署到多个环境时，再引入运行时配置。不要一开始就把配置系统做复杂。

Vite 的环境变量规则

Vite 会加载这些文件：

.env
.env.local
.env.[mode]
.env.[mode].local

比如 mode=staging 时，会加载：

.env
.env.local
.env.staging
.env.staging.local

常见文件职责：

文件 用途 是否提交
.env 所有环境通用配置 可以
.env.local 本地私有配置 不提交
.env.development 开发环境配置 可以
.env.staging 预发环境配置 可以
.env.production 生产环境配置 可以
.env.production.local 生产本地私有覆盖 不提交

.local 文件通常加入 .gitignore。

客户端变量必须有前缀

Vite 默认只有 VITE_ 开头的自定义变量会暴露给客户端代码；没有这个前缀的变量，不会被 Vite 默认注入到客户端的 import.meta.env 中，但可以在 Node 脚本或构建配置里通过 process.env 读取，前提是对应进程已经加载了这些变量。

VITE_API_BASE_URL=https://api.example.com
DB_PASSWORD=123456

客户端中：

console.log(import.meta.env.VITE_API_BASE_URL) // 可以读取
console.log(import.meta.env.DB_PASSWORD) // undefined

这条规则非常重要：凡是进入客户端的环境变量，本质上都是公开信息。

不要这样写：

VITE_SECRET_KEY=real-secret
VITE_DB_PASSWORD=real-password

只要打进前端产物，用户就有机会看到。前端环境变量不能保存真正的密钥。

mode 和 NODE_ENV 不是一回事

这是 Vite 项目里很容易混的点。

  • mode 决定加载哪个 .env.[mode] 文件；
  • NODE_ENV 影响 import.meta.env.DEV 和 import.meta.env.PROD。

可以简单理解成：

mode：选哪套环境变量文件，比如 .env.staging
NODE_ENV：判断当前是开发构建还是生产构建
VITE_xxx：文件里真正给业务代码读取的配置变量

比如：

vite build --mode staging

它表示用 staging 这个 mode 构建，但构建本身依然通常是生产构建。

所以不要简单认为：

mode=staging 就等于 NODE_ENV=staging

我的习惯是自己定义业务环境变量：

VITE_APP_ENV=staging
VITE_API_BASE_URL=https://staging-api.example.com

代码里读取：

export const appEnv = import.meta.env.VITE_APP_ENV
export const apiBaseURL = import.meta.env.VITE_API_BASE_URL

这样业务环境和构建环境就分开了。

给环境变量加类型

import.meta.env 默认类型不一定知道你的自定义变量。可以在 src/types/env.d.ts 中声明：

interface ImportMetaEnv {
  readonly VITE_APP_ENV: 'development' | 'test' | 'staging' | 'production'
  readonly VITE_API_BASE_URL: string
}

interface ImportMeta {
  readonly env: ImportMetaEnv
}

这样写错变量名时，编辑器就能提示。

// ❌ 拼错会被提示
import.meta.env.VITE_API_BSAE_URL

环境变量最终都是字符串

.env 里写：

VITE_ENABLE_MOCK=true
VITE_PAGE_SIZE=20

代码里拿到的是字符串：

const enableMock = import.meta.env.VITE_ENABLE_MOCK === 'true'
const pageSize = Number(import.meta.env.VITE_PAGE_SIZE)

不要直接这样判断：

// ❌ 字符串 "false" 也是 truthy
if (import.meta.env.VITE_ENABLE_MOCK) {
  // ...
}

这类 bug 很隐蔽，尤其是功能开关场景。

建议做一层配置读取封装

不要在业务代码里到处散写 import.meta.env。

export const appConfig = {
  env: import.meta.env.VITE_APP_ENV,
  apiBaseURL: import.meta.env.VITE_API_BASE_URL,
  enableMock: import.meta.env.VITE_ENABLE_MOCK === 'true'
}

业务使用：

import { appConfig } from '@/config/app'

console.log(appConfig.apiBaseURL)

这样变量名变了，只需要改一处。

环境变量要有示例文件

.env.local 不提交，但项目应该提交 .env.example。

VITE_APP_ENV=development
VITE_API_BASE_URL=https://api.example.com
VITE_ENABLE_MOCK=false

新人拉项目后，复制一份：

cp .env.example .env.local

然后按本地情况修改。

.env.example 的价值不是提供真实配置，而是告诉别人“项目需要哪些配置”。

多环境命令怎么设计

我通常这样写：

{
  "scripts": {
    "dev": "vite --mode development",
    "dev:test": "vite --mode test",
    "build:test": "vite build --mode test",
    "build:staging": "vite build --mode staging",
    "build:prod": "vite build --mode production"
  }
}

环境文件对应：

.env.development
.env.test
.env.staging
.env.production

这里不要把所有环境都叫 production，否则排查问题时很难知道当前产物到底是哪个后端地址。

配置错误要尽早失败

如果关键变量缺失，应该让应用启动或构建时直接失败，而不是线上打开页面才发现接口地址是 undefined。

可以写一个简单校验：

const requiredEnv = ['VITE_APP_ENV', 'VITE_API_BASE_URL'] as const

for (const key of requiredEnv) {
  if (!import.meta.env[key]) {
    throw new Error(`Missing env: ${key}`)
  }
}

更严格的项目可以用 zod 做 schema 校验，但阶段一先建立意识就够了。

小结

  1. 环境变量分构建时配置和运行时配置，不要一开始就过度设计。
  2. Vite 默认只暴露 VITE_ 前缀变量，暴露到客户端的都不是秘密。
  3. mode 决定加载哪个环境文件，NODE_ENV 影响开发/生产判断，两者不要混用。
  4. 环境变量最终都是字符串，布尔值和数字要手动转换。
  5. 建议统一封装配置读取，并维护 .env.example 和必要的变量校验。
