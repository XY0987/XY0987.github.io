Git 工作流与团队协作规范

发表于2026|更新于2026|工程化
|字数总计:1.5k|阅读时长:5分钟

前言：代码规范工具解决的是“代码怎么写”，Git 工作流解决的是“代码怎么进入主干”。如果没有协作流程，lint 配得再漂亮，项目还是会在多人协作时失控。

Git 工作流要解决什么

团队项目里，Git 不只是保存代码历史。

它至少承担四个职责：

职责 说明
隔离变更 不同需求、修复、实验在不同分支上进行
组织评审 通过 PR 让变更被讨论和确认
触发检查 CI 根据分支和 PR 自动运行
形成历史 提交记录、版本记录、changelog 能追溯

如果 Git 工作流没有约定，就会出现这些问题：

  • 直接往主干提交；
  • 一个分支混多个需求；
  • PR 描述只有一句“改完了”；
  • Review 只看格式，不看风险；
  • 合并后才发现没有跑构建；
  • 线上出问题时找不到对应变更。

所以我的理解是：Git 工作流不是流程负担，而是多人协作的最小秩序。

常见分支模型怎么选

前端业务项目里常见几种分支模型：

模型 特点 适合场景
Git Flow develop、release、hotfix 分支完整 发版节奏固定、流程较重的团队
GitHub Flow 从主干拉分支，PR 合并回主干 持续交付、Web 应用
Trunk-Based Development 小步提交到主干，靠 feature flag 控制 自动化成熟、团队纪律强

我的建议比较保守：

  • 大多数中小型前端团队，用 GitHub Flow 就够了；
  • 有固定测试周期和发版窗口，可以加 release/* 分支；
  • 不要一开始就上很重的 Git Flow，流程越重越需要维护成本。

一个简单可落地的分支约定：

main                 # 稳定主干
feature/user-list    # 新功能
fix/token-expired    # bug 修复
chore/update-eslint  # 工程配置调整
release/2026-06-13   # 可选，发版分支

分支名不是越复杂越好，能表达变更类型和主题就够。

PR 模板要写什么

PR 模板的目标不是凑表格，而是让评审者快速理解变更。

.github/pull_request_template.md：

## Summary

- 

## Test Plan

- [ ] pnpm lint
- [ ] pnpm typecheck
- [ ] pnpm test
- [ ] pnpm build

## Risk

- 

## Screenshots

如果有 UI 变化，请补充截图或录屏。

我认为最关键的是三块：

字段 价值
Summary 告诉别人改了什么、为什么改
Test Plan 说明你怎么验证
Risk 提醒评审者重点看哪里

不要把 PR 模板做成十几个必填项。模板太重，最后大家会机械填“无”。

Issue 模板的作用

Issue 模板适合把需求和 bug 描述标准化。

Bug 模板可以这样写：

## Current Behavior

当前表现是什么？

## Expected Behavior

期望表现是什么？

## Reproduction

1. 
2. 
3. 

## Environment

- Browser:
- OS:
- Version:

需求模板可以这样写：

## Background

为什么要做这个需求？

## Scope

这次做什么，不做什么？

## Acceptance Criteria

- [ ] 
- [ ]

这里最重要的是 Scope 和 Acceptance Criteria。

很多协作问题不是代码问题，而是一开始没说清楚“这次到底算做完”。

CODEOWNERS 让评审责任明确

CODEOWNERS 可以把目录和负责人绑定起来。

示例：

# 默认负责人
* @frontend-leads

# 组件库
/packages/ui/ @design-system-team

# 构建配置
/packages/build-config/ @infra-team

# 支付相关页面
/apps/web/src/features/payment/ @payment-team

它的价值是减少“这个 PR 到底该找谁看”的不确定性。

但也要注意：CODEOWNERS 不是甩锅工具。

如果一个目录长期需要某个人审批，说明这个人也要参与规范沉淀，否则 Review 会变成个人经验瓶颈。

Code Review Checklist

我更喜欢把 Review Checklist 写成短而有用的版本。

比如 .github/code-review-checklist.md：

## Code Review Checklist

- 变更是否只解决一个明确问题？
- 是否引入新的公共 API 或约定？
- 是否有明显的边界条件遗漏？
- 是否需要补充测试或截图？
- 是否影响构建、发布、权限、性能或可访问性？
- 是否有更简单的实现方式？

Checklist 不需要覆盖所有细节，工具能检查的不要再放进 Review 清单。

比如下面这些不应该成为 Review 重点：

  • 缩进；
  • import 排序；
  • 未使用变量；
  • 提交信息格式。

这些应该由 Prettier、ESLint、Commitlint 提前处理。

提交规范和 Changesets 怎么衔接

Conventional Commits 解决的是提交历史可读：

feat(auth): add password reset page
fix(request): handle token expired response

Changesets 解决的是发布意图明确：

---
"@example/ui": minor
---

新增 Button loading 状态。

二者可以配合，但不要互相替代。

我更推荐这条链路：

开发提交
  │
  ├── Commitlint 检查 commit message
  │
  ▼
打开 PR
  │
  ├── PR 模板说明变更和验证方式
  ├── CODEOWNERS 指定评审人
  ├── CI 跑 lint/typecheck/test/build
  │
  ▼
如果影响发版
  │
  └── 提交 changeset 文件

这样每个工具负责一段：

工具 负责什么
Commitlint 提交信息格式
PR 模板 变更上下文
CODEOWNERS 评审责任
CI 自动化质量检查
Changesets 版本和 changelog

合并策略怎么选

常见合并策略有三种：

策略 特点 我的建议
Merge commit 保留完整分支历史 适合需要保留上下文的项目
Squash merge 一个 PR 合成一个提交 适合大多数业务项目
Rebase merge 历史线性 要求团队 Git 能力更强

我在业务项目里更偏向 Squash merge。

原因是业务 PR 经常包含很多修修补补的提交，比如：

fix typo
update
fix lint

这些中间提交保留下来价值不大。Squash 后用一个高质量提交描述整个 PR，主干历史更清爽。

但如果是开源库或基础设施仓库，需要保留每个 commit 的语义，就要更谨慎。

小结

  1. Git 工作流的核心是让变更隔离、可评审、可检查、可追溯。
  2. 大多数前端团队用 GitHub Flow 就够，流程不要一开始设计得太重。
  3. PR 模板重点写 Summary、Test Plan、Risk，不要做成形式主义表格。
  4. CODEOWNERS 可以明确评审责任，但不能替代团队规范沉淀。
  5. Conventional Commits 管提交历史，Changesets 管发版意图，二者可以衔接但不要混用。
