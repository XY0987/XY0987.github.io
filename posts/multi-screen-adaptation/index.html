多端适配实战：从移动端到可视化大屏的全场景方案选型

发表于2026|更新于2026|项目
|字数总计:6.9k|阅读时长:26分钟

前言：适配这个话题看似老生常谈，但真到项目里选方案的时候，依然有人在 rem、vw、scale 之间反复横跳。这篇我系统的总结梳理一下（H5、小程序、可视化大屏、RN/Flutter App）的适配方案，重点讲清楚每种方案的边界在哪里，以及什么场景该选什么。

先把”适配”这件事想清楚

很多人把”适配”理解成”页面在不同设备上不变形”，这只是表象。本质上适配是在解决两类问题：

  1. 尺寸适配：屏幕物理大小不同（4 寸手机 vs 6.7 寸手机 vs 27 寸大屏），元素该等比放大还是保持物理尺寸？
  2. 像素密度适配：同样的 CSS 1px，在 DPR=1 的设备上是 1 个物理像素，在 DPR=3 的 iPhone 上是 3 个物理像素，怎么处理”细节不糊”？

这两个问题对应的方案完全不同。移动端主要解决的是问题 1 的”等比缩放”和问题 2 的”高清显示”；大屏（无论是 PC 可视化大屏、TV、车机、还是小程序/APP）主要解决的是问题 1

适配方案没有银弹，选型的核心是：先看你的容器是什么、设计稿基准是什么、用户的设备分布如何。

移动端 H5 适配方案

起点：viewport meta

不管用什么方案，这一行是前置条件：

<meta name="viewport" content="width=device-width, initial-scale=1.0, viewport-fit=cover">
  • width=device-width：让 viewport 宽度等于设备宽度
  • initial-scale=1.0：初始缩放为 1
  • viewport-fit=cover：iPhone X 之后的刘海/灵动岛适配前提，配合 env(safe-area-inset-*) 使用

漏了这一行，所有方案都会”看起来很奇怪”——这是新人最容易忽略的坑。

方案 1：rem + 动态根字号

核心思路：把设计稿宽度（比如 750px）映射到一个固定的根字号倍数上，所有元素用 rem 写。

// 设计稿基准 750px，根字号 = 屏幕宽度 / 7.5
// 即设计稿每 100px = 1rem
function setRem() {
  const designWidth = 750
  const clientWidth = document.documentElement.clientWidth
  // 限制最大宽度，避免大屏下元素过大（PC 打开 H5 的场景）
  const width = Math.min(clientWidth, 750)
  document.documentElement.style.fontSize = (width / designWidth) * 100 + 'px'
}

setRem()
window.addEventListener('resize', setRem)
window.addEventListener('pageshow', (e) => e.persisted && setRem())

设计稿上一个 200px × 80px 的按钮，写成 width: 2rem; height: 0.8rem; 即可。

这个方案的代表是当年淘宝的 flexible.js，虽然现在新项目用得少了，但思路依然是行业基础。

配套的 PostCSS 插件：

// postcss.config.js
module.exports = {
  plugins: {
    'postcss-pxtorem': {
      rootValue: 100,      // 1rem = 100px（对应根字号 100px 的设计稿基准）
      propList: ['*'],
      selectorBlackList: [/^\.van-/], // 排除 vant 等三方组件
    }
  }
}

写代码时直接用 px，构建时自动转 rem。

优点：浏览器兼容性好（IE9+ 都支持），动态控制力强（可以加最大/最小限制）。
缺点：依赖 JS 计算，存在闪屏风险（首屏渲染时根字号还没设置）；JS 出错会导致整页布局崩溃。

方案 2：vw / vh

CSS 原生单位，1vw = 视口宽度的 1%。设计稿 750px，1px = 1/7.5 vw ≈ 0.1333vw。

/* 设计稿 200px 宽的元素 */
.btn {
  width: 26.6667vw;  /* 200 / 7.5 */
  height: 10.6667vw;
}

手写显然不现实，配合 postcss-px-to-viewport：

module.exports = {
  plugins: {
    'postcss-px-to-viewport': {
      viewportWidth: 750,   // 设计稿宽度
      unitPrecision: 5,
      viewportUnit: 'vw',
      selectorBlackList: ['.ignore-'],
      minPixelValue: 1,
      mediaQuery: false,
    }
  }
}

优点：纯 CSS 方案，无 JS 依赖，无闪屏；写法直观。
缺点：在桌面浏览器或 iPad 上打开会被等比放大到很离谱；老旧机型（iOS 8 以下）兼容性差，但这点现在已经可以忽略。

方案 3：Flex/Grid + 媒体查询

不追求 1:1 还原设计稿，而是按”内容流式适配”。这种思路在响应式 Web 里更常见：

.list {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(160px, 1fr));
  gap: 12px;
}

@media (max-width: 375px) {
  .list { gap: 8px; }
}

适用场景：内容型页面（资讯、文章列表、电商商品流），强调可读性而非视觉一致性。

方案选型建议（移动端 H5）

方案 推荐场景 不推荐场景
rem + 动态根字号 需要严格还原设计稿、需要兼容低版本机型、需要 PC 打开时限宽 纯桌面项目
vw + PostCSS 现代项目首选，简单纯粹 需要 PC 打开 H5 还想限宽的场景（要配合 max-width 容器）
Flex/Grid + 媒体查询 响应式 Web、内容型页面 1:1 还原设计稿的活动页

移动端绕不开的两个细节问题

1px 边框问题

设计稿上的 1px 边框，在 DPR=2、DPR=3 的设备上会显得”粗”——因为 CSS 1px = 多个物理像素。

主流的解决方案是伪元素 + transform: scale：

.hairline-bottom {
  position: relative;
}
.hairline-bottom::after {
  content: '';
  position: absolute;
  left: 0;
  bottom: 0;
  width: 100%;
  height: 1px;
  background: #e5e5e5;
  transform: scaleY(0.5);
  transform-origin: 0 100%;
}

@media (-webkit-min-device-pixel-ratio: 3) {
  .hairline-bottom::after { transform: scaleY(0.333); }
}

更现代一些可以直接用 border: 0.5px solid —— iOS Safari 是支持的，但 Android 各厂商支持度参差不齐，所以实战里我还是更倾向 scale 方案。

安全区域（刘海/底部小黑条）

iPhone X 之后多了顶部刘海和底部小黑条，需要用 env() 函数处理：

.app-header {
  padding-top: env(safe-area-inset-top);
}

.app-tabbar {
  padding-bottom: env(safe-area-inset-bottom);
  /* 兼容旧语法 */
  padding-bottom: constant(safe-area-inset-bottom);
}

坑：viewport meta 必须加 viewport-fit=cover，env() 才会生效

小程序适配：从 rpx 到 page-meta + rem

起点：rpx 能做什么，不能做什么

微信小程序自带了一个适配单位 rpx（responsive pixel）：

规定屏幕宽度为 750rpx。1rpx = screenWidth / 750 px，由微信渲染层算出实际像素。

.btn {
  width: 200rpx;  /* iPhone 6/7/8 上 = 100px，iPhone 13 上按比例放大 */
  height: 80rpx;
}

设计稿 750 标准时 1px = 1rpx，几乎”所写即所得”。支付宝、抖音、快手等小程序也都跟进了类似单位。

但小程序不只跑在手机上——它还会跑在 iPad、PC（Windows / Mac 微信）、车机、安卓 WMPF。这时候 rpx 就暴露出它的致命缺陷：

设备 / 场景 windowWidth 1rpx = 100rpx 实际渲染
iPhone 6/7/8 375 0.5px 50px
iPad 768 1.024px ~102px
iPad Pro 1024 1.365px ~136px
PC 微信最大化 1920 2.56px 256px

rpx 按 screenWidth / 750 线性无上限等比放大，微信没有提供任何干预入口——不能封顶、不能改系数、不能改时机。PC 微信最大化下按钮和字号被放大到失真，本质不是 bug，而是规则就这么设计的。

这个问题摆在面前，小程序的适配方案就有了多种选择。

官方推荐的几条路径

翻微信官方 《小程序大屏适配指南》，官方给出的核心能力有四块——先开大屏模式，再按需组合布局方案。

前置：开启 resizable

// app.json
{
  "resizable": true,                 // 基础库 ≥ 2.21.3，覆盖 PC/iPad/车机/WMPF
  "window": { "pageOrientation": "auto" }
}

开启后，PC 微信窗口拖拽、iPad 横竖屏切换都会重新计算 rpx 并触发 Page.onResize。这一行是所有后续方案的前置条件，无论你选哪条路都需要。

方案 A：rpx + 媒体查询（官方首推的简单方案）

官方文档原话：”小程序基于 Webview 实现，利用 CSS 媒体查询可实时监听屏幕尺寸大小，结合 Flex/Grid 布局便能实现响应式适配。”

.container {
  display: flex;
  flex-direction: column;
  padding: 20rpx;
}

/* 平板双列 */
@media (min-width: 768px) {
  .container { flex-direction: row; padding: 24px; }
  .item { width: 50%; }
}

/* PC 三列 + 限宽 */
@media (min-width: 1200px) {
  .container { max-width: 1200px; margin: 0 auto; }
  .item { width: 33.33%; }
}
  • 优点：零成本、纯 CSS、贴近 Web 开发习惯
  • 缺点：只能切断点，无法连续缩放；rpx 在断点之间依然会被无限放大

方案 B：match-media 组件 / createMediaQueryObserver

处理”某些元素只在大屏显示”的结构差异时，官方更推荐 <match-media> 组件——比 CSS media query 多了”组件级隔离”：

<match-media min-width="769">
  <view class="sidebar">大屏侧边栏</view>
</match-media>

<match-media max-width="768">
  <view class="bottom-tabbar">底部 Tab</view>
</match-media>

JS 里用 this.createMediaQueryObserver()：

Page({
  onReady() {
    this.mq = this.createMediaQueryObserver()
    this.mq.observe({ minWidth: 769 }, (matches) => {
      this.setData({ isPC: matches })
    })
  },
  onUnload() { this.mq && this.mq.disconnect() }
})
  • 优点：比 wx:if + onResize 优雅，天然配合组件树
  • 缺点：解决的是结构显隐，不解决尺寸缩放

方案 C：栅格组件

weui-miniprogram 等扩展库提供了 row/col 栅格组件，24 等分 + xs/sm/md/lg/xl 断点：

<row>
  <col xs="24" sm="12" md="8" lg="6" xl="4">
    <view class="card">内容</view>
  </col>
</row>
  • 优点：多列布局场景下描述能力强
  • 缺点：引入了第三方组件库的尺寸规范，想和自己的设计稿协调不容易

方案 D：分栏模式（frameset）

不建议使用，目前小程序默认为分栏模式，frameset配置微信侧已不维护

PC 端可以把窗口分成左右两半各展示一个页面：

// app.json
{ "frameset": { "type": "sidebar" } }
  • 适用：工具类、工作台类小程序（列表 + 详情）
  • 不适用：大部分纯内容型场景

方案 E：page-meta + 动态 rem（官方提供入口的社区主流方案）

从基础库 2.9.0 开始，<page-meta> 支持 root-font-size 属性，可以在运行时动态设置页面的根 font-size——这是官方给”rem 派”开的合规入口。

很多老文章说”小程序没有 html 根节点，不推荐 rem”，这个说法在 2.9.0 之前是对的；之后 <page-meta root-font-size> 就是专门为 rem 方案服务的。

思路：

<page-meta :root-font-size="rootFontSize" />

// 动态算根字号
rootFontSize = Math.min(maxScreenWidth, screenWidth) / 10
  • 优点：可封顶；缩放规则完全在 JS 里可控；和 H5 能共用同一套 CSS
  • 缺点：需要自己搭 mixin + 构建插件 + PostCSS 链路，初次搭建成本高

小程序大屏方案选型对比

方案 解决什么 适合场景 能否连续缩放 能否封顶
默认 rpx 手机多机型等比 纯手机端 ✅ ❌
rpx + media query 断点切布局 偶尔兼顾大屏的内容型页面 ❌（跳跃） ❌
match-media 结构显隐差异 大小屏差异大、需要组件级控制 —— ——
栅格组件 多列布局 列表/卡片流 ❌ ——
frameset 分栏 两栏工作台 工具型/后台型 PC 小程序 —— ——
page-meta + rem 连续缩放 + 封顶 主要跑在 PC/iPad 的业务小程序 ✅ ✅

简而言之：只在手机跑 → 默认 rpx 就够；偶尔开 PC → rpx + media query 应付；PC 是主战场、窗口还要自由拖拽 → page-meta + rem。

实战：我们为什么选 page-meta + rem

我们实际项目，同时跑在手机微信 / iPad / PC 微信，PC 端又是核心使用场景。这套诉求下，前面几个方案逐一被排除：

  • 纯 rpx：PC 最大化下 UI 失真，直接 pass
  • rpx + media query：断点切换很生硬，从 767px 拖到 768px 整页”跳一下”，体验差，且需要每个页面额外开发适配，侵入性高
  • match-media / 栅格 / 分栏：解决的是结构和布局，非核心痛点（连续缩放 + 封顶）

只有 page-meta + rem 同时满足两点：跟着窗口连续缩放、且能封顶防止大屏失真。顺带还白拿了”和 H5 共用 CSS”的多端同构收益——我们有些组件是小程序/H5 双端共用的，这个收益非常实在。

核心实现就三件事：mixin 算、构建注、PostCSS 转。

① mixin 算 rootFontSize

全局 mixin（src/mixin/platforms/mp-weixin.js）在每个页面 onLoad 时计算：

onLoad() {
  if (!uni?.cacheRootFontSize) {
    let renderScreenWidth = 414          // 兜底值
    const maxScreenWidth = 430           // 封顶
    const fontSizeDivisor = 10           // 750 / 75

    try {
      const { screenWidth } = wx.getSystemInfoSync()
      if (screenWidth > 0) renderScreenWidth = screenWidth

      const newFontSize = `${Math.min(maxScreenWidth, renderScreenWidth) / fontSizeDivisor}px`
      if (this.rootFontSize !== newFontSize) {
        this.rootFontSize = newFontSize
      }

      const { isPCWeixin } = getPlatform()
      // 移动端缓存复用；PC 端窗口可拖拽，每次重算
      if (!isPCWeixin) uni.cacheRootFontSize = newFontSize
    } catch (e) { /* ... */ }
  }
}

三个关键细节：

  1. 封顶：Math.min(430, screenWidth) / 10 —— 手机端等比缩放，iPad/PC 锁在 43px
  2. 分平台缓存：手机 screenWidth 不变，全局缓存只取一次；PC 窗口可拖拽，不缓存，每次 onLoad 重算（配合 resizable: true 和 onResize 就能响应拖拽）
  3. 兜底值 414：getSystemInfoSync 失败时用，保证 UI 不会整体崩

② 构建期自动注入 <page-meta>

每个页面不手写 <page-meta>，由插件在编译 .vue 时自动注入：

function genPageMeta(src) {
  const { descriptor: { template: { content = '', loc } } } = parse(src) || {}
  const sourceStr = new MagicString(src)
  const templateStr = `<page-meta :root-font-size="rootFontSize"></page-meta>${content}`
  sourceStr.overwrite(loc.start.offset, loc.end.offset, templateStr)
  return sourceStr.toString()
}

// 仅 mp-weixin 平台注入，插件模式下某些页面由宿主注入，避免重复
if (process.env.UNI_PLATFORM === 'mp-weixin') {
  if (!(process.env.MP_PLATFORM === 'plugin' && ['/asset/index'].includes(filePath))) {
    source = genPageMeta(source)
  }
}

③ PostCSS 把 px 转 rem

设计稿 750 基准，remUnit = 75，源码写 px，构建产物里是 rem：

  • 设计稿 75px → 1rem
  • 运行时实际像素 = rootFontSize × rem 值

这样同一套 CSS 源码在 H5 / 小程序 / OEM 多端都能跑。

运行时链路

页面 onLoad
   └─ mp-weixin mixin 触发
       ├─ wx.getSystemInfoSync() 取 screenWidth
       ├─ Math.min(430, screenWidth) / 10 → newFontSize
       ├─ 手机端：写入 uni.cacheRootFontSize 供后续页面复用
       └─ 更新 this.rootFontSize
              ↓
   <page-meta :root-font-size="rootFontSize" />
              ↓ 微信渲染层下发
   页面根字号 = 41.4px（手机）/ 43px（大屏封顶）
              ↓
   CSS 里所有 rem 单位基于新基准生效

小程序大屏的核心结论

小程序大屏适配没有银弹——手机独占选 rpx，偶尔兼顾 PC 用 rpx + media query，PC 是核心场景选 page-meta + rem。

我们项目最终选 page-meta + rem，**唯一刚需是”能封顶”**，附加收益是缩放规则可控 + H5 共用 CSS。match-media、栅格、分栏不是和 rem 互斥的替代方案，而是正交能力，需要时可以叠加使用。

App 端适配：RN、Flutter、原生

React Native：基于 dp 的 density-independent

RN 的所有尺寸单位都是 dp（density-independent pixels）——逻辑像素，不是物理像素。Android 原生开发的同学对 dp 应该很熟了。

但 RN 没有原生的”等比缩放”机制，需要自己封装：

import { Dimensions, PixelRatio } from 'react-native'

const { width: SCREEN_WIDTH } = Dimensions.get('window')
const DESIGN_WIDTH = 375  // iPhone 8 设计稿宽度

// 等比缩放函数
export const scaleSize = (size) => (SCREEN_WIDTH / DESIGN_WIDTH) * size

// 字体不建议等比，避免极端机型字过大或过小
export const scaleFont = (size) => {
  const scale = Math.min(SCREEN_WIDTH / DESIGN_WIDTH, 1.2)
  return PixelRatio.roundToNearestPixel(size * scale)
}

使用：

<View style={{ width: scaleSize(200), height: scaleSize(80) }}>
  <Text style={{ fontSize: scaleFont(14) }}>按钮</Text>
</View>

关键经验：字体不要等比缩放。如果一个 14px 的字在 iPhone 8 上正好，硬等比到 iPhone 14 Pro Max（更宽）会变成 16px，看起来像老人机。我习惯做一个上限封顶。

Flutter：MediaQuery + LayoutBuilder

Flutter 的逻辑像素和 RN 类似。社区里最常用的是 flutter_screenutil 这个包：

ScreenUtil.init(context, designSize: Size(375, 812));

Container(
  width: 200.w,   // 200 * (实际宽度 / 375)
  height: 80.h,
  child: Text('按钮', style: TextStyle(fontSize: 14.sp)),
)

.w .h .sp 是这个包提供的扩展，思路和 RN 自己封装的 scale 函数一致。

鸿蒙 ArkUI

鸿蒙的尺寸单位是 vp（virtual pixel），本质也是逻辑像素，开发时按 vp 写，系统自动按设备 DPI 转物理像素。设计哲学和 RN 的 dp、Flutter 的逻辑像素一致——大家都在向”逻辑像素”靠拢。

可视化大屏适配：vw/vh、rem、scale 三大主流方案

到这里前面都是”内容型”适配——元素该多大就多大，文字、图片清晰可读是第一优先级。

但可视化大屏（数据驾驶舱、监控大屏）的需求完全不同：

  • 设计稿通常是固定的 1920×1080（或 3840×2160）
  • 上线的容器尺寸不固定（4K 屏、户外 LED 拼接屏、横向超宽屏）
  • 用户期望”在不同尺寸的屏上看起来差不多”

社区里主流的方案有三种：vw/vh、rem、transform: scale。这三种没有绝对优劣，是要根据项目情况选——之前我说”scale 是王道”是不准确的，纠正一下。下面逐个讲。

方案 A：vw / vh（响应式占满）

把设计稿尺寸按比例转 vw/vh，所有元素跟着窗口尺寸自适应。

// utils.scss
$designWidth: 1920;
$designHeight: 1080;

@function vw($px) { @return ($px / $designWidth) * 100vw; }
@function vh($px) { @return ($px / $designHeight) * 100vh; }

.box {
  width: vw(300);
  height: vh(100);
  font-size: vh(16);
}

ECharts 的字体、间距、坐标轴 padding 等是 JS 配置项，CSS 转换覆盖不到，需要单独写一个工具函数：

export const fitChartSize = (size, designWidth = 1920) => {
  const clientWidth = window.innerWidth || document.documentElement.clientWidth
  return Number((size * (clientWidth / designWidth)).toFixed(3))
}

ECharts option 里 fontSize: fitChartSize(14)、grid: { left: fitChartSize(10) } 这样写。

优点：屏幕比例不一致也不会留白，视觉上能占满；字体清晰、事件热区准确。
缺点：每个图表的字体、间距都要单独适配，工作量较大。

方案 B：rem + 动态根字号（最常用的大屏方案之一）

这是不少团队大屏项目的实际选择。思路和移动端 rem 类似，但基准放在 1920：

// rem.js
(function init(screenRatioByDesign = 16 / 9) {
  const docEle = document.documentElement
  function setHtmlFontSize() {
    const screenRatio = docEle.clientWidth / docEle.clientHeight
    // 屏幕比例超过 16:9 时按比例锁定，避免横向超宽屏字体过大
    const fontSize = (
      screenRatio > screenRatioByDesign
        ? (screenRatioByDesign / screenRatio)
        : 1
    ) * docEle.clientWidth / 10
    docEle.style.fontSize = fontSize.toFixed(3) + 'px'
  }
  setHtmlFontSize()
  window.addEventListener('resize', setHtmlFontSize)
})()

把屏幕分成 10 份，1920 设计稿下根字号约 192px，写代码时用 PostCSS 自动转 rem：

// .postcssrc.js
module.exports = {
  plugins: {
    '@njleonzhang/postcss-px-to-rem': {
      unitToConvert: 'px',
      widthOfDesignLayout: 1920,
      unitPrecision: 3,
      minPixelValue: 1,
    }
  }
}

代码里写 width: 200px，编译后变成 width: 1.042rem。

优点：字体清晰（不会因为缩放变糊），事件热区准确，开发体验接近 vw 但只需要管根字号一处。ECharts 字体仍需要 fitChartSize 之类的工具配合。
缺点：屏幕比例和设计稿不一致时会留白（这个其实是大屏里常见的可接受方案，毕竟内容完整比铺满更重要）。

方案 C：transform: scale（最快上手）

整个内容容器按设计稿尺寸写，外层用 scale 整体缩放：

<div class="screen-container">
  <div class="screen-content" id="screen">
    <!-- 所有内容按 1920×1080 设计稿写，单位用 px -->
  </div>
</div>

.screen-container {
  width: 100vw;
  height: 100vh;
  overflow: hidden;
  background: #000;
  display: flex;
  align-items: center;
  justify-content: center;
}

.screen-content {
  width: 1920px;
  height: 1080px;
  transform-origin: center center;
}

function resizeScreen() {
  const screen = document.getElementById('screen')
  const scale = Math.min(
    window.innerWidth / 1920,
    window.innerHeight / 1080
  )
  screen.style.transform = `scale(${scale})`
}

resizeScreen()
window.addEventListener('resize', resizeScreen)

整页内容按 1920×1080 写，所有 echarts、地图、CSS 动画都不用改一行——交给浏览器去做矩阵变换。社区里 v-scale-screen 这个包就是这个思路的封装。

优点：代码量最少、上手最快、无需写任何工具函数。
缺点：缩放比例过大时字体会模糊（4K 屏拉伸 2 倍 1920 设计稿尤其明显）；事件热区在大比例缩放下可能偏移；屏幕比例和设计稿不一致会留白。

三种方案对比

维度 vw / vh rem transform: scale
实现复杂度 中（每个图表单独适配） 中（需 PostCSS + 根字号脚本） 低（一次封装搞定）
字体清晰度 清晰 清晰 大比例缩放会模糊
事件热区 准确 准确 大比例缩放可能偏移
屏幕比例不一致 不留白，自适应填满 留白居中 留白居中
ECharts 适配 需 fitChartSize 工具 需 fitChartSize 工具 自动跟随，免维护
上手难度 中 中 简单

我的选型建议

  • 追求快速上线 + 客户能接受四周留白 → transform: scale，时间最省
  • 要求大屏在不同比例下都铺满（如户外异形屏） → vw/vh
  • 追求字体清晰度 + 事件热区准确 + 不依赖大量 JS 计算 → rem，综合体验最稳
  • 同时投到多种比例的屏（驾驶舱+监控墙+车机） → 用 rem 或 vw/vh，避免 scale 在大比例下的字体糊问题

三种缩放策略（针对 scale 方案）

策略 实现 视觉效果
等比缩放（推荐） Math.min(scaleX, scaleY) 内容完整可见，可能有黑边
拉伸缩放 scaleX, scaleY 分别赋值 充满整屏，但内容会变形
等比铺满 Math.max(scaleX, scaleY) 充满整屏，但内容会被裁切

90% 场景用第一种。第二种只在容器比例和设计稿比例非常接近时用。第三种几乎用不到。

scale 方案的几个坑

坑 1：echarts 鼠标 hover tooltip 错位

scale 之后，DOM 的实际位置变了，但 echarts 内部计算 hover 还是按原始坐标。表现是鼠标移动到柱子上，tooltip 会偏。

解决：echarts 5.x 内部已经做了 transform 兼容，升级版本即可。如果用的是老版本，需要在 chart.resize() 时把外层 scale 一起考虑进去。

坑 2：input、select 等表单元素事件区域错位

scale 不等于 1 的时候，部分浏览器的点击区域计算会有偏差。如果大屏里有表单交互，改用 position + width/height 直接计算的方案更稳。

坑 3：地图（高德/百度）SDK 在 scale 容器里渲染异常

地图 SDK 内部也用了 transform，套娃了之后手势/缩放会出问题。解决方案是地图区域不参与 scale，单独 absolute 定位、独立计算尺寸。

// 在 resize 时同步更新地图尺寸
function resizeMap() {
  mapContainer.style.width = window.innerWidth + 'px'
  mapContainer.style.height = window.innerHeight + 'px'
  amap.resize()
}

一个更完整的封装

// useScreenScale.js (React Hook)
import { useEffect, useState } from 'react'

export function useScreenScale(designWidth = 1920, designHeight = 1080) {
  const [scale, setScale] = useState(1)

  useEffect(() => {
    const calc = () => {
      const sx = window.innerWidth / designWidth
      const sy = window.innerHeight / designHeight
      setScale(Math.min(sx, sy))
    }
    calc()
    window.addEventListener('resize', calc)
    return () => window.removeEventListener('resize', calc)
  }, [designWidth, designHeight])

  return scale
}

// 使用
function Screen() {
  const scale = useScreenScale()
  return (
    <div style={{ width: '100vw', height: '100vh', overflow: 'hidden', background: '#000', display: 'flex', justifyContent: 'center', alignItems: 'center' }}>
      <div style={{ width: 1920, height: 1080, transform: `scale(${scale})`, transformOrigin: 'center center' }}>
        {/* 大屏内容 */}
      </div>
    </div>
  )
}

大屏 ≠ 只有 PC 可视化大屏

题目里特别提到了——“大屏适配是包含多个端的场景”。我理解这里的”大屏”是个广义概念：屏幕尺寸大于手机的所有展示容器，包括但不限于：

场景 容器特征 推荐方案
PC 可视化大屏 1920×1080 起，固定比例 rem / vw、vh / scale 三选一（按前文标准）
iPad / 平板 H5 768~1366px 宽，竖屏/横屏切换 vw + 媒体查询，限制最大宽度
小程序大屏（PC 微信、iPad、车机） 窗口可拉伸，rpx 无法封顶会失真 resizable:true + <page-meta root-font-size> + rem + 封顶
TV 端 / 智慧屏 1920×1080，遥控器交互 scale 或 rem + 焦点管理
车机 HMI 横屏宽比例（如 1920×720） scale 或 rem，需重新出针对车机比例的设计稿
户外 LED 拼接屏 比例诡异（如 5760×1080） vw/vh 自适应铺满，或单独出”超宽屏”设计稿

核心心法：大屏适配不全是技术问题，更多是设计稿和容器比例匹配的问题。技术上前面三种方案能覆盖绝大多数场景，剩下的需要设计师配合出多套稿子。

我之前接过一个车机项目，设计师交付了一份 1920×1080 的稿子，但车机实际是 1920×720 的横屏比例——硬上去要么左右大量黑边，要么裁掉一半。最后是设计师重新出了一版 1920×720 的稿子才搞定。

跨端项目里的统一适配思路

如果一个项目同时要发 H5、小程序、APP（比如用 Taro、uni-app），适配可以这样统一：

设计稿（750 宽）
    ↓
统一开发单位：rpx / px（让框架转换）
    ↓
H5 编译：postcss 转 vw
小程序编译：原生 rpx
RN/APP 编译：JS 计算 dp

Taro 默认就是这个思路：组件库里写 width: 200px，编译时按目标平台自动转换。uni-app 也类似，推荐用 rpx 写所有尺寸。

跨端框架的”魔法”，本质是编译时单位换算。理解了底层是 vw、rpx、dp 这三种基础方案的统一抽象，就能在出问题的时候定位到正确的层。

选型决策表

项目类型 推荐方案 备注
移动端 H5（活动页、电商） vw + PostCSS 现代首选
移动端 H5（要在 PC 也能打开） rem + max-width 容器限宽 经典方案
响应式 Web（资讯、PC+移动） Flex/Grid + 媒体查询 内容流式适配
微信/支付宝小程序（手机端） rpx 原生支持
微信小程序（PC、iPad、车机大屏） <page-meta root-font-size> + rem + 封顶 + resizable:true rpx 致命问题：无法封顶，大屏会失真
React Native App scale 函数封装，字体单独限制 自己封装
Flutter App flutter_screenutil 社区成熟方案
可视化大屏（追求字体清晰、长期运行） rem 综合体验最稳
可视化大屏（要求铺满异形屏） vw / vh 不留白，自适应填满
可视化大屏（追求快速上线） transform: scale 上手最快
车机/TV/LED 异形大屏 rem 或 vw/vh + 多套设计稿 技术 + 设计配合
Taro/uni-app 跨端项目 统一用 rpx，交给框架编译 别手写各端兼容代码

小结

  1. 移动端 H5 三大方案：rem 适合需要兼容老机型和限宽，vw 适合现代项目首选，Flex/Grid 适合内容型响应式
  2. 1px 边框用 transform: scale 伪元素方案，安全区域用 env(safe-area-inset-*) 配合 viewport-fit=cover
  3. 小程序手机端用 rpx 够了；大屏（iPad/PC/车机）下 rpx 的硬伤是无法封顶，推荐改用 <page-meta root-font-size> + rem + Math.min(maxWidth, screenWidth)/10 封顶，顺便还能和 H5 共用一套 CSS
  4. RN/Flutter/鸿蒙都收敛到了”逻辑像素 + 等比缩放函数”的模式，字体记得单独做上限处理
  5. PC 可视化大屏没有银弹：vw/vh 适合不留白的响应式、rem 综合体验最稳、scale 上手最快但大比例缩放会糊
  6. “大屏”是个广义概念，覆盖 PC 大屏、iPad、TV、车机、LED 拼接屏等，技术方案选完还要看设计稿是否匹配容器比例
  7. 跨端项目用框架的统一单位（Taro 用 px、uni-app 用 rpx），不要手写各端兼容
  8. 适配方案没有最优解，只有最匹配项目场景的解——先想清楚容器、设计稿、用户分布，再选方案
