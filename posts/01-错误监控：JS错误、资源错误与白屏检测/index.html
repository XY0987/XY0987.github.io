错误监控：JS 错误、资源错误与白屏检测

发表于2026|更新于2026|工程化
|字数总计:3.6k|阅读时长:12分钟

前言：前面把测试、CI、部署、性能都做了。但有个残酷的事实——再充分的测试也覆盖不了线上所有情况。用户的设备、网络、操作路径千奇百怪，线上一定会出你没测到的错。「上线后就不管了」和「上线后能第一时间知道哪出错了」，是有没有可观测性的区别。这一篇讲前端监控的第一块：错误监控——怎么捕获线上的各类错误并上报，让你在用户投诉之前就发现问题。

为什么线上错误监控是刚需

测试保证的是「我测过的场景是对的」，但线上会遇到：某个特定机型的浏览器 bug、某个用户的网络导致资源加载失败、某个你没想到的数据边界、某次发布引入的回归……

没有错误监控时，你发现问题的方式是用户投诉——而大部分用户遇到问题是默默离开，不会投诉。等你从客服那听到「有人说页面打不开」，可能已经影响了成千上万人，且你完全不知道是什么错、哪个版本引入的、影响多少人。

错误监控要回答的就是这几个问题：

出了什么错？   → 错误类型、堆栈
在哪出的？     → 页面、代码位置（配合 Source Map）
谁遇到了？     → 影响用户数、设备/浏览器分布
什么时候起的？ → 哪个版本引入的（配合版本映射）

前端错误的几种类型

前端的「错误」不止 try/catch 能抓的那种。要全面监控，得知道有哪些类型、各自怎么捕获：

错误类型 例子 捕获方式
JS 运行时错误 undefined is not a function window.onerror / error 事件
未处理的 Promise 拒绝 fetch 失败没 catch unhandledrejection 事件
资源加载错误 图片/JS/CSS 404 捕获阶段的 error 事件
接口错误 请求返回 500 封装请求层拦截
框架错误 React 渲染报错 错误边界 / 框架 hook
白屏 页面一片空白 单独检测（下面讲）

关键认知：**try/catch 只能抓同步代码里主动包起来的错，远远不够**。异步错误、资源错误、Promise 错误都逃出了 try/catch，得靠全局监听。

全局捕获：一套最小监控代码

用几个全局监听器覆盖大部分错误。这段代码是错误监控的地基：

// 1. JS 运行时错误
window.addEventListener('error', (event) => {
  // 注意：资源加载错误也会走到这里，要区分
  if (event.target && (event.target as HTMLElement).tagName) {
    // 有 tagName 说明是资源加载错误（img/script/link）
    report({
      type: 'resource',
      url: (event.target as HTMLImageElement).src
        || (event.target as HTMLLinkElement).href,
      tag: (event.target as HTMLElement).tagName,
    })
  } else {
    // 普通 JS 错误
    report({
      type: 'js',
      message: event.message,
      filename: event.filename,
      line: event.lineno,
      col: event.colno,
      stack: event.error?.stack,   // stack 是解析定位的关键
    })
  }
}, true)   // ← 关键：true = 捕获阶段，否则抓不到资源错误

// 2. 未处理的 Promise 拒绝
window.addEventListener('unhandledrejection', (event) => {
  report({
    type: 'promise',
    reason: String(event.reason),
    stack: event.reason?.stack,
  })
})

两个极其关键、极其容易踩的细节：

细节一：资源错误必须用「捕获阶段」监听（true）。资源加载失败（img 404）的 error 事件不冒泡，所以挂在 window 上的普通监听（冒泡阶段）根本抓不到。必须用 addEventListener('error', handler, true) 的第三个参数 true，在捕获阶段拦截。这是资源错误监控最经典的坑——很多人监控代码写了却抓不到资源错误，就是漏了这个 true。

细节二：window.onerror 和 error 事件都能抓 JS 错误，但要注意别重复上报。而且 event.target.tagName 是区分「JS 错误」还是「资源错误」的关键——两者都触发 error 事件，但资源错误的 target 是那个 DOM 元素。

框架层错误：错误边界

全局监听抓不到框架内部「优雅处理」掉的错误。React/Vue 有自己的错误捕获机制：

React 错误边界：React 原生错误边界底层还是 componentDidCatch / getDerivedStateFromError，但业务项目里一般不会再手写类组件，可以用 react-error-boundary 这类封装，用函数组件的方式落地：

import { ErrorBoundary } from 'react-error-boundary'

function ErrorFallback({ error, resetErrorBoundary }) {
  return (
    <div>
      <p>这块内容加载失败了</p>
      <button onClick={resetErrorBoundary}>重试</button>
    </div>
  )
}

function App() {
  return (
    <ErrorBoundary
      FallbackComponent={ErrorFallback}
      onError={(error, info) => {
        report({
          type: 'react',
          message: error.message,
          stack: error.stack,
          componentStack: info.componentStack,
        })
      }}
    >
      <ProductDetail />
    </ErrorBoundary>
  )
}

Vue 3 用 app.config.errorHandler 全局捕获组件错误。

框架错误边界的价值不只是上报，还有降级——一个组件崩了，用错误边界兜住，展示「这块加载失败」而不是整个页面白屏。这直接关系到下面的白屏问题。

白屏检测：最严重但最难抓的问题

白屏是最严重的线上事故——用户什么都看不到——但它偏偏最难监控。因为白屏时可能连你的监控 JS 都没跑起来（比如主 bundle 加载失败），或者没有任何 JS 错误抛出（比如渲染逻辑把内容清空了）。

白屏检测没有银弹，几种思路组合用：

1. 采样检测关键区域有没有内容

在页面加载后的某个时间点，检查页面关键区域（如根节点、主内容区）是不是空的。一种简单做法是取屏幕上几个采样点，看它们落在的元素是不是「空容器」（body、根 div），如果大量采样点都是空容器，判定为白屏：

// 简化思路：加载后检查根节点是否有实质内容
setTimeout(() => {
  const root = document.getElementById('app')
  if (root && root.childElementCount === 0) {
    report({ type: 'blankScreen', url: location.href })
  }
}, 5000)   // 给足加载时间再判断

真实的白屏检测更复杂（要排除正常的空状态、加载中等），成熟监控 SDK 用「多点采样 + 判断采样点元素是否在白名单空容器里」的算法。

2. 资源加载失败兜底

主 JS/CSS 加载失败是白屏的常见原因。前面的资源错误监控能抓到关键资源 404，配合「关键资源失败 = 高概率白屏」来告警。

3. 关键渲染打点

在应用成功渲染出首屏内容的地方打一个「渲染成功」的点。如果一段时间内某用户只有「页面开始加载」却没有「渲染成功」的点，大概率白屏了。

白屏检测做不到 100% 准确，目标是「大面积白屏能被发现并告警」。配合发布——白屏率在某次发布后突然飙升，几乎肯定是这次发布引入的，立刻回滚（回滚机制见部署篇）。把白屏率作为一个核心告警指标盯着，比追求单次白屏的精确判定更实用。

上报的工程细节

抓到错误后怎么上报，有几个实践要点：

1. 按场景选择上报方式，不同场景上报方式不同：普通运行时错误（比如 try/catch 里捕获到的业务错误）页面还活着，用 fetch 上报完全可以；页面即将关闭、切后台、卸载前要补发缓存队列时，再优先用 navigator.sendBeacon，因为它就是为这类「页面要走了，但我还想尽量把数据送出去」的场景设计的。

function report(data: object, options: { preferBeacon?: boolean } = {}) {
  const body = JSON.stringify({
    ...data,
    version: __APP_VERSION__,   // 带上版本号，关联到发布
    url: location.href,
    ua: navigator.userAgent,
    time: Date.now(),
  })

  if (options.preferBeacon && navigator.sendBeacon) {
    navigator.sendBeacon('/api/monitor', body)
    return
  }

  void fetch('/api/monitor', {
    method: 'POST',
    body,
    keepalive: true,
    headers: { 'Content-Type': 'application/json' },
  }).catch(() => {
    // 监控上报失败不要影响业务流程
  })
}

我的理解是：错误发生时能马上报就马上报；页面生命周期快结束时，再用 sendBeacon / keepalive 做兜底。别把所有错误都攒到离开页面时再发，那样页面崩得太早、队列丢了，反而更容易漏。

2. 一定要带版本号：上报数据里带上当前应用版本（呼应部署篇的版本映射）。这样才能回答「这个错是哪个版本引入的」，也才能在回滚后确认错误是否消失。

3. 采样与限流：高流量应用如果每个错误都全量上报，监控后端会被打爆，也费钱。对高频错误做采样（比如同一个错误只报前 N 次 + 计数），或整体按比例采样。

4. 去重/聚合：同一个 bug 会产生成千上万条几乎一样的错误。上报或后端要能按「错误指纹（类型+堆栈+位置）」聚合成一个 issue，否则你看到的是几万条噪音而不是「一个影响 3 万人的 bug」。

这些工程细节，成熟的监控 SDK（Sentry 等，下一篇讲）基本都内置了。自建监控则要自己处理。

日志与行为轨迹上报

只上报「错误本身」还不够。一个错误报上来 Cannot read properties of undefined，你知道它错了，但不知道用户是怎么一步步走到这一步的。光有错误、没有上下文，很多 bug 根本复现不出来。这就是日志上报（行为轨迹）要补的那块——记录「出错之前发生了什么」。

面包屑：还原出错前的操作轨迹

最有价值的日志形态是面包屑（breadcrumb）：在内存里维护一个有限长度的环形队列，持续记录用户的关键行为（点击、路由跳转、请求、控制台输出），出错时把这段轨迹连同错误一起上报。

const breadcrumbs: Array<{ type: string; msg: string; time: number }> = []

function addBreadcrumb(type: string, msg: string) {
  breadcrumbs.push({ type, msg, time: Date.now() })
  if (breadcrumbs.length > 30) breadcrumbs.shift()   // 只留最近 30 条，防止无限增长
}

// 在关键节点埋点
addBreadcrumb('route', '进入 /order/123')
addBreadcrumb('click', '点击「提交订单」')
addBreadcrumb('http', 'POST /api/order → 500')
// 出错时，report 里带上 breadcrumbs，就能看到「错误发生前这几步」

关键设计是限长环形队列——只留最近 N 条，既够还原现场，又不会让内存和上报体积无限膨胀。这套「面包屑」正是 Sentry 等平台的核心能力之一（下一篇会看到 Sentry.init 自动帮你记录），自建时要自己实现。

日志分级：别把所有东西都当同一级

日志和后端一样要分级，不同级别对应不同的上报策略，否则要么漏掉关键信息，要么被海量 debug 日志淹没：

级别 用途 上报策略
error 已发生的错误 实时上报
warn 可疑但未出错（降级、重试） 上报，用于预警
info 关键业务节点（下单、支付） 采样上报
debug 开发排查用 生产默认不报

核心原则：级别越低越啰嗦，越要控制上报量。debug 日志在生产环境默认关掉（或只在「捞日志」排查特定用户时按需开启），别让它们平时就往后端灌。

批量上报：别一条一条发

行为日志的量远大于错误——一次会话可能产生几百条。如果每条都单独发送，会产生大量请求，既费性能又打爆后端。正确做法是攒批 + 时机触发：

let buffer: object[] = []

function log(entry: object) {
  buffer.push(entry)
  if (buffer.length >= 10) flush()   // 攒够 10 条发一次
}

function flush() {
  if (buffer.length === 0) return
  // fetch 第二个参数是 RequestInit 对象，不能直接传字符串；
  // keepalive 保证页面卸载时请求也能发出去（body 有 64KB 限制）
  fetch('/api/logs', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(buffer),
    keepalive: true,
  })
  buffer = []
}

// 页面隐藏/卸载时把剩余的兜底发出去，别丢
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flush()
})

两个要点：用 visibilitychange 的 hidden 而不是 unload 做兜底 flush（移动端和 bfcache 场景 unload 常不触发，visibilitychange 更可靠）；以及页面隐藏时一定要把 buffer 里剩下的发掉，否则最后几条（往往正是接近出错的关键行为）会丢。

和错误监控的关系

理清三者的定位，别混为一谈：错误上报是「结果」，日志/面包屑是「过程」，两者要能关联。上报错误时带上 sessionId（本次会话唯一 id），日志也带同一个 sessionId，后端就能把「这个错误」和「这个用户这次会话的完整行为轨迹」拼起来。这才是从「知道错了」到「知道为什么错」的关键一步——排查线上疑难 bug 时，能回放用户轨迹，比对着一条干巴巴的堆栈猜要高效得多。

小结

  1. 测试覆盖不了线上所有情况，错误监控让你在用户投诉前发现问题，回答「什么错、在哪、谁遇到、哪个版本引入」。
  2. try/catch 只能抓主动包起来的同步错误，异步/资源/Promise 错误必须靠全局监听。
  3. 资源加载错误不冒泡，必须用 addEventListener('error', handler, true) 的捕获阶段才能抓到——这是最经典的坑。
  4. 用 event.target.tagName 区分 JS 错误和资源错误；unhandledrejection 抓未处理的 Promise 拒绝。
  5. 框架用错误边界（React componentDidCatch / Vue errorHandler）捕获并降级，避免单组件崩溃引发整页白屏。
  6. 白屏最严重也最难抓，用「采样检测空容器 + 资源失败兜底 + 关键渲染打点」组合，目标是大面积白屏能告警，配合发布快速回滚。
  7. 上报用 sendBeacon、必带版本号、做采样限流和按错误指纹去重聚合。
  8. 只报错误不够，用限长环形队列的面包屑记录出错前的行为轨迹；日志分级控制上报量、批量上报并在 visibilitychange: hidden 时兜底 flush；用 sessionId 把错误（结果）和日志（过程）关联起来。
