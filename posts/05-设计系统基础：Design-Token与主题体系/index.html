设计系统基础：Design Token 与主题体系

发表于2026|更新于2026|工程化
|字数总计:4.4k|阅读时长:16分钟

前言：上一篇讲组件库样式时反复提到「主题相关的值走 CSS 变量」，那些值就是 Design Token。这一篇专门讲 token 这套东西：它怎么组织、怎么导出成多端能用的格式、以及基于它怎么实现暗色模式和品牌主题切换。Design Token 是组件库从「一堆组件」升级成「设计系统」的分水岭——没有 token，主题、多端、暗色都是硬编码堆出来的，改起来要命。

什么是 Design Token

Design Token 就是把设计决策抽象成有名字的变量。

设计师说「主色是 #1677ff」，如果直接把 #1677ff 写死在几十个组件里，改主色就得全局搜替换，还容易漏。Token 的做法是给它起个名字：

color.primary = #1677ff

然后所有组件引用 color.primary，而不是 #1677ff。改主色只改一处。

这听起来就是「变量」，但 Design Token 的价值不止于此——它是设计和代码之间的契约，也是一份能被翻译成任何平台格式的中立数据。同一份 token，可以导出成 Web 的 CSS 变量、小程序的 WXSS、React Native 的 JS 对象、iOS 的 Swift、Android 的 XML。这是它区别于「随手定义几个 SCSS 变量」的关键。

Token 的三层组织

只有一层 token 是新手常犯的错。成熟的 token 体系是分层的，通常三层：

① 基础层 (Global / Primitive)   —— 纯粹的值，不带语义
   color.blue.500 = #1677ff
   color.gray.900 = #1a1a1a
   space.4 = 16px

② 语义层 (Semantic / Alias)     —— 带语义，引用基础层
   color.primary        → color.blue.500
   color.text.primary   → color.gray.900
   color.bg.container   → color.white

③ 组件层 (Component)             —— 组件专属，引用语义层
   button.color.bg      → color.primary
   button.padding.x     → space.4

为什么要分层？看一个场景就懂了：

  • 暗色模式：只改语义层（color.text.primary 在暗色下指向浅色），基础层的调色板不动，组件层自动跟随。
  • 换品牌主题：只改语义层（color.primary 指向另一个色阶），组件层不用动。
  • 调某个组件：只改组件层（button.padding.x），不影响其它组件。

分层的本质是让「值」和「用途」解耦。基础层是「有哪些颜色」，语义层是「这些颜色在什么场景用」，组件层是「这个组件用哪个场景的颜色」。改动被限制在最小范围。

没分层的 token 表：几百个 token 平铺，暗色模式要改一半，改完还担心漏，心智负担很重。分层之后，暗色只需重定义十几个语义 token。

用 Style Dictionary 导出多端格式

Token 分层设计好了，怎么变成各端能用的东西？如果只做 Web，手写 CSS 变量也行。但一旦要多端（Web / 小程序 / RN），就需要「一份 token 源，导出多种格式」的工具。社区标准是 Style Dictionary（Amazon 出的）。

思路是：token 用平台无关的 JSON 定义，Style Dictionary 根据配置把它「翻译」成各平台格式。

它的原理可以拆成四步：

token 源文件
   ↓  读取 JSON / JSONC / JS 等 token 数据
解析引用
   ↓  把 {color.blue.500} 这类 alias 关系串起来
按平台 transform
   ↓  例如命名转成 kebab-case，尺寸单位转成 px / dp / sp
按 format 输出文件
      例如 CSS 变量、SCSS 变量、JS 对象、Android XML、iOS Swift

这里最容易误解的是 transform。Style Dictionary 的 transform 是token 级别的值转换和命名转换，不是 CSS 编译。比如它可以把 color.primary 转成 --color-primary，把颜色值格式化成十六进制，把尺寸单位按平台转成 dp / sp。但它不会像 PostCSS、Lightning CSS、Babel 那样做 CSS 语法降级，也不会自动加浏览器前缀。

换句话说，它关心的是「设计 token 怎么变成各端能读的变量文件」，不关心「业务 CSS 怎么兼容不同浏览器」。

先写 token 源（JSON）：

// tokens/color.json
{
  "color": {
    "blue": { "500": { "value": "#1677ff" } },
    "primary": { "value": "{color.blue.500}" }
  }
}

注意 {color.blue.500} 是引用——语义层引用基础层，Style Dictionary 会自动解析。

配置导出目标：

// style-dictionary.config.js
export default {
  source: ['tokens/**/*.json'],
  platforms: {
    // Web：CSS 变量
    css: {
      transformGroup: 'css',
      buildPath: 'dist/css/',
      files: [{ destination: 'vars.css', format: 'css/variables' }],
    },
    // JS：给 RN / JS 逻辑用
    js: {
      transformGroup: 'js',
      buildPath: 'dist/js/',
      files: [{ destination: 'tokens.js', format: 'javascript/es6' }],
    },
    // 小程序：可用 CSS 变量或自定义 format 生成 WXSS
    miniprogram: {
      transformGroup: 'css',
      buildPath: 'dist/mp/',
      files: [{ destination: 'vars.wxss', format: 'css/variables' }],
    },
  },
}

跑 style-dictionary build，一份 JSON 就产出了三端的 token 文件：

/* dist/css/vars.css */
:root {
  --color-blue-500: #1677ff;
  --color-primary: #1677ff;
}

// dist/js/tokens.js
export const ColorBlue500 = '#1677ff'
export const ColorPrimary = '#1677ff'

所以答案是：Style Dictionary 能打包出 CSS 文件，但它打包的是 token 产物，不是完整意义上的 CSS 工程产物。css/variables 这个 format 会生成一份合法的 CSS 变量文件，你可以把它发布到 npm 包里，再通过稳定入口给应用引入：

import '@my-ui/theme/css'

但它的边界也要说清楚：

能做 不做
读取 token 源文件 编译业务 CSS / Less / Sass
解析 token 引用 给 CSS 自动加前缀
按平台转换 token 名称和值 做浏览器语法降级
生成 CSS 变量、JS、XML、Swift 等文件 做 CSS tree-shaking、压缩、抽取、代码分割

把 Style Dictionary 放在 @my-ui/theme 的构建阶段，负责产出 dist/css/vars.css、dist/js/tokens.js 这类主题原料；应用或组件库自己的样式，仍然交给 Vite / Rspack / Webpack + PostCSS / Lightning CSS 去处理。尤其是组件 CSS 里的嵌套语法、现代选择器兼容、前缀、压缩、抽取顺序，这些都不应该指望 Style Dictionary 解决。

如果你的 vars.css 已经只是简单的 :root { --xxx: value; }，它本身可以直接作为静态 CSS 发布；但只要进入真实项目，通常还是会被打包工具一起处理、合并和压缩。Style Dictionary 负责「生成变量」，CSS 工程链路负责「消费变量」。

落到组件库里，它只影响变量这一层。组件样式还是正常写 CSS / Sass / CSS Modules / Vanilla Extract，只是把颜色、字号、间距、圆角、阴影这类需要主题化的值，改成引用 CSS 变量：

.myui-button {
  display: inline-flex;
  align-items: center;
  padding: var(--myui-button-padding-y) var(--myui-button-padding-x);
  border-radius: var(--myui-radius-md);
  color: var(--myui-color-text-on-primary);
  background: var(--myui-color-primary);
}

display、position、flex、动画、选择器、响应式这些结构性样式，还是组件 CSS 自己负责。Style Dictionary 不会替你写组件样式，也不会把组件 CSS “token 化”。它只是提供一批稳定的变量，让组件 CSS 有东西可引用。

组件库开发和使用是两个阶段

这里要分清楚两个阶段：组件库开发阶段和业务项目使用阶段。很多困惑都来自把这两个阶段混在一起：一会儿看源码，一会儿看 dist，一会儿又问业务项目还要不要打包。

先看组件库开发阶段。在 Monorepo 里，开发者面对的是源码：

packages/theme/
  tokens/*.json
  style-dictionary.config.js

packages/components/
  src/button/index.tsx
  src/button/style.css

开发时通常有一个 playground 或 docs 作为内部消费者，但这里有两种模式，别混：

模式 怎么做 适合什么
源码直连 docs / playground 通过 alias 指到 packages/components/src 调组件逻辑、样式、交互，反馈最快
构建产物联调 各包 watch 生成 dist，docs / playground 像外部用户一样 import 包入口 验证 exports、样式产物、类型产物、按需引入

社区里两种都会用。日常开发更偏源码直连，因为改一个组件马上热更新，不需要每次都等库完整构建；但发版前一定要跑构建产物联调，否则你不知道 npm 用户拿到的 exports、dist、sideEffects、CSS 文件是不是完整的。

根目录任务一般会这样组织：

{
  "scripts": {
    "dev": "turbo run dev --parallel",
    "build": "turbo run build",
    "preview:package": "turbo run build && pnpm --filter docs dev"
  }
}

对应到包内部，theme 比较特殊：它的源码是 token JSON，业务侧真正要用的是生成后的 CSS 变量或 JS token，所以开发时通常要开 watch：

{
  "name": "@my-ui/theme",
  "scripts": {
    "dev": "style-dictionary build --watch",
    "build": "style-dictionary build"
  }
}

这不是因为开发者“只能引用 dist/css”，而是因为 tokens/*.json 本身不是浏览器能直接消费的样式。你可以让 docs 写稳定入口：

import '@my-ui/theme/css'

然后由 exports 映射到 dist/css/vars.css。开发时 style-dictionary build --watch 负责持续刷新这份生成物。

components 则不一定要在日常开发时先构建再调试。很多组件库会让 docs / playground 直接 alias 到源码：

// docs/vite.config.ts
import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'

export default defineConfig({
  resolve: {
    alias: {
      '@my-ui/components': fileURLToPath(new URL('../packages/components/src', import.meta.url)),
    },
  },
})

这样开发组件时走的是源码热更新；等要验证发布形态时，再切到构建产物：

把这件事压缩成一句话就是：theme 变量通常始终消费生成物，components 开发时消费源码、发布后消费构建产物。

包 组件库开发阶段 业务项目使用阶段
@my-ui/theme style-dictionary build --watch 生成 dist/css/vars.css，通过 @my-ui/theme/css 引入 安装 npm 包后仍通过 @my-ui/theme/css 引入，实际指向包内 dist/css/vars.css
@my-ui/components docs / playground alias 到 packages/components/src，走源码热更新 安装 npm 包后通过 @my-ui/components 引入，实际消费 dist/index.mjs、组件 CSS 和类型产物 
{
  "name": "@my-ui/components",
  "scripts": {
    "build": "vite build && tsc --emitDeclarationOnly",
    "build:watch": "vite build --watch"
  },
  "dependencies": {
    "@my-ui/theme": "workspace:*"
  }
}

这一步的目标不是生成最终页面，而是把源码加工成可发布、可被消费的库产物。注意这里的关系：@my-ui/theme 产出变量，@my-ui/components 的 CSS 消费这些变量。

@my-ui/theme
  tokens/*.json
      ↓ Style Dictionary
  dist/css/vars.css
  dist/js/tokens.js

@my-ui/components
  src/**/*.tsx / src/**/*.css
      ↓ 正常编写组件 CSS，并在主题相关值上使用 var(--myui-xxx)
      ↓ tsup / Vite lib / Rollup
  dist/index.mjs
  dist/index.d.ts
  dist/button/style.css

所以，更准确的说法是：开发时不一定每次都先构建整个组件库，但组件库发布前必须构建。theme 在开发时也常常需要 watch 生成 CSS 变量，因为 token JSON 不是最终 CSS；components 日常可以源码直连，发版前再构建验证。社区里的成熟组件库基本都是这个思路：变量层消费生成物，组件层开发看源码和 HMR，发布质量看构建产物。

再看业务项目使用阶段。用户安装的是发布后的 npm 包，不是你的源码目录：

pnpm add @my-ui/components @my-ui/theme

业务代码里应该通过包暴露出来的稳定入口使用：

import { Button } from '@my-ui/components'
import '@my-ui/theme/css'

背后靠 package.json 的 exports 把这些入口映射到 dist：

{
  "name": "@my-ui/theme",
  "exports": {
    "./css": "./dist/css/vars.css",
    "./tokens": {
      "types": "./dist/js/tokens.d.ts",
      "import": "./dist/js/tokens.js"
    }
  },
  "sideEffects": ["**/*.css"]
}

也就是说，dist 是包作者的发布产物目录，不是希望用户记住的 API。用户可以间接用到 dist，但最好不要直接写 @my-ui/theme/dist/css/vars.css，否则以后你调整目录结构就是破坏性变更。

那业务项目还要不要构建？要。组件库构建只解决「库源码变成可发布产物」；业务项目构建负责把应用代码、组件库 ESM、CSS 变量文件、组件样式一起打进最终产物，并根据业务项目自己的浏览器目标做降级、前缀、压缩和代码分割。

阶段一：组件库构建
packages/*/src 或 tokens → packages/*/dist → 发布到 npm

阶段二：业务应用构建
app 源码 + node_modules 里的组件库 dist → 最终浏览器资源

组件库必须构建后再发布，业务应用也必须再构建一次。前者是把库变成稳定商品，后者是把商品装进具体项目。不要让业务项目依赖组件库源码，也不要让用户依赖未声明的 dist 深层路径；稳定 API 应该由 exports 定义。

多端复用的价值就在这：设计改一次 token 源，Web、小程序、RN 全部同步更新，不会出现「Web 主色改了，小程序忘了改」的漂移。这也呼应了组件库工程结构篇里 @my-ui/theme 独立成包的设计——token 是所有端共享的原料。

提醒：Web 端能用 CSS 变量，但 React Native 不支持 CSS 变量（RN 没有 CSS 运行时），所以 RN 要用导出的 JS 对象，在样式里引用 ColorPrimary。小程序的 WXSS 支持 CSS 变量，可以走 CSS 变量方案。多端不是「同一套机制」，而是「同一份 token 源翻译成各端各自的机制」。

主题切换：暗色模式怎么落地

有了分层 token 和 CSS 变量，暗色模式就不再是「写两套样式」，而是「换一组语义层变量值」。

核心机制：把语义 token 的值挂在一个可切换的作用域上（html 的 data-theme 属性或 class）。

/* 亮色（默认） */
:root {
  --color-text-primary: #1a1a1a;
  --color-bg-container: #ffffff;
}

/* 暗色：只重定义语义层，基础调色板不变 */
:root[data-theme='dark'] {
  --color-text-primary: #e5e5e5;
  --color-bg-container: #1a1a1a;
}

组件代码完全不感知主题，它只认变量：

.myui-card {
  color: var(--color-text-primary);
  background: var(--color-bg-container);
}

切换只需改一个属性：

function setTheme(theme: 'light' | 'dark') {
  document.documentElement.dataset.theme = theme
  localStorage.setItem('theme', theme)   // 记住用户选择
}

这套设计的漂亮之处：组件对主题零感知，加多少主题都不用动组件代码。想加「护眼绿」「高对比」主题，就是多几组语义变量而已。

跟随系统 + 避免闪烁

跟随系统偏好用媒体查询检测：

const prefersDark = window.matchMedia('(prefers-color-scheme: dark)')
prefersDark.addEventListener('change', (e) => {
  setTheme(e.matches ? 'dark' : 'light')
})

这里有个真实的坑：暗色模式的「首屏闪白」。如果切主题的 JS 在页面渲染后才执行，用户会先看到亮色、再闪成暗色。解法是把读取并应用主题的脚本内联在 <head> 最前面、同步执行，在首次渲染前就把 data-theme 定下来：

<head>
  <script>
    // 阻塞式、极小的一段，必须在 body 渲染前跑
    const t = localStorage.getItem('theme')
      || (matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light')
    document.documentElement.dataset.theme = t
  </script>
  <!-- 其它资源 -->
</head>

这段脚本要小、要同步、要在最前面。这是几乎所有支持暗色的站点（包括各大文档站）都会做的处理。

品牌主题：多品牌换肤

暗色是「同一品牌的两种明暗」，品牌主题是「不同品牌的不同色系」。机制完全一样——换一组语义 token。

:root[data-brand='purple'] {
  --color-primary: #7c3aed;
  --color-primary-hover: #6d28d9;
}
:root[data-brand='green'] {
  --color-primary: #16a34a;
  --color-primary-hover: #15803d;
}

data-theme（明暗）和 data-brand（品牌）可以正交组合，用户可以选「暗色 + 紫色品牌」。这就是「换肤」功能的工程底座。

只要产品有多品牌、多主题或暗色需求，就应该从一开始上分层 token + CSS 变量。等硬编码颜色铺满全项目再回头改，成本是数量级的差异。这也是为什么设计系统要「先立 token，再写组件」。

小结

  1. Design Token 是有名字的设计决策，也是设计与代码的契约、能翻译成多端格式的中立数据。
  2. Token 要分三层：基础层（纯值）、语义层（带用途）、组件层（组件专属），让「值」和「用途」解耦，改动最小化。
  3. 用 Style Dictionary 把一份 JSON token 源导出成 Web CSS 变量、JS 对象、小程序 WXSS 等多端格式，避免多端漂移。
  4. Style Dictionary 能生成 CSS 变量文件，但它不是 CSS 编译器；前缀、降级、压缩、抽取仍然交给打包工具和 CSS 处理链路。
  5. 变量层通常始终消费生成物：开发时 watch 生成 dist/css/vars.css，使用时通过 @my-ui/theme/css 间接引用这份产物。
  6. 组件层开发时可以源码直连和 HMR，发布后用户消费的是构建后的 ESM、CSS 和类型产物。
  7. RN 不支持 CSS 变量要用 JS 对象；多端是「同一份 token 翻译成各端机制」，不是同一套机制。
  8. 暗色模式靠重定义语义层 CSS 变量 + data-theme 切换，组件对主题零感知。
  9. 暗色首屏闪白的解法是在 <head> 最前内联同步脚本，在首次渲染前定好主题。
  10. 品牌主题和暗色机制相同，data-theme 与 data-brand 可正交组合；有多主题需求就从一开始上分层 token。
