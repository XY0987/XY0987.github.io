E2E 测试：Playwright 端到端测试

发表于2026|更新于2026|工程化
|字数总计:2.1k|阅读时长:7分钟

前言：前两篇的单元测试和组件测试都跑在 jsdom 里——一个用 JS 模拟的假 DOM。它们快、稳，但盖不住「真实浏览器里整条流程走不走得通」。用户从打开首页、登录、下单到看到结果，这一整条链路要在真浏览器里验证，这就是 E2E（端到端）测试。工具我选 Playwright：微软出的，跨浏览器、稳、自带一堆治「flaky」的机制。

E2E 测什么，不测什么

E2E 在测试金字塔的最顶端——最贵、最慢、最脆，但最接近真实。正因为贵，E2E 要测的是「关键用户旅程」，不是覆盖所有细节。

组件测试（jsdom）      → 单个组件的行为、分支、校验
E2E（真实浏览器）      → 跨页面的完整流程、真实渲染、真实网络

哪些该写 E2E，我的判断标准是「这条流程挂了，业务是不是就废了」：

值得写 E2E 不值得写 E2E
登录 / 注册主流程 某个按钮 hover 变色
下单 / 支付 / 提交表单 单个输入框的字符校验
核心页面能正常打开、关键内容渲染 组件内部的条件分支
跨页面跳转与状态保持 纯计算逻辑

右边那些交给组件测试和单元测试，它们又快又便宜。E2E 数量应该很少但很关键——十几条核心旅程，比几百条脆弱的 E2E 有用得多。

最小可运行示例

环境：Node.js 20、Playwright 1.4x。用官方脚手架初始化：

pnpm create playwright

它会装 @playwright/test、下载浏览器内核（Chromium / Firefox / WebKit）、生成配置和示例。装完写一条测试 e2e/login.spec.ts：

import { test, expect } from '@playwright/test'

test('用户能登录并看到欢迎语', async ({ page }) => {
  await page.goto('/login')

  // 用可访问性语义定位，和 Testing Library 一个思路
  await page.getByLabel('用户名').fill('ann')
  await page.getByLabel('密码').fill('secret')
  await page.getByRole('button', { name: '登录' }).click()

  // 断言跳转后看到欢迎语
  await expect(page.getByText('欢迎，ann')).toBeVisible()
  await expect(page).toHaveURL('/dashboard')
})

跑测试：

npx playwright test

它会在真实（无头）浏览器里跑完整流程。加 --headed 能看到浏览器实际操作，调试时很有用：

npx playwright test --headed --project=chromium

Playwright 的定位器（getByRole / getByLabel / getByText）刻意和 Testing Library 保持一致——都是「按用户能感知的东西定位」。学过上一篇，这里几乎无缝衔接。

Playwright 最值得称道的：自动等待

E2E 最大的痛点是 flaky（不稳定）：同一条测试，有时绿有时红，往往是因为「元素还没出现/还不可点，测试就去操作了」。老一代工具（Selenium）要手动 sleep 或写各种显式等待，写起来又累又不可靠。

Playwright 的杀手锏是自动等待（auto-waiting）。每个操作前，它会自动等目标元素满足「可操作」条件——存在、可见、稳定（停止动画）、可接收事件、未被遮挡——满足了才操作，超时才失败。

// 不需要任何 sleep，Playwright 会自动等按钮出现且可点击
await page.getByRole('button', { name: '提交' }).click()

// 断言也会自动重试，直到成立或超时
await expect(page.getByText('提交成功')).toBeVisible()

expect(locator) 系列断言是会自动重试的（web-first assertions），这点极其关键。它和普通的 expect(value) 不一样——expect(page.getByText(...)).toBeVisible() 会在超时时间内反复检查，直到可见。所以 E2E 里**几乎不需要写 page.waitForTimeout**，写了往往就是引入 flaky 的根源。

Playwright 测试里出现 waitForTimeout(固定毫秒)，基本都是可以删掉、改成自动等待的。

配置：baseURL、多浏览器与自动起服务

playwright.config.ts 里几个关键配置：

import { defineConfig, devices } from '@playwright/test'

export default defineConfig({
  testDir: './e2e',
  use: {
    baseURL: 'http://localhost:4173',   // page.goto('/login') 会拼在这后面
    trace: 'on-first-retry',            // 首次重试时录 trace，用于排查
  },
  // 多浏览器矩阵：一套用例跑三个内核
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox', use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
  ],
  // 关键：让 Playwright 自己启动被测服务，跑完自动关
  webServer: {
    command: 'pnpm preview',
    url: 'http://localhost:4173',
    reuseExistingServer: !process.env.CI,
  },
})

webServer 这个配置解决了 E2E 的一大工程痛点：测试前得先把应用跑起来。配好之后，playwright test 会自动执行 pnpm preview 启动服务、等它就绪、再开始测、跑完关掉。CI 里就不用手动 preview & 再 sleep 等启动了。

projects 让同一套用例在 Chromium / Firefox / WebKit 三个内核跑——这是组件测试给不了的「真实跨浏览器」能力，尤其 WebKit（Safari 内核）常有独特的兼容性问题。

治 flaky：Playwright 给的三件工具

E2E 稳定性是长期战斗。Playwright 提供了几个专门武器：

1. Trace Viewer（时间旅行调试）

配了 trace: 'on-first-retry' 后，失败重试会录下完整 trace：每一步的 DOM 快照、网络、控制台、截图。用命令打开：

npx playwright show-trace trace.zip

你能像录像一样回放测试的每一步，看到失败那一刻页面长什么样。排查 CI 上「本地跑不出来」的偶发失败，这是最有效的工具，不用再靠猜。

2. 重试（retries）

CI 上允许失败自动重试几次，把偶发抖动过滤掉：

export default defineConfig({
  retries: process.env.CI ? 2 : 0,   // CI 重试 2 次，本地不重试
})

但要清醒：重试是止血，不是根治。如果一条测试老靠重试才过，说明它本身有问题（依赖了时序、共享了状态），该去修它，而不是把重试次数往上加。本地设 0 就是为了逼自己在本地就把 flaky 修掉。

3. 用 codegen 录制

不想手写定位器，可以录：

npx playwright codegen http://localhost:4173

它会打开浏览器，你操作，它实时生成代码。生成的定位器质量还不错（优先用 role/label）。可以用它起个草稿，再手动清理断言——录出来的适合当起点，不适合直接当最终用例。

一个真实的坑：登录态每条用例都重跑一遍

现象：几十条 E2E 每条开头都先登录一遍，整个套件慢得离谱。

原因：每个 test 默认是全新的浏览器上下文，登录态不共享，于是重复登录。

解决：用 Playwright 的 storageState 把登录态存下来，后续用例直接复用，跳过登录步骤。做法是写一个「setup 项目」先登录并保存状态：

// auth.setup.ts —— 只跑一次，把登录后的 cookie/localStorage 存成文件
import { test as setup } from '@playwright/test'

setup('登录并保存状态', async ({ page }) => {
  await page.goto('/login')
  await page.getByLabel('用户名').fill('ann')
  await page.getByLabel('密码').fill('secret')
  await page.getByRole('button', { name: '登录' }).click()
  await page.waitForURL('/dashboard')
  await page.context().storageState({ path: 'e2e/.auth/user.json' })
})

然后让业务用例复用这个状态：

export default defineConfig({
  projects: [
    { name: 'setup', testMatch: /auth\.setup\.ts/ },
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'], storageState: 'e2e/.auth/user.json' },
      dependencies: ['setup'],   // 先跑 setup，再跑本项目
    },
  ],
})

这样登录只做一次，几十条用例直接带着登录态跑，套件时间能砍掉一大截。E2E 的性能优化，很多时候就是「消除重复的前置步骤」。

小结

  1. E2E 在真实浏览器里测「关键用户旅程」，数量要少而精，细节交给组件/单元测试。
  2. Playwright 跨 Chromium / Firefox / WebKit，定位器思路和 Testing Library 一致（优先 role/label）。
  3. 自动等待是核心优势：操作和 expect(locator) 断言都会自动重试，几乎不需要 waitForTimeout。
  4. webServer 配置让 Playwright 自动起服务、跑完关掉，省去手动启动的工程麻烦。
  5. Trace Viewer 能回放失败的每一步，是排查 CI 偶发失败的利器。
  6. 重试是止血不是根治，老靠重试才过的用例要去修根因；本地设 0 逼自己修 flaky。
  7. 用 storageState 复用登录态，避免每条用例重复登录，大幅缩短套件耗时。
