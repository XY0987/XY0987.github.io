Claude Code Dynamic Workflows 动态工作流解析：让 Agent 学会给自己搭执行框架

发表于2026|更新于2026|AI相关
|字数总计:5.7k|阅读时长:18分钟

前言：Claude Code 这次随 Opus 4.8 被讨论最多的新概念之一，是 Dynamic Workflows，中文一般叫“动态工作流”。我的理解是：它不是简单的“多开几个 Agent”，而是让 Claude Code 在执行复杂任务时，先为任务临时写一套可执行的调度框架，再用这套框架去组织多个子 Agent 干活。

先说明一下信息来源：目前我能查到的公开资料里，Dynamic Workflows 的详细解释主要来自 Anthropic 工程师 Thariq Shihipar / Sid Bidasaria 关于 Claude Code 的文章和多篇转述整理；Claude Code 官方 Overview 文档页面暂时还没有把 Dynamic Workflows 作为独立功能页展开。因此，本文重点讲概念、用途和工程意义，具体内部 API 不做臆测。

一句话理解动态工作流

动态工作流 = Claude Code 根据当前任务，现场生成一段 JavaScript 执行框架，用它来调度多个子 Agent、验证者、评审者和汇总者。

如果用现实世界类比：

  • 普通 Claude Code：像一个很强的工程师，自己读需求、改代码、跑测试、总结结果。
  • Sub Agent：像你临时喊了几个同事帮忙，每个人负责一小块。
  • Dynamic Workflows：像项目经理先写了一份“任务作战图”，明确谁查什么、谁验证谁、什么时候汇总、什么时候停止。

它的关键不是“并行数量”，而是 执行结构。

普通 Agent：

用户目标
  │
  ▼
┌──────────────────────┐
│ 单个 Claude 上下文     │
│ 思考 → 工具 → 观察      │
│ 再思考 → 再工具         │
└──────────────────────┘
  │
  ▼
结果

Dynamic Workflows：

用户目标
  │
  ▼
┌──────────────────────────────┐
│ Claude 先生成 JavaScript Harness │
│ 拆任务 / 分配 Agent / 设置停止条件 │
└──────────────┬───────────────┘
               ▼
   ┌───────────┼───────────┐
   ▼           ▼           ▼
子 Agent A   子 Agent B   子 Agent C
   │           │           │
   └──────┬────┴────┬──────┘
          ▼         ▼
      Verifier    Reviewer
          │         │
          └────┬────┘
               ▼
            汇总结果

这就是为什么很多文章会把它叫作 harness：不是让 Agent 直接冲出去干活，而是先给这次任务搭一个“执行框架”。

它解决的不是“会不会做”，而是“怎么组织做”

在 Claude Code 之前，很多人已经会用多窗口、多终端、多 Agent 并行工作了。比如一个 Claude 负责写代码，一个 Claude 负责 Review，一个 Claude 负责查文档。

但这种方式有几个问题：

问题 人工多开 Agent Dynamic Workflows
任务拆分 人手动拆 Claude 根据任务动态拆
执行顺序 人手动协调 JavaScript harness 协调
中间状态 散落在多个对话里 由 workflow 保存和汇总
验证逻辑 靠人提醒 可以显式安排 verifier / reviewer
可复用性 经验在脑子里 可以保存为 workflow 或 Skill

所以它更像是从“聊天式编程”往“任务运行时”迈了一步。

我的判断是：Claude Code 这次想解决的，不是单个模型智商不够，而是复杂任务里的组织成本太高。

为什么普通 Agent 会在复杂任务上失效

动态工作流的背景，是单 Agent 在长任务里有几个很典型的问题。

问题一：Agentic Laziness，做到一半就说完成

这个现象很多人应该都遇到过：你让 AI 检查 50 个文件，它看了 15 个，然后告诉你“整体看起来没问题”。

不是它不会检查，而是任务太长以后，它会倾向于提前收敛。

动态工作流的处理方式是：

  • 先把 50 个文件拆成多个明确子任务；
  • 每个子 Agent 只负责一小块；
  • 最后再安排汇总 Agent 检查“有没有遗漏”。

这样任务完成度不再完全依赖单个上下文的自觉性。

问题二：Self-preferential Bias，自己审自己总觉得不错

让 Claude 自己写代码，再让它自己 Review，很容易出现一个问题：它天然更愿意相信自己的方案。

人也一样。自己刚写完的代码，第一遍 Review 往往看不出问题。

动态工作流可以把角色拆开：

  • Writer Agent：只负责产出方案；
  • Reviewer Agent：只负责找问题；
  • Refuter Agent：专门反驳结论；
  • Synthesizer Agent：只负责汇总可信结果。

重点是这些 Agent 有独立上下文，不共享同一套“自我辩护逻辑”。

问题三：Goal Drift，跑着跑着目标变了

长对话、多轮工具调用、上下文压缩以后，Agent 很容易忘掉最初的约束。

比如一开始说“不要改公共 API”，执行到后面它可能为了修测试顺手把 API 改了。

动态工作流可以把目标、约束、停止条件写进 harness，让执行框架反复约束各个子任务：

  • 目标是什么；
  • 哪些文件不能动；
  • 什么叫完成；
  • 什么时候需要人工确认；
  • 哪些结果必须经过 verifier。

这比单纯在开头写一句“请注意不要忘记”可靠得多。

动态工作流和传统 Workflow 的区别

很多人听到 workflow，会想到 GitHub Actions、CI Pipeline、LangGraph 这类“先设计流程，再按流程执行”的系统。

Dynamic Workflows 的区别在于：流程不是人提前写死的，而是 Claude 根据当前任务临时生成的。

维度 传统工作流 Dynamic Workflows
谁设计流程 人类工程师 Claude 根据任务生成
流程形态 静态、固定 动态、任务相关
适合任务 稳定重复任务 复杂、开放、变化大的任务
执行逻辑 预定义节点和边 JavaScript harness + 子 Agent
调整方式 修改配置 / 代码 任务中动态调整

传统 workflow 适合“每天凌晨跑构建、测试、部署”。

动态工作流适合“帮我分析这个大型仓库为什么最近测试经常偶发失败，并给出可信根因”。

前者确定性强，后者探索性强。

它大概是怎么工作的

公开资料里反复提到一个关键词：JavaScript harness。

我的理解可以拆成四步。

第一步：分析任务，判断是否需要 workflow

不是所有任务都该用动态工作流。

如果你只是让 Claude Code 改一个按钮文案，开 workflow 就是浪费。

适合开 workflow 的任务通常有几个特征：

  • 工作量大：涉及很多文件、很多数据、很多工单；
  • 可以并行：子任务之间互相依赖少；
  • 需要验证：不能只相信一个 Agent 的结论；
  • 任务周期长：可能跑很久，中间需要恢复；
  • 目标容易漂移：约束条件多，执行路径不确定。

第二步：生成 JavaScript 执行框架

Claude 会为这次任务生成一段 JavaScript 脚本。

这段脚本不是业务代码，而是“调度代码”，负责：

  • 拆分任务；
  • 启动多个子 Agent；
  • 控制并行度；
  • 收集中间结果；
  • 做过滤、排序、投票、验证；
  • 判断是否继续循环；
  • 最后汇总输出。

这里要注意：我没有找到官方公开的完整 workflow API 文档，所以不要把网上某些示例里的函数名当成稳定 API。理解它的设计思想更重要。

第三步：多个子 Agent 独立执行

每个子 Agent 可以有自己的上下文，只看自己需要看的材料。

这很关键，因为它降低了大上下文里的噪音。

比如做代码库安全审计时：

  • Agent A 只看登录模块；
  • Agent B 只看支付模块；
  • Agent C 只看文件上传模块；
  • Verifier D 只看前三者给出的漏洞证据是否成立。

比起把整个代码库塞给一个 Agent，这种方式更像真实团队协作。

第四步：验证、筛选、汇总

动态工作流最有价值的部分，不是“让很多 Agent 同时干活”，而是 让它们互相制约。

典型做法包括：

  • 对每个结论安排独立 verifier；
  • 让 refuter 尝试推翻已有结论；
  • 对多个候选方案做 tournament；
  • 对重复结果去重；
  • 只保留有证据链的结果。

这一步决定最终质量。

一个可运行的小例子：模拟 Fan-out-and-synthesize

下面这个例子不调用 Claude Code，也不模拟官方 API，只是用本地 JavaScript 展示“动态工作流”的核心思想：把任务拆开、并行处理、再汇总。

环境要求：Node.js 20+。

保存为 workflow-demo.mjs 后执行：

node workflow-demo.mjs

代码如下：

// workflow-demo.mjs
const files = [
  { path: 'auth.js', content: 'login(user); eval(input)' },
  { path: 'payment.js', content: 'charge(order); console.log(order.id)' },
  { path: 'upload.js', content: 'save(file); exec(file.name)' },
  { path: 'profile.js', content: 'updateProfile(user)' }
];

function analyzeFile(file) {
  const findings = [];

  if (file.content.includes('eval(')) {
    findings.push({
      file: file.path,
      risk: 'high',
      reason: '发现 eval 调用，可能执行不可信输入'
    });
  }

  if (file.content.includes('exec(')) {
    findings.push({
      file: file.path,
      risk: 'high',
      reason: '发现 exec 调用，可能触发命令注入'
    });
  }

  return findings;
}

function verifyFinding(finding) {
  // 简化版 verifier：真实场景中这里会交给独立 Agent 做反驳和证据检查
  const hasClearEvidence = finding.reason.includes('发现');
  return {
    ...finding,
    verified: hasClearEvidence,
    verifierNote: hasClearEvidence ? '证据明确，保留' : '证据不足，丢弃'
  };
}

async function runWorkflow() {
  console.log('1. Fan-out：并行分析多个文件');

  const parallelResults = await Promise.all(
    files.map(async file => analyzeFile(file))
  );

  const findings = parallelResults.flat();
  console.log('2. Filter：初步发现', findings.length, '个问题');

  const verified = findings
    .map(verifyFinding)
    .filter(item => item.verified);

  console.log('3. Synthesize：汇总可信结果');
  console.table(verified.map(item => ({
    file: item.file,
    risk: item.risk,
    reason: item.reason,
    verifier: item.verifierNote
  })));
}

runWorkflow();

预期输出类似：

1. Fan-out：并行分析多个文件
2. Filter：初步发现 2 个问题
3. Synthesize：汇总可信结果
┌─────────┬─────────────┬────────┬──────────────────────────────┬────────────────┐
│ (index) │ file        │ risk   │ reason                       │ verifier       │
├─────────┼─────────────┼────────┼──────────────────────────────┼────────────────┤
│ 0       │ 'auth.js'   │ 'high' │ '发现 eval 调用...'           │ '证据明确，保留' │
│ 1       │ 'upload.js' │ 'high' │ '发现 exec 调用...'           │ '证据明确，保留' │
└─────────┴─────────────┴────────┴──────────────────────────────┴────────────────┘

这个例子很简陋，但它说明了动态工作流背后的基本骨架：

  1. 任务拆分；
  2. 并行执行；
  3. 独立验证；
  4. 汇总收敛。

Claude Code 的动态工作流，只是把这个骨架升级成了“由模型动态生成，并且每个节点可以是一个子 Agent”。

六种常见模式

公开资料里提到的模式很多，我认为最值得记住的是下面六种。

1. Classify-and-act：分类再行动

先让分类 Agent 判断任务类型，再决定后续路线。

适合：

  • 工单分类；
  • Bug 报告分流；
  • 模型路由；
  • 用户反馈处理；
  • 内容审核。

比如一个客服工单系统，可以先让分类 Agent 判断：这是退款问题、登录问题、支付失败，还是产品咨询。不同类型走不同处理流程。

2. Fan-out-and-synthesize：并行展开再汇总

把一个大任务拆成多个独立子任务，并行处理后再合并。

适合：

  • 大型代码库分析；
  • 多模块重构；
  • 深度研究；
  • 多来源资料整理；
  • 技术文章事实核查。

这是最容易理解、也最常用的模式。

3. Adversarial verification：对抗性验证

一个 Agent 给结论，另一个 Agent 专门找漏洞。

适合：

  • 安全审计；
  • 架构评审；
  • 高风险代码修改；
  • 事故根因分析；
  • 技术文章核查。

我的看法是：只要结论会影响决策，就应该考虑对抗性验证。

4. Generate-and-filter：生成再过滤

多个 Agent 生成候选方案，再由过滤器去重、评分、筛选。

适合：

  • 命名；
  • 设计方案；
  • 产品创意；
  • 文案候选；
  • 技术路线对比。

它解决的是“想法数量”和“筛选质量”之间的矛盾。

5. Tournament：锦标赛

多个方案两两 PK，胜者进入下一轮。

适合：

  • 简历筛选；
  • 方案排序；
  • 命名筛选；
  • 大批量工单优先级排序；
  • 多个实现方案对比。

它比“一次性让模型给 100 个项目排序”更可靠，因为每次只比较少量对象。

6. Loop until done：循环直到完成

不预设轮数，直到满足停止条件。

适合：

  • 偶发测试复现；
  • 日志根因排查；
  • Backlog 清理；
  • 持续 triage；
  • “直到无新错误”为止的验证任务。

这个模式一定要写清停止条件，否则很容易变成 token 黑洞。

典型应用场景

场景一：大型重构和迁移

比如把一个大型模块从旧接口迁移到新接口。

普通 Agent 往往会遇到两个问题：

  • 文件太多，容易漏；
  • 改动太大，容易互相影响。

动态工作流可以这样组织：

  1. 扫描所有调用点；
  2. 按模块拆分；
  3. 每个子 Agent 负责一个模块；
  4. 每个子 Agent 在独立 worktree 中修改；
  5. Reviewer Agent 检查公共 API 是否被破坏；
  6. Verifier Agent 跑测试并汇总失败原因。

这里的重点不是“快”，而是“把大任务变成可管理的小任务”。

场景二：代码库级安全审计

安全审计非常适合动态工作流，因为它天然需要多视角。

可以按风险类型拆：

  • SQL 注入；
  • XSS；
  • 命令注入；
  • 鉴权绕过；
  • 敏感信息泄漏。

也可以按模块拆：

  • 登录；
  • 支付；
  • 上传；
  • 后台管理；
  • 第三方回调。

最后再让验证 Agent 检查每个漏洞是否有真实证据，避免“看起来像漏洞”的误报。

场景三：深度研究和事实核查

动态工作流不只适合写代码，也适合研究任务。

一个比较理想的研究流程是：

  1. 多个搜索 Agent 并行查资料；
  2. 抽取 claim；
  3. 每条 claim 分配 verifier；
  4. 检查引用来源质量；
  5. 最后合成报告。

这比单个 Agent 一边搜一边写更可靠，尤其适合写行业分析、技术调研、竞品报告。

场景四：偶发问题根因调查

比如测试偶发失败、线上错误偶发出现、数据管道偶尔断。

单个 Agent 很容易陷入第一个假设。

动态工作流可以让多个 Agent 从不同证据源出发：

  • 一个只看日志；
  • 一个只看代码改动；
  • 一个只看监控指标；
  • 一个只看测试历史；
  • 最后让 refuter 尝试推翻每个假设。

这很像真实事故复盘里的多角色调查。

场景五：大规模工单分流

对 1000 个用户反馈做分类、去重、排序，单个 prompt 基本不靠谱。

动态工作流可以用：

  • Classify-and-act 做分类；
  • Generate-and-filter 做去重；
  • Tournament 做优先级排序；
  • Loop until done 持续清 backlog。

如果再配合明确的升级规则，就可以把“AI 看工单”变成半自动 triage 系统。

场景六：沉淀 CLAUDE.md 和团队规则

这是我觉得很有意思的场景。

你可以让 workflow 回看最近一批会话或代码评审记录，找出 AI 反复犯的错误：

  • 总是忘记跑测试；
  • 总是误改生成文件；
  • 总是忽略某个目录约定；
  • 总是把内部 API 当公共 API 用。

然后让 verifier 检查这些规则是否真的有价值，最后提炼进 CLAUDE.md。

这相当于让 Agent 从过去的失败里学习“下次怎么别再犯”。

怎么提示 Claude Code 使用动态工作流

公开资料里提到，可以直接在任务里说明“使用 workflow”或“为这个任务创建动态工作流”。也有资料提到 ultracode 这样的触发词，但这类行为可能会随版本变化，我不建议把它当成长期稳定接口。

我更建议用明确的任务描述，而不是迷信触发词。

一个比较稳的提示模板是：

请为这个任务使用动态工作流思路处理：

目标：找出最近测试偶发失败的可能根因，并给出按置信度排序的结论。

要求：
1. 先拆分证据来源：测试日志、最近提交、相关模块代码、CI 环境差异。
2. 每个方向独立分析，不要互相影响。
3. 对每个根因假设安排独立 verifier 尝试反驳。
4. 最终只输出有证据支撑的结论。
5. 限制 token 预算，优先分析最近 7 天的数据。
6. 不要修改代码，只做调查和报告。

我的实战建议是：提示词里一定要写清四件事：

必填项 为什么重要
目标 防止 workflow 自己发散
拆分维度 决定并行质量
验证标准 防止自说自话
停止条件 / 预算 防止无限消耗 token

不要只写一句“帮我 ultracode 一下”。那样很酷，但不工程化。

保存、复用和分发

公开资料里提到，动态工作流可以保存到：

~/.claude/workflows

也可以通过 Claude Code 的 Skill 分发：

my-workflow-skill/
├── SKILL.md
└── workflows/
    └── security-audit.js

这里有一个关键点：我更建议把 workflow 当“模板”，而不是当“不可变脚本”。

原因很简单：动态工作流的优势就是“根据任务动态调整”。如果你把它完全写死，它就退化成普通 workflow 了。

更合理的 Skill 描述应该是：

当用户要求做代码库安全审计时，参考 workflows/security-audit.js 的结构：
1. 按模块 fan-out；
2. 按漏洞类型检查；
3. 对每条发现做 adversarial verification；
4. 最终只输出证据充分的问题。

可以根据当前仓库规模、语言和用户预算调整并行度和检查范围。

这才符合“动态”的本意。

它背后的意义：Prompt 不够了，Agent 需要可执行组织结构

我觉得动态工作流最重要的意义，不是 Claude Code 多了一个功能，而是它说明了一件事：

复杂 Agent 任务不能只靠 Prompt，必须有可执行的组织结构。

过去我们优化 AI 编程，主要在三件事上做文章：

  1. 写更好的 Prompt；
  2. 给更多上下文；
  3. 接更多工具。

但复杂任务真正的瓶颈，往往不是“模型不知道”，而是：

  • 谁先做？
  • 谁后做？
  • 谁验证？
  • 怎么防止遗漏？
  • 怎么防止偏见？
  • 怎么在成本可控的情况下收敛？

这些问题，本质上都是工程组织问题。

动态工作流把这件事显式化了：让模型不只是“回答问题”，而是“为问题设计执行系统”。

这也是它和前面几篇文章里提到的 Agent 工作模式、Skills、MCP、CLAUDE.md 的关系：

能力 解决的问题
CLAUDE.md 告诉 Agent 项目规则
Skills 告诉 Agent 某类任务怎么做
MCP 给 Agent 外部工具和数据
Sub Agents 让多个 Agent 分工
Dynamic Workflows 动态组织这些能力，形成任务级执行框架

所以它不是孤立功能，而是 Claude Code 扩展体系里的“编排层”。

什么时候不该用动态工作流

动态工作流很强，但我不建议一上来什么任务都用。

下面这些场景不适合：

场景 原因
改一个小 bug 启动多个 Agent 成本太高
明确的单文件修改 普通 ReAct 就够了
需求还没说清 workflow 会把错误目标放大
权限风险高但边界不清 并行 Agent 可能扩大误操作范围
token 预算很紧 多 Agent 成本不可忽略

我的判断标准很简单：

如果你自己都不知道要拆给几个人做，那先别急着用动态工作流；如果你已经能说清“这件事需要多个角色互相验证”，那就值得用。

使用时最容易踩的坑

坑一：把动态工作流当加速器

很多人第一反应是：多个 Agent 并行，那不就是更快吗？

不完全是。

它真正提升的是复杂任务的覆盖率和可信度，不一定总是更快。多个 Agent 同时跑测试、构建、搜索，甚至可能把本机资源打满。

解决方式：在 prompt 里明确限制：

不要并行运行资源密集型命令；测试阶段先只跑相关测试；需要全量测试时先询问我。

坑二：不给停止条件

“持续分析直到没有问题”为止，这种话听起来合理，但对 Agent 来说很危险。

什么叫没有问题？检查多久？覆盖多少？预算多少？

更好的写法是：

最多进行 3 轮分析；如果第三轮没有新增高置信度发现，就停止并汇总。

坑三：让读取不可信内容的 Agent 拥有高权限

如果 workflow 会读取网页、用户提交内容、工单、日志里的外部文本，就要考虑 prompt injection。

更安全的模式是隔离：

  • 读取不可信内容的 Agent 只能总结信息；
  • 真正改代码、执行命令的 Agent 不直接消费原始不可信文本；
  • 高风险操作前必须人工确认。

动态工作流越强，权限边界越重要。

我对它的判断

我的看法比较明确：Dynamic Workflows 是 AI Coding 从“单兵作战”走向“任务编排”的一个标志。

它不会替代普通 Claude Code 使用方式。大多数日常编码任务，普通模式仍然更简单、更省钱、更直接。

但一旦任务满足下面几个条件，它的价值会明显放大：

  • 任务大；
  • 可并行；
  • 需要验证；
  • 容易遗漏；
  • 结论需要可信度；
  • 过程需要复用。

尤其是“对抗性验证”这一点，我认为会成为后面 Agent 工程的标配。

未来的 AI 编程，不太可能是一个 Agent 从头到尾包打天下，而更可能是：

规则层：CLAUDE.md / 项目规范
能力层：Skills / MCP / 工具
角色层：Sub Agents / Reviewer / Verifier
编排层：Dynamic Workflows
治理层：权限 / 预算 / 审计 / 回滚

动态工作流正好卡在“角色层”和“编排层”之间。

小结

  1. Dynamic Workflows 的核心是让 Claude Code 为当前任务动态生成 JavaScript harness，而不是只靠单 Agent 对话推进。
  2. 它主要解决复杂任务里的任务拆分、并行执行、对抗验证、目标防漂移和结果汇总问题。
  3. 最适合代码库级审计、大规模重构、深度研究、事实核查、工单分流和根因调查。
  4. 它不是万能加速器，普通小任务用它反而会增加 token、权限和资源成本。
  5. 真正有价值的用法，是把目标、拆分维度、验证标准、停止条件和预算写清楚，让 workflow 可控地运行。
  6. 从工程意义上看，它说明 AI Coding 正在从“写 Prompt 驱动单 Agent”，走向“用可执行结构组织多 Agent”。
