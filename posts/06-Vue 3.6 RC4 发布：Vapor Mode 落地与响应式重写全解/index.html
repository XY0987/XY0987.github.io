Vue 3.6 RC4 发布：Vapor Mode 落地与响应式重写全解

发表于2026|更新于2026|Vue框架及周边库
|字数总计:5.2k|阅读时长:19分钟

前言：Vue 3.6.0-rc.4 于 2026-08-14 发布，这是自 Vue 采用虚拟 DOM 以来最大的一次架构级更新。这一篇我想把 Vapor Mode、alien-signals 响应式重写、以及它们带来的生态影响一次讲透。我的判断是：Vue 3.6 不是一次”性能补丁”，而是一次为 Vue 4.0 做地基的架构分叉。

先看这次升级了什么

如果只看版本号，Vue 3.6 像是一个普通小版本；但 RC4 里真正值得关注的不是 API 多了几个，而是 Vue 底层两块被换了。

简单说，这次升级主要有三件事：

  1. Vapor Mode 进入可评估阶段：这是一条不走 VDOM（虚拟DOM） 的新编译路径，模板会被编译成更直接的 DOM 创建和更新逻辑
  2. @vue/reactivity 换成 alien-signals 内核：响应式依赖收集和触发机制重写，普通 Vue 3.5 项目升级后也能受益
  3. Vapor 的使用边界变清楚：它主要面向 <script setup> 和 Composition API，Options API 不在这条路径里

所以这篇文章真正要讲的，不是”Vue 3.6 又发布了一个 RC”，而是：

通过一次编译，把 Vue 的运行时从”VDOM + diff”这条老路上省下来；同时把响应式内核换成 alien-signals，让所有 3.5 的老代码免费吃到性能红利。

我的判断是：Vapor 决定了 Vue 未来几年的渲染上限，alien-signals 决定了 Vue 3.6 这次升级对现有项目是否有立刻可见的价值。

Vue 官方在第三方 benchmark 里已经跑到和 Solid、Svelte 5 同一梯队，这是 VDOM 时代做不到的。

一、行业时间线：VDOM 是怎么被”绕过去”的

这次更新的意义只有放在整条前端渲染演进史里才看得清楚：

时间 事件
2013 React 提出 Virtual DOM，用”生成 → diff → patch”取代手写 DOM
2016 Vue 2 采用 VDOM + 响应式 getter/setter
2020 Vue 3 正式发布，Proxy + PatchFlags + Block Tree，靠编译期信息给 VDOM”打补丁”
2021 SolidJS 出圈，证明”编译到命令式 DOM 操作”这条路可以做到极致性能
2023 Svelte 5 Runes、Solid 2、Preact Signals 全面拥抱 fine-grained reactivity
2024-05 Vue 团队公开 Vapor Mode RFC，明确要做”编译期直出 DOM 操作”
2024-10 alien-signals 0.4.4 被合入 vuejs/core（PR #12349），完成响应式底层重写
2025-12 Vue 3.6.0-beta.1 发布，Vapor Mode 功能完备但标记为 unstable
2026-07 Vue 3.6.0-rc.1 进入 RC 阶段
2026-08 Vue 3.6.0-rc.4 发布，Vapor Mode 事实上进入”可评估上生产”状态

Vue 走的是所有主流框架里最”晚”也最”稳”的一条：先做完 VDOM 的极限优化（PatchFlags）→ 再另起一条编译路径（Vapor）→ 两条路径互操作。这不是保守，是把破坏性升级的代价降到最小。

二、Vapor Mode 到底改了什么

传统模式 vs Vapor Mode

先看一张表把两条路径的差异摆清楚：

维度 传统 VDOM Mode Vapor Mode
编译产物 返回 VNode 树的 render 函数 直接创建/更新 DOM 的命令式函数
运行时 runtime-core + runtime-dom（VDOM + diff） runtime-vapor（无 VDOM）
更新粒度 组件级 dirty，patch 时按 flag 走 绑定级细粒度，每个响应式源直连具体 DOM 操作
打包体积 完整 VDOM 运行时 纯 Vapor 应用可去掉 VDOM 运行时
支持的 API 全部 Vue 3 API 子集：<script setup> 组合式 API
心智模型 数据变 → 生成新树 → diff → patch 数据变 → 直接执行”要改的那一行 DOM 代码”

一句话记：**VDOM 模式是”把整棵树画一遍再对比找差异”，Vapor 模式是”编译时就知道谁依赖谁，运行时只改变化的那一处”**。

Vapor 编译产物长什么样

给一个最小示例，直接感受两种模式的差别。同一个 .vue：

<script setup>
import { ref } from 'vue'
const count = ref(0)
</script>

<template>
  <button @click="count++">Count: {{ count }}</button>
</template>

在 VDOM Mode 下（简化），编译结果大致是这样：

export function render(_ctx) {
  return (openBlock(), createElementBlock('button', {
    onClick: () => _ctx.count++
  }, 'Count: ' + toDisplayString(_ctx.count), 1 /* TEXT */))
}

运行时每次 count 变了，会重新执行 render 生成新的 VNode，然后走 patch 流程，只是靠 PatchFlag = 1（TEXT）省了大部分对比。

在 Vapor Mode 下（<script setup vapor>），编译产物更像这样：

import { template, renderEffect, setText, delegate } from 'vue/vapor'

const t0 = template('<button>Count: </button>')

export function render(_ctx) {
  const n0 = t0()
  delegate(n0, 'click', () => _ctx.count.value++)

  renderEffect(() => {
    setText(n0, 'Count: ' + _ctx.count.value)
  })

  return n0
}

差别有三处，都很关键：

  1. template() 静态克隆：整个静态 HTML 结构只 parse 一次，之后 clone 出来复用，不再有 VNode 对象的创建
  2. renderEffect 绑定到具体 DOM 节点：每个动态绑定是一个独立的响应式副作用，只关心自己那个节点
  3. 完全没有 patch/diff 步骤：count 变了直接触发对应的 setText(n0, ...)

我的理解是：Vue 3 靠 PatchFlags 已经把”运行时对比”的开销压得很低，但只要走 VDOM 就绕不开”每次更新至少要生成一遍 VNode”这条最低成本。Vapor 是把这条最低成本也去掉了。

v-for 里 diff 并没有消失

有一个容易被误传的点：Vapor Mode ≠ 完全没有 diff。

在 runtime-vapor/src/apiCreateFor.ts 里，对 v-for 的列表更新，Vue 保留了几乎与 3.5 patchKeyedChildren 一致的算法：双端对比 → 最长递增子序列。原因很直接——列表插入、删除、移动这类操作，编译期无法预知具体索引位置，运行时还是需要一个成熟的 diff 算法。

所以更精确的说法是：Vapor 消除了 90% 常见场景的 diff（简单绑定、条件渲染、静态节点），但 v-for 依然保留完整的 keyed diff。

三、alien-signals：藏在 3.6 里的第二次革命

Vapor 是显性大更新，alien-signals 是隐性大更新——它默认对所有 3.6 用户生效，不需要开任何开关。

3.5 的响应式为什么还有优化空间

先不看数据结构，换成业务代码的视角更好理解：Vue 3.5 已经能很快地记录”谁依赖了谁”，但它判断 computed 要不要重算时，还是偏”读的时候再检查”。

也就是说，数据变了以后，Vue 不会立刻把所有相关 computed 都算一遍，而是先标记一下。等你真正读取某个 computed 时，它再回头检查自己依赖的值有没有变。

这个模型在单个 computed 上没问题，问题出在下面这种场景：

一个 signal 变了 → 一堆依赖它的 computed 都要被读取。

这时每读一个 computed，都要做一次”dirty 检查”。如果依赖链很深，检查过程还会递归往上走；如果一个值被很多 computed 依赖，检查次数就会被放大。

底层实现上，Vue 3.5 已经从 Set/Map 优化到了双向链表（doubly-linked list），单次订阅/取消订阅的成本不是主要瓶颈。真正的瓶颈是这个纯 pull 模型：计算越深、fan-out 越广，就越慢。这是 alien-signals 作者在 PR #12349 里明确指出的问题：可复现的 30 倍以上性能差距。

如果不采用 alien-signals，会发生什么

假设页面里有一个基础状态 count，它被很多层 computed 包起来：

count
  → computedA
    → computedB
      → computedC

在 3.5 这类纯 pull 模型里，count 改变时，系统主要做的是”先标记一下，等读取时再确认”。真正麻烦发生在读取 computedC 的时候：

  1. 读 computedC，发现它可能脏了
  2. 往上检查 computedB
  3. computedB 再往上检查 computedA
  4. computedA 再检查 count
  5. 确认变更后，再一层层返回并决定要不要重算

如果只有一条链，这个成本还能接受。可真实页面经常是一个源数据被多个视图状态、格式化字段、筛选条件同时依赖，读一次查一遍，读很多次就重复查很多遍。

所以，不采用 alien-signals 的问题不是”会不会重新计算”，而是：很多 computed 在读取时各自回头查依赖，导致同一段依赖图被重复走。

push-pull 混合算法是怎么解决的

alien-signals 的核心思路是把”标脏”和”重算”拆开：

Push 阶段（写入时）：
  signal 变化
    → 沿链表向下遍历所有依赖节点
    → 只翻转一个位标记（Pending / Dirty flag）
    → 不做任何计算
    ↓
Pull 阶段（读取时）：
  读 computed
    → 检查 flag
    → 干净：直接返回缓存值
    → 脏：调 checkDirty 沿上游走一趟，确认真的变了才重算

这段可以用 Excel 公式来类比：

count 单元格变了
  → 依赖它的公式单元格先被贴上"可能过期"标签
  → 用户真正点开某个公式单元格
  → 再确认它要不要重新计算

更准确地说，count 改了不马上把所有 computed 算一遍，这不是新旧模型的差别，3.5 本来也偏 lazy。真正的差别在于：写入时是否把影响范围更早地传播出去。

  1. 旧模型主要等读取 computedC 时，再回头沿依赖链确认上游有没有变
  2. alien-signals 会在 count 改变时，先把受影响的下游节点标成”可能过期”
  3. 等真正读取 computedC 时，它可以结合这些标记和缓存做更少检查，而不是每次都从头回查一遍

总结一下就是：**以前主要是”读的时候回头查脏不脏”；现在是”写的时候先把可能受影响的节点标出来，读的时候再按需计算”**。

对我们业务代码的影响：

场景 3.5 表现 3.6 表现（alien-signals）
一个 ref 驱动 1 个 computed 差不多 差不多
一个 ref 驱动 100 个 computed，只读其中 1 个 100 个都要重算或做 dirty check 只有被读的那 1 个真正走 checkDirty
深依赖链（A → B → C → D → E）中间某个变 每次读都可能沿链递归 flag 迭代，缓存值直接复用
Diamond 依赖（多路径可达同一节点） 可能被算多次 Pending → Dirty 两阶段标记，保证只算一次，无 glitch

最实际的一条：如果你项目里有大量 computed 或 watch 嵌套（很多状态管理场景就是这样），升到 3.6 大概率能感受到 CPU 占用下降，且不需要改一行代码。

四、Vapor Mode 怎么用（可跑示例）

先说环境：Vue 3.6.0-rc.4 + Vite 6+，package.json 里锁到 vue@^3.6.0-rc.4。

局部启用：单组件切 Vapor

在任意 SFC 顶部标注 vapor 即可，其他一切照旧：

<script setup vapor>
import { ref, computed } from 'vue'

const list = ref(Array.from({ length: 1000 }, (_, i) => ({ id: i, name: `Item ${i}` })))
const keyword = ref('')

const filtered = computed(() =>
  list.value.filter(item => item.name.includes(keyword.value))
)
</script>

<template>
  <input v-model="keyword" placeholder="filter..." />
  <ul>
    <li v-for="item in filtered" :key="item.id">{{ item.name }}</li>
  </ul>
</template>

<script setup vapor> 是 <script setup> + vapor 属性的简写。也可以只写在 template 上：

<template vapor>
  <!-- 整个 SFC 走 Vapor 编译 -->
</template>

纯 Vapor 应用：干掉 VDOM 运行时

如果整个 app 都是 Vapor 组件（内部依赖也需要），可以用 createVaporApp，构建产物不会打包 VDOM 运行时：

import { createVaporApp } from 'vue'
import App from './App.vue'

createVaporApp(App).mount('#app')

混合模式：老应用局部试点

绝大多数团队会走这条路径。现有 createApp 应用要嵌 Vapor 组件，必须装 vaporInteropPlugin：

import { createApp, vaporInteropPlugin } from 'vue'
import App from './App.vue'

createApp(App).use(vaporInteropPlugin).mount('#app')

装了这个 plugin 后，Vapor 组件和 VDOM 组件可以互相嵌套，props / events / slots 都能穿透。但官方明确说了：**”仍有一些边界 case 有粗糙的地方，特别是用 VDOM 组件库时”**。

把 Vapor 当作”性能区域”来规划，不是当”整体开关”打开。比如把首屏关键渲染、长列表、图表这类性能敏感页面切成 Vapor，其他页面保留 VDOM，避免混合嵌套产生的边界成本。

自定义指令写法变了

Vapor 下自定义指令的接口完全变了。旧写法是一个生命周期对象，Vue 在 mounted、updated、unmounted 这些阶段把 binding.value 传进来：

const vFocus = {
  mounted(el, binding) {
    if (binding.value) {
      el.focus()
    }
  },
  updated(el, binding) {
    if (binding.value && !binding.oldValue) {
      el.focus()
    }
  },
}

Vapor 里不再走这套指令生命周期，而是把指令写成一个函数：

import { watchEffect } from 'vue'

const vFocus = (el, source) => {
  watchEffect(() => {
    if (source()) {
      el.focus()
    }
  })
  return () => console.log('cleanup on unmount')
}

新旧差异主要有三点：

  • 旧写法拿到的是 binding.value；新写法第二个参数 source 是一个响应式 getter，要调用 source() 才拿到当前值
  • 旧写法靠 mounted / updated 分阶段处理；新写法在指令内部用 watchEffect 建立响应式副作用，组件卸载时自动释放
  • 可选地返回一个 cleanup 函数

这类变更不建议靠记忆硬背。官方 release note 和 CHANGELOG 后面都有完整说明，真正迁移时优先跑官方 codemod，再人工检查少数复杂指令。

五、Vapor 目前还不能做什么

RC 阶段功能完备，但故意不支持的东西你得清楚。我按坑的严重程度排一下：

坑 1：Options API 完全不支持

<!-- ❌ 反面案例：Vapor 里不能用 -->
<script>
export default {
  data() { return { count: 0 } },
  methods: { inc() { this.count++ } }
}
</script>

<!-- ✅ 正面案例：改成组合式 API -->
<script setup vapor>
import { ref } from 'vue'
const count = ref(0)
function inc() { count.value++ }
</script>

如果项目大量使用 Options API，切 Vapor 意味着一次不小的组件重构。

坑 2：getCurrentInstance() 返回 null

很多老库在内部用 getCurrentInstance() 拿组件实例做魔改，在 Vapor 组件里全部失效。这也是为什么”UI 组件库全面支持 Vapor”还需要时间。

坑 3：模板 ref 拿不到 $el $props $attrs $slots $refs

Vapor 组件的模板 ref 不会暴露公共实例代理属性，只暴露显式 expose 的东西。依赖这些属性的调试/自动化代码要改。

坑 4：v-memo 不支持

v-memo 是 VDOM 模式下的 diff 层缓存指令，Vapor 已经细粒度到具体绑定，用不上这个了。

坑 5：@vue:mounted / @vue:updated 等 per-element 生命周期不支持

坑 6：事件委托在 rc.2 之后变成可选

Vapor 之前默认把所有事件委托到 document，rc.2 起改成了默认直接绑到元素上，需要显式加 .delegate 修饰符才走委托：

<button @click.delegate="onClick" />

这个改动是为了对齐 VDOM 模式，避免祖先 stopPropagation() 造成的行为差异。同时 compilerOptions.eventDelegation 选项被移除了。

坑 7：slots.default() 不再是”安全预览”

在 Vapor 里，调用 slots.default() 会真的执行渲染逻辑（创建 DOM、注册 effect）。所以别再用它做”先看看有没有插槽内容再决定要不要渲 fallback”的技巧：

<!-- ❌ 反面案例：Vapor 里会导致渲染副作用 -->
<script setup vapor>
import { useSlots } from 'vue'
const slots = useSlots()
const content = slots.default?.()
const showFallback = !content
</script>

<!-- ✅ 正面案例：让 template 做 fallback -->
<template>
  <slot>Fallback content</slot>
</template>

六、对生态的影响

这一节完全是我的判断，不是官方结论，仅供参考。

对 UI 组件库：Element Plus、Ant Design Vue、Naive UI 这些库短期内不会全量转 Vapor。原因是它们内部大量依赖 getCurrentInstance 和 $attrs/$slots 等属性。走 vaporInteropPlugin 通用能用，但性能收益会打折。真正的 Vapor 原生组件库我预计要等 1-2 年才能成熟，或者会出现专门的 “vapor-first” 新库。

对状态管理：Pinia 底层是纯响应式 API，会自动吃到 alien-signals 的红利，不需要迁移。这也是为什么我说响应式重写是”隐形收益”。

对跨端框架：短期影响不会像 H5 项目那么直接。原因很简单，uni-app、Taro 这类跨端框架本来就有自己的编译链路和平台运行时，尤其小程序端并不是浏览器 DOM 环境。Vapor 的价值在于把 Vue 模板编译成更直接的 DOM 更新逻辑，但跨端框架要吃到这部分收益，必须自己接入 Vapor 编译产物和对应运行时，不是把 Vue 升到 3.6 就自动完成。

更现实的收益来自 alien-signals：只要跨端框架内部或业务代码用的是 Vue 这套响应式，理论上就能吃到响应式内核重写带来的性能红利。我的判断是：跨端框架会先吃响应式红利，后面才可能评估 Vapor 编译链路。

对 SSR / Nuxt：Vapor 对 SSR 的影响也不能只看”能不能编译”。SSR 真正麻烦的是 hydration：服务端吐出的 HTML，要在客户端被 Vapor runtime 精准接管，事件、ref、条件分支、插槽都不能错位。

这也是为什么 rc.1 到 rc.4 的修复里，runtime-vapor: hydrate xxx 占了很大比例。Nuxt 4 大概率会在稳定版之后逐步开放 Vapor 支持，但短期不会成为默认。对 SSR 项目来说，Vapor 更像是一个需要框架层兜底的能力，不建议业务项目自己先冲。

对 Vue 3 → Vue 4 的路径：结合官方多次公开表态和这次的架构分叉，我的判断是：Vue 4 会把 Vapor 定为默认模式，VDOM 变成”兼容模式”或独立包。类似 React 从 Legacy Renderer 到 Fiber 的分叉。从 3.5 到 3.6 现在开始把项目切到组合式 API + <script setup>，就是在为 Vue 4 铺路。

对写业务代码的我们：短期什么都不用做，升到 3.6 直接吃响应式红利；中期在性能敏感的页面（长列表、图表、复杂表单）试点 Vapor；长期把 Options API 逐步替换掉。

七、我的建议

  1. 立刻可以做：把项目 vue 版本锁到 ^3.6.0-rc.4，跑一遍完整回归测试，验证 alien-signals 有没有引发行为差异（应该没有，官方对齐了 API）
  2. 谨慎推进：挑一个孤立的性能敏感页面切 Vapor，跑 benchmark 对比。别整站切
  3. 不要激进：别在正在开发的核心业务模块用 Vapor RC。Vue 官方原文是 “beta means ready for production evaluation, not make it the default tomorrow”
  4. 组件库依赖：如果你的 UI 库已经明确表态支持 Vapor（如已发布 Vapor 兼容版本），可以放心试点；没表态的，只用 vaporInteropPlugin 兜底，别在 Vapor 组件内部深度嵌套
  5. 技术储备：花时间把 Options API 组件逐步迁到 <script setup>，这是无论 Vapor 是否落地都要做的事

小结

  1. Vue 3.6 RC4 的核心是两件事：Vapor Mode 编译完备 + @vue/reactivity 基于 alien-signals 全量重写
  2. Vapor Mode 是可选的第二条编译路径，把模板直接编译成命令式 DOM 操作，绕开了 VDOM 的生成和 diff
  3. Vapor 并非完全没有 diff，v-for 列表更新仍保留 3.5 那套 keyed diff 算法
  4. alien-signals 是隐形红利，升级即生效，在深依赖 / 多 computed 场景可有 30 倍以上性能提升
  5. Vapor 只支持组合式 API + <script setup>，Options API、v-memo、部分模板 ref 属性不再可用
  6. 生态短期还在追赶，UI 组件库、跨端框架、SSR 框架都需要各自适配，不能把 Vapor 当成升级即开的默认能力
  7. 我的判断：Vapor 是为 Vue 4 铺的地基，现在把项目切到组合式 API 就是最好的准备
