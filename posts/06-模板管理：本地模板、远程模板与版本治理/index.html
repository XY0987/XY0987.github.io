模板管理：本地模板、远程模板与版本治理

发表于2026|更新于2026|工程化
|字数总计:3.2k|阅读时长:12分钟

前言：脚手架的「料」是模板。模板放哪、怎么更新、怎么管版本，直接决定了工具的维护成本。这一篇讲模板管理的几个关键问题：内置本地模板、远程拉取模板、本地缓存管理、模板版本治理，以及 giget、degit 这两个远程模板下载工具怎么用、怎么选。

三种模板存放策略

模板从哪来，本质就三条路：

策略 模板位置 优点 缺点
内置本地模板 跟工具一起发布到 npm 离线可用、版本绑定、快 更新模板要发新版工具
远程拉取模板 单独的 Git 仓库 模板独立更新、不发工具也能改 依赖网络、要处理鉴权/缓存
混合 内置一份兜底 + 支持远程覆盖 兼顾两者 实现复杂一点

没有绝对优劣，看场景。下面分别说。

内置本地模板

把模板目录和工具源码放一起，发布时一并打包进 npm 包。create-vite 就是这种：你 npm create vite 时，模板早就随着包下载到本地了，所以选完框架几乎瞬间生成。

目录结构通常长这样：

my-cli/
├── src/
│   └── index.ts        # CLI 逻辑
├── templates/          # 内置模板
│   ├── vue/
│   ├── react/
│   └── svelte/
├── package.json

关键点是 package.json 的 files 字段要把 templates 带上，否则发布后用户那边没有模板：

{
  "files": ["dist", "templates"]
}

运行时定位模板目录，靠的是上一篇讲的 import.meta.url（ESM 下还原路径）：

import { fileURLToPath } from 'node:url'
import path from 'node:path'

const __dirname = path.dirname(fileURLToPath(import.meta.url))

function getTemplateDir(name) {
  // dist 在 my-cli/dist，模板在 my-cli/templates
  return path.resolve(__dirname, '../templates', name)
}

内置模板的优点是稳定、离线、快：模板和工具版本严格绑定，my-cli@1.2.0 用的就是 1.2.0 里的模板，不会出现「工具和模板对不上」的问题。代价是改模板得发新版工具。对大多数脚手架，这是我的默认推荐。

远程拉取模板

如果模板更新很频繁，或者你想让模板独立于工具维护（比如团队内部模板由另一个小组管），就把模板放到独立 Git 仓库，运行时按需拉取。

这里**不要用 git clone**。git clone 会带上完整的 .git 历史，又慢又多余——你只想要某一时刻的文件快照，不需要提交历史。专门做这件事的工具是 degit 和 giget。

degit：经典的「无历史克隆」

degit（Svelte 作者出品）的思路是：下载仓库某个 ref 的 tar 包并解压，不带 .git。

npm i degit

import degit from 'degit'

const emitter = degit('user/repo', {
  force: true,   // 目标目录存在时覆盖
  cache: false,
})

await emitter.clone('my-app')
console.log('模板已拉取到 my-app')

也支持指定分支/tag/子目录：

degit('user/repo#v2')              // 指定 tag/分支
degit('user/repo/templates/vue')   // 仓库里的子目录

degit 简单好用，是早年远程模板的事实标准。它的社区维护近年放缓，所以也有人用它的活跃 fork tiged，API 基本一致，可作为替代。

giget：UnJS 生态的现代选择

giget 是 UnJS 出的模板下载工具，Nuxt 的 nuxi init 在用。相比 degit，它支持更多 provider（GitHub、GitLab、Bitbucket、Sourcehut）、带本地缓存（基于 etag）、还能离线复用缓存。

npm i giget

import { downloadTemplate } from 'giget'

const { dir, source } = await downloadTemplate('github:user/repo', {
  dir: './my-app',
  force: true,        // 目标目录已存在时仍写入
  preferOffline: true, // 有缓存优先用缓存，没网也能用
})

console.log(`已从 ${source} 拉取到 ${dir}`)

source 字符串的格式是 provider:repo[/subpath][#ref]，很灵活：

downloadTemplate('github:user/repo#v2')          // 指定 tag
downloadTemplate('github:user/repo/templates/vue') // 子目录
downloadTemplate('gitlab:group/repo')             // GitLab

私有仓库可以传 auth token：

await downloadTemplate('github:org/private-template', {
  dir: './my-app',
  auth: process.env.GITHUB_TOKEN,
})

degit vs giget 怎么选

维度 degit giget
维护活跃度 放缓（可用 tiged fork） 活跃（UnJS）
provider 主要 GitHub GitHub/GitLab/Bitbucket/Sourcehut
本地缓存 有 有（etag），支持离线
私有仓库鉴权 支持 支持（auth 选项）
生态 通用 Nuxt/UnJS 系

我的判断：**新工具优先 giget**，provider 多、缓存和离线支持好、维护活跃。只在维护老项目或习惯了 degit 的情况下继续用 degit / tiged。

本地缓存管理

远程模板不能每次都重新下载。比较合理的做法是：第一次下载到缓存目录，生成项目时从缓存复制；后续启动时先检查远端是否有更新，有更新再询问用户要不要刷新缓存。

缓存目录一般不要放在当前项目里，而是放到用户级目录：

~/.cache/my-cli/
└── templates/
    ├── vue/
    │   ├── files/          # 模板文件
    │   └── meta.json       # 模板元信息
    └── react/
        ├── files/
        └── meta.json

meta.json 里至少记录三类信息：

{
  "name": "vue",
  "source": "github:org/template-vue#v1.4.0",
  "version": "1.4.0",
  "updatedAt": "2026-06-28T10:00:00.000Z"
}

这样脚手架就有了判断依据：本地缓存是什么版本、来自哪里、什么时候更新过。

基本流程

完整流程可以抽象成四步：

选择模板
  ↓
检查本地缓存是否存在
  ↓
检查远端是否有新版本
  ↓
用户确认后更新缓存，再复制到目标目录

代码大概是这个味道：

import fs from 'node:fs/promises'
import path from 'node:path'
import os from 'node:os'
import prompts from 'prompts'

const cacheRoot = path.join(os.homedir(), '.cache', 'my-cli', 'templates')

function getTemplateCacheDir(name) {
  return path.join(cacheRoot, name)
}

async function readMeta(name) {
  try {
    const file = path.join(getTemplateCacheDir(name), 'meta.json')
    return JSON.parse(await fs.readFile(file, 'utf-8'))
  } catch {
    return null
  }
}

async function ensureTemplateCache(name) {
  const meta = await readMeta(name)
  const latest = await getLatestTemplateVersion(name)

  if (!meta) {
    await downloadTemplateToCache(name, latest)
    return
  }

  if (meta.version !== latest.version) {
    const { update } = await prompts({
      type: 'confirm',
      name: 'update',
      message: `模板 ${name} 有新版本 ${latest.version}，是否更新？`,
      initial: true,
    })

    if (update) {
      await downloadTemplateToCache(name, latest)
    }
  }
}

这里的 getLatestTemplateVersion 和 downloadTemplateToCache 取决于你用什么方式管理模板。常见有两种：npm 包管理和 Git 管理。

用 npm 管理模板

如果模板本身可以发成 npm 包，我更推荐这种方式。比如：

@my-cli/template-vue
@my-cli/template-react
@my-cli/template-node

每个模板包都有自己的 package.json，版本号就是模板版本：

{
  "name": "@my-cli/template-vue",
  "version": "1.4.0",
  "files": ["template"]
}

这里有个更工程化的做法：把缓存目录本身当成一个 npm 项目，模板包作为这个缓存项目的依赖项。

~/.cache/my-cli/
├── package.json
├── package-lock.json
└── node_modules/
    └── @my-cli/
        ├── template-vue/
        └── template-react/

缓存目录里的 package.json 长这样：

{
  "private": true,
  "dependencies": {
    "@my-cli/template-vue": "^1.4.0",
    "@my-cli/template-react": "^2.1.0"
  }
}

这样多个模板就都交给 npm 管理了。脚手架不需要自己维护一套复杂的模板索引，只要读取缓存目录中已安装模板包的 package.json，就能知道当前缓存里是什么版本：

import fs from 'node:fs/promises'
import path from 'node:path'

async function getCachedTemplateVersion(cacheRoot, pkgName) {
  const pkgJsonPath = path.join(cacheRoot, 'node_modules', pkgName, 'package.json')
  const pkg = JSON.parse(await fs.readFile(pkgJsonPath, 'utf-8'))
  return pkg.version
}

如果要检查是否有更新，可以在缓存目录里执行包管理器更新，或者先查 registry 上的最新版本，再让用户决定要不要更新缓存：

import { execa } from 'execa'

async function updateTemplatePackage(cacheRoot, pkgName) {
  await execa('npm', ['install', `${pkgName}@latest`], {
    cwd: cacheRoot,
    stdio: 'inherit',
  })
}

生成项目时，再从模板包里的 template 目录复制文件：

function getNpmTemplateDir(cacheRoot, pkgName) {
  return path.join(cacheRoot, 'node_modules', pkgName, 'template')
}

这个方案的好处是：版本解析、依赖安装、lockfile、私有 registry、权限控制都交给 npm。你的脚手架只负责三件事：维护缓存目录的 package.json、读取模板包版本、把模板目录复制到目标项目。

我的判断：团队内部模板如果已经有 npm 私服，优先用 npm 管理。它天然适合做多模板版本治理，@scope/template-* 这种命名也很清晰。

用 Git 管理模板

Git 管理也很常见，尤其是模板和业务代码一样需要 review、分支、tag 的团队。更新判断一般有两种：

判断方式 做法 适合场景
tag 版本 读取最新 tag，和本地缓存版本比较 正式发布模板
commit sha 读取远端分支 HEAD，和本地 sha 比较 内部快速迭代

比如用 git ls-remote 读取远端分支最新 commit：

import { execa } from 'execa'

async function getRemoteHead(repoUrl, branch = 'main') {
  const { stdout } = await execa('git', ['ls-remote', repoUrl, `refs/heads/${branch}`])
  return stdout.split(/\s+/)[0]
}

如果本地 meta.json 里的 commit 和远端 HEAD 不一致，就说明模板有更新，再询问用户是否更新缓存。

坑点：这里说的「用 Git 管理模板」，不等于生成项目时把 .git 一起复制给用户。模板缓存可以用 Git 作为版本来源，但最终生成项目时最好复制一份干净文件，或者继续用 giget / degit 下载无历史快照。

模板版本治理

无论本地还是远程，模板都要面对「版本」问题。几个实践经验：

1. 远程模板务必锁 ref，别只写默认分支

// ❌ 反面案例：默认分支随时在变，今天能跑明天可能挂
downloadTemplate('github:org/template')

// ✅ 正面案例：锁定 tag，可复现
downloadTemplate('github:org/template#v1.4.0')

直接拉默认分支（main）意味着模板作者一改，所有用户立刻受影响，没有任何缓冲。锁 tag 才能保证「同一条命令今天明天拉到的是同一份模板」。

2. 内置模板的版本 = 工具的版本

内置模板天然和工具版本绑定，这是它最大的优点。用户 npm create my-app@1.2.0 就锁定了那一版模板。如果要支持「用旧版模板」，让用户指定工具版本即可，不用自己造版本机制。

3. 模板里别写死依赖的精确版本

模板的 package.json 里，依赖版本建议用 ^ 范围而不是钉死，否则模板很快就过时、用户一装就是一堆旧包。但核心框架（如 vite、vue）可以适当跟紧，定期更新模板。这是个平衡，没有标准答案，定期维护是必须的。

坑点：远程模板最容易忽略的是离线和弱网。用户在没网或网络差的环境跑你的工具，远程拉取直接卡死或超时。所以远程模板方案最好配合缓存（giget 的 preferOffline），或者干脆「内置一份兜底模板 + 远程可选覆盖」的混合策略。纯远程在网络不好的环境体验会很差。

混合策略：兜底 + 远程

成熟工具常用混合策略：内置几个最常用模板保证开箱即用，同时允许 --template github:user/repo 拉远程模板满足定制需求。

async function resolveTemplate(name, targetDir) {
  // 远程模板：以 provider 前缀开头
  if (/^(github|gitlab|bitbucket):/.test(name)) {
    const { downloadTemplate } = await import('giget')
    await downloadTemplate(name, { dir: targetDir, preferOffline: true })
    return
  }

  // 本地内置模板
  const dir = getTemplateDir(name)
  if (!existsSync(dir)) {
    throw new Error(`未知模板：${name}`)
  }
  await copyTemplate(dir, targetDir, {})
}

这样既有内置模板的稳定离线，又保留远程模板的灵活，是我比较推荐的折中。

小结

  1. 模板有三种存放策略：内置本地、远程拉取、混合，按更新频率和离线需求选。
  2. 内置模板稳定、离线、与工具版本绑定，是大多数脚手架的默认推荐，代价是改模板要发新版。
  3. 远程模板别用 git clone（带历史、慢），用 degit 或 giget 做无历史下载。
  4. giget 是现代首选：provider 多、有 etag 缓存和离线支持、维护活跃；degit/tiged 适合老项目。
  5. 远程模板要有本地缓存：先下载到用户级缓存目录，再按版本、tag 或 commit 判断是否需要更新。
  6. 多模板可以用 npm 包管理，也可以用 Git 管理；有 npm 私服时，我更推荐用 npm 的版本体系。
  7. 远程模板务必锁 ref（#v1.4.0）保证可复现，别只拉默认分支。
  8. 模板里的依赖用 ^ 范围而非钉死，并定期维护更新，避免一装就过时。
  9. 远程方案要考虑离线/弱网，最稳的是「内置兜底 + 远程可选」的混合策略。
