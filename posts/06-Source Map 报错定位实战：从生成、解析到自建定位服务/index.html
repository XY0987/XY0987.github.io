Source Map 报错定位实战：从生成、解析到自建定位服务

发表于2026|更新于2026|项目
|字数总计:6k|阅读时长:23分钟

前言：之前那篇《Source Map 上报解析与 Sentry 工程化接入》讲的是「用 Sentry 平台省心」的路子。但很多团队因为数据合规、内网部署、成本或者纯粹想搞明白原理，会选择自建一套错误定位服务。这篇就把这条路走一遍——从 Source Map 是怎么生成的、里面到底记了什么、source-map 库怎么解析、一直到搭一个能对外提供解析能力的 Node 服务，端到端跑通。

一个每天都在发生的场景

线上一个用户反馈「点了确认按钮就白屏」。你打开监控平台，看到堆栈是这样的：

TypeError: Cannot read properties of undefined (reading 'orderId')
    at t (https://cdn.example.com/assets/app.b8f2a1c9.js:1:184732)
    at n.<anonymous> (https://cdn.example.com/assets/app.b8f2a1c9.js:1:184201)

app.b8f2a1c9.js:1:184732——第 1 行第 184732 列。生产构建把整份代码压成一行，你只知道大概在某个 chunk 里的某个函数出的错，代码是哪一行、什么变量、走的哪个分支——一概不知道。

Source Map 就是解决这件事的。它记录的是「压缩产物某个坐标 ↔ 源码某个坐标」的对应关系。有它，上面那行堆栈可以还原成：

TypeError: Cannot read properties of undefined (reading 'orderId')
    at submitOrder (src/pages/Order/index.tsx:87:12)
    at handleClick (src/pages/Order/index.tsx:63:5)

从「天书」变成「一眼可读」，前后就差一份 .map 文件。

Source Map 文件里到底记了什么

拿一份 app.b8f2a1c9.js.map 出来看，本质是一个 JSON：

{
  "version": 3,
  "file": "app.b8f2a1c9.js",
  "sources": ["webpack:///./src/pages/Order/index.tsx", "webpack:///./src/utils/api.ts"],
  "sourcesContent": ["import React from 'react'...", "export async function post..."],
  "names": ["React", "useState", "submitOrder", "orderId"],
  "mappings": "AAAA,SAASA,MAAM,CAAC,QAAQ...;;AAAA,eAAe..."
}

几个关键字段：

字段 作用
version Source Map 规范版本，目前统一是 3
sources 原始源码文件路径列表
sourcesContent 每个源文件的原始内容（可选，但监控场景一般要有）
names 原始变量名/函数名池（用于还原压缩后的短名）
mappings 真正的映射数据，VLQ 编码的坐标关系

其中 mappings 是核心。它是一大坨看起来像乱码的 Base64 字符串，实际按分号切分成行、按逗号切分成段，每一段用 VLQ（Variable-Length Quantity）编码 5 个数字：

生成代码列号, sources 索引, 源码行号, 源码列号, names 索引

举个具化的例子：

mappings 片段:  "AAAA,SAASA,MAAM"

解码：
  段1: [0, 0, 0, 0]           // 生成列 0 → sources[0] 第 0 行第 0 列
  段2: [9, 0, 0, 9, 0]        // 生成列 9 → sources[0] 第 0 行第 9 列，name = names[0]
  段3: [6, 0, 0, 6]           // 生成列 15 → sources[0] 第 0 行第 15 列

这里容易让人困惑：前面看起来明明是字母，为什么解码后又变成数字？原因是这些字母不是普通文本，而是 Base64 字符表里的“数字外壳”。比如在 VLQ 规则下，A 可以还原成 0，C 可以还原成 1，E 可以还原成 2。如果数字比较大，就用多个字符拼起来表示。也就是说，字母只是为了把数字写得更短，解析器最终拿到的还是一组坐标数字。

每段的数字都是相对上一段的增量（VLQ 差值编码），这也是 .map 文件为什么能压得那么小的原因——一个几百 KB 的压缩 JS，配套的 .map 通常只有几 MB，而不是几十 MB。

手写一个 VLQ 解码器不难，但没必要。工程实践里几乎都用 source-map 库（Mozilla 出品，Chrome DevTools 里也是它）。理解结构是为了看懂错误报告、排查解析失败，实际不用自己撸编码。

生成：不同构建工具怎么产出 Source Map

生成 Source Map 是构建工具的活。这里把日常最常见的两个——Webpack 和 Vite——的选项梳一遍，重点是生产环境该用哪个。

Webpack 的 devtool 全景

Webpack 的 devtool 配置项组合起来有十几种，官方文档给了张性能表，但实际选型只需要盯住三点：是否可用于生产、精度、是否暴露源码。

这些名字不用死记硬背，可以把它理解成几个开关拼出来的配置：

[eval-|inline-|hidden-][nosources-][cheap-[module-]]source-map

eval 是一个特例，可以单独使用；其他大多数配置都可以按这个格式拆。

拆开看就清楚了：

  • source-map：生成完整映射，通常可以定位到源码的行和列。
  • eval-：用 eval 包裹模块，重构建快，主要服务本地开发。
  • inline-：不生成单独 .map 文件，而是把 sourcemap 内联到 JS 里。
  • hidden-：生成 .map 文件，但不在 JS 末尾加 sourceMappingURL 注释。
  • nosources-：保留映射关系，但 .map 里不带源码内容。
  • cheap-：只保留行号，不保留列号，体积更小、精度更低。
  • module-：尽量映射回 loader 处理前的源码，比如 TS、Vue、SCSS。

所以 cheap-module-source-map 就是“行级精度 + 回到 loader 前源码 + 生成 sourcemap”，hidden-source-map 就是“生成完整 sourcemap，但不主动暴露 map 地址”。

devtool 生成 .map 文件 精度 生产可用 sourceMappingURL 注释
eval 否（inline） 模块级 否 无
eval-source-map 否（inline） 行 + 列 否 无
cheap-module-source-map 是 仅行号 可（体积小） 有
source-map 是 行 + 列 是（但会暴露 map URL） 有
hidden-source-map 是 行 + 列 是 无
nosources-source-map 是 行 + 列 是（无源码内容） 有
  • 本地开发：eval-cheap-module-source-map 或者 cheap-module-source-map，重构建速度。
  • 生产 + 有监控平台：hidden-source-map。生成完整 map，但不在 JS 里留 //# sourceMappingURL= 注释。这样浏览器不会自动去拉 map，只有你自己的解析服务能用到它。
  • 合规特别严的场景：nosources-source-map。map 里不包含 sourcesContent，堆栈能还原文件行号，但没法展示源码片段。
// webpack.config.js
module.exports = {
  devtool: process.env.NODE_ENV === 'production'
    ? 'hidden-source-map'
    : 'eval-cheap-module-source-map',
}

Vite 的 sourcemap 配置

Vite 更简洁，就一个 build.sourcemap 选项，四个取值：

值 含义
false 不生成（默认）
true 生成 .map 文件，JS 里带 sourceMappingURL 注释
'inline' 内联到 JS，base64
'hidden' 生成 .map 但不加注释

生产用 'hidden'，和 Webpack 的 hidden-source-map 语义一致：

// vite.config.ts
export default defineConfig({
  build: {
    sourcemap: 'hidden',
  },
})

一个反复踩过的坑：注释没删掉

有些团队图省事，生产直接用 devtool: 'source-map'，然后靠 Nginx 规则「不放 .map 到 CDN」来防泄露。这条路很脆弱——JS 文件末尾的 //# sourceMappingURL=app.xxx.js.map 注释还在，DevTools 或者爬虫会尝试请求这个 URL，一旦哪次部署漏掉了 Nginx 规则，源码就出去了。

正确姿势永远是：在源头（构建工具）就不产出这行注释。hidden 就是干这个的。

解析：source-map 库的核心用法

source-map 是 Mozilla 官方维护的库，从 0.7 版本开始底层用 WASM 实现，API 全部是异步的。

装它：

pnpm add source-map

一段最小可运行的解析代码：

这段代码做的事很单一：把压缩后 JS 里的报错行列号，翻译回源码里的文件、行号、列号和函数名。

假设线上错误上报里只有这种信息：

app.b8f2a1c9.js:1:184732

它只能告诉你“压缩后的 app.b8f2a1c9.js 第 1 行第 184732 列报错了”。但生产 JS 往往只有一行，这个位置肉眼根本没法看。下面这段代码就是读取对应的 .map 文件，然后用 originalPositionFor 把这个压缩后的位置反查回源码位置。

import { readFileSync } from 'node:fs'
import { SourceMapConsumer } from 'source-map'

async function locate() {
  const rawMap = readFileSync('./dist/app.b8f2a1c9.js.map', 'utf-8')

  await SourceMapConsumer.with(JSON.parse(rawMap), null, (consumer) => {
    const pos = consumer.originalPositionFor({
      line: 1,        // 生成代码的行号，1-based
      column: 184732, // 生成代码的列号，0-based
    })

    console.log(pos)
    // {
    //   source: 'webpack:///./src/pages/Order/index.tsx',
    //   line: 87,
    //   column: 12,
    //   name: 'submitOrder'
    // }
  })
}

locate()

几个关键点：

  • readFileSync 读取的是构建产物对应的 .map 文件。
  • JSON.parse(rawMap) 把 sourcemap 文本转成对象，交给 SourceMapConsumer。
  • originalPositionFor 接收的是生成后代码的位置，也就是线上报错里的行列号。
  • console.log(pos) 输出的是原始源码位置，比如 src/pages/Order/index.tsx 第 87 行第 12 列，函数名是 submitOrder。

SourceMapConsumer.with(map, sourceMapUrl, fn) 是推荐的用法：它会在回调结束后自动释放 WASM 资源，避免内存泄漏。

两个必须记住的细节

1）同一个报错，不同地方的行列号基准不一样。

比如线上同一个错误，在浏览器堆栈里可能长这样：

at submitOrder (app.b8f2a1c9.js:1:184733)

如果你用 window.onerror 接，它拿到的也是同一个位置：

lineno = 1
colno = 184733

这里容易绕：报错点还是同一个点，并不是从第 184733 列变到了第 184732 列，只是两边的计数规则不一样。

浏览器说“第 184733 列”，是从 1 开始数；source-map 的 column 是从 0 开始数。就像同一个数组元素，人说“第 1 个”，代码里下标却是 0。所以同一个报错点，传给解析库时要把列号换成 0-based 编号：

consumer.originalPositionFor({
  line: lineno,       // 还是 1
  column: colno - 1,  // 同一个位置，换成 0-based 编号
})

也就是说，位置不变，只是编号口径要转换：行号不用动，列号统一减 1。source-map 返回的 column 也是 0-based，如果最后要展示给用户看，再按展示习惯加回 1。踩过这坑的都知道，差 1 列有时候就会映射到完全不同的变量名上。

2）拿到 source 后要清洗路径。 source 字段返回的是 webpack:///./src/pages/Order/index.tsx 这样的 URI，前面有构建工具的协议前缀。展示时要把前缀去掉，或者拿它去 sourcesContent 里查原始代码：

function cleanSourcePath(source: string) {
  return source
    .replace(/^webpack:\/\/[^/]*\//, '')  // 去掉 webpack:///
    .replace(/^webpack:\/\//, '')
    .replace(/^\.\//, '')
}

如何顺便把源码片段捞出来

监控平台展示错误时，通常要在堆栈行旁边贴 5 行上下文源码。sourcesContent 已经提供了原文，用 sourceContentFor API 拿出来切片即可。

下面这个例子是把前面的定位逻辑补完整：先用 originalPositionFor 找到源码位置，再用 sourceContentFor 拿到这个文件的源码内容，最后截取报错行前后各 2 行。

import { readFileSync } from 'node:fs'
import { SourceMapConsumer } from 'source-map'

async function printSourceContext() {
  const rawMap = JSON.parse(
    readFileSync('./dist/app.b8f2a1c9.js.map', 'utf-8')
  )

  // 这里复用前面的定位思路：把生成后 JS 的报错位置反查成源码位置
  const generatedPosition = {
    line: 1,
    column: 184732,
  }

  await SourceMapConsumer.with(rawMap, null, (consumer) => {
    const pos = consumer.originalPositionFor(generatedPosition)

    if (!pos.source || pos.line === null) {
      console.log('没有找到对应源码位置')
      return
    }

    const sourceCode = consumer.sourceContentFor(pos.source, true)

    if (!sourceCode) {
      console.log('map 文件里没有 sourcesContent，无法展示源码片段')
      return
    }

    const lines = sourceCode.split('\n')
    const start = Math.max(0, pos.line - 3)
    const end = Math.min(lines.length, pos.line + 2)
    const around = lines.slice(start, end).map((line, index) => {
      const lineNumber = start + index + 1
      const marker = lineNumber === pos.line ? '>' : ' '

      return `${marker} ${String(lineNumber).padStart(4, ' ')} | ${line}`
    })

    console.log(`${pos.source}:${pos.line}:${(pos.column ?? 0) + 1}`)
    console.log(around.join('\n'))
  })
}

printSourceContext()

输出大概长这样：

webpack:///./src/pages/Order/index.tsx:87:13
    85 |   const orderId = getOrderId()
    86 |
>   87 |   await submitOrder(orderId)
    88 |
    89 |   setLoading(false)

这样堆栈就能像 IDE 一样，直接给出「出错行 + 前后 2 行代码 + 变量名」的完整定位视图。

端到端：自建一个报错定位服务

上面把生成和解析都搞清楚了，接下来把它拼成一套能用的服务。整体链路：

┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│  构建阶段（CI）  │      │   运行时（浏览器）│      │   解析服务（Node）│
├─────────────────┤      ├─────────────────┤      ├─────────────────┤
│ 1. 打包生成      │      │ 3. 捕获错误      │      │ 5. 收到上报      │
│    .js + .map   │      │    读 stack     │      │ 6. 找 release   │
│ 2. 上传 .map    │─────►│ 4. 上报 stack   │─────►│    对应的 map   │
│    到私有存储    │      │    + release    │      │ 7. 逐帧解析      │
│                 │      │                 │      │ 8. 落库 / 展示  │
└─────────────────┘      └─────────────────┘      └─────────────────┘

四块拆开讲。

一、构建阶段：把 map 存到私有位置

构建产出 .map 后，别丢公开 CDN，也别丢公司里所有人都能看的 OSS Bucket。放到「只有解析服务能访问的私有存储」——比如带鉴权的 S3、内网 MinIO，或者直接就在解析服务的机器上开一个受保护目录。

上传sourceMap的三条铁律：

  1. 上传时带上版本号（GIT_SHA 或 package.json 的 version），路径要能唯一定位「这次构建的所有 map」。
  2. 上传成功后，本地部署目录里的 .map 全部删掉。
  3. 构建注入的 __APP_VERSION__ 必须和上传路径的版本号一致，运行时上报要带上它。

二、运行时：上报关键字段

前端这块之前的《错误监控》篇讲过，这里只补 Source Map 场景下额外需要的字段：

window.addEventListener('error', (event) => {
  report({
    release: __APP_VERSION__,       // 构建时注入，和 map 存储的目录对应
    message: event.message,
    filename: event.filename,        // 出错的 JS 文件 URL
    lineno: event.lineno,            // 1-based
    colno: event.colno,              // 1-based（后端解析时要 -1）
    stack: event.error?.stack,       // 完整堆栈字符串
    timestamp: Date.now(),
    userAgent: navigator.userAgent,
  })
})

stack 字符串各浏览器格式不太统一（Chrome/Firefox/Safari 都有差别），自己写正则解析容易漏。用现成的 error-stack-parser 库，它把这些差异都处理了：

pnpm add error-stack-parser

import ErrorStackParser from 'error-stack-parser'

try {
  // ... 业务代码
} catch (err) {
  const frames = ErrorStackParser.parse(err as Error)
  // frames: [{ fileName, lineNumber, columnNumber, functionName }, ...]
  report({ release: __APP_VERSION__, frames })
}

三、解析服务：核心代码

用 Node + Koa 写一个最小可用版本。功能就三件事：接收堆栈 → 找对应版本的 map → 逐帧还原。

这里有个性能点要提前说清楚：SourceMapConsumer 不是普通 JSON 对象。它初始化时会解析 mappings 里的 VLQ 数据，0.7 版本以后底层还会用到 WASM 资源。大项目的 .map 文件可能几十 MB，如果每解析一次错误都重新读文件、重新创建 consumer，CPU 和内存都会很吃紧。

所以服务端一般会把已经创建好的 consumer 缓存起来。缓存 key 用 release + jsFileName，表示“某个版本下某个 JS 文件对应的 map”。但也不能无限缓存，否则 map 多了会把内存撑爆，所以这里用 LRU：最多保留 50 个，最近不用的自动淘汰。dispose 会在缓存项被淘汰时触发，里面调用 consumer.destroy()，把 source-map 底层占用的资源释放掉。

// server/parse.ts
import Koa from 'koa'
import bodyParser from '@koa/bodyparser'
import { readFileSync, existsSync } from 'node:fs'
import { join } from 'node:path'
import { SourceMapConsumer } from 'source-map'
import { LRUCache } from 'lru-cache'

interface StackFrame {
  fileName: string
  lineNumber: number
  columnNumber: number
  functionName?: string
}

interface ParseRequest {
  release: string
  frames: StackFrame[]
}

const MAP_STORAGE_DIR = process.env.MAP_DIR || '/data/sourcemaps'

// 缓存已经初始化好的 consumer，避免每次报错解析都重新读文件、重新解析 VLQ
// 大项目一个 map 可能几十 MB，构建 consumer 是 CPU 密集操作
const consumerCache = new LRUCache<string, SourceMapConsumer>({
  max: 50,
  dispose: (consumer) => consumer.destroy(),  // v0.7+ 必须显式释放
})

async function getConsumer(release: string, jsFileName: string) {
  // 同一个版本、同一个 JS 文件，对应唯一的一份 sourcemap
  const cacheKey = `${release}::${jsFileName}`

  // 命中缓存就直接复用，避免重复读文件和重复初始化 SourceMapConsumer
  if (consumerCache.has(cacheKey)) {
    return consumerCache.get(cacheKey)!
  }

  // map 文件按 release 分目录存储，避免不同版本的同名 JS 文件互相覆盖
  const mapPath = join(MAP_STORAGE_DIR, release, `${jsFileName}.map`)
  if (!existsSync(mapPath)) {
    throw new Error(`Source map not found: ${release}/${jsFileName}.map`)
  }

  // 首次访问才读取 .map 并创建 consumer；创建成功后放入 LRU 缓存
  const rawMap = readFileSync(mapPath, 'utf-8')
  const consumer = await new SourceMapConsumer(JSON.parse(rawMap))
  consumerCache.set(cacheKey, consumer)
  return consumer
}

function extractJsFileName(fileUrl: string) {
  // https://cdn.example.com/assets/app.b8f2a1c9.js → app.b8f2a1c9.js
  return fileUrl.split('/').pop()!.split('?')[0]
}

async function parseStack(req: ParseRequest) {
  const results = []

  // 一个错误堆栈里通常有多帧，每一帧都要尝试还原到源码位置
  for (const frame of req.frames) {
    try {
      // frame.fileName 通常是完整 CDN URL，这里只取出 JS 文件名去匹配 .map
      const jsName = extractJsFileName(frame.fileName)
      const consumer = await getConsumer(req.release, jsName)

      // 浏览器上报的列号是 1-based，source-map 的 column 参数是 0-based
      const pos = consumer.originalPositionFor({
        line: frame.lineNumber,
        column: frame.columnNumber - 1,  // 上报是 1-based，库要 0-based
      })

      // 找不到映射也不要中断整条堆栈，标记当前帧解析失败即可
      if (!pos.source) {
        results.push({ ...frame, resolved: false })
        continue
      }

      // 截取源码上下文（前后 2 行）
      // 第二个参数传 true：找不到 sourcesContent 时返回 null，而不是直接抛错
      const sourceCode = consumer.sourceContentFor(pos.source, true)
      const context = sourceCode
        ? sourceCode.split('\n').slice(
            Math.max(0, pos.line! - 3),
            pos.line! + 2,
          )
        : null

      results.push({
        resolved: true,
        source: pos.source.replace(/^webpack:\/\/[^/]*\//, ''),
        line: pos.line,
        column: pos.column,
        name: pos.name || frame.functionName,
        context,
      })
    } catch (err) {
      // 单帧解析失败不能影响其他帧，错误信息保留下来方便排查
      results.push({ ...frame, resolved: false, error: (err as Error).message })
    }
  }
  return results
}

const app = new Koa()
app.use(bodyParser())

app.use(async (ctx) => {
  // 只暴露一个解析接口：接收 release + stack frames，返回源码定位结果
  if (ctx.method === 'POST' && ctx.path === '/parse') {
    ctx.body = await parseStack(ctx.request.body as ParseRequest)
  } else {
    ctx.status = 404
  }
})

app.listen(3000, () => console.log('🔧 Source map parser on :3000'))

依赖版本供参考：koa@2.15、@koa/bodyparser@5、source-map@0.7.4、lru-cache@10、error-stack-parser@2.1、Node.js 20+。

四、几个必须做的工程细节

缓存 SourceMapConsumer。上面代码里的 LRU 不是可选项。一个 5 MB 的 map，new SourceMapConsumer 大约要 200-500ms（要跑 WASM 解压 VLQ 表）。线上一秒来几十条错误，每次都重建就是灾难。用 LRU 缓存，同一个 release 的 map 只解析一次。

**别忘了 consumer.destroy()**。source-map@0.7+ 依赖 WASM，consumer 持有的是 WASM 堆内存，不 destroy 就是内存泄漏。LRU 的 dispose 回调是最省心的挂载点。

批量解析。生产环境错误可能几十万条一天，一条条打接口会把服务打爆。可以把「同 release + 同 stack hash」的错误聚合后再送来解析，一天几百次就够。

map 存储别放公网。反复强调：私有 S3、带鉴权的内网存储，或者干脆放本地磁盘。哪怕解析服务被打穿了，也不能让 map 被下载走。

真实踩过的几个坑

坑 1：stack 里全是 ?，列号是 0

现象：上报堆栈里，跨域脚本的行列号全是 0，filename 显示 Script error。

原因：浏览器出于安全考虑，对跨域脚本的错误信息做了脱敏——CDN 上的 JS 如果没配 CORS，主页面收不到详细堆栈。

解决方案：两步都要做：

  1. CDN 响应加 Access-Control-Allow-Origin。
  2. HTML 里引入脚本时加 crossorigin="anonymous"。

第二步的目的不是为了加载 sourcemap，而是告诉浏览器：这个跨域 JS 按 CORS 模式加载。只有“页面主动用 CORS 加载脚本”并且“CDN 响应允许跨域”同时满足，脚本报错时页面才能拿到真实的 message、filename、lineno、colno 和 stack。否则浏览器会把错误脱敏成 Script error.，监控平台也就没法做后续定位。

anonymous 表示不带 Cookie 等用户凭证请求静态资源，适合 CDN 上的前端 JS 文件。

<script src="https://cdn.example.com/assets/app.js" crossorigin="anonymous"></script>

两个条件缺一不可，只加 crossorigin 而 CDN 不返 CORS 头，脚本反而会加载失败。

坑 2：解析出来的行号是负数或者 null

现象：originalPositionFor 返回 { source: null, line: null, column: null }。

原因通常是：

  1. 上报的列号是 1-based，但直接传给库了（库要 0-based）。差 1 列有时会掉出这一行的映射区间，返回 null。
  2. JS 和 map 不是同一次构建产物。哪怕内容改了一个字符，压缩后的列号就全变了。要保证「上传的 map」和「部署的 JS」来自同一次 CI 构建。
  3. 列号超出了这行的最大列。压缩代码可能一行几十万列，但错误列号可能是浏览器估算的，稍微超一点就 miss。这种时候可以给 originalPositionFor 加上 bias: SourceMapConsumer.LEAST_UPPER_BOUND 试试，向后找最近的映射点。

坑 3：release 上传成功了，解析还是找不到 map

现象：CI 日志显示 map 已上传到 s3://sourcemap-private/a1b2c3d4/，但解析服务报「Source map not found」。

原因：运行时上报的 release 不是构建时的 release。常见情况是 __APP_VERSION__ 用了 package.json 的 version（1.0.0），而 map 上传用的是 GIT_SHA（a1b2c3d4）——两边对不上。

解决方案：整个监控体系锁定一个版本号变量，构建注入、map 上传、运行时上报三处用同一个来源。我一般直接用 GIT_SHA，简单粗暴不会错。

坑 4：解析服务 CPU 飙到 100%

现象：QPS 一上来，解析服务 CPU 打满，响应超时。

原因：没缓存 consumer，每次请求都在解析同一份 map 的 VLQ。

解决方案：LRU + 按 release 聚合请求（前面代码里那套）。改完之后一台 4 核机器抗 100 QPS 完全没压力。

自建还是买？

写到这里，其实要说句实话：如果没有特别刚性的合规要求，直接用 Sentry 或者云厂商的监控，别自建。

自建有它的价值——数据完全可控、能深度定制、大体量下更省钱——但代价也很实在：

  • 存储、运维、告警、去重聚合、影响面统计……每一个都是坑。
  • 团队里得有人长期兜底，出问题时半夜也要爬起来。
  • Sentry 在这条路上跑了 10 年，短时间也无法追上。

我的实战判断：

  • 成长期团队：直接上 Sentry SaaS 或云厂商方案，把精力花在业务上。
  • 数据合规硬要求（金融、政务、医疗）：自建 Sentry 开源版，工作量可控。
  • 超大规模 + 有专职监控团队：完全自研，能省很多钱且能做深度定制。

但理解自建原理是有价值的——你会知道 Sentry 后台按了什么魔法、为什么 release 对不上就解析不出来、为什么 CORS 一定要配。用轮子的人，最好懂轮子怎么造。

小结

  1. Source Map 本质是一份 压缩坐标 ↔ 源码坐标 的映射文件，mappings 字段用 VLQ 编码存差值，所以能把几百万个映射压到几 MB。
  2. 生产构建的正确姿势：Webpack 用 hidden-source-map、Vite 用 sourcemap: 'hidden'，从源头就不产出 sourceMappingURL 注释。
  3. 解析用 source-map 库，SourceMapConsumer.with() 自动管理 WASM 资源；行列号基准要注意——上报是 1-based，库要 0-based，差 1 就映射不上。
  4. 自建服务的关键工程细节：LRU 缓存 consumer、destroy() 释放 WASM 内存、按 release 聚合批量解析、map 存到私有存储。
  5. 版本号是整个链路的主线：构建注入 → map 上传目录 → 运行时上报，三处必须用同一个来源（推荐 GIT_SHA）。
  6. 跨域脚本要拿到完整堆栈，CDN 的 CORS 头和 HTML 的 crossorigin 属性缺一不可。
  7. 除非有硬合规要求，绝大多数团队应该直接用 Sentry 或云监控，理解自建原理是为了用好平台、看懂问题。
