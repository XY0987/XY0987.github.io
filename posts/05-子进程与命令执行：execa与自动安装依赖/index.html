子进程与命令执行：execa 与自动安装依赖

发表于2026|更新于2026|工程化
|字数总计:1.9k|阅读时长:7分钟

前言：脚手架生成完文件，往往还要替用户干几件脏活累活：自动 npm install 装依赖、git init 初始化仓库、跑个格式化命令。这些都要靠「子进程」去调用外部命令。这一篇讲 Node 原生 child_process 的坑，以及为什么大家都换用 execa，最后实现一个能识别包管理器的自动装依赖功能。

为什么需要子进程

CLI 工具本身是个 Node 程序，但它经常需要调用别的命令行程序：npm、pnpm、git、tsc……这些不是 JS 函数，没法直接调用，只能以「开一个子进程去执行命令」的方式来跑。这就是 child_process 模块和 execa 要解决的事。

典型场景：

  • 生成项目后自动 npm install；
  • 自动 git init 并 git add 第一次提交；
  • 调用 prettier --write 格式化生成的代码；
  • 读取 git config user.name 拿默认作者名填进模板。

原生 child_process 的痛点

Node 自带 node:child_process，常用的是 spawn 和 exec。能用，但有几个让人难受的点：

import { spawn } from 'node:child_process'

const child = spawn('npm', ['install'], { stdio: 'inherit' })

child.on('close', (code) => {
  if (code !== 0) {
    console.error('安装失败')
  }
})

痛点在于：

  1. 基于事件/回调，要自己监听 close、error，包成 Promise 很啰嗦；
  2. 跨平台坑多，Windows 上跑 npm 这类命令经常要 shell: true 才行，否则报 ENOENT；
  3. 错误信息不够友好，排查麻烦。

所以社区几乎一边倒用 execa 来封装这些细节。

execa：更好用的子进程库

execa 是 sindresorhus 出的子进程库，把上面的坑都处理了：Promise 化、跨平台、错误信息清晰。当前主流是 v9，ESM-only（这也是上一阶段强调新 CLI 用 ESM 的原因之一）。

npm i execa

最常用的数组语法：

import { execa } from 'execa'

// execa(命令, [参数数组], 选项)
const { stdout } = await execa('node', ['--version'])
console.log('Node 版本:', stdout)

它返回一个 Promise，await 后能拿到 stdout、stderr、exitCode 等。命令失败（退出码非 0）时会直接 reject 抛错，配合 try/catch 处理，比手动判断退出码舒服得多：

try {
  await execa('git', ['status'])
} catch (err) {
  // err.stderr、err.exitCode 都在这
  console.error('不是一个 git 仓库')
}

输出要不要显示给用户

这是 execa 最关键的一个选项 stdio，决定子进程的输出怎么处理：

// 1. 默认：捕获输出到变量，终端看不到子进程输出
const { stdout } = await execa('git', ['config', 'user.name'])

// 2. inherit：把子进程输出直接接到当前终端，用户能实时看到
await execa('npm', ['install'], { stdio: 'inherit' })

什么时候用哪个，是新手最容易搞混的：

需求 stdio 例子
想拿命令输出做后续处理 默认（捕获） 读 git config user.name
想让用户实时看到进度 'inherit' npm install 的安装日志

装依赖这种耗时又有大量输出的操作，一定要 stdio: 'inherit'，否则用户盯着一个不动的 spinner 等几十秒，完全不知道发生了什么。反过来，你只是想悄悄读个 git 配置，就用默认捕获，别把输出刷到终端。

execa 也支持模板字符串语法。没有选项时可以写 await execa`npm install` ；需要传选项时，要先用括号传配置，再接模板字符串：await execa({ stdio: 'inherit' })`npm install` 。如果命令和参数是运行时拼出来的，数组语法 execa('npm', ['install']) 也很直观，参数边界更明确。

实战：自动安装依赖

脚手架最常见的子进程需求就是自动装依赖。但这里有个绕不开的问题：用户用的是 npm、pnpm 还是 yarn？ 装错了包管理器会很别扭。

好在现代包管理器在执行 npm create / npx 时，会通过环境变量 npm_config_user_agent 暴露自己。我们可以据此判断：

// 从 npm_config_user_agent 解析出当前包管理器
function detectPackageManager() {
  const ua = process.env.npm_config_user_agent || ''
  if (ua.startsWith('pnpm')) return 'pnpm'
  if (ua.startsWith('yarn')) return 'yarn'
  if (ua.startsWith('bun')) return 'bun'
  return 'npm'
}

比如用户跑 pnpm create my-app，npm_config_user_agent 会以 pnpm/... 开头，我们就用 pnpm 装依赖，和用户的习惯保持一致。这正是 create-vite 等工具能「你用啥我用啥」的原理。

然后封装一个装依赖函数：

import { execa } from 'execa'

async function installDeps(cwd) {
  const pm = detectPackageManager()
  console.log(`使用 ${pm} 安装依赖...`)

  // 各包管理器的安装命令统一都是 install
  await execa(pm, ['install'], {
    cwd,               // 在生成的项目目录里执行
    stdio: 'inherit',  // 实时显示安装进度
  })
}

注意 cwd 选项：它指定子进程的工作目录。脚手架是在「调用命令的目录」运行的，但装依赖要在「新生成的项目目录」里，所以必须传 cwd: targetDir，否则会装到错误的地方。这是又一个高频坑。

实战：初始化 git 仓库

另一个常见操作是自动 git init。注意要做容错——用户机器上可能没装 git，或者已经在一个 git 仓库里：

import { execa } from 'execa'

async function initGit(cwd) {
  try {
    // 先确认 git 可用
    await execa('git', ['--version'])
  } catch {
    console.warn('未检测到 git，跳过仓库初始化')
    return
  }

  await execa('git', ['init'], { cwd })
  await execa('git', ['add', '-A'], { cwd })
  await execa('git', ['commit', '-m', 'init'], { cwd })
  console.log('已初始化 git 仓库')
}

这里体现一个原则：自动化操作要可降级。git 初始化失败不该让整个脚手架崩掉，提示一句跳过即可——用户大不了自己手动 init。下一篇架构设计会专门讲这种「哪些错误该致命、哪些该降级」的取舍。

把流程串起来

结合前几篇，一个 create 命令的核心流程大致是：

import { spinner } from '@clack/prompts'

async function create(targetDir, options) {
  // 1. 拷贝并渲染模板（上一篇）
  await copyTemplate(templateDir, targetDir, options)

  // 2. 自动装依赖
  if (options.install) {
    const s = spinner()
    s.start('安装依赖')
    await installDeps(targetDir) // stdio:inherit 时进度会盖过 spinner，按需取舍
    s.stop('依赖安装完成')
  }

  // 3. 初始化 git
  if (options.git) {
    await initGit(targetDir)
  }
}

一个体验上的取舍：stdio: 'inherit' 会把 npm 的安装日志直接刷到终端，这时候它和 spinner 的转圈会「打架」（输出会盖掉 spinner）。所以要么装依赖时用 inherit 不配 spinner、让 npm 自己的进度条来反馈；要么用默认捕获输出 + spinner，安装完再统一提示。两种都行，关键是别让两套 UI 互相干扰。我个人偏向装依赖直接 inherit，让用户看到真实进度。

小结

  1. CLI 经常要调用外部命令（npm、git、tsc），这要靠子进程实现。
  2. 原生 child_process 基于回调、跨平台坑多，社区普遍改用 execa 封装。
  3. execa 数组语法 execa('npm', ['install'], opts) 最安全，命令失败会直接抛错，配合 try/catch。
  4. stdio: 'inherit' 让用户实时看到输出（装依赖必用），默认捕获模式用于读取命令结果。
  5. 用 cwd 指定子进程工作目录，装依赖要传新项目目录，否则装错地方。
  6. 通过 npm_config_user_agent 识别用户用的包管理器，保持「你用啥我用啥」。
  7. git init 等自动化操作要可降级，失败时提示跳过而不是让脚手架崩溃。
