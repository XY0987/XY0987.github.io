微前端选型：Module Federation、qiankun 与 wujie

发表于2026|更新于2026|工程化
|字数总计:3.3k|阅读时长:10分钟

前言：微前端是个被追捧也被滥用的概念。这一篇讲清楚它的核心思想、几个主流方案（Module Federation、qiankun、wujie）的实现差异，以及最重要的——什么时候该用、什么时候是给自己找麻烦。定位是认知 + 选型，不强求实现细节。我的基本态度先摆在前面：微前端是一种「组织架构的技术妥协」，不是技术先进性的体现，能不用尽量不用。

先理解微前端的几个核心原理

先把底层概念说清楚，否则一上来比较 Module Federation、qiankun、wujie，很容易只记住几个框架名字。

微前端的本质不是「把页面拆小」这么简单，而是：主应用负责承载和调度，子应用保持相对独立，在运行时被加载进来。一个很简化的模型是这样：

用户访问主应用
    ↓
主应用根据路由/配置决定加载哪个子应用
    ↓
加载子应用资源（JS / CSS / HTML / remoteEntry / iframe）
    ↓
执行子应用的 mount 生命周期，把它渲染到指定容器
    ↓
切走时执行 unmount，清理 DOM、事件、定时器、样式和全局副作用

这里面真正难的不是「加载一个 JS 文件」，而是多个独立应用跑在同一个产品里时，怎么不互相污染。核心概念主要有这几个：

核心概念 要解决的问题 常见做法
运行时集成 子应用如何在不重新构建主应用的情况下接入 HTML Entry、远程模块、动态脚本、iframe
生命周期 子应用什么时候初始化、挂载、卸载 bootstrap / mount / unmount
JS 沙箱 子应用改 window、注册全局变量、打补丁时别污染主应用 Proxy 拦截、快照恢复、iframe 隔离
CSS 隔离 子应用的样式别覆盖主应用或其他子应用 选择器加前缀、CSS Modules、Shadow DOM、动态样式卸载
路由与通信 主应用和子应用如何同步页面状态、传递数据 路由基座、props、事件总线、全局状态

安全沙箱这个词容易让人误会。很多微前端框架说的沙箱，主要是运行时隔离：拦截子应用对 window 的读写，记录它新增了哪些全局变量，卸载时再恢复现场。比如 qiankun 的思路就是用 Proxy 包一层全局对象，让子应用以为自己在改 window，实际改的是沙箱里的代理对象。这样能减少全局变量污染，但它不是浏览器级别的安全边界。

如果你真的要隔离不可信代码，Proxy 沙箱远远不够。更强的边界通常来自 iframe、不同源隔离、CSP、SRI、权限收敛这些浏览器和安全工程手段。微前端里的「沙箱」更多是在解决工程隔离，不要把它理解成可以放心执行任意第三方代码的安全容器。

CSS 隔离也是同一个逻辑：多个应用塞到一个页面里，.button、body、#app 这类选择器很容易互相覆盖。轻量做法是构建时给选择器加前缀，或者用 CSS Modules、BEM 这类命名约束；更强一点是 Shadow DOM，它能把样式作用域限制在 Web Component 内部；如果用 iframe，则浏览器天然会把样式环境隔开。

所以理解微前端时，我建议先抓住一句话：微前端的核心不是拆，而是运行时集成后的隔离与治理。选型差异，本质上就是不同方案在「集成体验、隔离强度、工程复杂度」之间做取舍。

微前端要解决的是什么问题

先说清楚微前端不是用来解决什么的。它不是「让代码更优雅」「让性能更好」的技术——恰恰相反，它几乎必然带来额外的复杂度和性能开销。

微前端解决的是组织和工程层面的问题：

① 巨石应用太大    一个前端仓库几十万行，构建慢、改动牵一发动全身
② 多团队协作      多个团队要在同一个前端产品上独立开发、独立发布，互不阻塞
③ 技术栈共存      老系统 Vue2、新模块想用 React，要在一个产品里共存
④ 渐进式迁移      老的巨石应用想一块块重写，而不是停下来大重构

核心诉求是 「独立开发、独立部署、运行时集成」——多个团队各自开发、各自发布自己的部分，最终在运行时拼成一个完整应用。它本质是把后端「微服务」的思路搬到前端。

关键判断：如果你没有「多团队独立交付」或「必须技术栈共存/渐进迁移」的硬需求，你大概率不需要微前端。 单团队的中小应用上微前端，是纯纯的过度设计——你会得到微前端的全部复杂度，却享受不到它的任何好处。

Module Federation：运行时共享的底层能力

Module Federation（模块联邦）是 Webpack 5 引入、后来被 Rspack/Vite 生态跟进的一个能力。它是底层机制，不是开箱即用的微前端框架。理解它的核心思想是关键：

两个核心概念：

Remote（远程）    暴露自己的模块给别人用（我把 Button、整个 App 暴露出去）
Host（宿主）      在运行时加载远程模块（我运行时去拉别人暴露的模块来用）

两个核心能力：

  1. 运行时远程模块加载：宿主应用在运行时（不是构建时）去加载另一个独立部署的应用暴露的模块。A 应用能直接 import B 应用运行时暴露的组件/页面，就像用本地模块一样。这意味着 A 和 B 可以独立构建、独立部署，运行时才拼到一起。

  2. 共享依赖（shared）：多个应用都用 React，没必要各自打包一份 React。Module Federation 能声明「React 是共享依赖」，运行时只加载一份，多个应用共用。这解决了微前端最头疼的「重复依赖导致体积爆炸」问题。

// 简化的 Module Federation 配置思路
new ModuleFederationPlugin({
  name: 'app_a',
  remotes: { app_b: 'app_b@https://b.example.com/remoteEntry.js' },  // 我要用 B
  exposes: { './Button': './src/Button' },   // 我暴露 Button 给别人
  shared: ['react', 'react-dom'],            // 这些依赖运行时共享一份
})

Module Federation 的定位：它给了微前端最硬核的能力（运行时模块共享 + 依赖共享），但它不管沙箱隔离、样式隔离、路由这些。它更偏「模块级共享」而非「应用级集成」，适合技术栈统一（都用 React/Vue）、想要细粒度模块共享的场景。

qiankun 与 wujie：应用级微前端框架

qiankun 和 wujie 是国内最流行的两个应用级微前端框架——它们要解决的是「把多个独立的完整应用（子应用）集成到一个主应用里」，重点在隔离。因为一旦把多个独立应用塞进同一个页面，就会互相污染：全局变量打架、CSS 互相覆盖、事件监听泄漏。这几个隔离问题，是应用级微前端的核心难点。三个维度对比：

维度 qiankun wujie
集成方式 加载子应用的 JS/HTML，在主应用 DOM 里运行 用 iframe + Web Component 承载子应用
JS 沙箱 基于 Proxy 的 JS 沙箱（快照/Proxy 隔离全局） 借助 iframe 天然的 JS 隔离
样式隔离 需要处理（scoped、shadow DOM 等），有边界情况 Web Component 的 Shadow DOM 天然隔离
通信 props / 全局状态 / 自定义事件 props / 事件总线，跨 iframe 通信
心智模型 「把子应用的代码跑在主应用环境里，靠沙箱模拟隔离」 「用 iframe 做真隔离，再想办法解决 iframe 的体验问题」

理解它们差异的关键，是「隔离」的实现哲学不同：

  • qiankun：让子应用的代码跑在主应用的环境里，用 JS 沙箱（Proxy 拦截全局访问）+ 样式处理来「模拟」隔离。优点是集成更「原生」（就在主应用 DOM 里）、体验流畅；缺点是隔离是「模拟」的，总有边界情况（某些全局副作用、样式泄漏难完全根治）。

  • wujie：直接用 iframe 承载子应用——iframe 天然就有完整的 JS 和样式隔离（浏览器给的，最彻底）。但 iframe 有自己的问题（路由同步、弹窗被限制在 iframe 内、通信麻烦），wujie 用「iframe 跑 JS + Web Component 渲染 DOM」的组合来规避 iframe 的体验缺陷。优点是隔离彻底、干净；缺点是这套组合本身有它的复杂度和坑。

一句话概括这两者的取舍：qiankun 是「在共享环境里努力隔离」，wujie 是「用天然隔离的 iframe 再努力优化体验」。前者隔离不彻底但集成原生，后者隔离彻底但要处理 iframe 的固有问题。

微前端的代价：想清楚再上

微前端不是免费的。它的代价非常实在，选型前必须掂量：

  1. 复杂度飙升：主子应用的生命周期、路由分发、通信、部署编排、公共依赖版本协调……每一样都是新的复杂度。原本一个应用的事，变成一套分布式系统的事。
  2. 性能开销：运行时加载多个应用、沙箱代理、可能的重复依赖，都是额外开销。微前端几乎不可能比等价的单体应用更快。
  3. 调试变难：一个问题可能横跨主应用和多个子应用，加上沙箱/iframe 隔离，排查链路变长。
  4. 公共依赖协调：子应用们用的 React 版本不一致怎么办？公共库怎么统一？这是持续的协调成本。
  5. 团队心智负担：每个开发者都要理解这套集成机制，新人上手门槛变高。

微前端是「组织问题倒逼出的技术方案」。 当你确实有「多个团队必须独立开发独立发布、且要合成一个产品」的强需求，或者「老系统必须渐进迁移/技术栈必须共存」，微前端才值得它的复杂度。除此之外——

单团队应用        → 别上微前端，好好做模块化和代码分割就行
只是想拆分代码    → Monorepo + 包拆分（第九阶段那套）就够了
只是嫌构建慢      → 优化构建（性能工程篇），不是上微前端

很多团队上了微前端后悔的核心原因，是用微前端解决了本该用「模块化/Monorepo/构建优化」解决的问题，结果背上了不该背的复杂度。先问「是不是组织协作问题」，是才考虑微前端；是技术问题，用技术手段解决。

怎么选（如果确实要用）

如果评估下来确实需要微前端，简单的选型指引：

场景 倾向
技术栈统一、想细粒度共享模块/依赖 Module Federation
多个完整应用集成、需要强隔离、渐进迁移老系统 qiankun / wujie
要彻底的隔离、能接受 iframe 方案的约束 wujie
要「原生」集成体验、能处理沙箱边界情况 qiankun
已经在用 Rspack/Webpack5、追求现代方案 Module Federation（含其上层封装）

再强调一次定位：这些都是认知层的选型参考。真要落地，每个方案都有大量工程细节和坑要踩，需要投入专门的调研和试点。别看了一篇文章就决定给生产项目上微前端——先做小范围 POC 验证它真的解决了你的问题、且代价可接受，再推广。

小结

  1. 微前端的核心不是拆页面，而是运行时集成后的隔离与治理，重点包括生命周期、JS 沙箱、CSS 隔离、路由和通信。
  2. 微前端解决的是组织/工程问题（多团队独立交付、技术栈共存、渐进迁移），不是性能或优雅性问题，本质是前端版微服务。
  3. 没有「多团队独立交付」或「技术栈共存/渐进迁移」硬需求，大概率不需要微前端，单团队应用上它是过度设计。
  4. Module Federation 是底层机制，核心是运行时远程模块加载 + 依赖共享（shared），适合技术栈统一、细粒度共享，但不管沙箱/样式隔离。
  5. qiankun 在共享环境里用 JS 沙箱（Proxy）+ 样式处理模拟隔离，集成原生但隔离有边界情况。
  6. wujie 用 iframe 做天然的 JS/样式隔离，再用 Web Component 优化 iframe 的体验缺陷，隔离彻底但有 iframe 固有问题。
  7. 微前端代价实在：复杂度、性能开销、调试变难、公共依赖协调、心智负担；很多后悔案例是用它解决了本该用模块化/Monorepo/构建优化解决的问题。
  8. 先判断是不是组织协作问题，是才考虑微前端；确需使用时先做小范围 POC 验证，别看一篇文章就上生产。
