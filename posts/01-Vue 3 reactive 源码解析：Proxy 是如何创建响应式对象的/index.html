Vue 3 reactive 源码解析：Proxy 是如何创建响应式对象的

发表于2026|更新于2026|Vue框架及周边库
|字数总计:2.6k|阅读时长:10分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：这一篇先看 Vue 3 响应式系统的入口 reactive。我的理解是，reactive 本身并不负责依赖收集和触发更新，它真正做的是判断目标对象能不能代理、选择合适的代理策略，并复用已经创建过的 Proxy。

先给结论

reactive 的核心链路可以拆成三层：

层级 负责文件 职责
API 入口 packages/reactivity/src/reactive.ts 判断模式，创建或复用 Proxy
拦截器 packages/reactivity/src/baseHandlers.ts 拦截普通对象和数组的 get、set 等操作
依赖系统 packages/reactivity/src/dep.ts 通过 track 收集依赖，通过 trigger 触发更新

所以看 reactive 时不要急着找“更新视图”的逻辑。reactive 只是把对象包成代理对象；真正的依赖收集发生在读取属性时，真正的触发更新发生在修改属性时。

最小示例

import { effect, reactive } from '@vue/reactivity'

const state = reactive({ count: 0 })

effect(() => {
  console.log(state.count)
})

state.count++

这段代码内部大致经历了下面的流程：

原始对象
  │
  ▼
reactive(obj)
  │
  ▼
createReactiveObject(obj)
  │
  ├─ 判断是否是对象
  ├─ 判断是否已经是 Proxy
  ├─ 判断对象类型是否可代理
  ├─ 从 WeakMap 读取缓存
  └─ new Proxy(obj, handlers)
        │
        ├─ get 时 track
        └─ set 时 trigger

reactive 入口做了什么

先看 reactive 的源码入口：

export function reactive<T extends object>(target: T): Reactive<T>
export function reactive(target: object) {
  // readonly 代理本身已经具备响应式读取能力，不能再包一层 mutable 代理，
  // 否则会破坏 readonly 语义，所以这里直接返回原对象。
  if (isReadonly(target)) {
    return target
  }
  // reactive 的本质是选择“可变对象”对应的 handler 与缓存表，
  // 真正的合法性判断、缓存复用和 Proxy 创建都交给 createReactiveObject。
  return createReactiveObject(
    target,
    false,
    mutableHandlers,
    mutableCollectionHandlers,
    reactiveMap,
  )
}

这里有两个关键信息：

  1. 如果传入的是 readonly 代理，直接返回，不再包一层可变代理。
  2. reactive 只是选择参数，真正创建代理的是 createReactiveObject。

这里传给 createReactiveObject 的几个参数很重要：

参数 含义
target 原始对象
false 当前不是 readonly 模式
mutableHandlers 普通对象、数组使用的可变拦截器
mutableCollectionHandlers Map、Set 等集合类型使用的可变拦截器
reactiveMap 缓存当前模式下创建过的代理对象

换句话说，reactive 的职责不是“实现响应式全部逻辑”，而是“进入响应式系统的分发入口”。

为什么要用四个 WeakMap

reactive.ts 中维护了四个缓存表：

// 四个 WeakMap 分别缓存不同响应式模式下的代理对象。
// 这样同一个原始对象多次调用 reactive/readonly 时，可以复用同一个 Proxy，
// 同时 WeakMap 不会阻止原始对象被垃圾回收。
export const reactiveMap: WeakMap<Target, any> = new WeakMap<Target, any>()
export const shallowReactiveMap: WeakMap<Target, any> = new WeakMap<
  Target,
  any
>()
export const readonlyMap: WeakMap<Target, any> = new WeakMap<Target, any>()
export const shallowReadonlyMap: WeakMap<Target, any> = new WeakMap<
  Target,
  any
>()

为什么不是一个 Map？我的理解主要有两点。

第一，不同模式下的代理语义不同。reactive(obj)、readonly(obj)、shallowReactive(obj)、shallowReadonly(obj) 不能共用同一个代理对象，否则读写行为会混乱。

第二，使用 WeakMap 可以避免内存泄漏。原始对象没有被业务代码引用后，对应的缓存记录也可以被垃圾回收。

这也解释了为什么下面这个判断会成立：

const obj = { count: 0 }

reactive(obj) === reactive(obj) // true

因为第二次调用会直接命中 reactiveMap 里的缓存。

createReactiveObject 的五步流程

createReactiveObject 是 reactive.ts 中最值得细读的函数。它不是一上来就 new Proxy，而是先做了多层保护。

function createReactiveObject(
  target: Target,
  isReadonly: boolean,
  baseHandlers: ProxyHandler<any>,
  collectionHandlers: ProxyHandler<any>,
  proxyMap: WeakMap<Target, any>,
) {
  // 1. 响应式系统只能代理对象。基本类型没有属性访问拦截点，直接返回原值。
  if (!isObject(target)) {
    if (__DEV__) {
      warn(
        `value cannot be made ${isReadonly ? 'readonly' : 'reactive'}: ${String(
          target,
        )}`,
      )
    }
    return target
  }

  // 2. 如果 target 已经是 Vue 创建的 Proxy，大多数情况下直接复用。
  // 唯一例外是 readonly(reactive(obj))：需要基于 reactive 代理再创建 readonly 代理，
  // 让读取仍能追踪依赖，同时对外暴露只读写保护。
  if (
    target[ReactiveFlags.RAW] &&
    !(isReadonly && target[ReactiveFlags.IS_REACTIVE])
  ) {
    return target
  }

  // 3. 过滤不可代理的目标，例如 markRaw 标记对象、不可扩展对象、Date/RegExp 等。
  const targetType = getTargetType(target)
  if (targetType === TargetType.INVALID) {
    return target
  }

  // 4. 同一个原始对象在同一种响应式模式下只创建一个 Proxy，
  // 既避免重复代理，也保证 reactive(obj) === reactive(obj)。
  const existingProxy = proxyMap.get(target)
  if (existingProxy) {
    return existingProxy
  }

  // 5. 根据目标类型选择不同 handler：普通对象/数组与 Map/Set 的拦截逻辑差异很大。
  const proxy = new Proxy(
    target,
    targetType === TargetType.COLLECTION ? collectionHandlers : baseHandlers,
  )
  proxyMap.set(target, proxy)
  return proxy
}

我把它理解为五步：

  1. 不是对象，直接返回。
  2. 已经是代理，大多数情况下直接返回。
  3. 不是 Vue 支持的代理目标，直接返回。
  4. 已经创建过对应代理，直接返回缓存。
  5. 最后才创建新的 Proxy。

这个顺序很关键。它让 reactive 同时做到语义正确、避免重复代理、减少无效开销。

哪些对象可以被 reactive 代理

对象类型的判断在 targetTypeMap 和 getTargetType 中完成：

// 根据原始对象类型决定使用哪一套 Proxy handler：
// 普通对象/数组走 baseHandlers，集合类型走 collectionHandlers，其他类型不代理。
function targetTypeMap(rawType: string) {
  switch (rawType) {
    case 'Object':
    case 'Array':
      return TargetType.COMMON
    case 'Map':
    case 'Set':
    case 'WeakMap':
    case 'WeakSet':
      return TargetType.COLLECTION
    default:
      return TargetType.INVALID
  }
}

// 判断一个值是否可以被转换为响应式对象，以及应该转换成哪类响应式对象。
function getTargetType(value: Target) {
  // 被 markRaw 标记或不可扩展的对象不能被代理，直接视为无效目标。
  return value[ReactiveFlags.SKIP] || !Object.isExtensible(value)
    ? TargetType.INVALID
    : targetTypeMap(toRawType(value))
}

这里可以得到一个很实用的结论：Vue 不是对所有对象都创建响应式代理。

类型 结果
普通对象 使用 baseHandlers
数组 使用 baseHandlers
Map / Set 使用 collectionHandlers
WeakMap / WeakSet 使用 collectionHandlers
Date / RegExp / 其他对象 不创建响应式代理
被 markRaw 标记的对象 不创建响应式代理
不可扩展对象 不创建响应式代理

这也是源码里要区分 COMMON 和 COLLECTION 的原因：普通对象的属性读写和集合类型的 get、set、add、delete 行为不是一套模型。

深层响应式是懒代理

很多人会以为 reactive 会递归遍历整个对象，把所有嵌套对象一次性转成代理。实际上不是。

深层对象是在 get 时按需转换的：

const res = Reflect.get(
  target,
  key,
  // if this is a proxy wrapping a ref, return methods using the raw ref
  // as receiver so that we don't have to call `toRaw` on the ref in all
  // its class methods
  isRef(target) ? target : receiver,
)

if (isSymbol(key) ? builtInSymbols.has(key) : isNonTrackableKeys(key)) {
  return res
}

if (!isReadonly) {
  track(target, TrackOpTypes.GET, key)
}

if (isShallow) {
  return res
}

if (isRef(res)) {
  // ref unwrapping - skip unwrap for Array + integer key.
  return targetIsArray && isIntegerKey(key) ? res : res.value
}

if (isObject(res)) {
  // Convert returned value into a proxy as well. we do the isObject check
  // here to avoid invalid value warning. Also need to lazy access readonly
  // and reactive here to avoid circular dependency.
  return isReadonly ? readonly(res) : reactive(res)
}

重点是最后这一段：只有当读取到的值仍然是对象时，才会继续调用 reactive(res) 或 readonly(res)。

这就是“懒代理”。它的好处是不用在初始化阶段递归遍历整个对象树，只有真正访问到的嵌套对象才会被代理。

get 和 set 分别连接 track 与 trigger

reactive 创建出来的代理对象之所以有响应式能力，是因为 handler 在读写时分别接入了依赖系统。

读取属性时调用 track：

if (!isReadonly) {
  track(target, TrackOpTypes.GET, key)
}

修改属性时调用 trigger：

const hadKey =
  isArray(target) && isIntegerKey(key)
    ? Number(key) < target.length
    : hasOwn(target, key)
const result = Reflect.set(
  target,
  key,
  value,
  isRef(target) ? target : receiver,
)
// don't trigger if target is something up in the prototype chain of original
if (target === toRaw(receiver)) {
  if (!hadKey) {
    trigger(target, TriggerOpTypes.ADD, key, value)
  } else if (hasChanged(value, oldValue)) {
    trigger(target, TriggerOpTypes.SET, key, value, oldValue)
  }
}

这里有一个很重要的拆分：

  • reactive.ts 负责创建代理。
  • baseHandlers.ts 负责拦截读写。
  • dep.ts 负责管理依赖关系。

这种拆分让响应式系统的边界很清晰。你在读 reactive.ts 时，只要把重点放在“代理对象如何创建”上；等读 baseHandlers.ts 时，再重点看“属性读写如何接入依赖系统”。

markRaw 和 toRaw 的定位

markRaw 和 toRaw 是两个容易混淆的 API。

markRaw 是提前告诉 Vue：这个对象以后不要代理。

export function markRaw<T extends object>(value: T): Raw<T> {
  // SKIP 标记会在 getTargetType 中被识别，后续 reactive/readonly 会直接返回原对象。
  // 只有可扩展对象才能安全地追加内部标记。
  if (!hasOwn(value, ReactiveFlags.SKIP) && Object.isExtensible(value)) {
    def(value, ReactiveFlags.SKIP, true)
  }
  return value
}

toRaw 是从代理对象反查原始对象：

export function toRaw<T>(observed: T): T {
  // 代理对象通过 ReactiveFlags.RAW 暴露它包裹的上一层对象。
  // 这里递归展开，是为了兼容 readonly(reactive(obj)) 这种多层代理场景。
  const raw = observed && (observed as Target)[ReactiveFlags.RAW]
  return raw ? toRaw(raw) : observed
}

一个是“创建代理前跳过”，一个是“创建代理后还原”。这两个 API 都是响应式系统的逃生通道，但不要在业务代码里长期持有 toRaw 返回的原始对象，否则很容易绕过响应式更新。

小结

  1. reactive 不是完整响应式系统，它只是响应式代理的入口。
  2. createReactiveObject 通过五步流程完成对象检查、代理复用和 Proxy 创建。
  3. Vue 使用四个 WeakMap 分别缓存四种响应式模式下的代理对象。
  4. 深层响应式不是初始化时递归完成的，而是在 get 阶段按需懒代理。
  5. 读属性时通过 track 收集依赖，写属性时通过 trigger 触发更新。

读懂 reactive.ts 后，下一步最自然的入口就是 baseHandlers.ts。因为 reactive 创建出来的 Proxy 到底如何收集依赖、如何触发更新，答案都在 handler 里。
