组件库构建（二）：subpath exports、按需引入与 sideEffects

发表于2026|更新于2026|工程化
|字数总计:5.8k|阅读时长:21分钟

前言：上一篇讲了产物格式和类型。这一篇讲组件库「按需引入」这件事的完整工程实现——从 @my-ui/button 这种细粒度导入路径怎么落地，到 babel-plugin-import 这类插件到底在干嘛，再到 sideEffects 怎么精确声明才不会把样式摇没。这三块是环环相扣的：想让用户只打包用到的组件，光靠一个 import 是不够的，得从产物结构、导入路径、副作用声明一起配合。

先搞清楚：什么叫「按需引入」

用户用组件库时，通常这样写：

import { Button, DatePicker } from '@my-ui/components'

「按需引入」要保证的是：用户只用了 Button 和 DatePicker，最终 bundle 里就只有这两个组件的代码和样式，不会把整个组件库几十个组件全打进去。

实现按需，本质上有两条技术路线，很多人把它们混为一谈：

路线 原理 依赖什么
Tree Shaking（现代） 打包器静态分析，删掉没用到的导出 ESM + sideEffects 正确声明
路径改写（传统） 把 import { Button } 改写成 import Button from '.../button' 插件（babel-plugin-import 等）

现代组件库应该走第一条路（Tree Shaking），第二条是历史方案，理解它能帮你看懂老项目和一些库的设计。下面分别讲。

Tree Shaking 路线：为什么组件库常常「摇不干净」

理论上，只要组件库出 ESM 产物，打包器就能 Tree Shaking。但组件库比普通工具库更容易「摇不干净」，原因有三个，逐个说。

原因一：入口文件的「桶文件」写法

组件库的入口通常是个 barrel（桶）文件，把所有组件 re-export：

// src/index.ts
export * from './button'
export * from './date-picker'
export * from './table'
// ...几十个

现代打包器对 export * 的 barrel 文件是能 Tree Shaking 的——前提是每个子模块都是纯 ESM 且没有副作用。问题往往出在下一条。

原因二：样式副作用没声明清楚

组件几乎一定有样式副作用。假设 button/index.ts 里这样引样式：

// src/button/index.ts
import './button.css'   // 副作用！
export const Button = /* ... */

打包器看到 import './button.css'，会认为这个模块「有副作用」，于是即使用户没用 Button，也不敢删它——因为删了可能丢样式。结果就是全量打包。

这正是 sideEffects 字段要解决的（下面单独讲）。这里先记住：样式引入是组件库 Tree Shaking 最大的绊脚石。

原因三：模块顶层的副作用代码

有些组件在模块顶层干了事情，比如注册全局指令、往 window 挂东西、执行 polyfill。这些都是副作用，打包器一律保守保留。

// ❌ 顶层副作用，会阻碍摇树
registerGlobalDirective('tooltip')

export const Tooltip = /* ... */

组件库作者应该尽量避免模块顶层副作用，把这类逻辑延迟到组件真正被使用时执行。

sideEffects：组件库里最容易配错的字段

sideEffects 的基础语义在「Tree Shaking、副作用与代码分割」那篇讲过：false 表示整个包纯净可随便摇，数组表示「除了这些文件其它都纯净」。组件库的深水区在于——要把 CSS 副作用和 JS 副作用分开精确声明。

最常见的正确写法：

{
  "name": "@my-ui/components",
  "sideEffects": [
    "**/*.css",
    "**/*.scss",
    "**/style/**"
  ]
}

它表达的是：除了样式文件，我所有的 JS 模块都是纯净的，没用到的 JS 尽管摇掉；但样式文件有副作用，请保留（用到哪个组件就保留哪个组件的样式）。

这里的精妙之处在于：打包器会把「JS 可摇」和「CSS 需保留」分开处理。用户 import { Button }，打包器摇掉了其它组件的 JS，同时因为 Button 的 JS 里 import './button.css' 被保留、其它组件的 JS 被删了（连带它们的 CSS import 也没了），最终样式也只剩 Button 的。JS 和 CSS 的按需，是一起达成的。

几个真实会踩的坑：

坑 1：图省事写 sideEffects: false，底层样式被摇掉。这是最经典的翻车，但表现往往不是「所有 CSS 都没了」，而是样式残缺、看起来怪怪的。

原因在于：打包器判断「要不要保留一个模块」，主要看它的导出有没有被用到。import './button.css' 这种语句不产生导出，只是往页面里注入样式，属于副作用。你写了 sideEffects: false，就等于告诉打包器「这个包里所有模块都是纯净的，副作用可以删」——于是这些 CSS import 会被当成可删除代码处理。

这里有个反直觉的点：文件被引用了，不代表文件里的所有 import 都会保留。打包器会把一个模块拆成两部分看：

// button/index.ts
import './button.css'          // 副作用：注入样式，不产生 JS 导出
export const Button = () => {} // 值导出：用户 import 了这个

用户 import { Button } 时，button/index.ts 这个模块会被保留，因为 Button 导出被用到了。但 import './button.css' 不产生任何 JS 值，只是执行时往页面塞样式。你声明了 sideEffects: false，打包器就认为「这个 import 删了也不影响 JS 逻辑」，于是把这条 import 干掉——模块留着，里面的 CSS import 没了。

如果是单独的文件，比如 style/base.css 只被 import './base.css' 引用、没有任何 JS 导出，那整个模块连带着一起被摇掉，因为打包器眼里它「没有任何被用到的导出」。

具体会丢哪些？

  1. 组件自己的样式文件。比如 Button 的 JS 被保留了，但它顶部的 import './button.css' 可能被摇掉，按钮 DOM 还在，颜色、圆角、间距全没了。
  2. 底层公共样式。像 base.css、reset、CSS 变量、主题 token 这类文件，通常单独放在 style/ 目录，靠入口或各组件间接 import，没有对应的 JS 导出，最容易被整段删掉。
  3. 没用到的组件样式。这个其实是正确行为，不该算坑——用户没 import Table，table.css 被摇掉是符合预期的。

所以问题不是「一写 sideEffects: false 就所有 CSS 都消失」，而是那些只通过副作用 import 存在的样式，尤其是底层基础样式，会被误删。有 CSS 的组件库**永远不要写 sideEffects: false**，至少要把 **/*.css 这类样式文件排除出来。

坑 2：CSS 的路径 glob 没匹配全。sideEffects 数组里的路径是 glob 模式，打包器拿它来判断「哪些文件有副作用、摇树时不能删」。配错了不会报错，但样式会静默丢失——和坑 1 一样，表现通常是个别组件样式残缺，很难第一时间定位到 glob。

先搞清楚匹配规则：sideEffects 的路径是相对于包根目录的，不是相对于 src/。你发到 npm 的是 dist/ 产物，glob 要覆盖的是用户实际安装到的文件路径。

@my-ui/components/
├── dist/
│   ├── button/
│   │   ├── index.mjs
│   │   └── style.css        ← 用户装到的是这个
│   └── style/
│       └── base.css
└── package.json               ← sideEffects 写在这里

几个常见漏配场景：

你写的 glob 能匹配到 匹配不到
*.css 根目录下的 style.css dist/button/style.css（只匹配一层）
**/*.css 任意深度的 .css .scss、.less 源文件
**/*.scss Sass 源文件 编译后的 .css（如果用户引的是产物）
**/style/** dist/style/base.css 等 style/ 目录下的文件 dist/button/style.css（style 是文件名，不是目录）

最容易漏的几种情况：

  1. **只写了 *.css，没写 **/*.css**。*.css 只匹配包根目录那一层，组件样式在 dist/button/style.css、dist/table/style.css 这种嵌套路径下就匹配不到。这是最高频的 glob 笔误。

  2. 源码后缀和产物后缀不一致。开发时写 .scss / .less，构建后发布的是 .css。sideEffects 要按用户最终引用的产物来写，不是按源码后缀。只写 **/*.scss 拦不住发布后的 .css 被误删。

  3. 零运行时 CSS-in-JS 的编译产物。Vanilla Extract、PandaCSS 这类方案，构建后通常产出普通 .css 文件，**/*.css 能覆盖。但如果某些样式逻辑留在 .css.js 或带副作用的 .js 里（运行时注入的老方案），只写 **/*.css 是不够的，对应的 .js 也要加进 sideEffects。

  4. 全量样式入口路径特殊。全量 CSS 放在 dist/style/index.css，组件 CSS 放在 dist/button/style.css——**/*.css 一般都能兜住。但如果你把公共样式放在非 .css 后缀的文件里，或者目录名不在 glob 覆盖范围内，就会漏。

比较稳的写法是按产物结构兜全：

{
  "sideEffects": [
    "**/*.css",
    "**/*.scss",
    "**/style/**",
    "**/*.css.js"
  ]
}
  • **/*.css：兜住编译后的组件样式和全量样式
  • **/*.scss：如果包里直接发布了 Sass 源文件让用户编译
  • **/style/**：兜住 style/ 目录下的所有文件（包括非 css 后缀的入口）
  • **/*.css.js：兜住部分 CSS-in-JS 方案的 JS 副作用文件

配完之后别靠肉眼猜，发版前用一个只 import 一个组件的 demo 项目跑一遍生产构建，然后检查：

# 1. 构建 demo
pnpm --filter demo build

# 2. 在产物里搜你的组件类名，看 CSS 在不在
rg "my-button" demo/dist/assets/

或者在浏览器里打开页面，看按钮有没有颜色、圆角。glob 漏配不会构建报错，只能靠这种「最小接入验证」抓出来。

坑 3：把有副作用的 JS 也当纯净的摇掉。坑 1、坑 2 都在保 CSS，但如果你用了数组形式的 sideEffects：

{
  "sideEffects": ["**/*.css", "**/*.scss"]
}

等于同时告诉打包器：除了这些样式文件，包里所有 JS 模块都是纯净的，没用到的尽管摇。这时候，有顶层副作用的 JS 文件就可能被误删——机制和坑 1 一样，只是对象从 CSS 换成了 JS。

什么样的 JS 算「有副作用」

模块被加载时，除了导出值之外还「干了别的事」，就是副作用。组件库里很常见：

// 注册全局指令 / 组件
app.component('Tooltip', TooltipDirective)

// 往 window 挂 API（Message、Notification 命令式调用）
window.__MY_UI_MESSAGE__ = createMessageService()

// 执行 polyfill
import 'core-js/stable'

// 扩展第三方库
dayjs.extend(relativeTime)

// 动态创建 DOM 容器
const container = document.createElement('div')
document.body.appendChild(container)

这些代码不产生导出，或者所在文件没有被用户直接 import 到，在「JS 全纯净」的声明下就危险了。

具体会怎么翻车

和 CSS 一样，分两种情况：

情况一：副作用写在单独文件里，靠 import 触发。这是最高频的坑。

// tooltip/index.ts
import './register'              // 只想执行注册，不用它的导出
export const Tooltip = () => {}

// register.ts
registerGlobalDirective('tooltip')  // 纯副作用，没有 export

用户 import { Tooltip } 时，tooltip/index.ts 会保留，但 import './register' 不产生 JS 值。打包器认为 register.ts 是纯净副作用，可以删——Tooltip 组件能渲染，指令却没注册，hover 没反应。

情况二：副作用写在入口文件，但用户没走这个入口。

// src/index.ts（主入口）
import './polyfill'
export { Button } from './button'
export { Table } from './table'

用户走子路径 import { Button } from '@my-ui/components/button'，根本没碰主入口，polyfill 永远不会执行。

优先重构，其次加白名单

我的建议是：能延迟就延迟，别在模块顶层搞副作用。把注册逻辑放到组件真正使用时：

// ✅ 副作用延迟到组件挂载时
let registered = false

export const Tooltip = {
  mounted() {
    if (!registered) {
      registerGlobalDirective('tooltip')
      registered = true
    }
  },
}

// ✅ 命令式 API 延迟初始化
let service: MessageService | null = null

export function message(content: string) {
  if (!service) service = createMessageService()
  return service.show(content)
}

这样副作用跟着「真正被调用的导出」走，不依赖额外的 sideEffects 声明，Tree Shaking 也更干净。

如果确实没法重构（比如必须顶层注册、第三方库要求 import 即执行），把对应文件加进 sideEffects：

{
  "sideEffects": [
    "**/*.css",
    "**/*.scss",
    "**/style/**",
    "**/register.js",
    "**/polyfill.js",
    "**/plugins/**"
  ]
}

注意路径还是相对于包根目录，按发布产物的路径写。如果构建后 register.ts 变成了 dist/tooltip/register.mjs，glob 要能匹配到：

"**/register.*"

或者更精确：

"./dist/tooltip/register.js"

怎么验证

和坑 2 一样，靠「最小接入 demo」抓。除了看样式，还要测非渲染类的能力：

  • 指令组件：hover / click 触发是否正常
  • Message / Notification：命令式 API 能不能弹出
  • 国际化：切换语言后文案是否更新
  • 图标字体：图标是显示正常还是方块

这类问题在开发环境（通常不做完整 Tree Shaking）往往正常，只有用户的生产构建才会暴露。所以发版前一定要用 demo 项目跑 build，别只跑 dev。

subpath exports：@my-ui/button 这种路径怎么来的

除了从主入口按需 import，很多组件库还提供细粒度的子路径导入：

import Button from '@my-ui/components/button'
import { useTable } from '@my-ui/components/table'

这种 @my-ui/components/button 的路径，就是 subpath exports。它的价值：

  1. 对不支持 Tree Shaking 的老环境，子路径导入是「物理级按需」——你 import 哪个路径就只加载哪个文件；
  2. 导入路径即产物边界，非常明确，用户不会不小心把主入口全量拉进来。

subpath exports 的基础写法在「exports 条件导出与双包陷阱」那篇提过。组件库的工程难点是：**组件几十上百个，不可能手写几十条 exports**。所以要自动生成。

但自动生成 exports 只是表面——它背后要求你的构建产物本身就是「每个组件一个独立文件」。这就引出了多入口构建。

为什么需要多入口构建

默认的库构建是单入口：一个 src/index.ts 导出所有组件，构建后产出 dist/index.mjs 一个文件。用户 import { Button, Table } from '@my-ui/components'，打包器从这个单文件里做 Tree Shaking，把没用到的组件摇掉——这是逻辑上的按需。

但 subpath exports 要支持的是另一条路：

import Button from '@my-ui/components/button'

这条路径要求 package.json 的 exports 里有一条 "./button" 指向 dist/button/index.mjs——一个真实存在的独立文件。单入口构建产不出这个文件，你就算在 exports 里写了 "./button"，用户 import 也会报模块找不到。

所以多入口构建解决的核心问题是：把「一个库一个大文件」拆成「每个组件一个独立入口文件」，让 subpath exports 有物理产物可以指向。

它解决什么、适合什么场景：

问题 / 场景 单入口 + Tree Shaking 多入口构建
现代打包器（Vite/webpack/Rollup）按需引入 够用，摇树即可 也能用，但构建产物更多
不支持 Tree Shaking 的环境（老 webpack、部分 SSR） 用户 import 主入口会全量引入 子路径导入只加载单个组件文件，物理级按需
需要 import x from '@my-ui/button' 这种明确路径 做不到，没有独立产物 天然支持
组件数量多，手写 exports 不现实 — 入口和 exports 都可以从目录结构自动生成
配合 babel-plugin-import 做编译时改写 改写目标必须是已存在的子路径 多入口产物就是这些子路径的实体

一句话：Tree Shaking 是「打包器帮你删没用的」；多入口是「从源头上就只产出独立的文件」。现代项目两者往往一起用——主入口给 Tree Shaking 用，子路径给物理级按需和工具链改写用。组件一多，多入口几乎是 subpath exports 的前置条件。

多入口构建 + 自动生成 exports

第一步，让构建工具按「每个组件一个入口」产出文件：

// tsup.config.ts
import { defineConfig } from 'tsup'
import { globSync } from 'tinyglobby'

export default defineConfig({
  // 每个组件目录的 index 都作为一个入口
  entry: globSync('src/*/index.ts'),
  format: ['esm', 'cjs'],
  dts: true,
  external: ['vue'],
  clean: true,
})

产物会变成 dist/button/index.mjs、dist/table/index.mjs 这样一组独立入口。

第二步，用脚本根据组件目录自动生成 exports 字段，别手写：

// scripts/gen-exports.ts
import { readdirSync, writeFileSync, readFileSync } from 'node:fs'

const components = readdirSync('src', { withFileTypes: true })
  .filter((d) => d.isDirectory())
  .map((d) => d.name)

const exportsField: Record<string, unknown> = {
  '.': {
    types: './dist/index.d.ts',
    import: './dist/index.mjs',
    require: './dist/index.cjs',
  },
  './style.css': './dist/style.css',
}

for (const name of components) {
  exportsField[`./${name}`] = {
    types: `./dist/${name}/index.d.ts`,
    import: `./dist/${name}/index.mjs`,
    require: `./dist/${name}/index.cjs`,
  }
}

const pkg = JSON.parse(readFileSync('package.json', 'utf-8'))
pkg.exports = exportsField
writeFileSync('package.json', JSON.stringify(pkg, null, 2) + '\n')

把这个脚本挂到 build 前面跑，exports 就永远和组件目录同步，不会漏、不会手误。Element Plus、Ant Design 这类库的 exports 都是自动生成的，手写不稳定且容易出错。

提醒：这里要区分两件事：package.json 的 exports 管的是「哪些子路径可以被包外访问」，主入口的 index.ts 管的是「从 @my-ui/components 能导出哪些成员」。如果你希望用户既能写 import Button from '@my-ui/components/button'，又能写 import { Button } from '@my-ui/components'，那除了生成 exports["./button"]，还要在主入口里重新导出：

// src/index.ts
export * from './button'
export * from './table'

exports 不会自动帮主入口补导出，它只负责声明可访问路径。加了 exports 后，没声明的深层路径仍然不能访问，比如 import x from '@my-ui/components/dist/button/xxx.js' 会报 ERR_PACKAGE_PATH_NOT_EXPORTED。这是好事，它能锁住公共 API 边界；但老库迁移时要注意，原来用户依赖过的深层路径可能会被你关掉。

还有一个容易误解的点：主入口里写了很多 export * from './button'，不等于用户从主入口导入时一定会全量打包。

// 用户只用 Button
import { Button } from '@my-ui/components'

在 ESM + Tree Shaking 正常工作的情况下，打包器会从 index.ts 追到每个 re-export，发现只有 Button 被使用，理论上可以把 Table、Dialog 这些没用到的导出摇掉。

真正会导致全量的是：这些被 re-export 的组件模块在顶层有副作用，而打包器又不敢删它们。比如每个组件入口都这样写：

// src/table/index.ts
import './style.css'
export const Table = /* ... */

如果没有正确配置 sideEffects，打包器会认为 table/index.ts 被主入口 re-export 了，而且里面还 import 了 CSS，删掉可能丢样式，于是保守地把 Table 也留下。组件一多，就变成「从主入口 import 一个 Button，结果很多组件都进包了」。

所以主入口 re-export 不是问题本身，问题是re-export 的模块能不能被安全摇掉。组件库通常要这样配：

{
  "sideEffects": [
    "**/*.css",
    "**/*.scss",
    "**/style/**"
  ]
}

它表达的是：JS 模块本身尽量纯净，没用到的组件 JS 可以删；CSS 是副作用文件，用到的组件样式要保留。这样用户从主入口 import { Button }，也能尽量只留下 Button 相关的 JS 和 CSS。

按需引入插件：babel-plugin-import 这类东西在干嘛

现在讲第二条路线，也是很多人对「按需引入」的历史印象来源。

早年的组件库（Ant Design 3、Element UI）产物不是 ESM、Tree Shaking 不可靠，用户 import { Button } from 'antd' 会把整个 antd 打进去。当时的解法是 babel-plugin-import：在编译时把这行代码改写成子路径导入。

// 你写的
import { Button } from 'antd'

// babel-plugin-import 编译后改写成
import Button from 'antd/es/button'
import 'antd/es/button/style'   // 顺便把样式也引进来

它做的就是「把命名导入改写成细粒度的路径导入 + 样式导入」，从而绕开「摇不干净」的问题。配置大概是：

// babel.config.js
module.exports = {
  plugins: [
    ['import', { libraryName: 'antd', style: true }],
  ],
}

我的判断是：**babel-plugin-import 是「产物不支持 Tree Shaking」时代的补丁**。如果你现在做组件库，正确做法是把库设计成 ESM + sideEffects 正确声明，让用户零配置就能 Tree Shaking，而不是要求用户装一个 babel 插件。它的现代替代是 unplugin 生态：

  • **unplugin-vue-components**：自动按需导入 Vue 组件。用户在模板里用 <el-button>，插件自动生成对应的 import 和样式引入，连 import 都不用手写。
  • **unplugin-auto-import**：自动导入 API（如 Vue 的 ref、computed，或组件库的 hooks），省掉手写 import。
// vite.config.ts
import Components from 'unplugin-vue-components/vite'
import { ElementPlusResolver } from 'unplugin-vue-components/resolvers'

export default {
  plugins: [
    Components({
      resolvers: [ElementPlusResolver()],   // 自动按需引入 Element Plus
    }),
  ],
}

这些插件本质上还是「路径改写 / 自动生成 import」，但体验比 babel-plugin-import 好得多，且不侵入 babel 配置。

作为组件库作者，你要做什么

关键认知：按需引入是「库的设计」和「用户的工具」共同达成的。作为库作者，我们要做的是：

  1. 出 ESM 产物；
  2. sideEffects 精确声明（CSS 保留、JS 可摇）；
  3. 提供 subpath exports（自动生成）；
  4. 如果要支持 unplugin-vue-components 的自动导入，提供一个 resolver（告诉插件「组件名 → 导入路径 + 样式路径」的映射规则）。

做好这四点，用户几乎零配置就能享受按需引入，这才是现代组件库该有的样子。别让用户为了按需去装 babel 插件、手写一堆配置——那是把库设计的债务转嫁给了用户。

把三件事串起来

用户: import { Button } from '@my-ui/components'
          │
          ▼
ESM 产物  ─────────────────────────────► 打包器能静态分析
          │
sideEffects: ["**/*.css"]  ────────────► JS 可摇、CSS 按用到的保留
          │
subpath exports (@my-ui/components/button) ─► 老环境/明确边界的备选路径
          │
          ▼
最终 bundle 只含 Button 的 JS + CSS

三者不是三选一，而是配合：ESM + sideEffects 是主力（让默认 import 就能按需），subpath exports 是补充（给不能摇树的环境和明确边界）。

小结

  1. 按需引入有两条路线：现代的 Tree Shaking（ESM + sideEffects）和传统的路径改写（babel-plugin-import），优先走前者。
  2. 组件库摇不干净的三大原因：barrel 入口、样式副作用未声明、模块顶层副作用代码。
  3. sideEffects 要精确声明：有 CSS 的库绝不能写 false，要用数组把样式文件排除出来，实现「JS 可摇、CSS 按需保留」。
  4. subpath exports（@my-ui/components/button）用多入口构建 + 脚本自动生成 exports，不要手写几十条。
  5. babel-plugin-import 是产物不支持 Tree Shaking 时代的补丁，现代替代是 unplugin-vue-components / unplugin-auto-import。
  6. 作为库作者，按需引入靠你做好四件事：出 ESM、精确声明 sideEffects、自动生成 subpath exports、提供 resolver，让用户零配置享受按需。
