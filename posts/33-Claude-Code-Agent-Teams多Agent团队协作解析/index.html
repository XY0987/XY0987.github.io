Claude Code Agent Teams 解析：让多个 Claude 会话像团队一样协作

发表于2026|更新于2026|AI相关
|字数总计:3.9k|阅读时长:13分钟

前言：前面讲 Subagents、Agent View、Dynamic Workflows 时，本质都在讲一件事：一个 Agent 不够用了。Agent Teams 则更进一步，它不是简单派子任务，也不是后台跑多个会话，而是让多个 Claude Code 会话组成一个“团队”，有负责人、有队友、有任务列表、有消息通信。

Agent Teams 是什么

Agent Teams 是 Claude Code 的实验性多 Agent 协作能力。

它的核心不是“多开几个 Claude”，而是让多个 Claude Code 会话拥有团队协作结构。

一个团队里通常有：

角色 / 组件 作用
Team lead 团队负责人，也就是主 Claude Code 会话
Teammates 队友，独立 Claude Code 会话
Shared task list 共享任务列表，记录任务、状态、依赖
Mailbox 消息系统，让队友之间可以通信
Plan approval 计划审批，高风险任务先提方案再执行

可以用一个图理解：

┌──────────────────────────────────────────┐
│              Team Lead                    │
│  拆任务 / 建团队 / 分配任务 / 汇总结果       │
└───────────────┬──────────────────────────┘
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
┌──────────┐ ┌──────────┐ ┌──────────┐
│ frontend │ │ backend  │ │ tester   │
│ teammate │ │ teammate │ │ teammate │
└────┬─────┘ └────┬─────┘ └────┬─────┘
     │            │            │
     └────────────┼────────────┘
                  ▼
        ┌──────────────────┐
        │ Shared Task List │
        │ + Mailbox        │
        └──────────────────┘

一句话：

Agent Teams 是 Claude Code 的多会话团队协作模式。

它和 Subagents、Agent View、Dynamic Workflows 的区别

Claude Code 现在的多 Agent 能力越来越多，很容易混。

先放一张表：

能力 谁在协调 Agent 之间能否直接通信 适合场景
Subagents 主会话 不能，通常只返回结果给主会话 快速研究、隔离上下文
Agent View / Background Agents 用户 不能直接协作，主要是独立后台任务 多个独立任务并行跑
Agent Teams Team lead + shared task list 可以，通过 mailbox 通信 需要讨论、分工、协作的复杂任务
Dynamic Workflows JavaScript workflow 由脚本编排，偏自动化 大规模子任务、可重复编排

我的理解是：

  • Subagents：临时派人查一件事；
  • Agent View：开多个后台工单；
  • Agent Teams：组一个项目小队；
  • Dynamic Workflows：写一套自动化流水线来批量调度。

Agent Teams 的独特性在于：队友之间可以协作，而不是只向主会话汇报。

为什么需要 Agent Teams

单 Agent 最大的问题是上下文和注意力都有限。

Subagent 能解决一部分问题，但它更像“外包一个子任务”。如果任务需要多个角色持续协作，Subagent 就不太够。

比如做一个完整功能：

  • 前端要改页面；
  • 后端要加接口；
  • 测试要补用例；
  • Reviewer 要检查 API 兼容性；
  • 文档要同步更新。

用单 Agent 做，它会不断切换上下文。

用 Subagents 做，它们各做各的，协作不够自然。

用 Agent View 做，你可以手动开多个后台任务，但协调成本在你身上。

Agent Teams 的目标就是：把“协调”也交给 Agent 体系处理。

Team lead：团队负责人

Team lead 是主 Claude Code 会话。

它负责：

  • 创建团队；
  • 生成 teammates；
  • 拆分任务；
  • 给队友分配任务；
  • 审批计划；
  • 汇总结果；
  • 和用户沟通。

你可以把它理解成 AI 项目经理。

但这里要注意：Team lead 不是甩手掌柜。

它仍然需要你给出清晰目标，比如：

Create a team with three teammates named frontend, backend, and tester.
Frontend handles UI changes, backend handles API changes, tester writes and runs tests.
Wait for teammates to finish before summarizing.

这种 prompt 比“帮我组个队做一下”可靠得多。

Teammates：独立 Claude Code 会话

每个 teammate 都是一个独立 Claude Code 会话。

它们有自己的：

  • 上下文窗口；
  • 任务提示；
  • 工具调用历史；
  • 权限环境；
  • 可以加载项目 CLAUDE.md、Skills、MCP；
  • 可以和 lead 或其他 teammate 通信。

这和 Subagent 有点像，但更完整。

Teammate 不继承 lead 的完整历史，所以创建它时要给足上下文。

不好的创建方式：

Spawn a teammate to handle frontend.

更好的方式：

Spawn a teammate named frontend. Its job is to update the dashboard filter UI.
It should only modify files under src/pages/dashboard and src/components/filter.
It must coordinate with backend before changing request parameters.

重点是：队友不是读心术，它需要明确的任务边界。

Shared Task List：共享任务列表

Agent Teams 里很重要的一点是共享任务列表。

任务通常有这些状态：

状态 含义
pending 待处理
in progress 正在处理
completed 已完成
blocked 被依赖阻塞或等待信息

任务还可以有依赖关系。

比如：

1. backend 定义接口返回结构
2. frontend 根据接口结构改 UI
3. tester 根据前后端结果补测试
4. reviewer 最后检查整体兼容性

这里第 2 步依赖第 1 步，第 3 步依赖第 1、2 步。

如果没有共享任务列表，多个 Agent 很容易各干各的。

有了任务列表，团队协作更像真实项目管理。

Mailbox：Agent 之间的通信机制

Agent Teams 另一个关键点是 mailbox。

Teammates 不只是向 lead 汇报，还可以互相发消息。

比如：

frontend -> backend:
我需要确认 /api/dashboard/filter 是否支持 dateRange 参数？

backend -> frontend:
支持，但字段名是 startDate 和 endDate，不是 dateRange。

tester -> frontend/backend:
我会基于 startDate/endDate 写集成测试，请保持字段稳定。

这就是 Agent Teams 和普通后台多任务最大的区别。

后台多任务像几个独立工单。

Agent Teams 像一个有沟通机制的小团队。

Plan approval：先计划，再执行

Agent Teams 适合复杂任务，但复杂任务也更容易误操作。

所以官方文档里提到一个很实用的模式：Plan approval。

也就是让 teammate 先提出计划，lead 审批后再做。

例如你可以要求：

Before editing files, each teammate must propose a plan.
The lead should approve only if the plan includes affected files, test strategy, and rollback risk.

这对高风险任务很有用：

  • 数据库迁移；
  • 鉴权模块修改；
  • 公共 API 改造；
  • 大规模重构；
  • 涉及生产部署的改动。

我的建议是：只要任务可能影响稳定性，就让 teammate 先 plan。

显示模式：in-process 和 split panes

Agent Teams 有两种常见显示方式。

in-process 模式

所有 teammates 都在主终端里显示。

特点：

  • 不需要额外工具；
  • 适合大多数终端；
  • 通过快捷键在 lead 和 teammates 之间切换；
  • 更稳定、更通用。

适合：第一次尝试 Agent Teams。

split panes 模式

每个 teammate 显示在独立 pane 中。

通常依赖：

  • tmux；
  • 或 iTerm2 的相关能力。

优点是可以同时看多个队友输出。

缺点是配置和终端兼容性更复杂。

我的建议是：先用 in-process，等你真的需要同时观察多个 Agent 时，再考虑 split panes。

怎么启用 Agent Teams

官方文档里说 Agent Teams 是实验性能力，默认关闭。

通常需要设置环境变量，例如：

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}

可以放到 settings.json 里，也可以用 shell 环境变量启动。

因为它是实验性功能，所以我建议只在：

  • 非关键分支；
  • 可回滚工作区；
  • 权限较保守；
  • 有 Git 状态保护；
  • 最好启用 worktree 隔离；

这些条件下尝试。

不要一上来就让 Agent Teams 在生产仓库里大改。

一个典型使用方式

假设我要实现一个“用户导出报表”功能。

可以这样提示：

Create an agent team with four teammates:

1. backend: implement the export API and data query.
2. frontend: add the export button and loading state.
3. tester: write unit and integration tests.
4. reviewer: review API compatibility, security, and edge cases.

Rules:
- Each teammate must propose a plan before editing.
- Backend and frontend must coordinate on the response format before coding.
- Tester should wait until backend and frontend finish their first pass.
- Reviewer should not edit files, only report issues.
- Lead should summarize final changes and unresolved risks.

这个 prompt 里有几个关键点：

  1. 明确队友名字；
  2. 明确每个人职责；
  3. 明确协作依赖；
  4. 明确谁能改文件、谁不能改；
  5. 明确 lead 最后要汇总。

这才是 Agent Teams 应该使用的方式。

适合哪些场景

场景一：跨前后端功能开发

例如：

  • backend 写接口；
  • frontend 接接口；
  • tester 补测试；
  • reviewer 审查协议和安全性。

这类任务天然适合团队分工。

场景二：复杂 Bug 的多假设调查

比如一个线上问题，有多个可能根因：

  • 最近提交；
  • 数据问题；
  • 缓存问题；
  • 并发问题；
  • 第三方服务问题。

可以让不同 teammate 分别调查，再互相挑战结论。

这比单 Agent 抱着第一个假设越挖越深更可靠。

场景三：架构评审

可以让不同 teammate 从不同角度审查：

  • 性能；
  • 安全；
  • 可维护性；
  • 可观测性；
  • 迁移成本。

最后由 lead 汇总冲突观点和共识。

这种多视角评审，是 Agent Teams 的强项。

场景四：大模块重构

如果一个模块可以切成多个相对独立部分：

  • 类型定义；
  • 数据层；
  • UI 层；
  • 测试层；
  • 文档层。

Agent Teams 可以让不同 teammate 并行推进。

但前提是边界清晰，否则很容易互相踩文件。

不适合哪些场景

Agent Teams 很酷，但不适合所有任务。

场景 原因
简单单文件修改 协调成本超过收益
强顺序任务 并行价值低
多人同时改同一文件 冲突严重
需求不清楚 多 Agent 会把模糊目标放大
token 预算紧 多会话成本高
高权限无人看守任务 风险大

我的判断标准是：

如果这个任务交给真人团队也需要分工沟通，那才适合 Agent Teams。

如果真人一个人 10 分钟能搞定，就别上团队。

和 Agent View 怎么选

Agent Teams 和 Agent View 都是多会话，但使用方式不一样。

维度 Agent View Agent Teams
关系 多个独立后台任务 一个协作团队
协调者 用户 Team lead + 任务列表
通信 用户分别接管 Teammates 可互相通信
适合 多个互不相关任务 一个复杂任务拆给多人协作
复杂度 中等 更高
成本 中等到高 更高

比如：

  • 同时审 5 个 PR → Agent View；
  • 实现一个跨前后端功能 → Agent Teams；
  • 大规模自动审计 500 个文件 → Dynamic Workflows；
  • 查一个模块怎么工作 → Subagent。

这就是我的选择逻辑。

和 Dynamic Workflows 怎么选

Dynamic Workflows 更像“自动化流水线”，Agent Teams 更像“协作团队”。

维度 Agent Teams Dynamic Workflows
编排方式 lead + task list + mailbox JavaScript workflow
互动性 更强，可以讨论、审批、调整 更自动化，偏批处理
适合规模 少量长期 teammate 数十到数百 subagents
中间状态 任务列表和会话上下文 脚本变量
复用方式 团队协作模式 保存 workflow 命令
典型任务 功能开发、架构评审、复杂调试 大规模扫描、迁移、研究、排序

我的理解是：

  • 需要“协作讨论” → Agent Teams；
  • 需要“大规模自动化编排” → Dynamic Workflows。

任务拆分要怎么写

Agent Teams 的效果，很大程度取决于你怎么拆任务。

不好的拆法：

Spawn 5 agents to improve this project.

这基本等于让 5 个人同时在屋里乱翻。

好的拆法要满足四个条件：

条件 说明
目标明确 每个 teammate 知道自己要产出什么
边界清晰 每个 teammate 知道能改哪些文件
依赖明确 谁要等谁，谁先确认接口
验收明确 什么叫完成，谁来 review

示例：

backend teammate:
- Only modify src/api/export and src/services/report.
- Produce an API contract before coding.
- Do not change existing public response fields.

frontend teammate:
- Wait for backend API contract.
- Only modify dashboard export UI.
- Do not introduce new UI library.

reviewer teammate:
- Read-only.
- Check security, compatibility, and test coverage.

这就比“你们分头做”可靠很多。

权限和安全要特别注意

Agent Teams 的风险比单 Agent 高。

原因很简单：

  • 会话更多；
  • 工具调用更多；
  • 并行操作更多；
  • 可能有多个 Agent 同时修改代码；
  • 权限请求可能冒泡到 lead；
  • 用户更容易看漏。

所以建议：

  1. 不要默认 bypassPermissions；
  2. 高风险 teammate 先用 plan；
  3. Reviewer 尽量只读；
  4. 不同 teammate 限制不同目录；
  5. 用 Git / worktree 保留回滚点；
  6. 对外部输入保持隔离；
  7. 关键修改最终由人审查。

尤其是 reviewer，我建议配置成只读。

它的职责是发现问题，不是顺手改问题。

一个推荐的 Agent Teams 工作模板

如果你想稳定使用 Agent Teams，可以套这个结构：

Create an agent team for this task.

Goal:
<明确最终目标>

Teammates:
1. <name>: <职责>，可修改 <路径>，不可做 <限制>
2. <name>: <职责>，可修改 <路径>，不可做 <限制>
3. reviewer: read-only，负责检查 <标准>

Coordination rules:
- Each teammate must propose a plan before editing.
- Teammates must communicate through mailbox when their work depends on another teammate.
- Avoid editing the same file from multiple teammates.
- The lead must wait for all teammates before final summary.

Acceptance criteria:
- Tests affected by the change pass.
- No public API breaking changes unless explicitly approved.
- Final summary includes changed files, risks, and follow-up tasks.

这个模板的核心是：目标、角色、边界、协作规则、验收标准。

少任何一项，团队协作质量都会下降。

使用时最容易踩的坑

坑一：队友上下文不够

Teammate 不继承 lead 的完整对话历史。

所以不能假设它知道所有背景。

解决方式：创建 teammate 时把任务背景、文件范围、约束条件写进去。

坑二：任务拆太碎

拆太碎会导致沟通成本暴涨。

比如 10 个 teammate 每人改一个小函数，最后协调成本可能比收益还高。

我的建议是：第一次从 3 个 teammate 开始。

坑三：多人改同一文件

这是多 Agent 协作最常见的问题。

解决方式：

  • 按目录拆；
  • 按模块拆；
  • 明确“谁拥有哪个文件”；
  • 公共文件由 lead 或指定 teammate 修改。

坑四：lead 自己冲去写代码

有时候 lead 会创建 teammates 后，自己也开始实现，导致它没等队友结果。

可以明确写：

The lead should wait for teammates to complete their assigned tasks before making final changes.

坑五：没有验收标准

没有验收标准时，多个 Agent 很容易都说“完成了”。

必须写清：

  • 哪些测试要过；
  • 哪些文件要改；
  • 哪些行为不能变；
  • 最终输出什么；
  • 谁负责 review。

我的判断

我认为 Agent Teams 代表的是 AI Coding 的另一个方向：不是让单个 Agent 变得无限强，而是让多个 Agent 形成协作结构。

这和真实工程组织很像。

一个优秀团队不是每个人都全能，而是：

  • 有人负责前端；
  • 有人负责后端；
  • 有人负责测试；
  • 有人负责 Review；
  • 有人负责协调和验收。

Agent Teams 把这套组织方式搬进了 Claude Code。

但我不认为它会替代普通 Claude Code。

更合理的使用层级是：

小任务：普通 Claude Code
中等研究：Subagent
多个独立任务：Agent View / Background Agents
复杂协作任务：Agent Teams
大规模批处理：Dynamic Workflows

这几个能力不是互相替代，而是不同复杂度下的工具箱。

小结

  1. Agent Teams 是 Claude Code 的实验性多会话协作能力，由 team lead、teammates、shared task list 和 mailbox 组成。
  2. 它和 Subagents 的区别是：Subagents 主要向主会话汇报，Agent Teams 中的 teammates 可以互相通信和协作。
  3. 它和 Agent View 的区别是：Agent View 管多个独立后台任务，Agent Teams 处理一个复杂任务里的团队协作。
  4. 它最适合跨模块功能开发、复杂 Bug 调查、架构评审和多角色协作任务。
  5. 使用 Agent Teams 的关键不是“多开几个 Agent”，而是写清目标、角色、边界、依赖和验收标准。
  6. 我的建议是先从 3 个 teammate 开始，权限保守、边界清晰、最终由人审查。
