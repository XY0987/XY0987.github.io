前端安全：XSS、CSP 与依赖投毒

发表于2026|更新于2026|工程化
|字数总计:2.6k|阅读时长:8分钟

前言：上一篇讲依赖层面的供应链安全。这一篇讲运行时的前端安全——最常见、危害最大的 XSS，用 CSP 做纵深防御，以及从工程角度怎么防依赖投毒。前端安全的话题很大，这篇聚焦工程化能落地的部分：不是讲「安全理论」，而是讲「工程上怎么把这些风险自动化地防住、扫出来」。

XSS：前端安全的头号敌人

XSS（跨站脚本攻击）是前端最常见、危害最大的漏洞。本质一句话：攻击者让你的页面执行了他注入的脚本。一旦得逞，攻击者能以用户身份做任何事——偷 Cookie/Token、冒充用户操作、篡改页面、钓鱼。

XSS 的根源永远是同一个：把「不可信的数据」当成「可信的代码/HTML」来处理了。三种常见类型：

类型 注入点 例子
存储型 数据存到后端，再渲染给所有人 评论区插入 <script>，所有看评论的人中招
反射型 URL 参数直接反射到页面 ?q=<script>...，页面把 q 渲染出来
DOM 型 前端 JS 直接把数据写进 DOM innerHTML = location.hash

现代框架帮你挡住了大部分

好消息：React/Vue 这类现代框架默认对插值做转义，帮你挡住了绝大多数 XSS。你写 <div>{userInput}</div>，即使 userInput 是 <script>，框架也会把它转义成纯文本显示，而不是当代码执行。

坏消息：框架的「后门」会绕过这个保护。危险的是这些「我要直接插 HTML」的 API：

React：  dangerouslySetInnerHTML   （名字里 dangerously 就是警告你）
Vue：    v-html
原生：    element.innerHTML = ...

一旦用这些把用户可控的数据直接当 HTML 插入，XSS 大门就打开了：

// ❌ 致命：把用户输入直接当 HTML，userComment 里的 <script> 会执行
<div dangerouslySetInnerHTML={{ __html: userComment }} />

工程上怎么防

  1. **默认信任框架的转义，别乱用 dangerouslySetInnerHTML/v-html**。绝大多数需求用普通插值就够了。
  2. 确实要渲染富文本 HTML 时，先用 DOMPurify 消毒：
import DOMPurify from 'dompurify'
// ✅ 先净化，剥掉 <script>、onerror 等危险内容，再插入
<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(userComment) }} />
  1. 用 ESLint 规则自动拦截：这是工程化的关键——别指望 code review 时人肉发现每一处 v-html。用 lint 规则（如 eslint-plugin-vue 的 vue/no-v-html、React 相关规则）把这些危险 API 的使用在 CI 里标记出来，强制作者说明理由或消毒。
把「危险 API 的使用」变成 lint 告警 → 每次用都被看见 → 不会静悄悄埋雷

这就是前端安全工程化的思路：把安全规则变成自动化检查，而不是靠人记得。呼应《ESLint 原理与 Flat Config》——安全类 lint 规则是 ESLint 很重要的一类用途。

CSP：纵深防御的兜底

即使你代码写得再小心，也难保证零 XSS（比如某个第三方依赖有漏洞）。CSP（Content Security Policy，内容安全策略）是浏览器层面的兜底防御——它通过 HTTP 响应头告诉浏览器「只允许执行/加载来自这些来源的资源」，即使有脚本被注入，不符合策略的也不会执行。

CSP 是一个响应头：

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.trusted.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;

它也可以写在 HTML 的 meta 标签里：

<meta
  http-equiv="Content-Security-Policy"
  content="default-src 'self'; script-src 'self' https://cdn.trusted.com"
/>

但我的建议是：生产环境优先用 HTTP 响应头。

原因很简单：HTTP 响应头在浏览器解析 HTML 之前就已经生效，控制力更强；meta 要等浏览器解析到这行标签之后才生效，如果它出现得太晚，前面已经加载过的资源就不一定受它约束。并且 meta 方式不能使用 Content-Security-Policy-Report-Only 做观察模式，像 frame-ancestors 这类策略也不支持。

所以可以这样理解：meta 更适合静态页面、没有服务端配置权限时的兜底方案；只要能控制服务端、网关或 CDN，CSP 就应该优先配在 HTTP 响应头里。

含义：脚本只能来自本站和指定 CDN，其他来源（包括被注入的内联 <script>）一律不执行。这样即使攻击者成功注入了 <script src="evil.com/x.js">，浏览器也会因为 evil.com 不在 script-src 白名单里而拒绝执行。CSP 不能替代前面的转义/消毒，它是「万一前面漏了」的第二道墙——这就是「纵深防御」。

CSP 落地的两个工程要点：

1. 先用 Report-Only 模式观察，别直接强上。CSP 配严了会把正常资源也拦掉（页面直接崩）。用 Content-Security-Policy-Report-Only 头先「只报告不拦截」，收集一段时间「哪些资源会被拦」的报告，调整策略到不误伤，再切成强制模式。

违规上报的写法要注意新旧差异。老写法用 report-uri：

Content-Security-Policy-Report-Only: ...; report-uri /api/csp-report
# 老写法，仍被广泛支持，但已被标记为废弃

现代浏览器推荐用 Reporting API 的 report-to，配合 Reporting-Endpoints 响应头声明上报端点：

Reporting-Endpoints: csp-endpoint="/api/csp-report"
Content-Security-Policy-Report-Only: ...; report-to csp-endpoint

实践上，因为部分浏览器对 report-to 支持进度不一，过渡期常见做法是 report-uri 和 report-to 两个都写，让浏览器各取所需。

**2. 警惕 'unsafe-inline' 和 'unsafe-eval'**。这两个值会大幅削弱 CSP（允许内联脚本/eval，正是 XSS 爱用的）。理想是不用它们，但很多老项目、内联样式会依赖 'unsafe-inline'。这是个「安全性 vs 改造成本」的权衡——至少 script-src 要尽量避免 unsafe-inline（用 nonce/hash 替代），style-src 的 unsafe-inline 危害相对小。

3. 进阶：用 Trusted Types 从源头堵住 DOM 型 XSS。CSP 的 require-trusted-types-for 'script' 指令（Chromium 系支持）能强制所有写入 innerHTML、script.src 等「危险 sink」的值必须先经过一个可信策略处理，否则直接抛错。它把「防 DOM XSS」从「靠人记得消毒」变成「浏览器强制拦截」，是 2024 年后大型应用值得投入的前沿实践：

Content-Security-Policy: require-trusted-types-for 'script'; trusted-types default dompurify

依赖投毒：供应链的运行时威胁

上一篇讲了依赖漏洞和 license，这里讲更主动的攻击——依赖投毒（supply chain poisoning）：攻击者往你会安装的包里植入恶意代码。手法有几种：

① 劫持已有包    攻击者拿到某流行包的发布权限，发一个带恶意代码的版本
② 抢注/仿冒    注册和流行包名字很像的包（typosquatting），骗你装错
③ 恶意新版本    你信任的包，某个新版本被植入恶意代码
④ 依赖混淆      利用私有包名，让你误装公网的同名恶意包

event-stream、ua-parser-js、node-ipc 都发生过真实的投毒事件，恶意代码在 npm install 时（安装脚本）或运行时窃取信息、破坏系统。

工程上怎么防（很多和上一篇的依赖治理相通）：

  1. lockfile + integrity 校验：lockfile 锁定了每个包的完整性哈希，能防止「同一版本号但内容被换掉」。始终提交 lockfile、CI 用 --frozen-lockfile。
  2. 禁用/审查安装脚本：很多投毒通过 postinstall 等安装脚本触发。pnpm、npm 较新版本默认不自动跑依赖的构建脚本，需要显式允许——这是个很好的默认。谨慎对待要求跑安装脚本的依赖。
  3. 锁定版本、延迟升级：别盲目追最新版本。投毒的恶意版本发布后，通常几小时到几天内被发现下架。稍微「让子弹飞一会」（不立刻升到刚发布的版本）能躲掉一部分。Renovate 可以配置「版本发布后等 N 天才升」（minimumReleaseAge 之类）。
  4. 警惕包名：安装依赖时看清楚包名，别被仿冒名（typosquatting）骗了。
  5. CI 里跑依赖安全扫描（上一篇的 audit + 专门的供应链扫描工具如 socket.dev 一类，能检测可疑行为）。

其他几个常见前端安全点

除了 XSS/CSP/投毒，工程上还该知道几个（简要提及，够形成安全意识）：

  • CSRF：跨站请求伪造。防御主要在后端（token、SameSite Cookie），前端配合。
  • 敏感信息不进前端：呼应环境矩阵篇——密钥、token 绝不硬编码进前端代码，前端能拿到的一切用户都能拿到。
  • 依赖 CDN 加 SRI：从第三方 CDN 引资源时加 integrity（子资源完整性）哈希，CDN 上的文件被篡改就拒绝加载。
  • 点击劫持：用 X-Frame-Options / CSP 的 frame-ancestors 防止你的页面被恶意站点用 iframe 套壳。

这些不用每个都深挖，关键是有安全意识 + 把能自动化的（lint、CSP、audit、SRI）配置成默认防线。

小结

  1. XSS 本质是「把不可信数据当可信代码/HTML 处理」，得逞后攻击者能以用户身份为所欲为。
  2. React/Vue 默认转义挡住大部分 XSS，但 dangerouslySetInnerHTML/v-html/innerHTML 会绕过保护，插入用户可控数据时必用 DOMPurify 消毒。
  3. 用 ESLint 规则把危险 API 的使用自动标记出来，别靠人肉 review——安全要工程化成自动检查。
  4. CSP 是浏览器层的纵深防御兜底，用白名单限制资源来源；先用 Report-Only 观察再强制，警惕 unsafe-inline/unsafe-eval。
  5. 依赖投毒通过劫持/仿冒/恶意版本/安装脚本植入恶意代码，靠 lockfile+integrity、审查安装脚本、延迟升级、看清包名、CI 扫描来防。
  6. 其他要点：CSRF（后端为主）、敏感信息不进前端、第三方 CDN 加 SRI、防点击劫持。
  7. 前端安全工程化的核心思路：有安全意识，把能自动化的防线（lint/CSP/audit/SRI）配成默认，别依赖个人记性。
