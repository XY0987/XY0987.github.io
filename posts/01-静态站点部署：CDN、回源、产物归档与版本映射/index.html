静态站点部署：CDN、回源、产物归档与版本映射

发表于2026|更新于2026|工程化
|字数总计:2.3k|阅读时长:7分钟

前言：前面把测试、CI、自动发布都串起来了，产物（dist/）能自动构建出来。但「构建出来」和「用户能访问到、访问得对、能回滚」是两回事。这一篇讲前端最主流的部署形态——静态站点部署。它看着简单（不就是把 dist 传上去嘛），但真正做对涉及 CDN 缓存策略、HTML 回源、产物归档、版本映射一整套东西。做错了，轻则用户加载到新旧混杂的资源白屏，重则想回滚却回不去。

静态部署的本质：分离 HTML 和带 hash 的资源

现代前端构建产物长这样：

dist/
├── index.html                      ← 入口，引用下面的资源
├── assets/
│   ├── index.a1b2c3d4.js           ← 文件名带内容 hash
│   ├── vendor.e5f6a7b8.js
│   └── index.9c8d7e6f.css

注意 JS/CSS 文件名里带一串 hash（a1b2c3d4），这是构建工具（Vite/Webpack）根据文件内容算出来的。内容变了 hash 就变，文件名就变。这个设计是整个部署缓存策略的地基，因为它把产物分成了两类，缓存策略截然相反：

产物类型 文件名 缓存策略
带 hash 的资源（JS/CSS/图片） 内容变则文件名变 强缓存，永久缓存（immutable）
HTML 入口 名字固定（index.html） 不缓存 / 协商缓存，每次校验

理解这个分离是理解一切的前提：

  • 带 hash 的资源可以永久强缓存，因为「同一个文件名 = 同一份内容」永远成立。内容变了必然是新文件名，不存在「文件名一样但内容变了」的情况，所以浏览器/CDN 尽管永久缓存，不会缓存到旧内容。
  • HTML 绝不能强缓存。因为它的名字是固定的 index.html，而它的内容（引用哪些 hash 资源）每次发布都在变。如果 HTML 被强缓存，用户就会拿着旧 HTML 去引用已经不存在的旧 hash 资源，直接白屏。

缓存头怎么配

具体到 HTTP 响应头，两类产物这么配：

# 带 hash 的静态资源，比如 app.a8f3c1.js、style.92ab10.css
# 文件名里有内容 hash，内容一变文件名也会变，所以可以放心长时间强缓存
# public 表示浏览器和 CDN 都可以缓存；max-age=31536000 表示缓存一年
# immutable 表示这个 URL 对应的内容不会再变，缓存期内不用再发请求校验
Cache-Control: public, max-age=31536000, immutable

# HTML 入口：不用强缓存，每次回源校验
Cache-Control: no-cache
# no-cache 不是「不缓存」，是「每次都要向服务器校验新鲜度」（配合 ETag）

no-cache 是个特别容易误解的词。它不等于「不缓存」（那是 no-store）。no-cache 的意思是「可以缓存，但每次用之前必须找服务器确认没过期」——配合 ETag，内容没变服务器返回 304，省了传输但保证了新鲜。HTML 用 no-cache 正合适：既避免拿到旧 HTML，又不用每次都全量下载。

一个真实的坑：HTML 也配了长 max-age。表现是发布后部分用户长时间还是旧页面，甚至白屏（旧 HTML 引用的 hash 资源已被清理）。原因就是 HTML 被 CDN/浏览器强缓存了。解决就是把 HTML 的缓存头改成 no-cache，并且清一次 CDN 上 HTML 的缓存。

CDN 与回源策略

静态站点标准架构是 对象存储 + CDN：

用户 ──► CDN 边缘节点 ──(未命中/需校验)──► 源站（对象存储 / Nginx）
         （缓存资源）                      （产物真正存放的地方）
  • CDN：分布在各地的边缘缓存节点，用户就近取资源，快。带 hash 的资源缓存在这一层，命中率极高。
  • 回源（origin fetch）：CDN 上没有或需要校验时，回到源站取。HTML 因为 no-cache，基本每次都要回源校验一次新鲜度。

这里有个 SPA 特有的问题——HTML 回源与前端路由。单页应用的路由（/user/123、/about）在服务端并不存在对应的物理文件，刷新这些地址会 404。解决方案是配置回源规则：找不到对应文件时，一律回源到 index.html，交给前端路由处理。

# Nginx 的 SPA 回源（history 路由的经典配置）
location / {
    try_files $uri $uri/ /index.html;
    # 找不到文件就返回 index.html，让前端路由接管
}

对象存储（如 S3、OSS、COS）通常在「静态网站托管」设置里有类似的「错误页/回退页指向 index.html」选项，作用一样。

产物归档与版本映射

这是「部署做得专业不专业」的分水岭。很多团队的部署是覆盖式的——新产物直接覆盖旧产物。这样做有个致命问题：想回滚时，旧产物已经没了。

正确做法是按版本归档，不覆盖。产物按版本号/构建号放进不同目录：

对象存储：
releases/
├── v1.2.0/          ← 每次发布是一个独立、不可变的目录
│   ├── index.html
│   └── assets/...
├── v1.2.1/
├── v1.3.0/          ← 当前线上指向这个

然后维护一份版本映射，记录「当前线上服务的是哪个版本」：

current → v1.3.0

「切换线上版本」这个动作，就变成了改一下这个映射指针——把 current 从 v1.3.0 指到别的版本，而不是重新上传文件。这带来几个巨大的好处：

  1. 回滚是秒级的：出问题，把指针从 v1.3.0 切回 v1.2.1 即可，旧产物还在，不用重新构建部署。
  2. 发布和生效解耦：可以先把 v1.3.0 传好（用户还访问 v1.2.1），验证没问题再切指针。上传和「生效」是两步。
  3. 方便灰度：不同用户、不同地域、不同流量比例可以指向不同版本，新版本先吃一小部分流量，稳定后再切全量。
  4. 可追溯：每个版本的产物都留档，线上出问题能精确定位「是哪个版本引入的」，甚至能把不同版本产物 diff 出来。

版本号最好和 git commit / tag 映射上（v1.3.0 → commit abc1234），这样从线上版本能直接追回源码。这和后面监控篇讲的 Source Map 版本对应也是同一套逻辑。

灰度发布：让新版本先给一部分人

有了版本归档和映射，就能做灰度（金丝雀）发布——新版本先放给一小部分用户，观察没问题再全量。

思路是在 CDN/网关层按规则分流：

                    ┌── 5% 流量 ──► v1.3.0（新，观察中）
用户请求 ──► 分流 ──┤
                    └── 95% 流量 ─► v1.2.1（旧，稳定）

分流规则可以按比例、按用户特征（内部员工先灰度）、按地域等。核心是：新版本的问题只影响一小撮人，且能立刻切回。观察一段时间（看监控指标——错误率、性能，见监控篇），健康就逐步放大比例到 100%，异常就秒切回旧版本。

灰度的工程前提正是前面那套：版本归档（多版本产物共存）+ 版本映射（可控制流量指向）。没有这两样，灰度无从谈起。具体分流能力取决于你的 CDN/网关（很多云厂商 CDN、EdgeOne、以及自建 Nginx + Lua 都支持）。

一条完整的部署流程

把上面的串起来，一条专业的静态部署 CI 流程是这样：

1. 构建产物（带 hash），标记版本号（= git tag / commit）
2. 上传到 releases/<version>/（归档，不覆盖）
3. 设置正确的缓存头（资源 immutable / HTML no-cache）
4. 切换版本映射指针 current → <version>（或先灰度一部分）
5. 刷新 CDN 上 HTML 的缓存（让 no-cache 立即生效）
6. 记录版本映射：<version> → commit → 部署时间 → 操作人

第 5 步「刷新 CDN 缓存」容易漏。HTML 是 no-cache（校验型），但如果 CDN 边缘还缓着旧的 304 逻辑或旧内容，切了指针用户也不一定马上拿到新 HTML。发布后主动 purge 一次 HTML 的 CDN 缓存，是让新版本即时生效的保险。带 hash 的资源不用 purge（本来就是新文件名）。

小结

  1. 静态产物分两类：带 hash 的资源（内容变则名变）和固定名的 HTML，缓存策略相反。
  2. 带 hash 资源永久强缓存（immutable），HTML 用 no-cache（每次校验，不是不缓存）；HTML 被强缓存是发布后白屏的常见原因。
  3. 架构是对象存储 + CDN，SPA 要配「找不到文件回源到 index.html」的回退规则处理前端路由。
  4. 产物按版本归档、不覆盖，维护「当前线上是哪个版本」的映射指针。
  5. 切版本 = 改指针，让回滚变成秒级、让发布和生效解耦、让每个版本可追溯。
  6. 版本归档 + 版本映射是灰度发布的前提：新版本先给一小部分流量，健康则放大、异常则秒切回。
  7. 发布后主动 purge CDN 上的 HTML 缓存，让新版本即时生效；带 hash 的资源无需 purge。
