Harness 的新思考：模型变强之后，缰绳该松哪几根

发表于2026|更新于2026|AI相关
|字数总计:3.6k|阅读时长:11分钟

前言：之前写过一篇 Harness Engineering，核心比喻是”给 AI 这匹能力极强但没方向感的马装缰绳”。当时的隐含前提是——模型不够聪明，容易跑偏，所以缰绳要拉得紧、约束要写得细。但最近半年模型迭代太快，这个前提正在松动。这篇想接着那篇往下聊：模型变强之后，Harness 这套缰绳还需不需要拉这么紧？提示词、约束这些是不是该做减法？哪几根缰绳该松、哪几根反而要收紧？

触发我重新思考的两件事

先说清楚不是拍脑袋，是两件实打实的事让我重新审视 Harness 的”重”。

第一件：Anthropic 的 unhobbling

2026 年 7 月，Anthropic 升级到 Claude 5 系列（Opus 5 / Fable 5）时，把 Claude Code 的 System Prompt 砍掉了 80% 以上，编码评测分数却没掉（见官方博客 The new rules of context engineering for Claude 5 generation models）。他们把这个动作叫 unhobbling（解除束缚）：那些在旧模型上”防止它犯傻”的指令，到了更强的模型上，反而变成互相打架的噪声、白白消耗 token。

Anthropic 在 Effective context engineering 里还有一句很关键的话：

We’re already seeing that smarter models require less prescriptive engineering, allowing agents to operate with more autonomy.

翻译过来：模型越强，越不需要你手把手规定它怎么做。

第二件：Prompting Inversion

一篇 arxiv 论文 The Prompting Inversion 给了更硬的数据：同一套精雕细琢的提示词技巧，在 gpt-4o 上能把准确率从 93% 提到 97%，但在更强的 gpt-5 上反而从 96.36% 掉到 94%。作者把这个现象叫 “Guardrail-to-Handcuff”（护栏变手铐）——中等模型需要的约束，到了强模型身上就成了束缚，让它变得”过度死板”。

这两件事指向同一个判断：

缰绳不是越紧越好。Harness 的松紧和模型能力是此消彼长的关系——马变聪明了，有些缰绳就该松。

先把适用前提放前面：下面说的”松缰绳”，主要针对 Claude 5、GPT-5 这类强模型，以及上下文质量还不错的场景。如果你用的是本地中小模型，或者项目上下文本来就很乱，那些手把手的约束依然有价值，不用照着口号硬减。

但别急着把缰绳全松开

看到”less is more”，很容易滑向另一个极端：模型这么强了，那 Harness 是不是可以不要了？

我的答案是不是。因为 Harness 从来不是一根缰绳，而是——约束力、判断力、拆解力、集成力、兜底力。模型变强，对这五根的影响完全不同。真正有用的思考不是”要不要 Harness”，而是一根一根看：哪根该松、哪根不动、哪根反而要收紧。

判断的总原则就一条：

Harness 里”替模型补脑子”的部分（补能力），随模型变强而贬值；”防止长任务翻车”的部分（补可靠性），随模型变强而保值甚至升值。

下面按五大支柱逐个过。

支柱一：约束力——从”手把手”松到”给目标+边界”

这是该松最多的一根。

之前 Harness 时代，约束力讲究”事无巨细”：技术栈、架构分层、代码规范，恨不得每一步都替模型规定死。因为弱模型你不盯着它就乱来。

强模型时代，过度约束就是那副”手铐”。很多约束是在教模型它早就会的东西——命名要有意义、函数别太长、要处理错误……这些强模型内化得比你写的规范还好。你写进去，只是在稀释它的注意力预算。

Anthropic 给的经验值是：多数任务 System Prompt 的甜点区在 150–300 词（参考值，非硬上限），核心是找到 **”altitude（高度）”**——既不硬编脆弱的流程逻辑，也不空泛到没有信号。

放到实际约束上，减法这样做：

<!-- ❌ 旧写法：手把手，把模型早就会的也写进去 -->
## 编码约束
- 写代码前要先理解需求
- 变量命名要有意义、要用驼峰
- 函数要单一职责，不超过 50 行
- 要写错误处理，要 try/catch
- 提交前要自测
- 循环里不要发请求

<!-- ✅ 新写法：只留"这个项目特有、模型猜不到"的边界 -->
## 项目边界
- 网络请求只能用 StockBridge.request，禁止 fetch/axios
- 只能改 service 层，不许动 controller 路由
- 部署走内网，容器目录 /app/data 必须持久化

一条约束，如果换成一个没读过它的强模型也能自己想到，那它就是噪声，删掉。

留下来的，应该都是模型无论如何猜不到的东西：项目约定、架构边界、环境事实。至于”怎么写好代码”这种通用能力，无需再教了。

但注意：松的是”手把手的流程约束”，不是”边界约束”。安全区的红线（不许动哪些文件、不许用哪些库、数据不许外泄）一条都不能少——那不是补能力，是补可靠性。

支柱二：拆解力——甜蜜区上移，但别停

之前 Harness 强调把大任务切成”AI 能吃下的小块”。强模型时代，它的”嘴”变大了——能一口吃下的任务粒度明显上移了。

以前你得把”实现用户模块”拆成 Schema、注册接口、JWT 中间件、列表接口四五步喂给它；现在很多强模型能一次把一个完整模块做得七七八八。硬切太碎，反而增加你自己的编排负担，还打断了模型的整体设计。

但拆解力不能退休，只是重心变了：

  • 粒度上移：别再切成”函数级”任务，可以按”模块级/功能级”交付
  • **重心从”切小”转向”定边界”**：拆解的价值不再是”切到足够小让模型不跑偏”，而是”想清楚模块之间的接口契约和依赖关系”——这部分强模型依然看不到全局

一句话：**拆解从”体力活”变成了”架构活”**。切得多细不重要了，边界划得清不清楚才重要。

支柱三：判断力——不降反升，而且更难

这根缰绳不但不松，还要收紧。

我在之前 Harness 篇里说过一个数据感受：AI 产出里约 60% 是”能跑但有问题”的——最危险的一档，因为它能骗过简单测试。强模型时代这个问题不但没消失，反而更隐蔽了：

  • 强模型写的代码更像对的——风格更好、注释更全、结构更漂亮，”能跑但有坑”的伪装度更高
  • 强模型更自信——它不太会说”我不确定”，错误被包装得更笃定
  • 你的心理防线更松——用久了容易”AI 说啥信啥”，审计习惯反而退化

所以判断力的价值是随模型变强而升值的。这也解释了为什么我之前说”审查速度才是真正的瓶颈”——模型写得越快越好，人做工程判断这一环的相对权重就越高。

判断力松不得的原因很本质：它依赖的是对底层原理的理解，而这恰恰是模型代替不了你的地方。模型能告诉你”怎么做（HOW）”，但”这么做对不对、值不值（WHY）”还得你来拍。

支柱四：集成力——基本不动

模型再强，看到的仍然主要是”当前这段代码/这个文件”。真正的系统级集成——接口契约、错误在各层怎么传播、数据一致性、事务边界、可观测性埋点——依赖的是对整个系统的全局视角，这不是靠单次上下文能补齐的。

所以集成力这根缰绳基本不用调。它一直是人的活，将来也大概率是。唯一变化是：模型能帮你更快地把集成方案落成代码，但”集成方案本身怎么设计”还是你的判断。

支柱五：兜底力——从”补救”升级成”系统性防线”

这根缰绳要收紧，而且是最该投入的方向。

之前 Harness 篇里兜底力讲的是”AI 搞不定时你能手动补救”。强模型时代，兜底的内涵升级了——因为大家越来越敢把长任务、无人值守的任务交给 Agent（可以回看 Loop Engineering）。任务链越长，中间翻车、跑飞、不收口的概率就越大，而这跟模型多聪明关系不大。

所以兜底力要从”事后补救”前移成”系统性防线”：

  • 验证收口：每一步产出要有自动校验（跑测试、跑 lint、跑类型检查），别等人肉发现
  • 韧性机制：长任务要有重试预算、超时、崩溃可续跑，不能一步失败全盘皆输
  • 上下文治理：警惕 context rot（上下文腐烂）——Transformer 注意力是 n² 的，塞进去的 token 越多，注意力越稀释。记忆和历史要拼信噪比，不是拼量，过期信息要及时清

这里有个反直觉点：强模型的指令遵循更强，喂错信息的代价反而更大。弱模型你喂它一条过期约定，它可能自己纠偏；强模型会忠实地照着错的执行。所以”喂对、喂少、及时忘”本身就是兜底的一部分。

五大支柱：模型变强后的调整总览

把上面五根缰绳汇总成一张表：

支柱 老 Harness 时代 模型变强后 缰绳怎么调
约束力 事无巨细手把手 过度约束变手铐 松：只留边界，删通用规范
拆解力 切到足够小 甜蜜区上移 松：粒度上移，重心转向定边界
判断力 审查 AI 产出 错误更隐蔽、更自信 收紧：审计权重更高
集成力 人做系统集成 依然看不到全局 不动：始终是人的活
兜底力 事后手动补救 长任务翻车风险放大 收紧：前移成系统性防线

一句话记忆：

补能力的缰绳（约束、拆解）该松；补可靠性的缰绳（判断、兜底）该收紧；集成力不动。

关于提示词精简

你最关心的”提示词要不要精简”，答案是要，但要减对地方：

// 一个粗略的提示词"体检"思路：给每条约束打标签，只保留"补可靠性/项目特有"的
const rules = [
  { text: '函数要单一职责，不超过 50 行', tag: 'general-skill' },   // 删
  { text: '要写错误处理', tag: 'general-skill' },                    // 删
  { text: '网络请求只能用 StockBridge.request', tag: 'project-fact' }, // 留
  { text: '禁止修改 controller 路由结构', tag: 'safety-boundary' },  // 留
];

function prunePrompt(promptRules) {
  return promptRules.filter((rule) => {
    // general-skill = 教模型通用能力，强模型已内化 → 删
    if (rule.tag === 'general-skill') {
      return false;
    }

    // 项目事实 + 安全边界 → 留
    return true;
  });
}

console.log(prunePrompt(rules).map((rule) => rule.text));
// 输出：
// ['网络请求只能用 StockBridge.request', '禁止修改 controller 路由结构']

核心不是这段代码，而是那三个标签背后的心法：

  1. general-skill（通用能力）→ 删：强模型早会了，写了是噪声
  2. project-fact（项目事实）→ 留：模型猜不到，必须喂
  3. safety-boundary（安全边界）→ 留：这是兜底，一根不能少

Anthropic 的建议也是这个思路：先用最强的模型 + 最小提示跑一遍，看它在哪失败，再针对失败点补约束——而不是一上来就写 5000 字的 System Prompt。

一个容易走过头的地方：别把减法做成裸奔

“less is more”最容易被念歪成”啥都别写，全丢给模型”。泼盆冷水：

坑：以为模型够强就能无 Harness 裸奔
现象：约束、验证、兜底全砍了，让强模型自由发挥，结果长任务照样翻车。
原因：Prompting Inversion 那篇论文自己也强调——模型能力强 ≠ 一定可靠，验证机制不足时，再强的模型也会以微妙的方式失败。
解决：减法只减在”补能力”的缰绳上（约束、拆解），判断、兜底、安全边界一根都不能松。

反过来，如果你在用本地小模型（比如 Ollama 上的中小参数模型），那些”手把手”的约束依然有价值——小模型确实还需要被兜住。缰绳松到什么程度，取决于你手里模型的实际水位，不是看别人喊口号。

我的判断

  1. 约束力做减法：删掉教模型通用能力的规范，只留项目事实和安全边界
  2. 拆解力做减法：任务粒度上移到模块级，重心从”切小”转向”定接口边界”
  3. 判断力要收紧：模型写得越像对的，越要保持审计习惯，别退化成”AI 说啥信啥”
  4. 集成力不用动：系统级集成始终是人的活
  5. 兜底力要加码：验证收口、重试韧性、上下文治理，长任务时代这是重点投入方向
  6. 提示词精简的心法：先用最强模型 + 最小提示跑，按失败点补，别一上来堆长
  7. 减法别做成裸奔：安全和可靠性的缰绳一根不能松；小模型场景该紧还得紧

小结

  1. 模型变强后，Harness 的松紧和模型能力此消彼长，unhobbling（砍 80% 提示分数不降）和 Prompting Inversion（护栏变手铐）是两个硬证据
  2. 但 Harness 不是一根缰绳，是五根，模型变强对每根影响不同，不能一刀切
  3. 约束力、拆解力该松：过度约束变手铐，任务粒度可以上移
  4. 判断力、兜底力该收紧：强模型错误更隐蔽，长任务翻车风险更大
  5. 集成力不动：系统全局视角始终是人的护城河
  6. 一句话——补能力的缰绳该松，补可靠性的缰绳该收紧
  7. 减法要减对地方，别把”less is more”做成”无 Harness 裸奔”
