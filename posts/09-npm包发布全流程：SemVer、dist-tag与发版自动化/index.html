npm 包发布全流程：SemVer、dist-tag 与发版自动化

发表于2026|更新于2026|工程化
|字数总计:3.1k|阅读时长:11分钟

前言：这是「组件库与发布」阶段的最后一篇。前面把组件库从工程结构、构建、样式、设计系统、文档都讲完了，最后一步是发出去。发布看着简单（npm publish 一行），但里面藏着一堆坑：版本号怎么定、scoped 包为什么发不上去、beta 版怎么发才不污染正式版、多包 Monorepo 怎么自动发。Changesets 的基础用法在 Monorepo 那篇讲过，这一篇聚焦发布本身的机制——SemVer、权限作用域、dist-tag，以及把它们串成自动化流程。

SemVer：版本号不是随便写的

npm 包的版本号遵循 SemVer（语义化版本），格式是 主版本.次版本.修订号（MAJOR.MINOR.PATCH）。它不是三个随便递增的数字，每一位都有明确含义：

位置 什么时候加 例子
MAJOR 主版本 破坏性变更（不兼容旧版 API） 删了个 prop、改了默认行为
MINOR 次版本 新增功能（向下兼容） 加了个新组件、新 prop
PATCH 修订号 修 bug（向下兼容） 修了个样式错位

核心契约是：用户看版本号就能判断能不能安全升级。从 1.2.3 升到 1.2.4（patch）或 1.3.0（minor）应该无痛；升到 2.0.0（major）就要小心，可能有破坏性变更。

这也是为什么 package.json 里依赖前面的符号很重要：

{
  "dependencies": {
    "@my-ui/components": "^1.2.3"   // ^ 允许升 minor/patch，不升 major
  }
}

^1.2.3 表示「>=1.2.3 且 <2.0.0」——自动接受兼容更新，但不会跨 major。所以如果你发了破坏性变更却只升了 minor，用户会在毫不知情的情况下自动升上来然后炸掉。这是库作者最不该犯的错：破坏性变更必须升 major，别为了「看起来版本没跳太多」而少升。

预发布版本号

正式版之外，还有预发布版本，用连字符加标识：

1.0.0-beta.0      测试版
1.0.0-rc.1        候选发布版
2.0.0-alpha.3     内测版

预发布版本的排序规则：1.0.0-beta.0 < 1.0.0（预发布永远小于对应正式版）。^1.0.0 默认不会装到 1.0.0-beta.0，用户得显式要才行。这保证了发 beta 不会误伤用普通版本范围的用户。

npm 发布的权限与作用域

npm publish 发不上去，十有八九是权限或作用域问题。这块坑最多，逐个说清。

scoped 包默认是私有的

@my-ui/components 这种带 @scope/ 前缀的叫 scoped 包。它有个反直觉的默认行为：scoped 包首次发布默认是「私有」的，而私有包需要付费。

如果你想免费发一个公开的 scoped 包，必须显式声明 public：

npm publish --access public

或者在 package.json 里配好，省得每次记：

{
  "name": "@my-ui/components",
  "publishConfig": {
    "access": "public"
  }
}

新手最常见的报错就是 scoped 包发布时报 402（需要付费）或 403（无权限），根因往往就是没加 --access public。**发公开 scoped 包，一定配 publishConfig.access: public**。

登录与 token

本地发布要先登录：

npm login
npm whoami        # 确认当前登录的账号

CI 里没法交互登录，传统做法是用 npm token：在 npmjs.com 生成一个 Automation 类型的 token（能绕过 2FA，适合 CI），配到 CI 的 .npmrc：

//registry.npmjs.org/:_authToken=${NPM_TOKEN}

${NPM_TOKEN} 从 CI 的 secret 注入，别写死在文件里提交上去——token 泄露等于别人能以你的名义发包。长期 token 还应定期轮换。

优先考虑 Trusted Publishing（OIDC），别再长期挂 token。 npm 现在支持 GitHub Actions / GitLab CI 通过 OIDC 免密发布：在 npm 包设置里把某个 CI workflow 配置为「可信发布者」，CI 发布时用短期 OIDC 凭据换取发布权限，不需要任何长期 NPM_TOKEN。这是 2025 年后官方推荐的 CI 发布方式，从根本上消除了 token 泄露和轮换负担。新项目建议直接走 OIDC，token 只作为暂不支持 OIDC 时的备选。

组织与团队权限

scoped 包的 scope 通常对应一个 npm organization（@my-ui 是个组织）。谁能发布由组织的成员和团队权限控制。发布前确认你的账号在该组织有对应包的 write 权限，否则 403。

用 files 字段控制发什么

发布时别把源码、测试、配置全发上去，用户只要产物。用 files 字段白名单控制：

{
  "files": ["dist"],
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  },
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts"
}

现代库应以 exports 为权威入口——它同时决定入口选择和「哪些子路径能被 import」。main（老 Node / 不认 exports 的工具兜底）和 types（老 TS）保留是为兼容；module 是非标准字段、只有部分打包器读，别把它当成 ESM 的「官方」入口。三者要和 exports 指向一致，避免不同工具解析到不同文件。

files: ["dist"] 表示只发 dist 目录（外加 package.json、README、LICENSE 这几个 npm 强制包含的）。发布前用 npm pack --dry-run 预览到底会打进哪些文件：

npm pack --dry-run

它会列出即将发布的文件清单，但不真的生成 tarball。每次发新包或改了产物结构，都该跑一下这个，避免把 .env、源码、node_modules 之类的东西误发上去。

dist-tag：latest、next、beta 是怎么回事

这是发布里最容易被忽视但特别有用的机制。dist-tag 是给版本贴的「标签」，让用户能按标签安装，而不用记具体版本号。

默认情况下，npm publish 会把版本贴上 latest 标签。用户 npm install @my-ui/components（不带版本）装的就是 latest 指向的版本。

这里容易和前面的 SemVer 规则混淆：^1.0.0 这种普通版本范围默认不会自动装 1.1.0-beta.0；但 npm install @my-ui/components 不带版本时看的是 latest tag。

关键点来了：如果你发 beta 版时不指定 tag，它会被贴到 latest 上。这时新用户直接 npm install @my-ui/components，或者 CI 里没有锁版本的安装，就可能装到你的测试版。这是发布事故的经典成因。

正确做法是给预发布版本贴专门的 tag：

# 发 beta 版，贴 beta 标签，不动 latest
npm publish --tag beta

# 发 next（下一个大版本预览）
npm publish --tag next

# 发金丝雀版（每次 CI 自动发的实验版）
npm publish --tag canary

用户按需安装不同通道：

npm install @my-ui/components          # 装 latest（稳定版）
npm install @my-ui/components@beta     # 装 beta 通道
npm install @my-ui/components@next     # 装 next 通道

常见的 tag 通道约定：

tag 含义 谁会装
latest 稳定正式版（默认） 不带版本安装的普通用户
next 下一个大版本的预览 想提前试新版的用户
beta / rc 测试版 / 候选版 愿意帮测的用户
canary 每次提交自动发的实验版 想验证某个未发布修复的用户

管理 dist-tag 的命令：

npm dist-tag ls @my-ui/components           # 查看所有 tag 指向
npm dist-tag add @my-ui/components@2.0.0 latest   # 手动把 latest 指到 2.0.0

比如你的 2.0 憋了很久用 next 通道测试，测稳了，就 npm dist-tag add ...@2.0.0 latest 把它扶正为正式版。这套 tag 机制让你能安全地并行维护稳定版和下一个大版本。

用 Changesets 把多包发布自动化

Monorepo 组件库有好几个包，手动一个个 npm version + npm publish 既慢又易错。Changesets 把这套自动化了。它的三步工作流（changeset 写意图 → changeset version 升版本 → changeset publish 发布）在 Monorepo 那篇讲过，这里补发布相关的细节。

changeset publish 帮你做了什么

pnpm changeset publish 不只是循环 npm publish，它做了几件省心的事：

  1. 只发版本有变化的包，没改的跳过；
  2. 按包管理器的发布能力打包：如果用 pnpm 发布，pnpm pack / pnpm publish 会把内部依赖的 workspace:* 替换成真实版本范围，因为 npm 上的用户没有你的 workspace；
  3. 打好 git tag；
  4. 按每个包的 publishConfig 发布（比如 access、registry）。

所以内部包引用可以用 workspace:*（组件库结构篇强调过），但要注意：真正做 workspace: 替换的是 pnpm 的 pack/publish 阶段，不是 Changesets 自己凭空改的。Changesets 负责决定哪些包该发、版本该怎么升、CHANGELOG 怎么写，再调用对应的发布流程。

预发布模式发 beta

Changesets 也支持预发布通道。进入 pre 模式后，changeset version 生成的是 x.y.z-beta.n 版本，publish 时自动贴对应 tag：

# 进入 beta 预发布模式
pnpm changeset pre enter beta
pnpm changeset version      # 生成 1.0.0-beta.0
pnpm changeset publish      # 自动以 --tag beta 发布

# 测试稳定后退出预发布
pnpm changeset pre exit

这把「SemVer 预发布版本号 + dist-tag beta 通道」两件事一起处理了，不用自己拼版本号和记 --tag。

CI 自动发布

最终形态是全自动。Changesets 官方的 GitHub Action 流程（Monorepo 那篇画过图）：开发者 PR 带 changeset → 合并到 main → CI 发现未消费的 changeset → 自动开一个 “Version Packages” PR → 合并这个 PR → CI 自动 changeset publish 发版。

一个典型的发布 workflow 骨架：

# .github/workflows/release.yml
name: Release
on:
  push:
    branches: [main]
jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      id-token: write   # 开启 OIDC / provenance 需要
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          registry-url: 'https://registry.npmjs.org'
      - run: pnpm install
      - run: pnpm build
      - uses: changesets/action@v1
        with:
          publish: pnpm changeset publish   # 有可发布内容时执行
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
          NPM_CONFIG_PROVENANCE: true   # 生成来源证明，npm 上显示「已验证的构建来源」

NPM_CONFIG_PROVENANCE: true 会让 npm 在发布时生成 provenance（来源证明），把「这个版本是由哪个仓库、哪条 CI workflow 构建发布的」用 Sigstore 签名记录下来，用户能在 npm 页面看到可验证的来源。它需要 CI 具备 id-token: write 权限，是供应链安全的推荐实践；配合上面说的 Trusted Publishing（OIDC）一起用，可以做到「免长期 token + 可验证来源」。

到这一步，发版就完全工具化了：没人手动改版本号、没人手动 npm publish、没人手写 CHANGELOG（上一篇讲的自动生成）。开发者只需在 PR 里写一个 changeset 描述改动，剩下的全自动。

发布前的检查清单

最后给一份发版前该过一遍的清单，都是真会翻车的点：

  1. package.json 的 files / exports / types 配对了吗？（npm pack --dry-run 看清单）
  2. scoped 包配了 publishConfig.access: public 吗？
  3. 破坏性变更升 major 了吗，还是偷懒只升了 minor？
  4. beta/rc 版是不是用了 --tag，没有覆盖 latest？
  5. 类型导出用 @arethetypeswrong/cli 自查过吗？（构建篇提过）
  6. 产物在只用一个组件的 demo 里，样式和按需都正常吗？
  7. NPM_TOKEN 是从 secret 注入的，没写死进仓库吧？

小结

  1. SemVer 三位各有含义：破坏性升 major、新功能升 minor、修 bug 升 patch；破坏性变更必须升 major，否则用户 ^ 范围会自动升上来炸掉。
  2. 预发布版本（1.0.0-beta.0）永远小于对应正式版，普通版本范围默认装不到，发 beta 不误伤用户。
  3. scoped 包默认私有，发公开包必须配 publishConfig.access: public，否则报 402/403。
  4. CI 发布用 Automation token 从 secret 注入，绝不写死进仓库；用 files 字段白名单控制发布内容，npm pack --dry-run 预览。
  5. dist-tag 是关键机制：发预发布版一定带 --tag beta/next/canary，不指定会覆盖 latest 导致所有用户装到测试版。
  6. Monorepo 用 Changesets 自动化：只发有变化的包、自动替换 workspace:*、打 tag，pre 模式一并处理 beta 版本号和通道。
  7. 终极形态是 CI 全自动发布，开发者只写 changeset，版本、CHANGELOG、publish 全部工具化。
