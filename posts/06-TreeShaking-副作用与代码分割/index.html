Tree Shaking、副作用与代码分割

发表于2026|更新于2026|工程化
|字数总计:1.8k|阅读时长:6分钟

前言：「为什么我只 import 了一个函数，打包产物却把整个库塞进来了？」「为什么首屏 JS 这么大？」这两个问题分别对应 Tree Shaking 和代码分割。这一篇把构建优化里最核心的两组概念讲清楚：怎么让没用的代码被删掉，以及怎么让用到的代码按需加载。

Tree Shaking：摇掉没用到的代码

Tree Shaking（摇树）这个名字很形象：把代码想象成一棵树，摇一摇，枯叶（没用到的代码）就掉下来了。它的作用是在打包时删除没有被使用的导出。

// utils.js
export function used() { return 'a' }
export function unused() { return 'b' } // 没人用

// main.js
import { used } from './utils.js'
console.log(used())

打包后，unused 会被删掉，产物里只有 used。

Tree Shaking 的前提：静态的 ESM

Tree Shaking 能成立，依赖一个关键前提：ESM 的 import/export 是静态的，构建工具能在不运行代码的情况下分析出「谁导出了什么、谁用了什么」。

CommonJS 很难做到这点，因为 require 是运行时的、动态的：

// CJS 很难可靠 Tree Shaking
const name = condition ? 'a' : 'b'
const mod = require(`./${name}`) // 运行时才知道加载谁

所以第一个实战结论：想让库被 Tree Shaking，库要优先提供 ESM 产物。这也是为什么现在库都强调发 ESM、为什么 lodash-es 比 lodash 更利于摇树。不是说 CJS 绝对不能优化，而是它缺少 ESM 那种静态结构，打包器只能做很有限、很保守的分析。

坑：import _ from 'lodash'（CJS 全量包）几乎摇不掉，会把整个 lodash 打进去。换成 import { debounce } from 'lodash-es' 才能只打需要的部分。

副作用与 sideEffects

Tree Shaking 有个绕不开的难题：构建工具不敢随便删代码，怕删掉有副作用的代码。

什么是副作用（side effect）？就是模块被引入时，除了导出值之外还「干了别的事」：

// polyfill.js —— 这个模块有副作用
Array.prototype.myMethod = function () {} // 修改了全局原型

// styles.css 的 import 也是副作用：注入样式
import './global.css'

假设你 import './polyfill.js' 但没使用它的任何导出，构建工具能删吗？不能！因为它修改了全局原型，删了就出 bug。所以默认情况下，构建工具对「可能有副作用」的模块会保守处理，不敢摇。

用 package.json 的 sideEffects 声明

库作者可以通过 package.json 的 sideEffects 字段，告诉打包器「我的哪些文件是纯净的、可以放心摇」：

{
  "name": "my-lib",
  "sideEffects": false
}

sideEffects: false 的意思是：这个包里所有模块都没有副作用，没用到的尽管删。这是库能被高效 Tree Shaking 的关键声明。

但如果包里确实有副作用文件（比如 CSS、polyfill），要列出来排除：

{
  "sideEffects": [
    "*.css",
    "./src/polyfill.js"
  ]
}

意思是：除了这些文件，其他都可以安全摇掉；这几个有副作用，请保留。

实战教训：我见过一个库设了 sideEffects: false，结果它的 CSS 在被 Tree Shaking 后没注入，页面样式全丢。原因就是漏了把 *.css 列进 sideEffects。所以发库时，有 CSS 一定要把它列为有副作用。

代码分割：不要一次性加载所有代码

Tree Shaking 是「删掉没用的」，代码分割（Code Splitting）是「把用到的也别一次全给」。

设想一个有 10 个路由的后台系统，如果全打进一个 bundle，用户打开首页就得下载全部 10 个页面的代码——首屏巨慢。代码分割就是把代码拆成多个 chunk，按需加载。

动态导入：代码分割的触发点

代码分割的核心语法是动态导入 import()。和静态 import 不同，它返回一个 Promise，运行时才加载：

// 静态导入：构建时就确定，打进主 bundle
import { heavyFn } from './heavy.js'

// 动态导入：构建工具会把 heavy.js 拆成独立 chunk，用到时才下载
button.addEventListener('click', async () => {
  const { heavyFn } = await import('./heavy.js')
  heavyFn()
})

构建工具看到 import()，会自动把那个模块及其依赖拆成单独的文件。用户点击按钮时才发请求加载——这就是「懒加载」。

框架里的路由懒加载

实际项目里最常见的代码分割就是路由级懒加载。以 React 为例：

import { lazy, Suspense } from 'react'

// Dashboard 会被拆成独立 chunk，访问该路由时才加载
const Dashboard = lazy(() => import('./pages/Dashboard.jsx'))

function App() {
  return (
    <Suspense fallback={<div>加载中...</div>}>
      <Dashboard />
    </Suspense>
  )
}

Vue 里类似：

const routes = [
  { path: '/dashboard', component: () => import('./pages/Dashboard.vue') },
]

效果是：首屏只加载首屏需要的代码，其他页面的代码等用户真正访问时才下载。

第三方依赖单独分块（vendor chunk）

还有一类常见分割：把不常变的第三方依赖单独打一个 chunk。好处是依赖没变时，这个 chunk 的 hash 不变，浏览器能长期缓存，你发版只更新业务代码 chunk。

Vite 7 及以前（底层生产构建走 Rollup）可以这样手动控制：

// vite.config.js（Vite 7 及以前）
const vendorRE = /[\\/]node_modules[\\/](vue|vue-router|pinia)[\\/]/

export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks(id) {
          // 把这几个库打到名为 vendor 的 chunk
          if (vendorRE.test(id)) {
            return 'vendor'
          }
        },
      },
    },
  },
}

注意：Vite 8 起底层换成 Rolldown，build.rollupOptions 只是兼容旧项目的 deprecated alias，不建议新项目继续写。更关键的是，output.manualChunks 的对象形式在 Vite 8/Rolldown 里不再支持，函数形式也已废弃，推荐迁到 Rolldown 的 codeSplitting。

Vite 8 里更推荐写成：

// vite.config.js（Vite 8）
export default {
  build: {
    rolldownOptions: {
      output: {
        codeSplitting: {
          groups: [
            {
              name: 'vendor',
              test: /node_modules\/(vue|vue-router|pinia)/,
            },
          ],
        },
      },
    },
  },
}

三者怎么配合

把这篇的概念串起来：

Tree Shaking  →  删掉「没用到的导出」（要 ESM + sideEffects 配合）
代码分割      →  把「用到的代码」拆成多个 chunk
动态导入      →  代码分割的触发手段，实现按需/懒加载
vendor 分块   →  把稳定依赖独立出来吃长期缓存

它们都为了同一个目标：让用户下载的 JS 尽可能少、尽可能按需。Tree Shaking 管「该不该打进来」，代码分割管「打进来的怎么切、何时加载」。

小结

  1. Tree Shaking 在打包时删除没用到的导出，前提是静态可分析的 ESM；CommonJS 缺少静态结构，摇树效果通常很有限。
  2. 想让库被摇，要发 ESM 产物；用 lodash-es 而非 lodash 这类全量 CJS 包。
  3. 副作用是模块「除了导出还干别的事」，构建工具默认不敢删；用 package.json 的 sideEffects 声明哪些纯净、哪些（如 CSS）要保留。
  4. 代码分割靠动态导入 import() 触发，把模块拆成独立 chunk，运行时按需加载。
  5. 路由级懒加载（lazy / () => import()）是最常见的分割方式，显著降低首屏体积。
  6. 把稳定的第三方依赖打成 vendor chunk，能吃到浏览器长期缓存，发版只更新业务代码。
