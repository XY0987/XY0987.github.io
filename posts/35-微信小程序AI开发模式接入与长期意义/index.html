微信小程序 AI 开发模式接入与长期意义

发表于2026|更新于2026|AI相关
|字数总计:5.6k|阅读时长:18分钟

前言：微信小程序 AI 开发模式不是简单地给小程序加一个聊天框，而是把小程序里的业务能力拆成 AI 可以理解、可以调用、可以展示的标准单元。本文基于微信官方文档，聊一下它怎么接、背后是什么机制、真正落地会遇到哪些挑战，以及它对小程序长期形态的影响。

先说结论

我的理解是：小程序 AI 开发模式，本质上是在小程序和大模型之间加了一层“业务能力协议”。

以前用户使用小程序，大多是这样的：

用户打开页面 -> 找入口 -> 填表单 -> 点按钮 -> 看结果

接入 AI 后，流程会更像这样：

用户说需求 -> AI 理解意图 -> 调用原子接口 -> 展示原子组件 -> 用户确认/修改 -> 继续执行

这里最关键的变化不是“多了一个 AI 对话入口”，而是小程序的能力要被重新封装成：

概念 作用 类比
全局提示词 AGENTS.md 描述小程序整体服务范围和多个 SKILL 的关系 公司介绍
SKILL.md 描述某个业务能力的流程、规则、意图分流 岗位手册
mcp.json 声明 AI 可以调用哪些原子接口、参数怎么填、结果怎么展示 接口契约
原子接口 真正执行业务逻辑，返回结果和下一步指引 后端接口 / 工具函数
原子组件 把结构化结果渲染成对话流里的 GUI 卡片 小程序卡片组件

所以这件事对前端开发者的要求也变了：不只是会写页面，还要会把业务能力拆成 AI 能稳定调用的“工具”。

小程序 AI 开发模式是什么

根据微信官方文档，小程序 AI 开发模式会让开发者把小程序功能抽象为原子接口和原子组件，并封装成 SKILL，供小程序 AI 调用。

当用户通过小程序 AI 发起对话时，小程序 AI 会通过小程序 MCP 协议分析用户意图，选择合适的原子接口和原子组件，完成数据处理、任务执行和结果展示。

这里有一个容易混淆的点：

小程序 MCP 不是标准 MCP 的简单照搬，而是微信针对小程序运行环境做过适配的一套协议。

标准 MCP 更像通用工具协议，小程序 MCP 更贴近微信生态内的小程序能力开放。开发者不需要从零实现 MCP Server，而是按微信约定提供 SKILL、mcp.json、原子接口和原子组件。

整体关系可以这样理解：

┌──────────────────────────────────┐
│            用户自然语言           │
└────────────────┬─────────────────┘
                 │
                 ▼
┌──────────────────────────────────┐
│          小程序 AI / 推理层        │
│  选择 SKILL、选择接口、生成参数      │
└────────────────┬─────────────────┘
                 │
                 ▼
┌──────────────────────────────────┐
│              SKILL                │
│  SKILL.md + mcp.json + index.js    │
└───────────────┬──────────────────┘
                │
      ┌─────────┴─────────┐
      ▼                   ▼
┌──────────────┐    ┌──────────────┐
│   原子接口    │    │   原子组件    │
│  执行业务逻辑  │    │  渲染 GUI 卡片 │
└──────────────┘    └──────────────┘

如何接入：从一个最小 SKILL 开始

官方文档里给出的接入路径大概可以拆成这几步：

  1. 在微信公众平台或微信开发者助手中申请 AI 能力的“开发模式”。
  2. 在小程序中声明 agent.skills。
  3. 为每个业务能力创建独立分包。
  4. 在分包里编写 SKILL.md、mcp.json、index.js、原子接口和原子组件。
  5. 使用微信开发者工具 Nightly 的“小程序 AI 编译”模式调试。

需要注意：官方文档明确说明，当前小程序 AI 开发模式还处于 beta / 内测阶段，暂未开放相关代码提审。所以现在更适合做技术预研、内部 Demo 和业务能力梳理，不建议直接合入正式版本发布链路。

第一步：在 app.json 声明 SKILL

官方要求 SKILL 必须封装在独立分包里，同时需要全局开启按需注入 lazyCodeLoading。

一个简化版配置如下：

{
  "lazyCodeLoading": "requiredComponents",
  "subPackages": [
    {
      "root": "package-ai",
      "independent": true,
      "pages": []
    }
  ],
  "agent": {
    "instruction": "AGENTS.md",
    "skills": [
      {
        "name": "shop",
        "description": "商品推荐与订单确认能力",
        "path": "package-ai/shop-skill"
      }
    ]
  }
}

这里有两个点要特别注意：

  • agent.skills[].path 要指向具体的 SKILL 目录；
  • instruction 指向的是全局提示词文件，官方文档里提到通常是 AGENTS.md，目前不是必填。

第二步：组织 SKILL 目录

一个比较清晰的目录可以这样放：

package-ai/
└── shop-skill/
    ├── SKILL.md
    ├── mcp.json
    ├── index.js
    ├── apis/
    │   └── getRecommendedProducts.js
    └── components/
        └── product-card/
            ├── index.js
            ├── index.json
            ├── index.wxml
            └── index.wxss

官方文档里也提到几个大小限制：

文件 说明 限制
AGENTS.md 全局提示词 最大 10000 字节
SKILL.md 单个 SKILL 的业务说明 最大 16000 字节
mcp.json 原子接口能力声明 最大 24000 字节

这意味着我们不能把所有业务规则都堆进一个大文档里。真正工程化时，需要把“接口怎么用”“业务流程怎么走”“本次调用结果是什么”分别放在正确的位置。

mcp.json：告诉 AI 有哪些工具可用

mcp.json 是模型可调用能力的声明文件，里面会声明原子接口的名称、描述、入参、出参，以及结果是否绑定原子组件。

例如一个“推荐商品”的原子接口可以这样写：

{
  "apis": [
    {
      "name": "getRecommendedProducts",
      "description": "推荐商品。根据用户的自然语言需求返回可购买商品列表；用户没有明确品类时，不要编造商品，应返回适合继续选择的推荐列表。",
      "_meta": {
        "ui": {
          "componentPath": "components/product-card/index"
        }
      },
      "inputSchema": {
        "type": "object",
        "properties": {
          "keyword": {
            "type": "string",
            "description": "商品关键词，例如『咖啡』『蛋糕』『轻食』。用户未说出具体品类时不要填写本字段。"
          }
        }
      },
      "outputSchema": {
        "type": "object",
        "properties": {
          "products": {
            "type": "array",
            "items": {
              "type": "object",
              "properties": {
                "productId": { "type": "string" },
                "name": { "type": "string" },
                "price": { "type": "number" },
                "reason": { "type": "string" }
              },
              "required": ["productId", "name", "price", "reason"]
            }
          }
        },
        "required": ["products"]
      }
    }
  ],
  "components": [
    {
      "path": "components/product-card/index",
      "relatedPage": "/pages/product/detail"
    }
  ]
}

这里最重要的不是 JSON 格式，而是 description 怎么写。

官方最佳实践里强调，mcp.json 的接口描述会强烈影响模型“选不选这个接口”，inputSchema.description 会影响模型“怎么填参数”。所以不要只写：

{
  "description": "获取商品列表"
}

这种描述对人类开发者够用，但对 AI 不够。更好的写法应该包含：

  • 这个接口处理什么业务对象；
  • 什么时候该调用；
  • 什么情况下不该调用；
  • 字段从哪里来；
  • 缺字段时应该怎么办。

我的建议是：把 mcp.json 当成写给 AI 的 OpenAPI，不要当成普通接口文档。

原子接口：返回结果，也返回下一步动作

原子接口是真正执行业务逻辑的地方，可以通过 wx.request 调后端，也可以通过微信云开发调用云函数或数据库。

下面这个示例不依赖后端，便于看清返回结构。它需要运行在小程序 AI 原子接口环境中：

// package-ai/shop-skill/apis/getRecommendedProducts.js
module.exports = async function getRecommendedProducts({ keyword }) {
  const allProducts = [
    {
      productId: 'coffee_001',
      name: '冰美式',
      price: 16,
      reason: '清爽、低糖，适合想喝点提神饮品的场景'
    },
    {
      productId: 'cake_001',
      name: '原味芝士蛋糕',
      price: 28,
      reason: '口味稳定，适合搭配咖啡'
    }
  ]

  const products = keyword
    ? allProducts.filter((item) => item.name.includes(keyword))
    : allProducts

  if (products.length === 0) {
    return {
      isError: true,
      content: [
        {
          type: 'text',
          text: `未找到和「${keyword}」相关的商品。请提示用户换一个关键词，或展示当前推荐商品供用户选择。不要继续用相同关键词重复调用本接口。`
        }
      ]
    }
  }

  return {
    isError: false,
    structuredContent: {
      products
    },
    content: [
      {
        type: 'text',
        text: '已找到可推荐商品。请展示商品推荐卡片，并用一句话引导用户选择想要的商品。'
      }
    ]
  }
}

注意这里返回了三类信息：

字段 给谁看 作用
isError 小程序 AI 标识是否异常，异常时通常不渲染 GUI 卡片
structuredContent 小程序 AI + 原子组件 结构化数据，供模型理解和组件渲染
content 小程序 AI 本次结果说明，以及下一步动作引导
_meta 原子组件 对模型不可见，适合放图片地址、冗余字段等私有数据

官方最佳实践里有一个很关键的建议：content 最好采用“事实 + 动作”的两段式。

反面写法：

return {
  content: [{ type: 'text', text: '接下来请展示商品卡片。' }]
}

正面写法：

return {
  content: [
    {
      type: 'text',
      text: '已根据用户需求找到 2 个推荐商品。请展示商品推荐卡片，并引导用户选择。'
    }
  ]
}

原因也很简单：AI 不只是读你的数据，还会读你的动作指令。如果只给动作，不说明事实，模型可能误解当前流程状态。

index.js：注册原子接口

有了接口实现之后，需要在 SKILL 入口文件里注册。

// package-ai/shop-skill/index.js
const getRecommendedProducts = require('./apis/getRecommendedProducts')

const skill = wx.modelContext.createSkill('/package-ai/shop-skill')

skill.registerAPI('getRecommendedProducts', getRecommendedProducts)

这里的 getRecommendedProducts 必须和 mcp.json 里的 apis[].name 保持一致。

如果业务复杂，还可以用官方提供的中间件机制做统一登录态、错误捕获、埋点上报等公共逻辑。但我的建议是：早期不要急着抽复杂中间件，先把每个原子接口的输入、输出、异常分支写稳定。

SKILL.md：描述整个业务怎么跑

mcp.json 负责描述“单个接口怎么用”，SKILL.md 负责描述“整个业务怎么跑”。

比如商品推荐 SKILL 可以这样写：

# 商品推荐与订单确认

## 能力范围

本 SKILL 用于根据用户需求推荐商品，并引导用户选择商品。

## 业务流程

1. 用户表达模糊需求，例如“想喝点清爽的”，调用 getRecommendedProducts，不填写 keyword。
2. 用户表达明确需求，例如“有咖啡吗”，调用 getRecommendedProducts，并把 keyword 填为“咖啡”。
3. 返回商品列表后，必须展示商品推荐卡片，不要只用纯文本罗列。
4. 用户选择商品后，再进入订单确认流程。

## 约束

- 不要编造 productId，productId 必须来自 getRecommendedProducts 的返回结果。
- 未调用下单接口前，不要对用户说“已下单”。
- 商品为空时，先说明未找到，再引导用户换关键词或从推荐商品中选择。

这个文件最适合写：

  • 用户意图如何分流；
  • 多个接口之间的前后依赖；
  • 哪些场景必须出卡片；
  • 哪些动作必须等用户确认；
  • 哪些 ID 只能来自上游接口，不能从自然语言里猜。

不要把所有单个接口的字段说明都重复写进 SKILL.md，否则很容易和 mcp.json 产生冲突。

原子组件：不是普通页面，而是对话流卡片

原子组件负责把原子接口返回的结构化数据渲染成 GUI 卡片。

它写起来接近小程序自定义组件，但运行环境和普通小程序页面不完全一样。官方文档里提到了一些限制：

  • 原子组件和原子接口运行环境隔离；
  • 组件初始化时决定卡片高度，后续不可再改变高度；
  • 默认不支持网络请求和云开发接口；
  • 默认不支持定时器；
  • 不支持动画；
  • 禁止上下滚动；
  • 支持点击后帮用户上行一条文本消息；
  • 需要关联小程序页面，方便用户从卡片进入完整页面。

我的理解是：原子组件更像“对话里的业务卡片”，不是一个缩小版页面。

所以组件设计要克制，适合展示关键结果和关键操作，不适合塞进完整业务流程。

例如商品推荐卡片只需要展示：

  • 商品名；
  • 价格；
  • 推荐理由；
  • 一个“选择这个”的操作。

更复杂的规格选择、地址管理、支付流程，最好还是通过半屏、小程序页面或后续原子接口继续承接。

调试方式：要按 AI 流程调，不只是按页面调

小程序 AI 开发模式的调试方式和普通小程序也不一样。

官方调试指南里提到，需要使用微信开发者工具 Nightly Electron Build，并在编译模式里切换到“小程序 AI 编译”，调试基础库切到 3.16.1。

这个模式支持：

调试对象 可以看到什么
单个 SKILL AI 是否能识别并进入对应能力
单个原子接口 入参、出参、错误分支是否符合预期
单个原子组件 卡片渲染和尺寸是否正常
完整对话流程 用户意图、接口调用、组件展示是否能连起来

这其实说明一个问题：接入 AI 后，测试对象从“页面状态”变成了“对话流程 + 工具调用链”。

以前前端测试一个页面，重点看接口返回后 UI 对不对。现在还要看：

  • AI 有没有选错接口；
  • 参数有没有填错；
  • 空结果会不会无限重试；
  • 用户修改需求后上下文能不能承接；
  • 卡片和对话文案是不是自然；
  • 写操作有没有提前执行。

真正的挑战不在接入，而在稳定性

从代码角度看，小程序 AI 开发模式的接入并不算特别复杂。真正难的是让 AI 在复杂业务里稳定运行。

挑战一：业务能力要重新拆分

传统小程序里，很多业务逻辑是藏在页面里的：

页面 onLoad -> 拉数据 -> 用户点击 -> 修改 data -> 调接口 -> 弹 toast

AI 接入后，这种写法不够用了。因为 AI 需要知道：

  • 当前有哪些动作可以调用；
  • 每个动作需要什么参数；
  • 参数从哪里来；
  • 调用成功后下一步做什么；
  • 失败时怎么给用户出口。

所以原来的页面逻辑需要被抽出来，变成可声明、可调用、可验证的原子接口。

这对老项目是一个挑战，因为很多小程序的业务边界并不干净。页面、接口、状态、埋点、权限混在一起时，AI 接入会倒逼你做一次业务能力治理。

挑战二：描述质量决定调用质量

小程序 AI 接入里有一个很反直觉的点：不是代码写对了，AI 就一定用得对。

模型会根据多个信息源做判断。官方最佳实践里给出的权重大概是：

信息源 主要影响
原子接口返回的 content 当前事实和下一步动作
mcp.json 的接口 description 选不选这个接口
inputSchema.description 参数怎么填
SKILL.md 跨接口流程和业务规则

这意味着描述不是文档附属品，而是运行时的一部分。

如果 description 写得模糊，模型可能选错接口；如果字段说明没有写清取值来源，模型可能编造 ID；如果 content 没有写清下一步动作，模型可能跳过用户确认。

我的实战建议是：把提示词、接口描述、返回文案都纳入代码评审，不要只 review JavaScript。

挑战三：写操作必须谨慎

查询类能力相对简单，比如查天气、查订单、查库存。

真正危险的是写操作：

  • 下单；
  • 退款；
  • 修改地址；
  • 使用优惠券；
  • 预约服务；
  • 删除数据。

这类能力必须明确区分“推荐”“确认”“执行”三个阶段。

推荐阶段：AI 可以主动调用接口获取候选项
确认阶段：必须让用户明确选择或确认
执行阶段：调用写接口前后都要有明确状态

一个很重要的约束是：未调用成功前，不要向用户宣称“已完成”。调用失败时，也不能只说“失败了”，要告诉用户失败原因和下一步可以怎么做。

挑战四：组件不是万能容器

很多前端开发者看到“原子组件”，第一反应可能是把现有页面搬进去。

我不建议这么做。

原子组件的高度、事件、滚动、网络请求、动画都有约束，它更适合做轻量卡片。把复杂页面塞进去，最后会变成一个既不好调试、也不好交互的半成品。

更合理的拆法是：

内容 放在哪里
核心结果展示 原子组件
复杂筛选、编辑、支付 小程序页面或半屏
数据获取和业务判断 原子接口
跨接口流程规则 SKILL.md
单接口参数约束 mcp.json

微信小程序融入 AI 的长期意义

我觉得这件事长期看会带来三个变化。

第一，小程序入口会从“页面导航”变成“意图导航”

过去小程序的核心体验是页面结构：

首页 -> 分类页 -> 详情页 -> 表单页 -> 结果页

用户必须理解你的信息架构，才能找到自己要的功能。

AI 接入后，用户可以直接说：

  • “帮我查一下上次买的那杯咖啡”；
  • “找一个适合下午喝的低糖饮品”；
  • “把明天上午的预约改到下午”；
  • “用积分换一张优惠券”。

这会让小程序从“用户找功能”逐步变成“功能理解用户”。

当然，这不代表页面不重要。页面仍然适合复杂浏览、强视觉展示和精细操作。但高频、明确、可被流程化的任务，会越来越适合被 AI 入口承接。

第二，前端工程会更重视业务语义

以前前端工程化更多关注：

  • 组件复用；
  • 状态管理；
  • 构建性能；
  • 类型检查；
  • 代码规范；
  • 请求封装。

这些依然重要，但 AI 接入会新增一层工程问题：业务语义怎么表达给模型。

例如：

  • productId 不能从用户口语里猜；
  • “再来一杯”需要查历史订单；
  • “清爽一点”不是一个固定枚举，需要推荐逻辑；
  • “下单”必须经过确认；
  • “修改地址”涉及隐私和权限。

这些不是单纯的 UI 问题，也不是单纯的接口问题，而是业务规则、用户语义和模型调用之间的契约问题。

长期看，优秀的小程序团队可能会沉淀出一套自己的 AI 能力工程规范，包括：

  • SKILL 拆分规范；
  • 原子接口命名规范；
  • 参数描述规范；
  • content 返回文案规范；
  • 写操作确认规范；
  • 对话流程评测用例；
  • AI 入口灰度和监控方案。

第三，AI 会倒逼业务能力服务化

很多小程序项目的历史包袱是：业务能力散落在页面里，复用靠复制，流程靠人记。

AI 接入会让这些问题暴露得更明显。因为模型不能调用“某个页面里的某段点击逻辑”，它只能调用被明确声明出来的原子接口。

这会倒逼团队把能力拆成更清楚的单元：

搜索商品
获取推荐
生成订单草稿
确认订单
查询订单状态
取消订单
修改预约时间

一旦这些能力被拆出来，不只是 AI 能用，普通页面、运营活动、客服系统、自动化测试也都能复用。

所以我更愿意把小程序 AI 接入看成一次“业务能力结构化”的机会，而不是一次单纯的 AI 功能尝鲜。

我的接入建议

如果现在要在真实项目里尝试，我会按这个顺序推进：

  1. 先选一个低风险、高频、查询或推荐类场景，不要一上来做支付、退款、删除这类写操作。
  2. 先拆 1 个 SKILL，控制在 2 到 5 个原子接口内，把链路跑通。
  3. mcp.json 重点写清接口触发条件、字段来源和缺省处理。
  4. SKILL.md 只写跨接口流程，不重复堆单接口字段说明。
  5. 原子接口返回的 content 统一采用“事实 + 动作”格式。
  6. 原子组件只做关键展示和关键选择，不要把完整页面搬进去。
  7. 把对话用例纳入测试，比如模糊意图、明确意图、空结果、用户修改需求、异常分支。

我的判断是：小程序 AI 短期内不会替代现有页面体系，但会优先改造那些“用户知道自己要什么，只是不想一步步点”的场景。

小结

  1. 小程序 AI 开发模式的核心是把业务能力封装成 SKILL，供小程序 AI 通过小程序 MCP 调用。
  2. 接入重点不是写一个聊天框，而是设计 SKILL.md、mcp.json、原子接口和原子组件之间的职责边界。
  3. description、inputSchema.description 和接口返回的 content 会直接影响 AI 的调用质量，必须当成运行时契约来写。
  4. 真正的落地挑战在于业务拆分、写操作确认、异常出口、组件限制和对话流程评测。
  5. 长期看，小程序 AI 会推动小程序从页面导航走向意图导航，也会倒逼业务能力更加结构化和服务化。
