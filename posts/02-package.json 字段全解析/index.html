package.json 字段全解析

发表于2026|更新于2026|工程化
|字数总计:4.9k|阅读时长:18分钟

前言：package.json 不是“依赖列表文件”，而是一个 Node.js 项目的工程入口。启动命令、依赖边界、模块入口、包发布、Node 版本、包管理器版本，很多关键约定都写在这里。

先看一个完整示例

下面这个 package.json 不是最全配置，但覆盖了大多数前端项目会遇到的核心字段：

{
  "name": "my-web-app",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "preview": "vite preview",
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "test": "vitest"
  },
  "dependencies": {
    "react": "^19.0.0",
    "react-dom": "^19.0.0"
  },
  "devDependencies": {
    "@vitejs/plugin-react": "^4.3.0",
    "typescript": "^5.8.0",
    "vite": "^6.0.0",
    "vitest": "^3.0.0",
    "eslint": "^9.0.0"
  },
  "engines": {
    "node": ">=20 <23"
  },
  "packageManager": "pnpm@9.15.0"
}

我建议读 package.json 时不要一行一行死记，而是按用途分组理解。

项目身份字段

name

name 是包名。如果项目只是内部应用，也建议认真命名，因为它会影响：

  • Monorepo 内部包引用；
  • 日志和构建产物识别；
  • 包发布时的 npm 包名；
  • workspace 之间的依赖声明。
{
  "name": "@company/admin-web"
}

带作用域的包名更适合团队内部库，比如 @company/ui、@company/request。

version

version 是版本号，通常遵循 SemVer：

主版本.次版本.修订版本
major.minor.patch

比如：

  • 1.0.1：修复 bug；
  • 1.1.0：新增兼容能力；
  • 2.0.0：破坏性变更。

应用项目不一定强依赖版本号，但组件库、工具库、SDK 必须认真维护。

private

{
  "private": true
}

private: true 表示这个包不应该被发布到 npm。业务应用建议都加上，避免误发布。

脚本字段：scripts

scripts 定义项目的标准动作。

{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "test": "vitest"
  }
}

我的建议是，项目至少保留这些命令：

命令 作用
dev 本地开发
build 生产构建
preview 本地预览构建产物
typecheck TypeScript 类型检查
lint 代码规范检查
test 测试

这样做的价值是：无论底层工具怎么换，团队成员和 CI 都只需要记住统一入口。

scripts 里的命令是怎么被找到的

这里有个很重要但经常被忽略的点：为什么我没有全局安装 vite，却可以在 scripts 里直接写 vite？

{
  "scripts": {
    "dev": "vite"
  },
  "devDependencies": {
    "vite": "^6.0.0"
  }
}

当你执行：

npm run dev

npm 会临时把当前项目的 node_modules/.bin 加到命令查找路径 PATH 的前面。于是 vite 这个命令会优先从本地依赖里找，而不是直接找全局命令。

大致过程可以理解成：

npm run dev
  └─ 读取 package.json scripts.dev = "vite"
      └─ 临时把 ./node_modules/.bin 加到 PATH
          └─ 查找 ./node_modules/.bin/vite
              └─ 执行 vite 包声明的 CLI 入口

node_modules/.bin/vite 通常不是完整源码，而是一个软链接或命令 shim。它会指向 vite 这个包在自己 package.json 里声明的 bin 入口。

比如 vite 包内部会有类似这样的配置：

{
  "bin": {
    "vite": "bin/vite.js"
  }
}

关键逻辑是：依赖包通过 bin 声明命令，包管理器把命令链接到 node_modules/.bin，npm run 再从 .bin 里找到它。

那如果我不通过 scripts，而是在终端里直接运行 vite 呢？

这时候就不是 npm 在帮你改 PATH 了，而是你的 Shell 自己按照当前环境变量 PATH 查找命令。多数情况下，Shell 不会自动去当前项目的 node_modules/.bin 里找，所以直接执行：

vite

能不能成功，取决于你有没有全局安装 vite，或者你的终端环境有没有额外把项目的 .bin 加进 PATH。这也是为什么有些人电脑上能跑，换一台机器就报 command not found: vite。

再看 npx vite。在现代 npm 里，npx 基本可以理解成 npm exec 的快捷入口。它会优先尝试使用当前项目依赖里的可执行命令；如果项目里没有对应依赖，npm 可能会提示你是否临时下载并执行这个包。

可以简单对比一下：

执行方式 命令来源 适合场景
npm run dev 读取 scripts.dev，并临时把本地 node_modules/.bin 加到 PATH 团队项目里的标准入口
vite 只按当前 Shell 的 PATH 查找 不建议依赖，容易跑到全局版本或直接找不到
npx vite 优先找本地依赖，找不到时可能临时下载执行 临时体验工具可以用，项目长期命令不建议依赖它

所以，npx vite 比直接敲 vite 稳一点，但它仍然不是我推荐的团队入口。团队项目里更好的做法，还是把命令沉淀到 scripts 里，让所有人都通过同一个入口执行。

因此我一般不建议团队依赖全局安装的 vite、eslint、tsc。更稳定的做法是把它们写进项目依赖，然后通过 scripts 执行。

# ✅ 推荐：使用项目本地版本
npm run dev
pnpm dev

# ❌ 不推荐：依赖全局 vite 版本
vite

pnpm、yarn 执行脚本时也会提供类似的本地命令查找能力，只是底层链接和缓存结构不同。

生命周期脚本要谨慎

npm 支持很多生命周期脚本，比如 prepare、preinstall、postinstall。

{
  "scripts": {
    "prepare": "husky install",
    "postinstall": "node scripts/setup.js"
  }
}

这些脚本会在特定安装或发布阶段自动执行。它们很有用，但也要克制，因为自动执行脚本会带来几个问题：

  1. 安装依赖变慢；
  2. 失败时不容易定位；
  3. 有供应链安全风险，因为安装依赖时可能执行第三方包里的代码。

这里要特别区分两个概念。

ignore-scripts 是全局开关。根据 npm v11 官方文档，它的默认值仍然是 false，也就是 npm 默认不会禁止执行 package.json 里的脚本。只有你显式设置：

npm install --ignore-scripts

或者在 .npmrc 里配置：

ignore-scripts=true

npm 才会跳过脚本。并且即使开启了 ignore-scripts，像 npm run dev、npm test 这种明确要执行某个脚本的命令，仍然会执行目标脚本，只是不会再执行对应的 pre / post 钩子。

另一个是 npm v11 引入的 allowScripts 策略。官方文档的说法是：当前版本里它还是 advisory，也就是提示性质。安装脚本默认仍会执行，但 npm 会列出哪些依赖的安装脚本还没有被审核；未来版本才会阻止未审核的安装脚本。

# 查看还有哪些依赖的安装脚本没有被审核
npm approve-scripts --allow-scripts-pending

# 审核通过指定依赖的安装脚本
npm approve-scripts canvas sharp

所以更准确的说法不是“最新 npm 默认禁止生命周期脚本”，而是：npm 已经在往安装脚本审核机制演进，但 npm v11 当前默认仍会执行安装脚本。

我的建议是：业务项目里少用复杂生命周期脚本，工具库发布场景再按需使用。

依赖字段：运行时和开发期要分清

dependencies

dependencies 是运行时依赖。也就是你的代码在实际运行时需要它。

{
  "dependencies": {
    "react": "^19.0.0",
    "axios": "^1.7.0"
  }
}

如果你写的是一个 npm 库，用户安装你的包时也会安装这些依赖。

devDependencies

devDependencies 是开发期依赖，比如 TypeScript、Vite、ESLint、测试框架。

{
  "devDependencies": {
    "typescript": "^5.8.0",
    "vite": "^6.0.0",
    "vitest": "^3.0.0"
  }
}

一个简单判断：**项目运行时不需要，只是开发、构建、测试需要，就放 devDependencies**。

peerDependencies

peerDependencies 常用于插件、组件库、框架适配包。

{
  "peerDependencies": {
    "react": ">=18 <20"
  }
}

它表达的是：我需要宿主项目提供这个依赖。

比如一个 React 组件库不应该自己偷偷打包一份 React，否则用户项目可能出现多份 React，导致 Hooks 报错。所以组件库通常把 React 放在 peerDependencies。

optionalDependencies

optionalDependencies 表示可选依赖，安装失败不一定阻断整个安装过程。常见于平台相关能力，比如某些原生模块。

业务前端项目不常用，但工具链里会见到。

模块入口与类型字段：type、main、module、types、exports

这部分是最容易踩坑的地方。

type

Node.js 官方文档建议包作者显式声明 type。

{
  "type": "module"
}

它决定当前包内 .js 文件默认按什么模块系统解析：

配置 .js 行为
"type": "module" 按 ESM 解析
"type": "commonjs" 按 CommonJS 解析
不写 通常按 CommonJS 处理，但不建议依赖默认值

.mjs 永远是 ESM，.cjs 永远是 CommonJS，不受 type 影响。

main

main 是传统入口字段：

{
  "main": "./dist/index.cjs"
}

它只能描述一个默认入口，主要服务于 require('pkg') 这类加载方式。

module

module 不是 Node.js 官方包入口标准字段，但很多打包工具会读取它，把它当作 ESM 入口。

{
  "module": "./dist/index.js"
}

现在更推荐用 exports 精确声明入口，而不是只依赖 module。

exports

exports 是现代包入口声明方式。它可以限制哪些路径允许被外部访问，也可以支持条件导出。

{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./styles.css": "./dist/styles.css"
  }
}

几个关键点：

  1. exports 存在时优先级高于 main；
  2. 未在 exports 声明的内部路径，外部不能随便导入；
  3. 条件顺序有意义，通常 types 放前面，default 放最后；
  4. 给老包新增 exports 可能是破坏性变更。

如果 type、main、module、exports 同时存在，不要把它们混成一件事。更清晰的理解方式是：

  1. 先按优先级决定“加载哪个文件”；
  2. 再根据文件后缀和 type 决定“这个文件按什么模块系统解析”。

从 Node.js 的视角看，包入口大致是这个优先级：

import 'pkg' / require('pkg')
  └─ 如果有 exports，优先按 exports 匹配入口
      ├─ import 调用，优先匹配 import 条件
      └─ require 调用，优先匹配 require 条件
  └─ 如果没有 exports，再看 main
  └─ 如果没有 main，才会回退到默认入口，比如 index.js

注意，module 不在这个 Node.js 官方入口优先级里。它更多是打包工具的约定字段，很多构建工具会把它当成 ESM 入口，但具体优先级要看工具自己的配置。

举个例子：

{
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}

如果使用 Node.js 加载这个包：

使用方式 先读哪个字段 最终入口文件 解析方式
import 'pkg' exports["."].import ./dist/index.js 因为 type: "module"，.js 按 ESM 解析
require('pkg') exports["."].require ./dist/index.cjs .cjs 永远按 CommonJS 解析
老环境不识别 exports main ./dist/index.cjs .cjs 永远按 CommonJS 解析

最后一步才是解析方式：

文件 有 "type": "module" 没有配置 type 或配置 "type": "commonjs"
.mjs ESM ESM
.cjs CommonJS CommonJS
.js ESM CommonJS

这里最容易误解的是：import 条件不等于“目标文件一定按 ESM 解析”，require 条件也不等于“目标文件一定按 CommonJS 解析”。它们只是入口选择条件。文件最终怎么解析，还是要看后缀和 type。

所以我的建议是，库项目尽量用明确后缀降低歧义：

{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}

如果你统一使用 "type": "module"，也可以让 ESM 入口继续使用 .js，但 CommonJS 入口最好仍然显式写成 .cjs。

CLI 字段：bin

如果你的包要提供命令行工具，需要配置 bin。

{
  "name": "create-demo",
  "bin": {
    "create-demo": "./bin/cli.js"
  }
}

bin 指向的文件通常要写 shebang：

#!/usr/bin/env node

console.log('hello cli')

否则全局安装后，系统可能不知道要用 Node.js 执行它。

发布控制字段：files

files 控制发布到 npm 时包含哪些文件。

{
  "files": [
    "dist",
    "README.md",
    "LICENSE"
  ]
}

我的建议是：库项目一定要写 files，不要把源码、测试、配置、临时文件一股脑发布出去。

可以通过下面命令在本地检查发布包内容：

npm pack --dry-run

这个命令不会真正发布，只会展示将被打进包里的文件。发布前看一眼，能避免很多低级错误。

环境约束字段：engines 和 packageManager

engines

{
  "engines": {
    "node": ">=20 <23"
  }
}

engines 用来声明项目支持的 Node.js 版本范围。需要注意，npm 默认多数情况下只是警告，不一定强制阻断安装，除非开启 engine-strict。

但即使只是警告，也值得写。它至少告诉团队：这个项目不是随便哪个 Node 版本都能跑。

packageManager

{
  "packageManager": "pnpm@9.15.0"
}

这个字段配合 Corepack 使用，用来固定包管理器及版本。它解决的是“有人用 npm，有人用 pnpm，有人用不同版本 pnpm”的问题。

团队项目建议必写。

其他常见字段

上面讲的是最核心的一批字段，但实际项目里还会经常看到下面这些。它们不一定每个项目都要写，但看到时要知道它们解决什么问题。

元信息字段：description、keywords、author、license

这些字段主要服务于包发布、检索和归属说明。

{
  "description": "A type-safe request sdk",
  "keywords": ["request", "sdk", "typescript"],
  "author": "Your Name",
  "license": "MIT"
}

如果是业务应用，这些字段影响不大；如果是 npm 包、组件库、CLI 工具，建议认真写。

其中 license 很重要，它告诉别人这个包能不能商用、能不能修改、能不能再分发。内部私有项目可以按公司规范写，开源项目不要乱填。

仓库与问题反馈：repository、bugs、homepage

这些字段用于告诉用户源码在哪里、问题去哪里提、文档在哪里看。

{
  "repository": {
    "type": "git",
    "url": "https://github.com/company/my-sdk.git"
  },
  "bugs": {
    "url": "https://github.com/company/my-sdk/issues"
  },
  "homepage": "https://github.com/company/my-sdk#readme"
}

库项目建议补齐，业务应用可以不写。

workspaces

Monorepo 项目会用到：

{
  "workspaces": [
    "apps/*",
    "packages/*"
  ]
}

它告诉包管理器哪些目录属于同一个工作区。比如 apps/admin、packages/ui、packages/utils 都可以被当成同一个仓库里的子包来管理。

imports

imports 是 Node.js 支持的包内部导入映射，key 必须以 # 开头。

{
  "imports": {
    "#utils/*": "./src/utils/*.js",
    "#config": "./src/config/index.js"
  }
}

它和 exports 的区别是：

字段 作用范围 主要用途
exports 给包外部用户用 声明这个包暴露哪些入口
imports 只给包内部代码用 给包内部做私有路径映射

比如包内部可以写：

import { formatDate } from '#utils/date.js'

但包外部用户不能通过 #utils/date.js 访问它。

sideEffects

库项目常见字段，用于辅助 tree-shaking。

{
  "sideEffects": false
}

含义是模块没有副作用，打包工具可以更大胆地移除未使用代码。但如果项目里有全局样式导入，就不能乱写。

{
  "sideEffects": [
    "*.css"
  ]
}

我的建议是：纯工具函数库可以考虑 sideEffects: false，组件库如果有样式导入，要谨慎配置白名单。

依赖修正字段：overrides、resolutions

有时你并不直接依赖某个包，但它是间接依赖，并且出现了安全漏洞或版本冲突。这时可以用依赖修正字段。

npm 和 pnpm 常见的是 overrides：

{
  "overrides": {
    "lodash": "4.17.21"
  }
}

Yarn Classic 常见的是 resolutions：

{
  "resolutions": {
    "lodash": "4.17.21"
  }
}

它们的作用都是强制依赖树里的某些包使用指定版本。

这个能力很有用，但不要滥用。因为你是在强行改依赖树，可能修好一个安全告警，又引入另一个兼容问题。我的建议是：只在安全漏洞、明确冲突、临时兜底时使用，并且要写清楚原因。

peerDependenciesMeta

它通常和 peerDependencies 搭配，用来声明某些 peer 依赖是可选的。

{
  "peerDependencies": {
    "react": ">=18",
    "vue": ">=3"
  },
  "peerDependenciesMeta": {
    "vue": {
      "optional": true
    }
  }
}

比如一个库主要支持 React，但也提供 Vue 适配能力，就可以把 vue 标记为可选 peer。这样用户不装 Vue 时，不一定会被强提示或强安装。

browserslist

browserslist 用来声明前端代码要兼容哪些浏览器。Babel、PostCSS、Autoprefixer、一些打包工具都会读取它。

{
  "browserslist": [
    ">0.5%",
    "last 2 versions",
    "not dead"
  ]
}

它会影响语法降级和 CSS 前缀处理。比如目标浏览器越老，构建产物可能越大，转换也越多。

也可以把它放到单独的 Browserslist 配置文件里，两种方式选一种即可。

config

config 可以给 npm scripts 提供项目级配置。

{
  "config": {
    "port": "3000"
  },
  "scripts": {
    "dev": "vite --host 0.0.0.0 --port $npm_package_config_port"
  }
}

这个字段现在不算特别常用，因为很多项目会把配置放到 .env 或单独配置文件里。但在一些 CLI 包或简单脚本里，还是能见到。

publishConfig

发布配置，比如指定 registry 或访问权限：

{
  "publishConfig": {
    "access": "public",
    "registry": "https://registry.npmjs.org/"
  }
}

内部包发布到私有源时很常见。比如公司内部包可以把 registry 指到私有 npm 仓库，避免误发到公网。

小结

  1. package.json 是项目工程入口，不只是依赖列表。
  2. scripts 应该沉淀项目标准动作，给团队和 CI 一个统一入口。
  3. dependencies 和 devDependencies 要按运行时/开发期区分。
  4. type、main、module、types、exports 决定包如何被加载和如何被 TypeScript 识别，是库项目的重点。
  5. 团队项目建议明确写 engines 和 packageManager，提升环境可复现性。
  6. workspaces、imports、sideEffects、overrides、browserslist 这些字段不一定每个项目都用，但在 Monorepo、库发布和依赖治理里很常见。
