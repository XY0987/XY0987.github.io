React Native 与 Expo 实战：顺便把主流跨端框架盘一遍

发表于2026|更新于2026|跨端
|字数总计:3.3k|阅读时长:12分钟

先把跨端框架分层说清楚

“跨端”这词被滥用得很厉害，Flutter、RN、uni-app、Taro、Electron、Tauri 全被归到一起，其实它们根本不是一回事。我自己是这么分的：

┌─────────────────────────────────────────────────┐
│  按目标平台划分                                   │
├─────────────────────────────────────────────────┤
│  移动端（iOS/Android）: RN / Flutter / Expo      │
│  移动 + 小程序:        uni-app / Taro            │
│  桌面端:              Electron / Tauri          │
│  全家桶（野心最大）:    Flutter / uni-app x       │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│  按渲染原理划分                                   │
├─────────────────────────────────────────────────┤
│  原生渲染:  RN / Expo（JS 调 iOS/Android 原生控件）│
│  自绘引擎:  Flutter（Skia 自己画）                │
│  WebView:  uni-app（小程序/H5 本质是 WebView）    │
│  编译时转换: Taro（一套代码编译到多端目标语言）     │
└─────────────────────────────────────────────────┘

本文只聊移动端原生这条线，也就是 RN 和 Expo。Flutter、uni-app、Taro 作为对比项出场，不展开细讲。

主流跨端框架横向对比

先一张表把主流选手拉到一起：

框架 语言 渲染 性能 生态 上手 典型代表作
React Native JS/TS 原生控件 中高 极强 中 Shopify、Discord、Meta 全家桶
Expo JS/TS 原生控件（基于 RN） 中高 极强 低 Coinbase、Pillar、Brex
Flutter Dart Skia 自绘 高 强 中高 Google Pay、闲鱼、美团外卖
uni-app Vue WebView/原生混合 中 中 低 一码多端中小应用居多
Taro React/Vue 编译到原生 中 中 中 京东、社交电商类

我的对比决策

  • 要做高质量 iOS/Android App：RN / Expo 或 Flutter 二选一
  • 主战场是小程序 + H5 附带 App：uni-app 或 Taro
  • 追求像素级一致 UI：Flutter
  • 团队本身是 React 技术栈：闭眼选 Expo

RN 和 Flutter 的差别，一句话：RN 让 App 长得像原生，Flutter 让 App 到哪都长一样。

哪个更好？看业务。强调平台一致的产品走 RN 路线合适；游戏化、品牌化强的产品走 Flutter 合适。

纯 RN 时代那些让人血压升高的事

在聊 Expo 之前，必须把纯 RN 的痛点说透——没踩过这些坑的人，是理解不了 Expo 为什么能迅速成为主流的。

坑 1：原生能力一用就要桥接

纯 RN 最大的痛点：JS 层给的 API 很薄，想用摄像头、相册、推送、蓝牙、生物识别这些能力，基本都要自己写原生模块或者装第三方库 + 手动 link。

举个最典型的场景：接摄像头。

# 纯 RN 时代的标准流程
yarn add react-native-camera
cd ios && pod install   # iOS 这一步经常炸
# Android 端还要改 AndroidManifest.xml 加权限
# iOS 端还要改 Info.plist 加 NSCameraUsageDescription

这还只是理想情况。真实情况是：

  • iOS 的 pod install 因为镜像/网络/版本不匹配，在新同事机器上经常跑不起来
  • Android 的 Gradle 版本、NDK 版本、compileSdkVersion 一个对不上就编译失败
  • 某些库还需要手动 react-native link（RN 0.60 之前）
  • 升级 RN 版本时，一堆原生依赖要跟着一起升，每次都是地狱

更深一层的痛：如果第三方库没覆盖到的能力，得自己写 Objective-C/Swift + Java/Kotlin 桥接模块。对一个纯 JS 背景的团队来说，这等于半只脚踩进了原生开发。

坑 2：打包发版门槛高

纯 RN 发版，你得同时具备三套知识：

  • JS 侧的打包（Metro）
  • iOS 侧的证书、描述文件、Xcode archive、TestFlight 上传
  • Android 侧的 keystore 签名、gradlew assembleRelease、上 Google Play

再加上如果想做热更新，还得自己接 CodePush 或者自研。每次发版都是大工程。

坑 3：升级噩梦

RN 的 upgrade 向来以痛苦著称，尤其跨大版本升级。官方出了 Upgrade Helper 对比 diff，但原生工程里的配置改动依然要手动合并，Pod、Gradle、AppDelegate、MainApplication 一个都跑不掉。

坑 4：开发环境重

一个新同事要上手纯 RN 项目，标准流程：

  1. 装 Node / Yarn
  2. 装 Xcode（十几个 G）+ iOS 模拟器
  3. 装 Android Studio + SDK + NDK + 模拟器
  4. 配 Java 环境
  5. 配 CocoaPods
  6. pod install 跑通
  7. Gradle sync 跑通

这套环境在 Mac 上折腾一天是常态，Windows 只能跑 Android。团队里来个新人，第一周基本都在配环境。

Expo 登场：它到底解决了什么

Expo 不是一个新框架，它本质是RN 的工程化增强套件。Expo 团队的思路很直接：把 RN 生态里所有脏活累活全包起来，给你一个”开箱即用”的开发体验。

它解决的核心三件事：

痛点 Expo 的答案
原生能力要桥接 内置几十个官方模块（expo-camera、expo-location 等），装完即用
打包发版门槛高 EAS Build 云端打包，OTA 热更新，一条命令发版
环境配置重 Expo Go 客户端扫码即可运行，零环境调试

Expo 的工作流：两种模式

Expo 现在主要是两种用法：

1. Managed Workflow（托管工作流）

完全不碰原生工程。你的项目里没有 ios/ 和 android/ 目录，一切原生配置通过 app.json / app.config.js 声明式描述，EAS Build 帮你在云上生成原生工程并打包。

2. Bare Workflow / Prebuild（裸工作流）

如果需要用到 Expo 没覆盖的原生能力，可以 expo prebuild 生成原生工程，你就能像纯 RN 那样自由改动，同时依然享受 Expo 生态的模块。

我的实战建议：能用 Managed 就用 Managed。Expo 的模块库现在已经覆盖了 95% 的常见需求，除非你要做蓝牙打印机、工业 PDA 这种深度定制的场景，否则没必要 prebuild。

Expo 常用模块盘一遍

这里挑开发中命中率最高的模块说一下，都是能直接 npx expo install xxx 就能用的。

媒体与文件类

npx expo install expo-camera expo-image-picker expo-file-system expo-media-library
  • expo-camera：摄像头，拍照、录像、扫码全覆盖，权限弹窗 Expo 帮你处理
  • expo-image-picker：系统相册选图/选视频
  • expo-file-system：文件读写、下载、上传，支持沙盒路径和流式读取
  • expo-media-library：访问系统相册、存图到相册

举个完整的拍照 + 存到相册的例子：

import { CameraView, useCameraPermissions } from 'expo-camera';
import * as MediaLibrary from 'expo-media-library';
import { useRef } from 'react';
import { Button, View } from 'react-native';

export default function CameraScreen() {
  const [permission, requestPermission] = useCameraPermissions();
  const cameraRef = useRef<CameraView>(null);

  if (!permission?.granted) {
    return <Button title="授权摄像头" onPress={requestPermission} />;
  }

  const takePicture = async () => {
    const photo = await cameraRef.current?.takePictureAsync();
    if (photo) {
      // 直接存到系统相册，无需桥接原生
      await MediaLibrary.saveToLibraryAsync(photo.uri);
    }
  };

  return (
    <View style={{ flex: 1 }}>
      <CameraView ref={cameraRef} style={{ flex: 1 }} />
      <Button title="拍照" onPress={takePicture} />
    </View>
  );
}

对比一下：这段代码在纯 RN 里要装 react-native-camera + react-native-cameraroll，还要改 Info.plist / AndroidManifest.xml 加权限字符串、改 Podfile、跑 pod install。Expo 把这些全部封进了模块内部。

设备与系统能力

npx expo install expo-location expo-notifications expo-local-authentication \
                 expo-haptics expo-device expo-battery
  • expo-location：GPS 定位、地理围栏、后台定位
  • expo-notifications：推送通知（本地 + 远程），自动处理 APNs/FCM 注册
  • expo-local-authentication：Face ID / Touch ID / Android 指纹
  • expo-haptics：触感反馈
  • expo-device / expo-battery：设备信息、电量

生物识别这个以前在纯 RN 是个老大难，现在三行代码搞定：

import * as LocalAuthentication from 'expo-local-authentication';

const authenticate = async () => {
  const hasHardware = await LocalAuthentication.hasHardwareAsync();
  if (!hasHardware) return;
  const result = await LocalAuthentication.authenticateAsync({
    promptMessage: '请验证指纹',
  });
  console.log(result.success ? '通过' : '失败');
};

存储与安全

npx expo install expo-secure-store @react-native-async-storage/async-storage
  • expo-secure-store：iOS Keychain + Android Keystore 统一封装，存 token、密钥专用
  • async-storage：普通 KV 存储，存用户设置、缓存之类

导航与路由

npx expo install expo-router

expo-router 是我最喜欢的一个改造：把 Next.js 的文件系统路由搬到了 RN 上。以前用 react-navigation 要手写一堆 Stack、Tab 嵌套，现在直接按目录组织就行：

app/
├── _layout.tsx            # 全局布局
├── index.tsx              # 首页 /
├── login.tsx              # /login
└── (tabs)/
    ├── _layout.tsx        # Tab 布局
    ├── home.tsx           # /home
    └── profile.tsx        # /profile

深链接、Web 同构、类型安全路由全自带，写多了会上瘾。

更新与发布

npx expo install expo-updates

expo-updates + EAS Update：不走应用商店的 OTA 热更新。改 JS 代码 → eas update 一键发布 → 用户下次打开就是新版本。对修 bug 来说是救命稻草。

注意：纯原生代码改动（加了新的原生依赖）还是得走应用商店发版，热更新只能推 JS Bundle。

EAS 三件套

Expo 的云服务 EAS（Expo Application Services），是我认为最值钱的部分：

  • EAS Build：云端打包 iOS / Android，不用本地装 Xcode
  • EAS Submit：一条命令提交到 App Store / Google Play
  • EAS Update：OTA 热更新
eas build --platform ios        # 云端打 iOS 包
eas submit --platform ios       # 直接上传到 TestFlight
eas update --branch production  # 推 OTA

对 Mac 都没有的团队成员来说，这简直是福音——没 Mac 也能发 iOS 包了。

纯 RN vs Expo：一张表对比

维度 纯 RN Expo (Managed)
原生能力接入 装包 + 手动配置 + pod install npx expo install 即用
摄像头/定位/推送 桥接或找第三方库 官方模块全覆盖
新人上手 配一天环境 Expo Go 扫码即跑
原生工程维护 必须会 不用碰
发版流程 Xcode / gradle 手动打包 eas build 一条命令
热更新 自接 CodePush eas update 一条命令
升级痛苦度 极高 Expo SDK 统一升
自由度 无限 受 Expo 模块约束（可 prebuild 解锁）

什么团队适合 Expo，什么团队不适合

适合 Expo 的团队

  • 中小团队：1-5 人做 App，Expo 把工程复杂度降到最低，能省一个原生工程师的开销
  • React 技术栈团队：无需额外学 Dart 或原生，直接复用现有技能
  • 创业团队 MVP 阶段：快速上线是第一优先级，Expo 的”扫码即跑” + “云端打包”把上线周期压到最短
  • 跨平台一致的 To C 产品：社交、工具、内容类 App，Expo 模块基本够用
  • Mac 资源紧张的团队：EAS Build 让没 Mac 的开发者也能发 iOS 包

不适合 Expo 的团队

  • 需要深度原生定制：比如接工业 PDA、蓝牙打印机、特殊硬件 SDK，Expo 模块覆盖不到，prebuild 之后也不如纯 RN 灵活
  • 已有成熟原生团队：如果团队已经有 iOS/Android 工程师，纯 RN 的自由度更高，EAS 的费用也省了
  • 对包体积极度敏感：Expo 默认会内置一些常用模块，包体积比精简纯 RN 稍大（差距没有以前那么夸张了，但还是有）
  • 大厂内部有自研发布/热更新体系：Expo 的 EAS 是全家桶式方案，和大厂自研体系会打架

我的实战建议

场景 推荐
个人/小团队新项目 Expo Managed
3-10 人产品团队新项目 Expo Managed（顶多后期 prebuild）
大厂内部新项目 Expo Bare 或纯 RN（视内部体系）
强原生定制项目 纯 RN 或原生
老 RN 项目升级 评估迁到 Expo Bare（能享受 EAS，不破坏原有原生工程）

一句话总结：Expo 把 RN 从”半只脚踩进原生”的工程，变成了”纯前端就能搞定 App”的工程。这是 RN 生态过去几年最大的一次体验升级。

踩过的坑

坑 1：Expo SDK 升级要整版跟

Expo 的模块版本和 SDK 版本强绑定。不能今天单独升 expo-camera、明天单独升 expo-location，要升就跟着 Expo SDK 一起升。好处是统一，坏处是升级窗口被 Expo 团队控制。

坑 2：prebuild 之后再回 Managed 很麻烦

expo prebuild 生成的 ios/ 和 android/ 目录一旦被手工改动，就很难无损回到 Managed 模式。决定 prebuild 前一定确认清楚。

坑 3：EAS Build 国内网络偶尔抽风

EAS 的构建服务器在海外，国内触发构建、拉依赖偶尔会超时。实在不行可以走 EAS 的 self-hosted 方案，或者改用本地 expo run:ios / expo run:android。

坑 4：某些模块在 Expo Go 里跑不了

比如推送、某些蓝牙模块，必须打 development build 才能调试。新手经常在 Expo Go 里一直测不通，排查半天发现是模块不支持 Expo Go。遇到这种情况走 eas build --profile development 打一个开发版客户端就好。

小结

  1. 跨端框架分三派：原生渲染（RN/Expo）、自绘（Flutter）、WebView/小程序（uni-app/Taro），选型先定派系
  2. 纯 RN 的痛点集中在：原生桥接繁琐、发版门槛高、升级地狱、环境配置重
  3. Expo 不是新框架，是 RN 的工程化增强：官方模块包 + EAS 云端打包 + OTA 热更新
  4. 常用 Expo 模块能覆盖 95% 的 App 需求：摄像头、定位、推送、生物识别、文件、路由全家桶
  5. Managed Workflow 优先，不够用再 prebuild 转 Bare，别反向走
  6. 中小团队、React 栈团队、MVP 阶段团队闭眼选 Expo；深度原生定制和大厂自研体系的场景留给纯 RN
  7. EAS Build 最大的隐形价值：没 Mac 也能发 iOS 包
