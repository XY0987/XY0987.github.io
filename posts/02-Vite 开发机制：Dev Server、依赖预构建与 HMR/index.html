Vite 开发机制：Dev Server、依赖预构建与 HMR

发表于2026|更新于2026|工程化
|字数总计:3.3k|阅读时长:10分钟

前言：上一篇先建立了构建工具坐标系：Vite 是上层编排者，Rollup / Rolldown 负责模块图，esbuild / SWC / Oxc 更偏单文件处理。这一篇继续沿着这个目标走，不展开 Vite 的完整使用教程，只讲清楚三个会影响工具边界判断的问题：Vite 开发阶段为什么快、依赖预构建解决什么、HMR 为什么和 Webpack 的体验不一样。

这篇只解决一个问题：Vite 的开发体验从哪来

学习 Vite 很容易跑偏。一种跑偏是把它当脚手架教程，讲一堆创建项目、目录结构、插件配置；另一种跑偏是直接扎进源码，讲中间件、模块图和插件容器的实现细节。

这两件事都值得学，但不适合放在这组文章里。这里的目标是建立构建工具链坐标系，所以我更关心：

问题 为什么重要
Vite 开发阶段和构建阶段有什么区别 解释为什么 dev 正常、build 可能出问题
Dev Server 做了什么 解释 Vite 为什么不需要启动前完整打包
依赖预构建为什么存在 解释 no-bundle 为什么不能简单套到 node_modules
HMR 怎么跑起来 解释 Vite 和 Webpack 在热更新粒度上的差异
底层工具各自负责什么 解释 Vite、Rollup、esbuild 的角色边界

我的判断是：如果只是业务开发，会用 Vite 配置就够了；但如果要系统理解构建工具，必须知道 Vite 的快不是魔法，而是它把开发阶段和构建阶段拆成了不同链路。

开发阶段和构建阶段是两条链路

先看最关键的对比：

维度 开发阶段 构建阶段
常见命令 vite / vite dev vite build
核心目标 启动快、更新快 产物小、加载快、适合部署
模块处理方式 no-bundle，按需处理源码模块 bundle，完整处理生产模块图
典型底层角色 Dev Server + 快速转译 Rollup / Rolldown 负责产物组织
产物形态 浏览器直接请求源码模块 URL 输出 dist 静态资源

传统打包器的开发模式通常是：

启动开发服务器
  → 从入口递归分析依赖
  → 生成开发用 bundle
  → 浏览器加载 bundle

应用越大，启动前要处理的模块越多，冷启动自然变慢。

Vite 的开发阶段换了一个前提：现代浏览器已经原生支持 ESM。既然浏览器能自己处理 import，那开发期就不必先把整个应用打成一个 bundle。

启动 Vite Dev Server
  → 浏览器请求 index.html
  → 浏览器继续请求 /src/main.ts
  → 遇到 import，再请求下一个源码模块
  → Vite 按需转译并返回

这就是 Vite 开发期 no-bundle 的核心：启动时不急着处理整个应用，而是浏览器请求哪个模块，Dev Server 才处理哪个模块。

但这里要注意一个边界：no-bundle 主要优化的是开发服务器启动和热更新链路，不代表页面首次访问完全没有成本。大项目首次打开页面时，浏览器仍然要沿着模块依赖图发起很多请求，只是这些请求发生在访问阶段，而不是启动服务器之前。

Dev Server：开发期的模块中转站

Vite Dev Server 不是一个简单的静态文件服务器。它更像开发阶段的模块中转站，浏览器请求什么，它就现场处理什么。

工作 解决的问题
提供 HTTP 服务 让浏览器能访问 index.html、源码模块和静态资源
改写导入路径 把浏览器不认识的裸模块导入改成可请求的 URL
按需转译文件 把 TS、JSX、Vue SFC 等转成浏览器可执行的 JS
维护模块关系 记录谁 import 了谁，为 HMR 做准备
通知浏览器更新 文件变化后通过 WebSocket 触发热更新

比如源码里写：

import { createApp } from 'vue'
import App from './App.vue'

浏览器不能直接理解 'vue' 这种裸模块导入，它只认识 URL。Vite Dev Server 会把导入关系改写成浏览器可以请求的形式，同时在请求 .vue、.ts、.tsx 等文件时做按需转换。

可以把它理解成这样：

浏览器：我要 /src/App.vue
Vite：这个文件浏览器不能直接执行，我先编译一下再返回

浏览器：我要 vue
Vite：这是第三方依赖，我给你指到预构建后的 ESM 文件

这也是 Vite 和 Rollup 的边界之一：开发期主角是 Dev Server，不是 Rollup 在启动时完整打包应用。Rollup / Rolldown 更重要的舞台在生产构建阶段，或者在新架构里承担更统一的模块图处理角色。

依赖预构建：no-bundle 的补丁，不是完整打包

既然 Vite 开发期强调 no-bundle，为什么还要做依赖预构建？

原因很简单：源码模块和第三方依赖不是一类东西。

业务源码通常有这些特点：

  • 改动频繁。
  • 模块数量随项目增长。
  • 开发时希望按需处理，改哪里更新哪里。

第三方依赖通常相反：

  • 改动很少。
  • 可能包含 CommonJS、UMD 等浏览器不能直接执行的格式。
  • 一个包内部可能拆成大量小文件。

所以 Vite 对它们用了两种策略：

对象 开发期策略 原因
业务源码 按需转译，不提前完整打包 保持启动快、热更新粒度细
第三方依赖 预构建并缓存 转成 ESM，减少请求数量

依赖预构建主要解决两个问题。

CommonJS 转 ESM

npm 生态里仍然有很多包不是纯 ESM。比如一个依赖内部可能是：

const dayjs = require('dayjs')

module.exports = dayjs

浏览器原生 ESM 不能直接执行这种格式。Vite 需要把它转换成浏览器可以加载的 ESM。

合并碎片化依赖

有些包内部拆得很细。如果完全交给浏览器逐个请求，开发阶段可能出现大量 HTTP 请求。Vite 会把这类依赖预先合并成一个或少数几个文件，缓存到：

node_modules/.vite/deps/
├── vue.js
├── react.js
├── react-dom_client.js
└── _metadata.json

所以依赖预构建不是和 no-bundle 矛盾，而是让 no-bundle 在真实 npm 生态里可用。

这里也能看出 esbuild 的典型角色。以 Vite 旧架构为例，esbuild 常被用来做依赖预构建和 TS / JSX 等快速转换。它很快，但它不是这个链路里的上层编排者；上层编排仍然是 Vite。

遇到依赖缓存问题时，可以强制重新预构建：

vite --force

或者删除缓存：

rm -rf node_modules/.vite

如果某个动态依赖没有被自动扫到，可以显式声明：

import { defineConfig } from 'vite'

export default defineConfig({
  optimizeDeps: {
    include: ['some-cjs-package'],
  },
})

这类配置不需要一开始就背，但要知道它在调什么：调的是开发期依赖预构建，不是生产构建的代码分割策略。

HMR：模块级更新，而不是重新打整个包

HMR 是 Hot Module Replacement，热模块替换。它的目标不是“刷新得快一点”，而是尽量做到：文件变了，只替换受影响的模块，页面状态不要丢。

先对比一下：

方式 发生了什么 开发体验
live reload 文件变化后整页刷新 状态基本丢失
bundle 级 HMR 更新打包器产出的模块片段 依赖打包器重新计算更新内容
Vite HMR 浏览器重新请求变化的源码模块 更新粒度更贴近源码模块

Vite 的 HMR 大致是：

文件变化
  → Dev Server 监听到变化
  → 根据模块关系判断受影响范围
  → 通过 WebSocket 通知浏览器
  → 浏览器重新请求变化模块
  → HMR runtime 执行局部替换

这里有两个关键点。

第一，Vite 开发期没有先把整个应用打成 bundle，所以变化发生后，不需要重新生成一个大 bundle。浏览器可以直接重新请求变动的源码模块。

第二，局部更新需要边界。一个模块能不能被热替换，要看有没有地方能“接受”这次更新。

普通模块可以手动写：

export const state = { count: 0 }

if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    console.log('state 模块已更新', newModule?.state)
  })
}

实际业务里我们很少手写这段，因为 Vue、React、Svelte 等框架插件已经帮组件建立了 HMR 边界。所以你改组件时通常能局部更新，改入口文件、路由初始化、全局副作用模块时，可能就会退化成整页刷新。

我的理解是：HMR 体验好不好，不只取决于“工具快不快”，还取决于模块边界是否清晰、框架插件是否能正确接住更新。

为什么 Vite 开发正常，build 后可能出问题

很多 Vite 问题都来自一个事实：开发链路和构建链路不完全一样。

开发阶段：

浏览器 ESM
  + Dev Server 按需转译
  + 依赖预构建缓存
  + HMR runtime

构建阶段：

从入口生成完整模块图
  → Tree Shaking
  → 代码分割
  → CSS 抽取
  → 压缩
  → 输出 dist

这两条链路关注点不同，所以这些问题经常只在 build 后暴露：

问题类型 为什么 dev 不一定暴露
Tree Shaking 误删 开发期通常不做完整生产级 Tree Shaking
动态导入路径异常 构建期需要静态分析和分块
资源路径错误 生产环境有 base、hash、目录结构变化
依赖格式问题 预构建和生产构建处理依赖的链路不同
插件行为差异 插件可能区分 serve 和 build 两种模式

所以排查 Vite 问题时，我会先问一句：这是 dev 问题，还是 build 问题？

如果是线上相关问题，不要只看开发服务器，至少跑一遍：

vite build
vite preview

preview 不是开发服务器，它只是把构建后的 dist 在本地起一个静态服务，更接近线上访问方式。

和 Webpack 的关键差异

后面会单独讲 Webpack，这里先给一个轻量对照，方便建立边界。

维度 Vite 开发期 Webpack 典型开发期
核心模型 no-bundle，浏览器按需请求 ESM bundle，从入口生成模块图并打包
启动成本 主要和启动 Dev Server、预构建依赖有关 通常和应用模块规模关系更强
更新粒度 更贴近源码模块 更贴近打包器内部模块
生态边界 现代 ESM、Vite 插件、Rollup 风格构建配置 loader / plugin 生态非常厚
适合场景 新项目、现代前端应用、开发体验优先 存量复杂项目、深度定制构建链路、历史生态依赖重

这不是说 Vite 一定比 Webpack 高级，而是二者的基础模型不同。

Vite 的优势来自现代浏览器 ESM 和更轻的开发链路；Webpack 的优势来自多年积累的生态和极强的可定制性。很多老项目里，Webpack 仍然是更稳的选择，尤其是依赖复杂 loader、老旧模块格式、微前端历史方案或内部构建平台深度绑定时。

这篇在整个系列里的位置

回到构建工具链坐标系，这篇只需要留下几个关系：

Vite
├── 开发期：Dev Server + 浏览器 ESM + 依赖预构建 + HMR
├── 构建期：Rollup / Rolldown 处理生产模块图
└── 快速引擎：esbuild / Oxc 等负责部分单文件处理

它不是 Vite 使用大全，也不是源码分析小册。更细的 Vite 配置、插件开发、SSR、框架集成、生产优化，可以放到单独的小册里讲。这里先把“为什么 Vite 是上层编排者”这件事坐实。

后面讲 Rollup 时，就重点看插件机制和构建流程；讲 Webpack 时，就重点看 entry、output、loader、plugin、chunk 这些共性概念；讲 esbuild / SWC / Babel 时，再回到单文件转译和兼容性策略。

小结

  1. Vite 开发期和构建期是两条不同链路，dev 正常不代表 build 一定正常。
  2. Dev Server 是开发期模块中转站，核心是按需处理源码模块，而不是启动前完整打包。
  3. 依赖预构建是 no-bundle 在 npm 生态里的必要补丁，主要解决 CJS 转 ESM 和请求数量问题。
  4. Vite HMR 更贴近源码模块更新，体验依赖模块边界和框架插件能否接住变化。
  5. Vite 和 Webpack 的关键差异不是配置语法，而是 no-bundle 与 bundle 两种开发模型。
  6. 在整个工具链坐标系里，Vite 负责编排，Rollup / Rolldown 负责模块图，esbuild / Oxc 等快引擎负责部分单文件处理。
