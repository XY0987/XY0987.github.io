组件库构建（一）：多产物矩阵与类型产物

发表于2026|更新于2026|工程化
|字数总计:2.6k|阅读时长:9分钟

前言：网上讲组件库构建，翻来覆去就是「ESM/CJS/类型/样式四件套」。但真到发一个正经组件库，四件套只是起点。这一篇专门讲两个被讲烂了却没讲透的点：多产物矩阵（到底要不要出 UMD/IIFE、什么时候出）和类型产物（.d.ts 为什么要打包、Project References 在库构建里到底放哪）。库构建工具（tsup/unbuild/Vite lib）本身在「库构建与脚本运行工具链」那篇讲过，这里不重复用法，只讲取舍。

先想清楚：产物是给谁用的

选产物格式之前，先问一个问题：你的组件库会被谁、以什么方式消费？

组件库的消费场景其实就三类：

消费场景 加载方式 需要的产物
现代前端项目（Vite/webpack） import ESM
老项目 / Node SSR / Jest（旧） require CJS
<script> 直接引、CDN、无构建 全局变量 UMD 或 IIFE

想清楚这三类里你真正要覆盖谁，产物矩阵就出来了。不要因为「别的库都出了」就把四种格式全出一遍——每多一种格式，都是构建时间、包体积、维护心智的成本。

四种格式到底是什么、什么时候触发

ESM 和 CJS 大家都熟，重点说说被忽略的 UMD 和 IIFE，因为它们的差别很多人分不清。

ESM：默认且首选

现代打包器（Vite、webpack、Rollup）和现代 Node 都原生支持 ESM。更关键的是，只有 ESM 的静态结构才能被 Tree Shaking（这点在「Tree Shaking、副作用与代码分割」那篇讲过）。组件库要能被按需引入，ESM 是硬前提。

结论：ESM 是任何组件库都非常必要出的格式。

CJS：看兼容需求，正在退场

CJS 的存在意义是照顾 require 的场景：老 webpack 项目、部分 Node SSR、旧版本 Jest。

我的判断是：CJS 是「兼容格式」，不是「必需格式」。如果你的目标用户都是 Vite / Vue 3 / React 18+ 这类现代技术栈，可以考虑只发 ESM。但现实里大多数面向公众的组件库还是会带上 CJS，因为你不知道用户的构建环境有多老。

出 CJS 时务必记住「双包陷阱」——组件库通常无状态（组件是函数/类，不维护模块级可变状态），风险比工具库小，但仍要保证 ESM 和 CJS 共享同一份实现。这在「exports 条件导出与双包陷阱」那篇有完整讲解。

UMD：给「无构建环境」的一份自执行产物

UMD（Universal Module Definition）是一段「见人下菜碟」的包装代码：检测当前环境，有 CommonJS 就走 module.exports，有 AMD 就走 define，都没有就挂到全局变量（如 window.MyUI）。

// UMD 产物的大致结构（简化）
(function (global, factory) {
  if (typeof exports === 'object' && typeof module !== 'undefined')
    factory(exports, require('vue'))        // CommonJS
  else if (typeof define === 'function' && define.amd)
    define(['exports', 'vue'], factory)     // AMD
  else
    factory(global.MyUI = {}, global.Vue)   // 挂全局
})(this, function (exports, vue) { /* ... */ })

它的主要触发场景是：用户不走构建工具，直接在 HTML 里 <script src="https://cdn/my-ui.umd.js">，然后用 window.MyUI 访问。CDN 引入、CodePen一些老的后台系统都属于这类。

关键取舍：UMD 产物是全量的、不能 Tree Shaking 的。因为它是一个自执行的整包，用户拿到的是整个组件库。所以 UMD 只适合「快速试用 / CDN 引入」，不适合作为项目里的正式依赖。

如果你的组件库需要支持 CDN 引入（比如给不懂构建的用户试用），出一份 UMD；否则完全可以不出。

IIFE：比 UMD 更纯粹的「只挂全局」

IIFE（立即执行函数表达式）比 UMD 更简单：它不做环境检测，直接把库塞进一个自执行函数，结果挂到全局变量。

var MyUI = (function (vue) { /* ... */ return exports })(Vue)

它和 UMD 的区别：

格式 兼容 CommonJS/AMD 只挂全局 体积 适合
UMD 是 也能 稍大（多了检测代码） 不确定用户环境，最大兼容
IIFE 否 是 更小 明确就是 <script> 挂全局

现实里，如果你已经出了 ESM/CJS 给构建工具用，那给 CDN 场景补的那一份，用 IIFE 就够了，比 UMD 更小更干净。UMD 和 IIFE 通常二选一，没必要都出。

一个务实的产物矩阵

给个我认为合理的默认值：

// tsup.config.ts
import { defineConfig } from 'tsup'

export default defineConfig([
  // 给构建工具用：ESM + CJS，可 Tree Shaking，保留 external
  {
    entry: ['src/index.ts'],
    format: ['esm', 'cjs'],
    dts: true,
    external: ['vue'],
    clean: true,
  },
  // 给 CDN 用：一份全量 IIFE（把 vue 当全局变量）
  {
    entry: ['src/index.ts'],
    format: ['iife'],
    globalName: 'MyUI',
    minify: true,
    external: ['vue'],
    outExtension: () => ({ js: '.global.js' }),
  },
])

大多数只在项目里被 import 的组件库，其实第一份就够了。第二份 IIFE 是「你确实要支持 CDN」时才加。

类型产物：不只是「生成 d.ts」

四件套里的「类型」，很多人以为就是 tsc --emitDeclarationOnly 生成一堆 .d.ts 就完事了。组件库的类型产物有几个深水区。

为什么要「打包」d.ts，而不是散着发

直接 tsc 生成的 .d.ts 是和源码一一对应的多个文件：Button.d.ts、utils.d.ts、internal/xxx.d.ts……它们之间还互相 import。

散着发有两个问题：

  1. 暴露内部结构：用户能从类型里看到你的内部文件路径，甚至 IDE 会提示 import 内部模块。
  2. 类型解析慢、易断链：几十上百个 .d.ts 互相引用，用户项目的 TS Server 要挨个解析；一旦某个内部引用路径没对上，类型就「断」了，用户看到 any。

所以正经组件库会把类型**打包（bundle）成一个（或按入口若干个）.d.ts**，把内部实现的类型内联进来，只留公共 API。

工具选择：

工具 类型打包能力 说明
tsup --dts 内置（底层用 rollup-plugin-dts） 最省事，大多数库首选
unbuild declaration: true 内置 UnJS 风格，同样开箱即用
rollup-plugin-dts 专门做 d.ts 打包 手写 Rollup 配置时用
vite-plugin-dts Vite lib mode 下补类型 Vite 生态组件库常用，支持 rollupTypes: true 合并

rollup-plugin-dts 是这几个工具背后的核心——它能把多个 .d.ts 合并成一个，并把内部类型内联。tsup、unbuild 只是把它封装好了。

坑：tsup 的 --dts 生成类型是把整个类型图重新用 rollup-plugin-dts 走一遍，大型组件库这一步会很慢（有时比出 JS 还慢几倍）。一个实用优化是把「出 JS」和「出类型」拆成两个任务并行，或者用 tsc -b 增量出散装类型 + 单独一步合并，别让类型拖慢整个构建。

exports 里的 types 条件导出

类型文件生成好了，还要让 TypeScript 找得到。这靠 exports 里的 types 条件——而且它必须放在每个入口的最前面：

{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./button": {
      "types": "./dist/button.d.ts",
      "import": "./dist/button.mjs",
      "require": "./dist/button.cjs"
    }
  }
}

为什么 types 要放最前？因为条件导出是按顺序匹配、命中即止的。TypeScript 解析类型时会找 types 条件，如果它排在 import/require 后面，某些解析策略下会先命中 import 拿到 .mjs（不是类型文件），导致类型丢失。记住这个顺序：types 永远第一，default 永远最后。

还有一个现代 TS 特有的坑：如果用户的 tsconfig 设了 "moduleResolution": "bundler" 或 "node16"，TS 会严格按 exports 找类型，不再退回老的「同目录找同名 .d.ts」逻辑。这时候如果你只写了 main/types 顶层字段却没在 exports 里配 types，现代用户就会报「找不到类型声明」。所以：**有 exports 就一定要在里面配 types**。

可以用官方工具自查：

npx @arethetypeswrong/cli --pack .

@arethetypeswrong/cli（arethetypeswrong）会模拟各种 moduleResolution 检查你的类型导出是否都能被正确解析，发库前跑一下能拦掉一大类「类型找不到」的问题。

Project References 在库构建里的位置

Monorepo 那篇讲过用 tsc -b + Project References 做全仓增量类型检查。这里要澄清一个常见误解：Project References 是给「类型检查」和「多包增量编译」用的，不是给「出发布产物」用的。

具体到组件库：

  • 类型检查 / CI 卡口：用 tsc -b 走 Project References，只重新检查改动的包及其下游，快。
  • **生成发布用的 .d.ts**：用 tsup --dts / rollup-plugin-dts 把类型打包成干净的单文件。

两者是两条线，别混。我见过有人试图直接把 tsc -b 输出的散装 .d.ts 当发布产物，结果就是上面说的「暴露内部结构 + 类型易断链」。正确姿势是：

tsc -b            →  开发/CI 阶段，增量类型检查（不产出发布物）
tsup --dts        →  构建阶段，产出打包后的单一 .d.ts（发布物）

一个组件库的 package.json 脚本大致会长这样：

{
  "scripts": {
    "typecheck": "tsc -b",
    "build": "tsup",
    "build:check": "tsc -b && tsup"
  }
}

typecheck 用 references 快速验类型，build 出真正干净的产物，职责分明。

小结

  1. 选产物格式前先想清楚「谁来消费」：构建工具用 ESM/CJS，无构建环境用 UMD/IIFE。
  2. ESM 是任何组件库的必需格式，也是 Tree Shaking 的前提；CJS 是兼容格式，可按用户群体取舍。
  3. UMD 做环境检测、最大兼容，IIFE 只挂全局更精简；面向 CDN 时二选一，且它们不可 Tree Shaking。
  4. .d.ts 要打包成单文件，避免暴露内部结构和类型断链，工具用 tsup --dts / rollup-plugin-dts。
  5. exports 里 types 条件必须放每个入口最前面；有 exports 就必须配 types，否则现代 TS 找不到类型。
  6. Project References + tsc -b 负责类型检查与增量，不负责产出发布物；发布用的 .d.ts 由打包工具生成，两条线别混。
  7. 发库前用 @arethetypeswrong/cli 自查类型导出，能拦掉一大类类型解析问题。
