前端性能优化实战：H5 与小程序的排查思路与方法论

发表于2026|更新于2026|项目
|字数总计:7.1k|阅读时长:26分钟

先问一个问题：什么时候该做性能优化？

性能优化是一门关于投入产出比的生意，不是一项工程洁癖。

举两个我自己之前听到的反差案例：

案例 A：付款页面

假设有一个付款页，99% 的用户体验已经很流畅了，只有 1% 的用户因为设备老旧、弱网等原因，付款流程慢到转化率明显下降。

很多人会说：99% 都 OK 了，那 1% 没必要。我的看法恰好相反——这 1% 非常值得优化。付款页直接挂钩 GMV，1% 用户流失对应的是真金白银的损失。哪怕只做 接口超时重试、骨架屏，ROI 都是正的。

案例 B：薅羊毛活动页

同样一个页面，从 2s 优化到 100ms。听起来好像不错。但这是一个”领现金红包”的活动页——用户的心理预期是：只要能领到，等 2s 也愿意等。

优化前后数据对比：转化率没有明显变化，领取数没有明显变化，留存也没变。这种情况下，即使技术上做得再漂亮，这次优化就是没必要的。

所以我的判断标准很简单：

性能优化的前提，是先确认优化有业务收益。没有收益的技术自嗨，不如把时间花在别的地方。

具体判断可以参考这个顺序：

  1. 先定位业务价值：这个页面的核心指标是什么（转化、留存、时长、GMV）？性能差是不是在影响它？
  2. 再看用户分布：问题影响多少用户？这些用户的权重够不够（比如付费用户权重肯定比白嫖用户高）？
  3. 最后算成本： 投入成本，能不能被预期的业务收益覆盖？

性能问题的排查思路

排查性能问题，最怕的是上来就猜。”是不是首屏资源太大了？””是不是接口慢？”——猜得再准，也不如先把整条链路摊开，看哪一段最耗时。

我的思路是自上而下、按时间轴定位：先看用户从点击到页面渲染成功这整条链路里，哪一段是大头，再到那一段里面去看细节数据，最后动手改。

第一步：把整条链路画出来

一个 H5 页面从”用户点击”到”看到内容并能交互”，中间其实有非常多阶段。很多人只盯着”前端渲染”，但耗时最大的往往不在那。

每一段都有自己的特征耗时和典型问题，先不看数据，你可以先做一个心里的预估：这个页面如果慢，最可能卡在哪一段？然后再拿数据验证假设。

第二步：拿数据确认”耗时大头”在哪一段

对应上面这条链路，前端能拿到的数据主要来自 PerformanceNavigationTiming 和 PerformanceObserver。
以下是一个诊断脚本：

// 页面加载完成后执行
window.addEventListener('load', () => {
  const nav = performance.getEntriesByType('navigation')[0]
  if (!nav) return

  const stages = {
    '重定向':       nav.redirectEnd - nav.redirectStart,
    'DNS':          nav.domainLookupEnd - nav.domainLookupStart,
    'TCP':          nav.connectEnd - nav.connectStart,
    'TLS':          nav.connectEnd - (nav.secureConnectionStart || nav.connectEnd),
    '请求(TTFB)':   nav.responseStart - nav.requestStart,
    'HTML 下载':    nav.responseEnd - nav.responseStart,
    'DOM 解析':     nav.domContentLoadedEventStart - nav.responseEnd,
    '资源加载':     nav.loadEventStart - nav.domContentLoadedEventEnd,
  }
  console.table(stages)
})

跑一次 console.table，哪一段数字大，哪一段就是先要动的地方。然后按”大头”所属的层，进一步细化：

如果大头在… 去哪里看细节 常见根因
DNS / TCP / TLS Network 面板的 Timing Tab 没有用 HTTP/2、CDN 选址不好、没有 preconnect
TTFB 后端日志 + CDN 命中率 服务端处理慢、缓存没命中、没走 CDN
HTML 下载 看 HTML 大小 SSR 返回内容过大、没开 gzip/brotli
资源加载 Network 瀑布流 资源串行阻塞、首屏 JS 过大、字体阻塞
DOM 解析 / JS 执行 Performance 面板 Main 轨道 长任务、hydration 卡顿、第三方脚本
接口耗时 Network 面板 + 后端 trace 接口串行、无并行、接口本身慢
交互响应 Performance 面板 Interactions INP 高、点击事件里有重计算

第三步：针对大头做最小化验证

找到大头以后，一次只改一件事，避免改一堆再来对比。原因很简单——如果一次改了五个地方数据变好了，你并不知道是哪个改动真正有效，也没法复用到其他页面。

最小化验证的流程：

  1. 建立基线：当前这段耗时的 p50/p75/p95 分别是多少
  2. 只改一个点，灰度或 AB 放量
  3. 对比同段耗时的分布，看是不是显著下降
  4. 确认无业务回退后全量

第四步：回到业务指标看收益

技术指标下降，不代表业务就一定好。优化完之后一定要回看一次文章开头提到的那件事：

  • 付款页优化 → 看支付成功率、GMV
  • 列表页优化 → 看 CTR、停留时长
  • 活动页优化 → 看领取率、分享率

如果业务指标没动，那这次优化要么方向不对，要么用户本来就不 care 这点耗时。不管哪种，都比”自嗨”强——你拿到了真实反馈。

小程序的链路差异

小程序的链路和 H5 大体类似，但多了几个特有环节，排查时要重点看：

启动 → 代码包下载（冷启首次） → 代码注入 → App.onLaunch
     → 首页 onLoad → 首次 setData → 渲染层绘制 → onReady

几个特有的耗时点：

  • 代码包下载：主包大小直接决定冷启耗时，分包是关键
  • 代码注入：包越大，JSCore 注入越慢
  • setData 通信：双线程架构下，这是最容易被忽视的大头
  • 渲染层绘制：WXML 层级过深、自定义组件过多都会拖慢

微信开发者工具的 Performance 面板和真机 Trace 能把这几段都打出来，基础库 2.11.0+ 就支持。

H5 性能优化的常用手段

1. 首屏相关：FCP / LCP 优化

资源优先级

HTML 里的 <link rel="preload"> 和 fetchpriority 属性，可以让浏览器优先加载首屏关键资源：

<!-- 首屏关键图片，高优先级 -->
<link rel="preload" href="/hero.webp" as="image" fetchpriority="high">

<!-- 首屏关键字体 -->
<link rel="preload" href="/font.woff2" as="font" type="font/woff2" crossorigin>

注意 fetchpriority 是 Chrome 101+ 才支持的，老版本浏览器会忽略，属于渐进增强。

图片格式与懒加载

  • 首屏图用 WebP/AVIF（比 JPEG 小 30%-50%）
  • 非首屏图用 loading="lazy"（浏览器原生懒加载，不用自己写 IntersectionObserver）
<img src="/banner.webp" alt="banner" fetchpriority="high">
<img src="/list-item.webp" alt="item" loading="lazy">

响应式图片：srcset / sizes

同一张图在手机和桌面端加载一样大的分辨率是浪费。srcset 让浏览器根据屏幕 DPR 和视口宽度自动挑合适的尺寸：

<!-- 根据设备像素密度选择 -->
<img src="/banner.webp"
     srcset="/banner.webp 1x, /banner@2x.webp 2x, /banner@3x.webp 3x"
     alt="banner">

<!-- 根据视口宽度选择（配合 sizes） -->
<img src="/banner-800.webp"
     srcset="/banner-400.webp 400w,
             /banner-800.webp 800w,
             /banner-1600.webp 1600w"
     sizes="(max-width: 600px) 100vw, 50vw"
     alt="banner">

在 Retina 手机上直接能省一半带宽，首屏 LCP 图尤其值得做。

首屏占位

图片还没到之前，留白会让页面显得”空”，也容易被用户当成”没加载出来”。业界有两种主流占位方式：

  • LQIP（Low Quality Image Placeholder）：先加载一张极小的低质图（比如 10-20px 宽的缩略图），用 CSS blur 拉伸铺满，大图到了再替换
  • BlurHash：把图片编码成一段 20-30 字节的字符串存进接口响应，前端解码出一张模糊色块图，体积比 LQIP 再小一个数量级
<div class="img-wrap" style="background-image: url(data:image/jpeg;base64,/9j/...)">
  <img src="/real.webp" onload="this.parentNode.classList.add('loaded')">
</div>

Instagram、Medium 用的就是这套思路，配合 width/height 占位，CLS 和首屏观感都能顾到。

关键 CSS 内联

如果 CSS 文件是外链的，浏览器必须下载并解析完 CSSOM 才能开始渲染——这就是所谓的”CSS 阻塞渲染”。对首屏体验影响很大，尤其在弱网下。

做法是：把**首屏真正用到的 CSS 抽出来直接内联到 HTML 的 <head>**，剩余样式异步加载：

<head>
  <!-- 首屏关键样式，直接内联，零 RTT -->
  <style>/* 由构建工具抽取的 critical css */</style>

  <!-- 非关键样式异步加载，不阻塞渲染 -->
  <link rel="preload" href="/main.css" as="style" onload="this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="/main.css"></noscript>
</head>

工具链上，critters（Next.js 默认集成）、critical、penthouse 都可以自动化抽取。用了之后 FCP 通常能提 100-300ms。

代码分割

路由级别做 dynamic import，避免一次性加载所有页面的 JS：

// ❌ 一次性全部打包进主 bundle
import UserCenter from './pages/UserCenter'

// ✅ 路由懒加载，按需加载
const UserCenter = () => import('./pages/UserCenter')

构建产物优化：Tree Shaking、Polyfill 按需、externals

首屏 JS 超标的锅，大多不在业务代码，而在依赖和构建配置。上线前必做的几件事：

  • 产物可视化：Webpack 用 webpack-bundle-analyzer，Vite 用 rollup-plugin-visualizer。打出 treemap 一看，经常能发现”lodash 全量引入占 70KB”、”moment.js 带了所有 locale 文件 200KB”这类问题
// vite.config.js
import { visualizer } from 'rollup-plugin-visualizer'
export default {
  plugins: [visualizer({ open: true, gzipSize: true })]
}
  • Tree Shaking / 依赖裁剪：确保依赖库提供 ESM 入口（package.json 里有 "module" / "sideEffects": false）。

常见坑：

  • import _ from 'lodash' → 改成 import debounce from 'lodash-es/debounce' 或用 lodash.debounce 子包

  • moment → 换成 dayjs（2KB vs 70KB）

  • antd 按需引入用 babel-plugin-import，或直接升级到 v5（天然支持 Tree Shaking）

  • Polyfill 按需：用 @babel/preset-env + useBuiltIns: 'usage' + browserslist，只注入目标浏览器真正缺的 polyfill。

// .browserslistrc —— 决定 polyfill 和语法降级的边界
> 0.5%
last 2 versions
not dead
not IE 11
  • CDN 外链：React、Vue、ECharts 这种通用大库可以不打进 bundle，直接用 CDN 的 UMD 包，利用跨站缓存命中。Webpack 配 externals，HTML 里加 <script> 引用：
// webpack.config.js
module.exports = {
  externals: {
    react: 'React',
    'react-dom': 'ReactDOM',
    echarts: 'echarts'
  }
}

<script src="https://cdn.jsdelivr.net/npm/react@18/umd/react.production.min.js"></script>

注意 CDN 外链要配 SRI（子资源完整性校验）防止被篡改，大厂一般会走自建 CDN。

2. 运行时：INP / 卡顿优化

INP（Interaction to Next Paint）是 2024 年 3 月 Google 正式用来替代 FID 的核心指标，衡量交互响应的整体延迟。

INP 高的根因通常是：主线程长任务阻塞了事件处理。

常见的优化手段：

拆分长任务

// ❌ 一次性处理 10000 条数据，主线程直接卡死
function processList(list) {
  list.forEach(item => heavyWork(item))
}

// ✅ 切片调度，每帧处理一部分
function processListChunked(list) {
  let i = 0
  function runChunk() {
    const deadline = performance.now() + 5  // 每片 5ms
    while (i < list.length && performance.now() < deadline) {
      heavyWork(list[i++])
    }
    if (i < list.length) {
      // 如果支持 scheduler.yield()，优先用它；否则降级到 setTimeout
      if (typeof scheduler !== 'undefined' && scheduler.yield) {
        scheduler.yield().then(runChunk)
      } else {
        setTimeout(runChunk, 0)
      }
    }
  }
  runChunk()
}

这里用到的 scheduler.yield() 是较新的 API（Chrome 129+），它比 setTimeout(fn, 0) 的优先级更高，能更快回到原任务。

防抖与节流：控制高频事件的执行频率

input、scroll、resize、mousemove 这类事件一秒能触发几十上百次。如果里面做了接口请求或重计算，INP 会瞬间飙升。

  • 防抖（debounce）：连续触发时只执行最后一次——适合搜索框联想、表单校验
  • 节流（throttle）：固定间隔内最多执行一次——适合滚动监听、按钮防连点
// 防抖：用户停止输入 300ms 后才发请求
searchInput.addEventListener('input', debounce((e) => {
  fetchSuggestions(e.target.value)
}, 300))

// 节流：滚动时最多每 100ms 算一次
window.addEventListener('scroll', throttle(() => {
  updateStickyHeader()
}, 100), { passive: true })

两个小细节经常被忽略：

  1. addEventListener 的 passive: true 告诉浏览器**这个监听器不会调用 preventDefault()**，浏览器就不用等 JS 执行完再滚动，滚动流畅度立竿见影
  2. 用 lodash-es 的 debounce/throttle 就行，自己手写容易漏掉 cancel、flush 这些边界场景

虚拟列表：长列表的标准解

一屏渲染一万条 DOM，内存和渲染都会崩。虚拟列表的思路是只渲染视口内的几十条节点，滚动时回收复用。

React 侧有 react-window、react-virtuoso，Vue 侧有 vue-virtual-scroller，原生也可以用 CSS 的 content-visibility: auto 做轻量版：

/* 视口外的节点浏览器自动跳过渲染，几乎零成本 */
.list-item {
  content-visibility: auto;
  contain-intrinsic-size: auto 80px;  /* 预估高度，避免滚动条抖动 */
}

content-visibility 是 Chrome 85+ 的特性，不适合交互复杂的场景，但做静态长文章、Feed 流非常合适，一行 CSS 就能把渲染耗时砍掉 70%+。

事件委托：别给每个节点都挂监听

列表里 1000 个 item，每个都绑 click 监听，不仅占内存，还会拖慢渲染。正确做法是把监听器绑在父节点，用 event.target 判断：

// ❌ 每个 item 都挂一个监听器
items.forEach(item => {
  item.addEventListener('click', handleClick)
})

// ✅ 只在父节点挂一个
list.addEventListener('click', (e) => {
  const item = e.target.closest('.list-item')
  if (!item) return
  handleClick(item.dataset.id)
})

React/Vue 这类框架已经帮你做了事件委托（所有事件都代理到 root 或 document），但你手写的原生 DOM 操作、第三方组件库的事件还是要自己注意。

Web Worker 处理重计算

加解密、大数据 JSON 解析、复杂计算，都应该扔到 Worker 里：

// main.js
const worker = new Worker('./compute.js')
worker.postMessage({ type: 'decrypt', data: payload })
worker.onmessage = (e) => {
  render(e.data.result)
}

// compute.js
self.onmessage = (e) => {
  if (e.data.type === 'decrypt') {
    const result = heavyDecrypt(e.data.data)
    self.postMessage({ result })
  }
}

3. 渲染优化：CLS 与重排

CLS 的常见成因：图片/广告/异步组件没占位，加载后把已有内容”挤”下去。

解决方案很简单但经常被忽略——给所有异步内容预留占位高度：

<!-- ❌ 图片加载前高度为 0，加载后撑开，CLS 爆炸 -->
<img src="/banner.webp" alt="">

<!-- ✅ 显式声明宽高，浏览器预留空间 -->
<img src="/banner.webp" alt="" width="750" height="400">

广告、弹窗等动态插入的内容，尽量用 position: absolute 或固定容器高度。

避免重排（reflow）与重绘（repaint）

CLS 是”视觉稳定性”，重排重绘则是”滚动/动画流畅度”。两者成因不同，但都属于渲染优化。

重排（改变几何属性，如宽高、位置）比重绘（改变颜色、背景）贵得多，一次重排可能会级联影响整棵渲染树。常见翻车姿势：

// ❌ 强制同步布局（forced synchronous layout / layout thrashing）
// 循环里交替读写 DOM，每次读都要触发一次重排来拿最新值
for (let i = 0; i < items.length; i++) {
  const height = items[i].offsetHeight          // 读：触发重排
  items[i].style.height = (height + 10) + 'px'  // 写：标记为 dirty
}

// ✅ 先批量读，再批量写
const heights = items.map(el => el.offsetHeight)
items.forEach((el, i) => el.style.height = (heights[i] + 10) + 'px')

动画层面的原则是**只改 transform 和 opacity**，这两个属性走的是合成层（compositor），不触发 layout 和 paint，能稳稳跑 60fps：

/* ❌ 改 left/top，每帧都重排 */
.move { transition: left 0.3s; }

/* ✅ 改 transform，只走合成层 */
.move { transition: transform 0.3s; }

/* 对频繁动画的元素提升为独立合成层 */
.animating { will-change: transform; }

/* 对独立模块用 contain 隔离布局影响 */
.card { contain: layout paint; }

will-change 别滥用——它会消耗 GPU 内存，用完记得改回 auto。

4. 网络优化：从连接层到接口层

网络优化是个被低估的方向。前端同学经常只盯着 JS 体积和首屏渲染，但链路图那节已经说过——DNS、TCP、TLS 这几段如果慢，首字节都没到，前端再快也没用。尤其在弱网和海外场景下，连接建立的耗时经常比传输本身还大。

按从底到上的顺序整理：

1）DNS：预解析 + HttpDNS

一次 DNS 解析在国内 4G 网络下平均约 20-100ms，海外甚至能到几百毫秒。优化手段：

<!-- 对首屏即将请求的第三方域名做 DNS 预解析 -->
<link rel="dns-prefetch" href="//api.example.com">

<!-- preconnect 更进一步：同时完成 DNS + TCP + TLS -->
<link rel="preconnect" href="https://api.example.com" crossorigin>

dns-prefetch 只做 DNS，成本极低；preconnect 把整个连接握手都提前了，效果更好但资源占用也更大，只用在首屏真正会请求的关键域名上，别 preconnect 一堆。

2）TCP / TLS：减少握手次数

一次完整的 HTTPS 建连要经过：TCP 3 次握手 + TLS 握手（TLS 1.2 是 2-RTT，TLS 1.3 是 1-RTT）。在 100ms 延迟的网络下，光握手就要 400ms。优化方向：

  • 升级到 HTTP/2：同域名下多路复用，一个连接复用给所有资源，不再受浏览器”每域名 6 个并发”限制
  • 升级到 TLS 1.3：握手从 2-RTT 降到 1-RTT，还支持 0-RTT 会话恢复
  • 减少域名分片：以前为了突破并发限制会把资源分散到 cdn1/cdn2/cdn3，在 HTTP/2 时代反而变成负优化——每个域名都要重新握手
  • **HTTP/3 (QUIC)**：基于 UDP，真正的 0-RTT 建连，移动端切网（Wi-Fi ↔ 4G）也不会断，腾讯视频、B 站等已经在用

3）CDN：把内容推到离用户最近的地方

这个不展开讲，但有几个常被忽视的点：

  • 接口类响应（动态内容）也可以走 CDN 动态加速，利用边缘节点的回源优化
  • CDN 的 Cache-Key 配置要对，别让无关参数（比如 ?t=时间戳）把缓存击穿
  • 边缘计算（Cloudflare Workers、EdgeOne Pages 等）可以把一些简单接口直接下放到 CDN 节点

4）传输压缩

Brotli 比 gzip 平均多压缩 15%-20%。现代浏览器基本都支持，文本类资源（HTML/JS/CSS/JSON）都应该开：

# Nginx 配置示例
brotli on;
brotli_types text/plain text/css application/json application/javascript;
brotli_comp_level 4;  # 压缩级别 1-11，4-6 性价比最高

注意只压缩文本，图片、视频这类已经压缩过的二进制别重复压，浪费 CPU 没收益。

5）资源提示：让浏览器提前准备

除了前面提到的 dns-prefetch 和 preconnect，还有：

<!-- 当前页面一定会用到的资源，提前下载 -->
<link rel="preload" href="/critical.js" as="script">

<!-- 预测下一个页面可能用到的资源，空闲时下载 -->
<link rel="prefetch" href="/next-page.js">

preload 是”当前页面马上用”，优先级高；prefetch 是”下个页面可能用”，浏览器空闲才去拉。别混用。

6）接口层（应用层）

底层都优化好之后，再看应用层：

  • 并行而非串行：多个无依赖接口用 Promise.all，别写成 await A; await B
  • 接口聚合 / BFF：首屏多个小接口合并成一个，弱网下尤其重要（每个接口都省一次建连成本）
  • HTTP 缓存：静态资源配 Cache-Control: max-age=31536000, immutable，搭配文件名 hash
  • 预请求：用户进入页面的高概率接口（比如 tab 切换、下一页列表），可以在空闲时预请求

7）Service Worker：离线缓存与二次打开秒开

HTTP 缓存受制于浏览器策略，控制粒度粗；Service Worker 相当于前端自己的一层可编程网络代理，能把缓存策略完全掌握在自己手里。典型收益：

  • 二次打开秒开：HTML/JS/CSS 命中 SW 缓存，零网络请求
  • 弱网/断网可用：接口降级到缓存兜底，不至于白屏
  • 静默更新：后台拉新版本，用户下次打开自动切换

主流方案直接用 Google 的 Workbox，策略几行就够：

// sw.js
import { registerRoute } from 'workbox-routing'
import { CacheFirst, StaleWhileRevalidate } from 'workbox-strategies'

// JS/CSS：缓存优先，离线也能用
registerRoute(
  ({ request }) => ['script', 'style'].includes(request.destination),
  new CacheFirst({ cacheName: 'static-v1' })
)

// 接口：先用缓存秒出，同时后台更新
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/'),
  new StaleWhileRevalidate({ cacheName: 'api-v1' })
)

小程序性能优化的关键点

小程序和 H5 的架构不一样。小程序是双线程模型：逻辑层（JSCore）和渲染层（WebView）通过 Native 桥接通信。

┌──────────────────┐          ┌──────────────────┐
│   逻辑层（JS）    │  <──→   │   渲染层（WebView）│
│  (业务代码运行)    │  Native │    (WXML/WXSS)   │
└──────────────────┘          └──────────────────┘
            每次通信都有成本 (setData)

这个架构决定了小程序性能优化的核心矛盾是：setData 的调用频率和数据量。

1. setData 是性能的生死线

每次 setData 都会经历：JS 序列化 → Native 桥 → WebView 反序列化 → diff → 渲染。频繁 setData 或一次性 setData 巨大数据都会卡顿。

// ❌ 高频 setData（比如 scroll 事件里）
Page({
  onPageScroll(e) {
    this.setData({ scrollTop: e.scrollTop })  // 滚动一次触发几十次
  }
})

// ✅ 节流 + 必要性判断
Page({
  onPageScroll(e) {
    const top = e.scrollTop
    // 只在需要控制显示/隐藏时才 setData
    const shouldShow = top > 100
    if (shouldShow !== this.data.showBackTop) {
      this.setData({ showBackTop: shouldShow })
    }
  }
})

官方在 小程序性能优化指引 里明确建议：单次 setData 的数据量不超过 256KB。

2. 长列表用 recycle-view

原生 <scroll-view> 滚动长列表（几百条以上）会把所有节点都渲染，内存和性能都崩。

微信官方提供了 recycle-view 自定义组件（需要安装 miniprogram-recycle-view 包），它做了虚拟列表：只渲染视口内的节点，滚动时复用。

// app.json
{
  "usingComponents": {
    "recycle-view": "miniprogram-recycle-view",
    "recycle-item": "miniprogram-recycle-view/recycle-item"
  }
}

一万条数据下，recycle-view 内存占用比 scroll-view 低一个数量级。

3. 分包加载

小程序整包限制 2MB（单包），总包 20MB。超过 2MB 必须分包：

// app.json
{
  "pages": ["pages/index/index"],
  "subpackages": [
    {
      "root": "packageA",
      "pages": ["pages/user/user", "pages/order/order"]
    }
  ],
  "preloadRule": {
    "pages/index/index": {
      "network": "all",
      "packages": ["packageA"]
    }
  }
}

preloadRule 能在主包进入时预加载子包，体感上几乎无等待。

独立分包：跳过主包的秒开利器

普通分包启动时必须先下载并注入主包，再下载子包。独立分包（"independent": true）可以完全脱离主包运行——用户从分享卡片、广告外投这类非主入口进来时，直接只下载几百 KB 的独立包就能起来，秒开体验上一个台阶。

{
  "subpackages": [
    {
      "root": "packageAd",
      "pages": ["pages/landing/landing"],
      "independent": true
    }
  ]
}

适用场景：

  • 外投落地页 / 分享卡片入口：用户不关心主包业务，独立包秒开就走
  • 活动页：不依赖主包的公共库、登录态

代价是独立分包不能使用主包的任何资源和 JS（包括全局 App、getApp()），公共逻辑只能自己复制一份。

4. 骨架屏与首屏

小程序从点击到首屏可见，包括：启动 → 下载代码包（首次） → 注入 → 首页 onLoad → setData 渲染。

优化手段：

  • 分包 + 分包预下载：减少主包大小，启动快
  • 骨架屏：微信开发者工具支持”自动生成骨架屏”（Page 编辑器右键）
  • 数据预拉取：app.json 里配置 preFetch，在小程序启动时就去请求首页接口，渲染时直接拿数据
// app.json
{
  "preloadRule": {
    "pages/index/index": {
      "network": "all",
      "packages": ["__APP__"]
    }
  }
}

5. 图片与资源

  • 小程序包内不要放大图，走 CDN
  • <image> 的 lazy-load 属性只在 scroll-view 和 page 里生效
  • 本地图片尽量用 WebP（iOS 14+、Android 都支持）

6. Worker 线程：把重计算挪出逻辑层

小程序的逻辑层本身就是单线程 JSCore，如果业务里有加解密、大数据解析、复杂算法，会直接卡住 setData 和用户交互。微信基础库 2.7.0+ 支持 Worker，用法和 Web Worker 类似：

// app.json —— 指定 worker 代码目录
{
  "workers": "workers"
}

// workers/compute.js
worker.onMessage((res) => {
  const result = heavyDecrypt(res.data)
  worker.postMessage({ result })
})

// 页面里
const worker = wx.createWorker('workers/compute.js')
worker.postMessage({ data: payload })
worker.onMessage((res) => {
  this.setData({ list: res.result })
})

几个注意点：

  • Worker 里没有 wx API（只能做纯计算）
  • 和逻辑层通信走 postMessage，数据会序列化，频繁传大数据反而更慢，适合”丢一次、算半天、回一次结果”的场景
  • 不用时记得 worker.terminate()，Worker 常驻会吃内存

几个容易被忽视的点

1. 不要在 useEffect / watch 里做级联请求

// ❌ 串行瀑布，A 完了才发 B，B 完了才发 C
useEffect(() => {
  fetchA().then(() => fetchB()).then(() => fetchC())
}, [])

// ✅ 无依赖并行
useEffect(() => {
  Promise.all([fetchA(), fetchB(), fetchC()])
}, [])

2. 监控要有”可用户维度”

只看 p50/p95 的平均值会被头部用户拉平，容易漏掉长尾问题。要做分机型、分网络、分地域的维度下钻，才能发现真正的优化点。

3. 上线前做一次”低端机测试”

开发机的配置往往比用户机好得多。真机调试至少要覆盖：

  • iPhone SE / 中低端安卓（RAM ≤ 4GB）
  • 3G / 4G 弱网（Chrome DevTools 可以模拟）
  • CPU throttling 4x / 6x

很多在 M 系列 Mac 上看不出来的问题，在用户真机上就是灾难。

小结

  1. 优化的前提是 ROI：先确认性能差在影响业务指标，再动手；没有收益的优化是技术自嗨
  2. 排查按全链路时间轴：先画链路找大头，再针对大头拿细节数据，最后最小化验证
  3. H5 四条主线：首屏（FCP/LCP）、交互（INP）、视觉稳定（CLS）、网络层
  4. 首屏优化是组合拳：资源优先级、响应式图片、LQIP 占位、Critical CSS、代码分割、构建产物瘦身，缺一不可
  5. 构建层是体积问题的源头：产物可视化 + Tree Shaking + Polyfill 按需 + externals，能把首屏 JS 砍掉一大截
  6. 运行时别让主线程卡死：长任务切片、防抖节流、虚拟列表、事件委托、Worker，各有各的场景
  7. 网络优化不要只盯接口：DNS / TCP / TLS / HTTP 版本同样关键，Service Worker 能让二次打开秒开
  8. 小程序的核心矛盾是 setData：控频率、控数据量，长列表用 recycle-view
  9. 小程序首屏利器：分包 + 预下载 + 独立分包，外投落地页尤其适合独立分包
  10. 监控要看长尾，不要被平均值迷惑；上线前务必做低端机 + 弱网测试
