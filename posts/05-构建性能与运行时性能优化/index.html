构建性能与运行时性能优化

发表于2026|更新于2026|工程化
|字数总计:2.2k|阅读时长:7分钟

前言：性能工程这一块，前面讲的都是「产物性能」——加载多快、渲染多快。这一篇补两个容易被合在一起、其实是两回事的话题：构建性能（开发/CI 时构建有多快）和运行时性能（页面跑起来卡不卡）。前者影响的是开发者体验和 CI 成本，后者影响的是用户体验。它们的优化手段完全不同，别混为一谈。

先把两种「性能」分清楚

「性能优化」是个被用烂的词，至少指三件不同的事，优化手段和受益者都不一样：

类型 慢在哪 受益者 典型手段
加载性能 资源下载/首屏 用户 前面几篇：体积、格式、渲染策略
构建性能 构建/HMR 耗时 开发者、CI 换工具、缓存、并行
运行时性能 页面交互卡顿 用户 减少重渲染、长任务拆分

加载性能前面讲透了。这一篇专讲后两个。它们最容易被忽视：构建慢大家默默忍受，运行时卡顿则常被归咎为「用户机器差」。

构建性能：慢构建的隐性成本

构建慢的成本比想象中高。它不只是「等一下」——它拖慢每一次开发反馈循环和每一条 CI。一个改一行代码要等 30 秒 HMR、CI 构建要 10 分钟的项目，团队的整体效率被持续拖累，且会催生「懒得跑测试」「能不重新构建就不重新构建」的坏习惯。

开发时构建（Dev / HMR）优化：

现代工具（Vite）的 dev 已经很快了（基于 esbuild 预构建 + 原生 ESM，见《Vite 开发机制》那篇）。如果 dev 还是慢，常见原因和对策：

  • 依赖预构建没利用好：Vite 首次启动会预构建依赖并缓存到 node_modules/.vite。如果频繁全量重启或缓存失效，会反复预构建。别没事删缓存。
  • barrel 文件（index.ts 大量 re-export）：一个 index.ts re-export 上百个模块，import 它会拖累依赖分析和 HMR。避免超大 barrel。
  • 过多/过重的插件：每个插件都参与转换，装了一堆用不上的插件会拖慢。精简插件。

生产构建 / CI 构建优化：

  • 换更快的底层工具：用 esbuild/SWC 做转译（比 Babel 快一个数量级），用 Rolldown/Rspack 这类新一代打包器（见《新一代构建工具链趋势》那篇）。工具选型是构建性能最大的杠杆。
  • 构建缓存：CI 缓存依赖和构建中间物（见《CI 进阶》缓存那节），Monorepo 用 Turborepo 只构建变化的部分。
  • 并行：多包/多任务并行构建，别串行等。
  • 减少不必要的工作：生产构建才需要的重活（压缩、生成 source map）别在 dev 做；type check 和构建分离（tsc --noEmit 单独跑，不阻塞打包，见《TypeScript 类型检查与构建检查分离》那篇）。

一个判断原则：构建性能优化，先量再优。用构建工具的分析/profile 功能（如 vite build --profile、打包分析插件）找出「时间花在哪」，别凭感觉瞎优化。往往瓶颈就集中在一两个大依赖或一个慢插件上。

运行时性能：页面为什么卡

运行时性能指页面运行起来流畅不流畅——滚动跟不跟手、点击响不响应、动画掉不掉帧。它直接对应性能指标篇的 INP（交互响应）。卡顿的根源几乎都是同一个：主线程被长任务堵住了。

浏览器主线程要同时干 JS 执行、样式计算、布局、绘制。如果一段 JS 跑太久（长任务，> 50ms），这期间用户的点击、滚动都得排队等它跑完——表现就是卡顿、掉帧、点了没反应。

主线程：[───长任务 300ms───][用户点击排队等待][终于响应]
                              ↑ 这 300ms 里点什么都没反应 → INP 差

运行时优化的核心就是别让主线程被长时间占住。几类常见手段：

1. 减少不必要的渲染（框架层）

React/Vue 里最常见的运行时问题是不必要的重渲染——一个 state 变化触发一大片组件重新渲染，其中大部分根本没变。手段：

  • 合理拆分组件、用 memo/useMemo/computed 避免无谓计算和渲染。
  • 别在 render 里创建新对象/函数当 props 传（每次都是新引用，破坏 memo）。
  • 但别过度优化——到处 useMemo 反而增加开销和复杂度。先用 React DevTools Profiler / Vue DevTools 找出真正频繁重渲染的热点，再针对性优化。

2. 长列表虚拟化

渲染几千个 DOM 节点必然卡。长列表只渲染视口内可见的那些（虚拟滚动），用 react-window、@tanstack/virtual、vue-virtual-scroller 之类。几千行的表格/列表不做虚拟化，是运行时卡顿的经典原因。

3. 长任务拆分 / 让出主线程

一个大计算（处理大数据、复杂运算）会独占主线程。把它拆成小块，用 requestIdleCallback、setTimeout、或 scheduler.yield() 在块之间让出主线程，让用户交互有机会插进来：

// 把大批量处理切片，每片之间让出主线程
async function processInChunks(items) {
  for (let i = 0; i < items.length; i += 500) {
    processChunk(items.slice(i, i + 500))
    await new Promise((r) => setTimeout(r))  // 让出主线程，别一口气跑完
  }
}

4. 重活挪到 Web Worker

真正 CPU 密集的活（大量计算、解析、加解密），挪到 Web Worker 里跑，彻底不占主线程。主线程只管 UI，Worker 算完把结果传回来。这是治「计算卡 UI」的根本手段。

代码分割：加载性能和运行时的交叉点

代码分割（code splitting）是个横跨「加载」和「运行时」的手段，值得单独说。它把大 bundle 拆成按需加载的小块：

❌ 一个巨大 bundle：首屏要下载并解析执行全部代码（慢在加载 + 慢在执行）
✅ 按路由/组件分割：首屏只加载当前需要的，其余按需懒加载

最常见的是按路由分割——每个路由一个 chunk，进哪个页面才加载哪个：

// 路由懒加载，React 为例
const Dashboard = lazy(() => import('./pages/Dashboard'))
// 进 /dashboard 才加载这个 chunk，不进就不下载不执行

代码分割同时改善两头：加载上首屏下载量小了（LCP 更快），运行时上首屏要解析执行的 JS 少了（主线程压力小，INP/可交互更快）。这也是为什么它是性能优化的常规操作。相关的 tree-shaking、副作用管理在《Tree Shaking、副作用与代码分割》那篇有更细的展开。

一个真实的坑：优化了平均，忽略了低端机

现象：开发者自己的高配机器上页面很流畅，线上却收到大量卡顿投诉。

原因：开发者的设备远好于真实用户的平均设备。你的 M 芯片 Mac 上主线程再长的任务也感觉不到，用户的中低端安卓手机上就是明显卡顿。运行时性能问题在好设备上被硬件性能掩盖了。

解决：

  1. 用 DevTools 的 CPU 限速（CPU throttling） 模拟低端设备调试——把 CPU 降到 4x/6x 慢速，卡顿立刻现形。
  2. 性能指标看真实用户数据（RUM）的分布（性能指标篇讲的 p75），别信自己机器上的体感。
  3. 在真实的中低端机上实测关键流程。

这和「看 p75 不看平均」是同一个道理：性能问题集中在长尾用户和低端设备上，用你的高配机器测不出来。 运行时性能尤其如此。

小结

  1. 「性能优化」至少三件事：加载性能（用户）、构建性能（开发者/CI）、运行时性能（用户），手段完全不同，别混。
  2. 构建慢拖累每次开发反馈和每条 CI，dev 优化靠依赖预构建/精简插件/避免超大 barrel，生产构建靠换快工具、缓存、并行、检查与构建分离。
  3. 构建优化先量再优，用 profile 找瓶颈，往往集中在一两个大依赖或慢插件。
  4. 运行时卡顿根源是主线程被长任务堵住，直接对应 INP；核心是别长时间占住主线程。
  5. 运行时手段：减少无谓重渲染（先 profile 再优化，别过度）、长列表虚拟化、长任务切片让出主线程、重活挪 Web Worker。
  6. 代码分割横跨加载和运行时，按路由懒加载同时减小首屏下载量和执行量。
  7. 开发者的高配机器会掩盖运行时问题，用 CPU 限速模拟低端机、看 RUM 的 p75 分布、在真实中低端机实测。
