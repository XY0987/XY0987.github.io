可访问性 a11y 工程化基础

发表于2026|更新于2026|工程化
|字数总计:1.8k|阅读时长:6分钟

前言：可访问性不是“有空再优化”的锦上添花。对很多用户来说，它决定了页面能不能被正常使用。工程化要做的不是让每个人都记住所有 a11y 规则，而是把能自动检查的问题提前拦住。

a11y 到底在解决什么

a11y 是 accessibility 的缩写，中间有 11 个字母，所以写成 a11y。

它关注的是：不同能力、设备、环境下的用户，能不能正常理解和操作你的页面。

常见场景包括：

  • 使用屏幕阅读器的用户；
  • 只能键盘操作的用户；
  • 色弱或低视力用户；
  • 临时无法使用鼠标的用户；
  • 移动端强光环境下阅读页面的用户。

很多人以为 a11y 只服务少数人，但实际不是。

比如下面这些要求，对所有用户都有帮助：

  • 表单 label 清楚；
  • 按钮语义正确；
  • 错误提示明确；
  • 焦点状态可见；
  • 颜色对比度足够；
  • 图片有替代文本。

我的理解是：a11y 本质上是更稳定的人机交互质量。

哪些问题适合自动化检查

a11y 可以自动检查一部分问题，但不是全部。

适合工具检查的：

问题 例子
缺少文本替代 img 没有 alt
错误 ARIA 属性 aria-labeledby 拼错
表单标签缺失 input 没有关联 label
交互元素不合法 div 绑定点击但不可聚焦
颜色对比度不足 文本和背景太接近

不适合完全自动判断的：

问题 原因
文案是否真的表达清楚 需要理解业务语义
页面流程是否顺畅 需要真实操作
焦点顺序是否符合用户预期 需要结合界面布局
alt 内容是否准确 工具只能判断有没有，不能判断好不好

所以不要以为接了 a11y 工具就万事大吉。

更合理的目标是：

Lint 插件
  └── 拦截明显代码问题

axe-core
  └── 自动扫描页面结构问题

人工 Review
  └── 判断语义、流程和体验是否合理

React 项目接入 eslint-plugin-jsx-a11y

React 项目里最常见的是 eslint-plugin-jsx-a11y。

安装：

pnpm add -D eslint-plugin-jsx-a11y

Flat Config 示例：

import jsxA11y from 'eslint-plugin-jsx-a11y'

export default [
  {
    files: ['**/*.{jsx,tsx}'],
    plugins: {
      'jsx-a11y': jsxA11y,
    },
    rules: {
      ...jsxA11y.configs.recommended.rules,
    },
  },
]

它能发现很多常见问题。

比如：

export function Avatar() {
  return <img src="/avatar.png" />
}

会提示图片缺少 alt。

更合理的写法：

export function Avatar() {
  return <img src="/avatar.png" alt="用户头像" />
}

如果图片只是装饰，可以写空 alt：

export function DividerIcon() {
  return <img src="/divider.svg" alt="" />
}

这里不要为了通过 lint 随便写 alt="image"，那对屏幕阅读器用户没有帮助。

Vue 项目接入可访问性规则

Vue 项目可以使用 eslint-plugin-vuejs-accessibility。

安装：

pnpm add -D eslint-plugin-vuejs-accessibility

配置思路和 React 类似：把可访问性规则接入 ESLint，让模板里的明显问题提前暴露。

示例问题：

<template>
  <img src="/logo.png">
</template>

应该补充：

<template>
  <img src="/logo.png" alt="公司 Logo">
</template>

如果项目已经使用 eslint-plugin-vue，需要注意规则组合顺序，避免覆盖掉 Vue 推荐规则。

不要滥用 ARIA

先解释一下 ARIA 是什么。ARIA 全称 Accessible Rich Internet Applications，是 W3C 制定的一套规范，核心是给 HTML 元素补充「无障碍语义」的一组属性，让屏幕阅读器等辅助技术能正确理解每个元素「是什么、处于什么状态」。

它主要由三类属性组成：

类型 例子 作用
role（角色） role="button"、role="dialog" 声明「这个元素是什么」
状态（state） aria-checked、aria-expanded 表达会变化的当前状态
属性（property） aria-label、aria-labelledby 补充描述信息

关键要理解的一点是：ARIA 只补充语义，不提供任何行为。它能告诉屏幕阅读器「这是个按钮」，但不会自动带来键盘聚焦、Enter/Space 触发这些能力。

所以 ARIA 很有用，但有一个原则要记住：

能用原生语义标签，就不要先上 ARIA。

反面例子：

export function SubmitButton() {
  return (
    <div role="button" tabIndex={0}>
      Submit
    </div>
  )
}

更好的写法：

export function SubmitButton() {
  return <button type="button">Submit</button>
}

原生 button 默认就支持：

  • 键盘聚焦；
  • Enter/Space 触发；
  • disabled 状态；
  • 屏幕阅读器语义。

用 div role="button" 等于自己重新实现一遍按钮行为，很容易漏。

我的建议是：先用正确 HTML，再考虑 ARIA 补充语义。

使用 axe-core 做自动化扫描

axe-core 是一个常用的自动化可访问性检查引擎，可以集成到测试环境里。

它适合检查页面渲染后的结构问题，因为 ESLint 只能看源码，不能完整理解运行时 DOM。

如果使用 Playwright，可以这样接入：

pnpm add -D @axe-core/playwright

测试示例：

import { test, expect } from '@playwright/test'
import AxeBuilder from '@axe-core/playwright'

test('home page should not have obvious accessibility violations', async ({ page }) => {
  await page.goto('http://localhost:5173')

  const results = await new AxeBuilder({ page }).analyze()

  expect(results.violations).toEqual([])
})

如果有问题，violations 里会包含规则、节点和帮助链接。

这类测试适合放在关键页面：

  • 登录页；
  • 注册页；
  • 表单页；
  • 订单提交页；
  • 核心业务流程。

不要一开始就扫描全站所有页面。先覆盖核心链路，更容易落地。

CI 里怎么放 a11y 检查

可以分两层：

层级 工具 触发时机
源码层 ESLint a11y 插件 本地、pre-commit、CI
页面层 axe-core + E2E CI、关键页面回归

对应脚本：

{
  "scripts": {
    "lint": "eslint .",
    "test:a11y": "playwright test tests/a11y"
  }
}

CI：

pnpm lint
pnpm test:a11y

如果项目还没有 E2E 测试，可以先从 ESLint 插件开始，不要为了 a11y 一口气引入过重流程。

Code Review 里看什么

自动化工具之外，Review 时可以关注这些问题：

  • 点击元素是否使用了正确语义标签；
  • 表单字段是否有 label；
  • 错误信息是否能被用户理解；
  • 弹窗打开后焦点是否进入弹窗；
  • 弹窗关闭后焦点是否回到触发元素；
  • 纯颜色是否承担了唯一信息表达；
  • 图片 alt 是否有真实含义。

这些比“有没有通过 a11y 插件”更重要。

因为工具能告诉你有没有 alt，但不能保证这个 alt 写得像人话。

小结

  1. a11y 不是少数用户专属问题，而是前端交互质量的一部分。
  2. ESLint 插件适合检查源码里的明显问题，比如缺少 alt、错误 ARIA。
  3. React 可以接入 eslint-plugin-jsx-a11y，Vue 可以接入 eslint-plugin-vuejs-accessibility。
  4. axe-core 适合扫描运行时页面结构，建议先覆盖关键页面。
  5. 自动化不能替代人工判断，语义、流程和文案仍然需要 Review。
