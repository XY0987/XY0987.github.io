组件库可访问性 a11y 实践

发表于2026|更新于2026|工程化
|字数总计:2.4k|阅读时长:8分钟

前言：「可访问性 a11y 工程化基础」那篇讲的是应用层——怎么用 ESLint 插件、axe-core 拦住页面里的明显问题。这一篇换到组件库作者的视角：当你在造一个下拉、弹窗、Tabs 时，键盘怎么导航、焦点怎么管、ARIA 怎么加。这是 a11y 里更难、也更值钱的部分——因为组件库的 a11y 做好了，用它的所有产品都白捡了无障碍能力；做砸了，所有产品都得自己踩坑。

为什么组件库是 a11y 的关键杠杆

应用开发者大多没精力研究「组合框的键盘交互规范」。但如果他们用的组件库把这些做好了，他们什么都不用管就得到了无障碍的组件。反过来，如果组件库的 Select 不支持键盘操作，那用它的每个产品都是不可访问的。

所以 a11y 在组件库这一层做，杠杆最大。这也是 Radix UI、React Aria、Ark UI 这类「headless（无样式）」库存在的核心价值——它们把最难的交互和无障碍逻辑封装好，样式交给你。

组件库作者要重点解决三件应用层不用管的事：键盘导航、焦点管理、正确的 ARIA 语义。ARIA 的基础概念（role/state/property，以及「能用原生标签就别上 ARIA」的原则）在 a11y 基础那篇讲过，这里直接进组件实践。

键盘导航：交互组件的及格线

鼠标能做的，键盘必须也能做。这是 a11y 的底线。不同组件有约定俗成的键盘交互模式（WAI-ARIA Authoring Practices 定义），组件库要照着实现。

几个高频组件的键盘约定：

组件 键盘交互
按钮 Enter / Space 触发
弹窗 Dialog Esc 关闭，Tab 在弹窗内循环
下拉菜单 Menu 上下键移动项，Enter 选择，Esc 关闭
Tabs 左右键切换 tab，Home/End 到首尾
单选组 Radio 上下/左右键在选项间移动

roving tabindex：一组选项只有一个可 Tab 进入

实现 Tabs、菜单、单选组这类「一组同类项」的键盘导航，标准模式叫 roving tabindex。

问题背景：如果一个 Tabs 有 5 个 tab，每个都 tabindex="0"，用户按 Tab 键要按 5 次才能跨过这组。正确体验是：Tab 键一次进入这组，然后用方向键在组内移动。

roving tabindex 的做法：组内只有「当前项」tabindex="0"，其余都是 tabindex="-1"（能被 JS 聚焦但不在 Tab 序列里）。方向键移动时，把 0 从旧项转移到新项。

// 简化的 roving tabindex 逻辑
function onKeydown(e: KeyboardEvent, items: HTMLElement[], current: number) {
  let next = current
  if (e.key === 'ArrowRight') next = (current + 1) % items.length
  if (e.key === 'ArrowLeft') next = (current - 1 + items.length) % items.length
  if (e.key === 'Home') next = 0
  if (e.key === 'End') next = items.length - 1

  if (next !== current) {
    items[current].tabIndex = -1
    items[next].tabIndex = 0
    items[next].focus()      // 焦点跟着走
    e.preventDefault()
  }
}

关键点：焦点要真的 .focus() 过去，不只是视觉高亮。屏幕阅读器是跟着焦点走的，只改样式不移焦点，无障碍用户根本感知不到。

焦点管理：弹窗类组件的核心难点

弹窗（Dialog、Drawer、Popover）的 a11y 难点全在焦点管理上，有三件事必须做对。

1. 焦点陷阱（focus trap）

弹窗打开后，Tab 键必须在弹窗内部循环，不能跑到弹窗后面的页面元素上。这叫焦点陷阱。

原理：监听 Tab，当焦点到达弹窗内最后一个可聚焦元素、再按 Tab 时，跳回第一个；反向（Shift+Tab）到第一个再往前，跳到最后一个。

function trapFocus(container: HTMLElement, e: KeyboardEvent) {
  if (e.key !== 'Tab') return
  const focusable = container.querySelectorAll<HTMLElement>(
    'a[href], button:not([disabled]), input:not([disabled]), select, textarea, [tabindex]:not([tabindex="-1"])'
  )
  const first = focusable[0]
  const last = focusable[focusable.length - 1]

  if (e.shiftKey && document.activeElement === first) {
    last.focus(); e.preventDefault()
  } else if (!e.shiftKey && document.activeElement === last) {
    first.focus(); e.preventDefault()
  }
}

自己实现容易漏边界（比如 iframe、动态增删的元素）。生产里更推荐用成熟的 focus-trap 库，别重造：

import { createFocusTrap } from 'focus-trap'
const trap = createFocusTrap(dialogEl)
// 打开时 trap.activate()，关闭时 trap.deactivate()

2. 打开时焦点进入、关闭时焦点归还

  • 弹窗打开：焦点要移进弹窗（通常是第一个可交互元素，或弹窗容器本身）。否则键盘用户还停留在触发按钮上，感知不到弹窗出现了。
  • 弹窗关闭：焦点要还给触发它的那个元素。否则关闭后焦点回到 <body>，用户「迷失」在页面顶部。
let triggerEl: HTMLElement | null = null

function openDialog(trigger: HTMLElement, dialog: HTMLElement) {
  triggerEl = trigger                    // 记住是谁打开的
  dialog.querySelector<HTMLElement>('[autofocus]')?.focus()
    ?? dialog.focus()
}

function closeDialog() {
  triggerEl?.focus()                     // 焦点归还
  triggerEl = null
}

「关闭时把焦点还给触发元素」是 a11y 基础篇 Code Review 清单里就点过的问题，在组件库里必须由组件自己实现，不能指望用户。

3. Esc 关闭 + 背景 inert

Esc 关闭是弹窗的标配。此外，弹窗打开时，背景内容应该对辅助技术「隐藏」，用 inert 属性（或 aria-hidden）：

// 弹窗打开时，让背景不可交互、对屏幕阅读器隐藏
mainContentEl.inert = true
// 关闭时
mainContentEl.inert = false

inert 会让元素及其子树无法聚焦、不响应交互、对辅助技术不可见，是处理模态背景的现代标准做法。

正确的 ARIA：以组合框为例

把 ARIA 用对，屏幕阅读器才能正确播报「这是什么、什么状态」。以一个下拉选择器为例，看看要标注哪些：

<!-- 触发按钮 -->
<button
  aria-haspopup="listbox"
  aria-expanded="true"          <!-- 展开状态，随开合变化 -->
  aria-controls="listbox-1"     <!-- 关联它控制的列表 -->
>
  选择城市
</button>

<!-- 下拉列表 -->
<ul id="listbox-1" role="listbox" aria-label="城市列表">
  <li role="option" aria-selected="true">北京</li>
  <li role="option" aria-selected="false">上海</li>
</ul>

要点：

  • aria-expanded 表示「这个控件控制的内容当前是不是展开」。下拉打开时它应该是 true，关闭后要改回 false。如果视觉上已经展开，但属性还写着 false，屏幕阅读器读到的就是错误状态；如果一直静态写死，就等于没有真正提供可访问状态。
  • role 和交互行为要匹配：标了 role="listbox" 就得实现 listbox 的键盘交互（方向键选择），不能只标语义不给行为。ARIA 只补语义不带行为，这点在基础篇强调过。
  • aria-label / aria-labelledby 给没有可见文本的控件补充可读名称。

别凭记忆手写 ARIA，照着 WAI-ARIA Authoring Practices（APG）对应组件的示例来。那里每个组件都有权威的 role/state/键盘交互清单。造轮子之前先读它，能少走大量弯路。

把 a11y 检查接进组件库的开发流程

光靠人写对不够，要有自动化守住。组件库有两个天然适合接 a11y 检查的地方。

1. Storybook + a11y addon

组件库一般用 Storybook 写示例（下一篇会讲）。Storybook 有官方 a11y 插件，基于 axe-core，能在你看每个组件 story 时实时报无障碍问题：

// .storybook/main.ts
export default {
  addons: ['@storybook/addon-a11y'],
}

装上后，每个组件的示例面板会多一个 a11y 标签，直接列出违规项。边写组件边看 a11y 反馈，比等到应用里才发现问题早得多。

2. 组件测试里跑 axe-core

在组件单测里对渲染结果跑 axe，把 a11y 变成可回归的断言（axe-core 的用法在基础篇讲过，这里是用在组件级别）：

import { render } from '@testing-library/vue'
import { axe } from 'vitest-axe'
import Button from '../src/button'

test('Button 无明显 a11y 违规', async () => {
  const { container } = render(Button, { slots: { default: '提交' } })
  const results = await axe(container)
  expect(results.violations).toEqual([])
})

组件级 axe 检查能拦住「缺 label、错 ARIA、对比度不足」这类问题。但记住基础篇的结论：自动化只能覆盖一部分，键盘流程、焦点顺序这些还得手动测——真的用键盘（拔掉鼠标）走一遍组件的完整交互，是任何工具替代不了的。

小结

  1. a11y 在组件库这一层做杠杆最大：组件库做对了，所有用它的产品白捡无障碍能力。
  2. 键盘导航是及格线，鼠标能做的键盘必须能做；一组同类项用 roving tabindex（组内只有当前项 tabindex=0，方向键移动焦点）。
  3. 焦点移动要真的 .focus()，不能只改视觉高亮，否则屏幕阅读器感知不到。
  4. 弹窗焦点管理三件事：焦点陷阱（推荐用 focus-trap 库）、打开进入焦点、关闭归还给触发元素。
  5. 弹窗打开时用 inert 让背景不可交互、对辅助技术隐藏，Esc 关闭是标配。
  6. ARIA 要随状态实时更新（如 aria-expanded），标了 role 就要实现对应键盘行为；照着 WAI-ARIA APG 实现，别凭记忆。
  7. 用 Storybook a11y addon 边写边查，组件单测里跑 axe-core 做可回归断言，但键盘流程仍需手动拔鼠标实测。
