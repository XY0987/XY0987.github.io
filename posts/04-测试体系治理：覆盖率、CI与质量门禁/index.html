测试体系治理：覆盖率、CI 与质量门禁

发表于2026|更新于2026|工程化
|字数总计:2.8k|阅读时长:9分钟

前言：前面三篇分别讲了单元测试、组件测试和 E2E 测试，解决的是「测试怎么写」。但测试写出来只是第一步，真正进入工程化，还要回答另一个问题：这些测试什么时候跑、谁来兜底、失败了能不能挡住问题代码合进去。这一篇讲测试体系治理：覆盖率、CI 和质量门禁。

测试体系不是测试越多越好

很多团队刚开始补测试时，容易陷入一个误区：好像测试越多越安全。实际不是。测试也是代码，也有维护成本。测试体系的目标不是「堆数量」，而是用合适成本覆盖关键风险。

我更推荐用下面这个分层来理解：

        ╱╲
       ╱  ╲        E2E：少量关键用户旅程，跑得慢但信心强
      ╱────╲
     ╱      ╲      组件测试：中等数量，覆盖 DOM 行为和交互
    ╱────────╲
   ╱          ╲    单元测试：数量最多，覆盖函数逻辑、边界和副作用
  ╱────────────╲

对应到工程流程里，我会这样分工：

测试类型 主要覆盖 运行频率 是否阻断合并
单元测试 函数逻辑、边界、异常、mock、副作用 本地高频 + 每次 PR 应该阻断
组件测试 DOM 渲染、用户交互、异步 UI 本地按需 + 每次 PR 应该阻断
E2E 测试 登录、下单、支付、核心链路 PR / 主干 / 定时任务 核心链路应阻断
覆盖率检查 防止测试覆盖断崖式下降 每次 PR 应该阻断

这里有个关键判断：越靠底层越适合高频运行，越靠顶层越要少而精。单元测试几百条没问题，E2E 几百条就很危险，慢、脆、排查成本高。

先把命令收敛到 scripts

测试治理的第一步不是上 CI，而是先把命令标准化。不要让每个人凭记忆敲不同命令，统一放到 package.json。

环境：Node.js 20、pnpm、Vitest 2.x、Playwright 1.4x。

{
  "scripts": {
    "test": "vitest",
    "test:unit": "vitest run",
    "test:coverage": "vitest run --coverage",
    "test:e2e": "playwright test",
    "test:e2e:ui": "playwright test --ui",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "build": "vite build",
    "quality": "pnpm lint && pnpm typecheck && pnpm test:unit && pnpm test:coverage"
  }
}

这里有几个细节：

  • test 保留给本地 watch，开发时改代码自动重跑。
  • test:unit 用 vitest run，CI 里必须跑一次就退出。
  • test:coverage 单独拆出来，因为覆盖率不是每次本地保存都要跑。
  • quality 把 lint、类型检查、单元测试、覆盖率串起来，作为 CI 的基础质量门禁。

我的习惯是：CI 里不要直接写一堆底层命令，优先调用 scripts。这样本地和 CI 用的是同一套入口，本地能复现，CI 才不神秘。

覆盖率：设底线，不设 KPI

上一篇讲过，覆盖率不是 KPI。到了治理层面，它的作用更明确：防止测试覆盖突然变差。

Vitest 覆盖率配置可以放在 vite.config.ts 的 test.coverage 里：

/// <reference types="vitest/config" />
import { defineConfig } from 'vite'

export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html', 'lcov'],
      thresholds: {
        lines: 70,
        branches: 65,
        functions: 70,
        statements: 70,
      },
    },
  },
})

这几个指标里，我最关注的是 branches。行覆盖看起来很好刷，分支覆盖会逼你处理 if/else、异常分支、边界条件。

阈值怎么设？最好的是分阶段：

阶段 推荐做法
旧项目刚开始补测试 先统计现状，不急着卡很高阈值
有一定测试基础 设一个略低于现状的全局阈值，先防止下降
核心模块稳定后 对核心目录单独设更高阈值
新模块开发 要求新增代码必须带测试，不给历史包袱背锅

不要一上来拍脑袋设 90%。这会逼大家去写很多没价值的测试，最后覆盖率上去了，信心没上去。

更实用的做法是：全局阈值保守一点，核心模块阈值严格一点。

export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      thresholds: {
        lines: 70,
        branches: 65,
        'src/core/**': {
          lines: 85,
          branches: 80,
        },
      },
    },
  },
})

上面这个思路很适合权限、计费、金额、订单、路由守卫这类模块。它们出错代价高，值得更高的测试要求。

CI：把质量检查变成自动动作

本地命令再规范，也挡不住有人忘跑。CI 的价值就是把质量检查从「靠自觉」变成「自动发生」。

下面是一个最小可用的 GitHub Actions 配置：

name: quality

on:
  pull_request:
  push:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Lint
        run: pnpm lint

      - name: Typecheck
        run: pnpm typecheck

      - name: Unit tests and coverage
        run: pnpm test:coverage

      - name: Build
        run: pnpm build

这条流水线做了四件事：

lint → typecheck → unit test + coverage → build

顺序也有讲究。lint 和类型检查最快，应该先跑；测试和构建相对慢，放后面。前面挂了就不用浪费时间继续跑。

如果项目里有 E2E，可以单独拆一个 job：

  e2e:
    runs-on: ubuntu-latest
    needs: test

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup pnpm
        uses: pnpm/action-setup@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Install Playwright browsers
        run: pnpm exec playwright install --with-deps

      - name: E2E tests
        run: pnpm test:e2e

这里让 e2e 依赖 test，意思是基础质量不过，就不跑 E2E。这样能省 CI 时间，也更符合测试金字塔的成本分布。

质量门禁：什么问题必须挡住

质量门禁不是把所有检查都堆上去，而是明确哪些问题不能带进主干。

我会把门禁分成三档：

档位 检查项 是否必须阻断
基础门禁 lint、typecheck、单元测试、构建 必须阻断
测试门禁 覆盖率阈值、组件测试、核心 E2E 必须阻断
观察指标 全量 E2E、性能趋势、包体积趋势 先观察，再决定是否阻断

为什么不一开始把所有东西都设成阻断？因为门禁太重会反噬效率。比如全量 E2E 如果经常 flaky，一上来就阻断所有 PR，最后团队只会学会一件事：忽略 CI 或者反复重跑。

我的建议是：

  1. 确定稳定的检查先阻断：lint、typecheck、unit、build。
  2. 核心流程 E2E 稳定后再阻断：登录、下单、提交这类主流程。
  3. 不稳定检查先做观察：收集失败率，修到足够稳定再进入门禁。

门禁的威信很重要。一旦 CI 红了却经常被无视，它就失去治理价值了。

PR 里应该看什么

测试体系接进 CI 后，PR review 不只是看代码，还要看质量信号。

可以重点看这几类：

信号 说明
测试是否新增 新增复杂逻辑时，有没有配套测试
覆盖率是否下降 下降是否合理，是否漏测关键分支
失败是否可复现 本地能不能用同一条命令复现
E2E 是否 flaky 是产品问题、测试问题，还是环境问题
快照是否可读 快照更新是否真的符合预期

尤其是覆盖率下降，不要只看总数。总覆盖率从 78% 掉到 77% 可能不严重，但如果刚好掉的是 src/core/permission.ts 的分支覆盖，那就应该认真看。

如果团队规模上来了，可以把覆盖率报告和测试报告上传成 CI artifact：

      - name: Upload coverage report
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: coverage
          path: coverage

这样 CI 挂了之后，不用靠日志猜，可以直接下载 HTML 报告看具体哪个文件没覆盖。

flaky 测试要治理，不能忍

flaky 测试就是「有时过，有时不过」的测试。它对测试体系杀伤力很大，因为它会消耗团队对 CI 的信任。

常见原因有这些：

原因 典型表现 处理方式
固定 sleep 本地过，CI 慢机器挂 改成自动等待 / findBy / waitFor
测试互相污染 单跑过，全量跑挂 清理 mock、localStorage、全局状态
依赖真实时间 跨天、跨时区挂 用 fake timers 或固定系统时间
依赖真实网络 网络抖动导致失败 mock 网络，组件测试用 MSW
数据不隔离 多条 E2E 抢同一份数据 每条用例使用独立测试数据

治理 flaky 的原则很简单：不要长期靠重试掩盖问题。

重试可以作为短期止血，比如 Playwright 在 CI 上设：

import { defineConfig } from '@playwright/test'

export default defineConfig({
  retries: process.env.CI ? 2 : 0,
})

但如果一条测试经常要靠第二次、第三次才过，它就应该进入修复清单。否则它每天都会偷走团队时间。

一个真实的坑：本地绿，CI 红

现象：本地 pnpm test 全绿，推到 CI 后挂了。

原因通常不是 CI「玄学」，而是本地和 CI 环境不一致：

  • 本地 Node.js 版本和 CI 不同。
  • 本地有缓存，CI 是干净安装。
  • 本地时区是东八区，CI 默认 UTC。
  • 本地跑的是 watch 模式，CI 跑的是 run 模式。
  • 本地没跑 build，CI build 才暴露类型或打包问题。

解决方式也很直接：把环境和命令固定下来。

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

--frozen-lockfile 很关键，它要求 CI 严格按 lockfile 安装。如果有人改了 package.json 却没更新 lockfile，CI 会直接失败。这比在线上才发现依赖版本漂移要好得多。

如果测试和时区有关，也可以显式固定：

      - name: Unit tests and coverage
        run: pnpm test:coverage
        env:
          TZ: Asia/Shanghai

我的习惯是：CI 命令应该能在本地原样跑。比如本地执行：

pnpm install --frozen-lockfile
pnpm quality
pnpm build

如果本地复现不了 CI 的失败，排查成本会高很多。

小结

  1. 测试体系不是测试越多越好，而是用合适成本覆盖关键风险。
  2. 单元测试和组件测试适合高频运行，E2E 要少而精，重点覆盖关键用户旅程。
  3. 先把测试命令收敛到 package.json scripts，再让本地和 CI 共用同一套入口。
  4. 覆盖率是健康度底线，不是 KPI；全局阈值保守，核心模块可以更严格。
  5. CI 至少要覆盖 lint、typecheck、unit、coverage、build，E2E 可以单独拆 job。
  6. 质量门禁要先阻断稳定检查，不稳定检查先观察，修稳后再纳入阻断。
  7. flaky 测试会消耗团队对 CI 的信任，重试只能止血，不能替代修复。
  8. 本地绿 CI 红通常是环境和命令不一致，Node 版本、lockfile、时区和运行模式都要固定。
