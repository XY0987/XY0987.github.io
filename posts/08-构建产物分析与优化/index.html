构建产物分析与优化

发表于2026|更新于2026|工程化
|字数总计:1.5k|阅读时长:5分钟

前言：优化的第一原则是「先量再改」。很多人一上来就凭感觉删依赖、加配置，结果改了半天产物没小多少。这一篇讲怎么先把构建产物看清楚（谁占体积、谁重复打包），再有针对性地优化。优化手段前面几篇铺垫过 Tree Shaking 和代码分割，这里把它们落到「怎么用工具发现问题」上。

先量：把产物可视化

凭感觉优化是大忌。第一步永远是生成产物分析报告，看清楚体积都花在哪。

Vite/Rollup：用 visualizer

npm i -D rollup-plugin-visualizer

// vite.config.js
import { visualizer } from 'rollup-plugin-visualizer'

export default {
  plugins: [
    visualizer({ open: true, gzipSize: true, brotliSize: true }),
  ],
}

npm run build
# 构建后自动打开一张图，每个方块大小代表该模块占的体积

这张图（treemap）能让你一眼看出：哪个依赖特别大、有没有意外打进来的东西、第三方占比多少。

Webpack：用 bundle-analyzer

npm i -D webpack-bundle-analyzer

const { BundleAnalyzerPlugin } = require('webpack-bundle-analyzer')
module.exports = {
  plugins: [new BundleAnalyzerPlugin()],
}

两者展示形式类似，核心都是 treemap 可视化。看图时我重点关注三件事：

  1. 有没有巨大的单个依赖（比如完整的 moment、lodash、某个图表库）。
  2. 有没有重复打包（同一个库的多个版本同时出现）。
  3. 第三方依赖和业务代码的比例（vendor 是不是过大）。

常见的体积问题与对策

看完图，对着具体问题下药。下面是我遇到最多的几类。

问题一：整个库被全量打进来

现象：明明只用了一个函数，visualizer 里却显示整个库占了几百 KB。

// ❌ 反面案例：全量引入
import _ from 'lodash'
_.debounce(fn, 300)

// ✅ 正面案例：用 ESM 版 + 具名导入，可被 Tree Shaking
import { debounce } from 'lodash-es'
debounce(fn, 300)

原因和对策在 Tree Shaking 那篇讲过：CJS 全量包静态分析困难，通常很难摇干净，优先换 ESM 版按需引入。moment 这种巨无霸可换成 day.js 这类小体积替代。

问题二：依赖重复打包

现象：treemap 里同一个库出现多个版本，或者多个 chunk 都打进了同一个公共库。

原因通常是依赖树里有多个版本（不同包依赖了不同版本的同一个库）。排查：

npm ls some-package   # 看这个包有几个版本

对策：用 overrides（npm）或 resolutions（yarn）强制统一版本，或用 manualChunks 把公共依赖提取到一个共享 chunk。

问题三：首屏 chunk 过大

现象：首屏要下载的 JS 几 MB。

对策就是代码分割——路由懒加载、按需 import()，把非首屏代码拆出去。配合 vendor chunk 让稳定依赖吃缓存。

// 路由懒加载，非首屏页面拆成独立 chunk
const Settings = lazy(() => import('./pages/Settings.jsx'))

压缩与现代产物

体积优化还有几个「设置一下就有效果」的手段。

压缩（minify）

生产构建默认会压缩 JS/CSS（去空格、缩短变量名）。Vite 默认用 esbuild 压缩（Vite 8 起底层引擎升级，压缩也更快）。一般不用动，但要确认 build 时确实开了压缩。

产物 target 别压太低

如果你的目标用户都是现代浏览器，把构建 target 设高一点，能省下大量降级代码和 polyfill：

// vite.config.js
export default {
  build: {
    target: 'es2020', // 目标现代浏览器，产物更小更现代
  },
}

target 设得越低（兼容越老的浏览器），产物里降级代码越多、体积越大。这又回到 browserslist 那套——按真实用户群体设定，别无脑兼容 IE。

gzip / brotli 压缩

最终传输体积还取决于服务器的压缩。treemap 里看 brotli 后的体积更接近用户实际下载量。确保 CDN/服务器开启了 gzip 或 brotli，这是「零代码改动」的收益。

优化的正确姿势：抓大放小

最后说方法论，比具体技巧更重要。

1. 先 build + 生成 visualizer 报告
2. 找出体积 Top 3 的来源
3. 针对性优化（换库 / 按需引入 / 代码分割）
4. 重新 build，对比前后体积
5. 收益变小就停手，别过度优化

我的实战感受：80% 的体积问题集中在少数几个大依赖上。与其花一天抠几 KB 的小优化，不如先解决那个 500KB 的图表库怎么按需加载。抓大放小，量化对比，见好就收。

另外提醒一个常被忽略的点：优化要看 gzip/brotli 后的体积，不是原始体积。有些代码原始体积大但压缩率高，实际传输并不大；盯着原始数字优化容易使错劲。

一个完整的分析流程示例

# 1. 装分析工具
npm i -D rollup-plugin-visualizer

# 2. 配好后构建
npm run build

# 3. 看自动打开的报告，记下 Top 3 大模块

# 4. 比如发现 lodash 全量进来了，改成按需
#    import { debounce } from 'lodash-es'

# 5. 再次构建对比
npm run build

跑一遍这个流程，你会对「自己的产物到底大在哪」有非常具体的认识，远比看十篇优化文章有用。

小结

  1. 优化第一步永远是「先量再改」：用 visualizer（Vite/Rollup）或 bundle-analyzer（Webpack）生成 treemap。
  2. 看图重点关注三件事：有没有超大依赖、有没有重复打包、vendor 占比是否过大。
  3. 全量库换 ESM 版按需引入，巨无霸依赖（moment）换轻量替代（day.js）。
  4. 依赖重复用 overrides/resolutions 统一版本；首屏过大用代码分割 + 路由懒加载。
  5. 构建 target 按真实用户群体设高一点能省降级代码，确保服务器开了 gzip/brotli。
  6. 方法论是抓大放小、量化对比、见好就收，且永远看压缩后的体积而非原始体积。
