Monorepo 工程化实践：Workspace、任务编排与版本发布

发表于2026|更新于2026|工程化
|字数总计:4.4k|阅读时长:15分钟

前言：Monorepo 不是把一堆项目硬塞进一个仓库就完事。它要解决的是”多个包共享工具链、互相依赖、又要能独立发版”这一类问题。这篇我会从零把一个 pnpm Monorepo 搭起来，把 workspace、任务编排、版本发布、CI 这几块讲全，看完能直接照着落地。

什么是 Monorepo

Monorepo 就是用一个 Git 仓库管理多个包（package）。

和它相对的是 Multirepo——每个包一个独立仓库。

举个例子，一个中后台产品可能有：

  • 一个主应用 web；
  • 一个管理后台 admin；
  • 一个共享 UI 组件库 ui；
  • 一个工具函数库 utils；
  • 一份共享的工程配置 config。

Multirepo 下这是 5 个仓库；Monorepo 下它们都在一个仓库里。

两种方式各有取舍：

维度 Monorepo Multirepo
跨包改动 一个 PR 改多个包，原子提交 要开多个 PR，难保证同步
代码复用 直接引用本地包，改了立即生效 要发版后再升级依赖
工具链 一套 ESLint/TS/CI 全仓共享 每个仓库各配一套，容易漂移
权限隔离 较弱，所有人看到全部代码 强，可按仓库授权
仓库体积 越来越大，clone 变慢 单仓库小
CI 成本 需要”只构建受影响的包”才不慢 天然按仓库隔离

我的判断是：团队内部强关联、需要频繁跨包改动的项目，优先 Monorepo；彼此独立、发版节奏完全不同的项目，没必要硬塞进一个仓库。不要为了”看起来工程化”而 Monorepo。

目录结构

一个典型的 pnpm Monorepo 结构是这样：

my-monorepo/
├── package.json            # 根配置，private: true
├── pnpm-workspace.yaml     # 声明哪些目录是 workspace 包
├── tsconfig.base.json      # 共享 TS 配置
├── turbo.json              # 任务编排配置（可选）
├── apps/                   # 可独立部署的应用
│   ├── web/
│   │   └── package.json
│   └── admin/
│       └── package.json
└── packages/               # 被复用的内部包
    ├── ui/
    │   └── package.json
    ├── utils/
    │   └── package.json
    └── config/
        └── package.json

这里有个约定俗成的划分：

目录 放什么 是否发布
apps/ 可独立运行/部署的应用 一般不发布到 npm
packages/ 被其他包复用的库 视情况发布或仅内部用

不是必须叫这两个名字，但用 apps / packages 区分”应用”和”库”，能让人一眼看懂仓库结构。

先理一下 Monorepo 工具的演进

现在我们默认用 pnpm 来做 workspace，但 pnpm 并不是这条路上的第一个工具。了解它之前发生过什么，能帮你理解”为什么今天会收敛到 pnpm”，也能看懂老项目里那些遗留配置。

大致是这么一条线：

时期 代表工具 解决了什么 没解决/痛点
早期 Lerna 第一个把”多包管理 + 版本发布”工程化的工具 自己不做依赖安装，早期要配合 bootstrap 软链，慢且容易乱
包管理器原生化 Yarn workspaces 包管理器原生支持 workspace，依赖统一安装 + 提升 依赖提升（hoisting）导致幻影依赖
包管理器原生化 npm workspaces（npm 7+） npm 官方也内置了 workspace，零额外依赖 任务编排能力弱，大仓性能一般
现在主流 pnpm workspace 硬链接 + 严格 node_modules 结构，省磁盘、依赖隔离严格 严格结构对老项目有迁移成本

几个关键点单独说一下：

  • Lerna 是这个领域的”祖师爷”。它最早把”一个仓库管多个包、统一发版”这件事工具化了。但它早期并不负责装依赖，需要 lerna bootstrap 把包之间软链起来，包一多就很慢。后来 Lerna 把依赖安装交给 Yarn/npm workspaces，自己专注发布；如今它由 Nx 团队接手维护，定位更偏”版本与发布”。

  • Yarn workspaces / npm workspaces 把 workspace 能力直接做进了包管理器，不再需要额外工具来软链本地包，这是一大步。但它们默认会把依赖**提升（hoist）到根 node_modules**，于是出现”幻影依赖”——一个包没在自己 package.json 里声明某依赖，却因为被提升到根目录碰巧能 import 成功，换个环境就崩。

  • pnpm 之所以成为现在的主流，核心就是用硬链接 + 符号链接构建了一套严格的、非扁平的 node_modules：每个包只能访问自己声明过的依赖，从机制上堵住了幻影依赖；同时全局 store 复用让磁盘占用大幅下降，大仓安装也更快。

所以结论不是”pnpm 发明了 Monorepo”，而是：Lerna 趟出了发版工程化的路，Yarn/npm 把 workspace 做进了包管理器，pnpm 在依赖结构的严格性和性能上做到了当前的最优解。如果你接手的是老项目，看到 lerna.json 或 workspaces 字段不用慌，它们只是这条演进线上的不同阶段。

小提醒：Lerna 和 workspace 不是互斥关系。今天仍有项目用 “pnpm workspace 管依赖 + Lerna 管发布” 的组合；只是在前端场景下，发布这块更多被后面会讲的 Changesets 取代了。

用 pnpm 搭建 workspace

Monorepo 的底座是包管理器的 workspace 能力。这里用 pnpm，它在 Monorepo 场景下的依赖结构最严格，也最省磁盘。

环境说明：

  • Node.js 20；
  • pnpm 9（corepack enable 即可启用）。

第一步，根目录 package.json：

{
  "name": "my-monorepo",
  "private": true,
  "packageManager": "pnpm@9.0.0",
  "scripts": {
    "build": "pnpm -r build",
    "lint": "pnpm -r lint",
    "test": "pnpm -r test"
  },
  "devDependencies": {
    "typescript": "^5.5.0"
  }
}

这里 "private": true 非常关键。根包永远不应该被发布到 npm，加上 private 能从机制上防止误发。我见过有人忘了加，一个 npm publish 把整个仓库的根目录发了出去。

第二步，pnpm-workspace.yaml，告诉 pnpm 哪些目录是包：

packages:
  - "apps/*"
  - "packages/*"

第三步，给每个内部包写 package.json。比如 packages/utils/package.json：

{
  "name": "@myorg/utils",
  "version": "0.1.0",
  "type": "module",
  "main": "./src/index.ts",
  "exports": {
    ".": "./src/index.ts"
  }
}

第四步，在仓库根目录执行一次安装：

pnpm install

pnpm 会把所有包的依赖统一安装，并把内部包之间软链接起来。

内部包怎么互相引用：workspace 协议

假设 apps/web 要用 @myorg/utils，在 apps/web/package.json 里这样写：

{
  "dependencies": {
    "@myorg/utils": "workspace:*"
  }
}

workspace:* 表达的是：这个依赖必须来自当前 workspace 里的本地包，不要去 npm registry 下载。

这能避免一个很隐蔽的坑：你以为引用的是本地正在改的包，结果安装时装了 registry 上的同名旧版本，改了半天本地代码没生效。

workspace 协议有几种写法：

写法 含义
workspace:* 本地任意版本，发布时替换成当前确切版本
workspace:^ 发布时替换成 ^当前版本
workspace:~ 发布时替换成 ~当前版本

注意最后一列：workspace:* 只在仓库内部有效。当你用 pnpm publish 把包发到 npm 时，pnpm 会自动把 workspace:* 替换成真实的版本号范围（比如 ^0.1.0），因为 registry 上的用户没有你的 workspace。

我的建议是：内部包引用一律用 workspace:*，别手写版本号假装同步。手写版本号迟早会忘了改，导致版本对不上。

用 catalog 集中管理公共依赖版本

Monorepo 里另一个高频问题：React、TypeScript、ESLint 这类基础依赖在十几个包里都出现，升级时要改十几个 package.json，还容易漏。

pnpm 的 catalog 就是为这个设计的——它是 workspace 级别的”版本常量表”。

在 pnpm-workspace.yaml 里定义：

packages:
  - "apps/*"
  - "packages/*"

catalog:
  react: ^18.3.1
  react-dom: ^18.3.1
  typescript: ^5.5.0

各个子包里就不写具体版本，改成引用 catalog：

{
  "dependencies": {
    "react": "catalog:",
    "react-dom": "catalog:"
  },
  "devDependencies": {
    "typescript": "catalog:"
  }
}

好处有两个：

  1. 所有包共享同一个版本声明，不会出现”A 包用 React 18.2，B 包用 18.3”这种隐性不一致；
  2. 升级时只改 pnpm-workspace.yaml 一处，子包不用动，也大大减少 package.json 的合并冲突。

如果某个包确实需要特殊版本，单独写死版本号覆盖即可。

在 Monorepo 里跑命令：filter 是核心

单仓库时 pnpm dev 就够了。Monorepo 下你经常需要”只对某个包”或”对一批包”执行命令，这靠 pnpm 的 --filter。

只对某个包：

# 只启动 web 应用
pnpm --filter web dev

# 只构建 ui 包
pnpm --filter @myorg/ui build

对所有包递归执行（-r 是 --recursive）：

pnpm -r build

并行执行（适合同时起多个 dev server）：

pnpm -r --parallel dev

filter 还能带依赖关系，这是 Monorepo 真正强大的地方：

写法 含义
--filter web 只有 web
--filter web... web 和它依赖的所有包
--filter ...web web 和所有依赖 web 的包
--filter "...[origin/main]" 相对 main 分支有改动的包及其下游

最后一条特别有用：CI 里可以只对”这次改动影响到的包”跑构建和测试，而不是每次全量。这是 Monorepo CI 不慢的关键。

# 只测试受本次改动影响的包
pnpm --filter "...[origin/main]" test

任务编排：什么时候需要 Turborepo

pnpm -r build 看起来够用，但包一多就会暴露两个问题：

  1. 不懂依赖顺序：utils 必须先于依赖它的 ui 构建，pnpm -r 默认按拓扑排序处理了顺序，但它不会做缓存；
  2. 不会跳过没变的包：你只改了 web，但 pnpm -r build 还是把 ui、utils 全重新构建一遍，纯浪费。

这时候就该上任务编排工具，最常用的是 Turborepo。它的核心能力是任务依赖图 + 缓存：没改过的包直接命中缓存，秒级返回。

安装：

pnpm add -D turbo -w

-w 表示装到 workspace 根目录。

根目录 turbo.json（Turborepo 2.x 语法）：

{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "lint": {},
    "test": {
      "dependsOn": ["build"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    }
  }
}

几个关键字段解释：

字段 含义
dependsOn: ["^build"] ^ 表示”先构建本包依赖的那些包”
dependsOn: ["build"] 不带 ^，表示”先跑本包自己的 build”
outputs 产物路径，Turborepo 据此缓存和恢复
cache: false dev 这种长驻任务不缓存
persistent: true 标记为长驻进程（如 dev server）

然后把根 package.json 的脚本换成走 turbo：

{
  "scripts": {
    "build": "turbo run build",
    "lint": "turbo run lint",
    "test": "turbo run test",
    "dev": "turbo run dev"
  }
}

执行 pnpm build，第一次全量跑；第二次如果什么都没改，你会看到类似：

 Tasks:    4 successful, 4 total
Cached:    4 cached, 4 total
  Time:    120ms >>> FULL TURBO

FULL TURBO 就是全部命中缓存。这对大型 Monorepo 的本地开发和 CI 提速非常明显。

Turborepo 之外还有 Nx。简单对比一下选型：

工具 特点 适合
Turborepo 轻量、配置简单、专注任务缓存 大多数前端 Monorepo
Nx 功能全（代码生成、依赖图分析、插件生态） 大型、强治理、需要脚手架能力的团队

我的建议是：前端业务 Monorepo 先用 Turborepo，简单够用；确实需要 Nx 那套代码生成和插件能力时再上。不要一开始就为了功能全而选最重的工具。

Monorepo 里的 TypeScript

Monorepo 下 TS 有个特有问题：包之间互相引用，类型怎么解析、怎么增量编译。答案是 Project References。

先做一个共享的 tsconfig.base.json：

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "skipLibCheck": true,
    "composite": true,
    "declaration": true,
    "declarationMap": true
  }
}

这里 composite: true 是 Project References 的开关，它要求每个被引用的包都能独立编译并输出声明文件。

每个包的 tsconfig.json 继承它：

{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}

如果 ui 依赖 utils，就在 ui 的 tsconfig 里声明引用：

{
  "extends": "../../tsconfig.base.json",
  "references": [{ "path": "../utils" }]
}

根目录再放一个只负责”组织引用”的 tsconfig.json：

{
  "files": [],
  "references": [
    { "path": "packages/utils" },
    { "path": "packages/ui" },
    { "path": "apps/web" }
  ]
}

然后用 build 模式做全仓类型检查：

tsc -b

tsc -b（build 模式）会按引用关系拓扑排序、增量编译：只重新检查改动过的包及其下游，没改的直接复用上次结果。这比对每个包单独跑 tsc --noEmit 快很多。

一个体验上的小建议：内部包都开 declarationMap: true，这样在应用里点击跳转能直接跳到包的 .ts 源码，而不是生成的 .d.ts，调试体验好很多。

版本管理与发布：Changesets

如果你的 Monorepo 里有包要发布到 npm（或私有 registry），就需要解决一个问题：这次改动该给哪些包升什么版本、changelog 怎么生成。

手动改版本号在多包场景下几乎不可维护。社区的标准答案是 Changesets。

安装并初始化：

pnpm add -D @changesets/cli -w
pnpm changeset init

它的工作流分三步。

第一步，开发完一个改动后，运行：

pnpm changeset

它会交互式地问你：这次改了哪些包？分别是 major / minor / patch？然后在 .changeset/ 目录生成一个 markdown 文件，长这样：

---
"@myorg/ui": minor
"@myorg/utils": patch
---

新增 Button loading 状态，修复 utils 里 debounce 的类型。

这个文件跟着代码一起提交、进 PR。它就是”显式的发布意图声明”。

第二步，准备发布时（通常在 CI 或发布脚本里）运行：

pnpm changeset version

它会读取所有未消费的 changeset 文件，自动 bump 各个包的版本号、更新 changelog、删除已消费的 changeset 文件。这里它还会智能处理内部依赖：如果 utils 升了版本，依赖它的 ui 也会被相应 bump。

第三步，发布：

pnpm changeset publish

它会把版本有变化的包发到 registry，并打好 git tag。前面提到的 workspace:* 也是在这一步被替换成真实版本范围。

Changesets 支持两种版本策略：

模式 含义 适合
independent（默认） 每个包独立版本号 包之间相对独立
fixed / linked 一组包版本号锁定一致 强绑定、必须同步发布的包

我的建议是：默认用 independent，让每个包按自己的改动节奏发版；只有那些必须保持版本一致的包，才用 fixed 锁在一起。

Monorepo 的 CI 策略

Monorepo 的 CI 最容易踩的坑就是每次都全量构建测试，越来越慢。优化思路有三个。

第一，只处理受影响的包。结合前面的 turbo 或 pnpm filter：

# 只对相对 main 有改动的包跑检查
- run: pnpm turbo run lint test build --filter="...[origin/main]"

第二，用缓存。Turborepo 的本地缓存可以通过 CI 缓存目录持久化，甚至接远程缓存（Remote Caching），让不同 CI runner 之间共享。

第三，发布流程自动化。Changesets 官方提供了 GitHub Action，典型流程是：

开发者在 PR 里附带 changeset 文件
  │
  ▼
合并到 main
  │
  ▼
CI 发现有未消费的 changeset
  │
  ├── 自动开一个 "Version Packages" PR（已跑过 changeset version）
  │
  ▼
合并这个 PR
  │
  └── CI 自动 changeset publish 发版

这样发版这件事就完全工具化了，不需要谁手动改版本号、手动 npm publish。

几个真实会踩的坑

**坑 1：根 package.json 忘了 private: true**。前面说过，后果是可能误发整个仓库。建好仓库第一件事就该加上。

坑 2：跨包的幻影依赖。apps/web 用了某个包但没在自己的 package.json 里声明，只是因为别的包装了它、被提升到了根 node_modules 才碰巧能跑。pnpm 的严格结构会让这类问题更早暴露——别急着放宽 pnpm 配置，先把缺的依赖补声明。

坑 3：包之间循环依赖。ui 依赖 utils，utils 又反过来 import ui。这在 Monorepo 里很容易不知不觉发生，会导致构建顺序混乱、类型解析出错。发现循环依赖应该从设计上拆开，而不是想办法绕过工具。

坑 4：CI 全量构建拖垮速度。这是 Monorepo 体验崩坏的头号原因。一旦 CI 要等十几分钟，团队就会开始抗拒往仓库加东西。务必上”只构建受影响包 + 缓存”这套。

小结

  1. Monorepo 用一个仓库管多个包，强关联、需频繁跨包改动的项目才值得用，别为工程化而工程化。
  2. 用 apps/ 放应用、packages/ 放库，根 package.json 必须加 private: true。
  3. 内部包引用一律用 workspace:*，公共依赖版本用 pnpm catalog 集中管理。
  4. pnpm --filter 是 Monorepo 跑命令的核心，配合 ...[origin/main] 能只处理受影响的包。
  5. 包多了用 Turborepo 做任务依赖图和缓存，TS 用 Project References + tsc -b 做增量检查。
  6. 发布用 Changesets：开发时写 changeset，发布时自动 bump 版本、生成 changelog、publish。
  7. CI 的命门是”只构建受影响的包 + 缓存”，否则迟早慢到没人愿意用。
