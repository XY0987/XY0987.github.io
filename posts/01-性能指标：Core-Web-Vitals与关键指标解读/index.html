性能指标：Core Web Vitals 与关键指标解读

发表于2026|更新于2026|工程化
|字数总计:3.6k|阅读时长:12分钟

前言：进入性能工程这一块。做性能优化之前，得先有能衡量的指标——否则「快」「慢」全凭感觉，优化了也不知道有没有效果。这一篇把前端性能最重要的几个指标讲清楚：它们各自量的是什么体验、及格线在哪、怎么采集。重点是 Google 的 Core Web Vitals（核心网页指标），它已经是行业公认的性能标尺，也是后面性能门禁和监控的基础。

为什么要用「以用户为中心」的指标

老一代性能指标是 load、DOMContentLoaded 这类——「页面加载完成」。问题是它们和用户的真实感受对不上。load 触发了不代表用户能看到内容、能点得动；一个页面可能 load 很快但主内容半天不出来，或者能看到但点按钮没反应。

所以业界转向以用户体验为中心的指标，回答用户真正关心的三个问题：

① 内容出来了吗？    → 加载 / 视觉呈现指标（FCP、LCP）
② 布局稳吗？        → 视觉稳定性指标（CLS）
③ 点得动吗？        → 交互响应指标（INP）

Core Web Vitals 就是 Google 从这些维度选出的三个核心指标：LCP、CLS、INP。加上辅助的 FCP、TTFB，构成一套完整的性能画像。

五个关键指标逐个讲

指标 全称 量的是 好 差
TTFB Time to First Byte 服务器响应速度 < 800ms > 1.8s
FCP First Contentful Paint 首次出现内容 < 1.8s > 3s
LCP Largest Contentful Paint 主内容渲染完 < 2.5s > 4s
CLS Cumulative Layout Shift 布局跳动程度 < 0.1 > 0.25
INP Interaction to Next Paint 交互响应速度 < 200ms > 500ms

（LCP/CLS/INP 是 Core Web Vitals 三大核心，阈值指「良好」阈值；具体数值以 web.dev 官方为准。）

TTFB（首字节时间）：从发请求到收到第一个字节的时间。它衡量的是后端/网络/CDN 的响应速度，是所有后续指标的起点——TTFB 慢，后面再优化也快不到哪去。CDN、服务端渲染的响应速度、接口耗时都影响它。

FCP（首次内容绘制）：浏览器首次渲染出任何内容（文字、图片）的时间。它标志「白屏结束了」——用户第一次看到「页面开始出东西了」。

LCP（最大内容绘制）：视口内最大的那个内容元素（通常是主图或大标题）渲染完成的时间。这是 Core Web Vitals 里最重要的加载指标，因为「最大元素出来了」通常意味着「用户想看的主内容到了」。LCP 慢的常见元凶：图片太大、关键资源加载慢、服务端响应慢（TTFB 拖累）、渲染被 JS 阻塞。

CLS（累积布局偏移）：量化页面布局的意外跳动。你肯定遇到过：正要点一个按钮，上面突然插进来一张图，整个页面往下窜，你点错了。CLS 就是量这个。它是个无单位的分数，累计所有意外偏移。常见元凶：图片/广告没设尺寸（占位是 0，加载后撑开）、动态插入内容、字体加载导致的文字重排。

INP（交互到下次绘制）：2024 年正式取代 FID 成为 Core Web Vitals 的交互指标。它衡量用户交互（点击、输入）到页面给出视觉反馈的延迟，且看的是整个会话里最差的那些交互，而不是第一次。INP 差说明主线程被长任务堵住了——点了按钮，JS 忙着算别的，半天才响应。它比老的 FID（只量首次交互的输入延迟）更全面、更贴近真实体验。

记住这个替代关系：INP 已经取代 FID。如果还在看 FID，该切到 INP 了。

实验室数据 vs 真实用户数据

采集性能数据有两条路，理解它们的区别至关重要，否则容易得出错误结论：

实验室数据（Lab） 真实用户数据（Field / RUM）
怎么来 受控环境模拟跑（Lighthouse） 真实用户浏览器上报
优点 可复现、可调试、CI 能用 反映真实用户的真实体验
缺点 是模拟，和真实用户有差距 有噪声、要等数据积累
INP/CLS 测不准（需要真实交互/滚动） 准
典型工具 Lighthouse、Lighthouse CI web-vitals 库、Google CrUX

关键认知：有些指标实验室根本测不准。INP 需要真实的用户交互序列、CLS 需要真实的滚动和加载时序——Lighthouse 在一个受控环境里跑一遍，给出的 INP/CLS 参考价值有限。这两个指标必须靠真实用户数据（RUM）才准。

所以合理的做法是两条腿走路：

  • 实验室数据（Lighthouse）用于 CI 门禁和开发调试——它可复现，能在每个 PR 上跑，适合「防止性能倒退」（下一篇的性能门禁）。
  • 真实用户数据（RUM）用于了解线上真实体验——用 web-vitals 库采集真实用户的 LCP/CLS/INP 上报，这才是用户实际感受到的（监控篇会讲怎么采集上报）。

这些指标到底是怎么拿到的

性能指标不是前端自己「猜」出来的，大部分来自浏览器维护的一条性能时间线（Performance Timeline）。页面从导航开始，到资源加载、首次绘制、布局变化、用户交互，浏览器都会在内部记录一些时间点或事件。我们能做的，是通过标准 API 把这些记录读出来。

简单理解是这样：

用户打开页面
   ↓
浏览器记录导航、资源、绘制、布局、交互等事件
   ↓
PerformanceObserver / performance.getEntriesByType 读取记录
   ↓
web-vitals 封装计算逻辑，产出 LCP / CLS / INP 等指标
   ↓
前端把指标上报到监控平台

几个典型例子：

  • TTFB 主要来自 Navigation Timing：浏览器知道请求什么时候发出、什么时候收到第一个字节，所以能算出服务端和网络响应耗时。
  • FCP 来自 Paint Timing：浏览器第一次把文本、图片、SVG 等内容画出来时，会产生 first-contentful-paint 记录。
  • LCP 来自 Largest Contentful Paint：浏览器会持续观察视口内最大的内容元素，直到页面进入后台或用户发生输入，取最后一次候选值。
  • CLS 来自 Layout Instability：浏览器能感知元素位置的意外变化，并按「影响面积 × 移动距离」累计成布局偏移分数。
  • INP 来自 Event Timing：浏览器记录用户输入事件从发生、事件处理、到下一次绘制之间的耗时，再从一次访问里的交互中选出代表性较差的值。

用代码写出来，大概是下面这个感觉：

type Metric = {
  name: string
  value: number
}

type LayoutShiftEntry = PerformanceEntry & {
  value: number
  hadRecentInput: boolean
}

function report(metric: Metric) {
  console.log(`[perf] ${metric.name}:`, Math.round(metric.value))
}

// TTFB：请求开始到收到第一个字节
const navigation = performance.getEntriesByType('navigation')[0] as PerformanceNavigationTiming | undefined
if (navigation) {
  report({
    name: 'TTFB',
    value: navigation.responseStart - navigation.requestStart,
  })
}

// FCP：首次内容绘制
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.name === 'first-contentful-paint') {
      report({ name: 'FCP', value: entry.startTime })
    }
  }
}).observe({ type: 'paint', buffered: true })

// LCP：视口内最大内容元素的最后一次候选值
let latestLCP = 0
new PerformanceObserver((list) => {
  const entries = list.getEntries()
  const lastEntry = entries[entries.length - 1]

  if (lastEntry) {
    latestLCP = lastEntry.startTime
  }
}).observe({ type: 'largest-contentful-paint', buffered: true })

// CLS：累计没有用户输入触发的意外布局偏移
let cls = 0
new PerformanceObserver((list) => {
  for (const entry of list.getEntries() as LayoutShiftEntry[]) {
    if (!entry.hadRecentInput) {
      cls += entry.value
    }
  }
}).observe({ type: 'layout-shift', buffered: true })

// 交互耗时：帮助理解 INP 的底层来源，不等同于完整 INP 算法
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report({
      name: `Interaction(${entry.name})`,
      value: entry.duration,
    })
  }
}).observe({ type: 'event', buffered: true, durationThreshold: 40 } as PerformanceObserverInit)

window.addEventListener('pagehide', () => {
  report({ name: 'LCP', value: latestLCP })
  report({ name: 'CLS', value: cls })
})

这段代码能帮助理解底层原理，但我不建议生产环境直接这么写。原因很简单：真正的 LCP 终止时机、CLS 会话窗口、INP 取值规则、浏览器兼容性都有细节，手写很容易漏。生产环境还是交给 web-vitals 更稳。

所以 web-vitals 的价值不是「发明了一套指标」，而是把这些底层 API 的兼容性、生命周期、边界条件封装好了。比如 LCP 什么时候最终确定、CLS 怎么按会话窗口累计、INP 怎么从多次交互里取值，这些自己手写很容易漏细节。

用 web-vitals 库采集真实指标

Google 官方的 web-vitals 库是 Web 应用采集 Core Web Vitals 的标准工具，几行代码就能拿到真实用户的指标：

pnpm add web-vitals

import { onLCP, onCLS, onINP, onFCP, onTTFB } from 'web-vitals'

function report(metric: { name: string; value: number; id: string }) {
  // 上报到你的监控后端（用 sendBeacon 保证页面关闭也能发出去）
  navigator.sendBeacon('/api/vitals', JSON.stringify(metric))
}

// 每个指标就绪时回调上报
onLCP(report)
onCLS(report)
onINP(report)
onFCP(report)
onTTFB(report)

几个采集细节：

  • 用 navigator.sendBeacon 而不是 fetch——它能在页面卸载时可靠地把数据发出去（很多性能指标要到用户离开页面才最终确定，比如 CLS、INP 是整个生命周期累计的）。
  • 这些指标是渐进就绪的：FCP/LCP 在加载阶段就有了，CLS/INP 要到页面交互一段时间甚至卸载时才最终确定。所以用回调而不是「加载完读一个值」。

不只是 Web：小程序和跨端应用怎么看指标

Core Web Vitals 是 Web 场景的标准答案，但性能工程不只服务浏览器。小程序、WebView、React Native、Flutter 这类应用，同样要回答用户的三个问题：看见了吗、稳不稳、点得动吗。只是底层运行时不同，指标名字和采集 API 会变。

我们可以先抽象成一套通用口径，再映射到具体平台：

体验问题 Web 常见指标 小程序 / 跨端常见口径 关注点
启动快吗 TTFB、FCP、LCP 冷启动耗时、页面启动耗时、首屏耗时 用户从打开到看到内容要多久
渲染顺吗 LCP、CLS 首帧时间、FPS、掉帧率、长任务 列表滚动、动画、页面切换是否卡顿
点得动吗 INP 点击响应耗时、JS 线程 / UI 线程阻塞、桥通信耗时 点击、输入、手势反馈是否及时
请求快吗 TTFB、接口耗时 API 耗时、失败率、弱网重试耗时 数据回来得快不快、稳不稳
稳定吗 JS Error、资源错误 崩溃率、白屏率、ANR、页面错误率 用户是否能正常完成路径

几个场景可以这样理解：

  • 小程序：运行在平台容器里，不是完整浏览器页面，不能直接照搬全部 Core Web Vitals。更常见的是看小程序启动、页面路由、首屏渲染、接口请求、JS 错误、白屏和卡顿。微信、支付宝等平台通常会提供自己的性能面板和运行时性能 API，具体字段要以各平台官方文档为准。
  • WebView / Hybrid App：里面的 H5 页面可以继续用 web-vitals 采集 LCP、CLS、INP，但用户感知还包括 App 壳启动、WebView 初始化、离线包命中、JSBridge 通信等耗时。只看 H5 指标，会漏掉容器层的问题。
  • React Native / Flutter：重点不再是 DOM 绘制，而是首帧、帧率、掉帧、JS 线程 / UI 线程阻塞、Native Bridge 或 Method Channel 通信、图片解码、列表渲染等。这里的「INP」可以类比为点击到下一帧反馈的耗时，但采集方式要依赖对应框架和原生监控能力。

也就是说，指标名字可以不同，但体验问题不能变。Web 里叫 LCP，小程序里可能叫首屏耗时，Flutter 里可能看 First Frame；Web 里叫 INP，跨端里可能看点击响应和掉帧。做性能治理时，先统一体验口径，再分别接入各端采集能力，这样数据才有可比性。

看指标要看分布，不是平均值

最后一个重要认知：性能指标要看分布（尤其是 p75），别看平均值。

平均值会被少数极端值带偏，也会掩盖「一部分用户体验很差」的事实。行业惯例是看 p75（75 分位）——即 75% 的用户体验优于这个值。Google 判定 Core Web Vitals 是否「良好」，用的就是 p75。

❌ 平均 LCP = 2.0s   →  看着达标，但可能 30% 用户在 5s+ 白等
✅ p75 LCP = 2.4s    →  75% 用户在 2.4s 内看到主内容，更能反映大盘

道理是：性能问题往往集中在「一部分用户」身上（低端机、弱网、特定地区）。平均值把他们的痛苦稀释掉了，分位数才暴露出来。优化性能，本质是把长尾那部分用户的体验拉上来。

小结

  1. 用以用户为中心的指标，回答三个问题：内容出来了吗（FCP/LCP）、布局稳吗（CLS）、点得动吗（INP），别只看老的 load。
  2. Core Web Vitals 三大核心是 LCP（主内容加载）、CLS（布局稳定）、INP（交互响应）；TTFB、FCP 是辅助。
  3. INP 已正式取代 FID，衡量交互到视觉反馈的延迟，看会话里最差的交互。
  4. 实验室数据（Lighthouse）可复现、适合 CI 门禁和调试；真实用户数据（RUM）才反映真实体验，INP/CLS 必须靠 RUM 才准。
  5. Web 指标主要来自浏览器 Performance Timeline，web-vitals 封装了底层采集和计算细节。
  6. 小程序、WebView、React Native、Flutter 也要做性能指标，只是要映射成启动、首屏、帧率、交互、接口、稳定性等通用口径。
  7. 采集用 navigator.sendBeacon 保证页面卸载也能发出，指标是渐进就绪的用回调获取。
  8. 看指标看 p75 分布而非平均值，性能问题常集中在长尾用户身上，平均值会掩盖它。
