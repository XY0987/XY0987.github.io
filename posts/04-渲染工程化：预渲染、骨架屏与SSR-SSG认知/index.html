渲染工程化：预渲染、骨架屏与 SSR/SSG 认知

发表于2026|更新于2026|工程化
|字数总计:3.1k|阅读时长:9分钟

前言：前面几篇优化的是「资源多大、加载多快」。这一篇换个维度——渲染方式本身对性能和体验的影响。同样一个页面，用纯客户端渲染（CSR）还是服务端渲染（SSR）、预渲染（SSG），首屏体验差别巨大。这一篇把 CSR / SSR / SSG / 预渲染 / 骨架屏这几个概念的取舍讲清楚，以及 SSR 工程化的常见坑。定位是认知层——帮你在项目选型时做对判断，不深入某个框架的实现细节。

问题的根源：CSR 的首屏空白

现代 SPA 默认是客户端渲染（CSR）：服务器返回一个几乎空的 HTML（<div id="app"></div>），然后浏览器下载 JS、执行、请求数据、才渲染出内容。

CSR 的首屏时间线：
下载空 HTML → 下载 JS bundle → 执行 JS → 请求数据 → 渲染内容 → 用户看到
     快          慢（大）        耗 CPU      等接口      终于出来
                （这段时间用户看到的是白屏）

问题很明显：首屏有一段白屏，而且 JS 越大、设备越弱、网络越差，白屏越久（直接体现在 LCP 上）。此外 CSR 对 SEO 不友好——爬虫拿到的是空 HTML。

针对这些问题，业界发展出几种渲染策略，本质都是「让内容更早出现」。

五种渲染策略对比

策略 内容在哪生成 首屏 SEO 适用
CSR 浏览器运行时 慢（白屏） 差 后台管理、登录后的应用
SSG 构建时预生成 HTML 极快 好 内容固定：官网、博客、文档
SSR 每次请求服务端生成 快 好 内容动态且要 SEO：电商、资讯
预渲染 构建时给部分路由生成 HTML 快（这些页） 好 SPA 里的少数静态页（首页、关于）
ISR 构建生成 + 按需增量更新 快 好 大量页面但更新不频繁

核心区别就一句话：内容是在「构建时」「请求时」还是「浏览器里」生成的。越早生成，用户越早看到，但灵活性/实时性和工程成本的权衡也不同。

  • SSG（静态站点生成）：构建时就把每个页面渲染成完整 HTML，部署的就是现成的 HTML。首屏极快（CDN 直接吐 HTML）。代价是内容变了要重新构建。博客、文档、官网的最佳选择。
  • SSR（服务端渲染）：每次请求时服务端现渲染 HTML 返回。内容能实时、能个性化，且首屏有内容。代价是需要一个 Node 服务器（不能纯静态托管，回到容器化那篇）、服务端有计算开销。
  • 预渲染（Prerendering）：介于 CSR 和 SSG 之间——一个 SPA 项目，只对少数关键路由（首页、落地页）在构建时生成静态 HTML，其余还是 CSR。用较小的工程改动，改善最重要几个页面的首屏和 SEO。

预渲染：SPA 的轻量首屏优化

如果你有一个 CSR 的 SPA，不想大改成 SSR，但想让首页/落地页的首屏和 SEO 好一点，预渲染是性价比最高的选择。

思路：构建时用一个无头浏览器把指定路由跑一遍，把渲染出的 HTML 抓下来存成静态文件。用户访问这些路由时，先拿到有内容的 HTML（首屏立现），JS 加载完再「接管」变成正常 SPA。

社区工具如 vite-plugin-prerender、prerenderer 等能在构建时做这件事。配置上大致是「指定要预渲染哪些路由」：

预渲染 /、/about、/pricing 这几个静态页
   → 构建时生成 index.html、about.html、pricing.html（带内容）
   → 其余动态路由仍走 CSR

预渲染的前提是这些页面的内容在构建时就确定（不依赖登录态、不依赖实时数据）。适合营销页、文档这类静态内容，不适合个性化/实时的页面——那些该用 SSR。

骨架屏：不能让内容更快，就让等待更「体面」

前面几种是「让内容更早出现」。骨架屏是另一个思路——内容还没来时，先展示页面的大致轮廓（灰色占位块），而不是白屏或转圈。

白屏          →  用户以为卡死了
转圈 loading  →  用户知道在加载，但没有页面结构感
骨架屏        →  用户看到「页面马上就好」的结构，感知等待更短

骨架屏不会让数据真的来得更快，但它改善的是「感知性能」——用户看到页面框架已经在了，会觉得更快、更少焦虑。研究和实践都表明，有结构的等待比空白/转圈的等待感觉更短。

工程化上，骨架屏可以：

  1. 手写：给每个页面写对应的骨架组件。精准但费工。
  2. 自动生成：有工具（如 page-skeleton-webpack-plugin 一类）能分析页面结构自动生成骨架屏。省事但精度一般，复杂页面效果不佳。

核心页面手写骨架屏（值得投入），一般页面用统一的通用骨架或简单 loading 即可。别为每个页面都精心做骨架屏，投入产出不划算。骨架屏和前面的渲染策略不冲突——CSR 项目用骨架屏缓解白屏，SSR/SSG 首屏本来就有内容，骨架屏主要用在后续的局部数据加载上。

Next / Nuxt 的组织方式（认知层）

在引出框架之前，先把 SSR 的底层链路说清楚。SSR 不是浏览器拿到空 HTML 后再渲染，而是请求先到服务端，服务端把页面组件和数据渲染成 HTML，再把这份 HTML 返回给浏览器。

SSR 的一次请求：
用户访问 /product/123
  → 服务端匹配路由
  → 服务端请求商品数据
  → 服务端把组件渲染成 HTML 字符串
  → HTML 带着首屏内容返回浏览器
  → 浏览器先展示内容，再下载 JS
  → JS 水合（hydration），页面变得可交互

所以 SSR 的关键不是「服务端能不能吐出 HTML」，而是要同时处理好几个问题：路由怎么匹配、数据什么时候取、HTML 怎么生成、初始数据怎么同步给浏览器、客户端 JS 怎么接管已有 HTML、缓存和部署怎么做。

这里有个容易误解的点：SSR 主要解决的是首次访问 / 刷新 / 直接打开 URL 时的首屏 HTML。一旦浏览器加载完 JS 并完成水合，后面的按钮点击、表单输入、弹窗、局部状态更新，大多就变成前端应用在浏览器里自己处理了。也就是说，SSR 负责「先把内容端上来」，水合之后的交互体验，本质上还是 CSR 那套运行时逻辑。

真到落地 SSR / SSG，大多数团队不会自己从零搭，而是选成熟框架：React 生态常见 Next，Vue 生态常见 Nuxt。它们解决的正是上面这些工程复杂度：把路由、数据获取、构建、服务端运行、静态生成、缓存这些事情组织成一套工程模型。

从工程组织上看，可以把它们理解成三层：

页面/路由层        决定哪些 URL 对应哪些页面
数据获取层        决定数据在构建时拿、请求时拿，还是浏览器里拿
渲染与部署层      决定这个页面最终是静态文件、Node 服务渲染，还是边缘运行

这个分层比具体 API 更重要。真正要问的不是「Next / Nuxt 哪个更强」，而是这个页面到底需不需要 SSR：

问题 倾向
内容固定、更新不频繁 SSG / 静态生成
内容动态、需要 SEO SSR
登录后页面、强个性化 CSR 或局部客户端渲染
页面很多但更新不频繁 ISR / 增量生成

先按页面类型选渲染策略，而不是整个项目一刀切。官网首页可以 SSG，商品详情可以 SSR，用户后台仍然 CSR。Next / Nuxt 只是落地这些策略的工程工具，重点不是「框架很强」，而是你要先判断页面是否真的需要服务端渲染。

这也解释了为什么 SSR/SSG 工程化经常和部署形态绑在一起：SSG 产物可以走静态 CDN；SSR 需要 Node 服务或边缘运行时；ISR 还要考虑缓存和再生成策略。渲染策略不是纯前端代码选择，它会影响构建、部署、缓存、监控和回滚。

SSR 工程化的常见坑（认知层）

SSR 能显著改善首屏和 SEO，但它的工程复杂度是几种里最高的——代码同时要在服务端（Node）和客户端（浏览器）两个环境跑。这带来一堆独特的坑，选型时要有心理准备。Next（React）、Nuxt（Vue）这类框架帮你处理了大部分，但理解这些坑才知道框架在解决什么。

坑一：水合不匹配（Hydration Mismatch）

前面讲过，SSR 的流程是：服务端渲染出 HTML → 发给浏览器（用户先看到）→ 浏览器加载 JS 后「水合（hydration）」，给这段 HTML 绑定事件、接管成可交互的应用。

水合的前提是服务端渲染的结果和客户端首次渲染的结果必须一致。如果不一致（比如用了 Date.now()、Math.random()、window.innerWidth 这种服务端和客户端算出不同值的东西），就会报「hydration mismatch」——轻则警告，重则页面错乱、闪烁、事件绑错。

❌ 服务端没有 window，客户端有 → 两边渲染结果不同 → 水合失败
❌ 服务端渲染的时间 和 客户端水合时的时间 不一样 → 内容对不上

解法通常是：把「只在客户端才能确定的东西」延迟到水合之后（如 useEffect 里）再渲染，保证首次渲染两端一致。

坑二：服务端没有浏览器 API

服务端是 Node，没有 window、document、localStorage。直接在模块顶层或渲染路径里访问它们，SSR 会直接崩。所以 SSR 代码里访问浏览器 API 必须判断环境或放到只在客户端执行的生命周期里。很多第三方库不支持 SSR，就是因为它们无脑访问了 window。

坑三：服务端的内存与状态

SSR 服务是常驻进程，多个请求共享同一个进程。如果不小心把用户相关的状态放到了模块级的全局变量（单例），会造成请求间的数据串台——A 用户的数据泄漏给 B 用户。这是 SSR 特有的、很危险的坑。每个请求要有独立的状态容器。

我的判断：SSR 是把双刃剑，收益（首屏 + SEO）明确，但工程成本和坑也明确。选型建议——纯内容站优先 SSG（简单又快），需要 SEO 的动态内容才上 SSR（用成熟框架 Next/Nuxt，别自己从零搭），登录后的后台应用 CSR 足矣（没 SEO 需求，白屏用骨架屏缓解）。别为了「SSR 显得高级」给一个后台管理系统上 SSR，那是纯给自己找麻烦。

小结

  1. CSR 的问题是首屏白屏 + SEO 差，各种渲染策略本质都是「让内容更早出现」。
  2. 五种策略的核心区别是内容在「构建时/请求时/浏览器里」生成：SSG 构建时（内容固定的站最佳）、SSR 请求时（动态且要 SEO）、CSR 浏览器里（后台应用够用）。
  3. 预渲染是 SPA 的轻量首屏优化：构建时给少数静态路由生成 HTML，改动小、收益集中在最重要的几个页面。
  4. 骨架屏改善的是「感知性能」——有结构的等待比白屏/转圈感觉更短；核心页面手写、一般页面用通用骨架。
  5. SSR 的底层链路是服务端匹配路由、获取数据、渲染 HTML，再让浏览器水合接管；Next / Nuxt 的核心价值是把这些复杂度组织成一套工程模型。
  6. SSR 工程复杂度最高，代码要同时在服务端和客户端跑，典型坑：水合不匹配、服务端无浏览器 API、请求间状态串台。
  7. 选型判断：内容站用 SSG，动态+SEO 用 SSR（选 Next/Nuxt 别自建），后台应用 CSR + 骨架屏即可，别为「显得高级」滥用 SSR。
