TypeScript Project References、声明构建与类型测试

发表于2026|更新于2026|工程化
|字数总计:2.4k|阅读时长:9分钟

前言：普通业务项目会配 tsconfig.json 就够了。但当项目进入 Monorepo、多包依赖、组件库和 SDK 这些场景后，TypeScript 的重点会变成：如何增量编译、如何输出声明文件、如何保证类型 API 不被改坏。

Project References 解决什么问题

TypeScript 官方把 Project References 设计成大型项目拆分能力。它允许一个 TypeScript 项目引用另一个 TypeScript 项目。

{
  "references": [
    { "path": "../shared" }
  ]
}

它解决的核心问题是：大型代码库不应该每次都从头检查所有源码。

在 Monorepo 里常见结构是：

packages/
├── shared/
│   ├── src/
│   └── tsconfig.json
├── ui/
│   ├── src/
│   └── tsconfig.json
└── app/
    ├── src/
    └── tsconfig.json

如果 app 依赖 ui，ui 依赖 shared，TypeScript 可以根据引用关系按顺序构建，并且只重建变更过的项目。

shared -> ui -> app

这比所有包混成一个巨大 TypeScript 项目更可控。

被引用项目必须开启 composite

被其他项目引用的包，需要开启：

{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}

composite 会带来几个约束：

  1. 必须能生成 .d.ts；
  2. 所有源文件必须被 include 或 files 明确包含；
  3. 项目边界更清晰，不能随便把外部文件混进来。

这些约束看起来麻烦，但它们正是工程化需要的“边界感”。

declaration 是跨包类型边界

开启：

{
  "compilerOptions": {
    "declaration": true
  }
}

TypeScript 会输出 .d.ts 文件。

src/index.ts  -> dist/index.js
              -> dist/index.d.ts

在 Project References 中，依赖方读取的是被引用项目的 .d.ts，而不是直接读取源码。

这意味着 .d.ts 就是包之间的类型契约。

// packages/shared/src/index.ts
export interface User {
  id: string
  name: string
}

生成后：

export interface User {
  id: string
  name: string
}

app 不需要关心 shared 内部怎么实现，只依赖它暴露出来的类型边界。

declarationMap 让跨包跳转更舒服

只开 declaration 的时候，编辑器“跳转到定义”可能跳到 dist/index.d.ts。

开启：

{
  "compilerOptions": {
    "declarationMap": true
  }
}

会额外生成 .d.ts.map，让 VS Code 这类编辑器可以从声明文件跳回源码。

我的建议是：Monorepo 内部包都开启 declarationMap，开发体验会好很多。

顶层 solution tsconfig.json

Monorepo 根目录可以有一个只负责组织引用的 tsconfig.json：

{
  "files": [],
  "references": [
    { "path": "./packages/shared" },
    { "path": "./packages/ui" },
    { "path": "./packages/app" }
  ]
}

注意 files: []。它表示根项目自己不编译源码，只作为构建入口。

然后执行：

tsc -b

TypeScript 会自动按依赖顺序构建，不需要你手动排序。

tsc -b 是构建协调器

tsc -b 和普通 tsc 不太一样。它会：

  1. 找到所有引用项目；
  2. 判断哪些项目过期；
  3. 按依赖顺序构建；
  4. 利用增量信息避免重复构建。

常用命令：

tsc -b              # 构建当前 solution
tsc -b --verbose    # 输出详细构建过程
tsc -b --clean      # 清理构建产物
tsc -b --force      # 强制重建

--clean 会删除产物，--force 会触发完整重建，CI 或本地排查问题时再用，不要无脑塞进日常脚本。

一个更完整的 Monorepo 示例

packages/shared/tsconfig.json：

{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "include": ["src"]
}

packages/ui/tsconfig.json：

{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "rootDir": "src",
    "outDir": "dist"
  },
  "references": [
    { "path": "../shared" }
  ],
  "include": ["src"]
}

tsconfig.base.json：

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "skipLibCheck": true
  }
}

这样每个包有自己的输出和边界，根目录负责统一调度。

类型测试：防止类型 API 被改坏

运行时代码可以用单测保护，类型也需要测试。

比如一个工具类型：

export type MaybeArray<T> = T | T[]

你希望它永远满足某些类型行为，就可以写类型测试。

expect-type

import { expectTypeOf } from 'expect-type'
import type { MaybeArray } from '../src'

expectTypeOf<MaybeArray<string>>().toEqualTypeOf<string | string[]>()

Vitest 的 expectTypeOf

如果项目已经用 Vitest，可以直接使用：

import { expectTypeOf, test } from 'vitest'
import type { MaybeArray } from '../src'

test('MaybeArray', () => {
  expectTypeOf<MaybeArray<number>>().toEqualTypeOf<number | number[]>()
})

这类测试不会验证运行时逻辑，它验证的是类型推导是否符合预期。

tsd

tsd 更适合 npm 库，对发布后的类型入口做测试。

import { expectType } from 'tsd'
import { createClient } from '.'

const client = createClient({ baseURL: '/api' })
expectType<Promise<string>>(client.getText())

我的建议是：

场景 建议
业务项目 Vitest expectTypeOf 足够
工具类型库 expect-type 或 Vitest
npm 包发布类型入口 tsd 更合适

常用断言不止「相等」

写类型测试时，光会 toEqualTypeOf 是不够的，几个高频断言要分清：

import { expectTypeOf } from 'vitest'

// 完全相等（最严格，宽窄都要一致）
expectTypeOf<MaybeArray<string>>().toEqualTypeOf<string | string[]>()

// 可赋值即可（子类型也算通过，适合校验「至少满足某形状」）
expectTypeOf({ a: 1, b: 2 }).toMatchTypeOf<{ a: number }>()

// 断言函数参数 / 返回值
expectTypeOf(createClient).parameter(0).toMatchTypeOf<{ baseURL: string }>()
expectTypeOf(createClient).returns.toEqualTypeOf<Client>()

// 断言「这个用法应该报类型错」——防止 API 意外放宽
// @ts-expect-error baseURL 必填，缺了必须报错
createClient({})

最后那个 @ts-expect-error 很重要：类型测试不仅要验证「正确用法能通过」，还要验证「错误用法会被拦住」。如果哪天有人不小心把参数改成可选，这行 @ts-expect-error 会因为「预期的错误没出现」而反过来报错，从而守住 API 边界。

让类型测试真正进 CI（关键的一步）

类型测试写了却不在 CI 跑，等于没写。落地要点是把它做成一条独立的、会让流水线失败的命令。

三种工具的接法不同：

// package.json
{
  "scripts": {
    // Vitest：类型测试要用 typecheck 模式跑，普通 vitest run 不检查类型断言
    "test:types": "vitest typecheck --run",
    // tsd：库项目，测的是「构建产物的类型入口」
    "test:types:pkg": "tsd"
  }
}

Vitest 需要在配置里开启 typecheck，并约定类型测试文件名（和运行时测试分开，避免拖慢普通单测）：

// vitest.config.ts
export default defineConfig({
  test: {
    typecheck: {
      enabled: true,
      include: ['**/*.test-d.ts'], // 只有这些文件走类型检查
    },
  },
})

tsd 则约定把类型测试放在 test-d/ 目录，并在 package.json 里声明测试对象：

{
  "tsd": {
    "directory": "test-d"   // 存放 *.test-d.ts
  }
}

CI 里把它放在类型检查这一层（fast feedback 阶段），和 tsc --noEmit 并列：

      - run: pnpm typecheck      # tsc --noEmit / tsc -b，检查业务代码类型
      - run: pnpm test:types     # vitest typecheck，检查类型断言符合预期

对库项目：把类型测试当成发布门禁

对要发布到 npm 的库，光测「源码里的类型」还不够——用户拿到的是**构建产物的 .d.ts**，源码类型对、产物类型错的情况真实存在（比如 exports.types 配错、d.ts 打包漏了内部类型）。所以库项目的类型防线应该是三层：

1. tsc --noEmit         → 源码类型自洽
2. vitest typecheck     → 类型 API 行为符合预期（含 @ts-expect-error 边界）
3. tsd + arethetypeswrong → 发布产物的类型入口对消费者可用

把第 3 层放进 prepublishOnly 或发布流水线，就能挡住「类型在本地好好的、发出去用户却报一堆类型错」这类最尴尬的事故。这也和后面《组件库构建》《npm 包发布》两篇的产物校验（@arethetypeswrong/cli、publint）形成闭环。

.d.ts 编写规范

手写 .d.ts 时，我有几个习惯：

只声明真实使用到的 API

// ✅ 只补项目实际使用的最小能力
declare module 'legacy-sdk' {
  export function login(username: string, password: string): Promise<{ token: string }>
}

不要为了“完整”凭空补一大堆没验证过的类型。类型声明一旦写错，会给团队制造假安全感。

模块扩展要放在清晰位置

declare module 'axios' {
  export interface AxiosRequestConfig {
    skipAuth?: boolean
  }
}

建议统一放在 src/types/modules.d.ts 或 types/axios.d.ts，不要散在业务目录里。

全局声明要克制

declare global {
  interface Window {
    __APP_VERSION__: string
  }
}

export {}

全局类型污染会让项目越来越难理解。能用模块导入解决的，就不要挂全局。

小结

  1. Project References 适合 Monorepo 和大型 TypeScript 项目，用来建立项目边界和增量构建能力。
  2. 被引用项目需要 composite、declaration，通常也建议开启 declarationMap。
  3. .d.ts 是跨包类型契约，declarationMap 能改善跨包跳转体验。
  4. tsc -b 是多项目构建协调器，不只是普通编译命令。
  5. 类型测试可以保护类型 API，库项目尤其应该重视：用 toEqualTypeOf/toMatchTypeOf/@ts-expect-error 覆盖正反用例，并通过 vitest typecheck / tsd 做成独立命令进 CI；库项目还要用 tsd + arethetypeswrong 把「发布产物的类型入口」纳入发布门禁。
