Vue 3 track 与 trigger 源码解析：依赖是如何收集和触发的

发表于2026|更新于2026|Vue框架及周边库
|字数总计:5.7k|阅读时长:23分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：前两篇分别看了 reactive 如何创建代理、baseHandlers 如何拦截读写。这一篇进入响应式系统的核心：track 和 trigger。我的理解是，track 解决“谁依赖了我”，trigger 解决“我变了要通知谁”。

先给结论

Vue 3.5 的依赖关系可以粗略理解成下面这个结构：

targetMap: WeakMap
  │
  ├─ target 原始对象
  │    │
  │    └─ depsMap: Map
  │         │
  │         ├─ key: 'count'
  │         │    │
  │         │    └─ dep: Dep
  │         │         │
  │         │         └─ subscribers: effect / computed
  │         │
  │         └─ key: ITERATE_KEY
  │              │
  │              └─ dep: Dep

如果用一句话概括：

track 把当前正在执行的 effect 记录到某个 target.key 对应的 Dep 中；trigger 在 target.key 变化时找到这个 Dep，再通知里面的订阅者。

从一个最小例子开始

const state = reactive({ count: 0 })

effect(() => {
  console.log(state.count)
})

state.count++

内部流程大致是：

effect 执行
  │
  ▼
读取 state.count
  │
  ▼
baseHandlers.get
  │
  ▼
track(target, GET, 'count')
  │
  ▼
把当前 effect 放进 target.count 对应的 Dep

修改 state.count
  │
  ▼
baseHandlers.set
  │
  ▼
trigger(target, SET, 'count')
  │
  ▼
找到 target.count 对应的 Dep
  │
  ▼
通知里面的 effect 重新执行

这个流程里有三个核心角色：

角色 含义
targetMap 全局依赖总表，负责从原始对象找到属性依赖
Dep 某个具体属性的依赖集合
Subscriber 订阅者，可以理解成 effect 或 computed

targetMap：依赖总表

先看依赖总表的定义：

// 响应式依赖总表：target -> key -> dep。
// target 是原始对象，key 是被访问的属性，dep 负责维护依赖这个属性的 subscriber 链表。
// 概念上可以理解成 Map<object, Map<key, Set<effect>>>，源码中用 Dep/Link 降低内存开销。
type KeyToDepMap = Map<any, Dep>

export const targetMap: WeakMap<object, KeyToDepMap> = new WeakMap()

概念上，它接近这个结构：

WeakMap<target, Map<key, Dep>>

为什么外层是 WeakMap？原因和前面 reactiveMap 类似：当原始对象不再被业务代码引用时，它对应的依赖记录也可以被垃圾回收。

为什么不是直接用 Set<effect>？Vue 3.5 这里用了 Dep 和 Link，主要是为了更高效地维护依赖关系、清理无效依赖，以及给 computed 提供版本号快速路径。

Link：Dep 和 effect 之间的边

Link 是理解新版响应式实现的关键。它不是单纯的“节点”，更像是一条连接 Dep 和 Subscriber 的边。

export class Link {
  /**
   * Link 是 Dep 与 Subscriber 之间的“边”。
   * version 用来判断这条边在本轮 effect 执行中是否仍然被访问：
   * - 执行前，旧 Link 的 version 会被重置为 -1
   * - 执行中，如果再次读取到对应响应式属性，version 会同步为 dep.version
   * - 执行后，仍为 -1 的 Link 说明这次没用到，需要清理
   */
  version: number

  /**
   * 同一个 Link 同时存在于两条双向链表中：
   * - nextDep/prevDep：挂在 Subscriber 上，表示一个 effect 依赖了哪些 Dep
   * - nextSub/prevSub：挂在 Dep 上，表示一个响应式属性被哪些 effect 订阅
   */
  nextDep?: Link
  prevDep?: Link
  nextSub?: Link
  prevSub?: Link
  prevActiveLink?: Link

  constructor(
    public sub: Subscriber,
    public dep: Dep,
  ) {
    // https://juejin.cn/post/7425134213748031514
    this.version = dep.version
    this.nextDep =
      this.prevDep =
      this.nextSub =
      this.prevSub =
      this.prevActiveLink =
        undefined
  }
}

这里最重要的是：同一个 Link 不是单纯的“链表节点”，而是一条真实的订阅关系。

一个 Link 表示：某个 Subscriber 依赖了某个 Dep。

如果直接看抽象图会比较懵，我们先用一段真实的 Vue 响应式代码固定场景：

import { effect, reactive } from '@vue/reactivity'

const state = reactive({ count: 0, name: 'Vue' })

const effectA = effect(() => {
  console.log(state.count, state.name)
})

const effectB = effect(() => {
  console.log(state.count)
})

这段代码里有两个响应式属性，也就可以理解成两个 Dep：

响应式读取 对应 Dep
state.count Dep_count
state.name Dep_name

同时有两个订阅者，也就是两个 Subscriber：

effect 读取了哪些属性
effectA state.count、state.name
effectB state.count

所以最终会形成三条订阅关系：

Link Subscriber Dep 含义
LinkA_count effectA Dep_count effectA 读过 state.count
LinkA_name effectA Dep_name effectA 读过 state.name
LinkB_count effectB Dep_count effectB 读过 state.count

画成二维关系会更直观：

                         Dep_count(state.count)      Dep_name(state.name)

Subscriber: effectA          LinkA_count  ───────►    LinkA_name
                                  │                       │
                                  │                       │
Subscriber: effectB          LinkB_count                  -

横向看，是“一个 effect 依赖了哪些属性”；纵向看，是“一个属性被哪些 effect 订阅”。而 Link 就是这个二维表里的交叉点。

这里有个容易混的点：Link 和 Link 之间确实也会互相连接，但要分清楚它们是沿着哪个维度连。

同一个 Subscriber 维度：
  effectA.deps ──► LinkA_count ──nextDep──► LinkA_name
                    ▲                         ▲
                    │                         │
                 prevDep                   prevDep

同一个 Dep 维度：
  Dep_count.subsHead ──► LinkA_count ──nextSub──► LinkB_count ◄── Dep_count.subs
                           ▲                         ▲
                           │                         │
                        prevSub                   prevSub

所以不是“同一个 sub，不同 effect”。更准确地说：

  • Subscriber 本身通常就是一个 effect 或 computed。
  • effectA 和 effectB 是两个不同的 Subscriber。
  • 同一个 Subscriber 下面的多个 Link，用 nextDep / prevDep 串起来。
  • 同一个 Dep 下面的多个 Link，用 nextSub / prevSub 串起来。

也就是说，LinkA_count 和 LinkA_name 之所以能连，是因为它们属于同一个 effectA；LinkA_count 和 LinkB_count 之所以能连，是因为它们属于同一个 Dep_count。

Vue 源码里真正创建 Link 的地方在 Dep.track：

if (link === undefined || link.sub !== activeSub) {
  // 当前 subscriber 第一次读取这个 Dep：创建 Link，并同时挂到 subscriber 与 dep 两侧。
  link = this.activeLink = new Link(activeSub, this)

  // add the link to the activeEffect as a dep (as tail)
  if (!activeSub.deps) {
    activeSub.deps = activeSub.depsTail = link
  } else {
    link.prevDep = activeSub.depsTail
    activeSub.depsTail!.nextDep = link
    activeSub.depsTail = link
  }

  addSub(link)

这里做了两件事。

第一，把 Link 挂到当前 activeSub 的依赖链表上。也就是：

effectA.deps ──► LinkA_count ──► LinkA_name
                 │              │
                 ▼              ▼
              Dep_count      Dep_name

effectB.deps ──► LinkB_count
                 │
                 ▼
              Dep_count

这条链表通过 nextDep / prevDep 连接。它服务的是 Subscriber 视角：当 effectA 重新执行或停止时，Vue 可以顺着 effectA.deps 找到它依赖过的所有 Dep。

第二，调用 addSub(link)，把同一个 Link 再挂到 Dep 的订阅者链表上：

const currentTail = link.dep.subs
if (currentTail !== link) {
  link.prevSub = currentTail
  if (currentTail) currentTail.nextSub = link
}

if (__DEV__ && link.dep.subsHead === undefined) {
  link.dep.subsHead = link
}

link.dep.subs = link

这时候从 Dep 视角看，关系变成这样：

Dep_count.subsHead ──► LinkA_count ──► LinkB_count ◄── Dep_count.subs
                       │               │
                       ▼               ▼
                    effectA         effectB

Dep_name.subsHead  ──► LinkA_name ◄── Dep_name.subs
                       │
                       ▼
                    effectA

注意一个细节：dep.subs 指向的是订阅链表尾部，触发更新时会从尾部通过 prevSub 往前遍历：

for (let link = this.subs; link; link = link.prevSub) {
  // 真正通知每个 subscriber。普通 effect 会被放入批处理队列；computed 会继续通知自己的 dep。
  if (link.sub.notify()) {
    // if notify() returns `true`, this is a computed. Also call notify
    // on its dep - it's called here instead of inside computed's notify
    // in order to reduce call stack depth.
    ;(link.sub as ComputedRefImpl).dep.notify()
  }
}

也就是说，当执行：

state.count++

Vue 只需要找到 Dep_count，再顺着 Dep_count.subs 这条链通知对应的 Subscriber：

Dep_count
  │
  ▼
Dep_count.subs: LinkB_count
  │
  ├─ link.sub.notify()  -> effectB
  │
  ▼ prevSub
LinkA_count
  │
  └─ link.sub.notify()  -> effectA

而 Dep_name 完全不需要参与，因为这次变的是 state.count。

为什么要这样设计

我刚开始看这里时也会觉得：为什么不简单一点，直接让 Dep 存一个 Set<effect>？

// 简化理解可以这样想，但源码不是这样做的
Dep_count.subscribers = new Set([effectA, effectB])

这个模型适合理解入门，但到了真实框架里不够用。原因是响应式依赖不是单向关系，而是多对多关系：

一个 effect 会依赖多个 Dep
一个 Dep 也会被多个 effect 依赖

Link 的价值，就是把“某个 effect 依赖某个 Dep”这件事单独抽象成一个对象。这样做有几个好处。

第一，两个方向都能遍历。

  • 从 effectA.deps 出发，可以知道 effectA 依赖过 Dep_count 和 Dep_name。
  • 从 Dep_count.subs 出发，可以知道 state.count 变化时要通知 effectA 和 effectB。

这两个方向都很重要。触发更新要从 Dep 找 Subscriber，清理旧依赖要从 Subscriber 找 Dep。

第二，清理旧依赖更方便。

比如 effect 里有条件分支：

const state = reactive({ ok: true, count: 0, name: 'Vue' })

effect(() => {
  console.log(state.ok ? state.count : state.name)
})

第一次执行时，依赖是 ok + count。当 ok 变成 false 后，下一次执行依赖会变成 ok + name。这时旧的 count 依赖就应该被清掉，否则以后 count 变化还会误触发这个 effect。

cleanupDeps 做的就是这件事：

function cleanupDeps(sub: Subscriber) {
  // 执行后清理本轮没有再次访问到的依赖，也就是 version 仍为 -1 的 Link。
  let head
  let tail = sub.depsTail
  let link = tail
  while (link) {
    const prev = link.prevDep
    if (link.version === -1) {
      if (link === tail) tail = prev
      // unused - remove it from the dep's subscribing effect list
      removeSub(link)
      // also remove it from this effect's dep list
      removeDep(link)
    } else {
      // The new head is the last node seen which wasn't removed
      // from the doubly-linked list
      head = link
    }

    // restore previous active link if any
    link.dep.activeLink = link.prevActiveLink
    link.prevActiveLink = undefined
    link = prev
  }
  // set the new head & tail
  sub.deps = head
  sub.depsTail = tail
}

因为 Link 同时有 prevDep / nextDep 和 prevSub / nextSub，所以 Vue 拿到某个失效的 Link 后，可以同时把它从两条链表里摘掉：

function removeSub(link: Link, soft = false) {
  const { dep, prevSub, nextSub } = link
  if (prevSub) {
    prevSub.nextSub = nextSub
    link.prevSub = undefined
  }
  if (nextSub) {
    nextSub.prevSub = prevSub
    link.nextSub = undefined
  }
  if (__DEV__ && dep.subsHead === link) {
    // was previous head, point new head to next
    dep.subsHead = nextSub
  }

  if (dep.subs === link) {
    // was previous tail, point new tail to prev
    dep.subs = prevSub

    if (!prevSub && dep.computed) {
      // if computed, unsubscribe it from all its deps so this computed and its
      // value can be GCed
      dep.computed.flags &= ~EffectFlags.TRACKING
      for (let l = dep.computed.deps; l; l = l.nextDep) {
        // here we are only "soft" unsubscribing because the computed still keeps
        // referencing the deps and the dep should not decrease its sub count
        removeSub(l, true)
      }
    }
  }

  if (!soft && !--dep.sc && dep.map) {

function removeDep(link: Link) {
  const { prevDep, nextDep } = link
  if (prevDep) {
    prevDep.nextDep = nextDep
    link.prevDep = undefined
  }
  if (nextDep) {
    nextDep.prevDep = prevDep
    link.nextDep = undefined
  }
}

第三，Link 自己可以携带状态。

前面 Link 里有一个 version 字段。它不是装饰品，而是用来判断“这条依赖关系在本轮 effect 执行后还是否有效”。

  • 执行前，旧依赖的 link.version 会被标记成 -1。
  • 执行中，如果这个属性又被读取，link.version 会恢复成 dep.version。
  • 执行后，仍然是 -1 的 Link 就说明本轮没读到，需要清理。

如果没有 Link 这个独立节点，这类“关系级别”的状态就不好存。你只能把状态塞到 Dep 或 effect 上，但它们都不准确，因为状态属于“某个 effect 和某个 Dep 之间的这条关系”。

第四，避免无关遍历。

当 state.count 变化时，只遍历 Dep_count 的订阅链表；当 effectA 重新执行时，只遍历 effectA 自己的依赖链表。Vue 不需要扫描所有 effect，也不需要扫描所有 Dep。

所以，这里的设计不是为了把代码写复杂，而是因为响应式系统本质上是一张多对多依赖图。Link 把这张图里的“边”显式建模出来，再让这条边同时挂在两个方向的链表上。

Dep：一个属性对应一个依赖容器

Dep 可以理解为某个 target.key 的依赖容器。

export class Dep {
  // 每次依赖对应的数据发生变化时递增，用于快速判断 subscriber 是否需要重新计算。
  version = 0

  /**
   * 当前正在收集依赖的 subscriber 与这个 Dep 之间的 Link。
   * 同一个属性在一次 effect 执行中可能被多次读取，activeLink 可以避免重复创建 Link。
   */
  activeLink?: Link = undefined

  /**
   * 订阅当前 Dep 的 subscriber 链表尾部。
   * 触发更新时会从尾部向前遍历，配合 batch 后仍能按正确顺序执行。
   */
  subs?: Link = undefined

  /**
   * 订阅链表头部，仅开发环境用于按原始顺序触发 onTrigger 调试钩子。
   */
  subsHead?: Link

  /**
   * map/key 反指向 targetMap 中的位置，用于订阅者清空后删除无用 Dep，降低内存占用。
   */
  map?: KeyToDepMap = undefined
  key?: unknown = undefined

  /**
   * subscriber 计数。计数归零时，说明这个属性已经没有 effect 订阅。
   */
  sc: number = 0

几个字段值得重点记：

字段 作用
version 属性变化版本号，变化时递增
activeLink 当前正在收集时的 Link，避免重复创建
subs 订阅当前属性的 subscriber 链表
map / key 反向记录自己在 targetMap 中的位置，方便清理
sc subscriber 计数

我刚开始读这里时，容易把 Dep 理解成 Set<effect>。这样理解可以入门，但不够精确。更准确地说，Dep 维护的是一组 Link，每个 Link 再指向具体的 Subscriber。

effect 是如何变成 activeSub 的

track 不是任何时候都会收集依赖。它只在有正在执行的 effect 时才收集，这个“正在执行的 effect”就是 activeSub。

ReactiveEffect.run 中会设置它：

  run(): T {
    // TODO cleanupEffect

    if (!(this.flags & EffectFlags.ACTIVE)) {
      // stopped during cleanup
      return this.fn()
    }

    this.flags |= EffectFlags.RUNNING
    // 清理旧的依赖
    cleanupEffect(this)
    // 重置为-1，并标记为待验证，等待后面运行依赖函数时，会重新标记，最后将哪些仍为-1的依赖清除
    prepareDeps(this)
    const prevEffect = activeSub
    const prevShouldTrack = shouldTrack
    activeSub = this
    shouldTrack = true

    try {
      return this.fn()
    } finally {
      if (__DEV__ && activeSub !== this) {
        warn(
          'Active effect was not restored correctly - ' +
            'this is likely a Vue internal bug.',
        )
      }
      // 清理旧依赖
      cleanupDeps(this)
      activeSub = prevEffect
      shouldTrack = prevShouldTrack
      this.flags &= ~EffectFlags.RUNNING
    }
  }

这里的关键流程是：

  1. 执行 effect 前，把旧依赖标记为待确认。
  2. 设置 activeSub = this。
  3. 执行用户函数 this.fn()。
  4. 用户函数里读取响应式属性，触发 track。
  5. 执行结束后清理本轮没有再访问到的旧依赖。
  6. 恢复上一个 activeSub。

这就是为什么只有在 effect 里读取响应式数据，才会建立依赖关系。

track：依赖收集的入口

track 是被 baseHandlers.get 调用的入口函数。

export function track(target: object, type: TrackOpTypes, key: unknown): void {
  if (shouldTrack && activeSub) {
    // 1. 找到当前原始对象对应的 key -> dep 映射表，没有则创建。
    let depsMap = targetMap.get(target)
    if (!depsMap) {
      targetMap.set(target, (depsMap = new Map()))
    }

    // 2. 找到当前属性对应的 Dep，没有则创建，并记录反向引用，方便后续清理空 Dep。
    let dep = depsMap.get(key)
    if (!dep) {
      depsMap.set(key, (dep = new Dep()))
      dep.map = depsMap
      dep.key = key
    }

    // 3. 将当前 activeSub 记录到 Dep 中；开发环境会携带调试信息。
    if (__DEV__) {
      dep.track({
        target,
        type,
        key,
      })
    } else {
      dep.track()
    }
  }
}

它做的事情很直接：

  1. 根据 target 找到 depsMap。
  2. 根据 key 找到 dep。
  3. 把当前 activeSub 收集进这个 dep。

也就是说，track(target, GET, 'count') 最终建立的是：

target.count ──► dep ──► 当前 effect

注意这里用的是原始对象 target，不是代理对象。代理对象只是拦截入口，真正存依赖时用的是原始对象。

Dep.track：真正把 effect 和 Dep 连起来

顶层 track 找到 Dep 后，会调用 dep.track()。

  track(debugInfo?: DebuggerEventExtraInfo): Link | undefined {
    // activeSub 是当前正在执行并允许收集依赖的 effect/computed。
    // shouldTrack 会在数组 push/pop 等场景被临时关闭，避免读写 length 造成递归追踪。
    // activeSub === this.computed 用于避免 computed 自己订阅自己。
    if (!activeSub || !shouldTrack || activeSub === this.computed) {
      return
    }

    let link = this.activeLink
    if (link === undefined || link.sub !== activeSub) {
      // 当前 subscriber 第一次读取这个 Dep：创建 Link，并同时挂到 subscriber 与 dep 两侧。
      link = this.activeLink = new Link(activeSub, this)

      // add the link to the activeEffect as a dep (as tail)
      if (!activeSub.deps) {
        activeSub.deps = activeSub.depsTail = link
      } else {
        link.prevDep = activeSub.depsTail
        activeSub.depsTail!.nextDep = link
        activeSub.depsTail = link
      }

      addSub(link)
    } else if (link.version === -1) {
      // 这条 Link 是上轮 effect 留下来的旧依赖，本轮又被访问到了。
      // 同步 version，表示它仍然有效，避免在 cleanupDeps 中被清理。
      link.version = this.version

      // 如果旧 Link 不在 deps 尾部，移动到尾部，保持依赖链表顺序与本轮访问顺序一致。
      if (link.nextDep) {
        const next = link.nextDep
        next.prevDep = link.prevDep
        if (link.prevDep) {
          link.prevDep.nextDep = next
        }

        link.prevDep = activeSub.depsTail
        link.nextDep = undefined
        activeSub.depsTail!.nextDep = link
        activeSub.depsTail = link

        // this was the head - point to the new head
        if (activeSub.deps === link) {
          activeSub.deps = next
        }
      }
    }

这里有两种情况。

第一种：当前 effect 第一次依赖这个属性。此时创建新的 Link，并把它同时挂到：

  • activeSub.deps 链表上
  • dep.subs 链表上

第二种：这个依赖上轮已经存在，本轮又访问到了。此时不用新建 Link，只需要同步 version，表示它仍然有效。

这就是 Vue 3.5 依赖清理的一个关键优化：不是每次都全量删除再全量重建，而是通过 version 标记旧依赖是否仍然有效。

trigger：触发更新的入口

当 baseHandlers.set 判断属性发生变化后，会调用 trigger。

export function trigger(
  target: object,
  type: TriggerOpTypes,
  key?: unknown,
  newValue?: unknown,
  oldValue?: unknown,
  oldTarget?: Map<unknown, unknown> | Set<unknown>,
): void {
  const depsMap = targetMap.get(target)
  if (!depsMap) {
    // 这个对象从未被追踪过，没有 subscriber 需要通知；但全局版本仍递增，供 computed 快速路径判断。
    globalVersion++
    return
  }

  const run = (dep: Dep | undefined) => {
    if (dep) {
      if (__DEV__) {
        dep.trigger({
          target,
          type,
          key,
          newValue,
          oldValue,
          oldTarget,
        })
      } else {
        dep.trigger()
      }
    }
  }

  startBatch()

  // 根据变更类型和目标类型，找出所有需要被通知的 Dep。
  if (type === TriggerOpTypes.CLEAR) {
    // Map/Set clear 会影响整个集合，所有 key 对应的依赖都需要通知。
    depsMap.forEach(run)
  } else {
    const targetIsArray = isArray(target)
    const isArrayIndex = targetIsArray && isIntegerKey(key)

    // 数组 length 变短时，被截断的索引依赖、length 依赖和数组迭代依赖都要触发。
    if (targetIsArray && key === 'length') {
      const newLength = Number(newValue)
      depsMap.forEach((dep, key) => {
        if (
          key === 'length' ||
          key === ARRAY_ITERATE_KEY ||
          (!isSymbol(key) && key >= newLength)
        ) {
          run(dep)
        }
      })
    } else {
      // SET/ADD/DELETE 都至少会影响当前 key 对应的依赖。
      if (key !== void 0 || depsMap.has(void 0)) {
        run(depsMap.get(key))
      }

      // 修改数组索引会影响数组迭代结果。
      if (isArrayIndex) {
        run(depsMap.get(ARRAY_ITERATE_KEY))
      }

      // ADD/DELETE 还会影响对象 key 集合；Map.SET 也会影响 Map 的迭代结果。
      switch (type) {
        case TriggerOpTypes.ADD:
          if (!targetIsArray) {
            run(depsMap.get(ITERATE_KEY))
            if (isMap(target)) {
              run(depsMap.get(MAP_KEY_ITERATE_KEY))
            }
          } else if (isArrayIndex) {
            // new index added to array -> length changes
            run(depsMap.get('length'))
          }
          break
        case TriggerOpTypes.DELETE:
          if (!targetIsArray) {
            run(depsMap.get(ITERATE_KEY))
            if (isMap(target)) {
              run(depsMap.get(MAP_KEY_ITERATE_KEY))
            }
          }
          break
        case TriggerOpTypes.SET:
          if (isMap(target)) {
            run(depsMap.get(ITERATE_KEY))
          }
          break
      }
    }
  }

  endBatch()
}

trigger 的难点不是“找到当前 key 的 dep”，而是判断除了当前 key，还有哪些依赖也应该被通知。

比如：

操作 除当前 key 外，还可能影响
新增对象属性 Object.keys、for...in 等迭代依赖
删除对象属性 迭代依赖、key in obj 依赖
新增数组索引 length 依赖
修改数组 length 被截断索引、数组迭代依赖
Map.set 新 key Map key 迭代依赖
Map.clear 所有依赖

这就是 trigger 里有那么多分支的原因。它不是简单地通知 depsMap.get(key)，还要根据操作类型扩大通知范围。

Dep.trigger 和批处理

顶层 trigger 找到要通知的 Dep 后，会调用 dep.trigger()。

  trigger(debugInfo?: DebuggerEventExtraInfo): void {
    // 当前属性发生变化：局部 dep.version 与全局 globalVersion 都递增。
    // computed 可以利用这些版本号走快速路径，避免无变化时重复计算。
    this.version++
    globalVersion++
    this.notify(debugInfo)
  }

  notify(debugInfo?: DebuggerEventExtraInfo): void {
    // 通知订阅者时开启批处理，避免同一轮变更中 effect 被同步重复执行。
    startBatch()
    try {
      if (__DEV__) {
        // subs are notified and batched in reverse-order and then invoked in
        // original order at the end of the batch, but onTrigger hooks should
        // be invoked in original order here.
        // 开发环境的 onTrigger 调试钩子需要按订阅原顺序触发，便于调试输出稳定。
        for (let head = this.subsHead; head; head = head.nextSub) {
          if (head.sub.onTrigger && !(head.sub.flags & EffectFlags.NOTIFIED)) {
            head.sub.onTrigger(
              extend(
                {
                  effect: head.sub,
                },
                debugInfo,
              ),
            )
          }
        }
      }
      for (let link = this.subs; link; link = link.prevSub) {
        // 真正通知每个 subscriber。普通 effect 会被放入批处理队列；computed 会继续通知自己的 dep。
        if (link.sub.notify()) {
          // if notify() returns `true`, this is a computed. Also call notify
          // on its dep - it's called here instead of inside computed's notify
          // in order to reduce call stack depth.
          ;(link.sub as ComputedRefImpl).dep.notify()
        }
      }
    } finally {
      endBatch()
    }
  }

这里有两个重点。

第一，dep.version 和 globalVersion 会递增。computed 可以根据版本号判断有没有必要重新计算。

第二，通知 subscriber 时不会简单粗暴地立刻执行所有 effect，而是进入批处理。普通 effect 会被放入队列，等批处理结束后统一执行。

effect.ts 中可以看到批处理队列：

let batchDepth = 0
let batchedSub: Subscriber | undefined
let batchedComputed: Subscriber | undefined
// 将订阅函数添加到不同的队列中
export function batch(sub: Subscriber, isComputed = false): void {
  sub.flags |= EffectFlags.NOTIFIED
  // 计算属性添加到batchedComputed队列中
  if (isComputed) {
    sub.next = batchedComputed
    batchedComputed = sub
    return
  }
  // 普通响应式依赖添加到batchedSub队列中
  sub.next = batchedSub
  batchedSub = sub
}

这可以避免同一轮同步修改里，一个 effect 被重复执行多次。

依赖清理：为什么需要 version

考虑这个例子：

const state = reactive({ ok: true, a: 1, b: 2 })

effect(() => {
  console.log(state.ok ? state.a : state.b)
})

第一次执行时，effect 依赖 ok 和 a。当 ok 变成 false 后，下一次执行会依赖 ok 和 b，此时旧的 a 依赖应该被清理掉。

Vue 通过 prepareDeps 和 cleanupDeps 完成这个过程：

// 将所有已有依赖的版本号设置未-1（link）
function prepareDeps(sub: Subscriber) {
  // Prepare deps for tracking, starting from the head
  for (let link = sub.deps; link; link = link.nextDep) {
    // set all previous deps' (if any) version to -1 so that we can track
    // which ones are unused after the run
    link.version = -1
    // store previous active sub if link was being used in another context
    link.prevActiveLink = link.dep.activeLink
    link.dep.activeLink = link
  }
}

function cleanupDeps(sub: Subscriber) {
  // Cleanup unused deps
  let head
  let tail = sub.depsTail
  let link = tail
  while (link) {
    const prev = link.prevDep
    if (link.version === -1) {
      if (link === tail) tail = prev
      // unused - remove it from the dep's subscribing effect list
      removeSub(link)
      // also remove it from this effect's dep list
      removeDep(link)
    } else {
      // The new head is the last node seen which wasn't removed
      // from the doubly-linked list
      head = link
    }

    // restore previous active link if any
    link.dep.activeLink = link.prevActiveLink
    link.prevActiveLink = undefined
    link = prev
  }
  // set the new head & tail
  sub.deps = head
  sub.depsTail = tail
}

流程是：

  1. effect 重新执行前，把旧依赖的 link.version 标记为 -1。
  2. 执行过程中，如果某个依赖又被访问到，就把 link.version 同步为 dep.version。
  3. 执行结束后，仍然是 -1 的 Link 说明本轮没访问到，需要从两边链表移除。

这就是 Link.version 的作用：它是依赖是否仍然有效的标记。

小结

  1. targetMap 是响应式依赖总表，结构是 target -> key -> Dep。
  2. Dep 不是简单的 Set<effect>，它通过 Link 维护和 subscriber 的多对多关系。
  3. track 在有 activeSub 时，把当前 effect 收集到当前属性对应的 Dep。
  4. trigger 根据变更类型找出需要通知的 Dep，不只是通知当前 key。
  5. version、prepareDeps、cleanupDeps 共同完成旧依赖清理，避免分支切换后仍触发无效 effect。

到这里，响应式系统的“收集依赖”和“触发更新”主线已经打通。下一步可以继续看 effect.ts，重点理解 ReactiveEffect、调度器、批处理和 stop 是怎么工作的。
