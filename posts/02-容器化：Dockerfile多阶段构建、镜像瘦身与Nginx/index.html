容器化：Dockerfile 多阶段构建、镜像瘦身与 Nginx

发表于2026|更新于2026|工程化
|字数总计:2k|阅读时长:6分钟

前言：上一篇讲的是「产物传 CDN」这种纯静态托管。但很多场景下，前端要以容器的形式交付——要么是公司统一用 K8s / 容器平台调度，要么是 SSR 应用需要一个 Node 运行时，要么是要把「Nginx + 静态产物」打成一个自带环境的可移植镜像。这一篇讲前端容器化的核心：多阶段构建（构建和运行环境分离）、镜像瘦身、以及 Nginx 配置规范。前端同学不一定天天写 Dockerfile，但这套认知在容器化团队里是硬通货。

为什么前端也要容器化

「前端不就是几个静态文件吗，为什么要装进容器？」几个真实理由：

  1. 环境一致性：镜像把运行环境（Nginx 版本、配置、Node 版本）和产物打包在一起，「在我机器上好好的」这类问题在容器面前基本消失——镜像在哪跑都是同一个环境。
  2. 统一调度：公司用 K8s / 容器云时，前端也得以镜像形式交付，才能被同一套 CI/CD、扩缩容、健康检查纳管。
  3. SSR 需要运行时：Next / Nuxt 的 SSR 不是纯静态，需要一个常驻的 Node 进程，容器是自然的载体。

对纯静态站点，CDN 托管通常更简单更快；容器化的价值主要在「需要运行时」或「团队统一用容器」的场景。别为了容器化而容器化。

核心：多阶段构建（Multi-stage Build）

前端容器化最重要的一个概念就是多阶段构建。理解它，就理解了前端 Dockerfile 的一大半。

问题背景：构建前端需要一大堆东西——Node、npm/pnpm、几百 MB 的 node_modules、源码。但运行前端（伺服静态文件）只需要一个 Nginx 和最终的 dist/。如果把构建环境和运行环境放一起，镜像会巨大（带着几百 MB 根本用不上的构建依赖），还多了一堆攻击面。

多阶段构建的思路：用一个阶段构建，再用一个干净的阶段只装最终产物。

# ---------- 阶段一：构建 ----------
FROM node:20-alpine AS builder
WORKDIR /app

# 先只拷贝依赖清单，利用 Docker 层缓存
COPY package.json pnpm-lock.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile

# 再拷贝源码构建
COPY . .
RUN pnpm build          # 产出 dist/

# ---------- 阶段二：运行 ----------
FROM nginx:1.27-alpine AS runner
# 只从上一阶段拷贝构建产物，构建依赖全部丢弃
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

关键在最后阶段的 COPY --from=builder /app/dist ...——只把 dist/ 拷进最终镜像，第一阶段那几百 MB 的 node_modules 和 Node 本身全都不进最终镜像。最终镜像只有「Nginx + 静态产物」，几十 MB，干净、小、安全。

层缓存：为什么先拷 package.json

上面 Dockerfile 有个刻意的顺序：先 COPY package.json、装依赖，再 COPY . . 拷源码。这是利用 Docker 的层缓存。

Docker 镜像是一层层叠起来的，每条指令一层。某一层的输入没变，这一层及其缓存就能复用。依赖安装（pnpm install）是最慢的一步，我们希望它尽量命中缓存：

❌ 反面：先 COPY . . 再 install
   任何源码改动 → COPY 层变 → 后面的 install 层缓存失效 → 每次都重装依赖

✅ 正面：先 COPY package.json + install，再 COPY 源码
   只改源码时 → package.json 没变 → install 层命中缓存 → 跳过重装，秒构建

这个「把变化频率低的放前面」的原则，和 CI 缓存那篇的思路一脉相承——让最贵的操作尽可能命中缓存。改一行业务代码却要重装几百个依赖，是新手 Dockerfile 最常见的浪费。

镜像瘦身的几个手段

小镜像意味着更快的拉取、更少的攻击面、更低的存储成本。除了多阶段构建这个大头，还有几招：

1. 用 alpine 或 slim 基础镜像

node:20 有近 1GB，node:20-alpine（基于 Alpine Linux）只有一百多 MB。运行阶段用 nginx:alpine 同理。alpine 极小，但要注意它用 musl libc 而非 glibc，个别依赖原生模块可能不兼容——遇到编译问题时，node:20-slim（基于 Debian）是更稳的折中。

2. .dockerignore 别把垃圾拷进去

和 .gitignore 类似，.dockerignore 告诉 Docker 哪些不要放进构建上下文：

# .dockerignore
node_modules
dist
.git
*.log
.env*

这不仅减小镜像，还避免把本地 node_modules、.env 密钥误拷进镜像（安全隐患）。**.env 一定要 ignore 掉**——密钥不该进镜像。

3. 合并 RUN、清理缓存

每条 RUN 都会生成一个镜像层。能合并的命令用 && 合并，并在同一层清理临时文件，避免文件先进入某个镜像层、再被后一层删除，导致最终容器里看不到它，但镜像体积仍然降不下来：

RUN apk add --no-cache some-tool \
    && do-something \
    && rm -rf /tmp/*        # 在同一层清理，才能真正减小体积

Nginx 配置规范

前端静态镜像的运行主体是 Nginx，它的配置直接决定了「访问对不对」。一份规范的前端 nginx.conf 要处理三件事——和上一篇静态部署的逻辑完全对应：

server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;

    # 1. SPA 路由回退：找不到文件就返回 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 2. 带 hash 的静态资源：永久强缓存
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 3. HTML 不强缓存，每次校验
    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    # 开 gzip / brotli 压缩，减小传输体积
    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;
}

三个 location 分别对应上一篇讲的：SPA 路由回退、hash 资源强缓存、HTML 不强缓存。容器里跑 Nginx 和用 CDN，缓存策略的道理是同一套，只是落地在不同层。把这份配置固化进镜像，就避免了「每个环境的 Nginx 配得不一样」的漂移。

一个常被忽略的点：容器要能被健康检查。K8s 会周期性探活，给个简单的健康端点或让 / 能返回 200 即可，别让探针失败导致容器被反复重启。

一个真实的坑：构建产物里写死了环境配置

现象：同一个镜像，在测试环境跑得好好的，推到生产就连错了后端地址。

原因：构建时（阶段一）把接口地址等配置编译进了产物（比如 .env.production 里的 VITE_API_BASE）。这样一来，一个镜像只对应一套配置，「同一镜像跑遍多环境」的优势就没了——每个环境得单独构建一个镜像。

这正是容器化和「环境配置」的交叉难点：理想是「一次构建，到处运行」，同一个镜像通过运行时注入不同配置跑遍 dev/test/prod。前端这块因为很多配置在构建期就固化了，处理起来比后端麻烦。怎么做「构建产物不锁死环境、运行时注入配置」，是下一篇《环境矩阵与配置注入》的核心话题，这里先埋个点。

小结

  1. 前端容器化的价值主要在「需要运行时（SSR）」或「团队统一用容器调度」，纯静态站 CDN 托管通常更简单。
  2. 多阶段构建是核心：一个阶段构建，另一个干净阶段只 COPY --from 拷产物，构建依赖不进最终镜像。
  3. 先拷 package.json 装依赖、再拷源码，利用层缓存让最慢的依赖安装尽量命中缓存。
  4. 瘦身手段：alpine/slim 基础镜像、.dockerignore（务必 ignore .env）、合并 RUN 并同层清理。
  5. Nginx 配置要处理 SPA 路由回退、hash 资源强缓存、HTML 不强缓存，和 CDN 缓存策略同一套道理。
  6. 容器要能被健康检查探活，避免探针失败导致反复重启。
  7. 别把环境配置编译进产物，否则「一次构建到处运行」的优势丧失——运行时注入配置是下一篇的核心。
