库构建与脚本运行工具链：tsx、tsup、unbuild 与 Vite lib mode

发表于2026|更新于2026|工程化
|字数总计:2.2k|阅读时长:8分钟

前言：前面几篇都在讲「打包一个应用」。但工程里还有两类高频需求被低估了：一是跑 TS 脚本（不想先 tsc 编译再 node 跑），二是构建一个要发布的库（不想手写一堆 Rollup/Rolldown 配置）。tsx、tsup、unbuild，再加上 Vite 自带的 lib mode，都是围绕这两件事做的封装。这一篇讲清楚它们各自解决什么、什么时候用哪个。

先分清两类需求

这些工具其实服务两个不同场景，别混：

需求 工具 一句话
跑 TS 脚本/服务 tsx 免编译直接 node 跑 TS
构建发布用的库 tsup / Vite lib mode / unbuild 封装好的库打包器

tsx：直接运行 TypeScript

写工具脚本、写 Node 服务时，原生流程很烦：先 tsc 编译成 JS，再 node 跑编译产物，改一行还得重新编译。tsx 把这一步省了——它基于 esbuild，能直接执行 TS 文件。

npm i -D tsx

// scripts/hello.ts
const msg: string = 'hello from ts'
console.log(msg)

npx tsx scripts/hello.ts        # 直接跑，不用先编译
npx tsx watch scripts/hello.ts  # 文件变了自动重跑

它适合的场景：

  • 项目里的构建/迁移/数据处理脚本（scripts/ 下那些）。
  • 本地开发时跑 TS 写的 Node 服务（配 tsx watch 当 nodemon 用）。
  • package.json 里直接用 TS 写脚本：
{
  "scripts": {
    "db:seed": "tsx scripts/seed.ts",
    "dev:server": "tsx watch src/server.ts"
  }
}

注意 tsx 是「运行」工具不是「类型检查」工具。它基于 esbuild，只做转译不做类型检查（为了快，esbuild 不检查类型）。所以 CI 里类型检查还得单独跑 tsc --noEmit，别指望 tsx 帮你拦类型错误。这点在「类型检查与构建检查分离」那篇也提过，是一回事。

tsx 和老牌的 ts-node 定位类似，但基于 esbuild 通常更快、对 ESM 支持更省心，现在新项目我更倾向 tsx。

tsup：零配置打包库

要发一个 npm 库，你需要：输出 ESM + CJS 双格式、生成 .d.ts 类型声明、可能还要压缩、生成 sourcemap。纯手写 Rollup 配置能做，但繁琐。tsup 是基于 esbuild 的封装，主打零配置出库。

npm i -D tsup

// src/index.ts
export function add(a: number, b: number) {
  return a + b
}

# 一行命令，同时出 ESM + CJS + 类型声明
npx tsup src/index.ts --format esm,cjs --dts

产物：

dist/
├── index.cjs     # CJS
├── index.mjs     # ESM
├── index.d.ts    # 类型声明

配置文件也很简洁：

// tsup.config.ts
import { defineConfig } from 'tsup'

export default defineConfig({
  entry: ['src/index.ts'],
  format: ['esm', 'cjs'], // 双格式产物
  dts: true,              // 生成 .d.ts
  sourcemap: true,
  clean: true,            // 构建前清 dist
  minify: false,          // 库一般不压缩，留给使用方
})

配合 package.json 的 exports 把双产物暴露出去（这块在「exports 条件导出与双包陷阱」那篇详细讲过）：

{
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}

tsup 的特点是快（esbuild 底层）、配置少、上手快。适合大多数普通工具库。

Vite lib mode：应用工具链顺手出库

如果你的库本来就生活在 Vite 生态里，比如组件库、前端 SDK、带 CSS 的 UI 工具包，也可以直接用 Vite 的 library mode。核心配置是 build.lib：把入口从 HTML 换成库入口，然后让 Vite 按库的方式产出 ESM/CJS/UMD 等格式。

npm i -D vite typescript

// vite.config.ts（Vite 8）
import { defineConfig } from 'vite'
import { resolve } from 'node:path'

export default defineConfig({
  build: {
    lib: {
      entry: resolve(import.meta.dirname, 'src/index.ts'),
      formats: ['es', 'cjs'],
      fileName: 'my-lib',
    },
    rolldownOptions: {
      // React/Vue 这类 peer dependency 通常不要打进库里
      external: ['vue'],
    },
  },
})

版本提醒：Vite 8 底层是 Rolldown，所以推荐写 build.rolldownOptions。如果你还在 Vite 7 及以前，常见写法是 build.rollupOptions，思路一样，字段名不同。

它和 tsup 最大的差别是：Vite lib mode 更适合已经依赖 Vite 插件体系的库。比如你有 Vue/React 插件、CSS 处理、静态资源处理、alias、环境变量这些 Vite 项目里的能力，直接用 Vite 出库会很顺手。

但它也有一个现实取舍：类型声明不是 Vite lib mode 的核心职责。要发 TS 库，通常还要配 vite-plugin-dts，或者单独跑 tsc --emitDeclarationOnly 生成 .d.ts。这一点 tsup --dts 会更省事。

unbuild：约定优于配置的库构建

unbuild 是 UnJS 生态（Nuxt 团队相关）出的库构建工具，底层用 Rollup。和 tsup 比，它更强调「约定优于配置」和稳健的产物。

npm i -D unbuild

// build.config.ts
import { defineBuildConfig } from 'unbuild'

export default defineBuildConfig({
  entries: ['src/index'],
  declaration: true, // 生成类型声明
  rollup: { emitCJS: true },
})

npx unbuild

它有个很实用的特性叫 passive watcher / stub 模式：开发库时生成一个「桩」，让本地 link 调试时不用每次改完都重新构建，源码改动直接生效。对一边开发库一边在另一个项目里联调的场景很友好。

tsup、Vite lib mode、unbuild 怎么选

维度 tsup Vite lib mode unbuild
底层 esbuild Vite 8 走 Rolldown，Vite 7 走 Rollup Rollup
风格 显式配置，灵活 沿用 Vite 配置和插件生态 约定优于配置
速度 很快 快，取决于 Vite/Rolldown 链路 较快
类型声明 --dts 很方便 通常要配插件或单独跑 tsc declaration: true
生态归属 独立 Vite 生态 UnJS（Nuxt 系）
适合 普通工具库，要细控产物 Vite 生态组件库、前端 SDK、带 CSS/资源处理的库 UnJS 风格项目，重视开发联调体验

我的判断：

  1. 大多数普通库：tsup，配置直观、快、社区用得最广。
  2. Vite 生态组件库/前端 SDK：Vite lib mode，复用现有 Vite 插件和 CSS/资源处理能力。
  3. UnJS 风格项目，或重视 stub 联调：unbuild。
  4. 要极致控制产物细节（复杂多入口、特殊插件）：直接用 Rollup/Rolldown，别封装。

这几个本质都是「底层打包器的场景化封装」，帮你少写配置。理解了前面 Rollup、Vite、Rolldown 那几篇，你会发现它们只是把常见库构建配置预设好了而已。

这些工具在工具链里的位置

回到坐标系视角：

跑 TS 脚本         →  tsx（基于 esbuild，只转译不检查类型）
打包应用           →  Vite
打包库             →  tsup / Vite lib mode / unbuild
类型检查           →  tsc --noEmit（始终单独跑）

一个关键认知：这些都不是「新打包器」，而是对底层引擎的场景化封装。它们存在的意义是让你针对「跑脚本」「出库」这些具体场景少配置、快上手。底层还是你已经认识的 esbuild、Rollup/Rolldown。

一个完整的库构建示例

mkdir my-lib && cd my-lib
npm init -y
npm i -D tsup typescript

// src/index.ts
export const greet = (name: string): string => `Hello, ${name}!`

// package.json 关键字段
{
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  },
  "scripts": {
    "build": "tsup src/index.ts --format esm,cjs --dts --clean",
    "typecheck": "tsc --noEmit"
  }
}

npm run build
# dist/ 下同时有 index.cjs (CJS)、index.mjs (ESM)、index.d.ts
npm run typecheck   # 类型检查单独跑，tsup 不负责

跑完这个例子，你就拥有了一个能同时被 import 和 require、带类型提示的标准 npm 库雏形。

这里的关键是：既然 package.json 里写了 "type": "module"，普通 .js 文件会被 Node 当成 ESM，所以 CJS 产物要用 .cjs 后缀。否则你把 require 指到 ./dist/index.js，使用方在 CommonJS 里加载时就可能直接报错。

小结

  1. 先分需求：跑 TS 脚本用 tsx，构建发布库用 tsup、Vite lib mode 或 unbuild。
  2. tsx 基于 esbuild 免编译直接跑 TS，适合脚本和本地服务，但只转译不做类型检查。
  3. tsup 零配置出 ESM + CJS + 类型声明，底层 esbuild，是大多数库的首选。
  4. Vite lib mode 适合 Vite 生态库，尤其是组件库、前端 SDK、需要复用 Vite 插件和 CSS/资源处理的项目。
  5. unbuild 底层 Rollup、约定优于配置，stub 模式对库联调很友好，适合 UnJS 风格项目。
  6. 无论用哪个，类型检查永远单独跑 tsc --noEmit，别指望转译工具帮你拦类型错误。
