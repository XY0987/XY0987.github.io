TypeScript 类型检查与构建检查分离

发表于2026|更新于2026|工程化
|字数总计:1.7k|阅读时长:6分钟

前言：很多项目里 tsc、Vite、Webpack、ESLint 被混在一起用，最后大家只知道“构建失败了”，但不知道到底是类型错了、语法错了，还是打包配置错了。工程化里一个很重要的能力，就是把检查职责拆清楚。

类型检查和构建不是一回事

先说结论：TypeScript 类型检查和项目构建应该分开看。

它们关注的问题不同：

检查 主要工具 关注点
类型检查 tsc --noEmit 类型是否正确
代码规范 ESLint 代码质量和潜在错误
构建检查 Vite / Webpack / Rspack 产物是否能正常打包
测试检查 Vitest / Jest / Playwright 行为是否符合预期

一个项目能构建成功，不代表类型一定严谨。

一个项目类型检查通过，也不代表最终产物一定能打包成功。

比如下面这段代码：

import data from './config.json'

console.log(data.name)

TypeScript 是否通过，取决于 resolveJsonModule 等配置。

构建是否通过，则取决于 bundler 是否支持这个导入方式，以及相关插件是否配置正确。

所以不要把所有问题都粗暴归为“构建失败”。

为什么很多构建工具不做完整类型检查

以 Vite 这类现代构建工具为例，开发阶段更关注速度。它通常依赖 esbuild、SWC 等工具快速转译 TypeScript。

这里要注意一个关键点：

转译 TypeScript 不等于检查 TypeScript 类型。

比如：

const count: number = '1'
console.log(count)

很多转译工具可以把它转成 JavaScript，因为类型标注会被擦除。

const count = '1'
console.log(count)

但这段代码明显有类型错误。

如果只跑构建，不跑 tsc --noEmit，这类问题就可能漏掉。

推荐的脚本拆分

我通常会这样设计 package.json：

{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "test": "vitest run",
    "check": "pnpm lint && pnpm typecheck && pnpm test && pnpm build"
  }
}

这里每个命令都很明确：

命令 职责
dev 本地开发
build 生成生产产物
typecheck 只做类型检查，不输出文件
lint 做静态规则检查
test 跑自动化测试
check CI 的统一入口

这比一个 npm run build 里面偷偷做所有事情更容易维护。

noEmit 为什么重要

类型检查脚本里常见写法是：

tsc --noEmit

--noEmit 的意思是只检查类型，不生成 JavaScript 和声明文件。

它适合应用项目，因为应用项目通常由 Vite、Webpack、Rspack 负责产物输出，tsc 不应该再生成一份重复产物。

对于库项目，情况要分开看：

项目类型 建议
前端应用 tsc --noEmit 做类型检查，bundler 负责构建
工具库 tsc 可以负责生成声明文件
组件库 bundler 生成 JS，tsc 或 vue-tsc 生成类型声明

不要看到 TypeScript 就默认让 tsc 负责所有产物。

Vue 项目要注意 vue-tsc

如果是 Vue + TypeScript 项目，仅使用 tsc --noEmit 不够，因为 .vue 单文件组件里的模板类型需要额外处理。

常见脚本：

{
  "scripts": {
    "typecheck": "vue-tsc --noEmit",
    "build": "vite build"
  }
}

如果是 React 项目，一般 tsc --noEmit 就够用。

如果是 Svelte、Angular 等框架，也应该使用对应生态推荐的类型检查命令。

核心原则是：类型检查命令要理解你的源码形态。

类型检查放在哪里跑

类型检查有三个常见位置：

位置 是否推荐 原因
保存时 不推荐全量 大项目太慢
pre-commit 谨慎 全量 typecheck 容易拖慢提交
CI 必须 主干质量最后防线

我更推荐：

  • 本地开发依赖编辑器 TypeScript Server 实时提示；
  • 提交前只做轻量 lint 和格式化；
  • CI 里跑完整 typecheck。

如果团队项目比较小，也可以在 pre-push 里跑类型检查。

但我不建议默认放进 pre-commit。提交是高频动作，慢了就会影响体验。

构建检查解决什么

类型检查通过后，仍然需要构建检查。

因为构建会暴露另一类问题：

  • import 路径大小写在不同系统下不一致；
  • 动态导入写法 bundler 不支持；
  • CSS、图片、字体等资源处理失败；
  • 环境变量缺失；
  • 生产构建 tree-shaking 或压缩报错；
  • 第三方包 ESM/CJS 兼容问题。

比如：

import logoUrl from './assets/logo.svg'

TypeScript 可能只需要一份声明文件：

declare module '*.svg' {
  const url: string
  export default url
}

但构建工具还需要真的知道如何处理 .svg。

类型声明只能让 TypeScript 不报错，不能替 bundler 完成资源处理。

CI 里的推荐顺序

我一般会把 CI 检查顺序设计成这样：

install
  │
  ▼
format:check
  │
  ▼
lint
  │
  ▼
typecheck
  │
  ▼
test
  │
  ▼
build

原因是越便宜的检查越早跑。

格式、lint 通常最快，失败也最容易修。构建和测试可能更耗时，放后面更合理。

对应脚本：

{
  "scripts": {
    "format:check": "prettier . --check",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "build": "vite build",
    "ci": "pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm build"
  }
}

如果项目很大，可以把这些任务拆成并行 job，但逻辑上仍然要保持职责清楚。

monorepo 里的类型检查

monorepo 里如果所有包都直接跑一遍 tsc --noEmit，很容易变慢。

可以结合前面阶段讲过的 Project References：

{
  "scripts": {
    "typecheck": "tsc -b --pretty"
  }
}

tsc -b 会按引用关系构建检查，适合多包项目。

也可以按包拆：

{
  "scripts": {
    "typecheck": "pnpm -r --parallel typecheck"
  }
}

选择哪种方式取决于项目结构。我的经验是：

  • 包之间类型依赖强，用 Project References；
  • 包之间比较独立，用包级脚本并行；
  • 大型仓库再引入 Turborepo、Nx 这类任务编排工具。

不要一上来就把任务编排工具作为默认答案，先把基本命令拆清楚。

小结

  1. TypeScript 类型检查、ESLint、测试、构建检查是不同职责，不要混成一个概念。
  2. tsc --noEmit 适合应用项目做类型检查，产物输出通常交给 bundler。
  3. Vue 项目要使用 vue-tsc 这类能理解框架文件的检查工具。
  4. 类型检查适合放在 CI 里完整执行，pre-commit 里要谨慎。
  5. 构建检查仍然必要，因为类型通过不代表资源、环境和打包链路一定通过。
