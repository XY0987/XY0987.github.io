Skills 工程化：怎么做一个好 Skill 与它的可观测性

发表于2026|更新于2026|AI相关
|字数总计:4.3k|阅读时长:13分钟

前言：上一篇《Skills 与 MCP 对比解析》讲清了 Skill 是什么、目录怎么组织、frontmatter 有哪些字段。这篇不重复那些基础，专门解决两个更工程化的问题：怎么写出一个真正好用的 Skill，以及 Skill 上线后怎么观测它到底有没有在干活。前者决定 Skill 能不能用，后者决定 Skill 值不值得留。

先定义”好 Skill”的标准

写之前得先想清楚，一个 Skill 好不好，看的到底是什么。我的标准就四条：

  1. 该触发的时候能触发——用户用大白话描述任务，它能被 AI 认出来
  2. 触发之后产出稳定——同类任务反复跑，结果都符合预期，而不是看运气
  3. token 开销可控——没被用到时几乎不占上下文，用到时也不臃肿
  4. 可维护、可观测——能知道它被用了多少次、成功率如何，能判断该不该淘汰

前两条是”怎么做一个好 Skill”，后两条里第 3 条靠渐进式披露解决（上篇讲过），第 4 条就是这篇的重点：可观测性。

一个反直觉但重要的事实先摆在这：一个 Skill 被触发，只能说明 AI 找到了它，不能说明它干对了活。官方文档原话是”Seeing a skill trigger tells you Claude found it, not that it did what you intended”。这句话是整篇可观测性部分的地基。

第一部分：怎么做一个好 Skill

description 是命门，触发全靠它

Skill 有没有用，一大半取决于 description 写得好不好。因为 AI 在决定”要不要用这个 Skill”时，看的只有 name + description 这点元数据，正文要等触发之后才加载。description 写砸了，正文写得再好也没人看。

Anthropic 自己在 skill-creator 里承认了一个倾向：Claude 有”undertrigger”（该用不用）的毛病。所以他们的建议是把 description 写得”pushy”一点——不光说”这个 Skill 是干嘛的”，还要明确列出”什么场景、用户说什么话时该用我”。

# ❌ 反面案例：只说了"是什么"，没说"什么时候用"
description: 构建一个展示内部数据的快速仪表盘

# ✅ 正面案例：是什么 + 什么时候用 + 触发词
description: >
  构建展示内部数据的快速仪表盘。当用户提到 dashboard、数据可视化、
  内部指标，或想展示任何公司数据时都要用这个 Skill——哪怕他没明说
  "仪表盘"这个词。

写 description 的三个要点：

  • 是什么 + 什么时候用，两者都要有，且”什么时候用”要写在 description 里，不要写在正文（正文触发后才加载，写在正文里的”使用场景”对触发毫无帮助）
  • 塞进用户会自然说出口的触发词，包括同义表达、口语、甚至可能的错别字场景
  • 控制长度：Claude Code 里 description + when_to_use 合起来会在技能清单中被截断到 1536 字符，所以把最关键的用途写在最前面

正文要精简，但该讲的 why 要讲清

Skill 一旦被加载，正文会作为一条消息常驻在整个会话上下文里，后续每一轮对话都在为它付 token。所以正文的原则是：每一行都得”配得上”它占的那点上下文。官方给的硬指标是 SKILL.md 正文控制在 500 行以内，接近这个数就该往 references/ 拆。

但”精简”不等于”不讲道理”。这里有个容易搞反的点：

  • 官方文档说正文要 “state what to do rather than narrating how or why”——指的是别写叙述性废话（背景故事、显而易见的解释、凑字数的铺垫）
  • 而 skill-creator 又反复强调 “explain the why”——指的是对那些反直觉的约束，要给出理由

这俩不矛盾。合起来就是：砍掉没营养的叙述，但对”你要求模型做、而它可能不理解或想跳过”的关键约束，一定要解释为什么。原因很实在——现在的模型很聪明，你越是堆 ALWAYS / NEVER 这种全大写的死命令，它越容易当成可以打折扣的教条；你把道理讲明白，它反而会认真执行。

如果你发现自己在正文里写了一堆全大写的 MUST，这是个黄灯信号——试着把它改成”为什么这么做”。

重复出现的确定性动作，抽成脚本

判断一个操作该不该写成脚本，有个特别实用的信号：如果同一类任务跑几次，AI 每次都自己现写一段功能差不多的代码（比如每次都手搓一个 build_chart.py），那就说明这段逻辑该被固化下来，写一次放进 scripts/，让 Skill 直接调。

这么做有两个好处：一是结果确定（脚本是确定性的，不像 AI 推理会飘）；二是省 token——脚本是被”执行”的，不是被”读进上下文”的，它的代码体量不占对话上下文。

判断标准：
  这个动作是"确定性"的吗（校验、转换、计算、扫描）？
        │
        ├── 是 → 写成 scripts/ 里的脚本，让 AI 调用
        └── 否（需要理解、判断、生成）→ 留给 AI，在正文里给指引

抽出来的脚本，要当生产代码写

脚本一旦固化，它就不再是”一次性胶水代码”——每次 Skill 被触发它都会执行一遍，而且常常要去碰外部服务。所以别用玩具代码的标准写它，重点是四件事：

  • 参数校验 + 显式报错：AI 传参不保证对。校验不过就在 stderr 上给一句人和 AI 都看得懂的错误、然后非零退出。脚本的输出会回灌给 AI，一句清晰的报错等于给了它自我纠正的机会；反过来，静默失败或一堆原始堆栈，只会让 AI 瞎猜、越修越乱。
  • 降级策略：依赖的下游（API、DB、第三方）随时可能挂，别让一个超时拖垮整个 Skill。能降级就降级（退回缓存或部分结果，并标注 degraded: true）；实在降不了，也要把”哪一步失败、为什么、下一步能怎么办”讲清楚，而不是抛个裸异常。
  • 关键上下文上报：在关键节点把输入摘要、调了哪个下游、参数、耗时结构化地记下来（JSONL）。线上一崩，这就是你的黑匣子——否则你只知道”Skill 失败了”，不知道死在哪一步。
  • 指标制定：给脚本定几个反映健康度的数——调用耗时、成功率、下游错误率、降级触发次数。这些数字攒起来，才答得出”这个 Skill 到底稳不稳”。

后两点尤其关键，因为它们正好补上第二部分那个缺口：Hook 的 PostToolUse 只能靠 grep 产出文本里有没有 “error” 来粗判成败，很脆；而脚本自己上报的 outcome 才是最可靠的语义级信号——这一次到底成没成、慢不慢、有没有降级，最清楚的就是干活的脚本本身。

具体怎么校验、怎么降级、上报哪些字段，各业务差别很大，这里不铺开写代码，读者按自己的场景评估即可。要记住的原则只有一条：**让脚本在关键节点结构化地记下”成没成、慢不慢、有没有降级”**。这样脚本自报的结果，就能和第二部分 Hook 落的日志合起来看——Hook 负责”哪个 Skill 被调了”，脚本负责”这次在业务上跑得怎么样”，观测粒度就从”跑没跑”下沉到了”每一步跑得怎么样”。

用渐进式披露组织知识

正文放”核心流程 + 选择指引”，详细知识放 references/。关键是：**从 SKILL.md 里明确引用这些文件，并说清楚”什么时候该去读它”**，否则模型根本不知道有这些文件存在。

cloud-deploy/
├── SKILL.md          # 主流程 + 平台选择指引
└── references/
    ├── aws.md        # 只在部署 AWS 时读
    ├── gcp.md        # 只在部署 GCP 时读
    └── azure.md      # 只在部署 Azure 时读

单个 reference 文件超过 300 行时，给它加个目录（TOC），方便模型定位。

一句话总结好 Skill 的写法

description 决定它会不会被用，正文的精简度决定它的 token 成本，脚本决定它的确定性，references 决定它的知识密度而不撑爆上下文。四者到位，才算一个工程上”好”的 Skill。但——写完不等于好用，得靠观测和评测验证。

第二部分：Skills 的可观测性

核心认知：触发 ≠ 生效

再强调一遍开头那句话。要判断一个 Skill 到底行不行，得把它拆成两个独立的问题分别去测：

Skill 是否有效 = 两个正交的问题
┌───────────────────────────┬───────────────────────────┐
│  问题 A：该触发时触发了吗？   │  问题 B：触发后产出对吗？     │
│  （召回 / triggering）       │  （质量 / output quality）  │
├───────────────────────────┼───────────────────────────┤
│  靠 description 调优         │  靠正文/脚本/references 调优 │
│  用 should-trigger 集合测    │  用 baseline 对比测          │
└───────────────────────────┴───────────────────────────┘

很多人只盯着”它被调用了没有”，这只回答了半个问题。生产环境里最坑的情况是：Skill 触发了，但产出是错的——日志上看着一切正常，实际全在裸奔。

触发问题排查：先用诊断三件套

Skill 触发环节出问题，Claude Code 里有几个现成命令能定位：

命令 看什么
/skills 从 project / user / plugin 加载到了哪些 Skill，带 user-only 之类的徽标
/context 当前上下文里各部分占用，Skills 那一行是应用预算之后的清单大小
/doctor 配置体检：清单的上下文成本估算、最占预算的 Skill、无效设置
claude --debug YAML 解析报错、清单超预算的告警等底层日志

对着现象查原因，基本能一条一条对上：

现象 可能原因 排查 / 修复
Skill 没出现在 /skills 放成了 .claude/skills/name.md，而不是目录 改成 .claude/skills/name/SKILL.md（必须是目录 + SKILL.md）
/skills 有但从不自动触发 frontmatter 里 disable-model-invocation: true（徽标显示 user-only）；或 description 太泛 看徽标；user-only 只能 /name 手动调；否则收窄 description
该触发时不触发 description 缺用户会说的关键词；或任务太简单，AI 自己就能干 description 加自然措辞的触发词；确认任务确实复杂到需要 Skill
触发太频繁 description 太宽泛 description 写具体；必要时加 disable-model-invocation
YAML 写错了但 /name 还能用 frontmatter 解析失败，正文照常加载，但 description 为空、无法匹配 claude --debug 看解析报错

这里有个隐蔽的坑值得单独拎出来——清单预算（listing budget）。

Claude Code 会把所有 Skill 的 name + description 拼成一份清单放进上下文，好让 AI 知道有哪些技能可用。这份清单有预算上限，默认是模型上下文窗口的 1%（skillListingBudgetFraction）。Skill 一多，清单超预算，Claude Code 会从”你最少用的 Skill”开始砍掉它们的 description——名字还在，但描述没了，于是模型再也无法自动匹配到它。现象就是：明明 /skills 里列着，却怎么都不触发。

排查靠 /doctor 看清单成本；治理有几招：把低优先级的 Skill 在 skillOverrides 里设成 "name-only" 腾预算、调大 skillListingBudgetFraction、或者干脆精简 description 文本。

还有一条反直觉的机制值得知道：AI 只有在”自己搞不定”的任务上才会去查 Skill。像”读一下这个 PDF”这种一步就能干完的简单请求，哪怕 description 匹配得再完美，也可能不触发——因为模型觉得自己直接就能处理。所以别拿”读文件 X”这种简单 prompt 去测触发率，测不出东西。

质量问题评测：baseline 对比法

触发对了，接下来测产出质量。官方推荐的办法很朴素，就是baseline 对比：

  1. 收集几个真实的测试 prompt
  2. 每个 prompt 在全新会话里跑两遍——一遍开着 Skill，一遍关掉 Skill
  3. 对比两次结果，看开 Skill 到底带来了什么改善

为什么强调”全新会话”？因为你在写这个 Skill 时的上下文（讨论、调试痕迹）会残留在当前会话里，掩盖掉 Skill 指令本身的漏洞——你以为是 Skill 写得好，其实是会话里早有铺垫。开新会话才能测出 Skill 真实的独立表现。

如果想把这个循环自动化，Anthropic 官方有个 skill-creator 插件：

/plugin install skill-creator@claude-plugins-official

装好之后，让它评测一个已有 Skill（比如”evaluate my summarize-changes skill with skill-creator”），它会把整套流程跑一遍：

  • 测试用例：prompt、输入文件、期望行为存到 Skill 目录下的 evals/evals.json
  • 隔离运行：每个用例开一个独立 subagent 跑，上下文干净，并记录 token 数和耗时
  • 打分：逐条断言（assertion）对照产出，通过/失败带证据写进 grading.json
  • 基准对比：把”开 Skill vs 不开 Skill”的通过率、耗时、token 聚合进 benchmark.json，让你权衡”通过率的提升值不值这点 token 和时间开销”
  • 描述调优：自动生成 should-trigger / should-not-trigger 两类 prompt，测命中率，触发不准时给出 description 的修改建议

description 调优这步尤其值得注意它怎么造测试集：**最有价值的负样本是”近似命中”**——那些跟 Skill 共享关键词、但其实需要别的工具的请求。用”写个斐波那契函数”去测一个 PDF Skill 的负样本毫无意义，因为它太好区分了，什么都测不出来。

从”跑没跑”到”跑对没”：生产环境观测

上面是开发期的评测。Skill 上了生产、每天被真实用户触发几十上百次之后，你需要的是持续的观测数据：谁在什么时候、因为什么触发了哪个 Skill，跑成功了还是失败了。

这里有个关键区分，也是社区实践里踩得最多的坑：**原生遥测（telemetry）只能回答”它跑了没”，回答不了”它跑对没”**。

以 OpenTelemetry 方案为例（DEV 社区有人分享过 Loki + OTEL 的完整搭法，可作参考）：

  • Skill 的激活是事件（log），不是指标（metric）。光靠 Prometheus 这类指标系统只能告诉你”某 Skill 消耗了多少 token”，答不出”谁、何时、因何触发”——那需要日志管线
  • 有个必坑：不开 OTEL_LOG_TOOL_DETAILS=1 的话，你自定义的 Skill 名字会全部塌缩成一个占位符 custom_skill，看板照渲染，但七个 Skill 显示成七行 custom_skill，等于白采
  • 更要命的是，遥测里的 success 反映的是 harness 层面有没有失败，不等于业务语义上的成功。一个 bash -c "exit 1" 在遥测里可能还是 success=true

结论就是：想知道 Skill 有没有”干对活”，得让 Skill 自己上报结果，或者用 Hook 去检查它的输出。 下一节就动手做这件事。

观测数据反哺 Skill 迭代

可观测性不是为了做看板好看，最终要回到”把 Skill 改好”上。数据能直接指导迭代：

  • 某 Skill 触发次数为 0 → description 有问题（关键词不对/被预算砍了），或这需求根本不存在，考虑删
  • 触发很多但 error 比例高 → 正文指令或脚本有问题，回到 baseline 对比去定位是哪一步崩的
  • 触发场景明显跑偏（该 A 触发的却是 B）→ 用 skill-creator 的 description 调优跑一轮 should-trigger / should-not-trigger

观测提供信号，评测定位问题，迭代解决问题——三者接成闭环，Skill 才会越用越准，而不是装完就烂在那。

小结

  1. description 是 Skill 的命门，AI 只凭 name + description 决定用不用它，要写”pushy”、含触发词、把关键用途放最前（1536 字符会被截断）
  2. 正文控制在 500 行内且常驻上下文，砍掉叙述性废话，但对反直觉的关键约束要讲清 why，少用全大写 MUST
  3. 反复出现的确定性动作抽成 scripts，脚本被执行而非读入上下文，既稳又省 token；且要当生产代码写——参数校验、下游降级、关键上下文与指标上报，脚本自报的 outcome 是最可靠的语义级观测信号
  4. 一个 Skill 被触发只代表”被找到了”，不代表”干对了”，要把触发和产出质量拆成两个正交问题分别测
  5. 触发问题用 /skills、/context、/doctor、--debug 四件套排查，重点留意清单预算把冷门 Skill 的 description 砍掉的坑
  6. 质量问题用 baseline 对比（全新会话开/关 Skill 跑同一 prompt），可用官方 skill-creator 插件自动化
  7. 原生遥测只能答”跑没跑”，答不了”跑对没”，语义级成功要靠 Skill 自报或 Hook 检查
  8. 用 PreToolUse / PostToolUse Hook 把调用和结果落成本地 JSONL，几行 shell 就能算触发排行、死技能和失败率，最后把观测数据反哺回 description 与正文的迭代
