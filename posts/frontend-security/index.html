前端安全：XSS、CSRF、点击劫持与常见防御实战

发表于2026|更新于2026|前端基础
|字数总计:3.5k|阅读时长:13分钟

前言

前端安全这块儿，面试常问、生产常踩坑，但很多同学的理解还停留在「XSS 是注入脚本、CSRF 是伪造请求」这种字面层面。真到写代码的时候，并不知道哪一行是隐患、应该怎么改。

这篇我把工作中常见的几类前端安全问题串起来：XSS、CSRF、点击劫持、CSP、Cookie 安全。不堆理论，重点说清楚攻击是怎么发生的、代码上具体怎么防。

一、同源策略：所有讨论的起点

聊前端安全绕不开同源策略（Same-Origin Policy，SOP）。这是浏览器的默认安全底线：不同源的页面之间，默认禁止读取对方资源。

「同源」的定义：协议、域名、端口三者完全一致。

URL A URL B 是否同源
https://a.com/page https://a.com/api 是
http://a.com https://a.com 否（协议不同）
https://a.com https://b.a.com 否（域名不同）
https://a.com:80 https://a.com:8080 否（端口不同）

同源策略限制的是读取，不是发送。这一点很关键，也是 CSRF 能成立的根本原因——浏览器允许跨源发请求，只是不让 JS 读响应。

很多前端安全问题，本质上就是「攻击者绕过了同源策略」或「同源策略管不到的场景」。

二、XSS：跨站脚本攻击

XSS（Cross-Site Scripting）的核心：让攻击者的 JS 代码在受害者的浏览器里、用受害者的身份执行。一旦成功，攻击者可以读 Cookie、改页面、发请求，相当于偷走了用户的身份。

2.1 三种 XSS 类型

类型 攻击载荷存在哪 典型场景
存储型 服务器数据库 评论区、个人资料
反射型 URL 参数 搜索结果、错误提示页
DOM 型 不经过服务器，纯前端 location.hash、document.write

存储型危害最大，因为能稳定影响所有访问者。反射型需要诱导点击。DOM 型是纯前端漏洞，后端日志里都看不到。

2.2 一个最朴素的 XSS 案例

假设有这样一段代码：

// ❌ 反面案例：直接把用户输入塞进 innerHTML
const keyword = new URLSearchParams(location.search).get('q');
document.getElementById('result').innerHTML = `搜索：${keyword}`;

只要访问 https://site.com/search?q=<img src=x onerror=alert(1)>，弹窗就出来了。如果把 alert(1) 换成偷 Cookie 的代码，账号就丢了。

2.3 防御核心：输出编码 + 不信任输入

防 XSS 没有银弹，但有一条铁律：永远不要把不可信内容直接拼进 HTML/JS/URL。在不同上下文里要做不同的编码处理。

// ✅ 用 textContent 而不是 innerHTML，浏览器会自动转义
document.getElementById('result').textContent = `搜索：${keyword}`;

// ✅ 必须用 HTML 时，先转义
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}
document.getElementById('result').innerHTML = `搜索：${escapeHtml(keyword)}`;

框架场景：React、Vue 默认会对插值内容做 HTML 转义，正常写 {userInput} 或 {{ userInput }} 都是安全的。但下面这几个 API 是「逃生舱」，等于自己手动绕过了框架的保护：

// ❌ React：危险
<div dangerouslySetInnerHTML={{ __html: userInput }} />

// ❌ Vue：危险
<div v-html="userInput"></div>

如果业务真的需要渲染富文本（比如用户写的文章），不要自己手写转义，用成熟的库做白名单过滤：

// 用 DOMPurify 清洗，只保留安全的标签和属性
import DOMPurify from 'dompurify';

const safeHtml = DOMPurify.sanitize(userInput);
element.innerHTML = safeHtml;

DOMPurify 是目前社区最常用的方案，维护活跃，默认配置就能挡住绝大部分注入。

2.4 容易被忽视的几个坑

坑 1：URL 上下文里的 XSS

// ❌ 攻击者传 javascript:alert(1)，点一下就执行
<a href={userUrl}>点我</a>

防御：校验协议必须是 http/https/mailto 等白名单。

坑 2：富文本编辑器

任何接收富文本的地方都是 XSS 重灾区，必须服务端 + 前端双重清洗。只在前端 sanitize 是不够的，攻击者可以直接调你的 API。

三、CSRF：跨站请求伪造

CSRF（Cross-Site Request Forgery）的核心：借用受害者已登录的身份，让浏览器替攻击者发请求。受害者甚至不需要打开攻击者的网站，看一封 HTML 邮件、点一个图片链接都可能中招。

3.1 攻击是怎么成立的

关键在于浏览器有个「自动带 Cookie」的特性：只要请求目标是 bank.com，浏览器就会自动带上 bank.com 的 Cookie，不管这个请求是从哪个页面发起的。

举个例子，用户登录了 bank.com，浏览器存了登录 Cookie。用户又打开了攻击者的 evil.com，页面里有：

<!-- 用户一访问 evil.com，浏览器就发了一个带 Cookie 的转账请求 -->
<img src="https://bank.com/transfer?to=hacker&amount=10000" />

银行后端一看，Cookie 是合法的，就执行了转账。这就是 CSRF。

3.2 防御方案对比

方案 原理 优缺点
CSRF Token 服务端下发随机 token，请求时一并提交 兼容性最好，需要后端配合
SameSite Cookie 限制 Cookie 在跨站请求中是否携带 简单有效，现代浏览器支持
校验 Referer/Origin 后端检查请求来源 容易被绕过、可能被代理剥离

3.3 SameSite：现在最推荐的第一道防线

SameSite 是 Cookie 的一个属性，控制跨站请求时是否携带 Cookie。

值 含义
Strict 完全不发送，跨站点击链接都不带
Lax 顶级导航的 GET 请求会带（默认值，Chrome 80+）
None 任何跨站请求都带，必须配合 Secure 
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax

Chrome 从 80 版本开始把 SameSite 默认值设为 Lax，这一改动直接干掉了大量经典 CSRF 攻击。但别只靠它：

  • 老浏览器不一定支持
  • Lax 对 GET 跳转还是放行的，所以不要把改数据的接口写成 GET
  • 如果业务必须 SameSite=None（比如第三方嵌入），就一定要加 CSRF Token

3.4 CSRF Token：兜底方案

// 前端：从 meta 标签或 Cookie 里读 token，放到请求头
const token = document.querySelector('meta[name="csrf-token"]').content;

fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': token,
  },
  body: JSON.stringify({ to: 'alice', amount: 100 }),
});

服务端校验 X-CSRF-Token 是否和 Session 里存的一致。攻击者的 evil.com 因为同源策略读不到这个 token，伪造的请求自然过不了校验。

四、点击劫持

点击劫持（Clickjacking）：攻击者把目标网站用 iframe 嵌入到自己的页面里，调透明度盖在一个诱饵按钮上，用户以为点的是「领红包」，实际点的是「转账确认」。

4.1 攻击示意

<!-- 攻击者的页面 -->
<style>
  iframe {
    position: absolute;
    opacity: 0.0001;  /* 几乎透明 */
    z-index: 2;
    width: 500px; height: 500px;
  }
  button {
    position: absolute;
    z-index: 1;
  }
</style>

<button>点我领 100 元红包</button>
<iframe src="https://bank.com/transfer-confirm"></iframe>

按钮的位置正好对齐 iframe 里的「确认」按钮，用户一点就上钩。

4.2 防御：禁止被嵌入

两种方式，**优先用 CSP 的 frame-ancestors**：

# 方式一（现代，推荐）：CSP frame-ancestors
Content-Security-Policy: frame-ancestors 'none'

# 方式二（老）：X-Frame-Options
X-Frame-Options: DENY              # 完全禁止被嵌入
X-Frame-Options: SAMEORIGIN        # 仅允许同源嵌入

X-Frame-Options 已经被 CSP 取代，但作为兼容性兜底两个一起加也无妨。

业务确实需要被某些站点嵌入（比如开放给合作伙伴）：

Content-Security-Policy: frame-ancestors 'self' https://partner.com

五、CSP：内容安全策略

CSP（Content Security Policy）是一个 HTTP 响应头，通过白名单告诉浏览器哪些资源可以加载、哪些脚本可以执行。它是 XSS 之后的「最后一道防线」——即使代码里漏过了一个注入点，CSP 也能挡住注入脚本的执行。

5.1 一个基础配置

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.jsdelivr.net;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  object-src 'none';
  base-uri 'self';

含义解释：

指令 作用
default-src 兜底策略，其他没指定的都用这个
script-src 控制 JS 能从哪里加载、能否 inline
style-src 控制样式来源
img-src 控制图片来源
connect-src 控制 fetch/XHR/WebSocket 请求目标
frame-ancestors 控制谁能用 iframe 嵌入本页
object-src 控制 <object>/<embed>/<applet>

加上这套策略后，下面这种注入即使被打进页面里也不会执行：

<!-- 浏览器拒绝执行：违反 script-src 'self' -->
<script src="https://evil.com/steal.js"></script>

<!-- 浏览器拒绝执行：违反 'unsafe-inline' 限制 -->
<script>alert(document.cookie)</script>

5.2 inline 脚本怎么办

CSP 默认不允许 <script>...</script> 这种 inline 写法。两种解决思路：

思路 1：把所有 inline 脚本改成外部文件（最干净）

思路 2：用 nonce 或 hash 放行

<!-- 服务端给每个 inline 脚本生成一个随机 nonce -->
<script nonce="rAnd0m123">
  console.log('inline script');
</script>

Content-Security-Policy: script-src 'self' 'nonce-rAnd0m123'

六、Cookie 安全三件套

Cookie 是会话凭证，被偷了等于被盗号。设置 Cookie 的时候记得加这三个属性：

Set-Cookie: session=abc123;
            HttpOnly;          # JS 读不到（防 XSS 偷 Cookie）
            Secure;            # 仅 HTTPS 才发送（防中间人）
            SameSite=Lax;      # 限制跨站携带（防 CSRF）
            Path=/;
            Max-Age=3600
属性 防御目标
HttpOnly 即使有 XSS 也读不到 Cookie
Secure 防止 Cookie 在 HTTP 链路被窃听
SameSite 防 CSRF

注意：HttpOnly 防的是 document.cookie 读取，不能防 XSS 替你发请求。XSS 真要做坏事，可以直接用受害者的浏览器去调 /api/transfer，根本不用偷 Cookie。所以 HttpOnly 是减损，不是免疫。

七、其他容易踩的坑

7.1 window.opener 钓鱼

<!-- ❌ 在新标签打开第三方链接，对方页面可以通过 window.opener 控制原页面 -->
<a href="https://other.com" target="_blank">外链</a>

对方页面可以执行：

window.opener.location = 'https://phishing.com';

把原标签页跳转到钓鱼页面。修复：

<a href="https://other.com" target="_blank" rel="noopener noreferrer">外链</a>

rel="noopener" 切断 window.opener 引用，noreferrer 顺带不发 Referer。现代浏览器对 target="_blank" 已经默认隐式加了 noopener，但显式写出来更稳。

7.2 postMessage 不验来源

// ❌ 谁来的消息都收
window.addEventListener('message', (e) => {
  document.getElementById('content').innerHTML = e.data;
});

// ✅ 校验 origin
window.addEventListener('message', (e) => {
  if (e.origin !== 'https://trusted.com') return;
  // 同时也要 sanitize e.data，不能直接 innerHTML
  document.getElementById('content').textContent = e.data;
});

7.3 第三方依赖的供应链风险

npm install 进来的包可能藏后门，构建产物里加几行恶意代码就能拿用户数据。基础动作：

  • 锁定版本（package-lock.json / yarn.lock 提交进仓库）
  • 定期跑 npm audit 或接入 Snyk 等扫描工具
  • CDN 引入的脚本加 SRI（Subresource Integrity）
<script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-xxxxxxxx"
  crossorigin="anonymous">
</script>

浏览器会校验文件 hash，被篡改了就不执行。

八、一个最小可运行的 XSS + CSP 演示

<!-- demo.html -->
<!DOCTYPE html>
<html>
<head>
  <meta charset="utf-8">
  <!-- 用 meta 标签声明 CSP（仅做演示，生产环境优先用 HTTP 头） -->
  <meta http-equiv="Content-Security-Policy"
        content="default-src 'self'; script-src 'self'">
</head>
<body>
  <input id="input" placeholder="试试输入 <img src=x onerror=alert(1)>">
  <button id="btn-bad">用 innerHTML（危险）</button>
  <button id="btn-good">用 textContent（安全）</button>
  <div id="output"></div>

  <script src="./demo.js"></script>
</body>
</html>

// demo.js
const input = document.getElementById('input');
const output = document.getElementById('output');

document.getElementById('btn-bad').addEventListener('click', () => {
  // 危险写法：注入的 <img onerror> 会被解析
  output.innerHTML = input.value;
});

document.getElementById('btn-good').addEventListener('click', () => {
  // 安全写法：所有内容当作纯文本
  output.textContent = input.value;
});

跑这个 demo 你会发现：

  1. 点「危险」按钮，输入 <img src=x onerror=alert(1)> 在没有 CSP 的情况下会弹窗
  2. 加上 CSP 的 script-src 'self' 后，inline 的 onerror 被浏览器拒绝执行
  3. 「安全」按钮永远不会触发脚本，因为内容只当文本处理

这也呼应了开头的判断：XSS 防御是分层的，输入校验、输出编码、CSP，缺一道都可能被打穿。

小结

  1. 同源策略是浏览器的安全底线，但只防「读」不防「写」，CSRF 就钻这个空子
  2. XSS 防御铁律：不可信内容绝不直接拼进 HTML/JS/URL，富文本用 DOMPurify 白名单清洗
  3. React/Vue 的 dangerouslySetInnerHTML 和 v-html 是逃生舱，用之前先想清楚
  4. CSRF 现代方案：SameSite=Lax + 关键操作加 CSRF Token + 改数据用 POST 系动词
  5. 点击劫持优先用 CSP 的 frame-ancestors，X-Frame-Options 作为兼容兜底
  6. CSP 是 XSS 的最后一道防线，先用 Report-Only 模式跑通再上线，别上来就拦
  7. Cookie 三件套：HttpOnly + Secure + SameSite，能加都加上
  8. 容易忽视的坑：window.opener 钓鱼、postMessage 不验 origin、第三方依赖供应链风险
