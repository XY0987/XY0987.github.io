前端高频场景题梳理与参考答案

发表于2025|更新于2026|面试
|字数总计:3.3k|阅读时长:12分钟

前言：八股文能背，但场景题背不了。场景题考的是”给你一个真实需求，你怎么设计、怎么权衡、怎么处理边界”。这篇我把面试里高频的一批场景题梳理出来，按”题目 → 思路 → 关键代码 → 追问点”的结构来答。答场景题的核心不是把方案说全，而是先讲清思路和取舍，再落到代码——面试官想看的是你的思考过程，不是一段背下来的代码。

答场景题有个通用套路，先记住：先问清需求边界 → 给出核心思路 → 讲清关键取舍 → 落地代码 → 主动补边界。很多人一上来就写代码，反而显得没想清楚。下面每道题我都尽量演示这个过程。

一、异步与并发控制

场景 1：实现一个并发请求限制器

题目：有 100 个接口要请求，但同一时刻最多只能并发 3 个，怎么实现？

这是最高频的场景题之一，考的是对 Promise 和异步调度的理解。思路：维护一个”正在执行”的池子，跑完一个就补一个进来，始终保持池子里不超过 limit 个。

// 并发限制器：tasks 是返回 Promise 的函数数组
async function concurrentLimit(tasks, limit) {
  const results = [];
  const executing = new Set();

  for (let i = 0; i < tasks.length; i++) {
    // 包一层，记录结果到正确位置
    const p = Promise.resolve().then(() => tasks[i]());
    results[i] = p;

    executing.add(p);
    // 任务完成后从执行池移除
    p.finally(() => executing.delete(p));

    // 池子满了就等最快的一个完成，再进入下一轮
    if (executing.size >= limit) {
      await Promise.race(executing);
    }
  }

  return Promise.all(results);
}

// 验证
const mockTask = (id, delay) => () =>
  new Promise((resolve) => setTimeout(() => resolve(`task-${id}`), delay));

concurrentLimit(
  [mockTask(1, 1000), mockTask(2, 500), mockTask(3, 800), mockTask(4, 300)],
  2
).then((res) => console.log(res)); // ['task-1', 'task-2', 'task-3', 'task-4']

追问点：怎么处理某个任务失败不影响其他？把 Promise.all 换成 Promise.allSettled，就能拿到每个任务的成功/失败状态，不会因为一个挂了全盘皆输。

场景 2：请求失败自动重试

题目：一个接口偶发失败，希望失败后自动重试最多 3 次，每次间隔递增。

思路：递归 + 递减的重试次数，配合指数退避（每次等待时间翻倍），避免瞬间打爆服务端。

async function requestWithRetry(fn, retries = 3, baseDelay = 1000) {
  try {
    return await fn();
  } catch (err) {
    if (retries <= 0) throw err;
    // 指数退避：1s → 2s → 4s
    const delay = baseDelay * 2 ** (3 - retries);
    await new Promise((r) => setTimeout(r, delay));
    return requestWithRetry(fn, retries - 1, baseDelay);
  }
}

追问点：所有错误都该重试吗？不是。4xx 客户端错误（参数错、没权限）重试多少次都没用，只应该对网络错误、超时、5xx 这类可能自愈的错误重试。答到这一点，比单纯写个重试函数加分得多。

场景 3：取消重复/过期的请求

题目：搜索框输入时频繁发请求，但返回顺序不保证，怎么保证展示的永远是最新一次输入的结果？

这是”竞态问题”（race condition），实战里非常常见。思路有两种，我更推荐 AbortController：

let controller = null;

async function search(keyword) {
  // 每次新请求前，取消上一次还没回来的
  if (controller) controller.abort();
  controller = new AbortController();

  try {
    const res = await fetch(`/api/search?q=${keyword}`, {
      signal: controller.signal,
    });
    return await res.json();
  } catch (err) {
    if (err.name === 'AbortError') return; // 被主动取消的，忽略
    throw err;
  }
}

追问点：如果底层库不支持 AbortController 怎么办？可以用”版本号/时间戳”标记每次请求，回来时判断是不是最新那次发出的，不是就丢弃。防抖（debounce）能减少请求数，但不能根治竞态——这是两回事，别混。

二、性能与体验优化

场景 4：大数据量渲染怎么不卡

题目：后端一次返回 10 万条数据要展示，直接渲染页面直接卡死，怎么办？

先问清楚需求：是列表还是必须全展示？

  • 如果是列表滚动：用虚拟列表，只渲染可视区域的节点（前一篇排查文里讲过核心逻辑）
  • 如果必须一次性处理这批数据（比如渲染成图表点）：用分片渲染，借助 requestAnimationFrame 把任务拆成一帧渲染一批
// 分片渲染：每帧渲染一批，避免长任务卡死主线程
function renderInChunks(data, chunkSize, renderOne) {
  let index = 0;

  function renderChunk() {
    const end = Math.min(index + chunkSize, data.length);
    for (; index < end; index++) {
      renderOne(data[index]);
    }
    // 还没渲染完，下一帧继续
    if (index < data.length) {
      requestAnimationFrame(renderChunk);
    }
  }

  requestAnimationFrame(renderChunk);
}

追问点：为什么用 requestAnimationFrame 而不是 setTimeout？rAF 会在浏览器每次重绘前执行，天然和渲染节奏对齐，不会出现渲染撕裂或空帧。更进一步可以用 requestIdleCallback 在浏览器空闲时处理，但它兼容性和执行时机不如 rAF 稳。

场景 5：图片懒加载怎么做

题目：一个长页面有几百张图，怎么做到滚到哪加载到哪？

现在的标准答案是 IntersectionObserver，别再手写监听 scroll 算 getBoundingClientRect 了——那套又费性能又容易算错。

const observer = new IntersectionObserver(
  (entries, obs) => {
    for (const entry of entries) {
      if (entry.isIntersecting) {
        const img = entry.target;
        img.src = img.dataset.src; // 真实地址放在 data-src
        obs.unobserve(img); // 加载后停止观察，避免重复触发
      }
    }
  },
  { rootMargin: '100px' } // 提前 100px 开始加载，体验更顺
);

document.querySelectorAll('img[data-src]').forEach((img) => observer.observe(img));

追问点：原生的 <img loading="lazy"> 不香吗？香，简单场景直接用它就行。但它的加载时机由浏览器决定、不可控，也没法做加载中占位、失败重试这些定制逻辑，所以复杂场景还是 IntersectionObserver 更灵活。

场景 6：埋点上报怎么设计

题目：页面要采集用户的点击、曝光行为并上报，怎么设计才不影响性能、不丢数据？

这题考的是工程思维。我会从三个维度答：采集方式、上报方式、可靠性。

  • 曝光埋点用 IntersectionObserver 监听元素进入视口，别用 scroll 硬算
  • 上报优先用 navigator.sendBeacon——它在页面卸载时也能可靠发出，不会被浏览器掐断
  • 高频事件要批量+节流，攒够一批或到时间了再一起发，别一个点击发一个请求
class Reporter {
  constructor(url, { batchSize = 10, flushInterval = 5000 } = {}) {
    this.url = url;
    this.queue = [];
    this.batchSize = batchSize;
    setInterval(() => this.flush(), flushInterval);
    // 页面隐藏/卸载时兜底上报，防止丢数据
    document.addEventListener('visibilitychange', () => {
      if (document.visibilityState === 'hidden') this.flush();
    });
  }

  track(event) {
    this.queue.push({ ...event, ts: Date.now() });
    if (this.queue.length >= this.batchSize) this.flush();
  }

  flush() {
    if (!this.queue.length) return;
    navigator.sendBeacon(this.url, JSON.stringify(this.queue));
    this.queue = [];
  }
}

追问点：为什么用 sendBeacon 而不是 fetch？因为页面关闭那一刻，普通 fetch 的请求会被浏览器直接取消，sendBeacon 是浏览器保证会发出去的，专为这种”临终上报”设计。

三、业务功能实现

场景 7：大文件分片上传

题目：要上传一个 2GB 的文件，直接传经常失败，怎么优化？

思路是四件事：分片、并发、秒传、断点续传。这是一道能层层递进的题，答得越深越好。

// 核心：把大文件切成固定大小的分片
function createChunks(file, chunkSize = 5 * 1024 * 1024) {
  const chunks = [];
  for (let start = 0; start < file.size; start += chunkSize) {
    chunks.push(file.slice(start, start + chunkSize));
  }
  return chunks;
}

完整方案分几步：

  1. 分片：用 file.slice 切成固定大小的块
  2. 算 hash：对整个文件算 hash（用 spark-md5，放 Web Worker 里算避免卡主线程），作为文件唯一标识
  3. 秒传：上传前拿 hash 问服务端”这文件传过没”，传过直接返回成功
  4. 断点续传：问服务端”哪些分片已经传过了”，只补传缺的那些
  5. 并发上传：剩下的分片用前面场景 1 的并发限制器控制并发数上传
  6. 合并：全部传完通知服务端按顺序合并

追问点：hash 算得慢怎么办？大文件全量算 hash 很耗时，可以用抽样 hash——只取文件头、尾和中间几个片段算，速度快很多，代价是极小概率误判，绝大多数业务能接受。

场景 8：前端权限控制怎么做

题目：不同角色能看到的菜单、能点的按钮不一样，前端怎么设计？

先明确一个态度：**前端权限只是”体验”，不是”安全”**。真正的安全边界一定在后端——前端藏了按钮，用户照样能直接调接口。这个认知答出来就赢一半了。

前端权限一般分两级：

  • 路由级：登录后拿到用户角色/权限码，动态生成可访问的路由表，或在路由守卫里拦截
  • 按钮级：用一个指令或组件包一层，根据当前用户的权限码决定渲染不渲染
// 按钮级权限：一个简单的判断函数
function hasPermission(required, userPermissions) {
  if (!required) return true;
  return userPermissions.includes(required);
}

// Vue 里可以封装成自定义指令 v-permission，React 里封装成 <Auth> 组件

追问点：动态路由怎么防止用户手动改 URL 访问没权限的页面？路由守卫里做兜底校验，匹配不到有权限的路由就重定向到 403。但再强调一次，前端拦不住有心人，后端接口鉴权才是根本。

场景 9：实现一个前端 EventBus

题目：不用任何框架，实现一个发布订阅，支持 on / emit / off / once。

考基础功能设计。核心是一个 事件名 → 回调数组 的映射。

class EventBus {
  constructor() {
    this.events = new Map();
  }

  on(name, fn) {
    if (!this.events.has(name)) this.events.set(name, []);
    this.events.get(name).push(fn);
    return this; // 支持链式调用
  }

  once(name, fn) {
    const wrapper = (...args) => {
      fn(...args);
      this.off(name, wrapper);
    };
    return this.on(name, wrapper);
  }

  emit(name, ...args) {
    (this.events.get(name) || []).slice().forEach((fn) => fn(...args));
    return this;
  }

  off(name, fn) {
    if (!fn) {
      this.events.delete(name); // 不传 fn 就清空该事件所有监听
    } else {
      const fns = this.events.get(name) || [];
      this.events.set(name, fns.filter((f) => f !== fn));
    }
    return this;
  }
}

追问点：emit 里为什么要 slice() 拷贝一份再遍历？因为回调里可能调用 off 修改原数组，边遍历边改会漏执行或报错。这个细节能体现你对边界的敏感度。

四、浏览器与网络

场景 10：Token 过期无感刷新

题目：access_token 有效期短，过期后怎么在用户无感知的情况下续期，而且并发请求同时过期时不能刷新多次？

思路：在请求拦截器里捕获 401，触发刷新逻辑。难点在于并发控制——多个请求同时 401，只能刷新一次 token，其余请求要排队等这次刷新完成。

let isRefreshing = false;
let pendingQueue = []; // 等待新 token 的请求队列

async function handleUnauthorized(originalRequest) {
  if (isRefreshing) {
    // 已经在刷新了，把当前请求挂起，等新 token
    return new Promise((resolve) => {
      pendingQueue.push((newToken) => {
        originalRequest.headers.Authorization = `Bearer ${newToken}`;
        resolve(fetch(originalRequest));
      });
    });
  }

  isRefreshing = true;
  try {
    const newToken = await refreshToken();
    // 唤醒所有排队的请求
    pendingQueue.forEach((cb) => cb(newToken));
    pendingQueue = [];
    originalRequest.headers.Authorization = `Bearer ${newToken}`;
    return fetch(originalRequest);
  } finally {
    isRefreshing = false;
  }
}

追问点：refreshToken 本身也过期了怎么办？那说明登录态彻底失效，直接清空本地凭证、跳登录页。这里要做兜底，否则会陷入死循环。

场景 11：判断元素是否在可视区域

题目：不用 IntersectionObserver，手写判断一个元素是否进入了视口。

考对 getBoundingClientRect 的理解。元素相对视口的位置能直接拿到，判断它是否和视口矩形有交集即可。

function isInViewport(el) {
  const rect = el.getBoundingClientRect();
  const vh = window.innerHeight || document.documentElement.clientHeight;
  const vw = window.innerWidth || document.documentElement.clientWidth;
  // 只要元素矩形和视口矩形有交集就算可见
  return (
    rect.top < vh &&
    rect.bottom > 0 &&
    rect.left < vw &&
    rect.right > 0
  );
}

追问点：为什么现在推荐 IntersectionObserver 而不是这套？因为 getBoundingClientRect 会触发同步布局计算，绑在 scroll 上高频调用会造成性能问题；IntersectionObserver 是异步的、由浏览器调度，不阻塞主线程。这就呼应了上一篇讲的强制同步布局。

小结

  1. 答场景题的套路是先问清边界、给思路、讲取舍、再写代码、补边界，思考过程比代码本身更重要
  2. 异步并发控制的核心是维护执行池 + Promise.race，重试要区分错误类型，搜索竞态用 AbortController 根治
  3. 大数据渲染分虚拟列表和分片渲染两条路，分片渲染优先 requestAnimationFrame
  4. 埋点和临终上报优先 sendBeacon，高频事件要批量加节流
  5. 大文件上传答分片、并发、秒传、断点续传四件套，hash 慢就用抽样 hash
  6. 前端权限只是体验不是安全，真正的鉴权边界永远在后端
  7. Token 无感刷新的难点是并发 401 时只刷新一次、其余请求排队，refreshToken 失效要兜底跳登录
