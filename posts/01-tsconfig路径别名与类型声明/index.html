tsconfig、路径别名与类型声明配置

发表于2026|更新于2026|工程化
|字数总计:4.9k|阅读时长:18分钟

前言：TypeScript 工程化不只是“给变量加类型”。真正影响项目体验的，往往是 tsconfig.json 怎么配、路径别名怎么统一、第三方类型缺失怎么处理、全局类型声明放在哪里。

tsconfig.json 是 TypeScript 项目的边界

tsconfig.json 做两件事：

  1. 告诉 TypeScript 编译器怎么检查和编译；
  2. 告诉编辑器哪些文件属于这个 TypeScript 项目。

一个常见配置长这样：

{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "jsx": "react-jsx",
    "strict": true,
    "skipLibCheck": true,
    "isolatedModules": true,
    "verbatimModuleSyntax": true,
    "noEmit": true,
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    },
    "types": ["vite/client"]
  },
  "include": ["src", "vite.config.ts"],
  "exclude": ["dist", "node_modules"]
}

我建议先按“输入范围、检查规则、运行环境”这几块理解。

include、exclude、files

这三个字段决定 TypeScript 看哪些文件。

字段 含义 常见用法
include 匹配要纳入项目的文件 src、配置文件
exclude 从默认匹配中排除 dist、node_modules
files 精确列出文件 小型配置包、solution tsconfig

业务项目一般用 include 就够了：

{
  "include": ["src", "vite.config.ts"]
}

如果你发现编辑器里某个 .ts 文件类型不生效，第一反应应该是：它有没有被当前 tsconfig.json 包含进来。

tsc 到底做什么

讲 tsconfig.json 之前，最好先知道 tsc 是谁。

tsc 是 TypeScript 官方编译器命令，全称可以理解成 TypeScript Compiler。它主要做两件事：

  1. 读取 tsconfig.json，按配置检查项目里的类型；
  2. 在需要时，把 TypeScript 编译成 JavaScript，并生成声明文件。

最常见的用法是：

npx tsc --noEmit

这条命令只做类型检查，不输出 JS。很多前端项目的 typecheck 脚本就是这么来的：

{
  "scripts": {
    "typecheck": "tsc --noEmit"
  }
}

如果不加 --noEmit，tsc 会根据 tsconfig.json 里的 outDir、declaration、sourceMap 等配置输出产物：

npx tsc

所以可以这样理解：

工具 主要职责
tsc TypeScript 官方类型检查和编译
tsconfig.json 告诉 tsc 怎么检查、怎么编译、看哪些文件
Vite/Webpack/esbuild/SWC 更偏向开发服务器、转译、打包和资源处理
编辑器 TS Server 基于 tsconfig.json 提供类型提示、跳转、报错

现在很多前端项目并不是靠 tsc 打包，而是靠 Vite、Webpack、esbuild、SWC 处理转译和构建。但这不代表 tsc 不重要。我的建议是：应用项目让构建工具负责打包，让 tsc --noEmit 负责类型检查。

tsc 常用命令

日常项目里，tsc 常用命令不用记太多，下面这些基本够用：

命令 作用 常见场景
npx tsc --noEmit 只做类型检查，不输出文件 前端应用的 typecheck 脚本
npx tsc 按 tsconfig.json 编译并输出产物 Node 工具包、npm 包
npx tsc -p tsconfig.app.json 指定某个 tsconfig 文件 多 tsconfig 项目
npx tsc -b 使用 build 模式构建项目引用 monorepo、Project References
npx tsc -w --noEmit 监听文件变化并持续类型检查 本地开发时快速发现类型错误
npx tsc --showConfig 展示最终生效的配置 排查配置继承、路径包含问题
npx tsc --init 生成一个基础 tsconfig.json 新建 TypeScript 项目

这里的 npx tsc 会优先使用项目本地安装的 TypeScript 版本。团队项目里我更建议通过 npm scripts 固定命令：

{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "typecheck:watch": "tsc --noEmit --watch",
    "build:types": "tsc -p tsconfig.build.json"
  }
}

这样做的好处是每个人、CI、编辑器任务跑的都是同一套命令，不会因为全局 TypeScript 版本不同导致结果不一致。

strict 建议打开

{
  "compilerOptions": {
    "strict": true
  }
}

strict 会开启一组更严格的类型检查。新项目我建议直接打开，不要等代码写多了再补。

老项目可以分阶段开：

{
  "compilerOptions": {
    "strict": false,
    "noImplicitAny": true,
    "strictNullChecks": true
  }
}

但新项目不要犹豫，直接 strict: true。TypeScript 的收益很大一部分就来自这些严格检查。

target、lib 和 jsx

这三个配置经常被放在一起看，因为它们决定了 TypeScript “按哪个运行环境理解代码”。

{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "jsx": "react-jsx"
  }
}
配置 解决什么问题 常见选择
target 输出 JS 的语法版本 现代前端常用 ES2020、ES2022
lib 让 TS 知道有哪些内置 API 浏览器项目加 DOM、DOM.Iterable
jsx JSX 怎么转换或保留 React 17+ 常用 react-jsx

这里最容易混淆的是 target 和 lib。

target 更像是“最终 JS 语法要降到什么程度”，比如要不要保留 async/await、class fields 等语法。lib 则是“类型系统能不能认识某些 API”，比如 document、fetch、Map、Promise。

所以浏览器应用一般要显式带上 DOM：

{
  "compilerOptions": {
    "lib": ["ES2022", "DOM", "DOM.Iterable"]
  }
}

如果是纯 Node.js 工具包，就不要随手加 DOM，否则代码里误用了 document，TypeScript 也不会提醒你。

noEmit 和构建工具的关系

很多前端项目会写：

{
  "compilerOptions": {
    "noEmit": true
  }
}

意思是 TypeScript 只做类型检查，不输出 JS 文件。

这是因为 Vite、Webpack、esbuild、SWC 通常负责转译和打包，TypeScript 编译器只负责类型检查。

所以常见脚本是：

{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "tsc -b && vite build"
  }
}

这里要注意：Vite 开发时默认不会完整做 TypeScript 类型检查，很多类型错误要靠 tsc 或插件在构建/提交阶段拦住。

skipLibCheck：可以开，但要知道它跳过了什么

很多项目会配置：

{
  "compilerOptions": {
    "skipLibCheck": true
  }
}

它的意思是跳过 .d.ts 声明文件之间的类型检查，通常能减少第三方依赖类型冲突带来的噪音，也能让类型检查更快一些。

我的建议是：应用项目可以开，公共库项目要谨慎。应用项目更关心自己的业务代码是否安全，第三方声明文件偶尔打架没必要卡住整个团队；但如果你在写要发布给别人用的库，声明文件就是你的公共契约，不能太随意跳过。

路径别名：TypeScript 和构建工具要同时配置

我们常写：

import { formatDate } from '@/shared/utils/formatDate'

对应 tsconfig.json：

{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}

但只配 TypeScript 不够。paths 主要让 TypeScript 和编辑器知道别名怎么解析，运行时或打包阶段还需要构建工具支持。

Vite 里可以这样配：

import { fileURLToPath, URL } from 'node:url'
import { defineConfig } from 'vite'

export default defineConfig({
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url))
    }
  }
})

或者使用 vite-tsconfig-paths 让 Vite 读取 tsconfig 的路径配置。

我的建议是：路径别名只保留少量稳定入口，比如 @/*，不要给每个目录都配一个别名。别名太多，反而降低可读性。

types、typeRoots 和全局类型

types

types 用来限制默认引入哪些全局类型包。

{
  "compilerOptions": {
    "types": ["vite/client", "vitest/globals"]
  }
}

如果你配置了 types，TypeScript 只会引入列出的类型包。这个规则很容易被忽略。

这里很多人会把 types 和前面讲的 lib 混在一起。它们确实都会影响 TypeScript 能看到哪些声明，但来源不一样，也不冲突：

配置 引入什么声明 例子
lib TypeScript 内置的运行环境声明 ES2022、DOM、DOM.Iterable
types 第三方包或工具链提供的全局类型包 node、vite/client、vitest/globals

简单说，lib 解决“这个运行环境有哪些内置 API”，types 解决“哪些额外类型包要自动进入全局作用域”。浏览器项目可以同时配置 lib: ["ES2022", "DOM"] 和 types: ["vite/client"]，这不是重复配置。

typeRoots

typeRoots 用来指定类型声明根目录：

{
  "compilerOptions": {
    "typeRoots": ["./types", "./node_modules/@types"]
  }
}

业务项目不一定需要配置它。很多时候，把自定义声明文件放进 src 或 types，并确保被 include 覆盖，就够了。

.d.ts 文件应该怎么放

我常见做法是：

src/
├── types/
│   ├── env.d.ts
│   ├── global.d.ts
│   └── modules.d.ts

环境变量类型

以 Vite 为例：

interface ImportMetaEnv {
  readonly VITE_API_BASE_URL: string
  readonly VITE_APP_ENV: 'development' | 'test' | 'staging' | 'production'
}

interface ImportMeta {
  readonly env: ImportMetaEnv
}

注意，这类全局声明文件里尽量不要写 import。一旦写了顶层 import，文件会变成模块，某些全局声明可能不会按你预期生效。

静态资源声明

declare module '*.svg' {
  const src: string
  export default src
}

declare module '*.module.css' {
  const classes: Record<string, string>
  export default classes
}

这类声明解决的是 TypeScript 不认识非 TS 模块的问题。

模块声明和第三方库扩展

有些第三方包没有类型，或者类型不完整，可以写模块声明。

declare module 'legacy-sdk' {
  export interface LegacyUser {
    id: string
    name: string
  }

  export function getUser(id: string): Promise<LegacyUser>
}

如果是扩展已有库的类型，要用模块扩展。

declare module 'axios' {
  export interface AxiosRequestConfig {
    skipAuth?: boolean
  }
}

这类声明要谨慎写。我的建议是：能安装官方类型或社区 @types/*，就不要自己补；必须自己补时，尽量只声明项目实际用到的最小范围。

moduleResolution 怎么选

先把几个名词说清楚：

名词 简单理解
module 决定 TypeScript 输出或理解哪种模块格式，比如 ESNext、NodeNext
moduleResolution 决定 TypeScript 按什么规则查找一个 import 对应的文件
Bundler 按现代打包工具的习惯解析模块，适合 Vite、Webpack、Rollup 这类应用项目
NodeNext 按现代 Node.js 的 ESM/CJS 规则解析模块，适合 Node.js 库或服务端项目

简单说，module 更关心“模块长什么样”，moduleResolution 更关心“模块去哪找”。

现在前端项目常见两种：

{
  "moduleResolution": "Bundler"
}

或者：

{
  "module": "NodeNext",
  "moduleResolution": "NodeNext"
}

大致可以这样判断：

场景 建议
Vite/Webpack/Rollup 应用 Bundler
Node.js ESM/CJS 库 NodeNext
需要严格模拟 Node.js 解析 NodeNext

Bundler 更贴近现代打包工具的解析方式，应用项目使用起来更顺手。库项目如果要发布给 Node.js 使用，就要更认真考虑 NodeNext 和 exports 的配合。

这里的 exports 指的是 package.json 里的包导出入口，用来告诉外部使用者“哪些文件可以被 import”。发布库时，TypeScript 的模块解析、Node.js 的运行时解析、包的 exports 配置最好保持一致，否则很容易出现“类型能找到，运行时找不到”。

isolatedModules 和 verbatimModuleSyntax

如果项目使用 Vite、esbuild、SWC、Babel 这类工具转译 TypeScript，我建议关注这两个配置：

{
  "compilerOptions": {
    "isolatedModules": true,
    "verbatimModuleSyntax": true
  }
}

这几个名词可以这样理解：

名词 简单理解
isolatedModules 要求每个文件都能被单独转译，不依赖跨文件类型分析
verbatimModuleSyntax import/export 尽量按原样保留，不帮你偷偷改写模块语法

isolatedModules 会要求每个文件都能被单独转译。因为很多构建工具并不会像 tsc 一样做完整的跨文件类型分析，它们更像是“拿到一个文件，转一个文件”。打开它之后，一些只在完整 TypeScript 编译流程里才安全的写法会提前暴露出来。

verbatimModuleSyntax 则让 import/export 更接近“你怎么写，TypeScript 就怎么保留”。配合它使用时，类型导入要写清楚：

import type { User } from './types'
import { createUser } from './user'

这样做的好处是运行时代码和类型代码边界更清楚，打包工具也更容易正确处理。

esModuleInterop 和默认导入

在一些 Node.js 或历史项目里，你还会看到：

{
  "compilerOptions": {
    "esModuleInterop": true,
    "allowSyntheticDefaultImports": true
  }
}

这里也先解释一下几个名词：

名词 简单理解
esModuleInterop 让 TypeScript 生成更兼容的代码，缓和 CommonJS 和 ES Module 的默认导入差异
allowSyntheticDefaultImports 允许类型层面使用“看起来像默认导入”的写法

它们主要解决 CommonJS 和 ES Module 默认导入之间的兼容问题。典型现象是某个包明明可以这样用：

import express from 'express'

但 TypeScript 提示你不能默认导入。

我的看法是：应用项目遇到这类依赖时可以开，没必要把时间耗在模块历史包袱上；库项目则要结合你的 module、moduleResolution、package.json#type 和输出格式一起判断，别只靠这两个配置“压过去”。

导入解析里的几个常见补充

除了 paths 和 moduleResolution，还有两个配置在前端项目里也比较常见：

{
  "compilerOptions": {
    "resolveJsonModule": true,
    "allowImportingTsExtensions": true
  }
}
配置 作用 我的建议
resolveJsonModule 允许直接 import data from './data.json'，并给 JSON 推导类型 需要导入 JSON 配置时再开
allowImportingTsExtensions 允许 import 路径里写 .ts、.tsx 扩展名 只在 noEmit 或只生成声明文件的场景使用

resolveJsonModule 很好理解，就是让 TypeScript 认识 JSON 模块。比如一些前端项目会导入本地配置、语言包、mock 数据，这时它就有用。

allowImportingTsExtensions 要谨慎一点。普通编译输出 JS 时，如果你在源码里写：

import { createUser } from './user.ts'

编译后的 JS 里路径可能还是 .ts，运行时就容易出问题。所以它通常只适合“不由 tsc 输出 JS”的项目，比如 Vite 应用里 noEmit: true，或者库项目只用 TypeScript 生成 .d.ts。

输出类配置：应用项目和库项目不一样

前端应用项目通常会写 noEmit: true，但如果你在写 npm 包、Node.js 工具包，输出相关配置就绕不开。

{
  "compilerOptions": {
    "rootDir": "src",
    "outDir": "dist",
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true
  }
}
配置 作用
rootDir 指定源码根目录，影响输出目录结构
outDir 指定编译产物输出目录
declaration 生成 .d.ts 类型声明文件
declarationMap 生成声明文件的 sourcemap，方便编辑器跳回源码
sourceMap 生成 JS sourcemap，方便调试编译后的代码

我的建议是：应用项目交给 Vite、Webpack 这类工具输出，tsc 只做类型检查；库项目才认真配置 outDir、declaration 这些输出项。

尤其是 declaration，它对发布 npm 包很重要。别人安装你的包以后，编辑器能不能拿到类型提示，很大程度就看你有没有正确输出 .d.ts。

增量构建和项目引用

这几个配置常和大型项目、monorepo、Project References 放在一起：

{
  "compilerOptions": {
    "composite": true,
    "incremental": true,
    "tsBuildInfoFile": "./node_modules/.cache/tsconfig.tsbuildinfo"
  }
}
配置 作用
incremental 保存上次编译信息，下次类型检查可以复用，提升速度
tsBuildInfoFile 指定增量编译缓存文件放在哪里
composite 让当前项目可以被其他 tsconfig 引用，是 Project References 的关键配置

普通小项目不一定需要手动配这些。项目变大以后，tsc --build、references、composite 才会真正体现价值。下一篇如果专门讲 TypeScript Project References，可以再展开这块。

质量类检查：别只知道 strict

strict 很重要，但它不是所有检查项的终点。新项目可以考虑补两个更容易发现真实问题的配置：

{
  "compilerOptions": {
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true
  }
}
配置 作用
noUncheckedIndexedAccess 通过下标访问数组、对象时，把结果视为可能是 undefined
exactOptionalPropertyTypes 更严格地区分“属性不存在”和“属性值为 undefined”

举个简单例子：

const users = ['Tom']

const firstUser = users[0]
firstUser.toUpperCase()

打开 noUncheckedIndexedAccess 后，firstUser 会被认为可能是 undefined。这会让你多写一点判断，但也能提前暴露很多线上常见空值问题。

这两个配置我不会强行要求所有项目一开始就开。业务复杂、数据结构经常变化的项目，可以先开；老项目如果错误太多，就放到后续类型治理里逐步处理。

另外还有几项偏“代码质量约束”的配置，也经常出现在项目模板里：

{
  "compilerOptions": {
    "forceConsistentCasingInFileNames": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true
  }
}
配置 作用
forceConsistentCasingInFileNames 强制 import 路径大小写和真实文件名一致
noUnusedLocals 不允许未使用的局部变量
noUnusedParameters 不允许未使用的函数参数
noFallthroughCasesInSwitch 防止 switch 分支意外贯穿到下一个 case

其中 forceConsistentCasingInFileNames 我建议打开。macOS 默认文件系统对大小写不敏感，Linux CI 往往大小写敏感，很多“本地能跑，CI 挂了”的问题就出在这里。

noUnusedLocals 和 noUnusedParameters 是否交给 TypeScript 管，要看团队习惯。如果项目已经用 ESLint 统一检查未使用变量，也可以不在 tsconfig 里重复加压。

前端项目常见的分层配置

稍微规范一点的前端项目，通常不会只有一个 tsconfig.json，而是拆成几份：

tsconfig.json
tsconfig.app.json
tsconfig.node.json

根配置负责引用子配置：

{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" }
  ]
}

tsconfig.app.json 管浏览器业务代码：

{
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022", "DOM", "DOM.Iterable"],
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "jsx": "react-jsx",
    "strict": true,
    "noEmit": true
  },
  "include": ["src"]
}

tsconfig.node.json 管 Node.js 侧配置文件，比如 vite.config.ts：

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "noEmit": true
  },
  "include": ["vite.config.ts"]
}

这样拆的好处是很直观：浏览器代码能用 document，Node.js 配置文件不能乱用浏览器全局变量；不同运行环境的类型边界不会混在一起。

小结

  1. tsconfig.json 决定 TypeScript 项目的文件范围、检查规则和模块解析方式。
  2. target、lib、jsx 决定项目按哪个运行环境和语法能力理解代码。
  3. 新项目建议开启 strict，并按项目情况评估 noUncheckedIndexedAccess、exactOptionalPropertyTypes。
  4. 路径别名要同时配置 TypeScript 和构建工具。
  5. .d.ts 适合放环境变量、静态资源、第三方模块声明，但不要随意扩大声明范围。
  6. 应用项目常用 moduleResolution: Bundler，Node.js 库项目更需要关注 NodeNext。
  7. 应用项目一般 noEmit: true，库项目才重点配置 outDir、declaration、sourceMap。
  8. 大型项目或 monorepo 再考虑 incremental、composite、references 这套项目引用能力。
  9. 前端项目可以按浏览器代码和 Node.js 配置文件拆分多个 tsconfig，减少环境类型混用。
