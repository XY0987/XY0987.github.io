Vue 3 props 与 emits 源码解析：组件通信如何被规范化

发表于2026|更新于2026|Vue框架及周边库
|字数总计:1.8k|阅读时长:7分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：组件实例创建后，下一步就要处理组件通信。props 决定父组件传进来的数据如何进入子组件，emits 决定子组件发出的事件如何被校验和分发。这一篇重点看 Vue 如何把用户写法规范化成运行时更好处理的数据结构。

先给结论

props 和 emits 的核心职责可以拆成两条线：

props:
父组件传入 rawProps
  -> normalizePropsOptions
  -> setFullProps
  -> props / attrs 分流
  -> props 变成 shallowReactive

emits:
组件声明 emits
  -> normalizeEmitsOptions
  -> emit(event, ...args)
  -> 校验事件名和参数
  -> 找到父组件传入的 onXxx 监听器并调用

我的理解是，props / emits 规范化解决的不是“能不能传值”这么简单，而是让组件通信有边界：

机制 解决的问题
propsOptions 哪些字段是组件声明接收的 props
attrs 哪些字段没有被 props 接收，需要透传到根节点
emitsOptions 哪些事件是组件声明会发出的事件
isEmitListener 哪些 onXxx 是事件监听器，不应该当成普通 attrs

propsOptions 和 emitsOptions 在哪里初始化

组件实例创建时，会先把组件定义上的 props、emits 规范化：

// props/emits 选项在实例创建时先规范化，后续初始化 props 和 emit 校验会复用这些结果。
propsOptions: normalizePropsOptions(type, appContext),
emitsOptions: normalizeEmitsOptions(type, appContext),

// emit
emit: null!, // to be set immediately
emitted: null,

为什么要提前规范化？因为用户写法很多：

props: ['foo']
props: { foo: String }
props: { foo: { type: String, default: 'x' } }

emits: ['submit']
emits: { submit: payload => true }

运行时不想每次都判断这些写法，所以先统一成更稳定的结构。

initProps：把 rawProps 分成 props 和 attrs

组件初始化 props 的入口是 initProps：

export function initProps(
  instance: ComponentInternalInstance,
  rawProps: Data | null,
  isStateful: number, // result of bitwise flag comparison
  isSSR = false,
): void {
  const props: Data = {}
  const attrs: Data = createInternalObject()

  instance.propsDefaults = Object.create(null)

  setFullProps(instance, rawProps, props, attrs)

  // ensure all declared prop keys are present
  for (const key in instance.propsOptions[0]) {
    if (!(key in props)) {
      props[key] = undefined
    }
  }

  // validation
  if (__DEV__) {
    validateProps(rawProps || {}, props, instance)
  }

  if (isStateful) {
    // stateful
    // props也建立响应式依赖
    instance.props = isSSR ? props : shallowReactive(props)
  } else {

这里有两个重点。

第一，props 和 attrs 是分开的：

  • 声明过的 prop 进入 props。
  • 没声明过、也不是 emit listener 的字段进入 attrs。

第二，有状态组件的 props 会变成 shallowReactive。这就是为什么父组件更新 prop 后，子组件能响应式更新。

setFullProps：props 和 attrs 如何分流

真正分流发生在 setFullProps：

function setFullProps(
  instance: ComponentInternalInstance,
  rawProps: Data | null,
  props: Data,
  attrs: Data,
) {
  const [options, needCastKeys] = instance.propsOptions
  let hasAttrsChanged = false
  let rawCastValues: Data | undefined
  if (rawProps) {
    for (let key in rawProps) {
      // key, ref are reserved and never passed down
      if (isReservedProp(key)) {
        continue
      }

      const value = rawProps[key]
      // prop option names are camelized during normalization, so to support
      // kebab -> camel conversion here we need to camelize the key.
      let camelKey
      if (options && hasOwn(options, (camelKey = camelize(key)))) {
        if (!needCastKeys || !needCastKeys.includes(camelKey)) {
          props[camelKey] = value
        } else {
          ;(rawCastValues || (rawCastValues = {}))[camelKey] = value
        }
      } else if (!isEmitListener(instance.emitsOptions, key)) {
        // Any non-declared (either as a prop or an emitted event) props are put
        // into a separate `attrs` object for spreading. Make sure to preserve
        // original key casing
        if (!(key in attrs) || value !== attrs[key]) {
          attrs[key] = value
          hasAttrsChanged = true
        }
      }
    }
  }

这段逻辑可以翻译成：

rawProps 里的每个 key：
  1. key/ref 这类保留字段跳过
  2. 如果命中 propsOptions，放进 props
  3. 如果是已声明 emits 对应的 onXxx，跳过 attrs
  4. 剩下的放进 attrs

举个例子：

<Child title="hello" class="card" @submit="save" />

子组件声明：

props: { title: String },
emits: ['submit']

那么运行时大概会分成：

字段 去向 原因
title props.title 子组件声明了 prop
class attrs.class 没有被 props / emits 接收，需要透传
onSubmit 不进入 attrs 它是 submit 对应的事件监听器

这解释了为什么声明 emits 会影响 attrs 透传：声明过的事件监听器不会被当成普通 attrs 透传到 DOM 上。

normalizePropsOptions：为什么要规范化

normalizePropsOptions 会把数组写法、对象写法、mixin / extends 合并成统一结构：

export function normalizePropsOptions(
  comp: ConcreteComponent,
  appContext: AppContext,
  asMixin = false,
): NormalizedPropsOptions {
  const cache =
    __FEATURE_OPTIONS_API__ && asMixin ? mixinPropsCache : appContext.propsCache
  const cached = cache.get(comp)
  if (cached) {
    return cached
  }

  const raw = comp.props
  const normalized: NormalizedPropsOptions[0] = {}
  const needCastKeys: NormalizedPropsOptions[1] = []

  // apply mixin/extends props
  let hasExtends = false
  if (__FEATURE_OPTIONS_API__ && !isFunction(comp)) {
    const extendProps = (raw: ComponentOptions) => {
      hasExtends = true
      const [props, keys] = normalizePropsOptions(raw, appContext, true)
      extend(normalized, props)
      if (keys) needCastKeys.push(...keys)
    }

这里除了规范化，还有一个很重要的设计：缓存。

同一个组件定义不会每次创建实例都重新解析 props 选项，结果会放到 appContext.propsCache 里。组件定义是稳定的，规范化结果也应该复用。

开发环境下，Vue 会校验两件事：

  1. 事件是否在 emits 里声明过。
  2. 如果声明的是校验函数，参数是否合法。

真正找到父组件监听器是在后面：

let handler =
  props[(handlerName = toHandlerKey(event))] ||
  // also try camelCase event handler (#2249)
  props[(handlerName = toHandlerKey(camelize(event)))]
// for v-model update:xxx events, also trigger kebab-case equivalent
// for props passed via kebab-case
if (!handler && isModelListener) {
  handler = props[(handlerName = toHandlerKey(hyphenate(event)))]
}

if (handler) {
  callWithAsyncErrorHandling(
    handler,
    instance,
    ErrorCodes.COMPONENT_EVENT_HANDLER,
    args,
  )
}

emit('submit', payload)

isEmitListener：emits 如何影响 attrs

isEmitListener 用来判断一个 onXxx 是否是组件声明过的事件监听器：

// Check if an incoming prop key is a declared emit event listener.
// e.g. With `emits: { click: null }`, props named `onClick` and `onclick` are
// both considered matched listeners.
export function isEmitListener(
  options: ObjectEmitsOptions | null,
  key: string,
): boolean {
  if (!options || !isOn(key)) {
    return false
  }

  key = key.slice(2).replace(/Once$/, '')
  return (
    hasOwn(options, key[0].toLowerCase() + key.slice(1)) ||
    hasOwn(options, hyphenate(key)) ||
    hasOwn(options, key)
  )
}

这就是组件通信里一个很容易忽略的细节：

emits 不只是文档和校验，它还影响 attrs 透传边界。

如果不声明 emits，父组件传下来的 onSubmit 可能会被当成普通 attrs 继续透传；声明后，Vue 知道它是组件事件监听器，就不会把它当成普通 DOM 属性处理。

小结

  1. propsOptions 和 emitsOptions 在组件实例创建时就被规范化。
  2. initProps 会把父组件传入的 rawProps 分成 props 和 attrs。
  3. 声明过的 prop 进入 props，未声明且不是 emit listener 的字段进入 attrs。
  4. emits 既用于事件校验，也用于识别 onXxx 是否应该从 attrs 中排除。
  5. emit 会从当前组件 VNode 的 props 上查找父组件传入的事件监听器并执行。
