微信小程序底层原理深解：从双线程架构到 Skyline 渲染引擎

发表于2026|更新于2026|跨端
|字数总计:10.4k|阅读时长:37分钟

前言：这篇不讲”怎么写小程序”，只讲”小程序是怎么跑起来的”。如果你已经写过小程序，想弄明白为什么它这么设计、底层到底在做什么事、Skyline 为什么把原来的双线程砍了——这篇就是写给你看的。

📦 配套开源实现：github.com/XY0987/miniapp-decoded

用 Web Worker 模拟 JSCore、用 iframe 模拟 WebView、用主页面模拟微信客户端，把本文讲到的双线程架构、PageFrame、WeixinJSBridge、setData 跨线程链路全部实装了一遍，可以打断点单步调试每一次跨线程通信。文末”配套开源实现”章节会详细介绍怎么用它读这篇文章。

为什么值得从原理层面看小程序

小程序在国内前端圈是个有点分裂的存在：日常用它的人太多，认真研究它的人太少。大部分资料停留在”怎么用 wx.request“、”怎么写页面”这个层面，但一旦你想回答下面这几个问题，就会发现自己其实不懂它：

  • 为什么小程序不让你操作 DOM，但又能渲染 DOM？
  • 为什么 setData 一次几百 KB 就可能卡，但 innerHTML 改整棵树也没这么夸张？
  • 为什么小程序的 scroll 手势听起来那么丝滑，但随便写一个拖动就会掉帧？
  • 为什么 Taro、Remax 这些跨端框架非要搞那么复杂的架构？
  • Skyline 号称架构级重构，那它到底改掉了双线程里的哪一部分？

这些问题的答案都指向同一个词：架构。小程序不是一个简单的 WebView 外壳，也不是一个普通的 Hybrid 方案，它的双线程模型、Exparser 组件系统、PageFrame 机制、WXS、甚至 Skyline，都是在”Web 能力 × 原生体验 × 安全管控”这三个约束下拧出来的工程化妥协物。把它们串起来看，才能真正看懂这个东西。

一个基本事实：小程序是双线程的

先立一个最关键的基准认知：传统小程序（WebView 渲染模式）是双线程架构。这一点理解不了，后面所有设计都讲不通。

┌──────────────────────────────────────────────────────────────┐
│                    Native 层（微信客户端）                       │
│   ┌─────────────────┐       ┌─────────────────┐             │
│   │  渲染线程         │◄──── │ 逻辑线程           │             │
│   │  （WebView）     │────► │ （JSCore/V8）     │             │
│   │                 │       │                 │             │
│   │  WXML/WXSS      │       │  .js 业务代码     │             │
│   │  虚拟 DOM        │       │  setData         │             │
│   │  真实节点绘制     │       │  生命周期        │             │
│   └─────────────────┘       └─────────────────┘             │
│          ▲                          ▲                       │
│          └───── WeixinJSBridge ─────┘                       │
│                （Native 做消息中转）                          │
└──────────────────────────────────────────────────────────────┘

这套架构有三个要点：

  1. 渲染线程 = WebView（iOS 是 WKWebView，Android 早期是 X5 内核，当前主要是基于 Chromium 的微信自研 XWeb），里面负责 WXML/WXSS 生成后的视图结构、样式和真实渲染
  2. 逻辑线程 = 一个纯 JS 执行环境（iOS 是 JavaScriptCore，Android 老版本用 X5 的 JsCore， 当前主要是 V8），没有 window、没有 document、没有任何 DOM API
  3. 双方不能直接通信，所有事件、数据都要经过 Native 中转

为什么要搞这么复杂

设计者的出发点其实就两条：安全 和 体验。

安全层面：如果像 H5 那样把业务 JS 和视图放在同一个 WebView 里，开发者随便一个 location.href = "xxx" 就能跳走、document.querySelector 就能扒用户信息、eval 一执行你根本拦不住。想把浏览器开放的接口一个一个禁掉？JS 太灵活，内核每次更新都可能冒出新漏洞。

根本的解决办法只有一个：把业务 JS 放进一个完全没有 DOM/BOM 能力的沙箱。逻辑层的 JSCore 就是这个沙箱——你拿不到 document，想操作视图只能通过 setData 让 Native 转发给 WebView。从架构上就堵死了。

体验层面：原生 App 的页面切换是层叠的（新页面从右侧滑入，旧页面还在），这是 SPA 做不到的（SPA 要卸载旧页面）。小程序采用多 WebView 策略：每个页面一个独立 WebView，新开页面就往上叠一个，这样才能做到接近原生的过渡动画。

双线程不是为了性能，而是为了把开发者能碰的东西框住——这是理解所有小程序”奇怪限制”的钥匙。

双线程的代价

凡事有代价。这套架构带来的直接后果就是跨线程通信昂贵：

  • 每次 setData，数据要 JSON 序列化 → 发给 Native → Native 转发 → 渲染层反序列化 → 触发虚拟 DOM 重建
  • 数据量大、频率高的场景（比如手势拖拽）性能崩盘
  • 这也是后面 WXS 和 Skyline 要解决的核心问题

WXML：一套”看起来像 HTML 其实不是”的标记语言

很多人以为 WXML 就是”微信家的 HTML”，其实完全不是一回事。

HTML 是给浏览器解析的，解析完直接渲染。WXML 不是——它会先被小程序编译链路处理成框架能消费的视图描述逻辑，再在运行时结合 data 生成页面结构。

下面这段属于基于开发者工具产物和社区逆向资料的理解，非官方文档内容。另外不同基础库、不同渲染后端下，内部实现细节可能变化。

传统 WebView 模式下，编译产物可以粗略理解成类似这样的 JS 逻辑（简化版）：

// 不是实际源码，只是帮助理解的简化模型
function createViewGenerator(templatePath) {
  return function generateView(data) {
    // 根据 data 生成小程序内部的视图节点描述
    return {
      tag: 'page',
      children: [
        { tag: 'wx-view', attr: { class: 'container' }, children: [...] }
      ]
    };
  };
}

关键点：

  1. 视图模板不会在运行时重新解析原始 WXML，而是复用编译后的模板逻辑
  2. 数据通过 setData 从逻辑层注入，渲染层再根据新数据更新视图
  3. 运行时节点会进入小程序自己的组件系统，而不是直接暴露浏览器 DOM 给开发者操作

为什么要设计成两步？因为 WXML 的结构是静态的模板，但数据是动态的。把模板编译和数据注入分开，同一个页面可以在不同数据下复用编译结果，避免每次更新都重新解析模板。

Mustache 和 wx:for/wx:if

WXML 里的 {{ }} 是 Mustache 语法，不是 Vue 或 React 的插值。Mustache 是一种 logic-less 模板语法，支持的表达式有限（三元、基础运算、属性访问），不支持任意 JS 表达式。

这也是为什么 WXML 里你不能写 {{ arr.filter(x => x.done) }}——Mustache 解析不了箭头函数。想做这类逻辑只有两条路：

  • 算好了再塞进 data
  • 用 WXS（后面讲）

WXSS：不是 CSS，是”带后处理的 CSS”

WXSS 和 CSS 的差异常被忽略，其实挺大的：

维度 CSS WXSS
单位 px、em、rem 多一个 rpx（响应式像素）
选择器 全套 部分不支持（如伪元素 :hover 在双线程模式下有限）
样式导入 @import @import 但走打包流程
作用域 全局 Page 级作用域（自定义组件有独立作用域）
编译 浏览器直接解析 编译成 JS 注入

rpx 的原理：rpx = responsive pixel，基于 750 rpx 宽度的逻辑屏。小程序会在运行时用 rpx = 屏幕宽度 / 750 * rpx值 换算成真实 px。iPhone 6 (375px) 上 2rpx = 1px，iPhone 6 Plus 上 1.65rpx = 1px。

WXSS 被编译的玩法：WXSS 也不是简单原样交给浏览器，它会经过小程序编译链路处理，再由基础库注入到对应页面的渲染环境里。每个页面都有自己编译后的 CSS 代码块，再由底层基础库来执行。

到了 Skyline，样式处理链路变化更大：官方文档明确提到它使用更精简的渲染管线，样式和布局能力也有自己的支持范围。后面专门讲 Skyline。

PageFrame：小程序页面”秒开”的秘密

这是一个很少被拿出来讲但非常有意思的设计。

每个页面都是一个 WebView，那怎么做到秒开？

小程序新开一个页面（wx.navigateTo）需要起一个 WebView。但 WebView 的冷启动开销在 iOS 上几百毫秒、Android 上有时候能到 1 秒。如果每次 navigateTo 都是”现起 WebView → 下发 WXML/WXSS → 渲染”，体验就废了。

微信的解法可以理解成 PageFrame：一个提前准备好的页面运行容器。

这里也要先说清楚：page-frame.html 这个名字可以从网络请求 referer、开发者工具产物等地方看到，但具体预热、注入、调度细节属于微信客户端和基础库内部实现，不能当成稳定 API。比较稳妥的理解方式是：

  1. 小程序启动时，框架会提前准备页面运行所需的基础环境，例如基础库、页面配置、公共运行时代码
  2. 当你调 wx.navigateTo 时，框架尽量复用已经准备好的页面容器，减少新页面冷启动成本
  3. 页面使用后，框架继续准备后续可用的页面容器，避免每次跳转都完整经历 WebView 冷启动
App 启动
  │
  ├─ 起首页 WebView   ──► 渲染 index
  └─ 起 pageFrame ──► 空转待命

用户点 navigateTo
  │
  ├─ 复用预热页面容器   ──► 注入/加载当前页资源 ──► 渲染
  └─ 后台再起一个新 pageFrame ──► 待命（下次用）

这个设计和 iOS 里 UINavigationController 预加载下一个 ViewController 的思路几乎一模一样，只不过这里预加载的是 WebView。

为什么页面栈最多 10 层

WebView 实例吃内存。iOS 上一个 WKWebView 常驻几十 MB 是很正常的。多 WebView 叠起来，10 层就是小几百 MB。再加上微信本体，内存就非常紧张了。所以历史上小程序的页面栈最多 10 层是个硬限制。

（顺带一提：Skyline 不再是每个页面一个独立 WebView，页面栈带来的内存压力会明显降低；至于具体路由层数限制，仍应以当前基础库文档和真机表现为准。）

Exparser：小程序的组件系统到底是个什么东西

小程序里所有组件（内置的 view、button，以及你写的自定义组件）都由一个叫 Exparser 的框架管理。Exparser 是微信自研的、写在基础库里的一套仿 WebComponents 的组件系统。

理解 Exparser 最快的路径是先理解 Web Components。

Web Components 快速回顾

Web Components 是浏览器原生的组件化标准，三大规范：

  • Custom Elements：定义自定义标签（必须带短横线，如 <my-button>）
  • Template：用 <template> 声明可复用的 DOM 片段
  • Shadow DOM：隐藏的 DOM 子树，实现样式和结构隔离

一个原生 Web Component 长这样：

<template id="my-card-tpl">
  <style> .card { padding: 16px; border: 1px solid #ccc; } </style>
  <div class="card">
    <slot name="title"></slot>
    <slot></slot>
  </div>
</template>

<script>
class MyCard extends HTMLElement {
  constructor() {
    super();
    const shadow = this.attachShadow({ mode: 'open' });
    const tpl = document.getElementById('my-card-tpl');
    shadow.appendChild(tpl.content.cloneNode(true));
  }
}
customElements.define('my-card', MyCard);
</script>

<my-card>
  <h2 slot="title">标题</h2>
  <p>正文内容</p>
</my-card>

重点特性：

  • attachShadow 创建影子 DOM，外部 CSS 影响不到内部
  • <slot> 是插槽，外部传进来的子元素被投影到对应位置
  • 自定义事件可以通过 composed: true 控制是否穿透 Shadow DOM 边界

Exparser 做了什么

Exparser 可以理解为不依赖浏览器原生支持的 Web Components 实现。官方的原话是这么描述的：

Exparser 的组件模型与 WebComponents 标准中的 Shadow DOM 高度相似。

三个核心特点：

  1. 基于 Shadow DOM 模型，但不依赖浏览器实现
  2. 可在纯 JS 环境中运行——这条很关键，因为逻辑层根本没有浏览器，但它也要维护一棵组件树
  3. 轻量高效，在组件实例极多的场景下性能表现好

几个对应关系：

Web Components Exparser
Shadow Tree Shadow Tree（组件内部结构）
HTML Tree Composed Tree（最终合成的页面树）
customElements.define Component({...})
attachShadow({ mode: 'open' }) 自动创建，不需要手写
属性传递（attribute） properties
事件 triggerEvent
插槽 <slot> 对应 WXML 的 <slot>

双线程下的 Exparser

双线程模型下，组件系统不能像浏览器里的 Web Components 那样只靠一棵 DOM 树解决问题。更稳妥的理解是：

  • 渲染层的 Exparser：负责视图真实节点、样式和事件分发
  • 逻辑层的 Exparser：负责组件实例、data、methods、lifetimes 等逻辑状态
  • 框架协议：负责把逻辑层状态变化同步到渲染层

两边通过 Native 桥接保持一致。这也是为什么 this.setData({...}) 会触发跨线程通信——逻辑层改了组件状态，必须通知渲染层更新视图。

事件系统的”三种冒泡”

Exparser 的事件系统基本完全复刻了 Shadow DOM。这里有个容易踩坑的细节：

在 WebComponents 的 Shadow DOM 里，事件冒泡分两种：Shadow Tree 上冒泡 和 Composed Tree 上冒泡。Exparser 对应到：

<!-- 自定义组件 input-with-label 内部 -->
<label>
  <slot></slot>  <!-- 使用方传的 button 会插进这里 -->
</label>

<!-- 使用方页面 -->
<view>
  <input-with-label>
    <button bindtap="onTap">点我</button>
  </input-with-label>
</view>

当 button 触发事件：

  • 非冒泡事件：只在 button 上能监听到
  • Shadow Tree 冒泡：button → input-with-label → view（走组件的 Shadow Tree）
  • Composed Tree 冒泡：button → slot → label → input-with-label → view（走合成后的完整树）

自定义组件用 this.triggerEvent 触发事件时，options 里的 bubbles（是否冒泡）、composed（是否跨 Shadow）、capturePhase（是否走捕获阶段）对应的就是这几种语义。

通信系统：WeixinJSBridge 到底在做什么

前面反复提”跨线程通信”，这里把它拆开讲。

两个线程之间的消息载体叫 WeixinJSBridge。Native 会在小程序启动时分别向两个线程（的全局环境）注入这个对象。它的核心 API 有：

WeixinJSBridge.invoke(apiName, params, callback);  // 调 Native API（如 wx.login）
WeixinJSBridge.publish(eventName, data);           // 向另一线程发消息
WeixinJSBridge.subscribe(eventName, handler);      // 订阅来自另一线程的消息
WeixinJSBridge.on(eventName, handler);             // 订阅开发者工具触发的事件

三种不同环境的实现

WeixinJSBridge 在不同宿主环境里的底层实现完全不同：

环境 实现方式
iOS 客户端 WKWebView 的 messageHandlers（window.webkit.messageHandlers.xxx.postMessage）
Android 客户端 WebView 注入 Java 方法到 window（@JavascriptInterface）
开发者工具 WebSocket（IDE 是 Electron 应用，模拟通信）

三者对上封装成统一的 WeixinJSBridge，开发者感知不到差异。这就是为什么同一份小程序代码能在 iOS、Android、开发者工具里都跑——兼容层做在了 Native 和 WebView 之间的那条路上。

一次完整的”点击 → setData → 渲染”链路

从用户点击按钮，到页面内容更新，完整发生了这些事：

[渲染线程]                              [Native]                    [逻辑线程]
   │                                      │                            │
   ① 用户点击                              │                            │
   │                                      │                            │
   ② 基础库捕获触摸事件                   │                            │
   │   → 转换为 tap 事件                   │                            │
   │   → 交给组件事件系统分发               │                            │
   │                                      │                            │
   ③ WeixinJSBridge.publish               │                            │
   │   command: WEBVIEW_PUBLISH ──────►   │                            │
   │   { eventName: 'tap',                │                            │
   │     data: { id, dataset... } }       │                            │
   │                                      │                            │
   │                                      ④ 转发 ──────────────────►  │
   │                                      │                            │
   │                                      │                            ⑤ 触发绑定的 onTap
   │                                      │                            │   执行业务逻辑
   │                                      │                            │
   │                                      │                            ⑥ this.setData({...})
   │                                      │      ◄────────────────────│   WeixinJSBridge.publish
   │                                      ⑦ 转发 APPSERVICE_PUBLISH    │
   │                                      │                            │
   ⑧ WeixinJSBridge.subscribe 收到 ◄─────│                            │
   │   → 走 virtual DOM diff              │                            │
   │   → 真实 DOM 更新                    │                            │

两次跨线程通信、数据两次序列化。这就是 setData 不能乱调的根因。

setData 的几个硬规则

从上面的机制推出几个实战铁律：

  1. 不要调用 setData 传入过大的数据——API 文档里的硬限制是单次不超过 1024KB，实战里越小越好（序列化是瓶颈）
  2. 不要频繁调用 setData——每次都是一次跨线程 RPC
  3. 只更新变化的字段，用 this.setData({ 'list[0].name': 'xxx' }) 精确路径，而不是整个 list 赋值
  4. 长列表渲染优化：要么分页/虚拟列表，要么迁移到 Skyline 下更适合长列表的组件和按需渲染能力

WXS：在渲染层直接跑 JS

上面讲到手势这种高频事件被跨线程通信卡脖子，微信团队的补救方案是 WXS（WeiXin Script）。

WXS 本质是在渲染层直接执行的一段 JS 子集。它的运行环境不在逻辑层的 JSCore，而在 WebView 里，所以：

  • 可以直接响应渲染层的事件
  • 可以直接操作组件的 transform、opacity 等样式
  • 不走跨线程通信，没有 setData 开销

一个典型的手势拖拽例子：

<!-- index.wxml -->
<wxs module="drag">
  var startY = 0;
  var currentY = 0;

  function touchstart(event, ownerInstance) {
    startY = event.touches[0].clientY;
  }

  function touchmove(event, ownerInstance) {
    currentY = event.touches[0].clientY;
    var delta = currentY - startY;
    // 直接修改视图层，不走逻辑层
    var instance = ownerInstance.selectComponent('.card');
    instance.setStyle({
      transform: 'translateY(' + delta + 'px)'
    });
  }

  module.exports = { touchstart: touchstart, touchmove: touchmove };
</wxs>

<view class="card"
      bind:touchstart="{{drag.touchstart}}"
      bind:touchmove="{{drag.touchmove}}">
  拖动我
</view>

WXS 的几个限制：

  • 不是完整的 JS，不支持 ES6+ 语法（箭头函数、解构、class 都不行，要用 ES5）
  • 不能调用小程序 API（wx.xxx 拿不到）
  • 不能访问逻辑层的变量，只能通过传参和返回值

所以 WXS 的定位很明确：高频视图交互的补丁，而不是业务逻辑的容器。

自定义组件与 behaviors

小程序 1.6.3 开始支持自定义组件。一个组件的结构是四个文件：

my-component/
├── my-component.wxml   # 模板
├── my-component.wxss   # 样式（默认作用域隔离）
├── my-component.js     # 逻辑
└── my-component.json   # 组件声明

my-component.json 里必须声明：

{
  "component": true,
  "usingComponents": {}
}

Component 构造器

Component({
  // 组件属性：父组件传入
  properties: {
    title: {
      type: String,
      value: '默认标题',
      observer: function(newVal, oldVal) {
        // 属性变化时的回调
      }
    }
  },

  // 组件内部数据
  data: {
    count: 0
  },

  // 组件方法
  methods: {
    onTap() {
      this.setData({ count: this.data.count + 1 });
      // 向父组件发事件
      this.triggerEvent('tap', { count: this.data.count }, {
        bubbles: true,       // 是否冒泡
        composed: true,      // 是否穿透 Shadow DOM
        capturePhase: false  // 是否走捕获阶段
      });
    }
  },

  // 组件生命周期
  lifetimes: {
    attached() { /* 插入节点树时 */ },
    ready() { /* 初次渲染完成 */ },
    moved() { /* 节点被移动 */ },
    detached() { /* 被移除 */ }
  },

  // 所在页面的生命周期
  pageLifetimes: {
    show() {},
    hide() {},
    resize() {}
  }
});

注意 lifetimes（组件生命周期）和 pageLifetimes（组件感知的页面生命周期）是两组不同的概念，别搞混。

Behavior：组件的”Mixin”

多个组件想共享一些逻辑，用 behavior：

// behaviors/countable.js
module.exports = Behavior({
  data: { count: 0 },
  methods: {
    increment() {
      this.setData({ count: this.data.count + 1 });
    }
  }
});

// my-component.js
const countable = require('./behaviors/countable');
Component({
  behaviors: [countable],
  methods: {
    // 可以直接用 this.increment()
  }
});

Behavior 的合并策略：同名字段按优先级合并（组件自身 > behaviors 里后声明的 > 先声明的 > 基础行为）。生命周期是全部执行，不是覆盖。

路由与生命周期

路由栈

小程序的路由就是一个 WebView 栈。五个 API 对栈的操作：

API 对栈的操作 限制
wx.navigateTo push（新 WebView 入栈） 不能打开 tabBar 页面，最多 10 层
wx.redirectTo replace（当前出栈、新的入栈） 不能打开 tabBar 页面
wx.navigateBack pop（出栈，可指定 delta） 最多回到首页
wx.switchTab 清栈，只留 tab 页面 只能打开 tabBar 页面
wx.reLaunch 清栈，留新页面 可以打开任意页面

生命周期全景

App 级（app.js 的 App({...})）：

  • onLaunch — 小程序首次启动
  • onShow — 从后台切到前台
  • onHide — 切到后台
  • onError — JS 报错兜底
  • onPageNotFound — 路由找不到

Page 级（Page({...})）：

  • onLoad(query) — 页面加载，只调一次
  • onShow — 页面显示（每次切回都触发）
  • onReady — 初次渲染完成（只调一次）
  • onHide — 页面隐藏
  • onUnload — 页面卸载

配合路由行为来看几个关键点：

  • wx.navigateTo 跳走：旧页面 onHide（**不会 onUnload**，因为 WebView 还在栈里）
  • wx.navigateBack 回来：目标页 onShow（**不会 onLoad**）
  • wx.redirectTo 跳走：旧页面 onUnload（当前 WebView 被替换）
  • wx.switchTab 跳走：非 tab 页面全部 onUnload

Component 级（上一节讲过）：created → attached → ready → moved → detached。

跨端框架是怎么”骗”小程序的

这是理解小程序架构威力的另一个角度。Taro、uni-app、Remax、mpvue 这些跨端框架，本质都在解决一个问题：让 Vue/React 的代码跑在小程序的约束里。它们分三派。

第一派：预编译（Taro 2.x、mpvue 早期、wepy）

思路：把 Vue/React 代码直接编译成小程序源码。

  • Vue 的 <template> → WXML
  • <script> → 小程序的 Page/Component
  • <style lang="less"> → WXSS
Vue/React 源码
    │
    ▼
  AST 解析
    │
    ▼
 DSL 转换
    │
    ▼
生成 WXML + WXSS + JS
    │
    ▼
 小程序运行

缺点很明显：

  • React/Vue 每出新特性，框架团队要跟着写语法解析（Taro 支持 Hooks 就是这么做的）
  • 转换有盲区——比如 {{ arr.filter(x => x.done) }} 这种动态表达式，WXML 没对等物
  • 出问题很难调

第二派：半编译半运行时（mpvue 重构后、Taro Next）

思路：template 预编译成 WXML，runtime 完整跑在逻辑层。

mpvue 就是 fork 了 Vue，改了两个关键位置：

  1. compiler 层：把 <template> 单独抽出来编译成 WXML
  2. runtime 的 patch 层：原本 Vue 的 patch 是操作 DOM，改成调 setData
// mpvue 改 Vue 的 patch 核心
function patchData(vm, newData) {
  const diff = diffData(vm._prevData, newData);  // diff 出变化
  if (Object.keys(diff).length > 0) {
    vm.$throttledSetData(diff);  // throttle 避免频繁通信
  }
}

这个方案比纯预编译好，因为 Vue 的响应式、生命周期、计算属性等运行时特性都能保留。但 template 还是要预编译，所以叫”半编译半运行时”。

uni-app：把半编译半运行时做到极致

uni-app 是这一派里最值得单拎出来讲的一个——它和 mpvue 同源却走得更远。早期 uni-app 和 mpvue 是一个路线：fork Vue + 编译 template。但 DCloud 把这套做法工程化到了另一个层级。

核心做法可以拆成四步：

1. 编译期：Vue SFC → 小程序四件套

.vue 文件
├── <template>  ──► wxml  （AST 转换，保留 Mustache/wx:for/wx:if 语义）
├── <style>     ──► wxss  （加前缀、rpx 处理）
├── <script>    ──► js    （Vue 运行时 + 业务逻辑）
└── 伴随的 config ──► json

Vue2 版编译器基于 Webpack，Vue3 版切到了 Vite。

2. 运行时：一个”小程序版 Vue runtime”

这是和 mpvue 最像的部分——逻辑层跑着一个裁剪版 Vue，响应式系统、生命周期、computed、watch 全部保留。数据变更的最终出口依然是 setData，而不是操作 DOM。

3. 组件策略：直接映射 vs 组件封装

这一步是 uni-app 的精髓。它的 <view>、<button>、<image> 这些基础组件**直接对应编译成小程序原生的 <view>、<button>、<image>**，不走 runtime 封装。这意味着：

uni-app 的 <view>      Taro 3.x 的 <View>
      │                       │
      ▼                       ▼
小程序原生 <view>      Taro 运行时组件 → 递归 template → <view>
  （零额外开销）            （一层封装，有性能代价）

uni-app 靠”组件规范贴近微信小程序”换来了编译产物几乎零 runtime 组件开销，代价是跨端时其他平台要做反向适配（比如 H5、App 要自己实现 <view>）。

4. API 转义：uni.* ≡ wx.*

uni.request 在微信端被直接转成 wx.request。这就是为什么 uni-app 在微信小程序上的性能表现常常和原生小程序差距很小——API 层就是个极薄的 alias，基本没有运行时成本。

和 mpvue 的核心差异：

维度 mpvue uni-app
Vue 版本 基于 Vue 2，没跟上 Vue 3 Vue2/Vue3 双版，Vue3 版用 Vite
编译目标平台 只做小程序 微信/支付宝/百度/头条/QQ/快手/钉钉/淘宝/快应用全覆盖
组件规范 Vue 标准组件名 贴近小程序组件名（直接映射）
App 端 无 自研 nvue（类 RN）+ uni-app x（纯原生）
维护状态 基本停更 活跃，x 版本在演进

和 Taro 3+ 的核心差异：

  • Taro 3+ 是纯运行时——要在小程序里模拟一份假 DOM，<View> 是 Taro 的组件不是小程序原生 <view>
  • uni-app 是半编译半运行时——<view> 在编译期就变成小程序原生 <view>
  • 直接结果：**uni-app 在小程序端的性能普遍优于 Taro 3+**，但 Taro 3+ 的 React 生态兼容性更好（Hooks、Redux、React 新特性都能吃到）

uni-app 的”骗法”总结：它对小程序的”骗”是最温和的——编译产物长得几乎和原生小程序一样，运行时只多了一层薄薄的 Vue。代价是框架设计必须向小程序的规范妥协（组件名、API 命名都贴近小程序），这也是为什么从微信小程序迁到 uni-app 比迁到 Taro 容易很多。

顺带提一下 uni-app x：这是 DCloud 2023 年后推出的下一代方案，用 .uvue 文件 + UTS 语言，目标是 App 端彻底抛弃 WebView，走纯原生渲染（类似 Flutter/RN 的路子）。小程序端的思路仍然延续半编译半运行时——因为小程序平台本身就没留口子让你换渲染器。

第三派：纯运行时（Remax、Taro 3+、Rax）

思路：template 也不编译了，直接在运行时动态渲染。

但小程序不给你 DOM API，怎么动态渲染？Remax 用的是递归 template技巧：

<!-- 一个万能的递归模板 -->
<template name="tpl-container">
  <block wx:for="{{root.children}}" wx:key="id">
    <template is="{{item.type}}" data="{{item}}" />
  </block>
</template>

<template name="tpl-view">
  <view>
    <template is="tpl-container" data="{{root: item}}" />
  </view>
</template>

<template name="tpl-text">
  <text>{{item.text}}</text>
</template>

<!-- 页面里 -->
<template is="tpl-container" data="{{root: pageData}}" />

再在 JS 侧实现一套假的 DOM API（createElement、appendChild、removeChild…），让 React Reconciler 跑在这些假 DOM 上，所有变更都反映到一个 JSON 树上，最后 setData 把这棵树同步到 WXML。

// Remax 的假 DOM（简化示意）
class VNode {
  constructor(type, props) {
    this.id = generateId();
    this.type = type;
    this.props = props;
    this.children = [];
  }
  appendChild(child) {
    this.children.push(child);
    this.root.update();   // 触发 setData
  }
}

React 跑起来完全不知道自己不在浏览器里——它以为自己在操作 DOM，其实在操作一个 JSON 树。这棵树再通过 setData 同步到 WXML 的递归 template，渲染出真实界面。

这个方案的威力：更容易跟进 React 的运行时能力，因为框架主要改的是最底层的渲染适配器，而不是每个语法特性都重新编译一遍。比如 Hooks 这类运行时特性通常更容易支持；但像 Suspense、Concurrent 这类能力，仍然取决于具体框架版本、渲染适配器和小程序环境限制，不能简单说“自动全支持”。代价是性能——全量 JSON 树的 diff + setData 序列化开销比预编译方案大。

Skyline：小程序的”架构级重构”

讲到这里，双线程架构的所有结构性问题已经很清晰了：

  1. 跨线程通信贵：WebView 模式下，setData 很容易成为性能瓶颈
  2. 每页一个 WebView 费内存：页面栈 10 层硬限制，iOS 回收 WKWebView 还有恢复问题
  3. WebView 渲染管线慢：要兼容 Web 标准，样式计算、布局、绘制都冗长
  4. Web 能力天花板：手势、转场、共享元素、长列表这些原生应用标配，Web 做起来别扭

微信团队的回答是：重新写一个渲染引擎。这就是 Skyline。

Skyline 和 WebView 模式的根本差异

最容易误解的一点是：Skyline 不是简单把双线程砍成单线程。

官方对 Skyline 的描述更接近这样：它不再使用传统 WebView 作为页面渲染后端，而是新增一套更轻量的渲染引擎；同时在 AppService 中划出独立上下文，运行原来 WebView 承担的视图构建逻辑，再由 Skyline 的渲染线程负责 Layout、Composite、Paint 等任务。

WebView 模式                         Skyline 模式
┌─────────────┐                     ┌─────────────────────┐
│ 渲染层 WebView│                     │ AppService            │
│ DOM/CSS/Layout│◄── JSBridge ──►    │ 业务 JS + 视图构建逻辑   │
└─────────────┘                     └──────────┬──────────┘
       ▲                                       │
       │                                       ▼
┌─────────────┐                     ┌─────────────────────┐
│ 逻辑层 JS    │                     │ Skyline 渲染线程      │
│ (JSCore)    │                     │ Layout/Paint/Composite│
└─────────────┘                     └─────────────────────┘

所以，Skyline 真正优化的是：

  • 不再为每个页面新建一个 WebView JS 引擎实例，减少内存和启动开销
  • 框架内部少了大量 WebView 与 AppService 之间的 JSBridge 数据交换
  • 渲染管线更短，Layout、Composite、Paint 更贴近原生渲染流程
  • WXS 在 Skyline 下会移到 AppService 中，部分查询页面信息的接口会变成异步；复杂动画则推荐用更靠近渲染流程的 Worklet

官方文档的说法是：新的架构能减少大量通信时间开销，界面也更不容易被逻辑阻塞。

但安全沙箱怎么办？Skyline 的渲染引擎不是 WebView，开发者依然拿不到浏览器 DOM/BOM API，只能使用小程序暴露的组件和接口。安全性不再主要依赖“业务 JS 和 WebView 分线程隔离”，而是依赖小程序自研渲染后端和能力白名单。

其他关键优化

优化点 具体做法 收益
更短的渲染管线 用 Skyline 后端替代 WebView 的复杂渲染链路 首屏、建树、布局链路更轻
减少框架通信 框架内部不再大量依赖 WebView 和 AppService 之间的 JSBridge 交换 通信耗时降低
资源复用 页面之间可以共享更多框架资源 内存和启动开销降低
长列表按需渲染 scroll-view / list-view 等组件支持更适合长列表的渲染能力 长列表更稳
Worklet 动画和手势逻辑更靠近渲染流程 高频交互更丝滑

Skyline 的新能力

Skyline 不是单纯的”更快的 WebView”，它补齐了 Web 体系缺的原生能力：

Worklet 动画：带 'worklet' 指令的函数可以运行在 UI 线程，动画和手势逻辑不必每一帧都绕回普通 JS 线程（和 RN 的 Reanimated 思路接近）。

const { shared, timing } = wx.worklet;

Page({
  onLoad() {
    const scale = shared(1);

    this.applyAnimatedStyle('.box', () => {
      'worklet';
      return {
        transform: `scale(${scale.value})`
      };
    });

    this._scale = scale;
  },

  onTap() {
    this._scale.value = timing(1.2, { duration: 200 });
  }
});

手势系统：基于 Worklet 的原生手势识别，支持手势协商——解决多层滚动、拖拽的冲突问题。

自定义路由 + 共享元素：页面切换动画可以完全自定义，两个页面之间的元素可以”飞”过去（iOS 的 hero transition）。

grid-view 瀑布流：原生实现的瀑布流组件，性能远超 WebView。

snapshot 截图组件：直接对 WXML 子树截图，替代以前复杂的 canvas 方案。

如何启用 Skyline

页面级（page.json）：

{
  "renderer": "skyline",
  "componentFramework": "glass-easel"
}

分包级（app.json）：

{
  "subPackages": [{
    "root": "packageA",
    "componentFramework": "glass-easel",
    "renderer": "skyline"
  }]
}

向后兼容：Skyline 页面和 WebView 页面可以互相跳转。不支持 Skyline 的环境可以降级到 WebView，但不是所有东西都能“无脑兼容”：Worklet、手势系统、部分 Skyline 组件属性和样式差异，仍然需要单独做兼容处理。

我的实战判断

  • 新项目可以考虑”优先适配 Skyline，关键路径保留 WebView 兜底”的策略
  • 老项目按页面或分包粒度渐进迁移，优先迁列表页、动画重的页面
  • 如果业务大量依赖 web-view 组件、复杂富文本或历史 CSS 行为，要重点做真机回归
  • Skyline 的样式、组件和事件细节与 WebView 不完全一致，要注意降级兼容
  • Skyline 现在默认搭配新版组件框架 glass-easel，老项目迁移时要同时关注组件适配问题

插件系统：小程序的”小程序”

小程序插件（plugin）是微信提供的模块化复用机制。一个插件就是一个可以被多个小程序引用的代码包，里面可以包含页面、自定义组件、JS 接口。

插件的两个角色

插件方（提供者）：

my-plugin/
├── plugin.json          # 插件配置
├── components/
│   └── hello-component/ # 对外暴露的组件
├── pages/
│   └── hello-page/      # 对外暴露的页面
└── index.js             # 对外暴露的 API

plugin.json 声明哪些东西对外开放：

{
  "publicComponents": {
    "hello-component": "components/hello-component/hello-component"
  },
  "publicPages": {
    "hello-page": "pages/hello-page/hello-page"
  },
  "main": "index.js"
}

使用方：

// app.json
{
  "plugins": {
    "myPlugin": {
      "version": "1.0.0",
      "provider": "wxabc123xxx"  // 插件 AppID
    }
  }
}

<!-- 页面 -->
<hello-component name="world" />

// 调插件的 API
const plugin = requirePlugin('myPlugin');
plugin.hello('world');

插件的原理约束

插件不是普通的 npm 包，它受很多限制：

  • 插件不能独立运行，必须宿主小程序引用
  • 插件有独立的 AppID，审核流程和普通小程序分开
  • 插件默认沙箱化：拿不到宿主的 wx.getUserInfo、wx.login——必须宿主主动把接口传进去
  • 功能页（functional-page-navigator）：微信开放了一些”功能页”（如获取用户信息、发票信息）专门给插件用，让插件能在不拿宿主 appid 的前提下调用

插件机制设计的核心是**在小程序平台上再建一层”第三方开放市场”**，让能力可以跨小程序流通，同时不泄露宿主的身份和权限。实际业务里常见的用法是把 SDK 封装成插件（支付、地图、客服、IM），供多个业务方统一接入。

踩过的坑

坑 1：setData 路径写法导致全量更新

// ❌ 错误：整个 list 都会重新 diff
this.setData({ list: newList });

// ✅ 正确：只更新变化的那一项
this.setData({ 'list[3].status': 'done' });

列表里改一项，第二种写法性能差十倍以上。原因就在跨线程序列化——第一种写法整个 list 都要重新 JSON 化。

坑 2：WXS 里写 ES6 语法直接白屏

WXS 不支持 ES6+。

// ❌ 在 WXS 里
var fn = (x) => x * 2;  // 直接报错

// ✅ 改成 ES5
var fn = function(x) { return x * 2; };

坑 3：自定义组件样式穿透

自定义组件默认有独立样式作用域，外部样式进不去。想让部分样式透进去要在组件 options 里加：

Component({
  options: {
    addGlobalClass: true,           // 允许全局样式类作用进来
    styleIsolation: 'apply-shared'  // 或者这个，含义不同
  }
});

styleIsolation 有 isolated、apply-shared、shared 三档，具体选哪个根据设计系统决定，但默认 isolated 最严格，很多时候会让新人以为”样式没生效”。

坑 4：Skyline 页面的 CSS 子集差异

切到 Skyline 后，有些 CSS 特性是不支持或行为不同的（比如某些高级选择器、部分伪类、复杂 filter）。迁移前一定要在开发者工具里把”Skyline 兼容性检查”打开，批量扫一遍。

坑 5：页面栈 10 层限制

WebView 模式下页面栈最多 10 层。过深路径（比如电商的”商品 → 详情 → 评价 → 某条评价 → 用户主页 → 另一个商品…”）要用 redirectTo 或 reLaunch 截断，否则 wx.navigateTo 会直接报错。Skyline 降低了每页一个 WebView 带来的内存压力，但具体路由限制仍要以当前基础库和真机表现为准，兼容老版本时更不能忽略这个问题。

小结

  1. 传统小程序是双线程架构：渲染层（WebView）+ 逻辑层（AppService），Native 中转，目的是安全沙箱 + 原生级体验
  2. WXML/WXSS 会经过小程序编译链路处理，运行时再结合 data 更新视图；具体编译产物属于内部实现，不应当成稳定 API
  3. PageFrame 可以理解成预热页面容器，用来降低新页面冷启动成本；具体注入和调度细节以基础库实现为准
  4. Exparser 是微信自研的仿 Shadow DOM 组件系统，逻辑层负责组件状态，渲染层负责视图节点，两边通过框架协议同步
  5. WeixinJSBridge 在不同宿主有不同底层实现，对上统一成小程序的通信和 API 调用通道
  6. setData 贵在跨线程通信 + 序列化，优化就是减少次数、精确路径、控制数据量
  7. WXS 在 WebView 模式下运行在渲染层，适合做高频视图交互；Skyline 下复杂动画更推荐 Worklet
  8. 跨端框架分三派：预编译（Taro 早期）、半编译半运行时（mpvue）、纯运行时（Remax、Taro 3+）
  9. Skyline 用自研渲染管线替代 WebView 渲染后端，减少框架层通信，并通过渲染线程、Worklet、手势系统等提升复杂交互体验
  10. 插件是小程序平台上的”小程序市场”，有独立 AppID 和沙箱，专为跨小程序能力复用设计

配套开源实现：miniapp-decoded

理论讲完了，光看文字还是容易”一听就懂、一写就忘”。我把本文讲到的双线程架构用 Web 技术栈实装了一遍，代码开源在：

🔗 github.com/XY0987/miniapp-decoded

核心思路很朴素——用浏览器里现成的三样东西，把小程序双线程架构复刻一遍：

本文讲到的 真机实现 miniapp-decoded 里用什么模拟
渲染线程 WKWebView / XWeb <iframe>
逻辑线程 iOS JSCore / Android V8 Web Worker
微信客户端 原生 App 主页面（一个 Web 应用）
WeixinJSBridge iOS messageHandlers / Android @JavascriptInterface window.JSBridge 对象 + mitt 事件总线
WAService.js / WAWebview.js 基础库运行时 logic/ / ui/ 两个 SDK 包
PageFrame 预热的页面容器 native/pageframe/index.html
小程序编译器 开发者工具内置 compile/ 包：wxml → Vue render 函数

它为什么值得一看

1. 能单步调试每一次跨线程通信。 真机里 JSCore ↔ WebView 之间的消息你看不见摸不着；这里打开 Chrome DevTools，主线程、Worker、iframe 三个上下文的断点可以同时打，一次点击的完整链路走单步没问题。

2. 架构关键点”硬约束”是真的，不是表演。 Worker 里真的没有 document，iframe 和 Worker 真的不能直连（所有消息必须经过主页面中转），这些正是本文反复强调的小程序设计本质。

3. 有”最小 demo”和”完整版”两档。 minimal-demo/ 把所有 SDK 和编译器都剥掉，只留 100 行左右的 Worker + iframe + postMessage 骨架——先用它搞懂”双线程到底是什么”，再回到完整版看”工程化之后长什么样”。

读到本文哪一节 就去看仓库的哪个文件

它刻意没做的部分

作为教学 demo，为了不喧宾夺主，有几处刻意简化或省略了，每一处都在仓库 README 里说明了原因，这里列个概览：

省略 原因
Exparser 换成 Vue 2 Exparser 是十万行级别的自研基础库，复现成本极高，偏离教学目标
setData 没做 data diff 对理解”为什么要跨线程”没有增量收益
跨 iframe 没真走 postMessage（直接调函数） 同源 iframe 下直接调用最直观，避免套一层无关异步
没有进程隔离 浏览器平台不提供该能力，不是偷懒，是平台限制
wx.* 原生 API 全未实现 那是独立话题（宿主客户端能力封装），混讲反而讲不清双线程
Skyline 完全不模拟 Web 平台没有非 WebView 的渲染后端，根本性能力缺失

一句话：**它复现的是”架构层面的消息流”，不是”运行时层面的性能/隔离特征”**。用它理解”为什么 setData 异步、为什么要 PageFrame 预热、为什么逻辑层不能操作 DOM”——够了；用它分析”小程序为什么快/慢”——不够，那些问题的答案藏在被省略的部分里（但本文正文已经讲清楚了）。
