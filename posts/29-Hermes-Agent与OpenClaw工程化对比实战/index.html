Hermes Agent 与 OpenClaw 工程化对比：架构、多 Agent 与落地选型

发表于2026|更新于2026|AI相关
|字数总计:4.8k|阅读时长:17分钟

前言：这周（2026-05-07）Hermes 刚发了 v0.13.0「Tenacity Release」，把曾经被撤回过一次的多 Profile Kanban 重新实现并转正——这意味着 Hermes 的多 Agent 叙事，从之前更偏「单 Agent 内角色切换 / Profile 切换」，推进到了「共享看板 + Worker 生命周期管理 + 故障恢复」这套工程化协作模型。刚好可以和 OpenClaw 的 Multi-Agent Routing / Sub-agents 放在一起对照。这篇换个工程视角，把两者架构、多 Agent 演进、部署路径完整对一下。

行业时间线

时间 事件
2025-11 OpenClaw 早期项目（Clawdbot / Moltbot 阶段）出现，主打本地优先 + 多平台 Gateway
2026-02-25 Nous Research 开源 Hermes Agent，主打 Learning Loop + Skills 自我沉淀
2026-03 前后 OpenClaw 多 Agent 路由和 Sub-agents 文档 / 社区实践逐步完善
2026-04 前后 Hermes 早期 Kanban 实现合入后被整体撤回（reverted）
2026-05-07 Hermes v0.13.0 「Tenacity Release」发布，多 Profile Kanban 重构转正（post-revert reimplementation）

这条时间线两个要点：

  1. OpenClaw 更早把多 Agent 路由做进 Gateway 体系；Hermes v0.13.0 的重点则是把多 Profile Worker + durable Kanban 这套任务韧性模型补齐。
  2. Hermes 的 Kanban 不是新生儿——更早版本曾经合入过一版但被撤回，v0.13.0 是 #17805「post-revert reimplementation」，重写时直接做成”durable + multi-profile by design”。这也解释了为什么这一版同时配套 Checkpoints v2 重写状态持久化。

两个项目的工程定位

维度 Hermes Agent OpenClaw
开发方 Nous Research Peter Steinberger（个人 + 社区）
协议 MIT MIT
主语言 Python Node.js / TypeScript
核心抽象 单体 Agent + Learning Loop Gateway + Skills + Prompt / 配置文件
架构定位 自进化智能体运行时 跨平台 Agent 执行网关
部署形态 本地 / VPS / Docker / Serverless 都可 本地常驻（推荐 Mac/NAS）
多 Agent 形态 v0.13 起重点补齐：多 Profile Worker + Kanban Multi-Agent Routing + Sub-agents + 可选 A2A

Hermes 把重心放在 Agent 怎么变聪明，OpenClaw 把重心放在 Agent 怎么连到各种地方协同干活。

Hermes 的架构骨架

Hermes 核心架构：

┌──────────────────────────────────────────────┐
│           消息网关（Telegram/Discord/...）     │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│           Agent 执行循环                       │
│   LLM Planner ↔ Tool Executor ↔ Skills       │
└──────────────────┬───────────────────────────┘
                   ▼
┌──────────────────────────────────────────────┐
│           学习闭环（Learning Loop）            │
│  MEMORY/USER ↔ session_search ↔ skill_manage │
└──────────────────────────────────────────────┘

差异化的核心是 Learning Loop。更准确地说，它不是官方文档里叫作「Compact / Session / Episodic」的三层记忆，而是几套机制叠在一起：

机制 作用 存储 / 实现
MEMORY.md 项目约定、环境事实、长期经验 ~/.hermes/memories/MEMORY.md，会作为冻结快照注入 System Prompt
USER.md 用户偏好、沟通风格、身份信息 ~/.hermes/memories/USER.md
session_search 查历史会话，不要求提前写进记忆 SQLite state.db + FTS5 全文搜索 + LLM 摘要
External Memory Providers 更深的语义记忆 / 用户建模 Honcho、Mem0、Supermemory 等可选 Provider

skill_manage 是 Hermes 最具标志性的设计——Agent 在执行过程中可以自己 create / patch / edit / delete / write_file / remove_file Skill。比如一次成功跑完的 RSS 推送流程，Agent 可以固化成 daily-rss-digest Skill，下次直接复用；踩过的坑也可以沉淀进 Skill 文档或辅助文件里。

OpenClaw 的架构骨架

OpenClaw 核心架构：

┌─────────────────────────────────────────────┐
│   消息接入层：WhatsApp/Telegram/iMessage/...  │
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────────────────────────────────────┐
│           统一消息总线（归一化）               │
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────────────────────────────────────┐
│           OpenClaw Core                     │
│   LLM 适配  │  Skills 执行器  │  Prompt/配置  │
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────────────────────────────────────┐
│   本地执行：Shell/FS/Browser/MCP             │
└─────────────────────────────────────────────┘

OpenClaw 的核心抽象可以拆成三件事：

Gateway 是控制平面——统一管理 sessions、channels、tools、events，把 WhatsApp、Telegram、iMessage、Discord 等入口接到本地 Agent。

**Skill 是一个”包”**——文件夹形态，核心是 SKILL.md，可选带 scripts/、references/、配置文件和辅助资源。通常由用户编写、从 ClawHub 安装，或由社区维护。

Prompt / 配置文件决定怎么做——常见文件是：

文件 作用
SOUL.md Agent 人格、语气、风格和边界
AGENTS.md 操作规则、流程约束、协作方式
TOOLS.md 工具说明和工具上下文
USER.md 用户画像和偏好（视配置 / 版本而定）

这些资产大多是文件化的 → Git 可追踪、Code Review 友好。

多 Agent 协作：本文重点对比

这是两者最近差异化最明显的维度。

OpenClaw：Routing + Sub-agents + 可选 A2A

OpenClaw 的官方多 Agent 能力：Gateway 负责确定性路由，Sub-agents 负责后台并行任务，Agent-to-Agent messaging 负责可选的跨 Agent 通信。

1. Multi-Agent Routing（多 Agent 路由）

多个独立 Agent 可以跑在同一个 Gateway 下，但每个 Agent 有自己的 workspace、agentDir、会话历史、模型、Skill 白名单和工具权限。配置通常写在 ~/.openclaw/openclaw.json，核心字段是 agents.list 和 bindings：

{
  agents: {
    defaults: {
      workspace: "~/.openclaw/workspace",
      skills: ["calendar", "notes"]
    },
    list: [
      {
        id: "news-bot",
        name: "News Bot",
        workspace: "~/.openclaw/workspace-news",
        model: "<model-id>",
        skills: ["rss-reader", "summarize"],
        groupChat: { mentionPatterns: ["@news-bot"] }
      },
      {
        id: "dev-bot",
        name: "Dev Bot",
        workspace: "~/.openclaw/workspace-dev",
        model: "<model-id>",
        skills: ["github", "code-review"]
      }
    ]
  },
  bindings: [
    { agentId: "news-bot", match: { channel: "telegram", accountId: "alerts" } },
    { agentId: "dev-bot", match: { channel: "discord", guildId: "<guild-id>" } }
  ]
}

消息进来后，Gateway 根据 channel、account、peer、guild、role 等条件做确定性路由。Agent 之间默认是隔离的，真正需要共享记忆或通信时要显式配置。

2. Sub-Agents（子 Agent 派生）

一个 Agent 在执行过程中可以派生后台子 Agent 跑独立任务。Sub-agent 会运行在独立 session 里，典型 key 类似 agent:<agentId>:subagent:<uuid>，跑完后通过 announce 把结果回传给请求方。典型场景：主 Agent 收到”调研一下今年的 AI Agent 框架”，派生一个 researcher 子 Agent 专门跑搜索 + 总结，结果回传后主 Agent 整合输出。

3. Agent-to-Agent messaging（可选跨 Agent 通信）

OpenClaw 也有受控的 Agent-to-Agent messaging，但默认关闭，需要显式启用并配置 allowlist。它更像一个安全边界明确的通信工具，不等于官方内置了完整的 Swarm 编排引擎。

所以这三者的关系更像：

Routing：不同入口 / 账号 / peer 路由到不同 Agent
   │
   ▼
Sub-Agent：单个 Agent 把慢任务派给后台子任务
   │
   ▼
A2A：必要时显式允许 Agent 之间通信

如果你在社区文章里看到「OpenClaw Swarm」，我的理解是：多数情况下是基于 Routing、Sub-agents、A2A 自己拼出来的编排实践，或者第三方扩展，不建议把它当成 OpenClaw 官方核心抽象。

Hermes：从角色切换到多 Profile Kanban

很多人对 Hermes 的旧印象是单体 Agent + 角色 / Profile 切换——同一个 Agent 根据当前 Profile、System Prompt 和 Skill 组合，切到「编码助手」「私人秘书」「研究员」这类不同角色。这个理解更贴近 v0.13.0 之前的多 Agent 叙事：它更像一个演员换不同剧本，不是多个 Worker 围绕同一个任务板并发协作。

v0.13 之前的 Hermes 多角色：
  
   同一个 Agent 执行循环
   ┌────────────────────────────────────┐
   │  Profile A：编码助手                │
   │  SOUL / Skills / Memory 切到 dev    │
   └────────────────────────────────────┘
                    │ 切换 Profile
                    ▼
   ┌────────────────────────────────────┐
   │  Profile B：私人秘书                │
   │  SOUL / Skills / Memory 切到 daily  │
   └────────────────────────────────────┘

   ※ 重点是角色 / Profile 切换，
      不是共享看板上的多 Worker 抢任务

v0.13.0「Tenacity Release」改变的是任务协作和任务韧性——更早版本曾经合入过一版 Kanban 但被整体撤回（reverted），#17805 是 post-revert reimplementation，社区戏称”曾被撤回的多 Agent 看板重构转正”。

重做时直接定位为 durable multi-profile collaboration board，从底层就是多进程 / 多 Profile 设计：

Hermes v0.13.0 多 Profile Kanban：

         ┌────────────────────────────┐
         │   Durable Kanban Board      │
         │  ┌──┐ ┌──┐ ┌──┐ ┌──┐       │
         │  │待 │ │执 │ │审 │ │完 │     │
         │  │办 │ │行 │ │核 │ │成 │     │
         │  └──┘ └──┘ └──┘ └──┘       │
         └─────┬─────────┬────────────┘
               │ Lane    │ Lane
        ┌──────▼──────┐ ┌▼──────────────┐
        │ Profile A    │ │ Profile B     │
        │ Worker (独立 │ │ Worker (独立  │
        │ 进程)        │ │ 进程)         │
        │ heartbeat ✓  │ │ heartbeat ✓   │
        │ ownership ✓  │ │ ownership ✓   │
        └──────┬───────┘ └──────┬────────┘
               │                │
               └────────┬───────┘
                        ▼
        spawn / timeout / crash 三态计数
                        ▼
        zombie 检测 → reclaim → retry-cap

判断它是真多进程而不是”单进程角色切换”的几个关键证据（来自 v0.13.0 Release Notes）：

  • 出现 heartbeat / reclaim / zombie detection——这些是典型的多进程协调原语；Release 里甚至专门修了 darwin zombie workers（macOS 僵尸进程）
  • spawn / timeout / crash 三种失败计数被统一——单进程切换不会有 spawn 概念
  • Worker task-ownership 校验（破坏性工具调用必须由任务持有者发起）——多 Worker 并发才需要的隔离
  • 配套上线 Checkpoints v2 重写状态持久化，让多 Worker 状态可靠落盘

关键运行时机制：

  • 任务卡牌自动接单：空闲 Worker 主动从待办 Lane 拉任务
  • 心跳与僵尸检测：Worker 长时间无心跳 → 任务 reclaim 回看板
  • 自动交接：进程崩溃后任务自动转给同 Lane 其他 Worker
  • Per-task retry budget：每张卡片独立的重试上限，避免某一任务把池子拖垮
  • Hallucination Gate：拦截 Worker 虚构卡片 ID 等幻觉行为
  • /goal 持久目标锁定：单 Agent 内的跨轮目标锁（Ralph loop）——这是 Tenacity 的另一个支柱，与 Kanban 互补

Hermes 这一版把”单 Agent 内的韧性”（/goal）和”多 Agent 间的韧性”（Kanban）一起补齐，所以版本名叫 Tenacity（韧性）。

多 Agent 维度对比

对比点 Hermes（v0.13.0） OpenClaw
演进路径 角色 / Profile 切换 → v0.13 补齐多 Profile Kanban Gateway 多 Agent 路由持续完善
上线时间 2026-05-07（Kanban 重构转正，曾被撤回过一次） 2026-03 前后多 Agent 文档和实践逐步完善
进程模型 多 Profile Worker（Release Notes 强调 worker lifecycle） 多 Agent 实例（隔离 workspace / session / agentDir）
核心抽象 Kanban 任务卡牌 + Worker 池 Routing + Sub-agents + 可选 A2A
Agent 关系 Worker 围绕共享看板处理任务 异质 Agent 按入口、角色、工作区隔离
触发方式 任务卡牌自动接单 路由分发 / 主 Agent 派生 / 显式 A2A
容错能力 heartbeat + zombie detection + reclaim + retry budget Sub-agent 有独立 session / announce / 超时等机制，但不是 Kanban 式任务回收
数据隔离 看板共享 + Worker task-ownership 每个 Agent 独立 workspace / session，硬隔离依赖 sandbox
适合场景 长任务韧性执行（不半途而废） 多入口、多身份、多工作区分流
成熟度 Kanban 重构首版，待社区充分验证 Routing / Sub-agent 文档更完整，复杂编排仍要自己设计

一句话区分两者

**OpenClaw 的多 Agent 像”分部门接线”**——不同入口、账号、群组、角色被路由到不同 Agent，每个 Agent 有自己的工位和权限。

**Hermes 的多 Agent 像”任务流水线 + 工人池”**——你贴一堆任务卡，谁有空谁来干，干到一半倒下了下一个 Worker 接着干。

两者各有所长：OpenClaw 强在多入口路由和角色隔离，Hermes 强在长任务韧性（这也是 v0.13.0 名字叫 Tenacity 的原因）。

同一个需求：两种实现路径

把”每天 9 点把 RSS 里最值得看的 3 篇推到 Telegram”这个简单需求拿来对比。

Hermes：自然语言下达

用户：每天早上 9 点，把我订阅的 RSS 里最值得看的 3 篇推给我，源在 ~/rss.opml。

第一次执行时它从零摸索，执行完你给反馈：”这三篇都是水文，我想看深度技术文。”

Hermes 内部大致会做两件事：

  1. 把「偏好深度技术文、过滤营销内容」这类长期偏好写进 USER.md / MEMORY.md，或者交给外部 Memory Provider 维护。
  2. 如果这个流程足够复杂且可复用，就通过 skill_manage 创建或更新一个 daily-rss-digest Skill，把读取 OPML、抓取文章、过滤、推送这些步骤沉淀下来。

这里我不写伪 API，因为 skill_manage 的真实参数和调度能力要以当前版本官方文档为准。核心区别是：Hermes 更鼓励你先用自然语言跑通，再把经验沉淀成 Skill 和 Memory。

第二天 9 点，如果调度和消息网关配置好了，它就可以命中记忆里的偏好，挑出来的文章也会比第一天更贴近你的口味。

OpenClaw：装 Skill + 改配置文件

# 装 Skill（官方 ClawHub 文档使用复数 skills）
openclaw skills install rss-reader
openclaw skills install telegram-push

然后把约束写到对应的文件里：

<!-- AGENTS.md 或具体 Skill 的 SKILL.md -->

## RSS 推送规则

- 每天 09:00 执行 rss-reader + telegram-push 组合
- RSS 源：~/rss.opml
- 推送偏好：深度技术文，过滤营销内容（最多 3 篇）

如果筛选不准，优先改 skills/rss-reader/SKILL.md 的筛选规则；如果是执行流程或权限边界问题，再改 AGENTS.md 或 openclaw.json。

关键差异

对比点 Hermes OpenClaw
用户输入 自然语言描述 装 Skill + 改配置文件
学习成本 低（会说话就行） 中（要懂 Skill / Gateway / 配置文件）
首次成功率 中（需几轮反馈） 高（Skill 和配置写好后更稳定）
长期收益 高（Memory + Skill 会沉淀经验） 稳定（更偏显式规则，不会主动自我优化）
维护方式 给反馈让它更新记忆或 Skill 手动改 SKILL.md / AGENTS.md / openclaw.json
可审计性 中（Memory / Skill 混合，部分行为不如文件直观） 高（规则、Skill、Agent 配置文件化，Git 可追踪）

部署对比

Hermes：远端和本地都能跑，长任务更适合常驻

官方强调 Hermes 可以跑在 $5 VPS、Docker、SSH 远程主机、Modal、Daytona 等环境里。我的建议是：如果你只是 CLI 试用，本地就够；如果要接 Telegram / Discord 这类消息入口，并让它长期执行任务，放到 VPS 或常驻机器上更省心。

# docker-compose.yml（示意，实际镜像和目录以官方文档为准）
version: '3.8'
services:
  hermes:
    image: nousresearch/hermes-agent:latest
    restart: always
    volumes:
      - ./data:/app/data       # 记忆 / 状态持久化
      - ./skills:/app/skills   # 本地 Skill 目录
    env_file: .env
    # 多 Worker / 长任务场景建议准备更充裕内存，但 16GB 不是官方硬门槛

坑 1：记忆和状态目录没持久化
现象：容器重启后记忆、会话或 Skill 丢了。
原因：MEMORY.md、USER.md、state DB、skills 等目录没有挂到持久化 Volume，或权限不对容器写不进去。
解决：用命名 Volume，或者确保挂载目录、UID/GID 和权限匹配。

坑 2：自动生成的 Skill 需要审计
现象：Agent 沉淀出来的 Skill 能跑，但流程里夹杂了临时路径、过期命令或一次性假设。
原因：skill_manage 解决的是经验沉淀，不等于自动产出生产级插件。
解决：重要 Skill 进 Git，像代码一样 Review；能用 patch 小改就不要整篇重写。

OpenClaw：推荐本地常驻

典型场景是 Mac Mini / NAS 常开：

# macOS 用 launchd 开机自启
cat > ~/Library/LaunchAgents/com.openclaw.plist <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<plist version="1.0">
<dict>
    <key>Label</key><string>com.openclaw</string>
    <key>ProgramArguments</key>
    <array>
        <string>/usr/local/bin/npx</string>
        <string>openclaw</string>
        <string>start</string>
    </array>
    <key>RunAtLoad</key><true/>
    <key>KeepAlive</key><true/>
</dict>
</plist>
EOF

launchctl load ~/Library/LaunchAgents/com.openclaw.plist

坑 1：iMessage 网关只能在 macOS 跑
原因：iMessage 协议是 macOS 独占。
解决：要接 iMessage 的实例必须跑在 Mac 上，其他网关（Telegram/Discord）可以跨平台。

坑 2：Skill 执行权限边界
现象：某个 Agent 或 Sub-agent 调 shell / 文件写入 / 浏览器等工具时被拦。
原因：OpenClaw 的权限边界更多在 openclaw.json 里的 agents.list[].tools.allow/deny、sandbox 策略和全局工具策略里控制，不是简单写一行规则就放开。
解决：按 Agent 粒度配置工具 allow/deny；高风险入口启用 sandbox，不要把所有工具一股脑给所有 Agent。

选型决策

              ┌──────────────────┐
              │  你最在意什么？   │
              └────────┬─────────┘
       ┌───────────────┼─────────────────┐
       ▼               ▼                 ▼
  自进化省心       多平台连接          多 Agent 协作
   选 Hermes      选 OpenClaw         看协作形态
                                          │
                              ┌───────────┴───────────┐
                              ▼                       ▼
                         多入口路由              长任务韧性
                          OpenClaw                Hermes
                      (Routing/Sub-agents)    (Kanban 自动接单/重试)

1. 多 Agent 选型直接对应场景
要把不同渠道、账号、群组、角色路由到不同 Agent → OpenClaw（Routing + Sub-agents + 可选 A2A）。要”一堆任务排队让 Agent 池消化、挂了能自动续上” → Hermes（多 Profile Worker + Kanban）。

2. 不要为新版本买单（重要）
Hermes 的 Kanban 是 v0.13.0 刚”重构转正”——更早版本曾经合入又被整体撤回，这本身就说明这条路走得不轻松。如果你的多 Agent 场景在 OpenClaw 上跑得稳，没必要为了”新”切到 Hermes，先等几个补丁版本（比如 v0.13.x 把 spawn race、retry budget、ownership 边界打磨一轮）再说。

3. 资源预算
Hermes 官方强调可以跑在低成本 VPS / Docker / Serverless 上；但多 Worker、长任务和大量工具调用会放大资源消耗。OpenClaw 更偏本地常驻，Mac Mini / NAS 这类机器比较适合。这里不要把 16GB 当硬门槛，更应该按同时跑多少 Worker、接多少渠道、执行多少工具来估算。

4. 可审计性看 Git 友好度
团队/企业用 → OpenClaw（Skill、Agent 配置、SOUL.md、AGENTS.md 等文件化资产更容易 PR Review）。个人折腾 → Hermes 的 Memory + Skill 自沉淀会更省心，但关键 Skill 也建议纳入 Git 审计。

一个容易踩的认知坑

不要觉得”两者都有 Skills、都有多 Agent，所以差不多”——抽象层级根本不一样：

  • Skill：OpenClaw 的是文件化能力资产（静态目录 + SKILL.md），Hermes 的是 Agent 可以通过 skill_manage 动态创建和 patch 的过程性记忆
  • 多 Agent：OpenClaw 更像 Gateway 层的多入口、多账号、多工作区路由；Hermes v0.13.0 的重点是 durable Kanban 和 Worker 生命周期管理。如果你看到的资料是 5 月 7 日之前的，里面讲的 Hermes “多 Agent”大概率不是这套 Kanban Worker 模型

选型时一定要落到具体场景和具体版本，别看到名字相似就划等号。

小结

  1. Hermes 是单体 Agent + Learning Loop 架构，核心是 skill_manage、MEMORY.md / USER.md、session_search 和外部 Memory Provider
  2. OpenClaw 是 Gateway + Skills + Prompt / 配置文件架构，核心是跨平台连接、文件化配置和确定性路由
  3. Hermes v0.13.0 的重点不是普通 Profile 隔离，而是 durable multi-profile Kanban 重构转正
  4. OpenClaw 官方核心多 Agent 能力更准确地说是 Routing + Sub-agents + 可选 A2A，不建议把 Swarm 当官方核心抽象
  5. Hermes Kanban 的容错（heartbeat / zombie / reclaim / retry budget）说明它在补长任务韧性，而不是单纯做角色分工
  6. 同一个需求，Hermes 靠自然语言 + 反馈迭代沉淀 Memory / Skill，OpenClaw 靠装 Skill + 改配置文件保证可控性
  7. Hermes 远端和本地都能跑，OpenClaw 更适合本地常驻；资源预算要按 Worker、渠道和工具调用量估算
  8. 团队/企业可审计需求 → OpenClaw；个人省心自进化 + 长任务韧性 → Hermes（但建议等 v0.13.x 几个补丁版本再重度依赖 Kanban）
  9. Skill 和多 Agent 名字相同但抽象层级不同，选型要落到具体版本和具体场景，别看到名字相似就划等号
