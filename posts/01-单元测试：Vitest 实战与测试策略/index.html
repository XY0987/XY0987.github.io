单元测试：Vitest 实战与测试策略

发表于2026|更新于2026|工程化
|字数总计:5.6k|阅读时长:20分钟

前言：前面几个阶段把本地工具链（lint、类型检查、构建、组件库、发布）都讲透了。从这一篇开始进入第六阶段——把工程化从「本地工具链」扩展到「持续交付和线上质量」。第一步是测试。没有测试，后面的 CI、自动发布、灰度回滚都是在裸奔——你根本不知道这次改动有没有把别的东西弄坏。这篇先从最基础也最高频的单元测试讲起，工具选 Vitest。

为什么是 Vitest 而不是 Jest

前端单元测试的老牌选手是 Jest。但如果你的项目已经用了 Vite，那么可以直接上 Vitest。

原因不是「Jest 不好」，而是配置成本和一致性风险。Jest 要跑现代前端代码（ESM、TS、JSX、import.meta），得配 babel-jest 或 ts-jest、transform、moduleNameMapper，还常常和 Vite 的路径别名对不上，等于把构建配置在测试里重写一遍。更麻烦的是，两套转换链路一旦出现差异，就可能出现「测试能跑，生产构建挂了」或者「测试环境没复现真实问题」的情况。Vitest 的核心卖点是复用 Vite 的配置和转换管线——你在 vite.config.ts 里配的别名、插件、define，测试里直接生效，测试环境和真实构建环境也更容易保持一致。

维度 Jest Vitest
ESM / TS 开箱 需要额外 transform 原生支持（走 Vite）
配置复用 独立一套 复用 vite.config
路径别名 单独配 moduleNameMapper 复用 Vite resolve.alias
API 兼容 —— 基本兼容 Jest（describe/it/expect）
watch 速度 较慢 基于 Vite，HMR 式重跑，很快

API 上 Vitest 几乎是 Jest 的超集，describe / it / expect / vi.fn() 都在。Jest 项目迁过来成本很低。

最小可运行示例

环境：Node.js 20、Vitest 2.x。先装依赖：

pnpm add -D vitest

写一个被测函数 src/utils/price.ts：

export function formatPrice(cents: number): string {
  if (!Number.isInteger(cents) || cents < 0) {
    throw new Error('cents 必须是非负整数')
  }
  return `¥${(cents / 100).toFixed(2)}`
}

对应测试 src/utils/price.test.ts：

import { describe, it, expect } from 'vitest'
import { formatPrice } from './price'

describe('formatPrice', () => {
  it('把分转成带两位小数的元', () => {
    expect(formatPrice(12345)).toBe('¥123.45')
  })

  it('0 元正常输出', () => {
    expect(formatPrice(0)).toBe('¥0.00')
  })

  it('非法输入抛错', () => {
    expect(() => formatPrice(-1)).toThrow('非负整数')
    expect(() => formatPrice(1.5)).toThrow()
  })
})

跑测试：

npx vitest run

预期输出：

 ✓ src/utils/price.test.ts (3)
   ✓ formatPrice (3)
 Test Files  1 passed (1)
      Tests  3 passed (3)

vitest 默认进 watch 模式（改文件自动重跑），vitest run 是跑一次就退出——**CI 里一定要用 vitest run**，否则进程会挂在 watch 里不退出。

配置：test 块与 jsdom 环境

单元测试如果只测纯函数，Node 环境就够了。但只要测到 DOM（document、window），就得切到浏览器模拟环境，最常用的是 jsdom。

pnpm add -D jsdom

在 vite.config.ts 里加 test 块（Vitest 直接读这里）：

/// <reference types="vitest/config" />
import { defineConfig } from 'vite'

export default defineConfig({
  test: {
    globals: true,          // 允许不 import 直接用 describe/it/expect
    environment: 'jsdom',   // 需要 DOM 的测试用 jsdom；纯逻辑可用 'node'
    setupFiles: ['./vitest.setup.ts'], // 测试运行前加载公共初始化脚本（通常用来全局测试初始化）
    coverage: {
      provider: 'v8',       // 用 V8 原生覆盖率，快
      reporter: ['text', 'html', 'lcov'], // 终端输出、HTML 报告、CI/覆盖率平台读取
    },
  },
})

globals: true 之后可以省掉每个文件顶部的 import { describe, it }，但要在 tsconfig.json 里加类型才不报错：

{
  "compilerOptions": {
    "types": ["vitest/globals"]
  }
}

**纯逻辑库用 node 环境，涉及组件/DOM 才用 jsdom**。jsdom 有启动开销，纯函数没必要为它买单。Vitest 支持在文件顶部用注释单独指定环境：

// @vitest-environment jsdom

常见 API：先掌握这一组就够用

Vitest 的 API 很多，但日常写单元测试并不需要一上来全背。我的建议是先把它分成五类：组织用例、准备数据、断言结果、处理异步、控制外部依赖。

类别 常用 API 什么时候用
组织用例 describe、it、test 给测试分组，描述一个具体行为
生命周期 beforeAll、beforeEach、afterEach、afterAll 初始化测试数据、清理状态、还原 mock
断言 expect、toBe、toEqual、toThrow、toMatchObject 判断实际结果是否符合预期
Mock vi.fn、vi.spyOn、vi.mock、vi.mocked 替换函数、监听调用、隔离外部模块
时间与环境 vi.useFakeTimers、vi.setSystemTime、vi.stubGlobal、vi.stubEnv 控制时间、全局对象、环境变量

describe / it / test：把行为说清楚

it 和 test 本质上是一回事，选一个风格坚持用就行。我更习惯用 it，因为读起来像一句话：

import { describe, it, expect } from 'vitest'

describe('formatPrice', () => {
  it('把分转换成保留两位小数的金额字符串', () => {
    expect(formatPrice(12345)).toBe('¥123.45')
  })
})

用例名别写成「测试 formatPrice」。这等于没写。好的用例名应该说清楚输入、行为、预期结果，失败时一眼能看出是哪条业务规则坏了。

beforeEach / afterEach：保持测试干净

生命周期钩子最常见的用法是「每个用例前准备一份干净数据，每个用例后清理副作用」：

import { beforeEach, afterEach, expect, it, vi } from 'vitest'

let store: Map<string, string>

beforeEach(() => {
  store = new Map()
})

afterEach(() => {
  vi.restoreAllMocks()
})

it('写入后可以读取缓存', () => {
  store.set('token', 'abc')
  expect(store.get('token')).toBe('abc')
})

vi.clearAllMocks()、vi.resetAllMocks()、vi.restoreAllMocks() 很容易混：

API 清什么 适合场景
vi.clearAllMocks() 只清调用记录 同一个 mock 实现要复用，只想清 calledTimes
vi.resetAllMocks() 清调用记录，也重置 mock 实现 每个用例都要重新定义返回值
vi.restoreAllMocks() 还原 vi.spyOn 改过的原始实现 spy 过真实对象，测试后必须还原

简单记：只是清次数用 clear，想重配实现用 reset，改过真实对象用 restore。

expect：常用断言别选错

断言不是越复杂越好，关键是选对语义。

断言 用法 注意点
toBe 基本类型、同一个对象引用 使用 Object.is 比较
toEqual 对象、数组结构相等 不要求是同一个引用
toStrictEqual 更严格的深比较 会检查 undefined 字段、对象原型等
toContain 数组 / 字符串包含 适合简单包含判断
toMatchObject 对象局部匹配 只关心关键字段时很好用
toHaveProperty 检查对象路径 适合校验嵌套字段
toThrow 同步函数抛错 传函数引用，不要直接调用

举个对象断言的例子：

const user = {
  id: 1,
  name: 'Ann',
  role: 'admin',
  createdAt: '2026-07-10',
}

expect(user).toMatchObject({
  id: 1,
  role: 'admin',
})

这里没用 toEqual，因为测试真正关心的是 id 和 role，不是整份对象的所有字段。断言要贴近业务意图，不要把无关字段也绑死，否则测试会变脆。

test.each：同一套逻辑测多组输入

边界条件多的时候，不要复制粘贴一堆 it，用 test.each 更清楚：

import { expect, test } from 'vitest'

test.each([
  [0, '¥0.00'],
  [1, '¥0.01'],
  [12345, '¥123.45'],
])('formatPrice(%i) => %s', (input, expected) => {
  expect(formatPrice(input)).toBe(expected)
})

这里的 %i 和 %s 是测试标题里的占位符，分别表示整数和字符串。Vitest 会把每一组参数填进去，所以最终测试名类似 formatPrice(0) => ¥0.00、formatPrice(12345) => ¥123.45。这样测试失败时，能直接看出是哪一组输入挂了。

这套占位符基本沿用 printf 风格，常见的有：

占位符 含义
%s 字符串
%d / %i 数字 / 整数
%f 浮点数
%j JSON
%o 对象
%# 当前 case 的索引
%% 输出一个 %

实际项目里不用写得太花，常用 %s、%i、%# 就够了：

test.each([
  [0, '¥0.00'],
  [12345, '¥123.45'],
])('case %#：formatPrice(%i) => %s', (input, expected) => {
  expect(formatPrice(input)).toBe(expected)
})

适合参数化测试的场景：金额、日期、权限枚举、表单校验、状态机流转。反过来，如果每个 case 的业务语义差别很大，就别硬塞进 each，拆成独立用例更可读。

Mock：三个最常用的场景

真实项目里不可能全是纯函数。Mock 是单元测试绕不开的能力，vi 对象提供了完整的 mock 工具。

场景一：mock 一个函数

import { vi, it, expect } from 'vitest'

const onChange = vi.fn()
onChange('a')
expect(onChange).toHaveBeenCalledWith('a')  // 检查调用时传入的参数
expect(onChange).toHaveBeenCalledTimes(1)   // 检查函数被调用了几次

场景二：mock 整个模块

比如被测代码里依赖了一个真实发请求的模块，测试时不想真发：

import { vi, it, expect } from 'vitest'
import { getUser } from './user'

vi.mock('./api', () => ({
  fetchUser: vi.fn().mockResolvedValue({ id: 1, name: 'Ann' }),
}))

it('getUser 拼接出显示名', async () => {
  const u = await getUser(1)
  expect(u.displayName).toBe('Ann #1')
})

vi.mock 会被提升到文件顶部（和 Jest 一样），所以别在里面引用外部变量，否则会报「未初始化」。要用变量得配合 vi.hoisted。

场景三：mock 时间

测试里遇到 setTimeout、Date.now() 这种和时间相关的逻辑，用假定时器让它可控：

import { vi, it, expect, beforeEach, afterEach } from 'vitest'
import { debounce } from './debounce'

beforeEach(() => vi.useFakeTimers())  // 接管 setTimeout / setInterval 等定时器
afterEach(() => vi.useRealTimers())   // 测试结束后还原，避免影响其他用例

it('debounce 在 300ms 后只触发一次', () => {
  const fn = vi.fn()                  // 被防抖包装的原始回调
  const debounced = debounce(fn, 300)
  debounced(); debounced(); debounced() // 连续触发，前两次会被后一次覆盖
  expect(fn).not.toHaveBeenCalled()     // 时间没到之前不应该执行
  vi.advanceTimersByTime(300)           // 快进 300ms，不用真的等待
  expect(fn).toHaveBeenCalledTimes(1)   // 最终只执行最后一次
})

vi.advanceTimersByTime 是测试防抖/节流/轮询这类逻辑的关键——**别在测试里真的 await sleep(300)**，那会让测试又慢又不稳定。

再补两个常用能力。

场景四：spy 一个真实方法

vi.fn() 是造一个新函数，vi.spyOn() 是盯住一个已有对象的方法。比如测试里不想真的打日志：

import { afterEach, expect, it, vi } from 'vitest'

afterEach(() => {
  vi.restoreAllMocks() // 还原被 spyOn 替换过的真实方法
})

it('异常时输出错误日志', () => {
  // 监听 console.error，同时用空函数替换实现，避免测试输出里真的打印错误日志
  const spy = vi.spyOn(console, 'error').mockImplementation(() => {})

  reportError(new Error('network error'))

  // 验证 reportError 最终把包含错误信息的内容交给了 console.error
  expect(spy).toHaveBeenCalledWith(expect.stringContaining('network error'))
})

这里一定要在 afterEach 里 restoreAllMocks()，否则 console.error 会一直被替换，影响后面的测试。

场景五：mock 全局对象和环境变量

前端代码经常依赖 window.location、localStorage、import.meta.env 这类环境信息。不要在测试里假设真实运行环境，直接 stub 掉：

import { afterEach, expect, it, vi } from 'vitest'

afterEach(() => {
  vi.unstubAllGlobals() // 还原 vi.stubGlobal 改过的全局对象
  vi.unstubAllEnvs()    // 还原 vi.stubEnv 改过的环境变量
})

it('从环境变量读取 API 地址', () => {
  vi.stubEnv('VITE_API_BASE_URL', 'https://api.example.com') // 临时覆盖 import.meta.env

  expect(getApiBaseUrl()).toBe('https://api.example.com')
})

it('根据浏览器语言返回默认 locale', () => {
  // 临时替换 navigator，模拟浏览器语言环境
  vi.stubGlobal('navigator', {
    language: 'zh-CN',
  })

  expect(getDefaultLocale()).toBe('zh-CN')
})

只要测试改了全局环境，就必须在同一个文件里看到对应的清理逻辑。否则这种污染很隐蔽，排查成本很高。

异步测试：别让 Promise 偷偷失败

只要代码里有 Promise、fetch、定时器、事件回调，就要认真处理异步。异步测试最常见的问题不是「不会写」，而是忘了 await，导致断言还没执行完测试就结束了。

async / await：最直观的写法

import { expect, it } from 'vitest'

it('异步获取用户信息', async () => {
  const user = await getUser(1)

  expect(user).toMatchObject({
    id: 1,
    name: 'Ann',
  })
})

如果是预期 Promise 成功或失败，可以用 resolves / rejects：

import { expect, it } from 'vitest'

it('用户存在时返回详情', async () => {
  await expect(getUser(1)).resolves.toMatchObject({ id: 1 })
})

it('用户不存在时抛错', async () => {
  await expect(getUser(-1)).rejects.toThrow('用户不存在')
})

注意这里的 await 不能省。省了之后，测试框架可能还没等 Promise settle 就把用例判成通过。

expect.assertions：保证异步分支真的跑到

有些异步逻辑放在 try/catch 或事件回调里，建议加 expect.assertions：

import { expect, it } from 'vitest'

it('接口失败时进入 catch 分支', async () => {
  expect.assertions(1) // 要求本用例必须执行 1 次断言，防止 catch 没跑到却假通过

  try {
    await getUser(-1)
  } catch (error) {
    expect(error).toBeInstanceOf(Error)
  }
})

如果 getUser(-1) 没有抛错，这个用例会因为「没有执行到 1 个断言」而失败。它能防止异步异常被吞掉。

Snapshot：能不用就少用

Vitest 也支持快照：

expect(renderMenu(items)).toMatchInlineSnapshot(`
  "<ul><li>Home</li><li>Settings</li></ul>"
`)

快照适合稳定、结构化、人工阅读成本低的输出，比如 AST 转换结果、序列化后的配置、少量 HTML 字符串。不适合大段 UI 树。

快照失败时，如果你需要花很久才能判断是对是错，那这个快照就太大了。

测试该测什么：金字塔与「值不值得测」

写测试最容易走两个极端：一个都不写，或者给每个 getter/setter 都写。都不对。

经典的测试金字塔给了个大致比例：

        ╱╲          E2E（少）        贵、慢、脆，但最接近真实
       ╱  ╲
      ╱────╲        集成 / 组件（中） 覆盖模块协作
     ╱      ╲
    ╱────────╲      单元测试（多）    便宜、快、稳，覆盖逻辑分支

底层的单元测试应该最多，因为它便宜、快、定位精准。往上越贵越慢越脆。这一篇讲的单元测试就是塔基。

那具体哪些代码值得写单元测试？判断标准是「逻辑复杂度」和「出错代价」：

值得重点测 不太值得测
纯函数：计算、格式化、校验、转换 简单的透传、getter
有分支/边界的逻辑（金额、日期、权限） 一眼能看穿对错的三行代码
容易回归的核心业务规则 频繁改动的实验性 UI
修过的 bug（补一个回归用例） 第三方库本身的行为

一个很实用的习惯：每修一个 bug，就补一个能复现它的测试用例。这样同一个 bug 不会回来第二次，测试集也在真实地增长，而不是为了覆盖率硬凑。

测试关注点：别只测 happy path

很多测试没价值，不是因为工具不行，而是因为只测了「正常输入正常输出」。真实线上问题往往出在边界、异常和副作用上。

写单元测试时可以按下面这张表扫一遍：

关注点 要问的问题 例子
正常路径 最典型的输入能不能得到正确结果 formatPrice(12345) 输出 ¥123.45
边界值 0、空数组、最大值、最小值怎么处理 金额为 0、分页 pageSize = 1
异常输入 非法类型、缺字段、越权参数是否被挡住 负数金额、空 token、未知枚举
分支逻辑 每个 if/else 是否都被走到 管理员 / 普通用户 / 游客权限
异步结果 成功、失败、超时是否都可控 请求成功、接口 500、Promise reject
副作用 有没有调用外部依赖，调用参数对不对 埋点、日志、缓存、事件回调
状态变化 调用前后状态是否符合预期 store 更新、重试次数递增
回归场景 修过的 bug 有没有固定下来 日期跨月、浮点数精度、时区问题

如果只能挑三类优先测，我会选：边界值、异常输入、回归场景。正常路径通常开发时就会手动跑到，真正容易漏的是「刚好卡在边上」和「之前已经踩过坑」的地方。

用 Arrange / Act / Assert 写清楚结构

单元测试最好保持三段式：

import { expect, it, vi } from 'vitest'

it('提交成功后调用 onSuccess 回调', async () => {
  // Arrange：准备输入和依赖
  const onSuccess = vi.fn()
  const form = createForm({ name: 'Ann' })

  // Act：执行被测行为
  await form.submit({ onSuccess })

  // Assert：验证结果
  expect(onSuccess).toHaveBeenCalledWith({ name: 'Ann' })
})

这个结构看起来朴素，但很有用。测试失败时，你能快速定位是数据准备错了、行为执行错了，还是断言写错了。

一个用例只验证一个核心行为

反面写法是一个测试里塞很多断言：

// ❌ 反面案例：一个用例测了创建、更新、删除三件事
it('用户管理流程正常', async () => {
  const user = await createUser({ name: 'Ann' })
  expect(user.id).toBeDefined()

  const updated = await updateUser(user.id, { name: 'Bob' })
  expect(updated.name).toBe('Bob')

  await deleteUser(user.id)
  await expect(getUser(user.id)).rejects.toThrow()
})

这种测试一旦失败，你只知道「用户管理流程坏了」，但不知道是哪条规则坏了。更好的写法是拆开：

// ✅ 正面案例：每个用例对应一个明确行为
it('创建用户后返回用户 id', async () => {
  const user = await createUser({ name: 'Ann' })

  expect(user.id).toBeDefined()
})

it('更新用户名称', async () => {
  const user = await createUser({ name: 'Ann' })

  const updated = await updateUser(user.id, { name: 'Bob' })

  expect(updated.name).toBe('Bob')
})

单元测试不是端到端流程回放。它要围绕一个清晰的行为点展开。

不要测试实现细节

测试应该关心「对外行为」，少关心「内部怎么实现」。比如一个函数内部到底调用了几个私有 helper，通常不值得测。否则你一重构实现，业务没变，测试先红一片。

// ❌ 反面案例：绑死内部实现
expect(normalizeName).toHaveBeenCalledTimes(1)

// ✅ 正面案例：验证对外结果
expect(createDisplayName({ firstName: 'Ann', lastName: 'Lee' })).toBe('Ann Lee')

当然也有例外：如果被测对象的职责就是「调用某个副作用」，比如埋点、日志、通知回调，那验证调用参数就是合理的。关键看它是不是这个模块的对外契约。

覆盖率：看趋势，别迷信数字

Vitest 内置覆盖率，跑一下：

npx vitest run --coverage

输出会给出四个指标：

% Stmts | % Branch | % Funcs | % Lines
  • Statements：语句覆盖
  • Branch：分支覆盖（if/else、三元、&& 都算）
  • Functions：函数覆盖
  • Lines：行覆盖

其中 Branch（分支覆盖）最有价值——它逼你想清楚每个 if 的两条路都测了没。行覆盖 100% 但分支只有 60% 是常见现象，说明有很多没走到的边界。

关于覆盖率阈值：它是个健康度信号，不是 KPI。可以在配置里设一个不太高的门槛，防止覆盖率断崖式下跌：

test: {
  coverage: {
    provider: 'v8',
    thresholds: {
      lines: 70,
      branches: 65,
    },
  },
}

设 70% 这种「够用」的线就行，别追求 100%。为了那最后 10% 去测一堆没意义的分支，是典型的用力过猛——测试的目的是保护业务，不是刷分。真正该盯的是趋势：覆盖率是在涨还是在跌，核心模块有没有被测到。这个指标后面讲「工程治理指标」时还会串起来。

一个真实的坑：测试之间互相污染

现象：单个文件跑绿的测试，全量跑时随机挂几个。

原因：测试之间共享了状态没清理——比如上一个测试往一个全局单例、localStorage、或某个模块级变量里写了东西，下一个测试读到了脏数据。

解决：每个测试要能独立运行，跑完自己收拾干净。用 beforeEach / afterEach 重置状态，mock 也要清：

import { afterEach, vi } from 'vitest'

afterEach(() => {
  vi.clearAllMocks()   // 清掉 mock 的调用记录
  localStorage.clear()
})

还可以在配置里开 test.isolate（默认开启），让每个测试文件在独立环境跑。但同一个文件内的用例污染还是得靠 beforeEach 自己管。判断测试写得好不好，有个简单标准：能不能用 .only 单独跑任意一个用例都通过。做不到，就说明用例之间有隐藏依赖。

小结

  1. 项目用了 Vite 就直接上 Vitest，它复用 Vite 的转换和别名配置，比 Jest 省一整套配置。
  2. CI 里必须用 vitest run，默认的 vitest 是 watch 模式不会退出。
  3. 纯逻辑用 node 环境，涉及 DOM 才用 jsdom，别为不需要的环境买单。
  4. 先掌握 describe/it、生命周期、expect、test.each、vi.fn、vi.spyOn、vi.mock 这一组高频 API。
  5. Mock 常见场景包括函数、模块、时间、真实方法、全局对象和环境变量；改了外部环境就要清理。
  6. 异步测试要 await，用 resolves/rejects 表达 Promise 结果，用 expect.assertions 防止异步分支没跑到。
  7. 按测试金字塔组织，单元测试占大头；按「逻辑复杂度 + 出错代价」决定哪些值得测。
  8. 测试关注点不要只盯 happy path，边界值、异常输入、分支逻辑、副作用和回归场景更容易发现问题。
  9. 每修一个 bug 补一个回归用例，让测试集真实增长。
  10. 覆盖率看趋势和分支覆盖，设一条「够用」的阈值防倒退，别把 100% 当 KPI。
  11. 测试要能独立运行，用 beforeEach/afterEach 清状态和 mock，避免用例互相污染。
