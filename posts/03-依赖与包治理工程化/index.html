依赖与包治理工程化

发表于2026|更新于2026|工程化
|字数总计:1.9k|阅读时长:6分钟

前言：依赖治理是很多团队容易忽略的一环。项目能安装成功，不代表依赖关系健康；没有安全告警，不代表没有供应链风险。工程化阶段二要开始把依赖也纳入质量体系。

依赖治理到底治理什么

前端项目的依赖数量通常很多。

一个普通业务项目，直接依赖可能几十个，间接依赖可能上千个。

依赖治理至少要关注六件事：

维度 问题
安全 是否存在已知漏洞
license 是否引入不合规开源协议
版本 多个包是否使用了不一致版本
安装 lockfile 是否稳定、可复现
结构 是否存在幻影依赖
升级 依赖升级是否可控

我的理解是：依赖治理不是追求永远最新，而是让依赖变化可见、可控、可回滚。

使用 pnpm audit 检查安全风险

pnpm audit 可以检查依赖中是否存在已知安全漏洞。

pnpm audit

如果存在问题，会输出漏洞等级、影响包和修复建议。

CI 里可以加：

pnpm audit --audit-level high

这表示只在 high 及以上风险时失败。

为什么不建议一开始就对所有等级都失败？

因为实际项目里低危漏洞可能来自间接依赖，而且不一定有可用修复版本。如果把所有低危都设成阻塞，团队很快会开始忽略 audit。

我的建议是：

等级 策略
critical 必须立即处理
high 默认阻塞合并
moderate 评估影响范围
low 记录并跟进，不一定阻塞

工具只负责发现风险，是否阻塞要结合业务暴露面判断。

license 检查不能忽略

安全漏洞是技术风险，license 是合规风险。

常见开源协议大致可以分成：

类型 例子 一般风险
宽松协议 MIT、Apache-2.0、BSD 低
弱 Copyleft MPL-2.0、LGPL 中
强 Copyleft GPL、AGPL 高
未声明 UNKNOWN、UNLICENSED 需要确认

前端业务项目通常会把 GPL、AGPL 这类协议列为高风险。

可以使用 license 检查工具，比如 license-checker-rseidelsohn 或其他团队认可的工具。

示例脚本：

{
  "scripts": {
    "license:check": "license-checker-rseidelsohn --summary"
  }
}

如果是公司项目，最终标准应该以公司法务或开源合规要求为准。技术团队不要自己拍脑袋决定所有 license 风险。

幻影依赖是什么

幻影依赖指的是：代码里使用了某个包，但 package.json 没有声明它。

例如：

import { debounce } from 'lodash'

但 package.json 里没有：

{
  "dependencies": {
    "lodash": "^4.17.21"
  }
}

为什么本地还能跑？

因为某个间接依赖也依赖了 lodash，并且它刚好被提升到了根 node_modules。

这就是幻影依赖的危险之处：它依赖的是安装结构的偶然结果。

一旦依赖树变化，项目可能突然报错：

Cannot find module 'lodash'

pnpm 为什么能减少幻影依赖

pnpm 的 node_modules 结构更严格。

它会把真实包存放在全局内容寻址 store 中，再通过硬链接和符号链接组织项目依赖。

简单理解：

node_modules/
├── .pnpm/
│   ├── react@18.3.1/
│   └── lodash@4.17.21/
└── react -> .pnpm/react@18.3.1/node_modules/react

项目只能直接访问自己声明过的依赖。

这会让一些以前“能跑”的幻影依赖暴露出来。

短期看像是 pnpm 更严格，长期看是好事。因为它逼你把依赖关系写清楚。

我的建议是：如果迁移 pnpm 后发现缺包，不要急着改 pnpm 配置放宽限制，先检查是不是项目本来就漏写了依赖。

lockfile 冲突怎么处理

团队协作里 pnpm-lock.yaml 冲突很常见。

处理原则：

  1. 不要手动凭感觉编辑大段 lockfile；
  2. 先解决 package.json 冲突；
  3. 再重新执行 pnpm install 生成 lockfile；
  4. 检查 lockfile diff 是否符合预期。

推荐流程：

git pull
pnpm install
pnpm test

如果冲突复杂，可以：

pnpm install --lockfile-only

这会只更新 lockfile，不重新安装全部依赖。

但要注意，最终仍然要跑一次完整检查，保证生成结果可用。

monorepo 内部依赖的版本治理

monorepo 场景下有两个和依赖治理强相关的实践，这里只讲治理价值，完整搭建可以看《Monorepo 工程化实践》那篇。

第一，内部包之间用 workspace:* 引用：

{
  "dependencies": {
    "@example/shared": "workspace:*"
  }
}

它表达的是”这个依赖必须来自当前 workspace，而不是 npm registry”，能避免一个很隐蔽的问题：你以为引用的是本地包，实际装了 registry 上的旧版本。发布到 npm 时，pnpm 会自动把它替换成合适的真实版本范围。不要手写版本号假装同步。

第二，公共依赖的版本用 pnpm catalog 集中声明，避免多个包版本漂移：

# pnpm-workspace.yaml
catalog:
  react: ^18.3.1
  typescript: ^5.5.0

子包里用 "react": "catalog:" 引用。升级时只改 pnpm-workspace.yaml 一处，既保证版本一致，也减少 package.json 的合并冲突。如果 React、TypeScript、ESLint 这类基础依赖在多个包里反复出现，catalog 很有价值。

peerDependencies 和 optionalDependencies

依赖类型也要理解清楚。

字段 含义 典型场景
dependencies 运行时必须依赖 应用直接使用的库
devDependencies 开发期依赖 构建、测试、lint 工具
peerDependencies 要求使用方提供 插件、组件库适配 React/Vue
optionalDependencies 可选依赖，安装失败不阻塞 平台相关能力、可选增强

组件库常见写法：

{
  "peerDependencies": {
    "react": ">=18",
    "react-dom": ">=18"
  }
}

原因是组件库不应该自己带一份 React，否则业务项目可能出现多个 React 实例。

optionalDependencies 要谨慎使用。它适合某些平台能力可用就增强、不可用也能降级的场景。

不要把真正必须的依赖放进 optionalDependencies，否则问题会被延迟到运行时才暴露。

Renovate 和 Dependabot 怎么用

依赖不升级会积累风险，盲目升级也会制造风险。

Renovate 和 Dependabot 的价值是自动发现依赖更新，并提交 PR。

但我不建议所有依赖都自动合并。

更稳的策略：

依赖类型 策略
patch CI 通过后可考虑自动合并
minor 自动提 PR，人工 Review
major 单独评估迁移成本
安全修复 提高优先级
核心构建链路 不自动合并

Renovate 配置思路：

{
  "extends": ["config:recommended"],
  "packageRules": [
    {
      "matchUpdateTypes": ["patch"],
      "automerge": true
    },
    {
      "matchPackageNames": ["eslint", "typescript", "vite"],
      "automerge": false
    }
  ]
}

这里的重点不是配置本身，而是升级策略：

  • 小版本可以高频升级；
  • 大版本集中处理；
  • 工具链核心包要人工确认；
  • 每个升级 PR 必须跑完整 CI。

小结

  1. 依赖治理关注安全、license、版本一致性、lockfile、幻影依赖和升级流程。
  2. pnpm audit 可以发现已知漏洞，但阻塞策略要按风险等级设计。
  3. 幻影依赖是没有声明却能使用的依赖，pnpm 的严格结构能更早暴露它。
  4. monorepo 内部依赖建议使用 workspace:*，共享版本建议使用 pnpm catalog。
  5. Renovate 和 Dependabot 应该配合 CI 和人工评审，不要把所有升级都自动合并。
