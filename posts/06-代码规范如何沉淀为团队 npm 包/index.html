代码规范如何沉淀为团队 npm 包

发表于2026|更新于2026|工程化
|字数总计:1.5k|阅读时长:6分钟

前言：当一个团队有多个项目时，最怕的是每个项目都复制一份 ESLint、Prettier、Stylelint 配置。短期看省事，长期看一定会出现规则漂移。更稳的方式，是把团队规范沉淀成 npm 包。

为什么要做团队规范包

如果团队只有一个项目，把配置写在项目里没问题。

但当你有多个项目时，很快会遇到这些问题：

  • A 项目 ESLint 规则更新了，B 项目忘了同步；
  • 新项目初始化时到处复制配置；
  • Prettier 配置看起来一样，但某个字段不同；
  • Stylelint 插件版本不一致；
  • 升级 ESLint v9 时，每个项目都要手动改；
  • Code Review 里反复讨论同样的规范问题。

这时候就应该考虑把配置做成团队 npm 包。

我的判断标准是：

同一套规范被复制到第三个项目时，就该考虑抽成包。

不是为了“显得工程化”，而是为了减少重复维护。

可以沉淀哪些内容

团队规范包不一定只有一个，可以按职责拆。

常见拆法：

包名 内容
@team/eslint-config ESLint Flat Config
@team/prettier-config Prettier 配置
@team/stylelint-config Stylelint 配置
@team/tsconfig 通用 tsconfig
@team/commitlint-config Commitlint 规则

也可以做一个总包：

@team/code-style
├── eslint
├── prettier
├── stylelint
├── tsconfig
└── commitlint

我更推荐前期先拆开，原因是升级更灵活。

比如某个老项目暂时不能升级 ESLint，但可以先升级 Prettier。拆包后影响范围更可控。

先做一个 ESLint Config 包

目录结构可以这样：

packages/eslint-config/
├── package.json
├── index.js
├── react.js
└── ts.js

package.json：

{
  "name": "@team/eslint-config",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./index.js",
    "./ts": "./ts.js",
    "./react": "./react.js"
  },
  "peerDependencies": {
    "eslint": ">=9",
    "typescript": ">=5"
  },
  "dependencies": {
    "@eslint/js": "^9.0.0",
    "typescript-eslint": "^8.0.0"
  }
}

这里有个关键点：eslint 放在 peerDependencies 更合理。

因为真正运行 ESLint 的是业务项目，规范包只是提供配置。让业务项目显式安装 ESLint，可以避免多个版本混在一起。

index.js：

import js from '@eslint/js'

export default [
  {
    ignores: ['dist/**', 'coverage/**', 'node_modules/**'],
  },
  js.configs.recommended,
]

ts.js：

import base from './index.js'
import tseslint from 'typescript-eslint'

export default [
  ...base,
  ...tseslint.configs.recommended,
  {
    files: ['**/*.{ts,tsx}'],
    rules: {
      'no-unused-vars': 'off',
      '@typescript-eslint/no-unused-vars': [
        'error',
        {
          argsIgnorePattern: '^_',
          varsIgnorePattern: '^_',
        },
      ],
    },
  },
]

业务项目使用：

import teamTsConfig from '@team/eslint-config/ts'

export default [
  ...teamTsConfig,
  {
    rules: {
      // 项目特殊规则写在这里
    },
  },
]

这样团队默认规则和项目特殊规则就分开了。

Prettier 配置包

Prettier 配置包更简单。

@team/prettier-config/package.json：

{
  "name": "@team/prettier-config",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./index.js"
  },
  "peerDependencies": {
    "prettier": ">=3"
  }
}

index.js：

export default {
  singleQuote: true,
  semi: false,
  trailingComma: 'all',
  printWidth: 100,
}

业务项目 prettier.config.mjs：

export { default } from '@team/prettier-config'

不要每个项目都复制 .prettierrc.json。一旦规则变化，复制粘贴会变成维护灾难。

Stylelint 配置包

@team/stylelint-config/package.json：

{
  "name": "@team/stylelint-config",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./index.js",
    "./scss": "./scss.js"
  },
  "peerDependencies": {
    "stylelint": ">=16"
  },
  "dependencies": {
    "stylelint-config-standard": "^36.0.0",
    "stylelint-config-standard-scss": "^13.0.0"
  }
}

index.js：

export default {
  extends: ['stylelint-config-standard'],
  rules: {
    'selector-max-id': 0,
    'max-nesting-depth': 3,
  },
}

业务项目：

export { default } from '@team/stylelint-config'

如果某个项目有特殊样式体系，也可以覆盖：

import base from '@team/stylelint-config'

export default {
  ...base,
  rules: {
    ...base.rules,
    'selector-class-pattern': null,
  },
}

tsconfig 也适合沉淀

很多项目的 tsconfig.json 也会高度重复。

可以做一个 @team/tsconfig：

packages/tsconfig/
├── package.json
├── base.json
├── react.json
└── node.json

base.json：

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  }
}

业务项目：

{
  "extends": "@team/tsconfig/base.json",
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  },
  "include": ["src"]
}

这里要注意：共享 tsconfig 里不要写项目路径，比如 include、paths。这些通常应该留在业务项目里。

peerDependencies 怎么取舍

规范包里最容易纠结的是依赖放哪里。

我的经验是：

依赖类型 放哪里 例子
运行主体 peerDependencies eslint、prettier、stylelint
配置内部直接 import 的包 dependencies @eslint/js、typescript-eslint
开发测试依赖 devDependencies 测试工具、构建工具

这样设计的好处是：业务项目明确控制核心工具版本，规范包提供规则组合。

如果所有东西都塞进 dependencies，短期省事，长期可能出现一个项目里多个 ESLint 版本共存的问题。

版本发布策略

团队规范包也要遵守 semver。

我通常这样判断：

变更 版本
修复配置错误 patch
新增不破坏现有项目的规则 minor
开启更严格规则导致项目可能报错 major
升级 ESLint 大版本 major

很多团队会忽略这一点，把“开启新规则”当成 patch 发出去。

结果业务项目一升级，突然多出几十个 lint error。

我的建议是：只要可能让下游项目从通过变成不通过，就按 breaking change 处理。

小结

  1. 同一套规范复制到第三个项目时，就应该考虑沉淀为 npm 包。
  2. ESLint、Prettier、Stylelint、tsconfig、Commitlint 都可以做成团队共享配置。
  3. 核心工具通常放在 peerDependencies，配置内部依赖放在 dependencies。
  4. 共享配置不要写死业务项目路径，项目差异要留出覆盖空间。
  5. 规范包也要遵守 semver，新增严格规则通常应该视为破坏性变更。
