CI 基础：GitHub Actions 与 GitLab CI 的核心模型

发表于2026|更新于2026|工程化
|字数总计:1.9k|阅读时长:6分钟

前言：前面在讲代码规范时写过一篇《CI 流水线与质量强约束闸口》，那篇的重点是「CI + 分支保护如何让规范无法被绕过」，站在质量约束的角度。这一篇换个角度，系统讲 CI 工具本身的核心模型——不管是 GitHub Actions 还是 GitLab CI，理解它们共通的那套抽象（触发、任务、步骤、并发、依赖），你换任何平台都能快速上手。这也是第六阶段「持续交付」的地基。

所有 CI 都是同一套抽象

市面上 CI 工具一大堆：GitHub Actions、GitLab CI、Jenkins、CircleCI、工蜂流水线……名字和语法各不相同，但核心模型是同一套。理解这套抽象，看任何平台的文档都是「换个词而已」。

触发事件（Trigger）          什么时候跑：push / PR / 定时 / 手动
   │
   ▼
工作流 / 流水线（Workflow / Pipeline）   一次完整的运行
   │
   ├── 阶段（Stage）        按流程把任务分层：检查 / 测试 / 构建 / 部署
   │
   ├── 任务（Job）           在一台干净的机器上跑
   │    │
   │    └── 步骤（Step）      Job 里的一条条命令
   │
   └── 任务之间：并发 or 依赖（needs）

这里的「阶段」不是某个平台的专有语法，而是一个通用的组织方式：先把一次流水线拆成几段大的流程，再把具体任务放进对应流程里。比如「测试阶段」下面可以同时跑单元测试、组件测试、E2E 测试；这些任务都通过之后，才进入构建或部署。

把这五个概念对上，剩下的都是语法细节：

概念 GitHub Actions GitLab CI
配置文件 .github/workflows/*.yml .gitlab-ci.yml
触发 on: rules: / only / workflow
任务 jobs.<id> 顶层每个 key
步骤 steps: script:
运行环境 runs-on: image: / runner tags
依赖顺序 needs: stages + needs
复用 Actions（uses:） include / templates

下面两边各给一份等价的最小配置，你会发现「长得不一样，说的是一回事」。

GitHub Actions 的模型

GitHub Actions 的运行单元是 workflow，放在 .github/workflows/ 下。核心是 on（触发）+ jobs（任务）。

# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest        # 每个 job 跑在一台全新的虚拟机上
    steps:
      - uses: actions/checkout@v4  # step 可以“用”一个现成的 action
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm
      - run: pnpm install --frozen-lockfile   # 也可以直接跑命令
      - run: pnpm test

GitHub Actions 最大的特色是 Actions 生态——uses: 能直接引用别人写好的可复用单元（actions/checkout、setup-node、pnpm/action-setup），像装 npm 包一样组合流水线。这是它比传统 CI 好用的地方：常见操作不用自己写脚本。

几个必须知道的点：

  • 每个 job 是一台全新的机器，job 之间默认不共享文件系统。要传文件得用 actions/upload-artifact / download-artifact。
  • runs-on 决定操作系统：ubuntu-latest / windows-latest / macos-latest。
  • 第三方 action 要锁版本：@v4 是浮动的，安全敏感的场景建议锁到 commit SHA，防止上游被投毒（这点在安全篇会再提）。

GitLab CI 的模型

GitLab CI 的配置是仓库根目录的 .gitlab-ci.yml。它的组织核心是 stages（阶段）——同一 stage 的 job 并发跑，前一个 stage 全过了才进下一个。

# .gitlab-ci.yml
stages:
  - test
  - build

default:
  image: node:20             # 所有 job 默认用这个 Docker 镜像

test:
  stage: test
  script:
    - corepack enable
    - pnpm install --frozen-lockfile
    - pnpm test

build:
  stage: build               # test 阶段全过了才会进 build
  script:
    - pnpm install --frozen-lockfile
    - pnpm build
  artifacts:
    paths:
      - dist/                 # 把产物传给后续 stage / 下载
    expire_in: 1 week

和 GitHub Actions 的关键差异：

  • GitLab 用 Docker 镜像作为运行环境（image: node:20），GitHub 用预装软件的虚拟机。GitLab 这种更「干净可控」，你指定什么镜像就是什么环境。
  • stages 是 GitLab 的一等公民，天然表达「先测后建」。GitHub Actions 里同样的顺序要用 needs 表达（下面讲）。
  • artifacts 在 GitLab 里是内建的产物传递机制，比 GitHub 的 upload/download action 更顺手。

三个必须理解的机制

不管哪个平台，有三个机制决定了流水线的行为，值得单独说清。

1. Job 之间：并发还是串行

默认同一层级的 job 是并发的（有空闲 runner 就一起跑）。要表达「B 依赖 A 的产物，A 先跑」，用依赖声明：

# GitHub Actions
jobs:
  lint:
    runs-on: ubuntu-latest
    steps: [...]
  build:
    needs: lint          # lint 成功后才跑 build
    runs-on: ubuntu-latest
    steps: [...]

needs 是流水线分层的基础——后面 CI 进阶篇会用它搭「fast feedback → test → build → deploy」的分层结构。

2. 缓存 vs 产物（Artifact）：别搞混

这是新手最常混淆的两个概念，定位完全不同：

缓存（Cache） 产物（Artifact）
目的 加速（复用依赖、构建中间物） 传递 / 归档结果（dist、报告）
生命周期 尽力而为，可能失效 明确保留，可下载
典型内容 node_modules、pnpm store dist/、测试报告、覆盖率
丢了会怎样 变慢，但结果不变 拿不到构建结果

一句话：缓存丢了顶多慢一点，产物是必须可靠拿到的东西。别用缓存去传产物，也别把产物当缓存。

3. Secrets：密钥不能写进代码

发布要用的 NPM_TOKEN、部署要用的云厂商密钥，绝不能硬编码进 yml。存在平台的加密变量里，运行时注入：

# GitHub Actions：在仓库 Settings → Secrets 里配好
- run: npm publish
  env:
    NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

# GitLab：Settings → CI/CD → Variables，标记为 Masked / Protected
- npm publish   # $NPM_TOKEN 作为环境变量注入

一个真实的坑：来自 fork 的 PR 默认拿不到 secrets（GitHub 的安全设计，防止外部贡献者偷密钥）。所以「跑测试」的流水线对 fork PR 能跑，但「发布/部署」这类需要密钥的操作对 fork PR 会失败或拿到空值。设计流水线时要把「需要密钥的步骤」和「纯检查的步骤」分开——这也和后面「流水线分层」呼应。

本地怎么快速验证流水线

CI 最烦的一点是改一行 yml 要 push 上去才能看效果，反馈慢。两个减少往返的办法：

  • GitLab：官方提供 CI Lint（项目里的 CI/CD → Editor / Lint），能校验 .gitlab-ci.yml 语法。
  • GitHub Actions：可以用社区工具 act 在本地用 Docker 跑 workflow，能覆盖大部分场景（但和真实环境有差异，复杂的还是得实测）。

可以先把每一步的命令在本地终端跑通，确认 pnpm lint、pnpm test、pnpm build 都没问题，再往 yml 里搬。CI 只是「在干净环境里替你重跑一遍本地命令」——如果本地都跑不过，CI 一定跑不过。别把 CI 当调试环境，那样往返成本极高。

小结

  1. 所有 CI 工具共享同一套抽象：触发 → 工作流/流水线 → 任务 → 步骤，以及任务间的并发/依赖。
  2. GitHub Actions 的特色是 Actions 生态（uses: 复用现成单元）；GitLab CI 的特色是 Docker 镜像环境 + 一等公民的 stages。
  3. 每个 job 跑在全新环境，job 间不共享文件系统，传文件靠 artifact。
  4. 缓存是为了加速（丢了只是变慢），产物是为了可靠传递/归档结果，两者别混。
  5. 密钥走平台的加密 secrets 注入，绝不硬编码；fork PR 默认拿不到 secrets，检查和发布步骤要分开。
  6. 先在本地把每步命令跑通再搬进 yml，CI 只是干净环境里重跑本地命令，别拿它当调试台。
