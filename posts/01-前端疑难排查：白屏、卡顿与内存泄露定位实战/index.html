前端疑难排查：白屏、卡顿与内存泄露定位实战

发表于2025|更新于2026|面试
|字数总计:3.1k|阅读时长:10分钟

前言：面试里最能拉开差距的往往不是”你知道多少 API”，而是”线上出问题了你怎么定位”。白屏、卡顿、内存泄露是三类最典型、也最容易被问到的疑难问题。这篇我把自己排查这三类问题的思路、工具和踩过的坑整理成一套可复用的方法论。核心只有一句话：先分类、再定位、最后才动手改，别一上来就猜。

排查问题最忌讳的是拍脑袋。我见过太多人一遇到白屏就开始”是不是接口挂了”、”是不是打包出错了”地乱猜，猜对了是运气，猜错了浪费半天。真正靠谱的做法是把可能性分层拆开，一层层排除，把范围缩到最小再动手。下面三个问题都按这个套路来讲。

白屏排查

白屏是最唬人的问题——用户看到的就是一片空白，但背后的原因可能天差地别。第一步不是打开代码，而是先判断白屏发生在哪个阶段。

先分清是哪种白屏

我习惯把白屏分成四类，每一类的排查方向完全不同：

白屏类型 典型现象 大概率原因
资源加载失败 Network 里有红色 404/CORS JS/CSS 路径错、CDN 挂了、跨域
JS 执行报错 Console 有红色报错，DOM 没挂载 代码异常、依赖缺失、环境不兼容
接口异常导致 骨架在、内容区空 接口 500/超时、数据格式变了
渲染逻辑问题 无报错但内容不显示 路由匹配失败、条件渲染判断错、样式 display:none

判断顺序很简单：打开 DevTools，先看 Console 有没有红，再看 Network 有没有失败请求，最后看 Elements 里 DOM 到底挂上没有。这三步能把 80% 的白屏归到某一类里。

一段最小的白屏兜底监控

线上白屏最麻烦的是你复现不了。所以监控要能自动上报”我白屏了”。最朴素但有效的思路：在页面加载完成后的某个时间点，检测根节点里有没有真实内容。

// 白屏检测：加载后延迟检查根节点是否有有效渲染内容
function detectBlankScreen(rootSelector = '#app', delay = 3000) {
  setTimeout(() => {
    const root = document.querySelector(rootSelector);
    if (!root) {
      report('blank_screen', { reason: 'root_not_found' });
      return;
    }

    // 用采样点判断中心区域是否为空（比只看 innerHTML 更接近"用户视觉上的白屏"）
    const isEmpty = root.innerText.trim() === '' && root.children.length === 0;

    if (isEmpty) {
      report('blank_screen', {
        reason: 'empty_root',
        url: location.href,
        ua: navigator.userAgent,
      });
    }
  }, delay);
}

function report(type, payload) {
  navigator.sendBeacon('/api/monitor', JSON.stringify({ type, ...payload }));
}

detectBlankScreen();

比 innerHTML 判断更严谨的做法是采样点检测：在屏幕上取几个关键坐标（比如页面中心和四个象限），用 document.elementFromPoint(x, y) 看命中的元素是不是都是根容器 / body。如果一堆采样点都命中根容器，说明上面啥都没渲染，判定为白屏。

// 采样点白屏检测：更贴近"人眼看到的空白"
function isBlankBySampling() {
  const points = [
    [innerWidth / 2, innerHeight / 2],
    [innerWidth / 4, innerHeight / 4],
    [(innerWidth * 3) / 4, (innerHeight * 3) / 4],
  ];

  let emptyCount = 0;
  const emptyTags = ['HTML', 'BODY', 'DIV#APP'];

  for (const [x, y] of points) {
    const el = document.elementFromPoint(x, y);
    const tag = el ? el.tagName + (el.id ? `#${el.id.toUpperCase()}` : '') : '';
    if (!el || emptyTags.includes(tag)) emptyCount++;
  }

  return emptyCount === points.length;
}

关于白屏检测的完整方案（MutationObserver 兜底、onerror 联动、Source Map 还原），我在工程化系列的《错误监控》里展开过，这里聚焦”人肉排查”的思路。

我的踩坑经验

坑 1：移动端白屏 90% 是环境不兼容。同一份代码 PC 好好的，某个安卓机型就白屏，大概率是用了目标浏览器不支持的语法（比如可选链没转译、某个新 API），或者 polyfill 没打进去。定位手段：用 vConsole / eruda 在真机上看 Console 报错，比在 Chrome 里瞎猜快十倍。

坑 2：路由白屏别只怪代码。history 模式下刷新出现白屏，多半是 nginx 没配 try_files 回退到 index.html，请求直接 404 了，跟前端一毛钱关系没有。

坑 3：首屏白屏时间长 ≠ 白屏 bug。有时候不是”渲染不出来”，而是”渲染得太慢”。这属于性能问题，要用下面卡顿排查的思路去看，别混为一谈。

页面卡顿定位

卡顿的本质是主线程被长时间占用，来不及响应用户操作和渲染下一帧。浏览器一帧的预算大约是 16.6ms（60fps），一旦某个任务超过 50ms 就会被算作”长任务”（Long Task），用户就能感知到卡。

卡顿的三个来源

定位卡顿前，先想清楚卡在哪一层：

用户操作 ──▶ JS 执行 ──▶ 样式计算 ──▶ 布局 ──▶ 绘制 ──▶ 合成
             │            │           │        │
          脚本卡      强制同步布局    重排      重绘
        (长任务)     (Layout Thrash)
  • JS 执行卡：一次性算了太多东西（大数组遍历、复杂计算、频繁 setState）
  • 渲染卡：频繁触发重排重绘，或者一次改了太多 DOM
  • 强制同步布局（Layout Thrashing）：读写 DOM 交替进行，导致浏览器被迫反复重新计算布局

用 Performance 面板定位长任务

嘴上说没用，直接录制。打开 DevTools 的 Performance 面板，点录制，复现卡顿操作，停止。重点看两处：

  1. Main 轨道里的红色三角：那些标了红角的就是长任务，点进去看调用栈，一眼就知道是哪个函数占的时间
  2. 底部的 Bottom-Up / Call Tree：按耗时排序，找出自身耗时（Self Time）最高的函数

代码里也可以主动监听长任务，把线上真实的卡顿点捞回来：

// 监听长任务：超过 50ms 的任务会被上报
if ('PerformanceObserver' in window) {
  const observer = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
      // entry.duration 是任务耗时，attribution 里能拿到归因信息
      report('long_task', {
        duration: Math.round(entry.duration),
        startTime: Math.round(entry.startTime),
      });
    }
  });

  observer.observe({ entryTypes: ['longtask'] });
}

强制同步布局：最隐蔽的卡顿元凶

这是面试高频考点，也是实战里最容易踩的坑。浏览器为了性能会把 DOM 修改批量、异步处理。但如果你在修改后立刻读取布局属性（offsetTop、offsetWidth、getComputedStyle 等），浏览器为了给你返回准确值，被迫立刻同步执行一次布局计算。放在循环里就是灾难。

// ❌ 反面案例：读写交替，每次循环强制一次同步布局
function badLayout(elements) {
  for (const el of elements) {
    // 读 offsetWidth 触发布局，写 width 让布局失效，下次循环再读又触发……
    el.style.width = el.offsetWidth + 10 + 'px';
  }
}

// ✅ 正面案例：先批量读，再批量写
function goodLayout(elements) {
  const widths = elements.map((el) => el.offsetWidth); // 集中读
  elements.forEach((el, i) => {
    el.style.width = widths[i] + 10 + 'px'; // 集中写
  });
}

这个「读写分离」的思路，就是 fastdom 这类库的核心原理。在 Performance 面板里，强制同步布局会显示成一段段紫色的 Recalculate Style / Layout，还会带一个”⚠️ Forced reflow”的警告，非常好认。

长列表卡顿

数据量一大就卡，几乎都是因为一次性渲染了太多 DOM 节点。解决思路就一个：只渲染可视区域内的节点（虚拟列表）。核心是根据滚动位置算出当前该显示哪几条，其余的用一个撑高的占位容器顶着。

// 虚拟列表核心逻辑：根据滚动位置计算可见区间
function getVisibleRange(scrollTop, itemHeight, containerHeight, total, buffer = 5) {
  const start = Math.max(0, Math.floor(scrollTop / itemHeight) - buffer);
  const visibleCount = Math.ceil(containerHeight / itemHeight);
  const end = Math.min(total, start + visibleCount + buffer * 2);
  return { start, end, offsetTop: start * itemHeight };
}

实际项目里直接用 react-window / vue-virtual-scroller 这种成熟库就行，别自己造轮子，边界情况（动态高度、滚动到底加载）比想象中多。

内存泄露排查

内存泄露的定义很简单：该被回收的对象因为还被引用着，GC 回收不掉，导致内存持续增长。现象通常是”页面用久了越来越卡，最后崩溃刷新才好”。这类问题最难查，因为它不会立刻报错，而是慢慢恶化。

先确认是不是真的泄露

别一看内存涨就喊泄露。判断方法：打开 Performance 面板，勾选 Memory，反复执行某个操作（比如打开又关闭弹窗几十次），然后强制 GC，看内存曲线。

正常情况：              泄露情况：
内存 ▲                  内存 ▲
    │   /\  /\  /\           │      ____/‾‾
    │  /  \/  \/  \          │   __/
    │ /            \___      │ _/
    └──────────────▶ 时间    └──────────────▶ 时间
   （锯齿状，GC 后回落）    （台阶式上涨，回不去）

判据：做完操作、触发 GC 之后，内存基线还是一路往上走、回不到起点，才是真泄露。锯齿状波动但整体平稳是正常的。

常见的四种泄露源

实战里内存泄露基本逃不出这几类，也是面试必背：

泄露类型 原因 解决
未清理的定时器 setInterval 组件销毁没 clear 卸载时 clearInterval
未解绑的事件监听 addEventListener 没 remove 卸载时 removeEventListener
闭包意外持有 闭包引用了大对象且长期存活 用完置 null、缩小闭包范围
游离 DOM JS 变量还引用着已从文档移除的 DOM 移除后把变量置 null 
// ❌ 反面案例：组件销毁后 timer 还在跑，回调闭包一直持有整个组件
function LeakyComponent() {
  const bigData = new Array(1000000).fill('x');
  setInterval(() => {
    console.log(bigData.length); // 闭包让 bigData 永远回收不掉
  }, 1000);
}

// ✅ 正面案例：保存句柄，销毁时清理
function SafeComponent() {
  const bigData = new Array(1000000).fill('x');
  const timer = setInterval(() => {
    console.log(bigData.length);
  }, 1000);

  // 组件卸载时调用（React 的 useEffect return、Vue 的 onUnmounted）
  return function cleanup() {
    clearInterval(timer);
  };
}

用 Memory 面板抓真凶

确认泄露后，用 Memory 面板的堆快照对比精准定位到底是哪个对象没被回收，这是最实用的技能：

  1. 操作前打一个堆快照（Heap Snapshot）
  2. 执行几十次可疑操作（开关弹窗、切换路由）
  3. 手动 GC 后再打一个快照
  4. 快照下拉框选 Comparison 模式，对比两个快照
  5. 按 # Delta（增量）排序，看哪种对象数量只增不减

找到只增不减的对象后，点开它看 Retainers（引用链）——这条链会告诉你”它是被谁拽着不放的”，顺着链往上就能找到根源，往往就是某个没清理的定时器闭包、某个挂在全局的缓存、或者某个游离 DOM。

我的踩坑经验

坑 1：SPA 路由切换是内存泄露重灾区。页面不刷新，组件反复挂载卸载，只要有一个监听/定时器忘了清，切几十次就能看出内存爬升。排查时优先怀疑 onUnmounted / useEffect 的清理函数是不是漏写了。

坑 2：全局缓存要设上限。往 window 或某个 module 级别的 Map 里塞数据当缓存，很方便，但如果只存不删，就是个无底洞。要么设 LRU 上限，要么用 WeakMap——它的 key 被回收时，对应的值会自动被 GC 掉，天然防泄露。

坑 3：第三方库和图表也会泄露。像 ECharts、地图组件这类，销毁时必须调它自己的 dispose() / destroy()，光把 DOM 删了没用，它内部还挂着一堆监听和缓存。

小结

  1. 排查的通用套路是先分类、再缩小范围、最后动手，别一上来就猜
  2. 白屏先看三处：Console 报错、Network 失败请求、Elements 里 DOM 是否挂载，移动端优先怀疑环境兼容
  3. 卡顿的本质是主线程被长任务占满，用 Performance 面板抓长任务，重点警惕读写交替导致的强制同步布局
  4. 长列表卡顿用虚拟列表解决，核心是只渲染可视区域节点
  5. 内存泄露先用内存曲线确认是否真泄露（GC 后回不到基线才算），再用 Memory 面板堆快照对比 + Retainers 引用链定位真凶
  6. 泄露四大来源：未清的定时器、未解绑的监听、意外的闭包引用、游离 DOM，SPA 路由切换是重灾区
