Graph Engineering：多 Agent 编排的新一层

发表于2026|更新于2026|AI相关
|字数总计:5.1k|阅读时长:17分钟

前言：之前我们聊了 Loop Engineering——怎么让单个 Agent 在无人催促下持续跑一个可靠的循环。这篇接着往上走一层：当一个循环不够用，你需要好几个各管一摊的 Agent 互相接力时，怎么把它们组织起来？这就是最近（2026 年 7 月中旬）在 X 上被讨论得很热的 Graph Engineering。这篇把它讲清楚：是什么、解决什么问题、和我们之前讲过的 Harness Engineering 到底是什么关系、以及我们能从里面学到什么。

Graph Engineering 是怎么冒出来的

先说个有意思的现象。2026 年 7 月中旬 Graph Engineering 这个词在 X 上刷屏时，底下最高赞的回复之一是：

congrats, you reinvented LangGraph（恭喜，你重新发明了 LangGraph）。

这句吐槽基本是对的。LangGraph 把 Agent 系统建模成图（官方自己就叫它”graph engineering”）已经三年了，月下载量 6500 万+。微软的 AutoGen 有 GraphFlow，谷歌的 ADK 把 sequential / parallel / loop 工作流 Agent 做成一等原语，A2A 协议还标准化了”图与图之间的边”。

所以 Graph Engineering 不是一个新能力，它是给一个早就存在的架构决策起了个共享的名字。这一点我觉得挺重要——别被”新词”忽悠，它的价值在于把一件大家一直在做但没统一叫法的事情说清楚了。

LangChain 官方在 3 Years of Graph Engineering with LangGraph 里那句话说得很到位：

Graph engineering isn’t a new idea. It’s the latest name for a well established approach to building reliable agents.
Graph engineering并非新概念，而是对构建可靠代理这一成熟方法的最新命名。

什么是 Graph Engineering

Graph Engineering：把多个各司其职的 Agent（或确定性步骤）显式地连成一张有向图——用节点做事、用边决定下一步走哪、用一份共享状态沿着边流动，从而组织出一个单个 Agent 循环做不到的协作系统。

如果用工程师更熟悉的类比来说，它很像一条”Agent 化的流水线”。只不过传统流水线里的节点通常是确定性的程序步骤，而 Graph 里的节点可以是一个会思考、会调用工具、会自我修正的 Agent；传统流水线大多是线性前进，而 Graph 可以分叉、并行、合流、循环，甚至根据审查结果把任务打回上一个节点。

所以流水线可以看成 Graph 的一种简化形态：当图足够简单时，它就是流水线；当图里出现多个 Agent、条件边和共享状态时，它就变成了 Graph Engineering。

它就三个原语，非常好记：

原语 是什么 举例
节点 Node 干一件具体的事 researcher、writer、reviewer、一次工具调用、一段确定性代码
边 Edge 决定这个节点跑完去哪 直连（A→B）、条件（审核过就发布，否则打回）、fan-out（一分三并行）、fan-in（三合一汇总）
共享状态 State 每个节点都读写的那份记录 任务、当前草稿、笔记、结论——让系统”记得住”而不是每次失忆

画成图大概长这样：

                    ┌──────────────┐
        任务进来 →   │  规划节点      │
                    └──────┬───────┘
                           │ fan-out（并行）
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        ┌─────────┐  ┌─────────┐  ┌─────────┐
        │检索节点 A│  │检索节点 B │  │检索节点 C│
        └────┬────┘  └────┬────┘  └────┬────┘
             └────────────┼────────────┘
                          │ fan-in（汇总）
                          ▼
                    ┌──────────────┐
                    │  写作节点     │◀──────┐
                    └──────┬───────┘       │ 条件边：没过就打回
                           ▼               │
                    ┌──────────────┐       │
                    │  审查节点     │───────┘
                    └──────┬───────┘
                           │ 条件边：审查通过
                           ▼
                         [ END ]

  ※ 一份共享状态（任务 / 草稿 / 笔记 / 审查结论）沿着所有边流动

这里有个特别关键的认知：一个 loop 其实就是最小的 graph——它是”单个节点 + 一条指回自己的边”。所以 Graph Engineering 不是要取代 Loop Engineering，它是当好几个 loop 需要互相交接时，你自然会得到的那一层。用 David Khourshid 的话说：a loop is just a directed, cyclic graph（循环不过是一张有向有环图）。

它到底解决什么问题

单个 Agent 循环（哪怕是很成熟的 Loop）有几个天然天花板，Graph Engineering 就是来捅破这几个天花板的。

单循环的问题 现象 Graph 的处理方式
跨领域塞不进一个循环 又要检索又要写代码又要审安全，一个 Agent 什么都懂但什么都不精 拆成多个专职节点，各管一摊
不能真并行 三件互不依赖的事只能排队干 fan-out 并行，fan-in 汇总
全靠 LLM 自己判断路径 想让它”审核过才发布”，它有时候自作主张 用条件边把关键路径写死成确定性逻辑
失败会污染整条链 一个环节崩了，整个任务重来 节点级失败隔离：重试本节点 / 走 fallback / 升级给人 / 砍掉这条分支
看不清跑了啥、花了多少 长任务像黑盒，出问题难复盘 图天然可观测：哪个节点跑了、产出啥、和计划哪里分叉、每个节点花多少 token

一句话概括我的理解：

Graph Engineering 的本质，是把”要不要相信模型自己决定下一步”这个问题，从”全都信”改成”该确定的地方我写死，该灵活的地方才交给模型”。

LangChain 那篇博客把这层意思讲得很直白：图让你能把”系统应该怎么跑”的先验，固化成受约束的路径，而不是完全押注在 LLM 的临场判断上。这跟 Harness Engineering、Loop Engineering 是同一个思路——把模型的推理放在对的位置，配上对的上下文，一步一步来。

在概念谱系里的位置

这几个”X Engineering”很容易糊成一团，我把它们摆在一起看：

层级 控制的是什么 核心原语 什么时候够用
Prompt Engineering 一次模型回复 指令文本 静态、一次性任务
Context Engineering 一次回复看到什么 RAG、上下文选择与压缩 单轮但依赖外部信息
Harness Engineering 一次执行跑得稳 工具、权限、沙箱、验收 单次 Agent 执行要可靠
Loop Engineering 一个 Agent 的行为循环 触发 → 执行 → 验证 → 重试 单领域的自主任务
Graph Engineering 多个 Agent 的组织方式 节点（Agent）+ 边（依赖） 跨领域、需要并行或互相交接

它们不是替代关系，是逐层叠加：

Prompt  →  Context  →  Harness  →  Loop  →  Graph
一句话     这句话的     这次执行     让执行     多个循环
           上下文       跑得稳       持续转      连成组织

  每一层都把下一层当成自己的零件：
  Graph 里的一个节点，可能就是一个完整的 Loop；
  这个 Loop 的每一步，靠 Harness 保证可靠；
  每一步的输入，靠 Context 组织；
  每一次调用，靠 Prompt 表达。

所以别问”Graph Engineering 会不会取代 Loop Engineering”。不会。它只是把一个个 loop 变成了图上的节点。

Graph Engineering 和 Harness Engineering 有什么区别

这俩最容易被混在一起，因为都属于”X Engineering”系列，都在讲”怎么让 AI 靠谱”。但它们的主语和作用范围完全不同——搞清楚这点，整个系列的脉络就通了。

Harness Engineering 的主语是人：工程师怎么约束、引导、校验 AI 产出，让一次执行能达到生产标准。Graph Engineering 的主语是系统：多个 AI 执行单元怎么用节点和边组织成协作网络。

所以它俩的关系不是对立，是分工分层。LangChain 那篇文章也把这层关系点出来了：Graph、Loop、Harness 是同一套思路——把模型的推理放在对的位置、配上对的上下文，一步一步来，区别只在作用范围。

摆一起对比：

维度 Harness Engineering Graph Engineering
主语 / 视角 人怎么驾驭 AI 系统怎么组织多个 AI
作用范围 一次 / 单个 AI 执行 多个执行单元的编排
核心产物 约束、验收、沙箱、错误恢复（五大支柱） 节点、边、共享状态
解决的问题 AI 这一次产出能不能上线 多个 Agent 怎么并行、交接、路由
在谱系里的层 单次执行跑得稳 多个执行连成组织（更外层）
谁在把关 工程师的判断力和兜底力 图里的条件边、验收节点、人工闸口

一句话区分：

**Harness Engineering 管”单点可靠”**——让一次 AI 执行跑得稳、能上线。
**Graph Engineering 管”整体结构”**——让多个这样的执行组成一个系统。

关键是：它俩要叠着用。一个真实的多 Agent 系统 = 用 Graph 画组织骨架 + 每个节点内部用 Harness 保证可靠。图画得再漂亮，如果节点本身没人约束、没人校验、出错不能兜底，整张图只是把混乱更”有组织”地放大。

所以顺序很简单：先把单个节点的 Harness 做扎实，再考虑上 Graph。Harness 在里层，Graph 在更外层，逐层叠加。

最小可运行示例：手写一个 mini graph 引擎

光说不练不行。下面这个例子不依赖任何大模型，也不装任何第三方包，纯 Node.js 就能跑。重点是把”节点 / 边 / 条件边 / 共享状态 / 受控环”这几个东西看清楚。

这段代码对应的结构图是这样：

                 共享状态 state
     { topic, draft, round, passed, verdict, revisionNotes }
                         │
                         ▼
                    ┌─────────┐
        entry ────▶ │ draft   │
                    │ 写初稿   │
                    └────┬────┘
                         │ 普通边 addEdge('draft', 'review')
                         ▼
                    ┌─────────┐
                    │ review  │
                    │ 审查     │
                    └────┬────┘
                         │ 条件边 addConditionalEdge('review', ...)
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
      passed === false         passed === true
        ┌─────────┐                [ END ]
        │ revise  │
        │ 修订意见 │
        └────┬────┘
             │ 普通边 addEdge('revise', 'draft')
             └───────────────回到 draft，形成受控环

  引擎层：nodes 保存节点函数，edges 保存普通边，condEdges 保存条件边；
  执行层：run() 从 entry 开始跑，每个节点返回 update，再合并进共享状态。

环境要求：

  • Node.js 20+
  • 不需要安装任何依赖

新建 mini-graph.mjs：

const END = 'END';

function createGraph() {
  const nodes = new Map();      // 节点：name -> 处理函数
  const edges = new Map();      // 普通边：from -> to
  const condEdges = new Map();  // 条件边：from -> (state) => nextName
  let entry = null;

  return {
    addNode(name, fn) { nodes.set(name, fn); return this; },
    addEdge(from, to) { edges.set(from, to); return this; },
    addConditionalEdge(from, router) { condEdges.set(from, router); return this; },
    setEntry(name) { entry = name; return this; },

    async run(initialState) {
      let state = { ...initialState };
      let current = entry;
      let steps = 0;
      const MAX_STEPS = 20; // 兜底：防止图里出现失控环，这是必须的刹车

      while (current && current !== END) {
        if (steps++ > MAX_STEPS) throw new Error('执行步数超限，可能存在死环');

        const node = nodes.get(current);
        if (!node) throw new Error(`未定义的节点: ${current}`);

        const update = await node(state);
        state = { ...state, ...update }; // 共享状态沿边流动、逐节点累积
        console.log(`[node] ${current} ->`, update);

        // 先看条件边，没有再走普通边，都没有就结束
        if (condEdges.has(current)) {
          current = condEdges.get(current)(state);
        } else {
          current = edges.get(current) ?? END;
        }
      }
      return state;
    }
  };
}

// 用这个引擎搭一张"写稿 → 审查 →（没过就打回重写）"的图
const graph = createGraph();

graph
  .addNode('draft', (s) => ({
    draft: `关于「${s.topic}」的初稿 v${(s.round ?? 0) + 1}`,
    round: (s.round ?? 0) + 1
  }))
  .addNode('review', (s) => {
    // 模拟审查：第 2 轮开始通过（真实系统里这里换成 verifier Agent）
    const passed = s.round >= 2;
    return { passed, verdict: passed ? '通过' : '结构松散，需重写' };
  })
  .addNode('revise', (s) => ({
    revisionNotes: [...(s.revisionNotes ?? []), `按审查意见修订：${s.verdict}`]
  }))
  .setEntry('draft');

graph.addEdge('draft', 'review');
graph.addConditionalEdge('review', (s) => (s.passed ? END : 'revise'));
graph.addEdge('revise', 'draft'); // 打回 draft，形成一个受控环

const result = await graph.run({ topic: 'Graph Engineering' });
console.log('\n最终状态:', result);

运行：

node mini-graph.mjs

预期输出：

[node] draft -> { draft: '关于「Graph Engineering」的初稿 v1', round: 1 }
[node] review -> { passed: false, verdict: '结构松散，需重写' }
[node] revise -> { revisionNotes: [ '按审查意见修订：结构松散，需重写' ] }
[node] draft -> { draft: '关于「Graph Engineering」的初稿 v2', round: 2 }
[node] review -> { passed: true, verdict: '通过' }

最终状态: {
  topic: 'Graph Engineering',
  draft: '关于「Graph Engineering」的初稿 v2',
  round: 2,
  passed: true,
  verdict: '通过',
  revisionNotes: [ '按审查意见修订：结构松散，需重写' ]
}

别看它简单，Graph Engineering 的几个核心点它都有了：

  • 节点各干一件事（draft / review / revise）
  • 条件边决定路径（review 过了走 END，没过走 revise）
  • 共享状态沿边累积（round、draft、verdict 逐步叠加）
  • 受控环（revise → draft 的打回）+ 步数上限这个刹车

真正接大模型时，不是把这些控制逻辑删掉，而是把 draft / review 这些节点函数换成 Agent 调用。结构不变，只是节点里的东西变强了——这跟 Loop Engineering 那篇里”把 implementTask 换成 Agent”是一个套路。

并行（fan-out / fan-in）这里没写进去，因为要处理并发写同一份 state 的合并问题（真实框架用 reducer 解决，比如 LangGraph 的 Annotated[list, add]）。这属于生产级细节，自己手搓容易踩坑，建议直接用成熟框架。

真实框架长什么样

自己手搓适合理解原理，生产环境别硬造轮子。主流框架已经把这套原语打磨得很成熟了：

框架 语言 图模型关键词
LangGraph（LangChain） Python / JS StateGraph + 节点 + 条件边 + checkpointer（持久化）+ 中断/恢复
AutoGen GraphFlow（微软） Python / .NET GraphFlow 图编排多 Agent
Google ADK Python / Go Sequential / Parallel / Loop 工作流 Agent 作为一等原语
Mastra TypeScript TS 原生工作流图
A2A（Agent2Agent 协议） 跨团队 标准化不同团队所属图之间的”边”

以 LangGraph 为例，它的关键设计（以官方文档为准，这里只讲思路不抠 API）：

  • typed state（带类型的共享状态）：用 schema 声明每个字段，并用 reducer 控制并发更新怎么合并——这是并行分支不打架的关键。
  • conditional edge（条件边）：一个函数读当前 state，返回下一个节点名（或 END）。Agent 的”决策”就是把 LLM 输出写进 state，再由条件边读出来路由。
  • checkpointer（检查点）：每次节点转移后把状态落盘，靠 thread id 索引。这让长任务能崩溃恢复、能中断再续。
  • human-in-the-loop（人工闸口）：在高风险节点前中断，等人批准再继续。

一个值得注意的坑：什么都往共享状态里塞，checkpoint 越写越慢。
现象：处理到几十条数据时，单次响应明显变卡。
原因：state 每次节点转移都要整份序列化落盘。有人把原始 LLM 响应（连 usage 元数据）全塞进 state，一条 checkpoint 就 180KB，数据库写入飙到几百毫秒。
解决：state 只留下游节点真正需要的字段，大块中间产物该丢就丢，别当仓库用。

什么时候该用、什么时候别用

说句实话，也是那些吐槽 Graph Engineering 是”炒作”的人有道理的地方：

大部分任务根本用不到图。

一个 prompt 能搞定的，别上 loop；一个 loop 能搞定的，别上 graph。过早引入图，只会让一个本来简单的任务背上一堆编排复杂度。

适合上 Graph 为什么
跨领域协作 检索 + 写作 + 审查 + 安全检查，各要一个专家节点
有真并行 多个互不依赖的子任务可以 fan-out
关键路径要确定 “审核通过才发布”这类必须写死的条件
长任务要能恢复 跑几小时、会崩、需要 checkpoint 续跑
要审计和可观测 生产系统要能复盘每个节点跑了啥、花了多少
别上 Graph 为什么
单轮问答 / 一次性任务 一个 prompt 足矣
单领域自主任务 一个 loop 就够，图是过度设计
需求还没想清楚 图会把模糊需求的复杂度放大
团队还没搞定可观测 没有 tracing 的多 Agent 图 = 更大的黑盒

我们能从里面学到什么

抛开”要不要用某个框架”，Graph Engineering 这波讨论里，有几个思维方式是值得我们吸收的，哪怕你现在还没到用图的阶段：

  1. 学会用”节点 / 边 / 状态”三件套拆问题。很多复杂 AI 工作流，本质就是”谁干活、谁向谁交接、传什么”。这个视角比”写一个超级 prompt / 超级 Agent”清晰得多。
  2. 该确定的地方就写死，别什么都押给模型。条件边、人工闸口、验收节点，都是把”关键决策”从模型手里拿回来的手段。这跟 Harness Engineering 的”约束力”是一脉相承的。
  3. 共享状态要当契约来设计。typed state、reducer、只留必要字段——这些不是框架细节，是让多 Agent 系统不失忆、不打架的地基。
  4. 可观测性要第一天就上。多 Agent 图不加 tracing，出了问题你根本不知道是哪个节点、哪条边出的岔。生产里赢的团队，都是先做了”不性感”的埋点和 typed state，而不是一味追求 Agent 自主性。
  5. 失败恢复要有明确规则。节点失败了是重试、走 fallback、升级给人、还是砍掉这条分支？这些要在图里写清楚，而不是指望模型临场发挥。
  6. 别为新词买单，但要理解它指向的转变。”Graph Engineering”这个标签几乎肯定还会变，但它背后那个真实的转变——**从”编程单个 Agent 的行为”到”编程多个 Agent 的组织”**——是实打实的。

我的判断

Graph Engineering 不是又一个要你马上学的新框架，它是一个提醒：当你发现自己在一个 Agent 里塞了太多互不相干的职责、或者在 prompt 里写”先做 A，如果 B 就 C，否则 D”这种流程控制时，你其实已经在画图了，只是画在了脑子里和 prompt 里，而不是画在代码里。

把它显式画出来，你就获得了确定性、可观测性和失败隔离。代价是编排复杂度。所以判断标准很简单：

如果你的任务能用一个循环说清楚，就别上图；一旦出现”多个专家要并行、要交接、关键路径必须写死”，图就是省心的选择。

从 Harness Engineering 关注的”一次执行怎么跑稳”，到 Graph Engineering 关注的”多个执行怎么组织”，本质是同一套工程思路在往外扩：把模型的推理放在对的位置。我的感受是：先把单个节点的 Harness 做扎实，再考虑上图。节点本身都不可靠，画再复杂的图也只是把混乱放大；而一旦单点稳了、活儿又需要多专家并行交接，图就是那层让你省心的骨架。

小结

  1. Graph Engineering 是把多个专职 Agent 用节点、边、共享状态连成有向图，解决单个循环搞不定的跨领域、并行和交接问题。
  2. 它不是新能力，是给一个存在三年的架构（LangGraph 那套）起了个共享的名字；价值在于把大家一直在做的事说清楚了。
  3. 三个原语要记牢：节点做事、边决定路径（含条件边和 fan-out/fan-in）、共享状态沿边流动；一个 loop 就是最小的图。
  4. 它在概念谱系里位于 Loop 之上：Prompt → Context → Harness → Loop → Graph，逐层叠加而非替代。
  5. 和 Harness Engineering 不是对立而是分工分层：Harness 管”一次执行怎么跑稳”（单点可靠），Graph 管”多个执行怎么组织”（整体结构），二者叠着用，图里每个节点内部仍要靠 Harness 保证可靠。
  6. 手搓一个 mini graph 引擎就能看清节点/条件边/共享状态/受控环；生产环境直接用 LangGraph、ADK、AutoGen 等成熟框架，别自造轮子。
  7. 大部分任务用不到图，一个 prompt 或一个 loop 能搞定就别上；只有跨领域、要并行、关键路径要写死、要审计恢复时才值得。
  8. 最值得吸收的思维：用节点/边/状态拆问题、该写死就写死、共享状态当契约设计、可观测性第一天就上、失败恢复要有明确规则。
