AI 编程最佳实践：把 Agent 当长期队友，而不是问答机器

发表于2026|更新于2026|AI相关
|字数总计:3.8k|阅读时长:12分钟

前言：OpenAI 最近放出的 Codex 官方最佳实践里，有个信号很明显：AI 编程工具已经不只是”问一句答一句”的代码助手，而是在往”长期队友”方向演进。这篇借 Codex 做一个切入，但重点不在某个具体工具，而是重新总结我们应该怎么和 AI Agent 协作。

Codex 官方指南真正想强调什么

先把资料来源说清楚。OpenAI 在 Codex 的 Best practices、Prompting、AGENTS.md 指南 里反复强调了几件事：

  1. 提示词最好包含 Goal（目标）、Context（上下文）、Constraints（遵守规则与边界）、Done when（完成状态，什么状态才算真的完成）四件事
  2. 复杂任务先用计划模式，让 Agent 读代码、澄清问题、提出方案
  3. 用 AGENTS.md 沉淀项目长期规则，而不是每次聊天重新交代
  4. 让测试、lint、类型检查、代码审查成为 AI 工作的验证闭环
  5. 重复工作可以抽成 Skills，外部系统可以通过 MCP 接进来
  6. 对有明确目标和停止条件的长任务，可以让 Agent 持续推进，而不是每一步都等人催

这些建议单独看都不新。我们之前聊过 Prompt Engineering、Context Engineering、Harness Engineering、Loop Engineering，很多概念都能对应上。

但把它们放在一起看，重点就不是”Codex 有哪些命令”，而是：

AI 编程正在从”聊天式工具”变成”可被管理、可被交接、可被验证的工程参与者”。

这才是这份指南最有价值的地方。

从问答机器到长期队友

过去很多人使用 AI 编程，大概是这种模式：

我：帮我写一个登录页面
AI：给你代码
我：这里报错了，修一下
AI：改好了
我：样式不对，再调一下
AI：再改

这本质上是”问答机器”模式。AI 每次只处理当前这一轮上下文，人的主要工作是不断追问、纠错、补充背景。

长期队友模式不一样。你不会把一个真实同事当成搜索框用，你会做几件事：

协作动作 对真实同事 对 AI Agent
入职交接 讲项目背景、技术栈、踩坑点 写 AGENTS.md、项目规则、架构说明
分配任务 说明目标、边界、完成标准 prompt 里写清 Goal / Context / Constraints / Done when
过程管理 先让他出方案，再评审方案 复杂任务先 plan，再 implement
质量验收 看 PR、跑测试、做 code review 让 AI 跑检查，人审 diff 和风险
经验沉淀 把反复出现的问题写进规范 把重复纠正写回 AGENTS.md 或 Skill

我对”长期队友”的理解不是拟人化，也不是说 AI 真的有责任感，而是把它放进一个工程协作系统里：给它上下文，给它边界，给它验证方式，也给它可持续学习的项目记忆。目的很简单：不是让 AI “看起来像同事”，而是让它少猜、少跑偏、可验收，最终更稳定地完成任务。

第一件事：别再写一次性 prompt

Codex 官方建议一个好 prompt 至少包含四类信息：

Goal：你要改什么、做什么
Context：相关文件、错误日志、设计文档、历史实现
Constraints：不能改什么、必须遵守什么、有哪些安全边界
Done when：什么状态算完成，跑哪些检查，验收什么行为

这个模板很朴素，但非常实用。

反面案例：

帮我优化一下这个页面。

这句话最大的问题不是短，而是没有”完成标准”。优化性能？优化样式？优化代码结构？减少请求？AI 只能猜。

更好的写法：

Goal：
优化用户列表页的首屏加载体验，重点减少首次进入时的阻塞请求。

Context：
- 页面入口：src/pages/user-list/index.tsx
- 数据请求在 src/services/user.ts
- 现在的问题：首屏会同时请求用户列表、筛选项、统计卡片，弱网下白屏时间明显

Constraints：
- 不改接口协议
- 不引入新的状态管理库
- 保持现有 UI 行为不变

Done when：
- 首屏只阻塞用户列表必需数据
- 非核心统计卡片延后加载
- npm run lint 和相关单测通过
- 总结改动和潜在风险

这不是”提示词工程玄学”，这就是正常的任务交接。

当你开始用这种方式给 AI 分配任务，AI 的输出会明显稳定。因为你不再要求它”读心”，而是在给它一个可执行的工作包。

第二件事：把项目规则写进 AGENTS.md

OpenAI 官方把 AGENTS.md 定位成”给 Agent 看的 README”。它不替代 README.md，而是专门存那些对 AI 工作有帮助、但对普通读者不一定重要的信息。

比如：

# AGENTS.md

## Project Overview
- This is a React + TypeScript admin dashboard.
- API clients live in src/services.
- Shared UI components live in src/components.

## Commands
- npm run lint: run ESLint and TypeScript checks.
- npm test: run unit tests.
- npm run build: verify production build.

## Engineering Rules
- Do not call fetch directly. Use src/services/request.ts.
- Do not add production dependencies without confirmation.
- Keep route-level components thin; move reusable logic into hooks.

## Done Means
- Relevant tests pass.
- Lint passes.
- The final response includes changed files, verification result, and risks.

这份文件的价值不在于”写得多”，而在于”长期有效”。

OpenAI 的建议也很克制：AGENTS.md 要短、准、重要。不要把所有编码常识都塞进去，比如”变量命名要清晰”、”代码要可读”这种强模型本来就知道的东西。真正值得写进去的是：

规则类型 适合写进 AGENTS.md 吗 例子
项目特有约定 适合 请求只能走 request.ts
构建和测试命令 适合 pnpm test --filter web
安全红线 适合 禁止输出用户隐私字段
架构边界 适合 页面层不能直接访问数据库
通用好习惯 不太适合 命名要有意义、函数要短
机械格式规则 不太适合 缩进、分号、换行，交给 lint

这里有个很重要的心态转变：

不要把 AGENTS.md 当提示词仓库，要把它当团队的 AI 入职手册。

当你连续三次纠正 AI 同一个问题，比如它总是直接用 fetch、总是忘记跑某个测试、总是改错目录，这就说明它不是一次性问题，而是项目规则没有沉淀。这个时候不要继续在聊天里骂它，应该把规则写回 AGENTS.md。

第三件事：先 plan，再动手

复杂任务最怕 AI 一上来就改代码。

这和真实开发一样。你给同事一个大需求，他如果不读代码、不问边界、不确认方案，直接交一坨 diff 过来，你大概率也不放心。

Codex 官方建议复杂或模糊任务先进入计划阶段。这背后的原则很简单：

读上下文 → 识别风险 → 提出方案 → 人确认 → 再执行

适合先 plan 的场景：

场景 为什么要先 plan
跨多个模块的重构 容易误伤边界，需要先看依赖
业务规则不清楚 需要先澄清需求，而不是猜
涉及数据迁移 回滚、兼容、验证都要提前想
性能优化 需要先定位瓶颈，不能凭感觉改
安全相关改动 需要明确威胁模型和验收标准

小任务让 AI 直接做，大任务先让 AI 写方案；方案不靠谱，代码大概率也不靠谱。

这里的 plan 不是形式主义。好的计划至少要回答四个问题：

  1. 准备改哪些文件
  2. 每一步为什么这么改
  3. 有哪些风险和替代方案
  4. 怎么验证它真的完成了

如果 AI 的计划只是在复述你的需求，没有体现它读过代码，那就让它继续补上下文，不要急着开工。

第四件事：把验证做成闭环

长期队友不是”我相信你”，而是”我知道怎么验收你”。

Codex 官方把测试、lint、类型检查、review 都放在最佳实践里，这点我非常认同。AI 写代码最大的问题不是它会犯错，而是它犯错时经常看起来很合理。

所以 AI 编程一定要有验证闭环：

┌────────────┐
│  分配任务   │
└─────┬──────┘
      ▼
┌────────────┐
│  AI 实现    │
└─────┬──────┘
      ▼
┌────────────┐
│  自动检查   │  lint / typecheck / test / build
└─────┬──────┘
      ▼
┌────────────┐
│  人审 diff  │  业务逻辑 / 风险 / 边界 / 可维护性
└─────┬──────┘
      ▼
┌────────────┐
│  规则沉淀   │  AGENTS.md / Skill / Review Rule
└────────────┘

这里最容易犯的坑是：只看 AI 的最终解释，不看 diff。

AI 很擅长总结自己做了什么，但总结不等于事实。真正可靠的检查顺序应该是：

  1. 先看 diff，确认改动范围是否合理
  2. 再看测试和构建结果
  3. 再看它的总结有没有遗漏风险
  4. 最后决定是否接受

换句话说，AI 可以是 coder，但人必须还是 reviewer。

第五件事：把重复协作抽成 Skill

如果说 AGENTS.md 是项目长期记忆，那 Skill 更像是”岗位操作手册”。

比如你经常让 AI 做这些事：

  • 根据接口文档生成 API client
  • 迁移一个组件到新设计系统
  • 给 PR 做安全 review
  • 根据线上日志定位问题
  • 按固定模板写技术博客

这些任务都有固定流程、固定输入、固定产出格式。如果每次都靠聊天临场发挥，效果一定不稳定。

更好的方式是抽成 Skill：

触发条件：用户说"生成接口代码"
输入材料：接口文档、目标目录、已有 service 示例
执行步骤：
  1. 读取接口定义
  2. 对比现有 service 风格
  3. 生成类型和请求函数
  4. 补 mock 或测试
  5. 跑 lint/typecheck
输出要求：
  - 说明生成了哪些文件
  - 说明哪些接口需要人工确认
  - 给出验证结果

这和真实团队里的 SOP 一样。新人照着 SOP 做事，稳定性会高很多；AI Agent 也一样。

所以我的判断是：未来 AI 编程能力的差距，不只在模型本身，更在于团队有没有把自己的工作方式沉淀成：

  1. AGENTS.md：长期规则
  2. Skills：可复用流程
  3. MCP：外部系统连接
  4. CI / Review：验证防线
  5. Goal / Loop：持续执行机制

模型越强，这些东西越不是”限制 AI”，而是让 AI 真正进入工程系统。

第六件事：长任务要有目标，也要有刹车

Codex 的 /goal 思路很值得关注：对有明确目标和验证方式的任务，让 Agent 持续工作，而不是每一步都等你发下一条 prompt。

这其实就是我们之前聊的 Loop Engineering。

但长任务不是”让 AI 自己随便跑”。一个好的长期目标必须写清楚：

目标：
把用户中心模块的旧 API client 迁移到新 request 层。

范围：
- 只处理 src/modules/user 下的代码
- 不改 UI 样式
- 不迁移订单模块

验证：
- npm run lint
- npm test -- user
- npm run build

停止条件：
- 所有 user 模块 API 迁移完成，并通过验证
- 或者遇到接口协议不明确的问题时暂停并汇报

进度要求：
- 每完成一个子模块记录一次 checkpoint
- 最终总结改动、验证结果、剩余风险

这里最关键的是”停止条件”。没有停止条件的 Agent 长任务，很容易变成昂贵的自嗨循环：越改越多，越跑越偏，最后人接手时还要先清理现场。

长期队友不是无限自治，而是有限自治：

在清晰目标、明确边界、可验证结果、可暂停机制之内，让 AI 自主推进。

这也是我觉得 Codex 指南里最值得推广到所有 AI 编程工具的一点。

这套方法不只适用于 Codex

虽然这篇是从 Codex 官方最佳实践切入，但这些原则并不绑定 Codex。Cursor、Claude Code、GitHub Copilot coding agent、Gemini CLI、Aider，本质上都在往同一个方向走：

能力层 Codex 里的体现 其他 AI 编程工具里的对应物
项目记忆 AGENTS.md Cursor rules、Claude CLAUDE.md、项目指令文件
任务计划 plan mode Plan 模式、Architect 模式、先分析后实现
工具连接 MCP MCP、插件、内置工具、浏览器/Issue/PR 集成
流程复用 Skills 自定义命令、工作流、模板、Agent Skills
自动验证 lint/test/review CI、pre-commit、review agent、test runner
长期执行 goal mode background agent、cloud agent、loop workflow

所以不用纠结”我是不是必须用 Codex”。真正值得学的是它背后的协作模型：

  1. 把口头交代变成项目记忆
  2. 把一次性 prompt 变成任务包
  3. 把人工催促变成工作循环
  4. 把相信 AI 变成验证 AI
  5. 把重复纠错变成规则沉淀

这套东西迁移到任何 Agent 工具里都成立。

我的实战建议

如果你现在还停留在”让 AI 帮我补代码”阶段，我建议按这个顺序升级，不要一步到位搞复杂系统。

第一步：先改 prompt 习惯

从今天开始，重要任务都可以尝试按四段写：

Goal：
Context：
Constraints：
Done when：

这一步成本最低，但收益很明显。

第二步：给项目补一个轻量 AGENTS.md

不要一上来写 200 行。先写 20 行就够：

  • 项目是什么
  • 怎么启动
  • 怎么测试
  • 哪些目录不能乱动
  • 哪些规则 AI 经常猜错

后面每次发现 AI 重复犯错，再一点点补；随着模型能力增强，也要定期回头 review 这些规则，把已经不需要的”手把手约束”删掉，避免这些内容慢慢变成噪声。

第三步：把复杂任务固定为”先 plan 后执行”

只要任务跨 3 个以上文件，或者你自己都觉得边界不清，就先让 AI 输出计划。计划看不懂、看不出风险，就别让它动代码。

第四步：把验证命令写进完成标准

不要只说”改好”。要说：

Done when:
- npm run lint passes
- npm test -- user passes
- The final response summarizes changed files and risks

AI 越能自己跑检查，你越应该把检查写清楚。

第五步：把高频流程抽成 Skill

当你发现自己连续多次给 AI 下同一类任务，而且每次都要重复解释流程，就该抽 Skill 了。

不要等流程完美才沉淀。先把当前版本写下来，让它在使用中迭代。

小结

  1. Codex 官方最佳实践的核心信号是：AI 编程工具正在从问答机器变成工程协作参与者。
  2. 好 prompt 不是玄学，而是正常任务交接：目标、上下文、约束、完成标准。
  3. AGENTS.md 的价值是长期项目记忆，应该写项目特有规则，而不是堆通用编码常识。
  4. 复杂任务要先 plan，再实现；计划质量往往决定最终代码质量。
  5. AI 可以写代码，但人必须负责 review，测试和 CI 是协作闭环的一部分。
  6. 重复流程应该沉淀成 Skill，外部系统通过 MCP 接入，稳定任务再进一步做成 Loop。
  7. 真正的”长期队友”不是无限信任 AI，而是在明确边界和验证机制内，让 AI 持续产生可靠产出。
