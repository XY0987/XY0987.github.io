Vue 3 scheduler 源码解析：组件更新为什么是异步批量执行的

发表于2026|更新于2026|Vue框架及周边库
|字数总计:1.9k|阅读时长:8分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：响应式状态变化后，组件并不会每次都立刻同步重新渲染。Vue 会把组件更新任务放进调度队列，在微任务中批量刷新。这一篇看 scheduler.ts：queueJob、nextTick、pre/post flush 队列是如何协作的。

先给结论

Vue 的调度系统主要解决三个问题：

问题 解决方式
同一轮多次状态变化导致重复更新 QUEUED 标记去重
父子组件更新顺序 按 job id 排序，父组件 id 更小
生命周期和 watch 的执行时机 pre / main / post 三类队列

组件更新的典型链路是：

响应式状态变化
  │
  ▼
组件 ReactiveEffect 被 trigger
  │
  ▼
effect.scheduler()
  │
  ▼
queueJob(component job)
  │
  ▼
Promise.then(flushJobs)
  │
  ▼
批量执行组件更新

scheduler 的几个队列

scheduler.ts 中维护了主队列和 post 队列：

// 主任务队列，主要放组件更新 job 和 pre flush watcher job。
const queue: SchedulerJob[] = []
let flushIndex = -1

// post flush 队列，主要放 mounted/updated 等后置生命周期和 post watcher。
const pendingPostFlushCbs: SchedulerJob[] = []
let activePostFlushCbs: SchedulerJob[] | null = null
let postFlushIndex = 0

const resolvedPromise = /*@__PURE__*/ Promise.resolve() as Promise<any>
// 当前正在等待 flush 的微任务 Promise；nextTick 也会复用它。
let currentFlushPromise: Promise<void> | null = null

可以粗略理解为三类任务：

队列 典型任务
pre flush 默认 watch 回调，组件更新前执行
main queue 组件更新 job
post flush mounted / updated，flush: 'post' 的 watch

nextTick 等的是什么

nextTick 的实现很短：

export function nextTick(): Promise<void>
export function nextTick<T, R>(
  this: T,
  fn: (this: T) => R | Promise<R>,
): Promise<R>
export function nextTick<T, R>(
  this: T,
  fn?: (this: T) => R | Promise<R>,
): Promise<void | R> {
  // 如果当前已有待 flush 的任务，nextTick 等待这轮 flush；否则退化为一个已 resolved 的微任务。
  const p = currentFlushPromise || resolvedPromise
  return fn ? p.then(this ? fn.bind(this) : fn) : p
}

所以 nextTick 等待的不是“浏览器下一帧”，而是当前 Vue flush 微任务。

如果当前已经有更新任务入队，currentFlushPromise 指向这轮 flushJobs。nextTick 会等它执行完。

queueJob：组件更新如何入队

组件渲染 effect 的 scheduler 会调用 queueJob(job)。

export function queueJob(job: SchedulerJob): void {
  // 同一个 job 在同一轮 flush 中只允许入队一次。
  if (!(job.flags! & SchedulerJobFlags.QUEUED)) {
    const jobId = getId(job)
    const lastJob = queue[queue.length - 1]
    if (
      !lastJob ||
      // fast path when the job id is larger than the tail
      (!(job.flags! & SchedulerJobFlags.PRE) && jobId >= getId(lastJob))
    ) {
      queue.push(job)
    } else {
      queue.splice(findInsertionIndex(jobId), 0, job)
    }

    job.flags! |= SchedulerJobFlags.QUEUED

    queueFlush()
  }
}

这里有两个重点。

第一，QUEUED 标记用于去重。同一轮里同一个组件状态变化多次，只会入队一次。

第二，队列按 job id 排序。组件实例创建时父组件先于子组件，所以父组件 id 更小。这样刷新时可以保证父组件先更新，子组件后更新。

queueFlush：用微任务批量刷新

function queueFlush() {
  if (!currentFlushPromise) {
    // 通过 Promise 微任务异步 flush，实现同一轮同步状态变更的批量更新。
    currentFlushPromise = resolvedPromise.then(flushJobs)
  }
}

这就是 Vue 更新异步批量执行的关键。

同步代码里多次修改状态：

count.value++
count.value++
count.value++

会多次触发响应式依赖，但组件更新 job 只会入队一次，并在微任务中统一执行。

post flush 队列

后置任务通过 queuePostFlushCb 入队：

export function queuePostFlushCb(cb: SchedulerJobs): void {
  // 后置任务用于 mounted/updated hooks、post flush watcher 等，主队列完成后再执行。
  if (!isArray(cb)) {
    if (activePostFlushCbs && cb.id === -1) {
      activePostFlushCbs.splice(postFlushIndex + 1, 0, cb)
    } else if (!(cb.flags! & SchedulerJobFlags.QUEUED)) {
      pendingPostFlushCbs.push(cb)
      cb.flags! |= SchedulerJobFlags.QUEUED
    }
  } else {
    // if cb is an array, it is a component lifecycle hook which can only be
    // triggered by a job, which is already deduped in the main queue, so
    // we can skip duplicate check here to improve perf
    pendingPostFlushCbs.push(...cb)
  }
  queueFlush()
}

比如 renderer 中的 mounted hook 会通过 queuePostRenderEffect 进入 post flush 队列，最终在 DOM patch 后执行。

flushPreFlushCbs：组件更新前的任务

pre flush 任务会在组件更新前执行：

// 刷新 pre flush 任务，典型场景是组件更新前执行的 watch 回调。
export function flushPreFlushCbs(
  instance?: ComponentInternalInstance,
  seen?: CountMap,
  // skip the current job
  i: number = flushIndex + 1,
): void {
  if (__DEV__) {
    seen = seen || new Map()
  }
  for (; i < queue.length; i++) {
    const cb = queue[i]
    if (cb && cb.flags! & SchedulerJobFlags.PRE) {
      if (instance && cb.id !== instance.uid) {
        continue
      }
      if (__DEV__ && checkRecursiveUpdates(seen!, cb)) {
        continue
      }
      queue.splice(i, 1)
      i--
      if (cb.flags! & SchedulerJobFlags.ALLOW_RECURSE) {
        cb.flags! &= ~SchedulerJobFlags.QUEUED
      }
      cb()
      if (!(cb.flags! & SchedulerJobFlags.ALLOW_RECURSE)) {
        cb.flags! &= ~SchedulerJobFlags.QUEUED
      }
    }
  }
}

默认 watch 的 flush 是 pre，所以它通常会在组件 DOM 更新前执行。

flushPostFlushCbs：组件更新后的任务

post 任务会先去重、排序，再执行：

export function flushPostFlushCbs(seen?: CountMap): void {
  if (pendingPostFlushCbs.length) {
    // post 队列执行前先去重并按 id 排序，保证父子组件后置任务顺序稳定。
    const deduped = [...new Set(pendingPostFlushCbs)].sort(
      (a, b) => getId(a) - getId(b),
    )
    pendingPostFlushCbs.length = 0

    // #1947 already has active queue, nested flushPostFlushCbs call
    if (activePostFlushCbs) {
      activePostFlushCbs.push(...deduped)
      return
    }

mounted、updated、flush: 'post' 的 watch 都属于这类。

flushJobs：真正刷新主队列

flushJobs 是主队列执行入口：

function flushJobs(seen?: CountMap) {
  // 主队列 flush：按 queue 中的顺序执行组件更新 job，并在 finally 中清理状态和刷新 post 队列。
  if (__DEV__) {
    seen = seen || new Map()
  }

  // conditional usage of checkRecursiveUpdate must be determined out of
  // try ... catch block since Rollup by default de-optimizes treeshaking
  // inside try-catch. This can leave all warning code unshaked. Although
  // they would get eventually shaken by a minifier like terser, some minifiers
  // would fail to do that (e.g. https://github.com/evanw/esbuild/issues/1610)
  const check = __DEV__
    ? (job: SchedulerJob) => checkRecursiveUpdates(seen!, job)
    : NOOP

  try {
    for (flushIndex = 0; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex]
      if (job && !(job.flags! & SchedulerJobFlags.DISPOSED)) {
        if (__DEV__ && check(job)) {
          continue
        }
        if (job.flags! & SchedulerJobFlags.ALLOW_RECURSE) {
          job.flags! &= ~SchedulerJobFlags.QUEUED
        }
        callWithErrorHandling(
          job,
          job.i,
          job.i ? ErrorCodes.COMPONENT_UPDATE : ErrorCodes.SCHEDULER,
        )
        if (!(job.flags! & SchedulerJobFlags.ALLOW_RECURSE)) {
          job.flags! &= ~SchedulerJobFlags.QUEUED
        }
      }
    }
  } finally {
    // If there was an error we still need to clear the QUEUED flags
    for (; flushIndex < queue.length; flushIndex++) {
      const job = queue[flushIndex]
      if (job) {
        job.flags! &= ~SchedulerJobFlags.QUEUED
      }
    }

    flushIndex = -1
    queue.length = 0

    flushPostFlushCbs(seen)

    currentFlushPromise = null
    // If new jobs have been added to either queue, keep flushing
    if (queue.length || pendingPostFlushCbs.length) {
      flushJobs(seen)
    }
  }
}

几个点值得注意：

  1. DISPOSED 的 job 会跳过，比如组件已经卸载。
  2. 执行 job 时会通过 callWithErrorHandling 统一处理错误。
  3. finally 中一定会清理 QUEUED 标记。
  4. 主队列执行完后会执行 post 队列。
  5. 如果 flush 过程中又产生了新任务，会继续递归 flush。

一个完整流程

假设组件 render 里读取了 count.value：

const count = ref(0)

当执行：

count.value++
count.value++

内部流程是：

count.value++
  │
  ▼
trigger 组件 render effect
  │
  ▼
effect.scheduler()
  │
  ▼
queueJob(instance.job)
  │
  ├─ 如果未入队，加入 queue
  ├─ 标记 QUEUED
  └─ queueFlush()
       │
       ▼
     Promise.then(flushJobs)

同一轮第二次 count.value++
  │
  └─ job 已有 QUEUED 标记，不重复入队

微任务执行
  │
  ▼
flushJobs()
  │
  ├─ 执行组件更新 job
  ├─ patch DOM
  └─ flushPostFlushCbs()

这就是 Vue 组件更新“异步批量”的核心原因。

小结

  1. queueJob 负责组件更新任务入队，并通过 QUEUED 标记去重。
  2. queueFlush 使用 Promise 微任务批量刷新任务队列。
  3. nextTick 等待的是当前 flush 微任务。
  4. 主队列按 job id 排序，保证父组件优先于子组件更新。
  5. pre flush 用于更新前任务，post flush 用于 mounted/updated 和 post watcher。
  6. flushJobs 会执行主队列、清理状态、刷新 post 队列，并处理 flush 过程中新增的任务。

到这里，运行时“响应式状态变化 -> 组件更新入队 -> 批量刷新 -> patch DOM”的链路就完整了。
