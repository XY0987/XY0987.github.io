MCP新版规范正式发布：无状态 HTTP 核心 + OAuth 2.1 加固

发表于2026|更新于2026|AI相关
|字数总计:6.1k|阅读时长:20分钟

前言：之前我写过一篇 MCP 协议深度解析，讲了 Streamable HTTP 怎么替换掉 HTTP+SSE。一年多过去，MCP 月下载量已经冲到 4 亿+，成了 AI Agent 连接外部世界的事实标准。而 2026-07-28 这版规范 是 MCP 诞生以来改动最大的一版：核心从有状态双向协议彻底变成了无状态的请求/响应模型，而且官方明确标注这是一次 breaking change。这篇就讲清楚：到底改了什么、为什么改、以及要不要迁移。

行业时间线

MCP 规范版本 关键变化
2024-11（初版） stdio + HTTP+SSE 两种传输，有状态双向协议
2025-03-26 Streamable HTTP 取代 HTTP+SSE，统一端点、按需升级流
2025-11-25 授权体系细化、Elicitation URL 模式等
2026-07-28 无状态核心：移除握手与 Session，OAuth 2.1 加固，扩展框架正式化

这几次变化背后，其实是在连续解决三个工程问题：

  • 2025-03 的 Streamable HTTP，解决的是传输入口割裂：以前服务器要同时维护普通 HTTP 请求端点和 SSE 流端点；现在统一走同一个 /mcp 端点，普通响应和流式响应按需切换。
  • 2025-11 的授权细化，解决的是接入生产系统时的安全边界：不能只靠协议会话本身来默认信任客户端，授权、回调、用户确认都要更明确。
  • 2026-07 的无状态核心，解决的是云上横向扩展的会话负担：请求不再依赖握手和 Session，负载均衡后面任意实例都能独立处理。

一句话看懂这次更新

MCP 从”打电话”变成了”发短信”。

之前的 MCP 像打电话：先拨号建立连接（initialize 握手），通话过程中双方都记着”我们正在通话”（Mcp-Session-Id 会话），中途还能互相插话（服务端主动发起请求）。这套模型在单机 stdio 下很自然，但放到需要横向扩展的云上就很别扭——负载均衡后面的每台实例都得共享会话状态。

现在的 MCP 像发短信：每条消息都是自包含的，写清楚”我是谁、用哪个协议版本、要干什么”，发到哪台服务器都能独立处理。这就是无状态核心（Stateless Core）。

这里有两个容易误解的点。

第一，旧 MCP 的”有状态”不一定是永远保存同一条 TCP 连接，更准确地说，是服务端要保存一份 MCP 协议会话状态。客户端先 initialize，服务端记住这个客户端是谁、支持什么能力、当前会话是什么，再通过 Mcp-Session-Id 把后续请求串起来。生产环境里，要么做粘性会话，让同一个会话尽量打到同一台机器；要么把 Session 放到 Redis 这类共享存储里。

无状态之后，这部分协议状态被挪回到每次请求里。客户端把协议版本、客户端信息、能力声明、认证信息等必要上下文带上来，负载均衡后面任意一台服务实例都可以独立处理。当然，这不代表业务系统完全没有状态。用户登录态、OAuth token、数据库里的任务状态、工具调用产生的数据，仍然可以存在。无状态说的是MCP 协议层不再维护会话状态。

第二，无状态之后，MCP 看起来确实更像普通 HTTP 后台接口了。这也是我第一眼的感觉：如果都变成请求/响应了，那是不是直接写 HTTP API 就够了？

我的理解是：如果只是自己业务里的前后端调用，MCP 确实没必要，普通 HTTP API 更直接。MCP 的价值不在”怎么发请求”，而在”AI 客户端如何用统一语言发现和调用外部能力”。普通 API 通常只定义某个服务怎么调，MCP 还标准化了 tools、resources、prompts、能力声明、输入输出 schema、错误模型和授权边界。传输层越普通，反而越说明 MCP 的价值正在从连接形态，转向能力描述和生态互操作。

有状态（旧）                          无状态（2026-07-28）
─────────────                        ───────────────────
Client ──initialize──→ Server        Client ──单条自包含请求──→ 任意实例
       ←──initialized──               （请求里带上版本+身份+能力）
Client ──带 Session-Id 的请求──→
       （必须命中同一个会话）           轮询 LB 后面随便哪台都行
                                      无需共享存储

无状态核心：告别握手和会话

旧协议到底怎么有状态

如果没看过旧 MCP 的交互流程，直接看”删掉 initialize、删掉 Mcp-Session-Id“会有点懵。旧模型可以简化成这几步：

1. Client ──initialize──→ Server
   带上 protocolVersion、clientInfo、clientCapabilities

2. Server ──initialize result──→ Client
   返回 serverInfo、serverCapabilities
   HTTP 场景下还可能返回 Mcp-Session-Id

3. Client ──notifications/initialized──→ Server
   告诉服务端：握手完成，可以开始正常通信

4. Client ──后续 tools/call 等请求──→ Server
   每次带上 Mcp-Session-Id，服务端用它找到同一个协议会话

如果需要服务端持续推消息，旧模型还会引入 HTTP GET 流端点：客户端打开一个 SSE 流，服务端通过这个流把通知或长任务结果推回来；如果中间断开，再靠 Last-Event-ID 做断线续传。

所以旧协议的状态主要藏在两处：一是握手阶段协商出来的客户端/服务端能力，二是 Mcp-Session-Id 对应的协议会话。后续请求本身不一定带齐完整上下文，服务端要先根据 Session 找回”这个客户端是谁、支持什么、当前会话到哪一步了”。

这次到底删了什么

2026-07-28 这版删得很干脆（SEP-2575、SEP-2567）：

  • 删掉 initialize / notifications/initialized 握手
  • 删掉 Mcp-Session-Id 请求头
  • 删掉 HTTP GET 流端点、SSE 断线重连（Last-Event-ID）
  • 删掉 ping、logging/setLevel、notifications/roots/list_changed

取而代之，每个请求自己携带全部上下文，塞在 _meta 里：

POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": { "q": "otters" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "my-app", "version": "1.0" },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

几个约定要记住：

  • 客户端 SHOULD 在每个请求带上 io.modelcontextprotocol/clientInfo
  • 服务端 SHOULD 在每个响应的 _meta 里带上 io.modelcontextprotocol/serverInfo
  • 协议版本对不上，服务端返回 UnsupportedProtocolVersionError

握手删了以后，能力发现怎么办

这里会冒出一个新问题：以前 initialize 不只是建立会话，它还顺手完成了能力发现。客户端通过握手知道服务端支持哪些协议版本、有哪些能力、服务端身份是什么。现在握手删了，这些信息从哪里来？

答案是新的 RPC：server/discover。规范规定服务端必须实现它，用来广播支持的协议版本、能力和身份；但客户端可以按需调用——你可以先探一次做版本选择，也可以直接发业务请求跳过它。这是”发现”和”调用”解耦的关键：发现不再是通信的前置门槛。

无状态 ≠ 你的业务不能有状态

这里要分清两层状态：

  • 协议层状态：MCP 自己记住”这个客户端已经握手过、支持哪些能力、当前 Session 是谁”。2026-07-28 这版要删的是这一层。
  • 业务状态：你的工具执行过程中产生的中间结果，比如查询 ID、上传任务 ID、长任务 ID、临时文件 ID。这一层仍然可以存在。

所以关键不是”业务不能保存状态”，而是不要把业务状态藏在 MCP Session 里。如果一个工具调用的结果要给下一个工具继续用，就把这个状态变成一个显式 ID 返回给模型，让模型在下一次请求里带回来。

// 第一次调用：发起一个分页查询
{
  "name": "search_logs",
  "arguments": {
    "keyword": "oauth error"
  }
}

// 服务端可以把查询进度存在数据库或 Redis 里，
// 但要把 query_id 这个业务句柄显式返回给模型。
{
  "items": ["log-1", "log-2"],
  "query_id": "query_abc123"
}

// 第二次调用：模型把 query_id 当普通参数传回来
{
  "name": "fetch_next_logs",
  "arguments": {
    "query_id": "query_abc123"
  }
}

这样一来，请求落到哪台 MCP Server 实例都可以处理：它只要拿着 query_abc123 去数据库或 Redis 查业务状态即可，不需要依赖某个 MCP 协议 Session。这就是”协议层无状态”和”业务可以有状态”之间的关系：状态可以有，但必须显式、可寻址、可跨实例恢复。

配套的传输层改造

无状态是地基，地基之上还有一套配套改动，都是为了让 MCP 真正像一个普通 HTTP 工作负载那样跑起来。

请求头路由：Mcp-Method 和 Mcp-Name

Streamable HTTP 请求现在必须带上 Mcp-Method 和 Mcp-Name 两个头（SEP-2243）。

减负点在网关这一层。MCP 请求本质上都是 POST /mcp，真正的方法名以前藏在 JSON body 里，比如 tools/call、tools/list、resources/read。如果网关想对不同方法做不同策略，就必须打开 body、解析 JSON、再读取 method 和 params.name。这对网关、限流器、WAF 都很别扭：要多做一次解析，还可能遇到大 body、流式 body、解析失败、性能开销和规则配置复杂度。

现在方法和名称直接放到请求头里，基础设施只看 header 就能做判断：tools/call 走更严格的限流，tools/list 可以走缓存，某个高危工具名可以被 WAF 单独拦截。也就是说，业务语义从 JSON body 里被”提到”HTTP 元数据层，网关不用懂 MCP 的完整 JSON-RPC 结构，也能做路由、计量和安全策略。

List 结果可缓存：ttlMs 和 cacheScope

ttlMs 和 cacheScope 不是 HTTP 响应头，而是 MCP 响应体里 result 对象上的缓存提示字段（SEP-2549）。它们的语义有点像 HTTP Cache-Control，但承载位置在 MCP 协议层。

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      { "name": "search", "description": "Search docs" }
    ],
    "ttlMs": 60000,
    "cacheScope": "public"
  }
}

ttlMs 表示客户端可以把这份结果当作新鲜数据缓存多久，单位是毫秒；cacheScope 表示缓存范围，public 代表共享网关或代理也可以缓存，private 代表只能在当前用户授权上下文里复用。tools/list、prompts/list、resources/list、resources/templates/list、resources/read、server/discover 这类结果都可以用这套字段。

同时规范建议 tools/list 返回确定性顺序，这样客户端能稳定缓存工具目录，上游的 prompt cache 命中率也更稳。以前每次重连都得重新拉一遍工具列表，这个坑算是填了。

从双向会话到多轮请求：MRTR

前面几个改动偏基础设施：网关怎么路由，列表结果怎么缓存。接下来这个改动讲的是交互模型：旧 MCP 允许服务端在协议会话里主动”反问”客户端；无状态之后，这个能力不能再依赖 Session 和双向会话通道了。

这里先补一个容易混淆的点：SSE 的确是一条长连接，但长连接不等于协议会话。

SSE 解决的是”服务端能持续往客户端推事件”。比如一次 tools/call 很耗时，服务端可以在这个 POST 响应里用 SSE 持续吐进度，最后吐结果；后面的 subscriptions/listen 也还是一个长连 POST 流，用来接收订阅通知。

但 SSE 是单向的：服务端往客户端推，客户端不能在同一条 SSE 连接里把回答再发回去。也就是说，SSE 可以把”需要你确认一下”这件事推给客户端，但用户点了”确认”之后，客户端必须再发一个新的请求回来。

旧协议里的会话更重，它不只是有一条流，还记着 Mcp-Session-Id、握手状态、客户端能力，并允许服务端在这个会话里主动发起 elicitation/create / sampling/createMessage / roots/list 这类反向请求。为了等用户回答，服务端通常还要把”当前工具调用卡在第几步、正在等哪个确认”这类上下文挂在会话上。

所以无状态不是说”再也没有长连接”，而是说”不再依赖一个长期存在的 MCP Session 来维持交互上下文”。SSE 可以继续用来推当前请求的事件，但如果工具执行到一半需要用户确认（比如”确定要删这批数据吗？”），客户端的回答要通过下一次请求显式带回来。

无状态之后，这种”等用户回答的上下文”不能再藏在会话里。那工具执行到一半确实需要用户补输入时怎么办？

答案是 Multi Round-Trip Requests（MRTR，SEP-2322）：服务端不主动推，而是在响应里说”我还需要输入”，客户端补齐信息后重发原请求。

// 第 1 轮请求：客户端发起 tools/call
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "delete_records",
    "arguments": { "ids": [1, 2, 3] }
  }
}

// 第 1 轮响应：服务端发现需要用户确认，返回 input_required
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "input_required",
    "inputRequests": [
      { "type": "elicitation", "message": "确认删除 3 条记录？", "id": "confirm_1" }
    ]
  }
}

// 第 2 轮请求：客户端拿到用户回答后，重发原请求并带上 inputResponses
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "delete_records",
    "arguments": { "ids": [1, 2, 3] },
    "inputResponses": [ { "id": "confirm_1", "value": true } ]
  }
}

配套地，所有响应现在都必须带 resultType 字段：普通结果是 "complete"，需要补输入的中间态是 "input_required"。为了兼容旧服务端，客户端 必须 把没有这个字段的结果当作 "complete" 处理。

服务端到客户端的变更通知也顺势重构了：旧的 GET 流端点和 resources/subscribe/unsubscribe 被一个 subscriptions/listen 长连 POST 流替代，客户端按通知类型逐一 opt-in（toolsListChanged、resourcesListChanged 等），不再是全量推送。

OAuth 2.1 加固：从”能跑就行”到”企业级合规”

授权是实现者花时间最多的地方。这版把 MCP 的授权彻底往主流 OAuth 2.1 / OIDC 生产实践上靠。核心一句话：远程 MCP Server 现在就是一个标准的 OAuth 2.1 Resource Server。

这张图景可以先用人话理解：客户端要访问远程 MCP Server，不能再靠”我认识你”这种隐式信任，而是要走一套标准登录链路——去授权服务器登录，拿 token，再拿 token 调 MCP Server。2026 版加固的重点，就是把这条链路里几个容易出错的地方补上。

加固点 用人话说 解决的坑
OAuth 2.1 + PKCE 登录和换 token 必须按现代 OAuth 2.1 流程走 不再自定义一套半吊子授权，对接 Entra/Okta 这类企业身份系统更顺
iss 校验 换 token 前，先确认这个授权码到底是谁发的 防止客户端把 A 授权服务器发的 code 拿去 B 授权服务器换 token，也就是 mix-up 攻击
application_type 注册客户端时说明自己是 Web、桌面还是 CLI 桌面/CLI 常用的 localhost 回调不会被当成异常 Web 回调拒掉
凭证绑定 issuer 每个授权服务器的凭证分开存，不能串用 换了授权服务器必须重新注册，避免一个地方拿到的凭证被带到另一个地方用
受保护资源元数据 MCP Server 明确告诉客户端：”我的授权服务器在这里” 客户端不用猜登录入口，可以自动发现该去哪里拿 token

这些名字看着吓人，但本质上都是在回答同一个问题：当 MCP Server 变成远程服务以后，客户端、资源服务器、授权服务器三方之间怎么互相信任。

DCR 被废弃，改用 CIMD

这个变化讲的是”客户端怎么登记身份”。

在 OAuth 里，客户端也要有身份。授权服务器需要知道：这个客户端叫什么、允许跳回哪些回调地址、是不是桌面应用、用什么方式认证。传统做法是 DCR（动态客户端注册）：客户端第一次来时，先向授权服务器提交一份注册申请，授权服务器给它发一个 client_id，并把这份注册信息存下来。

这在 MCP 里会变麻烦：一个 Cursor、Claude Desktop 这样的客户端，可能要连接很多 MCP Server；每个 Server 背后又可能接不同的授权服务器。如果都靠 DCR，就意味着客户端要到处动态注册，授权服务器也要维护一堆运行时写入的客户端记录。

CIMD 的思路更像”公开名片页”：客户端把自己的身份信息放在一个稳定的 HTTPS URL 上，然后直接把这个 URL 当作 client_id。授权服务器看到这个 URL，就去拉取里面的 JSON，校验通过后使用。

可以粗暴理解为：以前是”客户端到每个授权服务器那里现场填表注册”，现在是”客户端提前把自己的名片页放好，授权服务器需要时自己去看”。

{
  "client_id": "https://my-client.example.com/oauth/client-metadata.json",
  "client_name": "My MCP Client",
  "redirect_uris": ["http://localhost:3000/callback"],
  "application_type": "native"
}

这样授权服务器不一定要先写入一条注册记录，而是按需读取、校验、缓存这份元数据。它更适合 MCP”一个客户端、连接很多服务器”的开放生态。

需要注意：DCR 并没有立刻消失。如果某个授权服务器还不支持 CIMD，或者企业就是想要服务端登记、审计、审批那套流程，DCR 仍然可以作为兼容方案。只是新实现应该优先按 CIMD 设计。关于 CIMD 的完整字段格式，建议直接查官方客户端注册文档，这里我不逐字列字段，避免后续规范调整导致文章过时。

扩展框架与废弃策略

核心瘦身，能力进”扩展”

这版把一批”实验性/边缘”能力从核心协议里挪了出去，塞进了正式的扩展框架（Extensions）：

  • Tasks（io.modelcontextprotocol/tasks，SEP-2663）：长任务能力。从阻塞式的 tasks/result 改成轮询式 tasks/get + 新增 tasks/update（客户端向服务端补输入），去掉了 tasks/list。
  • MCP Apps：服务端渲染 UI。
  • EMA（Enterprise Managed Authorization）：企业托管授权。

思路是”核心保持精简、能力按自己的节奏演进”，扩展通过 ClientCapabilities / ServerCapabilities 里新增的 extensions 字段协商。

废弃了什么，多久移除

这版第一次有了正式的功能生命周期与废弃策略（SEP-2596）。简单说，就是给协议里的功能打三种状态标签：

  • Active：正常推荐使用。
  • Deprecated：还可以用，但不建议新项目继续采用，后面会移除。
  • Removed：已经从规范里移除，新实现不应该再支持。

关键点是：从 Deprecated 到 Removed 之间，规范要求有最短 12 个月的废弃窗口。也就是说，被标记废弃的东西至少还能再用一年，你可以从容规划升级，而不是被动救火。

本次进入废弃状态的：

  • Roots、Sampling、Logging（SEP-2577）——仍可用，但新实现不应再采用。官方给了迁移建议：用工具参数/资源 URI 传目录替代 Roots；直连 LLM 厂商 API 替代 Sampling；用 stderr 或 OpenTelemetry 替代 Logging。
  • HTTP+SSE 传输——从 2025-03-26 就软废弃了，这次正式归入 Deprecated，一年缓冲期后移除。

顺带还统一了错误码：资源未找到从 -32002 改成 -32602（对齐 JSON-RPC 的 Invalid Params），并划定 -32020 ~ -32099 为 MCP 规范专用区间。

迁移建议：这是一次破坏性升级

必须说清楚：2026-07-28 是向后不兼容的。也就是说，新版协议的客户端连不上旧版的服务端，反过来也一样。所以现实的迁移路径只有一条——同时支持新旧两版，靠版本协商过渡。

好在升级是 opt-in（选择性加入） 的：服务端可以同时声明支持 2025-11-25 和 2026-07-28，客户端在每个请求里选版本。只请求旧版的客户端行为完全不变，只有主动请求 2026-07-28 的客户端才会走新逻辑。

SDK 层面，官方第一梯队维护的四个 SDK（TypeScript、Python、Go、C#）当天就支持了新版规范，Rust SDK 提供 beta 支持。这里的”第一梯队”可以理解为官方优先保障、优先跟进规范变化的 SDK。官方也针对”依赖 Session ID”这类破坏性改动给了详细迁移说明。

  1. 先别急着删旧代码。服务端加上 2026-07-28 的支持，和旧版并存跑一段时间。
  2. 重点排查会话依赖。凡是靠 Mcp-Session-Id 维持的状态，改成”工具返回句柄、模型回传参数”的模式。
  3. 授权栈先自检。你的授权服务器现在返回 iss 吗？规范虽然当前只要求客户端校验”存在的 iss“，但明确警告未来版本会要求客户端拒绝没有 iss 的响应——现在不补，以后就是坑。
  4. 升级 SDK 而不是手写协议。协议细节这版改动很大，跟着官方 SDK 的迁移指南走，比自己对着 changelog 手搓靠谱得多。

我的看法

把这次更新连起来看，我的感受是：它不是在给 MCP 加更多花哨能力，而是在把 MCP 改造成一个更像标准 Web 服务的东西。

无状态核心解决的是云上横向扩展；Mcp-Method / Mcp-Name 让网关、限流、WAF 能看懂请求；ttlMs / cacheScope 让工具列表和资源结果能被缓存；MRTR 把”中途问用户一句”从隐式会话改成显式多轮请求；OAuth 2.1、iss 校验、CIMD 则是把远程 MCP Server 接进现有企业身份体系。

所以我觉得这次变化的重点不是”协议更酷了”，而是”协议更普通了”。普通到可以被负载均衡、缓存、网关、IAM、审计系统这些成熟基础设施接住。对想在生产环境大规模铺 Agent 的团队来说，这反而是最重要的信号。

小结

MCP 2026-07-28 核心要点：

  1. 无状态核心是主角：删掉 initialize 握手和 Mcp-Session-Id，每个请求自带协议版本、身份和能力
  2. 能力发现解耦：server/discover 由服务端必须实现、客户端可选调用，不再是通信前置门槛
  3. 状态改由应用管：服务端铸造显式句柄，模型当参数回传，比藏在传输层更可控
  4. 配套三件套：Mcp-Method/Mcp-Name 头路由、ttlMs/cacheScope 可缓存列表、MRTR 无状态交互
  5. OAuth 2.1 加固：强制 OAuth 2.1、RFC 9207 iss 校验、凭证绑定 issuer，DCR 废弃转向 CIMD
  6. 核心瘦身：Tasks/MCP Apps/EMA 归入扩展框架，Roots/Sampling/Logging 与 HTTP+SSE 进入 12 个月废弃窗口
  7. 这是破坏性升级但 opt-in：新旧版本靠协商共存，迁移重点是排查会话依赖和授权合规
