Loop Engineering：AI工作范式的新一层

发表于2026|更新于2026|AI相关
|字数总计:4.7k|阅读时长:15分钟

前言：如果说 Prompt Engineering 解决的是”怎么跟 AI 说”，Context Engineering 解决的是”让 AI 看什么”，Harness Engineering 解决的是”怎么让一次 AI 执行可靠”，那么 Loop Engineering 解决的就是：怎么让 AI 在无人反复催促的情况下，持续发现任务、执行任务、验证结果，并在该停的时候停下来。

Loop Engineering 为什么突然火了

最近 Loop Engineering 这个词开始被频繁讨论，比较有代表性的是 Addy Osmani 在 2026 年 6 月写的 Loop Engineering，里面有一句话很直白：

Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead.

翻译成人话就是：

以前是你一轮一轮地提示 AI，现在是你设计一个系统，让这个系统去提示 AI。

这个变化不只是”把 prompt 写长一点”，而是工作方式变了。

过去我们使用 AI 编程工具，大概是这样：

我：帮我修这个 bug
AI：给你改好了
我：这里不对，继续改
AI：我再试试
我：跑一下测试
AI：测试失败了，我继续修
...

你一直在旁边当调度员、质检员、上下文补充员、停止按钮。

Loop Engineering 想解决的问题是：这些重复的调度动作，能不能系统化？

比如每天早上自动检查 CI 失败、自动归类 issue、自动让一个 Agent 尝试修复、再让另一个 Agent 审查、最后只把需要人判断的结果交给你。

这就从”我会写 prompt”变成了”我会设计 AI 工作循环”。

什么是 Loop Engineering

我的定义：

Loop Engineering：围绕 AI Agent 设计一个可重复运行的工作循环，让系统能够自动发现任务、分配上下文、调用工具、验证结果、保存状态，并在满足条件或需要人类判断时停止。

一个最小的 Loop 通常长这样：

┌────────────┐
│  发现任务   │  从 CI、Issue、PR、日志、队列中发现待处理事项
└─────┬──────┘
      │
      ▼
┌────────────┐
│  任务交接   │  打包目标、上下文、约束、工作区
└─────┬──────┘
      │
      ▼
┌────────────┐
│  Agent执行  │  修改代码、写文档、分析失败、生成方案
└─────┬──────┘
      │
      ▼
┌────────────┐
│  独立验证   │  测试、lint、规则检查、另一个 Agent Review
└─────┬──────┘
      │
      ▼
┌────────────┐
│  保存状态   │  写入 PR、Issue、STATE.md、日志、看板
└─────┬──────┘
      │
      ▼
┌────────────┐
│  判断停止   │  完成 / 重试 / 升级给人 / 下次继续
└────────────┘

重点不是”循环”两个字，而是这个循环必须有边界、证据和刹车。

否则它就不是 Loop Engineering，而是一个昂贵的死循环。

它到底解决什么问题

Loop Engineering 主要解决四类问题。

问题一：人工提示太碎

很多 AI 工作并不是难在一次 prompt，而是难在中间要不断接力：

  1. 先找问题
  2. 再判断优先级
  3. 再补上下文
  4. 再让 AI 改
  5. 再跑测试
  6. 再根据失败结果继续改
  7. 最后整理成 PR 或报告

这中间有大量”机械但不能完全省略”的动作。人一直做这些动作，注意力会被切碎。

Loop Engineering 把这部分动作变成系统流程，让人只处理真正需要判断的节点。

问题二：Agent 长任务容易失控

Agent 一旦跑得久，就会出现几个典型问题：

现象 原因 Loop Engineering 的处理方式
越改越偏 每轮上下文都在变化，目标被稀释 用明确的 goal 和 stop condition 约束
自己说自己完成 生成者天然倾向于认可自己的结果 拆分 implementer 和 verifier
反复重试烧 token 没有预算上限和失败策略 设置 max iteration、timeout、cost cap
下次运行忘记上次结论 记忆只存在对话窗口里 写入 STATE.md、Issue、PR、数据库

我的理解是：Loop Engineering 本质上是在给 Agent 加”项目管理能力”和”质量控制能力”。

它不是让 AI 更聪明，而是让 AI 的工作过程更可控。

问题三：一次运行可靠，不代表持续运行可靠

Harness Engineering 关心的是一次 Agent 执行是否可靠：

给它什么工具？
有哪些权限？
怎么处理失败？
怎么验证结果？
怎么记录日志？

但 Loop Engineering 关心的是多次执行之间的关系：

什么时候再次运行？
上次做了什么？
这次要不要继续？
多个 Agent 会不会互相覆盖？
结果要不要进入人工审批？
失败三次后是继续烧钱，还是暂停？

这就是它比 Harness Engineering 更高一层的原因。

问题四：AI 产出越来越多，人类 Review 跟不上

这是我觉得最现实的问题。

AI 编程工具越来越强之后，瓶颈不再是”能不能生成代码”，而是：

生成出来的东西，谁来确认它真的对？

Loop Engineering 不是取消 Review，而是把 Review 变成系统的一部分：

  • 简单规则交给测试、lint、类型检查
  • 结构性问题交给 verifier Agent
  • 高风险决策交给人
  • 所有运行都留下日志和状态

这比”AI 改完你看一眼”要稳得多。

从 Prompt、Context、Harness 到 Loop 的演进关系

这几个词很容易混在一起。我的看法是：它们不是替代关系，而是逐层叠加。

层级 解决的问题 核心问题 典型产物
Prompt Engineering 单轮怎么问 我该怎么表达任务？ system prompt、user prompt、few-shot 示例
Context Engineering 单轮看什么 模型现在应该知道什么？ RAG、上下文压缩、文件选择、工具结果
Harness Engineering 单次怎么跑稳 Agent 这一次执行如何可靠？ 工具权限、沙箱、日志、错误恢复、验收条件
Loop Engineering 多轮怎么持续 系统如何自动决定下一步，并安全停止？ 调度、状态、隔离、验证器、人工闸口

可以用一个更直观的图表示：

┌──────────────────────────────────────────────┐
│ Loop Engineering                              │
│ 什么时候跑、跑几次、谁验证、何时停止、状态存哪 │
│  ┌────────────────────────────────────────┐  │
│  │ Harness Engineering                     │  │
│  │ 工具、权限、沙箱、日志、错误恢复、验收条件 │  │
│  │  ┌──────────────────────────────────┐  │  │
│  │  │ Context Engineering                │  │  │
│  │  │ 文件、知识库、历史、工具输出、记忆     │  │  │
│  │  │  ┌────────────────────────────┐  │  │  │
│  │  │  │ Prompt Engineering          │  │  │  │
│  │  │  │ 指令、角色、约束、输出格式      │  │  │  │
│  │  │  └────────────────────────────┘  │  │  │
│  │  └──────────────────────────────────┘  │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘

一句话总结：

Prompt 是一句话，Context 是这句话周围的信息，Harness 是这句话的一次可靠执行环境，Loop 是让这个执行环境持续运转的控制系统。

所以不要问”Loop Engineering 会不会取代 Prompt Engineering”。

不会。

它只是把 prompt、context、harness 都变成了循环系统里的零件。

一个 Loop 需要哪些核心组件

结合 Addy Osmani 的文章和 Loop Engineering Guide 的总结，一个成熟 Loop 通常有六个组件。

1. Automations：让循环自己醒来

没有触发器，就只是一次手动运行。

触发方式可以是：

  • 定时任务：每天早上扫描 CI 失败
  • Webhook：有新 issue 时触发分类
  • CI 事件：测试失败时触发诊断
  • 队列消息：有新工单时触发处理
  • 人工按钮：先从半自动开始

我的建议：刚开始不要一上来就做全自动，先做”自动发现 + 人工确认”。

2. Worktree / Sandbox：隔离执行环境

多个 Agent 同时改一个仓库，最怕互相踩文件。

所以 Loop 需要隔离：

main repo
  ├── worktree/fix-ci-001
  ├── worktree/update-docs-002
  └── worktree/triage-issue-003

每个任务一个独立分支、独立工作区，最后通过 PR 或 diff 汇总。这其实就是把人类团队里的”分支协作”搬给 Agent 用。

3. Skills：沉淀可复用经验

如果每次都在 prompt 里写：

这个项目用 pnpm
不要改 package-lock
测试命令是 pnpm test
不要绕过 lint
提交前要看 docs

那很快就会变成一坨没人维护的超级 prompt。

Skills 的价值是：把稳定的项目知识、流程规范、判断标准沉淀成外部文件，让 Loop 每次运行都能读取。

我的理解是：Skill 是给 Agent 看的团队 SOP。

4. Connectors / MCP：连接真实系统

Loop 如果只能读本地文件，能做的事很有限。

要处理真实工作，通常要接：

  • GitHub / GitLab：读 issue、开 PR、查 CI
  • Linear / Jira：同步任务状态
  • Slack / 飞书：通知负责人
  • 数据库 / 日志平台：查询线上异常
  • 文档系统：读取业务规则

这里 MCP 的意义就出来了：它让 Agent 能通过统一协议接入外部工具，而不是每个工具都手写一套胶水代码。

5. Sub-agents：生成者和验证者分离

这是 Loop Engineering 里我最认同的一点：

写代码的 Agent，不应该是唯一判断代码是否完成的 Agent。

可以拆成：

角色 职责
Explorer 只读探索，找上下文和风险
Implementer 动手修改，尽量小步提交
Verifier 跑测试、看 diff、挑战假设
Reviewer 从工程质量、安全、可维护性角度审查

这不是为了炫技，而是为了避免”自我评分”。

AI 很容易把自己的输出解释成合理的，尤其是长任务后半段。独立 verifier 是 Loop 的刹车。

6. Memory / State：把记忆放到对话外面

长循环不能只依赖上下文窗口。

因为窗口会满，摘要会丢细节，Agent 也可能重启。稳定的做法是把状态写到外部：

# STATE.md

## Current Goal
修复最近 24 小时内 main 分支上失败的 CI

## Tried
- 2026-07-05 09:00：发现 test/auth.spec.ts 失败
- 2026-07-05 09:10：尝试修复 token 过期判断，测试仍失败

## Verified
- pnpm lint 通过
- pnpm test:auth 未通过

## Next
- 检查 mock time 与真实 Date.now 的差异

这类状态文件看起来很土，但很关键。

对长任务来说，模型会忘，文件不会忘。

最小可运行示例：手写一个简化 Loop

下面这个例子不依赖真实大模型，只模拟 Loop 的结构。它能跑起来，重点是看清楚”发现任务 → 执行 → 验证 → 保存状态 → 判断停止”这条线。

环境要求：

  • Node.js 20+
  • 不需要安装第三方依赖

新建 mini-loop.mjs：

import { readFile, writeFile } from 'node:fs/promises';

const STATE_FILE = './loop-state.json';
const MAX_ITERATIONS = 3;

async function loadState() {
  try {
    const raw = await readFile(STATE_FILE, 'utf8');
    return JSON.parse(raw);
  } catch {
    return { runs: [], solvedTaskIds: [] };
  }
}

async function saveState(state) {
  await writeFile(STATE_FILE, JSON.stringify(state, null, 2));
}

function discoverTasks(state) {
  const tasks = [
    { id: 'ci-001', title: 'auth test failed', risk: 'medium' },
    { id: 'doc-002', title: 'README missing setup step', risk: 'low' }
  ];

  return tasks.filter((task) => !state.solvedTaskIds.includes(task.id));
}

function implementTask(task) {
  // 真实系统里这里会调用 coding agent，并在隔离 worktree 中修改代码
  if (task.risk === 'low') {
    return { taskId: task.id, changedFiles: ['README.md'], result: 'fixed' };
  }

  return { taskId: task.id, changedFiles: ['auth.test.js'], result: 'needs-review' };
}

function verifyResult(result) {
  // 真实系统里这里会跑测试、lint，或者交给另一个 verifier agent
  return result.result === 'fixed';
}

async function runLoop() {
  const state = await loadState();

  for (let i = 0; i < MAX_ITERATIONS; i++) {
    const [task] = discoverTasks(state);

    if (!task) {
      console.log('No pending tasks. Loop stopped.');
      break;
    }

    const result = implementTask(task);
    const passed = verifyResult(result);

    state.runs.push({
      time: new Date().toISOString(),
      task,
      result,
      passed
    });

    if (passed) {
      state.solvedTaskIds.push(task.id);
      console.log(`Task ${task.id} passed verification.`);
    } else {
      console.log(`Task ${task.id} needs human review. Loop paused.`);
      await saveState(state);
      break;
    }

    await saveState(state);
  }
}

runLoop().catch((error) => {
  console.error(error);
  process.exitCode = 1;
});

运行：

node mini-loop.mjs

第一次可能输出：

Task ci-001 needs human review. Loop paused.

这很符合真实情况：不是所有任务都应该自动继续。高风险任务应该停下来，让人判断。

这个例子虽然简单，但已经包含了 Loop Engineering 的几个核心点：

  • 有任务发现
  • 有最大迭代次数
  • 有状态文件
  • 有验证步骤
  • 有人工接管点
  • 有明确停止条件

真正接入大模型时，不是把这些控制逻辑删掉，而是把 implementTask 和 verifyResult 替换成 Agent 调用。

什么时候应该接入 Loop Engineering

我的判断：不要因为概念火就急着上 Loop。它适合的是重复、可验证、有明确边界的工作。

适合接入的场景

场景 为什么适合
CI 失败诊断 输入明确，验证方式明确，失败可回滚
PR babysit 任务重复，状态变化频繁，适合自动跟进
Issue 初筛 分类、去重、补充上下文可以半自动
依赖升级 可以用测试和 lockfile diff 做验证
文档同步 风险低，容易人工 Review
Release note 草稿 AI 擅长总结，人类负责最终判断

这些场景的共同点是：系统知道去哪找任务，也知道怎么算阶段性完成。

不适合接入的场景

场景 为什么不适合
产品方向决策 目标模糊，无法自动验证
高风险生产操作 错了代价太大，必须强人工控制
大规模架构重构 影响面广，长期上下文复杂
安全敏感写操作 权限边界和审计要求更高
需求还没想清楚 Loop 会把模糊需求自动放大

这里有个简单判断标准：

如果你没法写出清晰的停止条件，就先不要做 Loop。

比如”把系统优化一下”就不适合。

“把 pnpm test:auth 修到通过，不能修改鉴权公共接口，最多尝试 3 轮，失败后输出诊断报告”才适合。

Loop Engineering 的成本是多少

Loop Engineering 的成本不能只看模型 token。它有四类成本。

1. Token 成本

Loop 一旦自动化，token 消耗会明显上升：

  • 每轮都要读取上下文
  • 失败后会重试
  • verifier 也要单独消耗
  • 多 Agent 并行会放大消耗
  • 长任务还要做总结和状态维护

所以成本控制必须前置：

max_iterations: 3
timeout_minutes: 20
max_changed_files: 5
max_daily_runs: 10
expensive_model_only_for: verifier
stop_on_repeated_failure: true

我的建议是：便宜模型做发现和分类，强模型做实现和关键验证。

不要让最贵的模型每天扫一堆低价值 issue。

2. Review 成本

Loop 会增加产出，但人的 Review 能力不会自动增加。

如果每天自动开 20 个 PR，而团队只能认真看 3 个，那么剩下 17 个就是新的债务。

所以 Loop 的目标不是”多产出”，而是”把值得看的东西筛出来”。

一个健康的 Loop 应该减少人的低价值检查，而不是制造更多待办。

3. 工程接入成本

你需要准备：

  • 任务来源：CI、Issue、日志、队列
  • 运行环境：worktree、容器、沙箱
  • 工具权限：读写边界、审批策略
  • 验证手段：测试、lint、静态分析、规则检查
  • 状态存储：文件、数据库、看板、Issue comment
  • 观测能力：日志、运行摘要、失败原因

这些都是实打实的工程成本。

所以小团队不要一上来追求”自动修复一切”，先做一个很窄的 Loop，比如”每天总结失败 CI 并给出诊断建议”。

4. 理解成本

这是最容易被低估的。

当 Loop 不断替你改代码、写文档、整理任务，你可能会逐渐不理解系统为什么变成现在这样。

Addy Osmani 在文章里也提醒过类似风险：Loop 不会替你承担工程责任，你仍然要确认它产出的东西能不能上线。

我的观点很直接：

Loop 可以替你做重复劳动，但不能替你拥有判断力。

如果你用它来加速自己理解的工作，它是杠杆。

如果你用它来逃避理解，它就是风险放大器。

一个可落地的接入顺序

我会按这个顺序接入，而不是一步到位：

第一步：只读 Loop

先让 Loop 做只读任务：

  • 扫描 CI 失败
  • 总结 PR 阻塞点
  • 归类 issue
  • 生成每日风险摘要

这一步的目标不是自动修复，而是验证两个问题：

  1. 它发现的问题是否有价值
  2. 它的总结是否可信

第二步：半自动 Loop

让 Loop 可以生成 patch 或 PR，但不能自动合并：

发现问题 → 生成修复 → 跑测试 → 开 PR → 等人 Review

这一步要重点看：

  • PR 是否足够小
  • 测试是否真的覆盖问题
  • 失败时是否会停
  • 说明是否让人看得懂

第三步：低风险自动化

只对低风险任务放开自动化：

  • 文档修正
  • 拼写修复
  • release note 草稿
  • 非破坏性依赖升级
  • 自动补充测试报告

注意，即使是低风险，也建议保留审计日志和回滚路径。

第四步：高价值专用 Loop

最后再做更强的专用 Loop，比如：

  • CI sweeper
  • PR babysitter
  • dependency sweeper
  • changelog drafter
  • flaky test detector

这类 Loop 不追求通用，而是追求稳定、窄、可验证。

我的实战判断

Loop Engineering 不是每个团队马上都需要。

如果你现在还处在”偶尔让 AI 帮我写点代码”阶段，先把 Prompt 和 Context 打牢。

如果你已经在用 Agent 做真实开发，那就该补 Harness：权限、测试、日志、边界、验收条件。

如果你发现自己每天都在重复提示 Agent 做同一类事，比如：

帮我看下今天 CI 为什么挂了
帮我总结这个 PR 还差什么
帮我扫一下新 issue
帮我根据失败日志给出修复建议
帮我再跑一遍测试并继续修

这时候就可以考虑 Loop Engineering。

我的选择标准很简单：

一个流程，如果你已经手动重复做了 5 次以上，而且每次都有相似的输入、相似的判断标准、相似的停止条件，就值得设计成 Loop。

但如果一个任务本身还说不清目标，先别 Loop。你会得到一个非常勤奋、非常昂贵、非常自信的混乱制造机。

小结

  1. Loop Engineering 解决的是”让系统自动提示 Agent 并安全循环”的问题，不是把 prompt 写得更长。
  2. Prompt、Context、Harness、Loop 是逐层叠加关系，Loop 位于更外层，负责调度、状态、验证和停止。
  3. 一个可用 Loop 至少需要触发器、隔离环境、技能沉淀、工具连接、独立验证和持久化状态。
  4. 适合接入 Loop 的任务必须重复、边界清晰、可验证，不适合模糊目标和高风险决策。
  5. Loop 的成本包括 token、Review、工程接入和理解成本，最危险的是产出变多但判断力变少。
  6. 最稳的接入路径是从只读 Loop 开始，再到半自动 PR，最后只对低风险、高重复任务开放更强自动化。
