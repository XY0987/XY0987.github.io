Docker 从入门到实战精通：镜像、容器、网络、数据卷和 Compose 一次讲清楚

发表于2026|更新于2026|全栈
|字数总计:6.5k|阅读时长:25分钟

前言：Docker 不是“会几条命令”就算掌握，也不是把项目塞进镜像就结束。真正有用的 Docker 能力，是你能稳定地构建镜像、运行服务、定位问题、管理数据，并且知道生产环境里哪些做法危险。

学 Docker 时，最容易混淆的是三个东西：镜像、容器、数据卷。我的理解是：

  • image 是安装包；
  • container 是运行中的进程；
  • volume 是不跟着容器一起消失的数据；
  • Dockerfile 是制作安装包的说明书；
  • compose.yaml 是描述一组服务的配置文件，docker compose 是启动和管理它们的命令。

这篇我按这个思路讲，从安装开始，一直讲到 Dockerfile、网络、数据卷、Compose、调试和最佳实践。所有案例都是真实可运行的，不写伪代码。

先安装 Docker

Docker 的安装方式和操作系统强相关，不能只给一条命令。我的建议是：个人电脑优先装 Docker Desktop，Linux 服务器优先装 Docker Engine。

本文示例在下面环境验证过思路，版本不要求完全一致：

工具 建议版本 说明
Docker Engine / Docker Desktop 24+ / 25+ / 26+ 均可 本文命令都是常规能力
Docker Compose v2 使用 docker compose，不是旧版 docker-compose
Node.js 镜像 node:22-alpine 示例运行在容器里，本机不一定要装 Node.js
PostgreSQL 镜像 postgres:16-alpine Compose 实战会用到

这里顺手说一下 Docker 里几个新旧写法的差异，避免你看旧教程时懵：

旧写法 现在更推荐 说明
docker-compose up docker compose up Compose v1 是独立命令，Compose v2 集成到了 Docker CLI 里
docker-compose.yml compose.yaml 旧文件名仍然能用，但现在官方更推荐 compose.yaml
version: "3" 通常不写 version 新版 Compose Specification 已经不太需要这个字段
旧版 docker build 构建器 BuildKit / docker buildx 新版 Docker 默认更多使用 BuildKit，缓存和多平台构建能力更强

本文统一使用新写法：compose.yaml + docker compose。

macOS 安装

macOS 推荐安装 Docker Desktop。最省事的方式是直接去 Docker 官方页面下载安装包，然后拖到 Applications 目录：https://docs.docker.com/desktop/setup/install/mac-install/。

安装前先确认两个信息：

sw_vers -productVersion
uname -m
  • sw_vers -productVersion：查看 macOS 版本；
  • uname -m：查看芯片架构，arm64 一般是 Apple silicon，x86_64 一般是 Intel。

Docker Desktop 官方支持策略是：支持当前 macOS 主版本以及前两个主版本。所以如果你安装时报：

Error: This software does not run on macOS versions other than Sonoma.

或者类似“系统版本不支持”的错误，通常不是命令写错了，而是 Docker Desktop 安装包和你的 macOS 版本不匹配。

解决思路很直接：

  1. 先确认自己是 Apple silicon 还是 Intel，下载对应架构的安装包；
  2. 如果 macOS 版本太旧，优先升级 macOS；
  3. 如果暂时不能升级，就去 Docker Desktop release notes 找支持当前系统的旧版本安装包；
  4. 不建议在旧系统上直接用 brew install --cask docker，因为 Homebrew 往往会拉最新版本，最新版本可能已经不支持你的系统。

如果你已经下载了匹配系统和芯片的 Docker.dmg，可以用官方命令行方式安装：

sudo hdiutil attach Docker.dmg
sudo /Volumes/Docker/Docker.app/Contents/MacOS/install --accept-license
sudo hdiutil detach /Volumes/Docker
open -a Docker

如果你的 macOS 版本是受支持的，而且习惯用 Homebrew，也可以这样装：

brew install --cask docker
open -a Docker

这里要说明一下：brew install --cask docker 本质上不是安装一个纯命令行版 Docker，而是通过 Homebrew 下载并安装 Docker Desktop。所以它和上面的 Docker.dmg 安装方式最终装的是同一个东西，只是下载和安装入口不同。

Windows 安装

Windows 推荐使用 Docker Desktop + WSL 2。先确认 WSL：

wsl --version

如果没有安装 WSL，可以用管理员身份打开 PowerShell：

wsl --install
wsl --update

然后从 Docker 官方页面下载 Docker Desktop Installer.exe：https://docs.docker.com/desktop/setup/install/windows-install/，在安装包所在目录执行：

Start-Process 'Docker Desktop Installer.exe' -Wait -ArgumentList 'install', '--user'

安装完成后手动启动 Docker Desktop。大多数前端、后端、全栈开发场景，默认使用 Linux containers 就够了，不需要切到 Windows containers。

Linux 安装，以 Ubuntu 为例

Linux 发行版很多，安装命令不完全一样。这里以 Ubuntu 为例，使用 Docker 官方 apt 仓库安装 Docker Engine：

sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

启动并查看 Docker 服务：

sudo systemctl start docker
sudo systemctl status docker

验证安装：

sudo docker run --rm hello-world

如果你不想每次都写 sudo，可以把当前用户加入 docker 组：

sudo usermod -aG docker $USER
newgrp docker

这一步不是必须的，而且加入 docker 组意味着这个用户基本拥有较高的 Docker 控制权限，服务器上要谨慎。

先把 Docker 跑起来

先确认 Docker 可用：

docker version
docker compose version

跑第一个容器：

docker run --rm hello-world

hello-world 是 Docker 官方提供的测试镜像。这个命令会拉取镜像、创建容器、打印欢迎信息，然后因为加了 --rm，容器退出后会被自动删除。

如果能看到 Docker 的欢迎信息，说明基础环境没问题。

再跑一个更真实的 Web 服务：

docker run --rm -d --name nginx-demo -p 8080:80 nginx:1.27-alpine
curl http://localhost:8080
docker stop nginx-demo

这里有几个关键点：

参数 含义
--rm 容器停止后自动删除容器记录
-d 后台运行
--name nginx-demo 给容器起名字，方便后续操作
-p 8080:80 把宿主机 8080 映射到容器内 80
nginx:1.27-alpine 使用指定版本镜像，不用飘忽不定的 latest

很多人第一次卡住都是因为端口理解错了：-p 8080:80 左边是你电脑上的端口，右边是容器里的端口。

镜像和容器到底是什么

我的理解是：镜像负责分发，容器负责运行。

┌──────────────┐   docker run    ┌────────────────┐
│    Image     │ ──────────────> │   Container    │
│  静态模板     │                  │   运行实例      │
└──────────────┘                  └────────────────┘
       │                                  │
       │ docker pull/build                │ 进程、网络、文件系统
       ▼                                  ▼
  可以保存和推送                         可以启动、停止、删除

用命令看更直观：

docker pull nginx:1.27-alpine

docker image ls nginx

docker run -d --name web -p 8080:80 nginx:1.27-alpine

docker ps

docker stop web
docker rm web

注意：删除容器不会删除镜像。

docker image ls nginx

这也是 Docker 很重要的设计：镜像像模板，可以被反复创建容器；容器像进程，用完可以删。

先认识 Dockerfile

前面我们一直在用别人做好的镜像，比如 nginx:1.27-alpine、hello-world。但真实项目里，我们最终要把自己的代码做成镜像，这时候就需要 Dockerfile。

我的理解是：Dockerfile 就是镜像的制作说明书。你把基础镜像、工作目录、依赖安装、代码复制、启动命令写进去，Docker 按顺序执行，最后生成一个可以运行的镜像。

先看一个最小结构，暂时不用纠结每条指令的细节，后面会专门拆：

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "src/server.js"]

现在先记住一件事：Dockerfile 是按顺序执行的，前一行的结果会影响后一行。理解了这个，再看 Docker 的分层机制就顺很多。

再理解 Docker 的分层机制

Docker 镜像不是一个大压缩包，而是由 Dockerfile 的多条指令一层一层叠起来的。

┌──────────────────────────┐
│ 应用代码层 COPY . .       │
├──────────────────────────┤
│ 依赖安装层 RUN npm ci     │
├──────────────────────────┤
│ 工作目录层 WORKDIR /app   │
├──────────────────────────┤
│ 基础镜像层 FROM node      │
└──────────────────────────┘

这就是为什么 Dockerfile 的顺序很重要。变化少的东西放前面，变化多的代码放后面，构建缓存才能发挥作用。

反面案例：

# ❌ 反面案例：代码一变，npm install 的缓存也失效
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm install --omit=dev
CMD ["node", "src/server.js"]

这里的 COPY . . 可以理解成：把执行 docker build -t my-app . 时最后那个 . 指向的构建目录内容，复制到镜像当前工作目录。因为前面写了 WORKDIR /app，所以它基本等价于“把当前项目目录里的内容复制到镜像的 /app 目录”。但 .dockerignore 里排除的文件不会被复制。

这段的问题是：先 COPY . .，再安装依赖。只要你改一行业务代码，Docker 就会认为 COPY . . 这一层变了，后面的 RUN npm install 也要重新执行。

正面案例：

# ✅ 正面案例：先复制依赖声明，再安装依赖，最后复制业务代码
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "src/server.js"]

这段的好处是：只要 package.json 和 package-lock.json 没变，依赖安装这一层就可以复用缓存。你改业务代码时，一般只会重新执行后面的 COPY . .。

这不是洁癖，是构建速度问题。项目大了以后，一个错误的 COPY . . 顺序，可能让每次构建多等几分钟。

用 Dockerfile 打包一个 Node.js 服务

下面做一个最小但真实的 Node.js HTTP 服务。它不依赖 Express，只用 Node.js 内置模块，避免把重点放到框架上。

新建目录：

mkdir docker-node-demo
cd docker-node-demo
mkdir src

创建 package.json：

{
  "name": "docker-node-demo",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node src/server.js"
  },
  "dependencies": {}
}

创建 src/server.js：

import http from 'node:http';
import os from 'node:os';

const port = Number(process.env.PORT || 3000);

const server = http.createServer((req, res) => {
  if (req.url === '/health') {
    res.writeHead(200, { 'content-type': 'application/json; charset=utf-8' });
    res.end(JSON.stringify({ status: 'ok' }));
    return;
  }

  res.writeHead(200, { 'content-type': 'application/json; charset=utf-8' });
  res.end(JSON.stringify({
    message: 'Hello Docker',
    hostname: os.hostname(),
    node: process.version,
    time: new Date().toISOString()
  }, null, 2));
});

server.listen(port, '0.0.0.0', () => {
  console.log(`server is running at http://0.0.0.0:${port}`);
});

创建 .dockerignore：

.git
node_modules
npm-debug.log
Dockerfile
compose.yaml
*.md
.env

创建 Dockerfile：

FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm install --omit=dev

COPY src ./src

ENV NODE_ENV=production
ENV PORT=3000

EXPOSE 3000

USER node

CMD ["node", "src/server.js"]

构建镜像：

docker build -t docker-node-demo:1.0.0 .

运行容器：

docker run --rm -d --name node-demo -p 3000:3000 docker-node-demo:1.0.0
curl http://localhost:3000
curl http://localhost:3000/health
docker logs node-demo
docker stop node-demo

预期你能看到类似输出：

{
  "message": "Hello Docker",
  "hostname": "8f7f0c6b0d6a",
  "node": "v22.x.x",
  "time": "2026-05-16T10:00:00.000Z"
}

这里有一个很容易踩的坑：Node 服务必须监听 0.0.0.0，不能只监听 localhost。

现象是容器正常启动，日志也没报错，但是宿主机访问不到。

原因是：

  • localhost 在容器里指容器自己；
  • 宿主机通过端口映射访问容器时，需要服务监听容器网卡；
  • 所以容器内 Web 服务一般监听 0.0.0.0。

Dockerfile 指令怎么理解

常用指令不用死记，按职责分就很好理解。

指令 作用 我的建议
FROM 指定基础镜像 生产环境不要用 latest
WORKDIR 设置工作目录 用绝对路径，比如 /app
COPY 复制文件到镜像 普通复制优先用它
RUN 构建阶段执行命令 安装依赖、编译代码
ENV 设置环境变量 不要放密码和 Token
EXPOSE 声明容器内端口 只是声明，不会自动映射
USER 指定运行用户 尽量不要用 root 跑应用
CMD 容器默认启动命令 推荐 exec 格式数组

CMD 推荐写成：

CMD ["node", "src/server.js"]

不推荐写成：

CMD node src/server.js

数组形式对 Unix 信号处理更友好，容器停止时应用更容易正确收到 SIGTERM。

端口映射和容器网络

Docker 默认会给容器创建一个隔离网络。容器里监听的端口，不等于宿主机能直接访问。

宿主机 localhost:3000
        │
        │ -p 3000:3000
        ▼
容器 node-demo:3000
        │
        ▼
Node.js 进程监听 0.0.0.0:3000

下面用几条命令模拟一个常见场景：创建一个自定义网络，把 nginx 容器放进去，再启动另一个临时容器访问它。

# 查看当前有哪些 Docker 网络
docker network ls

# 创建一个名为 app-net 的自定义网络
docker network create app-net

# 启动一个 nginx 容器，并加入 app-net 网络
docker run --rm -d --name web1 --network app-net nginx:1.27-alpine

# 启动一个临时 busybox 容器，也加入 app-net，然后通过容器名 web1 访问 nginx
docker run --rm --network app-net busybox:1.36 wget -qO- http://web1

# 停止 nginx 容器，如果前面加了 --rm，停止后容器会自动删除
docker stop web1

# 删除刚才创建的 app-net 网络
docker network rm app-net

这个例子的作用是验证一件事：同一个 Docker network 里的容器，可以用容器名互相访问。

这就是后面 Compose 里应用连接数据库时，可以写 postgres:5432 的原因。postgres 不是公网域名，而是 Compose 网络里的服务名。

数据卷：别把重要数据写进容器里

容器是临时的，数据不能跟着容器走。数据库、上传文件、缓存持久化，都应该使用 volume。

先看一个最小示例：

docker volume create demo-data

docker run --rm \
  --name volume-writer \
  -v demo-data:/data \
  busybox:1.36 \
  sh -c "date > /data/time.txt && cat /data/time.txt"

docker run --rm \
  --name volume-reader \
  -v demo-data:/data \
  busybox:1.36 \
  cat /data/time.txt

你会发现第一个容器已经删了，但第二个容器还能读到 time.txt。因为数据存在 demo-data 这个 volume 里，不存在容器里。

查看 volume：

docker volume ls
docker volume inspect demo-data

清理示例数据：

docker volume rm demo-data

volume 和 bind mount 的区别也很实用：

方式 写法 适合场景
volume -v demo-data:/data 数据库数据、上传文件、需要 Docker 管理的数据
bind mount -v $(pwd):/app 本地开发，把宿主机代码挂进容器
tmpfs --tmpfs /tmp 临时数据，不希望落盘

我的建议：数据库优先用 volume，本地开发代码同步用 bind mount。

Compose：一条命令启动完整应用

真实项目很少只有一个容器。通常至少有：

  • 应用服务；
  • 数据库；
  • Redis；
  • Nginx；
  • 后台任务。

如果全部用 docker run，命令会越来越长。Compose 的价值就是把这些配置写到一个文件里。

下面做一个真实可运行的 Node.js + PostgreSQL 访问计数服务。

目录结构：

docker-compose-demo/
├── compose.yaml
├── Dockerfile
├── package.json
├── package-lock.json
└── src/
    └── server.js

创建目录：

mkdir docker-compose-demo
cd docker-compose-demo
mkdir src

创建 package.json：

{
  "name": "docker-compose-demo",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node src/server.js"
  },
  "dependencies": {
    "pg": "8.11.3"
  }
}

生成 lock 文件：

npm install --package-lock-only

如果你本机没有 Node.js，也可以先把 Dockerfile 里的 npm ci --omit=dev 改成 npm install --omit=dev，这样不需要提前生成 package-lock.json。真实项目我更建议保留 lock 文件，然后用 npm ci。

创建 src/server.js：

import http from 'node:http';
import { Pool } from 'pg';

const port = Number(process.env.PORT || 3000);
const databaseUrl = process.env.DATABASE_URL;

if (!databaseUrl) {
  throw new Error('DATABASE_URL is required');
}

const pool = new Pool({ connectionString: databaseUrl });

async function initDatabase() {
  await pool.query(`
    CREATE TABLE IF NOT EXISTS visits (
      id SERIAL PRIMARY KEY,
      created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
    )
  `);
}

async function addVisit() {
  await pool.query('INSERT INTO visits DEFAULT VALUES');
  const result = await pool.query('SELECT COUNT(*)::int AS count FROM visits');
  return result.rows[0].count;
}

const server = http.createServer(async (req, res) => {
  try {
    if (req.url === '/health') {
      await pool.query('SELECT 1');
      res.writeHead(200, { 'content-type': 'application/json; charset=utf-8' });
      res.end(JSON.stringify({ status: 'ok' }));
      return;
    }

    if (req.url === '/visits') {
      const count = await addVisit();
      res.writeHead(200, { 'content-type': 'application/json; charset=utf-8' });
      res.end(JSON.stringify({ visits: count }));
      return;
    }

    res.writeHead(200, { 'content-type': 'application/json; charset=utf-8' });
    res.end(JSON.stringify({
      message: 'Node.js + PostgreSQL is running',
      endpoints: ['/health', '/visits']
    }, null, 2));
  } catch (error) {
    res.writeHead(500, { 'content-type': 'application/json; charset=utf-8' });
    res.end(JSON.stringify({ error: error.message }));
  }
});

await initDatabase();

server.listen(port, '0.0.0.0', () => {
  console.log(`server is running at http://0.0.0.0:${port}`);
});

process.on('SIGTERM', async () => {
  server.close(async () => {
    await pool.end();
    process.exit(0);
  });
});

创建 .dockerignore：

.git
node_modules
npm-debug.log
.env
*.md

创建 Dockerfile：

FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev

FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production
ENV PORT=3000
COPY --from=deps /app/node_modules ./node_modules
COPY package*.json ./
COPY src ./src
EXPOSE 3000
USER node
CMD ["node", "src/server.js"]

创建 compose.yaml：

services:
  app:
    build: .
    container_name: compose-node-app
    environment:
      PORT: 3000
      DATABASE_URL: postgresql://app:secret@postgres:5432/appdb
    ports:
      - "3000:3000"
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:16-alpine
    container_name: compose-postgres
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  postgres-data:

启动：

docker compose up --build

另开一个终端测试：

curl http://localhost:3000
curl http://localhost:3000/health

curl http://localhost:3000/visits

预期输出类似：

{"visits":1}
{"visits":2}

停止服务：

docker compose down

再次启动：

docker compose up --build
curl http://localhost:3000/visits

你会发现计数没有从 1 重新开始，因为 PostgreSQL 数据保存在 postgres-data 这个 volume 里。

如果你想连数据一起删除：

docker compose down -v

这个命令要谨慎。-v 会删除 Compose 创建的 volume，数据库数据会没。

Compose 文件逐行拆解

Compose 的核心就是三个概念：services、networks、volumes。

┌─────────────────────────────┐
│        compose.yaml          │
├─────────────────────────────┤
│ services                    │
│   ├── app                   │
│   └── postgres              │
├─────────────────────────────┤
│ networks                    │
│   └── 默认网络自动创建        │
├─────────────────────────────┤
│ volumes                     │
│   └── postgres-data         │
└─────────────────────────────┘

几个字段重点看：

字段 作用 示例
build 从 Dockerfile 构建镜像 build: .
image 直接使用已有镜像 postgres:16-alpine
environment 注入环境变量 DATABASE_URL=...
ports 映射宿主机端口 3000:3000
depends_on 控制启动依赖 等数据库健康后启动应用
volumes 挂载数据卷 postgres-data:/var/lib/postgresql/data
healthcheck 健康检查 pg_isready

这里有个实战经验：depends_on 只解决“启动顺序”，不等于服务真的可用。数据库容器启动了，不代表数据库已经能接连接。所以我更建议配合 healthcheck 使用。

常用命令速查

日常开发基本离不开这些命令。

目标 命令
查看运行中容器 docker ps
查看所有容器 docker ps -a
查看镜像 docker image ls
查看日志 docker logs -f <container>
进入容器 docker exec -it <container> sh
停止容器 docker stop <container>
删除容器 docker rm <container>
删除镜像 docker image rm <image>
查看 volume docker volume ls
查看网络 docker network ls
构建镜像 docker build -t name:tag .
启动 Compose docker compose up --build
后台启动 Compose docker compose up -d --build
停止 Compose docker compose down
连 volume 一起删 docker compose down -v

进入 Alpine 镜像通常用 sh：

docker exec -it compose-node-app sh

进入 Debian / Ubuntu 类镜像可能可以用 bash，但不要默认所有镜像都有 bash。很多精简镜像只有 sh。

调试 Docker 问题的思路

Docker 出问题时，不要一上来就删镜像重装。我的习惯是按这条链路查：

镜像是否构建成功
        │
        ▼
容器是否启动
        │
        ▼
应用是否监听正确端口
        │
        ▼
端口映射是否正确
        │
        ▼
容器间网络是否能解析服务名
        │
        ▼
数据卷和环境变量是否正确

问题 1：端口访问不到

先看容器是否还活着：

docker ps -a

再看日志：

docker logs compose-node-app

检查端口映射：

docker port compose-node-app

如果日志显示服务监听 127.0.0.1:3000，基本就是监听地址错了。容器内服务应该监听 0.0.0.0。

问题 2：应用连不上数据库

进入应用容器看环境变量：

docker exec -it compose-node-app sh
printenv DATABASE_URL

注意数据库地址应该写 Compose 服务名：

postgresql://app:secret@postgres:5432/appdb

不是：

postgresql://app:secret@localhost:5432/appdb

因为在应用容器里，localhost 指应用容器自己，不是 PostgreSQL 容器。

问题 3：改代码后镜像没变化

可能是缓存导致的。可以强制不走缓存构建：

docker compose build --no-cache

或者直接：

docker build --no-cache -t docker-node-demo:1.0.0 .

如果还想拉取最新基础镜像，可以加 --pull：

docker build --pull --no-cache -t docker-node-demo:1.0.0 .

生产环境 Dockerfile 应该注意什么

Docker 官方构建最佳实践里有几个点我觉得非常值得记住。

使用 .dockerignore

.dockerignore 不是可有可无。它能避免把 .git、node_modules、日志、密钥文件发进构建上下文。

.git
node_modules
*.log
.env
coverage
dist

尤其是 .env，不要一不小心复制进镜像。

不要用 latest

latest 最大的问题是不可重复。今天和明天构建出来的东西可能不一样。

# ❌ 反面案例
FROM node:latest

# ✅ 正面案例
FROM node:22-alpine

如果你对供应链安全要求很高，可以进一步用 digest 固定镜像：

FROM node:22-alpine@sha256:...

不过 digest 需要维护更新，否则也可能错过安全补丁。我的建议是：普通业务先固定版本 tag，有严格合规要求再引入 digest 和自动扫描。

不要把密钥写进镜像

下面这种写法很危险：

# ❌ 反面案例
ENV DATABASE_PASSWORD=secret
ENV API_TOKEN=xxxxx

镜像层和构建历史里可能留下痕迹。更好的做法是运行时注入：

docker run -e DATABASE_PASSWORD=secret my-app:1.0.0

Compose 里也可以用环境变量文件，但 .env 不应该提交到 Git。

尽量不要用 root 用户跑应用

# ✅ Node 官方镜像内置 node 用户
USER node

这不是绝对安全，但至少符合最小权限原则。应用如果被打穿，非 root 用户能造成的破坏通常更小。

多阶段构建

前端项目很适合多阶段构建：第一阶段用 Node 构建静态资源，第二阶段用 Nginx 提供服务。

FROM node:22-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

最终镜像里没有 Node.js、没有源码依赖、没有构建工具，只有构建后的静态文件和 Nginx。

一个更完整的发布流程

如果是实际项目，我一般会这样设计 Docker 交付流程：

本地开发
  │
  ├─ docker compose up 跑完整依赖
  │
  ▼
提交代码
  │
  ├─ CI 构建镜像
  ├─ 运行测试
  ├─ 扫描镜像漏洞
  └─ 推送镜像仓库
  │
  ▼
服务器 / K8s / PaaS 拉取镜像运行

最小 CI 思路是：

docker build --pull -t my-app:${GIT_SHA} .
docker run --rm my-app:${GIT_SHA} node --version

真实项目会继续加测试、镜像扫描、推送仓库、部署等步骤。这里不展开，因为不同团队差异很大。

Docker 学习路线

阶段 重点 要达到的程度
入门 run、ps、logs、exec 能运行和排查单容器
构建 Dockerfile、.dockerignore、构建缓存 能给自己的项目写镜像
数据 volume、bind mount 知道数据该放哪里
网络 bridge network、服务名访问 能让多个容器互通
编排 Docker Compose 能一条命令启动完整开发环境
优化 多阶段构建、非 root、固定版本 镜像更小、更安全、更稳定
交付 CI/CD、镜像仓库、部署 能进入团队工程化流程

大部分前端和全栈开发者，把 Docker + Compose 用熟，已经能解决 80% 的本地开发和测试环境问题。Kubernetes 当然重要，但它解决的是更大规模的调度问题，不应该成为 Docker 入门的第一站。

常见误区

误区 1：容器就是虚拟机

不是。容器更像隔离后的进程，共享宿主机内核；虚拟机有完整操作系统内核。容器启动更快，资源开销通常更小，但隔离边界也不是虚拟机那种模型。

误区 2：用了 Docker 就不会有环境问题

Docker 解决的是“运行环境可复制”，不是所有问题自动消失。

这些问题依然可能存在：

  • CPU 架构不同，比如 amd64 和 arm64；
  • 环境变量缺失；
  • 外部服务版本不一致；
  • 文件权限不同；
  • 时区和编码差异。

所以 Docker 是降低环境不一致，不是魔法消除 bug。

误区 3：容器删了，数据也一定删了

不一定。容器删除不等于 volume 删除。

docker compose down

只删除容器和默认网络，通常不会删除 volume。

docker compose down -v

才会删除 Compose 创建的 volume。生产环境别手滑。

误区 4：镜像越新越好

不是。生产环境更看重可控和可重复。不要盲目追 latest，也不要长期不更新基础镜像。比较稳的方式是固定主版本或小版本，并定期重建、扫描和升级。

小结

  1. Docker 的核心模型是镜像负责分发，容器负责运行，volume 负责保存数据。
  2. Dockerfile 的顺序会影响构建缓存，依赖安装应该尽量放在代码复制之前。
  3. 容器内服务要监听 0.0.0.0，宿主机访问依赖 -p 宿主机端口:容器端口。
  4. 多容器项目优先用 Docker Compose，服务之间用服务名通信。
  5. 数据库数据不要写进容器文件系统，应该使用 volume 持久化。
  6. 生产镜像尽量固定版本、使用 .dockerignore、不用 root、不要写入密钥。
  7. 学 Docker 不要急着跳 Kubernetes，先把单容器、网络、volume 和 Compose 用熟。
