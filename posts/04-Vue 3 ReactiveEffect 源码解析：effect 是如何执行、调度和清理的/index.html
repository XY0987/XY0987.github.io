Vue 3 ReactiveEffect 源码解析：effect 是如何执行、调度和清理的

发表于2026|更新于2026|Vue框架及周边库
|字数总计:4.2k|阅读时长:16分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：前面已经看完 reactive、baseHandlers、track 和 trigger。这一篇继续看 effect.ts。我的理解是，ReactiveEffect 是响应式系统里的“可执行订阅者”：它负责执行副作用函数、打开依赖收集窗口、接收依赖变化通知，并在必要时清理旧依赖。

先给结论

ReactiveEffect 主要解决四个问题：

问题 对应实现
如何让读取响应式数据时能收集当前 effect 执行前设置 activeSub = this
如何避免分支切换后旧依赖仍然触发 prepareDeps + cleanupDeps
如何避免同一轮变更重复执行 batch + NOTIFIED 标记
如何停止一个 effect stop 从所有 Dep 里移除当前 effect

可以把 effect 的完整生命周期理解成：

effect(fn)
  │
  ▼
new ReactiveEffect(fn)
  │
  ▼
e.run() 立即执行一次
  │
  ├─ 设置 activeSub
  ├─ 执行 fn
  ├─ fn 内部读取响应式数据
  ├─ track 收集当前 effect
  └─ 清理本轮没用到的旧依赖

响应式数据变化
  │
  ▼
trigger
  │
  ▼
Dep.notify
  │
  ▼
ReactiveEffect.notify
  │
  ▼
batch 入队
  │
  ▼
endBatch flush
  │
  ▼
e.trigger() / e.runIfDirty() / e.run()

Subscriber：effect 和 computed 的共同抽象

在 Vue 3.5 里，ReactiveEffect 和 ComputedRefImpl 都可以作为订阅者。源码里用 Subscriber 抽象它们：

/**
 * Subscriber 是响应式系统中的“订阅者”抽象。
 * ReactiveEffect 和 ComputedRefImpl 都是 Subscriber：它们会订阅 Dep，也会在 Dep 变化时被通知。
 */
export interface Subscriber extends DebuggerOptions {
  /**
   * 当前订阅者依赖的 Dep 链表头部。
   * @internal
   */
  deps?: Link
  /**
   * 当前订阅者依赖的 Dep 链表尾部。
   * @internal
   */
  depsTail?: Link
  /**
   * 标记当前订阅者的运行、追踪、暂停、脏值等状态。
   * @internal
   */
  flags: EffectFlags
  /**
   * 批处理队列中的下一个订阅者。
   * @internal
   */
  next?: Subscriber
  /**
   * returning `true` indicates it's a computed that needs to call notify
   * on its dep too
   * @internal
   */
  notify(): true | void
}

这里有两个字段很关键：

  • deps / depsTail：当前订阅者依赖了哪些 Dep。
  • notify：当依赖变化时，Dep 会调用它通知订阅者。

所以响应式依赖不是单向的。上一篇讲 Dep 能找到订阅它的 effect；这里反过来看，effect 自己也知道它依赖了哪些 Dep。这个双向关系靠 Link 串起来。

activeSub：依赖收集窗口的开关

activeSub 是理解 effect 执行的关键。

// 当前正在执行并允许收集依赖的订阅者。
// ReactiveEffect.run / refreshComputed 会在执行用户函数前设置它，track 会读取它来建立依赖关系。
export let activeSub: Subscriber | undefined

当 effect 执行用户函数时，Vue 会把当前 effect 放到 activeSub 上。之后用户函数里读取响应式属性，就会触发 baseHandlers.get -> track，而 track 会读取 activeSub，把当前 effect 收集到对应属性的 Dep 中。

这就解释了一个常见问题：为什么只有在 effect 里读取响应式数据才会建立依赖？

因为普通代码执行时没有设置 activeSub，track 找不到当前订阅者，自然不会收集。

ReactiveEffect 的核心字段

ReactiveEffect 本身是一个可执行的订阅者。

export class ReactiveEffect<T = any>
  implements Subscriber, ReactiveEffectOptions
{
  /**
   * 当前 effect 依赖的 Dep 链表头部。
   * @internal
   */
  deps?: Link = undefined
  /**
   * 当前 effect 依赖的 Dep 链表尾部。
   * @internal
   */
  depsTail?: Link = undefined
  /**
   * effect 创建后默认处于激活和可追踪状态。
   * @internal
   */
  flags: EffectFlags = EffectFlags.ACTIVE | EffectFlags.TRACKING
  /**
   * 批处理队列中的下一个订阅者。
   * @internal
   */
  next?: Subscriber = undefined
  /**
   * 下一次执行前或 stop 时需要调用的清理函数。
   * @internal
   */
  cleanup?: () => void = undefined

  scheduler?: EffectScheduler = undefined
  onStop?: () => void
  onTrack?: (event: DebuggerEvent) => void
  onTrigger?: (event: DebuggerEvent) => void

  constructor(public fn: () => T) {
    // 如果当前处于 effectScope 中，自动把 effect 记录到 scope，方便统一 stop。
    if (activeEffectScope && activeEffectScope.active) {
      activeEffectScope.effects.push(this)
    }
  }

几个字段可以这样理解：

字段 作用
fn 用户传进来的副作用函数
deps / depsTail 当前 effect 依赖的所有 Dep
flags 当前 effect 的状态集合
scheduler 自定义调度器，有的话触发时不直接执行 run
cleanup 下一次执行前或停止时要执行的清理函数
next 批处理队列中的链表指针

constructor 里还有一个细节：如果当前处在 effectScope 中，这个 effect 会自动登记到 scope。这样后面可以通过停止 scope 一次性停止一批 effect。

effect(fn)：创建后为什么会立即执行一次

用户调用的 effect(fn) 入口在这里：

export function effect<T = any>(
  fn: () => T,
  options?: ReactiveEffectOptions,
): ReactiveEffectRunner<T> {
  // 如果传入的是已有 runner，则复用它背后的原始副作用函数，避免 effect 套 effect。
  if ((fn as ReactiveEffectRunner).effect instanceof ReactiveEffect) {
    fn = (fn as ReactiveEffectRunner).effect.fn
  }

  const e = new ReactiveEffect(fn)
  if (options) {
    extend(e, options)
  }
  try {
    // effect 创建后会立即执行一次，用这次执行完成初始依赖收集。
    e.run()
  } catch (err) {
    e.stop()
    throw err
  }
  // 返回 runner，用户后续可以手动重新执行，也可以通过 runner.effect.stop() 停止。
  const runner = e.run.bind(e) as ReactiveEffectRunner
  runner.effect = e
  return runner
}

这里的关键是：effect 创建后会立刻 e.run()。

为什么要立即执行？因为只有执行用户函数，才能知道它读取了哪些响应式属性。也就是说，初始依赖收集不是静态分析出来的，而是通过第一次运行动态收集出来的。

举个例子：

const state = reactive({ count: 0 })

effect(() => {
  console.log(state.count)
})

第一次执行 fn 时读取 state.count，才会建立：

state.count 的 Dep ──► 当前 ReactiveEffect

最后返回的 runner 本质上是 e.run.bind(e)。所以用户手动调用 runner，其实就是重新执行这个 effect。

run：打开依赖收集窗口

run 是 ReactiveEffect 最核心的方法。

  // 执行副作用函数，并在执行期间打开依赖收集窗口。
  run(): T {
    // TODO cleanupEffect

    if (!(this.flags & EffectFlags.ACTIVE)) {
      // 已 stop 的 effect 再执行 runner 时，只调用原函数，不再收集依赖。
      return this.fn()
    }

    this.flags |= EffectFlags.RUNNING
    // 执行前先调用上一次注册的 cleanup，避免旧副作用残留。
    cleanupEffect(this)
    // 把旧依赖标记为待确认；本轮执行中再次访问到的依赖会被重新激活。
    prepareDeps(this)
    const prevEffect = activeSub
    const prevShouldTrack = shouldTrack
    // 设置全局 activeSub，后续响应式属性 get 时，track 就能收集到当前 effect。
    activeSub = this
    shouldTrack = true

    try {
      return this.fn()
    } finally {
      if (__DEV__ && activeSub !== this) {
        warn(
          'Active effect was not restored correctly - ' +
            'this is likely a Vue internal bug.',
        )
      }
      // 清理本轮没有再次访问到的旧依赖，避免分支切换后仍被无效触发。
      cleanupDeps(this)
      activeSub = prevEffect
      shouldTrack = prevShouldTrack
      this.flags &= ~EffectFlags.RUNNING
    }
  }

这段逻辑可以拆成五步：

  1. 如果 effect 已经停止，直接执行原函数，不收集依赖。
  2. 标记当前 effect 正在运行。
  3. 执行前处理 cleanup，并把旧依赖标记为待确认。
  4. 设置 activeSub = this，打开依赖收集窗口。
  5. 执行结束后清理无效依赖，并恢复上一个 activeSub。

最重要的是这两行：

    // 设置全局 activeSub，后续响应式属性 get 时，track 就能收集到当前 effect。
    activeSub = this
    shouldTrack = true

没有这两行，track 就不知道当前应该收集谁。

第 3 步里的两个清理不要混在一起

第 3 步同时出现了两个动作：

cleanupEffect(this)
prepareDeps(this)

它们处理的不是同一类东西：

代码 处理对象 简单理解
cleanupEffect(this) 上一次注册的 cleanup 函数 清理定时器、事件监听、请求等副作用资源
prepareDeps(this) 旧的依赖 Link 先把旧依赖标记为待确认，后面再决定是否移除

先看 cleanupEffect。它执行的是用户通过 onEffectCleanup 注册的函数：

export function onEffectCleanup(fn: () => void, failSilently = false): void {
  // 只能在 effect 正在执行时注册 cleanup，注册结果会挂到当前 activeSub 上。
  if (activeSub instanceof ReactiveEffect) {
    activeSub.cleanup = fn
  } else if (__DEV__ && !failSilently) {
    warn(
      `onEffectCleanup() was called when there was no active effect` +
        ` to associate with.`,
    )
  }
}

function cleanupEffect(e: ReactiveEffect) {
  const { cleanup } = e
  e.cleanup = undefined
  if (cleanup) {
    // cleanup 自身不应该参与依赖收集，所以执行期间临时清空 activeSub。
    const prevSub = activeSub
    activeSub = undefined
    try {
      cleanup()
    } finally {
      activeSub = prevSub
    }
  }
}

比如一个 effect 里开启了定时器：

import { effect, onEffectCleanup, reactive } from '@vue/reactivity'

const state = reactive({ count: 0 })

effect(() => {
  const timer = setInterval(() => {
    console.log(state.count)
  }, 1000)

  onEffectCleanup(() => {
    clearInterval(timer)
  })
})

如果 effect 以后重新执行，上一轮创建的定时器就应该先被清掉，否则每执行一次 effect 就会多一个定时器。cleanupEffect(this) 处理的就是这种“副作用资源”的清理。

prepareDeps(this) 处理的是另一件事：把旧的依赖 Link 标记为待确认。后面“依赖清理”小节会展开，这里先记住一句话：

cleanupEffect 清理副作用资源，prepareDeps 为依赖关系的重新确认做准备。

notify 与 batch：为什么不是立刻执行

当响应式数据变化时，Dep.notify 会通知每个 subscriber。对于普通 effect，最终会进入 ReactiveEffect.notify。

  /**
   * @internal
   */
  notify(): void {
    // 正在运行中的 effect 默认不能再次触发自己，除非显式允许递归。
    if (
      this.flags & EffectFlags.RUNNING &&
      !(this.flags & EffectFlags.ALLOW_RECURSE)
    ) {
      return
    }
    // 同一轮批处理中只入队一次，避免重复调度。
    if (!(this.flags & EffectFlags.NOTIFIED)) {
      batch(this)
    }
  }

这里没有直接调用 run()，而是调用 batch(this)。原因很简单：同一轮同步代码里，响应式数据可能被改很多次，如果每次都立刻执行 effect，开销会很大。

批处理相关代码在这里：

let batchDepth = 0
let batchedSub: Subscriber | undefined
let batchedComputed: Subscriber | undefined

// 将订阅者加入批处理队列。同一个 subscriber 会通过 NOTIFIED 标记避免重复入队。
export function batch(sub: Subscriber, isComputed = false): void {
  sub.flags |= EffectFlags.NOTIFIED
  // computed 先进入独立队列，只清理 NOTIFIED 标记，不在这里直接求值，保持 computed 的惰性。
  if (isComputed) {
    sub.next = batchedComputed
    batchedComputed = sub
    return
  }
  // 普通 effect 进入 batchedSub，待最外层 batch 结束后统一触发。
  sub.next = batchedSub
  batchedSub = sub
}

/**
 * @internal
 */
export function startBatch(): void {
  batchDepth++
}

/**
 * Run batched effects when all batches have ended
 * @internal
 */
export function endBatch(): void {
  // 支持嵌套批处理：只有回到最外层时，才真正 flush 队列。
  if (--batchDepth > 0) {
    return
  }

  if (batchedComputed) {
    let e: Subscriber | undefined = batchedComputed
    batchedComputed = undefined
    while (e) {
      const next: Subscriber | undefined = e.next
      e.next = undefined
      e.flags &= ~EffectFlags.NOTIFIED
      e = next
    }
  }

  let error: unknown
  // 普通 effect 队列可能在执行过程中继续产生新任务，所以这里用 while 持续刷新到队列为空。
  while (batchedSub) {
    let e: Subscriber | undefined = batchedSub
    batchedSub = undefined
    while (e) {
      const next: Subscriber | undefined = e.next
      e.next = undefined
      e.flags &= ~EffectFlags.NOTIFIED
      if (e.flags & EffectFlags.ACTIVE) {
        try {
          // ACTIVE flag is effect-only
          ;(e as ReactiveEffect).trigger()
        } catch (err) {
          if (!error) error = err
        }
      }
      e = next
    }
  }

  if (error) throw error
}

这里有几个设计点：

  • NOTIFIED 标记保证同一个 subscriber 一轮只入队一次。
  • batchDepth 支持嵌套批处理，只有最外层结束才 flush。
  • computed 和普通 effect 分开处理，computed 保持惰性，不在这里直接求值。
  • 普通 effect 队列使用 while，因为执行 effect 的过程中可能继续触发新的 effect。

这里的“重复入队”可以用一个简单场景理解：一个 effect 可能同时依赖多个属性。

effect(() => {
  console.log(state.a)
  console.log(state.b)
})

如果一次更新同时触发了 state.a 和 state.b 对应的 Dep，这个 effect 就可能被通知两次。Vue 不希望它在同一轮里执行两次，所以第一次通知时会设置 NOTIFIED 并入队；后面同一轮再通知时，发现已经有 NOTIFIED，就不会重复入队。

等队列真正执行时，Vue 会清掉 NOTIFIED，这样下一轮更新还能正常入队。

trigger：scheduler、pause 和 dirty 判断

effect 真正被触发时，会走到 ReactiveEffect.trigger：

  // 响应式数据变化后，Dep 最终会通过这里触发 effect。
  trigger(): void {
    if (this.flags & EffectFlags.PAUSED) {
      // 暂停期间不立即执行，只记录“恢复后需要补触发”。
      pausedQueueEffects.add(this)
    } else if (this.scheduler) {
      // 如果用户传入 scheduler，则把执行权交给调度器。
      this.scheduler()
    } else {
      this.runIfDirty()
    }
  }

  /**
   * @internal
   */
  runIfDirty(): void {
    // 只有依赖版本发生变化时才重新执行，避免无效运行。
    if (isDirty(this)) {
      this.run()
    }
  }

  get dirty(): boolean {
    return isDirty(this)
  }

这里的优先级是：

  1. 如果 effect 暂停了，不执行，只记录到 pausedQueueEffects。
  2. 如果有自定义 scheduler，交给调度器。
  3. 否则通过 runIfDirty 判断是否真的需要重新执行。

scheduler 是很重要的扩展点。Vue 运行时里的组件渲染 effect 就会配合调度器，把组件更新放到任务队列中，而不是每次响应式变化都立刻同步渲染。

依赖清理：分支切换时避免旧依赖误触发

上一篇讲过 Link.version，这里再从 effect.ts 角度看一次。

function prepareDeps(sub: Subscriber) {
  // 执行前把旧依赖全部标记为 -1。
  // 如果本轮执行中再次访问到这个依赖，Dep.track 会把 version 同步回来。
  for (let link = sub.deps; link; link = link.nextDep) {
    link.version = -1
    // 保存 Dep 当前 activeLink，执行结束后恢复，避免嵌套 effect/computed 互相覆盖。
    link.prevActiveLink = link.dep.activeLink
    link.dep.activeLink = link
  }
}

function cleanupDeps(sub: Subscriber) {
  // 执行后清理本轮没有再次访问到的依赖，也就是 version 仍为 -1 的 Link。
  let head
  let tail = sub.depsTail
  let link = tail
  while (link) {
    const prev = link.prevDep
    if (link.version === -1) {
      if (link === tail) tail = prev
      // unused - remove it from the dep's subscribing effect list
      removeSub(link)
      // also remove it from this effect's dep list
      removeDep(link)
    } else {
      // The new head is the last node seen which wasn't removed
      // from the doubly-linked list
      head = link
    }

    // restore previous active link if any
    link.dep.activeLink = link.prevActiveLink
    link.prevActiveLink = undefined
    link = prev
  }
  // set the new head & tail
  sub.deps = head
  sub.depsTail = tail
}

function isDirty(sub: Subscriber): boolean {
  for (let link = sub.deps; link; link = link.nextDep) {
    // 依赖 Dep 的版本号和 Link 记录的版本号不同，说明依赖发生过变化。
    // 如果依赖的是 computed，需要先尝试刷新 computed，再重新比较版本。
    if (
      link.dep.version !== link.version ||
      (link.dep.computed &&
        (refreshComputed(link.dep.computed) ||
          link.dep.version !== link.version))
    ) {
      return true
    }
  }

用一个例子理解：

const state = reactive({ ok: true, a: 1, b: 2 })

effect(() => {
  console.log(state.ok ? state.a : state.b)
})

第一次执行依赖 ok 和 a。当 ok 改成 false 后，下一次执行依赖 ok 和 b。这时旧的 a 依赖应该被清掉，否则以后修改 a 还会触发这个 effect。

prepareDeps 和 cleanupDeps 解决的就是这个问题：

  1. 执行前把旧依赖都标记为 -1。
  2. 本轮执行中访问到的依赖会被重新同步版本。
  3. 执行后仍然是 -1 的依赖说明本轮没访问到，移除。

stop：停止 effect 后发生什么

stop 的作用是让 effect 不再被响应式依赖触发。

  stop(): void {
    if (this.flags & EffectFlags.ACTIVE) {
      // 从所有 Dep 的订阅链表中移除当前 effect。
      for (let link = this.deps; link; link = link.nextDep) {
        removeSub(link)
      }
      this.deps = this.depsTail = undefined
      cleanupEffect(this)
      this.onStop && this.onStop()
      this.flags &= ~EffectFlags.ACTIVE
    }
  }

停止时主要做四件事：

  1. 从所有依赖的 Dep 订阅链表里移除当前 effect。
  2. 清空自己的 deps / depsTail。
  3. 执行 cleanup。
  4. 去掉 ACTIVE 标记。

外部的 stop(runner) 只是一个很薄的封装：

/**
 * Stops the effect associated with the given runner.
 *
 * @param runner - Association with the effect to stop tracking.
 */
export function stop(runner: ReactiveEffectRunner): void {
  runner.effect.stop()
}

需要注意的是：停止后的 runner 仍然可以手动执行，只是不会再参与依赖收集。

cleanup：下一次执行前清理副作用

前面讲 run() 时已经看过 cleanupEffect(this)：它会执行上一轮通过 onEffectCleanup 注册的清理函数。

这里再补充两个时机：

  1. effect 下一次重新执行前，会先执行 cleanup。
  2. effect 被 stop() 时，也会执行 cleanup。

还有一个细节：执行 cleanup 时会临时把 activeSub 清空。

原因是 cleanup 本身只是清理逻辑，不应该因为读取了响应式数据而被收集为新的依赖。否则清理函数可能反过来污染 effect 的依赖关系。

小结

  1. ReactiveEffect 是响应式系统中的可执行订阅者，负责执行副作用函数并维护依赖链表。
  2. run 会设置 activeSub，让用户函数里的响应式读取可以被 track 收集。
  3. notify 不直接执行 effect，而是通过 batch 入队，避免同一轮变更重复执行。
  4. trigger 支持暂停、调度器和脏值判断，是 effect 被依赖变化唤醒后的入口。
  5. prepareDeps / cleanupDeps 通过 Link.version 清理分支切换后的旧依赖。
  6. stop 会把 effect 从所有 Dep 中移除，之后响应式变化不再触发它。

到这里，响应式系统的核心链路已经比较完整：reactive 创建代理，baseHandlers 拦截读写，track/trigger 维护依赖，ReactiveEffect 负责执行和调度。下一步可以继续看 ref.ts，理解为什么 ref 要用 .value，以及它和 reactive 在依赖收集上的差异。
