Agent 工作模式全景解析：ReAct / Plan-Execute / Reflection / ToT 怎么选

发表于2026|更新于2026|AI相关
|字数总计:3.8k|阅读时长:13分钟

前言：Agent 拿到任务后，到底怎么”跑”？ 是一边想一边做，还是先想清楚再做，还是边做边改？这就是 Agent 的工作模式。

为什么要单独讲”工作模式”

先澄清三个概念的层次关系：

┌───────────────────────────────────────────────────┐
│   工作模式（本文重点）                                │
│   决定 Agent 思考-行动的节奏和流程                     │
│   ReAct / Plan-Execute / Reflection / ToT / 多 Agent │
├─────────────────────────────────────────────────────┤
│   架构组件                                           │
│   规划 + 记忆 + 工具 + 行动                           │
├─────────────────────────────────────────────────────┤
│   框架与实现                                          │
│   LangGraph / CrewAI / 手写 Loop                     │
└──────────────────────────────────────────────────────┘

架构决定”Agent 由什么组成”，工作模式决定”这些组件怎么配合起来解决问题”。同样是”规划 + 工具 + 记忆”，工作模式不同，最后的表现可能差一个量级。

工作模式的两条核心评估轴

在看具体模式之前，先立两条评估轴，后面每个模式都会在这两条轴上定位：

评估轴 两个极端 影响
规划粒度 边走边想 ←→ 先想清楚再走 前者灵活、后者稳定
反思深度 一次性输出 ←→ 多轮自我修正 前者快、后者准

基本盘是：规划越重、反思越多，质量越高但成本越高。

模式一：ReAct —— 走一步看一步

ReAct（Reasoning + Acting）是最早、最通用、也是大多数 Agent 的默认模式。核心思路简单到一句话说得完：

思考 → 行动 → 观察 → 思考 → 行动 → 观察 → ... → 完成

每一步只规划下一个动作，执行完看结果再决定下一步。不预设完整计划，走一步看一步。

最小实现

// react-mode.mjs
async function runReAct(goal, maxSteps = 10) {
  const messages = [
    { role: 'system', content: '你通过"思考-行动-观察"循环完成任务。完成后直接给出答案。' },
    { role: 'user', content: goal }
  ];

  for (let i = 0; i < maxSteps; i++) {
    const resp = await openai.chat.completions.create({
      model: 'gpt-4', messages, tools, tool_choice: 'auto'
    });
    const msg = resp.choices[0].message;
    messages.push(msg);

    // 不调工具 = 任务完成
    if (!msg.tool_calls) return msg.content;

    // 执行工具 → 结果回填 → 下一轮让 LLM 自己决定怎么走
    for (const tc of msg.tool_calls) {
      const result = await execute(tc.function.name, JSON.parse(tc.function.arguments));
      messages.push({ role: 'tool', tool_call_id: tc.id, content: String(result) });
    }
  }
}

什么时候该用 ReAct

判断一个任务要不要用 ReAct，看一条：任务不太复杂（步骤少），或者路径在执行前画不出来——满足其一就用 ReAct。

  • 路径画不出来 → 用 ReAct：下一步做什么必须看上一步的结果。典型的就是探索型任务——排查 bug、做技术调研、按自然语言需求查数据。哪怕逻辑本身很”难”，只要路径不确定，走一步看一步就是最优解。
  • 步骤少→ 用 ReAct：即使路径大致清晰，任务短到几步就结束的话，也没必要专门跑一次”规划 + 执行”两阶段流程，ReAct 的轻量循环更省事。
  • 两条都不满足 → 别用 ReAct：任务复杂（步骤多）且 路径可预测，就该用 Plan-and-Execute，让 LLM 每一步重新”思考”一遍已经确定的流程，纯属浪费 token。

模式二：Plan-and-Execute —— 先画路线图再上路

ReAct 的问题是没全局观。Plan-and-Execute 把 Agent 拆成两个角色：

┌────────────┐       ┌─────────────┐
│  Planner   │ ────▶ │   Executor  │
│ 只负责规划  │       │ 只负责执行   │
└────────────┘       └─────────────┘
      ▲                     │
      │     整体失败时重规划   │
      └─────────────────────┘

Planner 一次性输出完整步骤，Executor 按部就班执行，中途基本不改计划。

最小实现

// plan-execute-mode.mjs
async function runPlanExecute(goal) {
  // 第一阶段：Planner 规划完整步骤
  const planResp = await openai.chat.completions.create({
    model: 'gpt-4',
    messages: [
      { role: 'system', content: '你是任务规划器。把用户目标拆成有序步骤，每步一个动作。用 JSON 数组返回。' },
      { role: 'user', content: goal }
    ],
    response_format: { type: 'json_object' }
  });
  const plan = JSON.parse(planResp.choices[0].message.content).steps;
  console.log('规划完成:', plan);

  // 第二阶段：Executor 按计划执行
  const results = [];
  for (const step of plan) {
    const result = await executeStep(step, results);  // 前面步骤的结果作为上下文
    results.push({ step, result });

    // 关键节点可选：执行失败 → 触发重规划
    if (result.failed) {
      return await runPlanExecute(`${goal}\n已完成: ${JSON.stringify(results)}\n失败原因: ${result.error}`);
    }
  }
  return summarize(results);
}

为什么它比 ReAct 更适合复杂任务

  • 全局视角：Planner 一次看到全貌，容易发现可并行的步骤
  • 职责分离：Planner 用强模型保证规划质量，Executor 可以用便宜的小模型
  • 可审查：规划输出是结构化的，可以在执行前给用户看、让用户批
  • 可恢复：失败时带着已完成的进度重规划，而不是整个从头来

什么时候该用 Plan-and-Execute

和 ReAct 正好反过来：任务足够复杂（步骤多） 且 路径在执行前大致可预测

  • 步骤多 + 路径可预测 → 用 Plan-Execute：比如”把 PRD 拆成开发任务并估时”、”跑一条数据处理流水线”、”生成一份竞品调研报告”。流程能被提前想清楚，全局规划的价值就能兑现——能识别并行、能让人审、失败能带进度重规划。
  • 步骤少 → 别用 Plan-Execute：3 步任务跑一次完整规划是杀鸡用牛刀，回退到 ReAct 或一次 LLM call 更划算。
  • 路径不可预测 → 别用 Plan-Execute：Planner 规划出来也是瞎猜，执行两步就全盘作废，白付规划成本，改用 ReAct。

ReAct 和 Plan-Execute 不是竞争关系，而是互补——看不清路或路很短时用 ReAct，看得清路且路够长时用 Plan-Execute。

模式三：Reflection —— 自我批评式精修

前两种模式都是”做完就收工”。Reflection 加了一个内置批评家：Agent 产出结果后，自己（或另一个 Agent）审一遍，找问题，再改一次。

生成 ──▶ 自我评审 ──▶ 修正 ──▶ 再评审 ──▶ ... ──▶ 合格输出
          ▲                    │
          └────────────────────┘
           评审不通过就继续改

最小实现

// reflection-mode.mjs
async function runReflection(goal, maxRounds = 3) {
  let draft = await generate(goal);   // 先生成初稿

  for (let i = 0; i < maxRounds; i++) {
    // 关键：用独立的"评审 Prompt"
    const critique = await openai.chat.completions.create({
      model: 'gpt-4',
      messages: [
        { role: 'system', content: '你是严格的评审员。指出下面内容的具体问题。若无问题，回复 APPROVED。' },
        { role: 'user', content: `目标：${goal}\n\n内容：${draft}` }
      ]
    });
    const feedback = critique.choices[0].message.content;

    if (feedback.includes('APPROVED')) return draft;

    // 按评审意见修改
    draft = await revise(draft, feedback);
  }
  return draft;
}

Reflection 的两个变体

Self-Reflection：生成和评审都是同一个 LLM 扮演两个角色。轻量、便宜，但容易”自己看自己都对”。

Actor-Critic：评审由独立的 Agent / 模型 / 规则引擎完成。效果更好但成本更高。

我的实战建议：评审 Prompt 要写得比生成 Prompt 还严格，才能逼出有价值的反馈。不要写”请检查一下”这种话，要写”必须指出至少 3 个可改进点，无可改进点才回复 APPROVED”。

适合与不适合

  • 特别适合：代码生成、文章写作、数据分析报告——这些任务有明确的质量标准
  • 不太适合：简单信息查询、确定性强的工具调用——为一个”今天天气”的查询做 Reflection 纯属浪费

模式四：Tree of Thoughts —— 同时探索多条路径

前三种模式都是”一条路走到黑”。ToT（Tree of Thoughts）反过来——同时展开多条思路，用评分挑出最好的。

                         问题
                          │
           ┌──────────────┼──────────────┐
           ▼              ▼              ▼
        思路A          思路B          思路C
        评分:7         评分:9         评分:5
           │              │              │
       展开子路径       展开子路径       剪枝
           │              │
         ...            ...
                          │
                      最优方案

核心动作：分支 → 评估 → 剪枝 → 展开，本质是在思考空间里做搜索。

最小实现

// tot-mode.mjs
async function runToT(problem, branchWidth = 3, depth = 3) {
  let candidates = [{ path: [], state: problem }];

  for (let d = 0; d < depth; d++) {
    // 1. 分支：让 LLM 为每个候选生成 N 种"彼此不同"的下一步
    const expanded = [];
    for (const c of candidates) {
      const resp = await llm.chat(`任务：${problem}\n当前进展：${c.state}\n` +
        `请给出 ${branchWidth} 种**差异明显**的下一步思路，JSON 数组输出。`);
      for (const s of JSON.parse(resp)) {
        expanded.push({ path: [...c.path, s], state: `${c.state}\n→ ${s}` });
      }
    }

    // 2. 评估：让 LLM 给每条路径打分（0-10）
    const scored = await Promise.all(expanded.map(async (e) => {
      const resp = await llm.chat(`目标：${problem}\n路径：${e.state}\n` +
        `这条路走下去能解决问题的可能性，0-10 打分，只返回数字。`);
      return { ...e, score: Number(resp) };
    }));

    // 3. 剪枝：只留 Top-K；最优路径已经够好就提前返回
    candidates = scored.sort((a, b) => b.score - a.score).slice(0, branchWidth);
    if (candidates[0].score >= 9) return candidates[0];
  }
  return candidates[0];
}

“分支”负责发散（强调”差异明显”是防止模型给三个一样的答案）
“评估”负责打分（直接决定剪枝质量，所以前面那张表里 ToT 的评估函数必须用强模型），外层循环只是个普通的 beam search，不含任何 LLM 逻辑。

适合与不适合

ToT 的成本是前三种模式的 N 倍（N 是分支宽度）。所以只在真正需要它的场景用：

  • 数学题、逻辑推理题：答案要么对要么错，值得多路径搜索
  • 复杂决策（比如”给这个方案选最优架构”）：需要权衡多种可能
  • 普通业务任务：基本用不上，ReAct 或 Plan-Execute 就够了

模式五：多 Agent 协作 —— 分工比单打独斗更强

前四种模式都是一个 Agent 干一切。当任务涉及多个专业角色（产品 + 技术 + 审核）、或单个 prompt 塞不下全部职责时，就该拆成多个 Agent 协作

核心思路一句话：让不同 Agent 扮演不同角色，各自领域更强、视角互补。

三种常见拓扑

① Supervisor-Worker（最常用）        ② 辩论 / 多视角
        Supervisor                        问题
       ╱    │    ╲                   ╱    │    ╲
   Worker Worker Worker           方案A  方案B  方案C
    调度者派任务 → 执行者汇报          ╲    │    ╱
                                       Judge 裁判选

③ 流水线 / 接力
   需求分析 Agent → 代码生成 Agent → 代码审查 Agent → 输出
  • Supervisor-Worker：一个调度 Agent 根据任务分派给合适的 worker，像技术主管带团队
  • 辩论：多个 Agent 独立出方案，裁判选最优——适合决策类任务
  • 流水线：角色顺序固定，A 的输出是 B 的输入——适合分工明确的生产流程

最小实现（Supervisor-Worker）

// multi-agent.mjs
const workers = {
  coder:    '你是资深工程师，只负责写代码，不做别的。',
  reviewer: '你是代码审查员，找出 bug 和风格问题，不写代码。',
  writer:   '你是技术文档工程师，把代码/方案写成易懂的文档。',
};

async function runMultiAgent(task) {
  const history = [`用户任务：${task}`];

  for (let i = 0; i < 10; i++) {
    // 1. Supervisor 决定下一步由谁来做
    const route = await llm.chat(
      `你是调度者，可选的 worker：${Object.keys(workers).join(', ')}。\n` +
      `上下文：\n${history.join('\n')}\n` +
      `请选择下一个 worker，或回答 DONE 表示完成。只返回名字或 DONE。`
    );
    if (route.trim() === 'DONE') return history.at(-1);

    // 2. 被选中的 worker 带着自己的角色 prompt 接手
    const reply = await llm.chat([
      { role: 'system', content: workers[route] },
      { role: 'user',   content: history.join('\n') },
    ]);
    history.push(`[${route}] ${reply}`);
  }
}

Supervisor 的 prompt 只负责”路由决策“（不做业务），Worker 的 prompt 只负责”单一专业职责“（不越界）。
一旦职责混在一个 prompt 里，多 Agent 就退化成换汤不换药的单 Agent。

什么时候该用多 Agent

主判据：单个 Agent 的上下文/角色装不下整个任务——一个 prompt 既要当 PM、又要当程序员、还要当审核员，彼此互相干扰，就该拆。

  • 多专业角色协作 → 用多 Agent：写代码 + 审查代码、生成方案 + 批判方案、不同领域知识分头查
  • 任务简单、单一角色能搞定 → 别用多 Agent：多 Agent 是串行对话，延迟高、token 贵，没必要
  • 角色边界模糊 → 别用多 Agent：分不清 A 和 B 各自负责什么，路由会乱成一锅粥，不如一个 Agent 硬扛

多 Agent 不是”Agent 的升级版”，而是当职责无法用一个 prompt 讲清楚时的拆分手段。职责拆得清才用，拆不清就别拆。

模式六：Workflow vs Agent —— 经常被混为一谈

这是 Anthropic 在 “Building effective agents” 里正式拉出来的对比。很多人把这两个当同义词，其实差别非常本质：

维度 Workflow Agent
流程 开发者预定义好 LLM 自主决定
可预测性 高，每次都走一样的路 低，LLM 每次可能走不同路
适用任务 路径明确、步骤固定 路径开放、方案多样
调试难度 低，像普通程序 高，需要大量日志
成本 可控 不可控（取决于 LLM 决策）

用图说明

Workflow（开发者编排）：
    任务 ──▶ 步骤A ──▶ 步骤B ──▶ 步骤C ──▶ 结果
              │          │          │
            LLM调用    LLM调用    LLM调用
            （路径固定，LLM 只在节点内部工作）

Agent（LLM 编排）：
    任务 ──▶ LLM 决策循环 ──▶ 结果
             │
             ├── 工具A
             ├── 工具B
             └── 工具C
            （LLM 自己决定调哪个、调几次）

任务路径能预先固定的，用 Workflow；不固定的，用 Agent。

常见工作模式组合

实际项目里，这些模式经常组合使用。最常见的三种组合：

组合一：Plan-Execute + ReAct（嵌套式）

外层是 Plan-Execute 保证大方向不跑偏，每个步骤内部用 ReAct 处理动态细节。

外层：Plan → Step1, Step2, Step3
       │
       └─▶ 每个 Step 内部：ReAct 小循环处理具体动作

组合二：ReAct + Reflection

每完成 N 步 ReAct 就触发一次 Reflection，让 Agent 回顾”到目前为止做得对不对”。适合长流程任务。

组合三：Workflow 主流程 + Agent 局部

整体用 Workflow 保证可预测性，只在真正需要灵活性的节点（比如”从这堆内容里挑 10 条”）换成 Agent。

Workflow:  采集 ──▶ 清洗 ──▶ [Agent 智能筛选] ──▶ 推送
           固定       固定         灵活           固定

选型决策表

你的任务特征 推荐模式
流程固定、步骤明确 Workflow
探索性、路径不定、工具少 ReAct
步骤多且可预测、需要审批 Plan-and-Execute
有明确质量标准（代码、文案） ReAct/Plan-Execute + Reflection
需要探索多种可能方案 Tree of Thoughts
涉及多个专业角色协作 多 Agent 协作
生产级复杂业务 Workflow 主干 + Agent 局部

小结

  1. 工作模式决定 Agent 的执行节奏，比框架选型更影响最终质量
  2. ReAct 是默认选择，但工具不能太多、步骤不能太长
  3. Plan-and-Execute 适合复杂、可预测、需要审批的业务流程
  4. Reflection 用在有明确质量标准的任务上，效果提升明显
  5. Tree of Thoughts 是”重武器”，日常业务基本用不到
  6. 多 Agent 协作解决”单 prompt 装不下多角色”的问题，职责拆得清再用
  7. Workflow 和 Agent 不是对立关系，大部分生产系统是两者混合
  8. 模式选型要和模型能力匹配，小模型跑不了复杂模式
