前端项目目录设计与项目规范

发表于2026|更新于2026|工程化
|字数总计:1.7k|阅读时长:5分钟

前言：目录设计不是把文件摆整齐这么简单。一个好的目录结构，应该能让新人一眼看出业务边界、公共能力、配置入口和测试位置。我的看法是：目录结构就是项目的第一份架构文档。

先说一个常见误区

很多项目一开始会这样组织：

src/
├── api/
├── components/
├── pages/
├── utils/
└── hooks/

这个结构不能说错，但它只表达了“文件类型”，没有表达“业务边界”。

随着业务增加，components 会变成公共组件、业务组件、页面私有组件的大杂烩；utils 会变成所有人都能随便塞东西的垃圾桶；api 里文件越来越多，最后只能靠文件名猜接口属于哪个模块。

所以目录设计的关键不是“层级越多越专业”，而是先想清楚：这个项目最需要表达什么边界。

两种常见组织方式

前端项目常见有两种目录组织方式：按技术分层，或者按业务模块分层。

按技术分层

src/
├── pages/
├── components/
├── services/
├── hooks/
├── utils/
└── types/

这种方式适合：

  • 项目规模不大；
  • 页面之间复用较多；
  • 团队刚开始建立规范；
  • 业务边界还没有特别复杂。

优点是简单直接，新人容易理解。缺点是业务变大后，文件会在多个目录之间来回跳。

按业务模块分层

src/
├── app/
├── features/
│   ├── user/
│   │   ├── components/
│   │   ├── services/
│   │   ├── hooks/
│   │   ├── types.ts
│   │   └── index.ts
│   └── order/
├── shared/
│   ├── components/
│   ├── utils/
│   └── hooks/
└── pages/

这种方式适合：

  • 中大型业务系统；
  • 多人并行开发；
  • 业务模块边界清晰；
  • 后续可能拆包或做 Monorepo。

它的好处是业务内聚，改用户模块时大部分文件都在 features/user 下面。我的实战建议是：中后台系统优先考虑按业务模块组织，公共能力再下沉到 shared。

我常用的目录结构

如果是一个 React/Vue 中型项目，我一般会从下面这个结构开始：

src/
├── app/                 # 应用级入口、路由、Provider、全局状态挂载
├── pages/               # 路由页面，尽量只做编排，不堆复杂逻辑
├── features/            # 业务功能模块，按领域拆分
│   ├── user/
│   └── order/
├── shared/              # 跨业务复用能力
│   ├── components/      # 通用 UI 组件
│   ├── hooks/           # 通用 hooks / composables
│   ├── utils/           # 纯函数工具
│   └── constants/       # 公共常量
├── services/            # 请求实例、接口 SDK、数据层适配
├── types/               # 全局类型、环境变量类型、第三方声明
├── config/              # 运行时配置、菜单配置、权限配置
├── assets/              # 静态资源
├── styles/              # 全局样式、主题变量
└── tests/               # 测试工具、mock server、测试夹具

这里有几个我比较坚持的点。

pages 不要写成业务垃圾桶

pages 更像路由入口，它主要负责“把东西组装起来”。复杂逻辑应该沉到 features、services 或 shared。

// ❌ 反面案例：页面里同时写请求、状态、表格列、弹窗逻辑
export function UserPage() {
  // 这里省略一堆复杂逻辑
}

// ✅ 正面案例：页面只负责组合业务模块
import { UserSearch } from '@/features/user/components/UserSearch'
import { UserTable } from '@/features/user/components/UserTable'

export function UserPage() {
  return (
    <main>
      <UserSearch />
      <UserTable />
    </main>
  )
}

这样做的好处是，页面不会无限膨胀，业务模块也更容易被复用或迁移。

shared 必须控制准入

shared 不是“谁都可以放”的地方。我的判断标准是：

至少被两个业务模块稳定复用，并且不依赖具体业务语义，才放进 shared。

比如 formatDate 可以放 shared/utils，但 formatOrderStatus 更适合留在 features/order，因为它带有订单业务语义。

shared/utils/formatDate.ts          # ✅ 通用日期格式化
features/order/utils/formatStatus.ts # ✅ 订单状态格式化

很多项目公共模块变乱，就是因为太早把业务代码抽成“公共代码”。公共代码一旦被多人依赖，修改成本会比私有代码高很多。

services 要区分请求实例和业务接口

我一般会把请求层拆成两层：

services/
├── http.ts              # axios/fetch 实例、拦截器、错误处理
├── sdk/                 # OpenAPI 生成的 SDK 或手写接口函数
└── query/               # React Query / VueQuery / SWR 的查询封装

不要在组件里散写 fetch 或 axios。短期很快，长期一定难维护。

// ❌ 反面案例：组件直接关心接口地址和错误结构
const res = await fetch('/api/users?page=1')

// ✅ 正面案例：组件只关心业务函数
const users = await userApi.listUsers({ page: 1 })

这样接口地址变化、鉴权方式变化、错误码变化，都可以集中处理。

配置、脚本、测试也要有固定位置

一个项目除了 src，根目录也要有规范。

.
├── src/
├── scripts/             # 构建辅助脚本、发布脚本、代码生成脚本
├── tests/               # E2E 或跨模块测试
├── public/              # 不经过打包处理的静态文件
├── package.json
├── tsconfig.json
├── vite.config.ts
├── eslint.config.js
├── .env.example
├── .nvmrc
└── README.md

scripts 放自动化脚本

只要一个操作需要重复执行，就应该考虑脚本化。比如：

  • 根据 OpenAPI 生成接口类型；
  • 检查环境变量是否完整；
  • 发布前同步版本号；
  • 批量生成业务模板。

脚本不要散落在根目录，否则项目越久越乱。

.env.example 是团队协作必需品

.env.local 通常不提交，但新人总要知道需要哪些变量。所以我建议每个项目都保留 .env.example。

VITE_API_BASE_URL=https://api.example.com
VITE_APP_ENV=development

它不放真实密钥，只放变量名和示例值。这样新人拉项目后，不需要问“本地环境变量怎么配”。

README.md 要写运行路径

很多项目 README 写得像产品介绍，却没写怎么启动。我的建议是至少写清楚：

## 开发

1. 使用 Node.js 20.x
2. 启用 Corepack
3. 安装依赖：pnpm install
4. 启动项目：pnpm dev
5. 类型检查：pnpm typecheck
6. 构建：pnpm build

README 不需要很长，但必须让新人能跑起来。

目录规范背后的依赖方向

目录设计真正重要的是依赖方向。

我通常会遵守这个规则：

pages  -> features -> services/shared
app    -> pages/features/shared
shared -> 不依赖业务模块

也就是说：

  • pages 可以引用 features；
  • features/user 不应该随便引用 features/order；
  • shared 不应该依赖 features；
  • services/http.ts 不应该知道具体 UI 组件。

可以用一张图理解：

┌──────────┐
│   app    │
└────┬─────┘
     ▼
┌──────────┐
│  pages   │
└────┬─────┘
     ▼
┌──────────┐      ┌──────────┐
│ features │ ---> │ services │
└────┬─────┘      └──────────┘
     ▼
┌──────────┐
│  shared  │
└──────────┘

如果这个方向被打破，后面通常会出现循环依赖、公共模块变重、业务模块难拆的问题。

小结

  1. 目录结构不是装饰，它表达的是项目边界和依赖方向。
  2. 小项目可以按技术分层，中大型项目更适合按业务模块内聚。
  3. pages 负责编排，复杂逻辑应该沉到 features、services 或 shared。
  4. shared 要控制准入，不要把业务代码过早公共化。
  5. 根目录也要规范，脚本、环境变量示例、README 都是协作效率的一部分。
