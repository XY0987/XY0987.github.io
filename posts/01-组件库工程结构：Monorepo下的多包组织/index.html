组件库工程结构：Monorepo 下的多包组织

发表于2026|更新于2026|工程化
|字数总计:3.6k|阅读时长:12分钟

前言：从这一篇开始进入「组件库与发布」这个阶段。前面在「Monorepo 工程化实践」那篇里，我们已经系统讲过 pnpm workspace、catalog、任务编排、Changesets 这套底座。这篇不再重复工具怎么配，而是只看组件库自己的问题：哪些东西该拆成包、包之间怎么依赖、哪些依赖必须 peer、开发时怎么做到源码直连。分包分错了，后面的构建、按需引入、发布全都会别扭。

先判断：组件库适不适合 Monorepo

Monorepo 的价值不是「一个仓库看起来更高级」，而是解决强关联包一起演进的问题。

组件库刚好是典型场景。一个中大型组件库通常不只有 components 一个包，还会有主题、图标、hooks、工具函数、文档站、playground、内部构建工具。它们之间的变化经常是联动的：

  • 比如颜色、圆角、间距这些设计变量改了，按钮、弹窗等组件的样式也要跟着检查和调整；
  • 图标构建脚本改了，图标包和组件包都要验证；
  • utils 的类型调整了，下游组件要一起检查；
  • 发布一个新组件时，文档、示例、类型导出、样式导出都要同步。

如果这些东西分散在多个仓库里，一个需求可能要开好几个 PR：先发 utils，再升级 components，再改 docs。版本一错，联调就开始打补丁。Monorepo 的核心好处是：跨包改动可以在一个 PR 里完成、一次 CI 里验证、一次发布流程里处理依赖版本。

但也别把所有东西都塞进来。我的判断是：

场景 是否适合 Monorepo 原因
组件、主题、图标、hooks 强关联 适合 经常一起改、一起验证
文档站、playground 适合 是组件库的内部消费者，能做真实联调
完全独立的业务应用 不一定 如果发版节奏和权限边界完全不同，硬放进来反而变慢
跟组件库无关的工具项目 不建议 只会增加依赖图和 CI 成本

一句话：有共享代码、共享发布、共享验证需求，就适合；只是组织上属于同一个团队，不等于适合。

先把通用底座当成前置知识

这一篇默认你已经有了前面那套 Monorepo 底座：

  • 用 pnpm workspace 识别多包；
  • 内部包依赖用 workspace:*；
  • 公共工具链版本用 catalog 收口；
  • 构建、测试、发布交给 Turborepo / Nx 和 Changesets。

这些概念不再展开。放到组件库场景里，我只补几个更具体的约定：

约定 组件库里的做法 原因
要发布的包 放在 packages/* 方便统一构建、检查和发布
文档与调试应用 docs / playground 放根目录平级，并标记 private: true 它们是内部消费者，不应该发到 npm
内部工程配置 放在 tooling/* ESLint、tsconfig、构建配置可以复用，但不混进组件包
框架依赖 对外放 peerDependencies，对内用 catalog 管开发版本 避免用户项目里出现两份 Vue / React

后面重点讲的不是「workspace 怎么连起来」，而是连起来之后，这些包的边界怎么设计。

组件库为什么天然是多包

先说个反直觉的判断：成熟的组件库，几乎没有单包结构的。

一个能长期维护的组件库，除了「组件」本身，至少还会长出这些东西：

  • 一套统一的样式规则，比如颜色、字号、间距、圆角；
  • 一批图标；
  • 一堆工具函数（hooks、格式化、DOM 操作）；
  • 一个文档站；
  • 若干示例 demo；
  • 可能还有配套的 ESLint 配置、CLI 工具。

如果全塞进一个包，会遇到几个绕不开的问题：图标改一次要整个组件库重新发版；文档站的依赖（VitePress、Storybook）被打进了用户安装的产物里；工具函数明明可以独立复用，却只能跟着组件库一起用。

所以组件库天然适合 Monorepo：每一类东西是一个独立的包，共享同一套工具链，又能各自按需发版。

一个组件库的典型分包

常见的结构长这样：

my-ui/
├── package.json              # 根配置，private: true
├── pnpm-workspace.yaml
├── tsconfig.base.json
├── turbo.json                # 任务编排（可选）
├── packages/
│   ├── components/           # @my-ui/components  组件本体
│   ├── theme/                # @my-ui/theme       颜色、CSS 变量、主题
│   ├── icons/                # @my-ui/icons       图标
│   ├── hooks/                # @my-ui/hooks       通用组合式逻辑
│   ├── utils/                # @my-ui/utils       纯工具函数
│   └── preset/               # @my-ui/preset      对外的一体化入口（可选）
├── docs/                     # 文档站（VitePress，只给开发者查看，不发 npm）
├── playground/               # 本地调试用的 demo 应用（不发布）
└── tooling/
    ├── eslint-config/        # @my-ui/eslint-config
    └── tsconfig/             # 共享 tsconfig

这里的「不发布」指的是不发布到 npm，不是说文档站不能部署。docs 只是给开发者和使用者看的说明书，里面通常会有 VitePress / Storybook、示例代码、搜索插件等依赖。用户安装组件库时只需要组件、样式和类型声明，不应该顺手把整套文档工程也装进去，否则会增加安装体积、依赖数量和构建成本。

这里的划分逻辑，和「脚手架 monorepo」那篇的原则是一致的：按能力边界拆，不按文件类型拆。theme、icons、hooks、utils 都是能一句话说清职责的包，而不是 types、constants 这种泛泛的分法。

几个划分要点：

包 职责 是否发布 是否有副作用
components 组件实现，依赖 theme/icons/hooks/utils 发布 有（CSS）
theme 设计token（颜色、字体、间距、圆角等）、CSS 变量、暗色/品牌主题 发布 有（CSS）
icons 图标，通常自动生成 发布 无
hooks 框架相关的组合逻辑（如 useDisclosure） 发布 无
utils 纯 JS 工具，无框架依赖 发布 无
docs / playground 文档与调试 不发布 —
tooling/* 内部共享配置 视情况发布 无

最后一列「是否有副作用」现在先记住，它直接决定后面 sideEffects 和 Tree Shaking 怎么配，是组件库能不能被按需引入的关键。

依赖关系：单向、无环

分包之后，最容易失控的就是包之间的依赖。组件库里一个健康的依赖方向是这样的：

@my-ui/components
  ├── @my-ui/theme
  ├── @my-ui/icons
  ├── @my-ui/hooks
  │     └── @my-ui/utils
  └── @my-ui/utils

@my-ui/preset (对外聚合入口)
  ├── @my-ui/components
  ├── @my-ui/theme
  └── @my-ui/icons

几条硬规则：

  1. utils 是最底层，只能被依赖，不能反向依赖任何业务包。它应该是纯 JS、无框架依赖的，这样连 hooks 都能用它。
  2. **theme / icons 不依赖 components**。token 和图标是「原料」，组件是「成品」，成品依赖原料，反过来就成环了。
  3. 绝对不能有循环依赖。components 依赖 hooks，hooks 又反过来 import components，构建顺序会乱、类型解析会出错。这在 Monorepo 里很容易不知不觉发生。

循环依赖是组件库里的高频坑，而且往往是「一个组件顺手 import 了另一个组件的内部工具」引起的。可以用工具在 CI 里守住：

npx madge --circular --extensions ts,tsx packages

madge --circular 会把所有循环依赖列出来。发现循环，正确做法是从设计上把公共部分下沉到 utils，而不是想办法绕过工具。

多包依赖管理：谁依赖谁要写清楚

Monorepo 里最常见的坏味道是「能跑，但依赖没写清楚」。比如 components 里 import 了 @my-ui/utils，但 components/package.json 没声明这个依赖，只是因为根目录或别的包装过，所以本地刚好能解析到。

这种问题在组件库里非常危险：本地能构建，不代表发布后的 npm 包也能用。用户安装的是单个发布包，不是你的整个仓库。

规则很简单：

依赖类型 放哪里 例子
运行时必须带上的内部包 dependencies @my-ui/components 依赖 @my-ui/utils
用户项目必须提供的框架 peerDependencies vue、react、react-dom
本仓库开发、测试、构建才需要 devDependencies typescript、vite、vitest
只在文档站使用 docs 自己的 dependencies vitepress、示例依赖

尤其要注意 peerDependencies 和 devDependencies 经常成对出现。比如组件库对外要求用户提供 vue，所以 vue 要写进 peerDependencies；但组件库自己开发和测试也要 import Vue，所以根包或子包的 devDependencies 里也要有 vue，版本用 catalog 统一。

依赖关系建议在 CI 里加几类检查：

# 检查循环依赖
npx madge --circular --extensions ts,tsx packages

# 检查源码 import 和 package.json 声明是否一致
npx knip

# 检查发布包入口、exports、类型声明等配置
npx publint

knip 更适合发现未声明依赖、未使用依赖和无效导出；publint 更偏发布包检查，能发现一部分 exports、文件入口、类型声明问题；循环依赖则用 madge 更直接。别等用户装包报错，发布前就应该把这些问题拦掉。

内部包怎么互相引用

内部包引用一律用 workspace 协议，这点在 Monorepo 那篇讲过，这里只强调组件库特有的一个细节：

{
  "name": "@my-ui/components",
  "dependencies": {
    "@my-ui/theme": "workspace:*",
    "@my-ui/icons": "workspace:*",
    "@my-ui/utils": "workspace:*"
  },
  "peerDependencies": {
    "vue": "^3.4.0"
  }
}

注意 vue（或 react）放在 **peerDependencies**，不是 dependencies。

这是组件库和普通库最大的区别之一：框架必须是 peer 依赖。如果把 vue 写进 dependencies，用户的项目里就会出现两份 Vue——一份用户自己的，一份从你组件库带进来的。轻则包体积翻倍，重则响应式系统、上下文（如 provide/inject）直接失效，因为两份 Vue 是两套运行时。

我踩过这个坑：一个内部组件库把 vue 错写进 dependencies，结果用户项目里 inject 拿不到 provide 的值，排查半天才发现是两份 Vue 实例。框架、以及框架生态的核心库（vue-router、react-dom），一律 peer。

「源码直连」让联调飞起来

Monorepo 做组件库有一个巨大的开发体验红利：内部包之间可以直接引用 TS 源码，不用先构建。

做法是在开发环境下，让内部包的入口指向源码：

{
  "name": "@my-ui/utils",
  "type": "module",
  "exports": {
    ".": {
      "types": "./src/index.ts",
      "default": "./src/index.ts"
    }
  }
}

这样 components 里 import { xxx } from '@my-ui/utils'，改 utils 的源码，playground 里立刻生效，中间不需要构建 utils。这就是 Monorepo 组件库开发比 Multirepo 顺畅太多的核心原因——改一处，全链路即时可见。

但这里有个坑要提前说清楚：指向 src 的 exports 只适合仓库内部开发，发布时必须换成指向 dist 的构建产物。因为 npm 上的用户没有你的 .ts 源码环境，直接给他们 ./src/index.ts 会让他们的构建报错。

解决方式有两种，后面构建篇会展开：一种是发布前用脚本把 exports 从 src 改写到 dist；另一种是用 publishConfig 覆盖发布时的字段：

{
  "exports": {
    ".": "./src/index.ts"
  },
  "publishConfig": {
    "exports": {
      ".": {
        "types": "./dist/index.d.ts",
        "import": "./dist/index.mjs",
        "require": "./dist/index.cjs"
      }
    }
  }
}

publishConfig 里的字段只在 npm publish / pnpm publish 时生效，把「开发指向源码、发布指向产物」这件事声明式地解决掉。我更推荐这种，比写脚本改文件干净。

根目录放什么、不放什么

组件库的根 package.json 和普通 Monorepo 一样，最重要的是 private: true：

{
  "name": "@my-ui/root",
  "private": true,
  "packageManager": "pnpm@9.0.0",
  "scripts": {
    "build": "turbo run build --filter=./packages/*",
    "dev": "pnpm --filter playground dev",
    "docs:dev": "pnpm --filter docs dev",
    "lint": "eslint .",
    "test": "vitest run",
    "release": "pnpm build && changeset publish"
  },
  "devDependencies": {
    "typescript": "catalog:",
    "turbo": "catalog:"
  }
}

这里有个组件库特有的 filter 用法：build 用 --filter=./packages/* 只构建要发布的包，把 docs、playground 这类不发布的排除掉。你不会想在 CI 发布流程里顺手把 VitePress 文档站也构建一遍——慢，而且没意义。

docs 和 playground 通常不放进 packages/，而是放在根目录下平级，并且不在 pnpm-workspace.yaml 的发布范围里做特殊处理——它们只是内部消费者，package.json 里加 "private": true 保证永远不会被误发。

tsconfig 的组织

组件库多包，TypeScript 用 Project References 做增量检查，这在 Monorepo 那篇讲过。组件库里补一个实践细节：共享配置单独成包。

tooling/tsconfig/base.json：

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "skipLibCheck": true,
    "composite": true,
    "declaration": true,
    "declarationMap": true,
    "jsx": "preserve"
  }
}

各包继承它，并声明对其他包的引用：

{
  "extends": "@my-ui/tsconfig/base.json",
  "compilerOptions": { "rootDir": "src", "outDir": "dist" },
  "references": [
    { "path": "../theme" },
    { "path": "../utils" }
  ],
  "include": ["src"]
}

declarationMap: true 在组件库里体验提升特别明显：用户在自己项目里点组件跳转，能直接跳到你的 .ts 源码而不是编译后的 .d.ts，读源码、debug 都方便。

小结

  1. Monorepo 适合强关联、频繁跨包改动的组件库，不适合把无关项目硬塞进一个仓库。
  2. workspace、catalog、任务编排和 Changesets 沿用前一篇的通用底座，这篇重点是组件库的包边界。
  3. 组件库天然是多包结构：组件、主题、图标、hooks、utils、文档各自独立，共享工具链又能按需发版。
  4. 按能力边界拆包，不按文件类型拆；utils 最底层，theme/icons 不依赖 components。
  5. 框架依赖对外放 peerDependencies，对内用 devDependencies 支撑开发测试，版本继续交给 catalog 统一。
  6. 依赖必须显式、单向、无环，用 madge / knip / publint 在 CI 里提前拦住问题。
  7. 内部包开发时入口指向 src 源码，实现改一处全链路即时生效；发布时用 publishConfig 切换到 dist 产物。
  8. 根包必须 private: true，docs/playground 也加 private，构建时用 filter 只处理要发布的包。
