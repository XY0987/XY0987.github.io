Webpack 核心概念与它和 Vite 的关键差异

发表于2026|更新于2026|工程化
|字数总计:2k|阅读时长:7分钟

前言：Webpack 现在不是新项目的首选，但它还在支撑大量存量系统，面试也常问，更重要的是——理解 Webpack 的 bundle 模型，能反过来帮你想明白 Vite 的 no-bundle 为什么快。这一篇不追求精通 Webpack 配置，目标是掌握共性概念，并把它和 Vite 的关键差异讲透：什么场景今天仍然该选 Webpack。

Webpack 的五个核心概念

Webpack 的整个世界由五个概念撑起来，搞懂这五个，配置文件就不再是天书。

entry ──> [ 依赖图 ] ──> output
              ▲
        loader（翻译各种文件）
        plugin（介入构建生命周期）
              ▼
        chunk（产物如何切块）

entry：从哪里开始

入口，构建依赖图的起点。Webpack 从 entry 出发，递归找出所有依赖。

// webpack.config.js
module.exports = {
  entry: './src/index.js',
  // 也可以多入口（多页应用）
  // entry: { home: './src/home.js', about: './src/about.js' },
}

output：产物放哪、叫什么

module.exports = {
  output: {
    path: __dirname + '/dist',
    filename: '[name].[contenthash].js', // contenthash 利于缓存
    clean: true, // 构建前清空 dist
  },
}

loader：把「非 JS」翻译成模块

这是 Webpack 最核心的设计：一切皆模块。但 Webpack 原生只认 JS，CSS、图片、TS 它不懂。loader 就是「翻译官」，把各种文件转成 Webpack 能塞进依赖图的模块。

module.exports = {
  module: {
    rules: [
      // loader 从右到左、从下到上执行
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
      { test: /\.ts$/, use: 'ts-loader' },
      { test: /\.(png|jpg)$/, type: 'asset/resource' },
    ],
  },
}

注意 use: ['style-loader', 'css-loader'] 的执行顺序是从右往左：先 css-loader 把 CSS 解析成 JS 模块，再 style-loader 把它注入到页面。顺序写反是新手高频坑。

plugin：介入整个构建生命周期

loader 是「文件级翻译」，plugin 是「全局能力」。它能在构建的各个生命周期节点做事：生成 HTML、提取 CSS、压缩、注入环境变量等。

const webpack = require('webpack')
const HtmlWebpackPlugin = require('html-webpack-plugin')

module.exports = {
  plugins: [
    new HtmlWebpackPlugin({ template: './src/index.html' }),
    new webpack.DefinePlugin({
      'process.env.NODE_ENV': JSON.stringify('production'),
    }),
  ],
}

loader 和 plugin 的区别，我的记法：loader 管「单个文件怎么翻译」，plugin 管「整个流程额外干什么」。

chunk：产物怎么切块

chunk 是 Webpack 输出的代码块。默认所有代码打成一个大 bundle，但通过配置可以拆分：第三方依赖一块、公共代码一块、按路由懒加载一块。

module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all', // 自动把 node_modules 等公共依赖拆出去
    },
  },
}

Webpack 的 HMR 实现思路

Webpack 也有 HMR，但实现思路和 Vite 不同。理解它有助于对比。

1. webpack-dev-server 监听文件变化
2. 重新编译"受影响的那部分模块"（增量编译，不是全量）
3. 通过 WebSocket 通知浏览器：有更新，附带一个 hash
4. 浏览器端 HMR runtime 用 hash 拉取更新的 chunk（manifest + 更新代码）
5. 替换运行时模块，调用 module.hot.accept 处理边界

和 Vite 一样靠 WebSocket 通知、靠 module.hot.accept（对应 Vite 的 import.meta.hot.accept）确定边界。但本质区别在于：Webpack 必须先有一个打包结果，更新时是「重新编译受影响的模块并打补丁」；Vite 是「本来就没整体打包，直接重发那一个模块」。

这就是为什么项目越大，Webpack 的 HMR 越慢——它的增量编译仍然要在一个已打包的体系里做计算。

和 Vite 的关键差异

这是这篇的重点。把核心差异列清楚，你才知道该怎么选。

维度 Webpack Vite
开发期策略 bundle（先打包整个应用） no-bundle（浏览器按需请求）
冷启动 随项目变大而变慢 几乎与项目大小无关
构建时机 dev 和 build 都打包 dev 不打包，仅 build 打包
HMR 粒度 重编译受影响模块 + 打补丁 直接重发单个模块
底层语言 JavaScript 上层 JS + 底层 Rust（Rolldown）
生态成熟度 极厚，几乎万物有方案 主流场景齐全，极冷门略少
配置心智 重 轻，约定优于配置

差异一：bundle vs no-bundle

这是最根本的分歧。Webpack 开发时必须先把整个应用打包成 bundle 才能跑；Vite 开发时不打包，靠浏览器原生 ESM 按需加载。前者随项目变大启动越来越慢，后者基本恒定。

差异二：构建时机

Webpack dev 和 build 都走打包，所以 dev/build 行为更一致。Vite dev 不打包、build 才打包，启动飞快但要警惕「dev 正常、build 出问题」的不一致（虽然 Vite 8 统一引擎后大幅缓解）。

差异三：HMR 粒度

都靠 WebSocket + accept 边界，但 Webpack 是在打包体系里做增量编译再打补丁，Vite 是直接重发单个模块。大项目下 Vite 的 HMR 通常更快更稳。

也别把 Webpack 理解成完全没有现代优化。Webpack 5 有持久化缓存（filesystem cache）、lazy compilation 等能力，配置得当时也能明显改善冷启动和重建速度。只是它的基本模型仍然是 bundle-first，和 Vite 的 no-bundle 开发模型不是一类思路。

差异四：生态边界

Webpack 十年积累，loader/plugin 极其丰富，一些非常冷门的需求只有 Webpack 有现成方案。Vite 主流场景（React/Vue/SSR/库）都很完善，但偶尔会碰到「某个老旧需求 Vite 生态还没人做」的情况。

什么场景今天仍优先选 Webpack

实话实说，新项目我基本都上 Vite。但下面这些情况，Webpack（或其 Rust 兼容替代 Rspack）仍然合理：

场景 原因
维护已有大型 Webpack 项目 迁移成本高、收益不确定，别为新而迁
依赖某个只有 Webpack 才有的 loader/plugin 生态边界问题
重度依赖 Module Federation 微前端 Webpack 的联邦方案最成熟（Vite 也有但生态较新）
团队有深厚 Webpack 运维经验 人的成本也是成本

而且要补一句：如果你嫌 Webpack 慢又不想换思路，Rspack 是用 Rust 重写的、和 Webpack 配置/生态高度兼容的替代品，迁移成本比换 Vite 低得多。这部分会在「新一代工具链」那篇展开。

我的判断：不要把「Webpack 老 = 该淘汰」当成铁律。技术选型看的是迁移成本、生态匹配、团队能力，不是新旧。

一个最小可跑的 Webpack 示例

mkdir webpack-demo && cd webpack-demo
npm init -y
npm i -D webpack webpack-cli html-webpack-plugin style-loader css-loader

// webpack.config.js
const HtmlWebpackPlugin = require('html-webpack-plugin')

module.exports = {
  mode: 'development',
  entry: './src/index.js',
  output: { filename: 'bundle.js', clean: true },
  module: {
    rules: [{ test: /\.css$/, use: ['style-loader', 'css-loader'] }],
  },
  plugins: [new HtmlWebpackPlugin({ title: 'Webpack Demo' })],
}

// src/index.js
import './style.css'
document.body.innerHTML = '<h1>Hello Webpack</h1>'

npx webpack
# 看 dist/ 下生成 bundle.js 和 index.html
# CSS 通过 css-loader + style-loader 被打进了 JS

对比着跑一遍 Webpack 和 Vite，你会对 bundle 和 no-bundle 的差异有更直观的体感。

小结

  1. Webpack 五大概念：entry（起点）、output（产物）、loader（翻译单个文件）、plugin（介入全局流程）、chunk（产物切块）。
  2. loader 从右往左执行，顺序写反是高频坑；loader 管文件翻译，plugin 管全局能力。
  3. Webpack HMR 靠增量编译 + 打补丁，Vite 靠直接重发单模块，大项目下 Vite 更快。
  4. 核心差异是 bundle vs no-bundle，由此衍生出冷启动、构建时机、HMR 粒度的不同。
  5. Webpack 5 有持久化缓存、lazy compilation 等现代优化，但基本模型仍是 bundle-first；仍优先选它的场景包括维护存量项目、依赖独有生态、重度微前端联邦、团队经验深厚。
  6. 嫌 Webpack 慢但不想换思路，先考虑 Rspack（Rust 重写、配置兼容），迁移成本更低。
