JavaScript 模块格式与运行时差异

发表于2026|更新于2026|工程化
|字数总计:3.2k|阅读时长:11分钟

前言：很多前端工程问题，表面是“依赖报错”或者“打包产物跑不起来”，本质是模块格式、运行环境和构建目标没有对齐。ESM 和 CJS 很重要，但它们只是 JavaScript 模块格式演进里的一部分。

为什么会有这么多模块格式

JavaScript 最早是在浏览器里通过 <script> 标签运行的，语言本身没有模块系统。大家写复杂项目时，只能把变量挂到全局对象上：

window.App = {
  init() {
    console.log('app init')
  }
}

这种写法简单，但问题也明显：

  1. 全局变量容易冲突；
  2. 文件加载顺序必须靠人维护；
  3. 依赖关系不清晰；
  4. 代码复用和发布都很难管理。

所以社区和运行时环境开始各自解决问题：浏览器侧出现了 IIFE、AMD、UMD，Node.js 里出现了 CommonJS，后来语言标准正式加入了 ESM。

我的理解是：这些格式不是谁“高级”、谁“低级”的关系，而是不同历史阶段、不同运行环境下的工程折中。

常见模块格式全景

先放一张总表，建立整体印象：

格式 典型环境 加载方式 主要用途
IIFE 浏览器 <script> 立即执行函数 传统浏览器全局脚本、独立 SDK
AMD 浏览器 define() / require() 早期浏览器异步模块加载
UMD 浏览器 + Node.js 自动判断环境 同一份产物兼容多种运行环境
CommonJS Node.js require() Node.js 服务端、旧工具链
ESM 浏览器 + Node.js + 构建工具 import / export 现代标准模块系统
System.register 浏览器 + SystemJS System.register() 需要动态加载和兼容旧浏览器的场景

现在新项目里最常见的是 ESM 和 CJS，但在看 npm 包、CDN 产物、旧项目、微前端和组件库打包配置时，IIFE、UMD、AMD 这些名字仍然会出现。

IIFE：把代码包进一个立即执行函数

IIFE 是 Immediately Invoked Function Expression，也就是立即执行函数表达式。

;(function () {
  const version = '1.0.0'

  function init() {
    console.log(`app version: ${version}`)
  }

  window.MyApp = {
    init
  }
})()

它解决的核心问题是：不要把所有变量都暴露到全局作用域。

在没有模块系统的年代，IIFE 是非常实用的封装手段。现在它仍然常见于一些浏览器直引的 SDK：

<script src="https://cdn.example.com/my-sdk.min.js"></script>
<script>
  window.MySDK.init()
</script>

但 IIFE 本身不负责依赖管理。它更像“把一包代码包起来执行”，不是完整意义上的模块系统。

AMD：为浏览器异步加载模块

AMD 是 Asynchronous Module Definition，代表工具是 RequireJS。它主要解决浏览器里的异步模块加载问题。

define(['./math'], function (math) {
  function main() {
    console.log(math.add(1, 2))
  }

  return {
    main
  }
})

使用时通常类似这样：

require(['./app'], function (app) {
  app.main()
})

AMD 的出现有很强的时代背景：当时浏览器没有原生模块，打包工具也没有今天这么成熟，异步加载 JS 文件是一个真实需求。

现在新项目一般不会主动选择 AMD，但如果你维护老项目，或者看到构建产物里有 define(...)，就要知道它不是普通函数调用，而是在声明 AMD 模块。

UMD：一份产物兼容多种环境

UMD 是 Universal Module Definition，它的目标很直接：一份 JS 文件，既能在浏览器全局变量里用，也能在 CommonJS、AMD 环境里用。

典型结构大概长这样：

;(function (root, factory) {
  if (typeof define === 'function' && define.amd) {
    define([], factory)
  } else if (typeof module === 'object' && module.exports) {
    module.exports = factory()
  } else {
    root.MyLib = factory()
  }
})(typeof globalThis !== 'undefined' ? globalThis : this, function () {
  function add(a, b) {
    return a + b
  }

  return {
    add
  }
})

这段代码看起来啰嗦，但思路很朴素：

  1. 如果当前环境支持 AMD，就注册成 AMD 模块；
  2. 如果当前环境支持 CommonJS，就挂到 module.exports；
  3. 否则就挂到全局对象上。

UMD 在组件库和工具库里曾经很常见，尤其是希望同时支持 npm 安装和 CDN 直引时。

现在我的建议是：如果是新库，优先产出 ESM，必要时再补 CJS；只有明确要支持浏览器 <script> 直引时，才考虑 IIFE 或 UMD。

CommonJS：Node.js 里的经典模块系统

CommonJS，也就是 CJS，是 Node.js 早期主要模块系统。

const fs = require('node:fs')

module.exports = {
  readConfig() {}
}

CJS 的特点是运行时加载：

if (process.env.NODE_ENV === 'development') {
  const debug = require('./debug')
  debug.start()
}

这种写法很灵活，但也意味着依赖关系不一定能在代码执行前完整分析出来。

CJS 在 Node.js 生态里仍然非常多，很多老项目、构建配置、脚手架工具都还在使用它。工程上没必要看到 CJS 就急着迁移，关键是看项目是否真的需要 ESM 的能力，以及依赖链是否已经准备好。

ESM：JavaScript 标准模块系统

ES Module，也就是 ESM，是 JavaScript 语言标准里的模块系统。

import fs from 'node:fs'

export function readConfig() {}

ESM 最大的特点是静态结构清晰。也就是说，import 和 export 通常可以在代码执行前被分析出来。

这带来几个好处：

  1. 构建工具更容易做 Tree Shaking；
  2. 浏览器可以原生加载模块；
  3. Node.js、浏览器、打包工具逐渐向同一套标准靠拢；
  4. 顶层 await 等能力可以建立在标准模块语义之上。

简单对比 CJS 和 ESM：

维度 CommonJS ESM
加载方式 require() import / import()
导出方式 module.exports export / export default
加载时机 运行时加载 静态结构，运行前可分析
顶层 await 不支持 支持
典型文件 .cjs .mjs

我的理解是：CJS 更像“运行到这里再加载”，ESM 更像“先把模块依赖图分析清楚”。

System.register：更偏运行时加载的模块格式

有些构建工具还会出现 System.register 产物，它通常和 SystemJS 一起使用。

System.register([], function (exports) {
  return {
    execute: function () {
      function add(a, b) {
        return a + b
      }

      exports('add', add)
    }
  }
})

它的定位不是取代 ESM，而是提供一套运行时模块加载机制。比如某些需要动态加载、兼容旧浏览器、或者微前端相关的场景，会看到这种格式。

普通业务项目里不需要主动使用它。你只要知道：看到 System.register，就说明这份代码不是给浏览器直接按普通脚本理解的，而是要交给 SystemJS 这类加载器执行。

Node.js 怎么判断 ESM 和 CJS

前面讲的是模块格式全景。回到今天最常见的工程问题，还是 ESM 和 CJS 的运行时差异。

Node.js 官方规则里有几个关键点：

文件/配置 模块类型
.mjs 永远是 ESM
.cjs 永远是 CJS
.js + "type": "module" ESM
.js + "type": "commonjs" CJS
.js + 未声明 type 通常按 CJS 处理

所以我建议项目一定显式写 type：

{
  "type": "module"
}

或者：

{
  "type": "commonjs"
}

不要依赖默认行为。默认行为越隐式，排查问题越痛苦。

require 和 import 的解析差异

这是很多报错的根源。

CJS 的 require() 更宽松

require() 会做一些自动尝试：

require('./foo')

它可能尝试：

./foo.js
./foo.json
./foo.node
./foo/index.js

这让 CJS 用起来比较“省事”，但也更依赖 Node.js 的文件系统解析规则。

ESM 的 import 更严格

在 Node.js ESM 中，相对路径通常要写完整扩展名：

// ✅ 正面案例
import { foo } from './foo.js'

// ❌ 反面案例：Node.js ESM 下可能报错
import { foo } from './foo'

它也不支持像 CJS 那样默认把目录当模块解析。

这就是为什么很多 TypeScript + Node.js ESM 项目里，源码写的是：

import { foo } from './foo.js'

明明导入的是 TS 文件，却写 .js。原因是 TypeScript 编译后会输出 .js，Node.js 运行时需要看到真实扩展名。

ESM 没有这些 CJS 全局变量

CJS 里常用：

console.log(__dirname)
console.log(__filename)
console.log(module)
console.log(exports)
console.log(require)

ESM 里没有这些变量。常见替代写法：

import { fileURLToPath } from 'node:url'
import { dirname } from 'node:path'

const __filename = fileURLToPath(import.meta.url)
const __dirname = dirname(__filename)

console.log(__dirname)

import.meta.url 是 ESM 中当前模块的 URL。

CJS 导入 ESM 为什么经常出问题

经典报错：

Error [ERR_REQUIRE_ESM]: require() of ES Module not supported

这通常表示：你在 CJS 里用 require() 加载了一个只支持ESM格式的包。

// CommonJS 文件里
const chalk = require('chalk') // chalk 新版本只支持esm格式时会报错

解决思路有三个：

  1. 把当前项目迁移到 ESM；
  2. 在 CJS 中使用动态 import()；
  3. 降级依赖到仍支持 CJS 的版本。
// CJS 中动态导入 ESM
async function main() {
  const chalk = await import('chalk')
  console.log(chalk.default.green('hello'))
}

main()

这不是最优雅，但在老项目里经常是过渡方案。

ESM 导入 CJS 的默认导出问题

CJS 导出：

module.exports = function createClient() {}

ESM 中通常这样导入：

import createClient from './client.cjs'

但如果 CJS 导出的是对象：

module.exports = {
  createClient() {}
}

ESM 命名导入不一定总是可靠：

import { createClient } from './client.cjs'

Node.js 会尝试静态分析 CJS 的命名导出，但不是所有写法都能准确分析。更稳妥的方式是默认导入后再取属性：

import client from './client.cjs'

client.createClient()

require.resolve 与 import.meta.resolve

CJS 里常用 require.resolve 找到模块实际路径：

const path = require.resolve('react')
console.log(path)

ESM 里可以使用 import.meta.resolve：

const url = import.meta.resolve('react')
console.log(url) // file:///path/to/node_modules/react/index.js

要注意二者返回形式不同：

  • require.resolve 返回的是文件系统路径字符串（/path/to/...）。
  • import.meta.resolve 返回的是 file:// URL 字符串——如果要当路径用，需要 fileURLToPath(url) 转一下。

版本方面，import.meta.resolve 在 Node 20.6+ / 18.19+ 已稳定、默认可用（更早版本需要 --experimental-import-meta-resolve 标志）。写工具链代码时，最好根据项目目标 Node.js 版本确认官方文档。

打包产物应该选哪种格式

如果你在 Vite、Rollup、tsup、unbuild 这类工具里看到 format 配置，通常就是在选择输出模块格式。

我的建议是：

场景 建议格式
新前端应用 ESM，由构建工具处理最终产物
新 Node.js 工具 优先 ESM，但确认依赖兼容
老 Node.js 项目 CJS，不急着全量迁移
npm 工具库 ESM + CJS 双产物，按用户群体决定
浏览器 CDN 直引 IIFE 或 UMD
需要兼容 AMD 加载器的旧系统 AMD 或 UMD
微前端运行时加载场景 视框架要求选择 ESM、UMD 或 System.register

这里最容易踩坑的是：不要把“源码模块格式”和“发布产物格式”混为一谈。

源码里你可以用 ESM 写：

export function add(a, b) {
  return a + b
}

但发布时可以输出多种格式：

dist/index.mjs       # ESM
dist/index.cjs       # CommonJS
dist/index.iife.js   # IIFE
dist/index.umd.js    # UMD

也就是说，模块格式不是只在写代码时决定，也会在构建和发布阶段再次被选择。

我的实战建议

如果是普通业务项目，不要把模块格式问题复杂化：

  1. 前端应用源码统一写 ESM；
  2. Node.js 新项目优先 ESM，但先确认依赖和运行版本；
  3. 老 Node.js 项目继续 CJS 也没问题，迁移要看收益；
  4. 发 npm 包时认真设计 exports、type 和产物格式；
  5. 只有明确要支持 CDN 直引时，再考虑 IIFE / UMD；
  6. 只有维护旧系统时，才需要重点关注 AMD。

现在生态整体在向 ESM 迁移，但 CJS、IIFE、UMD 仍然会长期存在。工程上不要为了“新”强行迁移，应该看运行环境、依赖生态、发布目标和团队成本。

小结

  1. IIFE 主要解决浏览器全局变量污染问题，但不是真正完整的模块系统。
  2. AMD 主要服务早期浏览器异步模块加载，现在更多出现在旧项目里。
  3. UMD 追求一份产物兼容浏览器、CJS 和 AMD，适合需要广泛兼容的库。
  4. CJS 是 Node.js 经典模块系统，ESM 是 JavaScript 标准模块系统。
  5. 新项目优先理解 ESM，但排查工程问题时要同时看源码格式、运行环境和构建产物格式。
