SSE 与 WebSocket 对比：从协议底层到 AI 流式处理

发表于2026|更新于2026|前端基础
|字数总计:4k|阅读时长:14分钟

前言：这篇从前端基础视角把 SSE 和 WebSocket 讲透，再落到 AI 流式处理上。不是教你怎么接 ChatGPT，而是讲清楚”浏览器里的流到底是怎么流起来的”。

之前写过一篇 SSE 流式调用 AI 大模型实战，偏实战落地。这篇换一个视角——从 HTTP 协议层往上讲，搞清楚 SSE 和 WebSocket 在底层到底是什么、为什么 AI 场景几乎都选 SSE、以及 fetch + ReadableStream 和 EventSource 到底差在哪。

一、先从 HTTP 说起

要理解 SSE 和 WebSocket，得先理解一个关键概念：HTTP 响应体不是”一次性返回”的。

1.1 Transfer-Encoding: chunked

HTTP/1.1 协议里有一个叫 Transfer-Encoding: chunked 的传输编码。它允许服务器不提前知道响应总大小，而是把响应体切成一块一块（chunk）陆续发送：

HTTP/1.1 200 OK
Content-Type: text/plain
Transfer-Encoding: chunked

7\r\n
Mozilla\r\n
9\r\n
Developer\r\n
7\r\n
Network\r\n
0\r\n
\r\n

每个 chunk 先发一个十六进制的长度，再发数据，最后用 0\r\n\r\n 表示结束。SSE 本质上就是基于 chunked 传输的一种约定格式，并没有什么神秘的地方。

这也是为什么生产环境 Nginx 默认 proxy_buffering on 会毁掉流式——它会攒一大堆 chunk 再一起发给客户端，所谓的”流”就没了。

1.2 HTTP 本身不支持双向

HTTP 的模型是 请求-响应：客户端发一个请求，服务器回一个响应。一个连接在同一时刻只能”服务器往客户端写”或”客户端往服务器写”，不能同时双向。

这就是 WebSocket 存在的根本原因——它跳出了 HTTP 的请求响应模型，建立一个真正的全双工通道。

二、SSE：HTTP 的流式约定

SSE 全称 Server-Sent Events，中文叫”服务器推送事件”。本质上就是一个 HTTP 长连接 + 一种文本格式约定。

2.1 协议长什么样

服务器返回一个 Content-Type: text/event-stream 的响应，然后持续往里写符合 SSE 格式的文本：

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

data: hello

data: world

event: update
data: {"progress": 50}

id: 42
data: 带ID的消息

: 这是注释行，用于心跳

规则很朴素：

  • 每个字段一行，格式 字段名: 值
  • 消息之间用空行分隔（这是关键）
  • data 可以多行，多行会被拼接（用 \n 连接）
  • 以冒号开头的是注释，常用于心跳保活

就这么简单。没有握手、没有帧结构、没有魔数，纯文本。

2.2 EventSource：浏览器原生客户端

浏览器内置了一个叫 EventSource 的 API 专门处理 SSE：

// 最小可运行示例
const es = new EventSource('/api/stream');

es.onmessage = (e) => {
  console.log('收到:', e.data);
};

// 监听自定义事件类型
es.addEventListener('update', (e) => {
  console.log('update 事件:', JSON.parse(e.data));
});

// 错误会自动重连，不需要手动处理
es.onerror = (e) => {
  console.log('连接异常，浏览器会自动重连');
};

EventSource 最大的价值是自动重连：连接断了，浏览器会自己重新连上来，默认间隔 3 秒（可通过服务器 retry: 字段调整）。如果服务器发过 id: 字段，重连时还会带上 Last-Event-ID 请求头，服务端可以据此实现断点续传。

2.3 EventSource 的致命限制

看起来很美好，但它有两个硬伤：

  1. 只能 GET：不支持 POST，想传复杂参数只能拼在 URL 里或者走一次预请求
  2. 不能自定义 header：Authorization: Bearer xxx 这种鉴权头加不上

这两个限制直接决定了——**只要你要传 token、要发 POST，就不能用 EventSource**。

这就是为什么 AI 场景下大家清一色用 fetch + ReadableStream 而不是 EventSource。

三、WebSocket：真正的双向通道

3.1 从握手到全双工

WebSocket 的生命周期有两个阶段：

阶段1：HTTP 握手（Upgrade）
─────────────────────────────
客户端:
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

服务器:
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

─────────────────────────────
阶段2：切换到 WebSocket 帧协议
─────────────────────────────
双方开始在同一个 TCP 连接上
以二进制帧（frame）格式双向通信

握手用的是 HTTP，握完之后协议”升级”成了完全不同的东西——以二进制帧为单位的全双工通信，URL schema 也从 http:// 变成了 ws://（或 wss://）。

3.2 客户端 API

const ws = new WebSocket('wss://example.com/chat');

ws.onopen = () => {
  ws.send(JSON.stringify({ type: 'hello', name: 'Alice' }));
};

ws.onmessage = (e) => {
  // e.data 可能是 string 也可能是 Blob/ArrayBuffer
  console.log('收到:', e.data);
};

ws.onclose = (e) => {
  console.log('关闭:', e.code, e.reason);
  // 注意：需要自己实现重连逻辑
};

ws.onerror = (e) => {
  console.error('出错了');
};

跟 EventSource 相比，WebSocket 能发能收，但需要自己处理重连、心跳、消息序列化。

四、SSE vs WebSocket 全面对比

维度 SSE WebSocket
底层协议 HTTP/1.1 chunked TCP（HTTP 握手后升级）
方向 单向：服务器 → 客户端 双向全双工
数据格式 UTF-8 文本 文本或二进制帧
浏览器 API EventSource WebSocket
自动重连 内置支持 需自行实现
跨域 走 HTTP 的 CORS 规则 有自己的跨域策略
自定义 Header EventSource 不支持 握手 header 浏览器限制较多
代理穿透 友好（就是 HTTP） 部分老旧代理不支持 Upgrade
HTTP/2 支持 原生支持多路复用 需 HTTP/2 WebSocket（RFC 8441）
服务端资源 连接数 = HTTP 并发数 长连接常驻，需关注 fd

4.1 什么时候用 SSE

只要你的场景是服务器主动往客户端推，而客户端不需要频繁往服务器发消息，就应该优先考虑 SSE。典型场景：

  • AI 大模型流式输出
  • 消息通知、系统公告推送
  • 实时日志、监控数据大屏
  • 长任务进度反馈
  • 股票/加密货币价格推送

4.2 什么时候用 WebSocket

双方都要频繁、低延迟地发消息，才真正需要 WebSocket：

  • 聊天室、IM
  • 多人协同编辑（Figma、腾讯文档）
  • 在线游戏
  • 需要传二进制的场景（音视频流、文件传输）

4.3 我的判断

AI 聊天场景用 WebSocket 是典型的过度设计。我见过有团队坚持用 WebSocket 做 AI 对话，理由是”未来可能要做语音双向”，结果：

  • 服务端要维护连接池，对运维不友好
  • Nginx/网关需要配置 Upgrade 支持
  • 鉴权要走自定义握手流程
  • 客户端要自己实现重连和心跳

而 AI 对话实际上是一问一答的请求响应模式，只是响应是流式的。用 SSE 一个 HTTP 请求搞定，部署、鉴权、重连全都不是问题。

五、AI 流式处理的底层原理

5.1 为什么 AI 必须流式

大模型的生成过程是 token by token 的——一个词一个词往外吐。非流式等于”等全部生成完一起返回”，用户要等 5-30 秒盯着白屏。流式则是生成一个 token 就推一个，用户从第一个字就开始看。

这不是前端的优化技巧，这是由大模型的自回归生成特性决定的——既然后端本来就是流式生成的，前端就没理由等它攒完再给用户看。

5.2 AI 场景下的 SSE 格式

OpenAI 兼容接口的流式响应格式基本都是这样：

data: {"choices":[{"delta":{"content":"你"}}]}

data: {"choices":[{"delta":{"content":"好"}}]}

data: {"choices":[{"delta":{"content":"！"}}]}

data: [DONE]

注意几个细节：

  • 每条 data: 里是一个 JSON，包含一小段 delta 内容
  • 最后用字符串 [DONE]（不是 JSON）表示结束
  • 这是 OpenAI 自己约定的格式，不是 SSE 协议本身的要求

5.3 为什么是 fetch + ReadableStream，而不是 EventSource 或 axios

这是个容易被忽略的问题：浏览器里能发请求的 API 有三个——XMLHttpRequest（axios 的底层）、fetch、EventSource。AI 流式场景下只有 fetch 能打，另外两个都不行。

先看三者的关键能力矩阵：

能力 XHR / axios EventSource fetch
POST 请求 支持 不支持 支持
自定义 header（如 Authorization） 支持 不支持 支持
流式读取响应体 伪流式 支持（封装过） 支持（原生 ReadableStream）
取消请求 xhr.abort() es.close() AbortController
底层返回类型 字符串累积 解析后的事件 ReadableStream<Uint8Array>

三者都”能拿到流式数据”吗？看起来是，但只有 fetch 是真流式。

EventSource 的问题：协议限制死了——只能 GET、不能加自定义 header。AI 接口普遍要 Authorization: Bearer xxx 做鉴权、要 POST 传 messages 数组，直接出局。

axios / XHR 的问题要细说。XHR 确实有一个 onprogress 事件，看起来能”边下边读”：

// ❌ 基于 XHR 的伪流式方案
const xhr = new XMLHttpRequest();
xhr.open('POST', '/api/chat');
xhr.setRequestHeader('Authorization', 'Bearer xxx');

let lastIndex = 0;
xhr.onprogress = () => {
  // responseText 是从开头到当前的全部文本
  const chunk = xhr.responseText.substring(lastIndex);
  lastIndex = xhr.responseText.length;
  handleChunk(chunk);
};

xhr.send(JSON.stringify({ messages }));

这段代码确实能跑，但它有三个硬伤：

  1. 内存持续膨胀：xhr.responseText 会保留从请求开始到现在的全部响应文本，不会随着读取而释放。AI 回答几千字还好，如果是几万字的长文档生成，浏览器内存会一直涨——这不是流，是”在不断变长的字符串上打游标”。
  2. 字符串切片效率低：每次 onprogress 都要对整个 responseText 做 substring，数据量大了之后 CPU 也扛不住。
  3. axios 根本没暴露这个能力：axios 的 onDownloadProgress 回调只给你进度百分比，不给你增量数据。想用 axios 玩流式，只能自己退回到裸 XHR，失去了 axios 封装的意义。

fetch 为什么是真流式：response.body 返回的是一个 ReadableStream<Uint8Array>，这是 WHATWG Streams 标准的原生流对象。每次 reader.read() 拿到的是只属于这一段的字节，读完就被 GC 回收，不会在内存里堆积。加上 AbortController 能干净地中断整个流，整条链路都是标准化的。

// ✅ fetch 的流是真流，每个 chunk 读完就释放
const reader = response.body.getReader();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  // value 是 Uint8Array，只包含本次新到的字节
  // 处理完之后这部分内存就可以回收了
}

一句话总结：EventSource 限制太死（GET + 无 header），axios/XHR 是”假流”（全量累积 + 无增量 API），fetch 是浏览器里目前唯一的真流式 HTTP 客户端。所以前端标准解法就是 fetch + ReadableStream：

// streamAI.mjs —— 最小可运行的 AI 流式消费代码
// 环境：Node.js 20+ 或现代浏览器

async function streamAI() {
  const response = await fetch('https://api.openai.com/v1/chat/completions', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${process.env.OPENAI_API_KEY}`
    },
    body: JSON.stringify({
      model: 'gpt-4o-mini',
      stream: true,
      messages: [{ role: 'user', content: '用一句话介绍 SSE' }]
    })
  });

  // response.body 是一个 ReadableStream<Uint8Array>
  const reader = response.body.getReader();
  const decoder = new TextDecoder('utf-8');
  let buffer = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    // 关键：stream: true，避免多字节字符在 chunk 边界被切坏
    buffer += decoder.decode(value, { stream: true });

    // 按 SSE 的空行分隔符切出完整消息
    const parts = buffer.split('\n\n');
    buffer = parts.pop() ?? ''; // 最后一段可能不完整，留到下次

    for (const part of parts) {
      const line = part.split('\n').find(l => l.startsWith('data: '));
      if (!line) continue;

      const payload = line.slice(6).trim();
      if (payload === '[DONE]') return;

      try {
        const json = JSON.parse(payload);
        const delta = json.choices?.[0]?.delta?.content;
        if (delta) process.stdout.write(delta);
      } catch {
        // 非 JSON 的 data（如注释/心跳）跳过
      }
    }
  }
}

streamAI();

这段代码看着简单，但里面藏着三个前端基础知识的”必考点”：

5.4 三个必须注意的细节

细节 1：多字节字符被切断

TextDecoder.decode(chunk, { stream: true }) 里的 stream: true 不能漏。因为网络传来的 Uint8Array 可能在任意字节切断，中文一个字三字节，很容易切在中间变成乱码。stream: true 会让 decoder 把不完整的字节序列缓存起来，等下一个 chunk 拼完整再解码。

// ❌ 反面案例：中文字符可能变成 
buffer += decoder.decode(value);

// ✅ 正面案例
buffer += decoder.decode(value, { stream: true });

细节 2：SSE 消息边界

一次 reader.read() 读出来的数据不一定是完整的一条 SSE 消息——可能是半条，也可能是好几条。必须用 \n\n 分隔、并把最后不完整的部分留到 buffer 里等下次。

这个坑我踩过——早期代码写成每读一次就 JSON.parse 一次，偶尔就报 Unexpected end of JSON input。现象是偶发、无规律，排查时一脸懵。原因就是 TCP 层面的数据分片和应用层的消息边界不一致。

细节 3：前端渲染节流

setState 在每一个 token 都触发一次，React 的 reconciliation 会被打爆。即使是很简单的聊天界面，一秒钟几十次 setState 也会明显掉帧。

// ❌ 每个 token 都 setState
for await (const token of stream) {
  setContent(prev => prev + token); // 一秒触发 30+ 次重渲染
}

// ✅ 用 requestAnimationFrame 合并到下一帧
const bufferRef = useRef('');
const rafRef = useRef(null);

function append(token) {
  bufferRef.current += token;
  if (rafRef.current) return;
  rafRef.current = requestAnimationFrame(() => {
    setContent(bufferRef.current);
    rafRef.current = null;
  });
}

requestAnimationFrame 把多次变更合并到一帧内，60fps 上限，天然节流。

六、一些延伸话题

6.1 AbortController 统一取消

流式请求一定要支持”停止生成”按钮。fetch 的原生取消机制就是 AbortController：

const controller = new AbortController();

fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ message }),
  signal: controller.signal
});

// 用户点停止
stopButton.onclick = () => controller.abort();

abort() 会同时终止请求和 ReadableStream 的读取，干净利落。WebSocket 则要自己 ws.close() 并清理状态，啰嗦得多。

6.2 Streamable HTTP：SSE 的升级

MCP 协议 2025 年 3 月把传输层从 “HTTP + SSE” 升级成了 Streamable HTTP。核心变化是一个端点同时支持普通 HTTP 响应和 SSE 响应，按需升级，无状态更友好。

但对于 AI 聊天应用本身，SSE 仍然够用——Streamable HTTP 主要是为 MCP 这种需要工具调用、服务端主动发起请求的复杂场景设计的。

6.3 HTTP/2 下 SSE 的并发问题

HTTP/1.1 下浏览器对同一域名的并发连接数限制是 6。SSE 是长连接，一个 tab 开一个就占一个名额，多开几个 tab 网站就打不开了——这是 HTTP/1.1 时代 SSE 的真实痛点。

HTTP/2 的多路复用彻底解决了这个问题：同一个 TCP 连接上可以跑成百上千个流，SSE 只是其中的普通一个流。所以生产部署上，启用 HTTP/2 对 SSE 来说几乎是白嫖的性能提升。

小结

  1. SSE 本质是 HTTP chunked 传输 + 一种文本格式约定，没什么玄学
  2. WebSocket 是 HTTP 握手后升级到的全双工二进制协议，能力强但复杂度也高
  3. 服务器单向推送优先选 SSE，真双向高频通信才上 WebSocket
  4. AI 聊天场景清一色用 fetch + ReadableStream，因为 EventSource 不支持 POST 和自定义 header
  5. 前端消费流式响应要过三关：多字节字符边界、SSE 消息边界、渲染节流
  6. AbortController 是流式请求取消的标准方案
  7. HTTP/2 让 SSE 的并发短板消失，生产环境建议启用
