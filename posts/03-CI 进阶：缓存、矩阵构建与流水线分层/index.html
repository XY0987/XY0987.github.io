CI 进阶：缓存、矩阵构建与流水线分层

发表于2026|更新于2026|工程化
|字数总计:2.2k|阅读时长:7分钟

前言：上一篇搭好了一条能跑的自动检查流水线。但真实项目跑久了会遇到两个问题：一是 CI 越来越慢（每次重装依赖、重复构建），二是要覆盖多环境（多个 Node 版本、多操作系统）。这一篇讲三个进阶手段——缓存加速、矩阵构建、流水线分层——把 CI 从「能跑」变成「又快又全」。工具慢了就会有人想绕开它，所以让 CI 快，本身就是保障它被认真对待的前提。

缓存：CI 提速的第一杠杆

CI 每次都在全新机器上跑，默认什么都要从头来：重新下载所有 npm 依赖、重新做各种构建中间物。依赖安装往往是最耗时的一步，缓存它收益最大。

前面用的 setup-node 的 cache: pnpm 已经缓存了 pnpm store。但对更复杂的场景，用 actions/cache 手动控制缓存粒度：

      - uses: actions/cache@v4
        with:
          path: ~/.local/share/pnpm/store    # pnpm 的全局 store
          # key 里带 lockfile 的哈希：依赖没变就命中，变了就重建
          key: pnpm-store-${{ hashFiles('pnpm-lock.yaml') }}
          restore-keys: pnpm-store-           # 精确 key 没命中时的退路

actions/cache 的核心是这套 key 机制：

  • **key**：缓存的唯一标识。这里用 pnpm-lock.yaml 的哈希——lockfile 没变说明依赖没变，直接命中旧缓存；lockfile 一变哈希就变，key 变了自然重建。
  • restore-keys：精确 key 没命中时的前缀模糊匹配退路。比如加了一个依赖 lockfile 变了，精确 key 没命中，但能匹配到 pnpm-store- 开头的旧缓存，在它基础上只下增量，比全量下快得多。

这套「用内容哈希当 key」的思路是所有缓存的通用模式，不只依赖——构建缓存、测试缓存都能这么设计。

一个常见误区：key 设成固定字符串（比如 key: pnpm-store）。这样它永远命中第一次的缓存，依赖更新了也读旧的，会出现「本地新装的依赖 CI 里没有」的诡异问题。key 一定要包含能反映内容变化的东西（lockfile 哈希）。

Turborepo 远程缓存：Monorepo 的杀手锏

上面的缓存是「缓存依赖」。Monorepo 里还有更狠的一招——缓存任务的执行结果。

在《Monorepo 工程化实践》里讲过 Turborepo 的本地缓存：同样的输入（源码 + 依赖 + 配置），它记住上次 build / test 的结果，输入没变直接吐出上次的产物和日志，跳过执行。远程缓存（Remote Cache）把这块缓存放到云端团队共享：

你本地构建过 pkg-a          → 结果上传到远程缓存
同事 / CI 构建同样的 pkg-a  → 直接从远程缓存拉，秒出，不重跑

它的威力在 CI 上尤其明显：只改了包 A，包 B、C、D 的构建和测试输入没变，全部命中缓存跳过。PR 的 CI 时间从「构建整个仓库」缩短到「只构建真正变了的那部分」。

配置思路（Turborepo 为例）：

      - run: pnpm build
        env:
          TURBO_TOKEN: ${{ secrets.TURBO_TOKEN }}
          TURBO_TEAM: my-team
          # 或用自建 remote cache 服务，配 TURBO_API

要点：远程缓存的正确性完全依赖「输入哈希」算得准。Turborepo 靠 turbo.json 里声明的 inputs / outputs / dependsOn 计算哈希。如果漏声明了某个会影响产物的输入（比如某个环境变量、某个配置文件），就会出现「输入其实变了但哈希没变 → 错误命中旧缓存」的隐蔽 bug。用远程缓存的前提是把任务的输入声明干净，这是它比依赖缓存更需要谨慎的地方。

矩阵构建：一套配置跑多个组合

前端库经常要保证「在多个 Node 版本、多个操作系统下都能用」。手写 N 份几乎一样的 job 太蠢，matrix（矩阵）让你声明维度、自动展开成所有组合：

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false            # 一个组合挂了，不要连带取消其他组合
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm install
      - run: npm test

这份配置会展开成 3 × 3 = 9 个并发 job（三系统 × 三 Node 版本）。几个关键点：

  • **fail-fast: false**：默认矩阵里任一组合失败会取消其他所有组合。测多环境兼容性时要关掉它——你想知道「到底哪些组合挂了」，而不是第一个挂就全停。
  • 矩阵会放大 CI 消耗：9 个 job 就是 9 倍的机器时间。别对每个 PR 都跑全矩阵。常见做法：PR 只跑一个主组合（如 ubuntu + Node 20）快速反馈，全矩阵只在合入主干或发布前跑。
  • 应用项目 vs 库项目：给别人用的库才真正需要多版本矩阵（用户环境不可控）；自己部署的应用通常锁定一个运行环境，测那一个就够，别为用不上的矩阵浪费额度。
    matrix:
      # include 可以精细控制组合，避免全笛卡尔积的浪费
      include:
        - { os: ubuntu-latest, node: 20 }   # 主组合，PR 就跑它
        - { os: windows-latest, node: 20 }  # 只补关键的额外组合

流水线分层：fast feedback → test → build → deploy

前面的检查如果全挤在一个 job 里串行，会有个体验问题：一个耗时的 E2E 挂了，但其实一开始 lint 就该红。更好的组织是分层——按「反馈速度」和「依赖关系」把流水线切成几层：

第 1 层  fast feedback     lint + typecheck        几十秒，最快暴露低级问题
   │      （挂了直接停，不浪费后面的机器）
   ▼
第 2 层  test              单元 + 组件测试          几分钟
   │
   ▼
第 3 层  build             构建产物                 几分钟
   │
   ▼
第 4 层  deploy / e2e      部署预览、E2E、性能门禁   最慢，且往往要密钥

用 needs 表达这个分层：

jobs:
  fast-check:                     # 第 1 层：最快的检查
    runs-on: ubuntu-latest
    steps: [ ... lint + typecheck ... ]

  test:                           # 第 2 层：依赖第 1 层通过
    needs: fast-check
    runs-on: ubuntu-latest
    steps: [ ... vitest run ... ]

  build:                          # 第 3 层
    needs: test
    runs-on: ubuntu-latest
    steps: [ ... vite build ... ]

  deploy-preview:                 # 第 4 层：只在特定条件跑
    needs: build
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps: [ ... 部署预览环境 ... ]

分层的好处很实在：

  1. 快速失败省资源：lint 就挂了，根本不会启动昂贵的 build 和 deploy 机器。
  2. 反馈分层：几十秒就知道有没有低级问题，不用等整条跑完。
  3. 职责清晰：需要密钥的 deploy 单独一层，能针对性控制权限和触发条件（呼应上一篇「fork PR 拿不到 secrets，检查和部署要分开」）。

分层不用一步到位，先分「快检查」和「慢检查」两层就有明显收益。lint/typecheck 一层、test/build/e2e 一层，光这个改动就能让大多数失败在一分钟内暴露。

一个真实的坑：缓存把 bug 藏起来了

现象：CI 一直绿，但同事 clone 下来全新构建却报错。

原因：CI 命中了旧缓存，跳过了真正的重新安装/构建，用的是缓存里的旧产物，掩盖了「新代码在干净环境下其实跑不通」的问题。

解决：

  1. 关键的发布/主干流水线定期跑一次「无缓存」的干净构建，验证从零能不能成功。
  2. 缓存 key 一定要包含内容哈希，别用固定 key。
  3. 怀疑缓存作怪时，清掉缓存重跑（GitHub 在 Actions → Caches 里可手动删）。

缓存是双刃剑：它加速的同时，也可能让 CI 测的不是真实的当前状态。享受它的速度，就要记得偶尔来一次「从零验证」，确认地基没被缓存糊住。

小结

  1. 缓存是 CI 提速第一杠杆，核心是「用内容哈希当 key」，配 restore-keys 做模糊退路，别用固定 key。
  2. Monorepo 用 Turborepo 远程缓存共享任务结果，PR 只构建真正变了的部分，但前提是把任务的 inputs/outputs 声明干净。
  3. 矩阵构建用一套配置展开多组合，测兼容性要 fail-fast: false；库项目才需要多版本矩阵，应用锁定环境即可。
  4. 矩阵放大消耗，PR 跑主组合快速反馈，全矩阵留给主干/发布前。
  5. 流水线分层（fast feedback → test → build → deploy）用 needs 表达，快速失败省资源、反馈分层、职责清晰。
  6. 分层不必一步到位，先分「快检查 / 慢检查」两层就有明显收益。
  7. 缓存可能掩盖「干净环境跑不通」的 bug，主干/发布流水线定期跑一次无缓存的从零验证。
