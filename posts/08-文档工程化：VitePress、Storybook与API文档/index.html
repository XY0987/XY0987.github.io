文档工程化：VitePress、Storybook 与 API 文档

发表于2026|更新于2026|工程化
|字数总计:4.2k|阅读时长:15分钟

前言：组件库没有文档等于没发布。但文档不是「写一堆 Markdown」这么简单——它是一套工程：示例要能跑、API 要和代码同步、CHANGELOG 要自动生成。这一篇讲组件库文档的几套工具怎么分工：VitePress 建站、Storybook 做示例驱动开发、TypeDoc 自动生成 API、Changesets 自动化 CHANGELOG。核心是让文档「跟着代码走」，而不是靠人肉维护。

文档工程的三个层次

先理清组件库文档到底包含什么，别一上来就纠结用哪个工具。文档其实是三类不同的东西：

层次 内容 谁来维护 工具
使用文档 怎么安装、怎么用、示例 人写 VitePress
组件开发/示例 组件各状态的可交互示例 跟组件一起写 Storybook
API 参考 props、类型、返回值 从代码自动生成 TypeDoc

关键判断：能自动生成的（API 参考）就别手写，会手写的（教程、示例）要写好。手写 API 表格是文档腐烂的头号原因——代码改了 props，文档表格没跟上，用户照着过时文档踩坑。

VitePress：建组件库文档站

VitePress 是 Vue 团队的静态站点生成器，基于 Vite，启动快、Markdown 里能原生跑 Vue 组件——这对 Vue 组件库文档是决定性优势：你可以在文档里直接渲染真实组件，而不是贴截图。

搭一个最小文档站：

pnpm add -D vitepress

docs/
├── .vitepress/
│   └── config.ts
├── index.md
├── guide/
│   └── getting-started.md
└── components/
    └── button.md

配置：

// docs/.vitepress/config.ts
import { defineConfig } from 'vitepress'

export default defineConfig({
  title: 'My UI',
  description: '一个组件库',
  themeConfig: {
    nav: [
      { text: '指南', link: '/guide/getting-started' },
      { text: '组件', link: '/components/button' },
    ],
    sidebar: {
      '/components/': [
        { text: '基础', items: [{ text: 'Button', link: '/components/button' }] },
      ],
    },
  },
})

在 Markdown 里渲染真实组件

这是 VitePress 做组件库文档的杀手锏。在 .vitepress/theme/index.ts 里全局注册你的组件，然后 Markdown 里直接用：

// docs/.vitepress/theme/index.ts
import DefaultTheme from 'vitepress/theme'
import MyUI from '@my-ui/components'
import '@my-ui/components/style.css'

export default {
  extends: DefaultTheme,
  enhanceApp({ app }) {
    app.use(MyUI)     // 注册组件库，文档里就能用
  },
}

<!-- button.md -->
# Button

<MyButton type="primary">主要按钮</MyButton>

```vue
<template>
  <MyButton type="primary">主要按钮</MyButton>
</template>
```

上面既渲染了真实按钮，又展示了源码。用户看到的示例就是真组件，不会和实际行为脱节。

这里要说清楚：VitePress 不是只能展示 Vue 生态的东西，但它原生最顺手的是 Vue 组件。因为 VitePress 的 Markdown 最终会被当成 Vue SFC 处理，所以 Vue 组件可以直接写在 Markdown 里。

React 组件当然也能做文档，只是路线不同：

场景 更合适的方案
Vue 组件库 VitePress 直接渲染组件
React 组件库 Docusaurus / Nextra / Storybook
多框架组件库 Storybook 作为统一组件工作台，文档站再嵌入示例

如果硬要在 VitePress 里跑 React，也不是完全不行，可以写 Vue wrapper 去挂载 React，或者把 React 示例打成 iframe 嵌进去。但我的建议是别把文档工程搞别扭：React 组件库优先用 React 生态的文档工具，Vue 组件库再优先考虑 VitePress。

移动端组件也类似，关键看它是什么类型：

类型 文档里怎么展示
移动端 H5 组件（Vue/React） 在浏览器里用窄 viewport、手机外框、iframe 真实渲染
响应式 Web 组件 Storybook viewport addon / 文档站里的设备预览容器
React Native / Flutter 这类原生组件 用对应生态的 Storybook、Expo、模拟器截图或录屏

也就是说，移动端 H5 组件依然可以「跑真实组件」，只是要把预览区域限制成手机尺寸；真正的原生组件不能直接在普通 Web 文档站里运行，通常靠平台自己的预览工具，再把结果接进文档。

Vant 这类移动端组件库文档就是典型做法：PC 文档站负责写说明和 API，右侧手机预览其实是一个 iframe，iframe 里跑的是组件库开发者写好的 mobile demo 页面。

桌面文档站
  ├── 左侧：组件目录
  ├── 中间：Markdown 文档、API、代码示例
  └── 右侧：手机预览容器
        └── iframe
              └── mobile demo SPA
                    ├── /button
                    ├── /popup
                    └── /calendar

比如切到 Button 文档时，右侧 iframe 可能加载的是：

<iframe src="/mobile.html#/button"></iframe>

这个 /mobile.html#/button 不是截图，也不是文档工具自动生成的神奇页面，而是开发者维护的一套路由化 demo 应用。每个组件都有自己的 demo 文件，比如 ButtonDemo.vue、PopupDemo.vue，里面直接引用组件库源码或构建产物。这样用户在 PC 文档站看到的是手机尺寸预览，扫码或打开同一个地址时，又能在真实手机浏览器里体验。

移动端 H5 组件库不要只在文档正文里摆几个静态示例，最好单独维护一套 mobile demo。文档讲清楚「怎么用」，demo 负责证明「真的能跑」。

主题定制

VitePress 的默认主题够用，但组件库通常要品牌化。定制主要靠覆盖 CSS 变量（VitePress 主题本身就是用 CSS 变量搭的，正好呼应设计系统那篇）：

/* docs/.vitepress/theme/custom.css */
:root {
  --vp-c-brand-1: #7c3aed;      /* 品牌主色 */
  --vp-c-brand-2: #6d28d9;
}

深度定制可以用 slot 覆盖布局的特定区域，或直接自定义 layout。但我的建议是别过度定制文档站——用户是来看组件怎么用的，不是来看你文档站多花哨的。默认主题 + 品牌色 + 清晰的侧边栏，就够了。

Storybook：示例驱动开发（CSF）

VitePress 是「给用户看的文档」，Storybook 更多是「给开发者用的工作台」。它让你脱离业务、单独开发和调试每个组件的每种状态。

Storybook 的核心是 CSF（Component Story Format）——用标准 ES module 描述组件的各种「故事」（story，即一个特定状态的示例）。

// Button.stories.ts
import type { Meta, StoryObj } from '@storybook/vue3'
import Button from '../src/button'

const meta: Meta<typeof Button> = {
  title: 'Basic/Button',
  component: Button,
  argTypes: {
    type: { control: 'select', options: ['primary', 'default', 'danger'] },
    disabled: { control: 'boolean' },
  },
}
export default meta

type Story = StoryObj<typeof Button>

// 每个导出就是一个 story
export const Primary: Story = {
  args: { type: 'primary' },
  render: (args) => ({
    components: { Button },
    setup: () => ({ args }),
    template: '<Button v-bind="args">按钮</Button>',
  }),
}

export const Disabled: Story = {
  args: { type: 'primary', disabled: true },
  render: Primary.render,
}

CSF 的好处：

  1. story 就是标准模块，能被测试、被文档、被视觉回归工具复用——你写一次 story，多处受益。
  2. argTypes 自动生成交互控件，在 Storybook 里能实时拖动 props 看效果，不用改代码。
  3. 组件开发和示例合一：开发新组件时先写 story，等于顺手把示例和边界状态都覆盖了。这就是「示例驱动开发」——写 story 的过程会逼你想清楚组件的各种状态。

Storybook 还能接一堆插件：上一篇讲的 a11y addon、交互测试、视觉回归（Chromatic）。它是组件库开发阶段的中枢。

VitePress 和 Storybook 要都用吗

不一定。取舍：

只用 VitePress VitePress + Storybook
文档和示例合一，维护简单 分工明确：Storybook 开发、VitePress 对外
适合中小型库 适合大型库、多人协作、要视觉回归

我的判断：中小组件库用 VitePress 就够了（文档即示例）；大型库、团队协作、需要视觉回归和组件工作台时，再上 Storybook。别为了「看起来专业」两个都上却都维护不好。

TypeDoc：从代码自动生成 API 参考

这里要分清两个东西：组件详情页 和 API 参考页 不是一回事。

正常组件库页面通常长这样：

Button 组件页
├── 什么时候用
├── 基础用法 demo
├── 禁用状态 demo
├── 加载状态 demo
├── Props 表格
├── Events 表格
├── Slots 表格
└── 类型定义链接

其中「什么时候用」「用法示例」「交互 demo」通常还是人写的，或者从 Storybook story / mobile demo 复用过来。因为这些内容需要解释使用场景，不是类型系统能自动推出来的。

真正适合自动生成的是下面这些结构化信息：

内容 常见来源
Props / Events / Slots 表格 组件源码、defineProps、类型声明、docgen 工具
TS 类型、接口、工具函数签名 TypeDoc + TSDoc
代码示例 手写 demo、Storybook story、移动端 demo
使用说明和最佳实践 人写

所以 TypeDoc 解决的是「类型/API 参考」这一层，不是自动生成完整组件文档页。它适合生成 ButtonProps、ThemeVars、ConfigProviderProps、工具函数签名这类偏类型参考的内容。

那生成出来的类型定义怎么和组件详情页放到一起？常见有两种接法。

第一种是链接式接入，最简单也最稳。docs/components/button.md 里正常写用法和 demo，底部加一个「类型定义」链接，跳到 TypeDoc 生成的 API 参考页：

## 类型定义

- [ButtonProps](/api/interfaces/ButtonProps)

这种做法的优点是维护成本低，缺点是组件页里的 Props 表格不会自动出现，用户要点到 API 页看完整类型。

第二种是片段式接入，更像常见组件库官网的效果。构建前先用 docgen / TypeDoc / 自定义脚本从源码里抽取 props、events、slots，生成一个组件页可用的 Markdown 片段：

src/button/props.ts
  └── docs:gen-api
        └── docs/.generated/button.api.md

生成出来的片段可能长这样：

## API

### Props

| 参数 | 说明 | 类型 | 默认值 |
|------|------|------|--------|
| type | 按钮类型 | `'primary' \| 'default' \| 'danger'` | `'default'` |
| disabled | 是否禁用 | `boolean` | `false` |

然后在 docs/components/button.md 里预留一个位置：

# Button 按钮

## 基础用法

<ButtonDemo />

<!-- API:START -->
<!-- 这里由脚本写入 docs/.generated/button.api.md 的内容 -->
<!-- API:END -->

构建脚本做的事情就是：读 button.md，找到 <!-- API:START --> 和 <!-- API:END -->，把生成的 API 片段塞进去，再交给 VitePress 构建。这样最终用户看到的是一个完整的组件详情页：上面是说明和 demo，下面是自动生成的 Props / Events / Slots 表格。

我的建议是：中小组件库先用链接式接入，别一上来写复杂生成器；组件数量多了、Props 表格开始频繁过期，再升级成片段式接入。重点不是所有内容都自动生成，而是容易过期的结构化内容自动生成。

如果采用链接式接入，TypeDoc 这条链路可以这样做。先给公共类型写 TSDoc 注释：

export interface ButtonProps {
  /** 按钮类型 */
  type?: 'primary' | 'default' | 'danger'
  /** 是否禁用 @default false */
  disabled?: boolean
}

/**
 * 防抖函数
 * @param fn 要防抖的函数
 * @param wait 等待毫秒数
 * @returns 防抖后的函数
 */
export function debounce<T extends (...args: any[]) => void>(fn: T, wait: number) {
  /* ... */
}

安装 TypeDoc 和 Markdown 插件：

pnpm add -D typedoc typedoc-plugin-markdown typedoc-vitepress-theme

再配置 typedoc.json，让 TypeDoc 只扫描组件库的公共入口，把 API 参考输出成 VitePress 能识别的 Markdown：

{
  "entryPoints": ["src/index.ts"],
  "out": "docs/api",
  "plugin": ["typedoc-plugin-markdown", "typedoc-vitepress-theme"]
}

然后把生成命令串进文档构建。注意这里的顺序：先生成 docs/api，再启动或构建 VitePress。

{
  "scripts": {
    "docs:api": "typedoc",
    "docs:dev": "pnpm docs:api && vitepress dev docs",
    "docs:build": "pnpm docs:api && vitepress build docs"
  }
}

链接式接入的连通关系是这样的：

src/index.ts + TSDoc 注释
  └── typedoc
        └── docs/api/*.md
              └── VitePress 文件路由：/api/

也就是说，TypeDoc 不负责启动文档站，VitePress 也不负责分析 TS 类型。TypeDoc 只负责把类型信息生成到 docs/api，VitePress 只负责把 docs/api 下面的 Markdown 当成普通页面渲染出来。组件详情页里的「类型定义」链接，只是指向这些生成好的页面。

目录大概长这样：

docs/
├── .vitepress/
│   └── config.ts
├── guide/
│   └── getting-started.md
├── components/
│   └── button.md
└── api/
    ├── index.md
    ├── interfaces/
    │   └── ButtonProps.md
    └── typedoc-sidebar.json

如果想让左侧侧边栏也自动接上，可以把插件生成的 sidebar 文件引进 VitePress 配置：

// docs/.vitepress/config.ts
import { defineConfig } from 'vitepress'
import typedocSidebar from '../api/typedoc-sidebar.json'

export default defineConfig({
  themeConfig: {
    nav: [{ text: 'API', link: '/api/' }],
    sidebar: {
      '/api/': typedocSidebar,
    },
  },
})

这就是所谓「嵌进 VitePress 站点」：不是运行时打通，而是构建前先生成 Markdown，构建时由 VitePress 一起收进站点。

如果采用片段式接入，思路就不一样了：不要直接把 TypeDoc 生成的整页 Markdown 塞进组件页，而是让 docgen / 自定义脚本生成更适合组件页展示的 Props / Events / Slots 表格片段。TypeDoc 仍然可以保留，用来承载完整类型参考；组件页只嵌入读者最常看的那部分 API 表格。

关键价值：API 参考和组件页里的结构化表格要尽量跟代码同步。你改了 props 类型或注释，重新生成文档就更新了，不存在「文档和代码对不上」。

实践建议：把 API 参考、Props 表格这类生成步骤接进 CI 或文档构建流程，每次发版自动重新生成。别让它变成「想起来才手动跑一次」的一次性动作。

CHANGELOG 自动化

文档工程的最后一块是 CHANGELOG——用户升级前会看「这版改了什么」。手写 CHANGELOG 和手写 API 一样迟早废弃。两种主流自动化方案：

方案 依据什么生成 适合
Changesets 每次 PR 附带的 changeset 文件 Monorepo、多包、显式声明改动
standard-version / conventional-changelog 规范化的 commit message 单包、遵循 Conventional Commits

组件库大多是 Monorepo 多包，首选 Changesets（它的完整发布流程下一篇讲）。这里只看它怎么产出 CHANGELOG：

开发时写 changeset，声明这次改了哪些包、什么级别、干了什么：

---
"@my-ui/components": minor
---

Button 新增 loading 状态

发布时 changeset version 会把所有未消费的 changeset **汇总进各包的 CHANGELOG.md**，按版本、按 major/minor/patch 分组，自动生成。你写的那句「Button 新增 loading 状态」就成了 changelog 条目。

conventional-changelog 路线则是从 commit message 生成——前提是团队严格遵循 feat: / fix: 这类 Conventional Commits 规范（这在「Commitlint、Husky 与 lint-staged 提交约束」那篇讲过）。commit 不规范，生成的 changelog 就是垃圾。

我的判断：Monorepo 组件库用 Changesets，一步到位既管版本又管 changelog；单包项目且 commit 规范执行得好，可以用 standard-version。

把文档工程串起来

一套完整的组件库文档工程，各工具的分工是这样的：

开发阶段
  ├── Storybook (CSF)      →  单独开发/调试每个组件的每种状态
  └── 写 TSDoc 注释         →  为 API 参考打基础

文档站
  ├── VitePress            →  使用指南 + 组件详情页
  ├── mobile demo          →  移动端组件的手机预览 iframe
  ├── docgen/API 片段       →  生成 Props / Events / Slots 表格
  └── TypeDoc              →  生成独立 API 参考页，供组件页链接

发布时
  └── Changesets           →  自动汇总生成 CHANGELOG

一个原则贯穿始终：容易过期的结构化内容（Props 表格、类型参考、CHANGELOG）尽量自动生成，能跑起来的示例绝不贴截图。文档一旦需要人肉同步，就注定会腐烂。

小结

  1. 组件库文档分三层：使用文档（VitePress 人写）、组件示例（Storybook / demo 跟组件写）、结构化 API（docgen / TypeDoc 自动生成）。
  2. VitePress 的杀手锏是能在 Markdown 里原生渲染 Vue 真实组件；React 组件库更适合 Docusaurus、Nextra 或 Storybook，别为了统一工具链硬拧。
  3. 移动端 H5 组件库通常用 iframe 嵌入一套 mobile demo SPA，类似 Vant 的右侧手机预览：文档负责讲清楚，demo 负责跑真实组件。
  4. Storybook 用 CSF 描述组件各状态，argTypes 自动生成交互控件，实现示例驱动开发，是开发阶段的工作台。
  5. VitePress 和 Storybook 不必都用：中小库 VitePress 足够，大型库/团队协作/视觉回归再上 Storybook。
  6. TypeDoc 更适合生成独立 API 参考页；组件详情页里的 Props / Events / Slots 表格通常用 docgen 或自定义脚本生成片段后插入。
  7. CHANGELOG 自动化：Monorepo 用 Changesets（changeset 文件汇总生成），单包可用 conventional-changelog（依赖规范 commit）。
  8. 贯穿原则：容易过期的结构化内容尽量自动生成，能跑的示例绝不贴截图，否则文档必然腐烂。
