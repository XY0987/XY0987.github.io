Vue 3 组件实例源码解析：createComponentInstance 和 setupComponent 做了什么

发表于2026|更新于2026|Vue框架及周边库
|字数总计:3.3k|阅读时长:13分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：上一篇看了 renderer 如何通过 mountComponent 进入组件挂载流程。这一篇继续往组件内部走，重点看 createComponentInstance 和 setupComponent：组件实例如何创建，props、slots、setup、render 又是如何一步步准备好的。

先给结论

组件挂载的核心链路是：

mountComponent(initialVNode)
  │
  ▼
createComponentInstance(vnode)
  │
  ├─ 创建组件实例对象
  ├─ 继承 appContext / provides
  ├─ 初始化 propsOptions / emitsOptions
  └─ 绑定 emit
  │
  ▼
setupComponent(instance)
  │
  ├─ initProps
  ├─ initSlots
  └─ setupStatefulComponent
       │
       ├─ 创建 render proxy
       ├─ 调用 setup(props, context)
       ├─ handleSetupResult
       └─ finishComponentSetup
            │
            ├─ 确定 render 函数
            └─ 应用 Options API

如果说 renderer.ts 负责“把组件 VNode 放进渲染流程”，那 component.ts 就负责“把组件 VNode 变成可执行的组件实例”。

组件实例是什么

在 Vue 运行时里，组件不是直接执行组件对象。Vue 会先为组件创建一个内部实例 ComponentInternalInstance。

这个实例保存了组件运行所需的全部状态：

字段 作用
vnode 当前组件对应的 VNode
type 组件定义对象或函数
parent 父组件实例
appContext 应用级上下文
props / attrs props 和非 props 属性
slots 插槽
setupState setup 返回对象
render 最终渲染函数
subTree 组件 render 后得到的子树 VNode
effect 组件渲染 ReactiveEffect
update / job 组件更新入口和调度任务

组件实例是连接“组件定义”和“渲染执行”的中间层。

createComponentInstance：创建组件实例

组件挂载时，renderer 会调用 createComponentInstance。

export function createComponentInstance(
  vnode: VNode,
  parent: ComponentInternalInstance | null,
  suspense: SuspenseBoundary | null,
): ComponentInternalInstance {
  const type = vnode.type as ConcreteComponent
  // 组件实例继承父组件的 appContext；根组件则从根 VNode 上读取 appContext。
  // appContext 提供全局组件/指令、app.provide、config 等应用级能力。
  const appContext =
    (parent ? parent.appContext : vnode.appContext) || emptyAppContext

  const instance: ComponentInternalInstance = {
    uid: uid++,
    vnode,
    type,
    parent,
    appContext,
    root: null!, // to be immediately set
    next: null,
    subTree: null!, // will be set synchronously right after creation
    effect: null!,
    update: null!, // will be set synchronously right after creation
    job: null!,
    // 每个组件实例都有独立 effectScope，组件卸载时可以统一停止 render effect、watch 等副作用。
    scope: new EffectScope(true /* detached */),
    render: null,
    proxy: null,
    exposed: null,
    exposeProxy: null,
    withProxy: null,

    // provide/inject 原型链：子组件默认继承父组件 provides；根组件继承 appContext.provides。
    provides: parent ? parent.provides : Object.create(appContext.provides),
    ids: parent ? parent.ids : ['', 0, 0],
    accessCache: null!,
    renderCache: [],

这里有几个重点。

第一，组件实例会继承 appContext。根组件从根 VNode 上拿，子组件从父组件拿。

这保证了全局组件、全局指令、app.provide、app.config 可以在整棵组件树里共享。

第二，每个组件实例都有自己的 EffectScope：

scope: new EffectScope(true)

组件卸载时，可以统一停止这个 scope 中的副作用，比如组件渲染 effect、watch 等。

第三，provides 是原型链结构：

provides: parent ? parent.provides : Object.create(appContext.provides)

子组件默认继承父组件的 provides。真正调用组件级 provide 时，会在需要时创建新的 provides 对象，从而形成层级覆盖。

props/emits 和运行时状态容器

实例创建时还会提前规范化 props 和 emits：

    // local resolved assets
    components: null,
    directives: null,

    // props/emits 选项在实例创建时先规范化，后续初始化 props 和 emit 校验会复用这些结果。
    propsOptions: normalizePropsOptions(type, appContext),
    emitsOptions: normalizeEmitsOptions(type, appContext),

    // emit
    emit: null!, // to be set immediately
    emitted: null,

    // props default value
    propsDefaults: EMPTY_OBJ,

    // inheritAttrs
    inheritAttrs: type.inheritAttrs,

    // 组件实例的运行时状态容器：props/attrs/slots/setupState/data/refs 都挂在实例上。
    ctx: EMPTY_OBJ,
    data: EMPTY_OBJ,
    props: EMPTY_OBJ,
    attrs: EMPTY_OBJ,
    slots: EMPTY_OBJ,
    refs: EMPTY_OBJ,
    setupState: EMPTY_OBJ,
    setupContext: null,

这些字段后续会被不同阶段填充：

  • initProps 填充 props / attrs
  • initSlots 填充 slots
  • setup 返回对象后填充 setupState
  • Options API 的 data 会填充 data
  • 模板 ref 会填充 refs

root 和 emit 初始化

实例最后会设置 ctx、root 和 emit：

  if (__DEV__) {
    instance.ctx = createDevRenderContext(instance)
  } else {
    instance.ctx = { _: instance }
  }
  // root 指向整棵组件树的根实例；emit 绑定当前实例，后续 this.$emit/setupContext.emit 都会走这里。
  instance.root = parent ? parent.root : instance
  instance.emit = emit.bind(null, instance)

  // apply custom element special handling
  if (vnode.ce) {
    vnode.ce(instance)
  }

  return instance
}

emit 绑定当前实例很重要。因为事件校验、事件名转换、已触发事件记录等，都需要知道当前是哪个组件在 emit。

currentInstance：让 setup 知道当前组件

很多组合式 API 都依赖当前组件实例，比如：

  • getCurrentInstance
  • provide / inject
  • 生命周期注册
  • useAttrs / useSlots

这些 API 能工作，是因为 Vue 在执行 setup 或生命周期时会设置 currentInstance。

export const setCurrentInstance = (instance: ComponentInternalInstance) => {
  const prev = currentInstance
  // setup/lifecycle 执行期间设置 currentInstance，让 getCurrentInstance、provide/inject 等 API 能定位当前组件。
  internalSetCurrentInstance(instance)
  instance.scope.on()
  return (): void => {
    instance.scope.off()
    internalSetCurrentInstance(prev)
  }
}

export const unsetCurrentInstance = (): void => {
  currentInstance && currentInstance.scope.off()
  internalSetCurrentInstance(null)
}

这里还会打开当前组件的 effectScope，这样 setup 里创建的副作用可以归属到当前组件 scope。

setupComponent：初始化 props、slots 和 setup

创建完组件实例后，renderer 会调用 setupComponent。

export function setupComponent(
  instance: ComponentInternalInstance,
  isSSR = false,
  optimized = false,
): Promise<void> | undefined {
  isSSR && setInSSRSetupState(isSSR)

  const { props, children } = instance.vnode
  const isStateful = isStatefulComponent(instance)
  // 初始化 props 和 slots，这是 setup(props, context) 之前必须准备好的输入。
  initProps(instance, props, isStateful, isSSR)
  initSlots(instance, children, optimized || isSSR)

  // 只有有状态组件才需要执行 setupStatefulComponent；函数式组件没有实例状态初始化流程。
  const setupResult = isStateful
    ? setupStatefulComponent(instance, isSSR)
    : undefined

  isSSR && setInSSRSetupState(false)
  return setupResult
}

这一步做了两件基础工作：

  1. 初始化 props 和 attrs。
  2. 初始化 slots。

然后根据组件类型判断是否继续执行 setupStatefulComponent。

函数式组件没有完整的状态实例初始化过程，所以这里重点是有状态组件。

setupStatefulComponent：创建代理并执行 setup

有状态组件会先创建访问缓存和组件代理。

  // 0. 创建渲染代理的属性访问缓存，用于加速 this.xxx 从 setupState/props/data/ctx 中解析。
  instance.accessCache = Object.create(null)
  // 1. 创建组件公开实例代理。render 中的 this 和用户拿到的组件代理都会经过这些 handlers。
  instance.proxy = new Proxy(instance.ctx, PublicInstanceProxyHandlers)
  if (__DEV__) {
    exposePropsOnRenderContext(instance)
  }
  // 2. 执行 setup()
  const { setup } = Component

instance.proxy 就是我们常说的组件公开实例代理。模板和 render 函数里访问 this.xxx 时，会通过它去解析：

  • setupState
  • data
  • props
  • ctx
  • $attrs、$slots、$emit 等公共属性

accessCache 是访问缓存，用来记住某个 key 上次是从哪里解析出来的，避免每次 render 都重复判断。

setup 的执行过程

如果组件定义了 setup，Vue 会这样执行：

  if (setup) {
    // 执行 setup 本身不应该被当前外层 effect 收集依赖，因此先暂停依赖追踪。
    pauseTracking()
    const setupContext = (instance.setupContext =
      setup.length > 1 ? createSetupContext(instance) : null)
    const reset = setCurrentInstance(instance)
    const setupResult = callWithErrorHandling(
      setup,
      instance,
      ErrorCodes.SETUP_FUNCTION,
      [
        // props 在 setup 中是只读的，开发环境用 shallowReadonly 防止直接修改。
        __DEV__ ? shallowReadonly(instance.props) : instance.props,
        setupContext,
      ],
    )
    const isAsyncSetup = isPromise(setupResult)
    resetTracking()
    reset()

这里有几个关键点。

第一，执行 setup 前会 pauseTracking()。

setup 本身不应该被外部 effect 收集依赖。真正的组件响应式更新，应该发生在 render effect 执行 render 时。

第二，setupContext 是按需创建的。

setup.length > 1 ? createSetupContext(instance) : null

如果用户只写：

setup(props) {}

就不创建 context。如果写：

setup(props, context) {}

才创建 attrs、slots、emit、expose 组成的 context。

第三，props 在开发环境是 shallowReadonly。

所以 setup 里直接修改 props 会被警告。

async setup 的处理

setup 可能返回 Promise。

    if (isAsyncSetup) {
      setupResult.then(unsetCurrentInstance, unsetCurrentInstance)
      if (isSSR) {
        // SSR 会等待 async setup 完成后继续处理 setup 结果。
        return setupResult
          .then((resolvedResult: unknown) => {
            handleSetupResult(instance, resolvedResult, isSSR)
          })
          .catch(e => {
            handleError(e, instance, ErrorCodes.SETUP_FUNCTION)
          })
      } else if (__FEATURE_SUSPENSE__) {
        // 客户端 async setup 需要 Suspense 承接，这里先记录 Promise，后续由 Suspense 重新进入挂载流程。
        instance.asyncDep = setupResult

SSR 场景可以等待 Promise 完成。客户端场景下，async setup 需要配合 Suspense，否则开发环境会警告。

handleSetupResult：处理 setup 返回值

setup 返回值主要有两类。

返回函数：作为 render 函数

export function handleSetupResult(
  instance: ComponentInternalInstance,
  setupResult: unknown,
  isSSR: boolean,
): void {
  if (isFunction(setupResult)) {
    // setup 返回函数时，这个函数就是组件的内联 render。
    if (__SSR__ && (instance.type as ComponentOptions).__ssrInlineRender) {
      // when the function's name is `ssrRender` (compiled by SFC inline mode),
      // set it as ssrRender instead.
      instance.ssrRender = setupResult
    } else {
      instance.render = setupResult as InternalRenderFunction
    }

这对应这种写法：

setup() {
  return () => h('div', 'hello')
}

返回函数时，它就是组件 render 函数。

返回对象：作为 setupState

  } else if (isObject(setupResult)) {
    if (__DEV__ && isVNode(setupResult)) {
      warn(
        `setup() should not return VNodes directly - ` +
          `return a render function instead.`,
      )
    }
    // setup 返回对象时，这些对象会作为 setupState 暴露给 render/template。
    if (__DEV__ || __FEATURE_PROD_DEVTOOLS__) {
      instance.devtoolsRawSetupState = setupResult
    }
    // proxyRefs 让模板/render 访问 setup 返回的 ref 时自动浅层解包。
    instance.setupState = proxyRefs(setupResult)
    if (__DEV__) {
      exposeSetupStateOnRenderContext(instance)
    }

这对应最常见的 Composition API 写法：

setup() {
  const count = ref(0)
  return { count }
}

返回对象会被放进 instance.setupState，并经过 proxyRefs 处理，所以模板里可以直接写：

{{ count }}

而不需要：

{{ count.value }}

finishComponentSetup：确定 render 函数

无论 setup 返回什么，最后都会进入 finishComponentSetup。

这一步负责确定最终的 instance.render。

来源有几种：

来源 场景
setup 返回函数 setup() { return () => ... }
组件本身有 render render() { ... } 或 SFC 编译后结果
template 运行时编译 full build 下 template 编译成 render
都没有 使用 NOOP，开发环境警告

最终会落到：

    // 最终把组件 render 函数落到 instance.render 上，renderer 后续会调用 renderComponentRoot(instance)。
    instance.render = (Component.render || NOOP) as InternalRenderFunction

    // for runtime-compiled render functions using `with` blocks, the render
    // proxy used needs a different `has` handler which is more performant and
    // also only allows a whitelist of globals to fallthrough.
    if (installWithProxy) {
      installWithProxy(instance)
    }
  }

  // Options API 支持：把 data/computed/methods/watch/lifecycle 等选项应用到实例上。

renderer.ts 后续执行 renderComponentRoot(instance) 时，就会调用这里准备好的 instance.render。

Options API 在哪里处理

如果构建支持 Options API，finishComponentSetup 最后会调用 applyOptions：

  // Options API 支持：把 data/computed/methods/watch/lifecycle 等选项应用到实例上。
  if (__FEATURE_OPTIONS_API__ && !(__COMPAT__ && skipOptions)) {
    const reset = setCurrentInstance(instance)
    pauseTracking()
    try {
      applyOptions(instance)
    } finally {
      resetTracking()
      reset()
    }
  }

data、computed、methods、watch、生命周期选项等，都会在这个阶段被应用到实例上。

Composition API 的 setup 在前，Options API 的选项应用在后。

字段 作用
attrs 非 props attribute

expose 如何影响组件 ref

如果组件调用了 expose，父组件通过模板 ref 拿到的不是完整实例代理，而是 exposed 代理：

export function getComponentPublicInstance(
  instance: ComponentInternalInstance,
): ComponentPublicInstance | ComponentInternalInstance['exposed'] | null {
  if (instance.exposed) {
    // 组件调用 expose 后，父组件通过 ref 拿到的是 exposed 代理，而不是完整组件实例代理。
    return (
      instance.exposeProxy ||
      (instance.exposeProxy = new Proxy(proxyRefs(markRaw(instance.exposed)), {
        get(target, key: string) {
          if (key in target) {
            return target[key]
          } else if (key in publicPropertiesMap) {
            return publicPropertiesMap[key](instance)
          }
        },

这对应 <script setup> 里的 defineExpose，本质上也是控制 instance.exposed。

一个完整流程

以这个组件为例：

const App = {
  props: ['msg'],
  setup(props) {
    const count = ref(0)
    return { count }
  },
  template: `{{ msg }} - {{ count }}`,
}

挂载时内部大致是：

mountComponent(vnode)
  │
  ▼
createComponentInstance(vnode)
  │
  ├─ 创建 instance
  ├─ 继承 appContext
  ├─ 初始化 provides / scope / ctx
  └─ 绑定 emit
  │
  ▼
setupComponent(instance)
  │
  ├─ initProps(instance, vnode.props)
  ├─ initSlots(instance, vnode.children)
  └─ setupStatefulComponent(instance)
       │
       ├─ instance.proxy = new Proxy(ctx, handlers)
       ├─ setCurrentInstance(instance)
       ├─ setup(shallowReadonly(props), setupContext)
       ├─ handleSetupResult
       │    └─ setupState = proxyRefs({ count })
       └─ finishComponentSetup
            ├─ 确定 render
            └─ applyOptions

完成这些后，renderer 的 setupRenderEffect 才能执行组件 render，得到组件子树并进入 patch。

小结

  1. createComponentInstance 创建组件内部实例，保存组件运行时所需的全部状态。
  2. 组件实例继承 appContext，因此能访问 app 级全局组件、指令、provide 和 config。
  3. 每个组件实例有独立 EffectScope，卸载时可以统一停止副作用。
  4. setupComponent 先初始化 props 和 slots，再处理有状态组件的 setup。
  5. setupStatefulComponent 会创建组件代理、设置 currentInstance、执行 setup。
  6. setup 返回函数时作为 render，返回对象时作为 setupState，并通过 proxyRefs 自动浅层解包。
  7. finishComponentSetup 负责最终确定 instance.render，并应用 Options API。
  8. expose 会影响父组件通过 ref 拿到的公开实例内容。
