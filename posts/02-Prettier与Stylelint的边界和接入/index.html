Prettier 与 Stylelint 的边界和接入

发表于2026|更新于2026|工程化
|字数总计:1.6k|阅读时长:6分钟

前言：代码规范最容易吵起来的地方，往往不是 bug，而是缩进、换行、属性顺序这些细节。我的建议很简单：能交给工具自动处理的，就不要留给 Code Review 讨论。

Prettier 解决什么问题

Prettier 的定位非常明确：代码格式化工具。

它关心的是代码长什么样，比如：

  • 缩进几个空格；
  • 一行最多多长；
  • 对象属性怎么换行；
  • JSX 属性怎么排列；
  • 是否保留分号；
  • 使用单引号还是双引号。

它不关心这段代码有没有逻辑问题。

比如下面这段代码：

const result={name:"Tom",age:18,items:[1,2,3].map((item)=>{return item*2})}

Prettier 会把它格式化成：

const result = {
  name: 'Tom',
  age: 18,
  items: [1, 2, 3].map((item) => {
    return item * 2
  }),
}

但是它不会告诉你 return item * 2 是否应该简写，也不会告诉你变量命名是否合理。

所以我对 Prettier 的理解是：

Prettier 负责消灭格式争论，不负责提升代码质量。

ESLint 和 Prettier 的边界

ESLint 和 Prettier 经常被放在一起讲，但它们的职责不同。

工具 主要职责 典型问题
ESLint 代码质量和潜在错误 未使用变量、Hooks 规则、Promise 未处理
Prettier 代码排版格式 缩进、换行、引号、尾逗号

早期很多 ESLint 规则也会管格式，比如缩进、分号、逗号换行。现在我的建议是：格式问题尽量交给 Prettier，ESLint 专注语义和质量。

原因有两个：

  1. Prettier 的格式化能力更强，覆盖 JS、TS、CSS、HTML、Markdown 等多种文件；
  2. ESLint 的格式规则和 Prettier 容易互相打架。

典型冲突是：ESLint 认为这里必须换行，Prettier 又把它合并回去。最后开发者保存一次，报错一次。

这种工具冲突最伤团队体验。

推荐的 Prettier 配置

安装：

pnpm add -D prettier

创建 .prettierrc.json：

{
  "singleQuote": true,
  "semi": false,
  "trailingComma": "all",
  "printWidth": 100
}

创建 .prettierignore：

dist
coverage
node_modules
pnpm-lock.yaml

脚本配置：

{
  "scripts": {
    "format": "prettier . --write",
    "format:check": "prettier . --check"
  }
}

这里有一个取舍：我会把 lockfile 放进 .prettierignore，因为锁文件应该由包管理器生成，不应该被格式化工具处理。

是否需要 eslint-config-prettier

如果你的 ESLint 配置里还包含格式类规则，建议安装 eslint-config-prettier：

pnpm add -D eslint-config-prettier

Flat Config 中可以这样接入：

import eslintConfigPrettier from 'eslint-config-prettier'

export default [
  // 其他 ESLint 配置
  eslintConfigPrettier,
]

它的作用不是运行 Prettier，而是关闭可能和 Prettier 冲突的 ESLint 规则。

也就是说：

eslint-config-prettier
  └── 负责让 ESLint 少管格式

prettier
  └── 负责真正格式化代码

这两个概念不要混在一起。

Stylelint 解决什么问题

如果项目里有 CSS、Sass、Less、CSS Modules，只有 ESLint 和 Prettier 还不够。

Stylelint 的定位是：样式代码的 lint 工具。

它可以检查：

  • CSS 语法错误；
  • 不合法的属性值；
  • 重复选择器；
  • 低兼容性的写法；
  • 选择器复杂度；
  • Sass/Less 特定规则；
  • 团队自定义的样式约束。

举个例子：

.card {
  color: #fff;
  color: white;
}

这段 CSS 语法上没问题，但 color 重复声明，很可能是误写。Stylelint 可以提前发现。

再比如：

.page .content .list .item .title {
  color: #333;
}

选择器嵌套太深，后期维护和覆盖都会很痛苦。Stylelint 可以通过规则限制复杂度。

Stylelint 的最小接入

安装：

pnpm add -D stylelint stylelint-config-standard

创建 stylelint.config.mjs：

export default {
  extends: ['stylelint-config-standard'],
  rules: {
    'selector-max-id': 0,
    'max-nesting-depth': 3,
  },
  ignoreFiles: ['dist/**', 'coverage/**'],
}

脚本：

{
  "scripts": {
    "lint:style": "stylelint \"src/**/*.{css,scss,vue}\"",
    "lint:style:fix": "stylelint \"src/**/*.{css,scss,vue}\" --fix"
  }
}

如果项目使用 Sass，可以继续补充：

pnpm add -D stylelint-config-standard-scss

配置改成：

export default {
  extends: ['stylelint-config-standard-scss'],
  rules: {
    'max-nesting-depth': 3,
  },
}

CSS Modules 项目要注意什么

CSS Modules 里经常会出现 camelCase 类名：

.userCard {
  padding: 16px;
}

如果默认规则要求选择器必须 kebab-case，就会报错。

这时不要直接关掉所有命名规则，而是明确团队约定。

比如团队决定 CSS Modules 使用 camelCase：

export default {
  extends: ['stylelint-config-standard'],
  rules: {
    'selector-class-pattern': [
      '^[a-z][a-zA-Z0-9]+$',
      {
        message: 'CSS Modules className 使用 camelCase',
      },
    ],
  },
}

如果团队决定所有 CSS class 都用 kebab-case，也可以反过来约束。

关键不是哪种命名更高级，而是项目里不要混着来。

保存时格式化还是提交前格式化

我更推荐两层都做：

时机 做什么 目的
保存时 Prettier 自动格式化 让开发体验顺滑
提交前 lint-staged 格式化暂存文件 防止漏掉配置或 IDE 差异
CI format:check 保证最终进入主干的代码一致

只靠编辑器保存是不够的，因为团队成员的 IDE 配置不一定一致。

只靠提交前格式化也不够，因为反馈太晚，开发过程不舒服。

比较稳的组合是：

{
  "scripts": {
    "format": "prettier . --write",
    "format:check": "prettier . --check",
    "lint": "eslint .",
    "lint:style": "stylelint \"src/**/*.{css,scss,vue}\""
  }
}

然后在 CI 里跑：

pnpm format:check
pnpm lint
pnpm lint:style

我的实际建议

如果是一个新的前端项目，我会这样分工：

工具 负责范围
Prettier JS、TS、CSS、HTML、Markdown 的格式
ESLint JS、TS、框架规则、潜在 bug
Stylelint CSS、Sass、选择器、样式质量
TypeScript 类型正确性

不要让一个工具干所有事情。工具边界越清楚，后面维护越轻松。

小结

  1. Prettier 负责格式化，核心价值是消灭格式争论。
  2. ESLint 负责代码质量和潜在错误，不建议继续承担大量格式规则。
  3. eslint-config-prettier 是用来关闭冲突规则的，不是用来运行 Prettier 的。
  4. Stylelint 负责样式代码质量，适合检查 CSS、Sass、选择器复杂度等问题。
  5. 保存时、提交前、CI 三层检查配合起来，团队规范才不依赖个人习惯。
