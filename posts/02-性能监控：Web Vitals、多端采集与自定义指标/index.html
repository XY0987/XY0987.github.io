性能监控：Web Vitals、多端采集与自定义指标

发表于2026|更新于2026|工程化
|字数总计:3.3k|阅读时长:11分钟

前言：上一篇讲错误监控，回答「线上有没有报错」。这一篇讲性能监控，回答「线上到底快不快」。性能工程那几篇讲的 Lighthouse 是实验室数据，能防倒退，但代替不了真实用户的感受——那必须靠 RUM（真实用户监控）。这一篇讲怎么采集真实用户的 Web Vitals、多端性能数据和自定义业务指标，把线上性能变成可以持续观测的数据。

为什么必须有 RUM

性能指标篇讲过实验室数据和真实用户数据的区别，这里强调一遍它的重要性：你的 Lighthouse 跑 95 分，不代表用户体验好。原因：

  • Lighthouse 在一个固定的模拟环境跑，而真实用户分布在各种设备、网络、地区。
  • INP、CLS 这些指标实验室根本测不准（需要真实交互和滚动）。
  • 你只跑首页，用户访问的是各种页面、各种路径。

RUM（Real User Monitoring，真实用户监控）就是采集真实用户运行环境里的性能数据并上报，让你看到「用户实际感受到的性能分布」。这里的运行环境不只浏览器，也包括小程序容器、App WebView、React Native / Flutter 这类跨端运行时。Lighthouse 防倒退，RUM 看真实——两者配合，不可互相替代。

用 web-vitals 采集核心指标

先说 Web。采集 Core Web Vitals 的标准工具还是 Google 官方的 web-vitals 库（性能指标篇介绍过）。这里讲得更完整一点：

pnpm add web-vitals

import { onLCP, onCLS, onINP, onFCP, onTTFB } from 'web-vitals'

function sendToAnalytics(metric) {
  const body = JSON.stringify({
    name: metric.name,        // 'LCP' / 'CLS' / 'INP' ...
    value: metric.value,      // 数值
    rating: metric.rating,    // 'good' / 'needs-improvement' / 'poor'
    id: metric.id,            // 本次页面加载的唯一 id
    navigationType: metric.navigationType,
    // 上下文：把指标和「谁、在哪个页面、什么设备」关联起来
    url: location.pathname,
    version: __APP_VERSION__,
    connection: navigator.connection?.effectiveType,  // 网络类型
  })
  report('/api/vitals', body)
}

onLCP(sendToAnalytics)
onCLS(sendToAnalytics)
onINP(sendToAnalytics)
onFCP(sendToAnalytics)
onTTFB(sendToAnalytics)

几个采集要点（部分在性能指标篇提过，这里补充上下文相关的）：

1. 一定要带「上下文维度」：光有一个 LCP 数值没用，要能按维度切分——页面路径、应用版本、设备/网络类型、地区。因为性能问题往往是「某个页面、某个版本、某种网络下才慢」。带上这些维度，才能定位「不是全站慢，是这个页面在弱网下慢」。

2. metric.rating 直接给出好/中/差：web-vitals 内置了 Google 的阈值判定，直接告诉你这个值属于 good/needs-improvement/poor，不用自己判。

3. 指标渐进就绪，用 sendBeacon 兜住卸载时刻：CLS、INP 是整个页面生命周期累计的，到用户离开才最终确定，可以用回调 + sendBeacon（性能指标篇讲过）。

小程序与跨端框架不能照搬 Web Vitals

这里要先纠正一个容易踩的坑：Web Vitals 是 Web 页面指标，不是所有前端运行时的统一指标。小程序、Hybrid、React Native、Flutter、Taro、uni-app 这些场景里，用户看到的是「前端体验」，但底层运行时完全不一样，指标也不能硬套。

我的建议是把性能指标分成两层：

层级 作用 例子
平台原生指标 反映运行时自己的性能瓶颈 Web 的 LCP/INP/CLS，小程序的启动/路由/首渲染，App 的冷启动/页面渲染
业务自定义指标 反映用户真正关心的关键时刻 搜索结果出现、商品信息可见、编辑器可输入、支付按钮可点

这样做的好处是：不同端可以各采各的原生指标，但最终都能落到同一套业务体验语言上。否则 Web 端报 LCP，小程序端报 firstRender，App 端报 screenRender，名字都不一样，看板很容易变成各说各话。

小程序性能采集：看启动、路由和首渲染

以微信小程序为例，官方提供了 wx.getPerformance()。基础库 2.11.0 开始支持，低版本要做兼容。它能拿到小程序运行时的性能条目，比如：

entryType name 含义
navigation appLaunch / route 小程序启动、页面切换耗时
render firstRender 页面首次渲染耗时
script evaluateScript 脚本注入耗时

最小采集代码可以放在 App.onLaunch 里，尽量早点监听：

App({
  onLaunch() {
    if (!wx.getPerformance) return

    const performance = wx.getPerformance()
    const observer = performance.createObserver((entryList) => {
      for (const entry of entryList.getEntries()) {
        report({
          platform: 'miniprogram',
          name: entry.name,              // appLaunch / route / firstRender ...
          entryType: entry.entryType,    // navigation / render / script
          value: entry.duration,
          path: entry.path,
          startTime: entry.startTime,
          version: __APP_VERSION__,
        })
      }
    })

    observer.observe({ entryTypes: ['navigation', 'render', 'script'] })
  },
})

小程序里最关注三个指标：

1. appLaunch：小程序启动耗时。用户从点开小程序到可用，慢了就是第一印象差。分包、首包体积、初始化逻辑都会影响它。

2. route：页面切换耗时。小程序不是传统 SPA，也不是普通多页 Web，页面栈和 WebView 创建、页面初始化、数据同步都会影响跳转体验。

3. firstRender：页面首次渲染耗时。它比 Web 的 LCP 更贴近小程序语境，但不要把它直接等价成 LCP。小程序的渲染链路里有逻辑层、视图层、通信和基础库调度，慢点可能不在同一个地方。

如果业务用了 Taro、uni-app、Remax 这类框架，也不要只停留在框架层埋点。框架可以帮你统一代码，但最终运行在小程序时，还是应该把 wx.getPerformance() 这类平台指标采上来。跨端框架解决的是开发体验，不会自动解决观测口径。

Hybrid 与跨端 App：重点看容器和首屏

Hybrid、React Native、Flutter 这类场景，性能监控要从「页面」扩大到「容器 + 运行时 + 业务首屏」：

场景 重点指标 常见定位方向
App WebView / H5 容器 WebView 创建、HTML 加载、JS 执行、首屏可见 容器预热、离线包、资源缓存、接口慢
React Native Bundle 加载、JS 线程阻塞、首屏组件渲染、Native 通信 包体积、启动初始化、长任务、跨线程通信
Flutter 首帧时间、帧耗时、Jank、页面切换耗时 首屏构建、图片解码、列表渲染、主线程阻塞
Taro / uni-app 目标平台原生指标 + 框架生命周期耗时 编译产物、setData/数据同步、页面生命周期

这里不要追求一个指标横扫所有端。更现实的做法是统一上报协议，而不是统一底层指标：

type PerfPayload = {
  platform: 'web' | 'miniprogram' | 'rn' | 'flutter' | 'hybrid'
  metric: string
  value: number
  page: string
  version: string
  network?: string
  deviceLevel?: 'low' | 'middle' | 'high'
}

也就是说，Web 可以上报 LCP，小程序可以上报 firstRender，React Native 可以上报 screen-render，Flutter 可以上报 first-frame。底层名字不同没关系，但都必须带上 platform、page、version、network、deviceLevel 这些维度，方便看板做横向对比和分端定位。

自定义指标：业务真正关心的「快」

Core Web Vitals 和平台原生指标都很重要，但每个业务有自己的「关键时刻」，通用指标未必覆盖。比如：

  • 电商：用户从进商品页到「看到价格和加购按钮」的时间。
  • 搜索：从提交搜索到「结果列表出现」的时间。
  • 编辑器：从打开文档到「可编辑」的时间。

这些「业务关键时刻」才是用户真正的体验，通用的 LCP 或小程序 firstRender 不一定对得上。所以要打自定义指标。Web 里可以用标准的 performance API 打点：

// 在业务关键节点打点
performance.mark('search-start')   // 用户提交搜索
// ... 请求、渲染 ...
performance.mark('search-results-shown')   // 结果渲染完成

// 测量两点之间的时间
performance.measure('search-duration', 'search-start', 'search-results-shown')
const measure = performance.getEntriesByName('search-duration')[0]
report({ name: 'search-duration', value: measure.duration })

用 performance.mark/measure 而不是自己 Date.now() 相减的好处：这些打点会出现在 DevTools 的 Performance 面板时间轴上，本地调试时能直观看到。

在小程序和跨端框架里，也可以用同样思路打点，只是 API 换成当前平台可用的时间函数或框架生命周期：搜索开始时记录 search-start，列表真正渲染出来时记录 search-results-shown，最后统一上报 duration。

自定义指标的价值：它把「性能」和「业务体验」对齐了。老板问「我们的搜索快不快」，你能拿出「搜索结果 p75 是 800ms」这种业务语言的数据，而不是一个抽象的 LCP 或 firstRender。我的建议：每个产品都该定义 1-3 个「性能指标」——最能代表核心体验的那几个时刻，所有端都围绕它监控。

其他值得采集的性能数据

除了 Web Vitals、平台原生指标和业务自定义指标，还有几类数据对排查有用：

资源加载性能（Resource Timing）：用 PerformanceObserver 观察资源加载耗时，能发现「哪个接口慢、哪个 CDN 资源慢」：

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 1000) {   // 只报慢的，别全量
      report({ name: 'slow-resource', url: entry.name, duration: entry.duration })
    }
  }
}).observe({ type: 'resource', buffered: true })

接口性能：在请求层（见《接口契约 Mock 与请求层工程化》那篇）统一记录每个接口的耗时、成功率。接口慢往往是前端「感觉慢」的真凶，这一点在 Web、小程序和 App 里都一样。

长任务（Long Task）：PerformanceObserver 观察 longtask，能发现阻塞主线程的长任务（对应运行时性能和 INP）。

不用一次全上，先上当前平台最核心的原生指标 + 1-2 个业务关键指标，跑起来看到数据了，再按排查需要逐步补充。别一开始就想采集所有东西——数据采多了没人看，反而是负担。

让数据能用：看板与告警

采集只是第一步，数据要能看、能报警才有价值。两件事：

1. 看板（Dashboard）：把关键指标做成随时能看的图表——各指标的 p75 趋势、按平台/页面/版本/网络的切分。这样你能一眼看出「最近性能是涨是跌」「哪个端、哪个页面最慢」。这也直接喂给后面《工程治理指标》要讲的「Lighthouse 分数趋势」等治理看板。

2. 告警（Alert）：关键指标突破阈值时主动通知，别等人去翻看板。典型告警：

Web LCP p75 > 4s 持续 10 分钟          → 通知
小程序 firstRender p75 明显劣化         → 通知（关联版本）
某次发布后 INP p75 明显劣化             → 通知（关联版本）
白屏率 / 错误率突增                     → 通知（上一篇）

告警要关联到版本和发布：性能在某个时间点突然变差，第一嫌疑就是那个时间点的发布。把发布事件标注在指标时间轴上（部署时打一个 marker），性能劣化和发布的关联一目了然，能立刻决定要不要回滚。

一个真实的坑：只看平均，被拉不出的长尾坑了

现象：性能看板上平均 LCP 一直很漂亮，但持续有用户反馈慢。

原因：又是「看平均值」的老问题（性能指标篇强调过）。平均值被大量快速加载稀释，把「一部分用户很慢」完全掩盖了。

解决：监控看板一律看分位数（p75、p95），并且带维度切分。你会发现平均 2s 的背后，可能是「p95 达到 8s，全是某地区弱网用户」。RUM 的价值恰恰在于暴露这种长尾——能被平均值藏住的问题，才是最容易被长期忽视、最伤用户的问题。看 p75/p95、按维度切分，是 RUM 用对的前提。

小结

  1. Lighthouse 是实验室数据只能防倒退，真实用户性能必须靠 RUM 采集，两者互补不可替代。
  2. Web 端用 web-vitals 采集 LCP/CLS/INP/FCP/TTFB，sendBeacon 上报，metric.rating 直接给好/中/差判定。
  3. 小程序和跨端框架不能硬套 Web Vitals，要采平台原生指标，比如启动、路由、首渲染、首帧、页面渲染耗时。
  4. 多端监控的关键不是强行统一底层指标，而是统一上报协议和维度：平台、页面、版本、设备、网络都要带上。
  5. 通用指标不够，用自定义打点记录业务关键时刻，把性能和业务体验对齐；每个产品定义 1-3 个北极星性能指标。
  6. 按需补充资源加载、接口、长任务等数据；先上核心的，别一开始就贪多。
  7. 采集后要有看板和告警，并把发布事件标注在时间轴上关联劣化与版本；看分位数和维度切分，别只看平均值。
