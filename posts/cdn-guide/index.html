CDN 完全指南：从原理到实战的系统讲解

发表于2026|更新于2026|基础知识
|字数总计:9.1k|阅读时长:30分钟

CDN 这个词几乎所有前端、后端都听过，但真要说清楚”它到底怎么把一个静态文件从北京机房送到广州用户手里只用 20ms”，能讲透的人并不多。这篇我把 CDN 从最底层的 DNS 调度，到节点缓存、回源、刷新预热，再到实战配置和踩坑经验，整理成一份系统的指南。

一、为什么需要 CDN

1.1 没有 CDN 的世界

假设你在北京机房部署了一个网站，所有用户的请求都直接打到这台源站服务器：

广州用户  ──── 跨越 2000+ 公里 ────→  北京源站
深圳用户  ──── 跨越 2000+ 公里 ────→  北京源站
新疆用户  ──── 跨越 3000+ 公里 ────→  北京源站
海外用户  ──── 跨越数万公里 ─────→  北京源站

带来的问题非常直接：

  1. 物理距离：电信号在光纤中传播速度约为光速的 2/3，北京到广州一个来回大约 30~50ms，这是物理定律决定的下限
  2. 网络拥塞：跨运营商访问（如电信用户访问联通源站）经常出现丢包和高延迟
  3. 源站压力：所有流量都打到一台服务器，热点资源会瞬间打爆带宽
  4. 海外访问慢：跨国链路质量差，丢包率高，常常出现”打开个网站要 5 秒”

1.2 CDN 解决的核心问题

CDN（Content Delivery Network，内容分发网络）的核心思路一句话：把内容缓存到离用户最近的节点。

            ┌──────────────┐
            │   北京源站   │
            └──────┬───────┘
                   │ 回源
        ┌──────────┼──────────┐
        ▼          ▼          ▼
   ┌────────┐ ┌────────┐ ┌────────┐
   │广州节点 │  │上海节点 │ │成都节点 │  ← CDN 边缘节点
   └────┬───┘ └────┬───┘ └────┬───┘
        ▼          ▼          ▼
     广州用户     上海用户    成都用户

我的理解是：CDN 本质上就是一个分布式的多级缓存系统，附带智能调度能力。它不”创造”内容，只是把源站的内容放到离用户更近的地方。

二、CDN 的工作原理

2.1 一次完整的 CDN 请求流程

以用户访问 https://static.example.com/app.js 为例，全流程如下：

1. 用户输入 URL 或页面引用资源
   ↓
2. 浏览器发起 DNS 查询：static.example.com 的 IP 是什么？
   ↓
3. Local DNS 递归查询，最终问到权威 DNS
   ↓
4. 权威 DNS 返回 CNAME：static.example.com → static.example.com.cdn.com
   ↓
5. Local DNS 继续查询 CNAME，被引导到 CDN 厂商的 GSLB（全局负载均衡）
   ↓
6. GSLB 根据用户 IP、运营商、节点负载等因素，返回最优边缘节点 IP
   ↓
7. 浏览器向边缘节点发起 HTTP/HTTPS 请求
   ↓
8. 边缘节点检查本地缓存：
   - 命中 → 直接返回（最快）
   - 未命中 → 向上层节点或源站回源 → 缓存后返回

CNAME 接入是 CDN 最经典也最普遍的接入方式，本质就是把域名解析的”决定权”交给 CDN 厂商。

2.2 关键组件

组件 作用
源站（Origin） 内容的真实存储位置，CDN 缓存未命中时回源拉取
边缘节点（Edge） 离用户最近的缓存节点，直接对用户提供服务
中间层节点 部分 CDN 在边缘和源站之间还有一层”父节点”，用于减少回源
GSLB 全局调度系统，决定把用户引到哪个节点
调度系统 实时监控节点状态、链路质量，动态调整调度策略

2.3 CDN 调度的三种主流方式

1. DNS 调度

最经典也最常见。GSLB 根据 Local DNS 的 IP 推断用户位置，返回不同的边缘节点 IP。

  • 优点：实现简单、覆盖广
  • 缺点：CDN 往往只能根据 Local DNS 的位置来猜用户位置，用户用了公共 DNS 时可能猜错；而且 DNS 结果会被缓存，节点切换不能做到秒级立即生效

2. HTTP 302 调度

边缘节点收到请求后，判断不是最优节点，返回 302 重定向到更合适的节点。

  • 优点：调度精准，能用真实客户端 IP
  • 缺点：多一次往返，增加首包延迟，不适合频繁的小请求

3. Anycast 调度

多个节点对外宣告同一个 IP，靠 BGP 路由把流量自动引到”网络上最近”的节点。

  • 优点：无需 DNS 调度，切换快、抗 DDoS 强
  • 缺点：成本高、对中小厂商不友好，国内运营商支持复杂

实战中，主流商业 CDN 多采用 DNS 调度 + HTTP 302 微调 的组合方案。

三、CDN 缓存机制详解

3.1 缓存命中的判断流程

边缘节点收到请求后，缓存判断逻辑大致如下：

请求到达边缘节点
       ↓
计算 Cache Key（通常是 URL + 部分 Header）
       ↓
查询本地缓存
       ↓
   ┌───────┴───────┐
   ▼               ▼
 命中            未命中
   ↓               ↓
检查是否过期    回源拉取
   ↓               ↓
未过期 → 直接返回  按规则缓存
过期 → 回源验证    返回给用户

3.2 缓存键（Cache Key）

这是 CDN 一个非常关键的概念，**决定了”什么样的请求算同一个资源”**。

默认的 Cache Key 通常是：

Cache Key = Host + URI + 部分查询参数

比如 /app.js?v=1 和 /app.js?v=2 默认是两个不同的缓存对象。

实战中容易踩的坑：

  • 坑 1：URL 带随机参数导致缓存命中率为 0

    • 现象：监控里发现命中率长期在个位数
    • 原因：前端给每个请求加了 ?_t=时间戳 防止本地缓存
    • 解决：在 CDN 配置里忽略指定查询参数，或者只保留有意义的参数

  • 坑 2：携带 Cookie 导致每个用户缓存独立

    • 现象：同一个静态资源命中率极低
    • 原因：CDN 默认把 Cookie 纳入 Cache Key
    • 解决：静态资源域名独立部署，剥离 Cookie；或在 CDN 配置中忽略 Cookie

3.3 缓存过期与回源验证

CDN 的缓存过期时间，由三个因素叠加决定，按优先级从高到低：

  1. CDN 控制台的缓存规则：管理员手动配置的过期时间（最高优先级）
  2. 源站响应头：Cache-Control: max-age=xxx 或 Expires
  3. CDN 的默认策略：通常是 24 小时

过期后并不一定立刻回源拉新，常见做法是回源验证：

GET /app.js HTTP/1.1
If-None-Match: "abc123"
If-Modified-Since: Wed, 28 May 2026 10:00:00 GMT

源站如果资源没变，返回 304 Not Modified，CDN 节点就刷新缓存有效期，不需要重新传输 body。

3.4 缓存刷新与预热

这是 CDN 后台管理里最常用的两个操作：

操作 作用 使用场景
刷新（Purge） 强制使指定 URL 的缓存失效 紧急修复 BUG、内容下线
预热（Prefetch） 主动让边缘节点从源站拉取资源 大促前预先把资源推到全网节点

实战经验：

  • 刷新有数量限制和频次限制，不要把它当做日常发布手段（正确的做法是版本化文件名，比如 app.a1b2c3.js）
  • 预热在大流量活动前一定要做，否则活动开始的瞬间会有大量回源请求把源站打爆

四、CDN 回源策略详解

回源（Back-to-Origin）是 CDN 边缘节点向源站拉取资源的过程，是 CDN 中除”缓存”之外最关键的一环。配置不当轻则命中率低、源站压力大，重则导致整站不可用。

4.1 回源类型：IP 回源 vs 域名回源

CDN 配置源站时，主流厂商通常提供以下几种方式：

回源类型 配置方式 优点 缺点
IP 回源 直接填源站公网 IP 跳过 DNS 解析，回源更快；不受源站 DNS 故障影响 IP 变更要手动改配置；不支持源站负载均衡
域名回源 填源站域名 灵活，源站可平滑迁移、扩容；天然支持负载均衡 多一次 DNS 解析；依赖源站 DNS 可用性
OSS/COS 回源 填对象存储地址 原生集成、免维护、回源带宽便宜 仅适用于纯静态资源

我的实战建议：

  • 静态资源回对象存储：如阿里云 OSS、腾讯云 COS，省心又便宜，且 CDN 厂商往往对自家对象存储做了带宽优惠
  • 动态业务回域名：方便后端做扩缩容、灰度、切流
  • IP 回源只在特殊场景用：比如源站 DNS 不稳定、对回源延迟极度敏感、内网直连场景

4.2 回源 Host：最容易踩坑的配置

回源 Host 决定了 CDN 节点向源站发起请求时，HTTP 报文里 Host 头的值。这个概念是回源里最容易被忽略也最容易出问题的地方。

用户请求：     GET /index.html HTTP/1.1
              Host: cdn.example.com
                       ↓ CDN 节点回源
回源请求：     GET /index.html HTTP/1.1
              Host: ???      ← 这里填什么？

主流 CDN 上通常可以选择：

  1. 加速域名（默认值）：原样把 cdn.example.com 透传给源站
  2. 源站域名：用配置里的源站域名 origin.example.com
  3. 自定义 Host：手动指定，比如 www.example.com

为什么这事容易踩坑？因为很多源站是基于 Host 路由的——同一个 IP 上跑了多个网站，Nginx/网关靠 Host 头分发。

实战踩坑：

  • 坑 1：回源 Host 错误导致全站 404

    • 现象：CDN 接入后所有请求都 404
    • 原因：源站 Nginx 是虚拟主机模式，回源 Host 用了加速域名，但 Nginx 上没有 server_name cdn.example.com 的配置
    • 解决：把回源 Host 改成源站实际配置的域名，或在 Nginx 增加对应 server_name

  • 坑 2：回源 OSS 时报 SignatureDoesNotMatch

    • 现象：从对象存储回源时返回签名错误
    • 原因：OSS 签名验证依赖 Host 头，回源 Host 写错了
    • 解决：回源 Host 必须填 OSS 标准域名（如 bucket.oss-cn-beijing.aliyuncs.com）

4.3 回源协议

CDN 到源站之间的协议，一般有三种选项：

协议 描述 适用场景
HTTP CDN 到源站走明文 HTTP 内网源站、性能敏感场景
HTTPS CDN 到源站强制走 HTTPS 公网源站、安全合规要求
协议跟随 用户用什么协议，CDN 就用什么协议回源 折中方案

实战中要注意：协议跟随容易让同一个资源出现两套回源路径。用户用 HTTP 访问时，CDN 可能用 HTTP 回源；用户用 HTTPS 访问时，CDN 又用 HTTPS 回源。如果源站对 HTTP 和 HTTPS 的处理不完全一致，比如跳转逻辑、Cookie、安全 Header 不一样，就可能出现缓存内容不一致、重复回源、排查困难的问题。生产环境推荐固定 HTTPS 回源。

举个例子：

用户用 HTTP 访问：
http://static.example.com/app.js
        ↓ CDN 协议跟随，用 HTTP 回源
源站返回：301 跳转到 https://static.example.com/app.js

用户用 HTTPS 访问：
https://static.example.com/app.js
        ↓ CDN 协议跟随，用 HTTPS 回源
源站返回：200，直接返回 app.js

这样同一个 app.js，HTTP 链路拿到的是跳转响应，HTTPS 链路拿到的是文件内容。如果 CDN 缓存规则没配好，就可能把 301 或错误的缓存头缓存下来，后面排查会很绕。

4.4 多源站策略

实际生产环境很少只有一个源站，CDN 通常支持配置多源站和回源策略：

策略 行为 适用场景
主备 主源故障时切到备源 容灾，最常用
轮询 按顺序均匀分配 多源站等同性能
权重 按比例分配（如 7:3） 灰度、按容量分配
一致性哈希 同一 URL 固定到某个源 配合源站本地缓存

健康检查机制是多源策略的灵魂——CDN 会定期探测源站可用性（通常是 HTTP 状态码 + 超时），不健康的源站会被自动摘除，恢复后再重新挂回。

4.5 回源请求头

CDN 回源时会主动加一些请求头，让源站能识别真实用户信息：

GET /app.js HTTP/1.1
Host: origin.example.com
X-Forwarded-For: 1.2.3.4, 10.0.0.1   # 客户端真实 IP, 中间节点 IP
X-Real-IP: 1.2.3.4                    # 客户端真实 IP（部分 CDN 提供）
X-Forwarded-Proto: https              # 用户原始访问协议
Via: 1.1 cdn-edge.example             # 经过的代理标识
User-Agent: ...                        # 透传用户的 UA

源站获取真实 IP 的标准做法（Nginx）：

# 信任 CDN 的 IP 段（只有从这些 IP 来的 X-Forwarded-For 才被采信）
set_real_ip_from 1.2.3.0/24;
set_real_ip_from 5.6.7.0/24;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

如果源站不配置 set_real_ip_from，所有日志里的客户端 IP 都会变成 CDN 节点 IP，做风控、限流时会出大问题。

4.6 回源优化机制

1. 回源合并（Origin Shielding / Request Coalescing）

同一时刻多个用户请求同一个未缓存的资源时，CDN 节点合并成一次回源，避免重复请求源站。

没有回源合并：
1000 个用户同时请求 → 1000 次回源 → 源站爆炸

启用回源合并：
1000 个用户同时请求 → 1 次回源 → 1000 个用户共享结果

怎么开启（商业 CDN）：

各家叫法不同，但功能本质一致，在控制台缓存或回源相关的配置页能找到：

厂商 常见名称 备注
阿里云 CDN/DCDN “回源请求合并” 部分产品默认开启
腾讯云 CDN/EdgeOne “合并回源请求” 配合中间层节点效果更好
AWS CloudFront “Origin Shield” 更接近”中间层”概念，是一个独立可选的区域级中转节点
Cloudflare “Argo Tiered Cache” 分层缓存机制，包含合并能力

具体菜单路径各家版本会变，建议直接在控制台搜”合并””Shield””Tiered”这几个关键词。

怎么开启（Nginx 自建场景）：

如果你是用 Nginx 自建反向代理 / 边缘缓存，对应的能力是 proxy_cache_lock：

# 1. 先定义缓存区
proxy_cache_path /var/cache/nginx/cdn
                 levels=1:2
                 keys_zone=cdn_cache:100m
                 max_size=10g
                 inactive=24h;

server {
    listen 80;
    server_name edge.example.com;

    location / {
        proxy_cache cdn_cache;
        proxy_cache_key "$scheme$host$request_uri";
        proxy_cache_valid 200 301 302 1h;

        # 关键：回源合并
        proxy_cache_lock on;              # 同一 key 同一时刻只放一个请求回源
        proxy_cache_lock_timeout 5s;      # 等锁超过 5s 就放行（防止全部卡死）
        proxy_cache_lock_age 5s;          # 上一个回源 5s 没回来，允许再发一个

        # 配套优化：等锁期间可以先返回旧缓存
        proxy_cache_use_stale updating timeout;
        proxy_cache_background_update on; # 后台静默更新

        proxy_pass http://origin_upstream;
    }
}

参数解释：

  • proxy_cache_lock on：核心开关，等同于商业 CDN 的”回源合并”
  • proxy_cache_lock_timeout：兜底超时，避免源站长时间不响应导致所有请求都堵死
  • proxy_cache_use_stale updating：等锁的请求可以先用旧缓存兜底，体验最好
  • proxy_cache_background_update：源站慢的时候用旧缓存返回用户，后台异步更新

验证是否生效：

最简单的办法——压测。

# 先清掉缓存确保是冷启动
curl -X PURGE https://edge.example.com/big.json

# 同时发起 100 个并发请求
ab -n 100 -c 100 https://edge.example.com/big.json

# 同时在源站看 access.log，统计这一秒收到几次请求
tail -f /var/log/nginx/origin-access.log | grep big.json | wc -l

没开合并时，源站会看到 100 次请求；开了合并后，理想情况只有 1 次。

注意事项（踩坑提醒）：

  1. 只对 GET/HEAD 有效：POST、PUT 这类非幂等请求不能合并，CDN 也不会合并
  2. 锁的粒度是 Cache Key：如果 Cache Key 设计太散（带了一堆查询参数），合并效果会大打折扣
  3. 等锁超时是把双刃剑：超时太短会”打穿”（多次回源），超时太长会拖慢用户体验，一般 3~10 秒
  4. **要配合 use_stale**：纯靠合并解决不了”缓存击穿”，旧缓存兜底才是更稳的方案
  5. 源站慢响应会放大问题：一旦源站某个 URL 响应变慢，等锁的所有用户都会被拖住，所以源站超时控制和熔断不能省

2. 中间层节点（父节点）

边缘节点和源站之间增加一层中间层，多个边缘节点共享同一个父节点的缓存：

用户  →  边缘节点  →  父节点（中间层缓存）  →  源站

效果是把可能上百次的回源收敛成几次。腾讯云、阿里云 CDN 都默认提供这个能力，可在控制台开启。

3. Range 回源

大文件（视频、安装包等）支持分片缓存。用户请求 Range: bytes=0-1023 时，CDN 只回源拉这一段，而不是整个文件。

这个能力对视频点播、大文件下载场景非常关键。否则一个 1GB 的视频用户只看了 10MB，CDN 也得把 1GB 全拉下来，浪费严重。

4. 回源跟随重定向

源站返回 301/302 时，CDN 是否要自己跟随重定向再回源？

  • 默认行为通常是不跟随，把重定向直接透传给用户
  • 开启跟随后 CDN 会处理重定向，最终缓存的是重定向后的内容

我的建议：默认关闭，需要时再针对性开启，避免缓存逻辑变得难以排查。

4.7 回源限速与熔断

为保护源站，主流 CDN 提供回源保护机制：

  • 回源带宽上限：超过阈值时延迟或丢弃回源请求
  • 回源 QPS 限制：限制单位时间内的回源次数
  • 回源熔断：源站连续报错时，CDN 临时停止回源，直接返回旧缓存或错误页

我的踩坑记忆：有一次源站升级出 BUG，CDN 连续回源拿到 500，没开熔断的情况下，CDN 把所有节点的缓存都污染成了 500 错误页，源站修复后还得手动刷新全网缓存才恢复。生产环境回源熔断必须开。

五、CDN 与 HTTP 缓存头

5.1 三个关键响应头

CDN 行为受源站响应头强烈影响，最关键的三个：

Cache-Control: public, max-age=31536000, s-maxage=86400
ETag: "abc123"
Last-Modified: Wed, 28 May 2026 10:00:00 GMT

Cache-Control 各指令的含义：

指令 作用
public 允许 CDN 等共享缓存存储（关键，没有它部分 CDN 不会缓存）
private 只允许浏览器缓存，CDN 不缓存
no-cache 每次都要回源验证（不是不缓存！）
no-store 完全不缓存
max-age=N 缓存 N 秒（浏览器和 CDN 共用）
s-maxage=N 仅对共享缓存（CDN）生效，覆盖 max-age

5.2 静态资源的推荐配置

# 带版本号的静态资源（如 app.a1b2c3.js）
Cache-Control: public, max-age=31536000, immutable

# HTML 入口文件
Cache-Control: public, max-age=0, must-revalidate

# 用户私有数据接口
Cache-Control: private, no-cache

immutable 是个好东西，告诉浏览器”这个资源永远不会变，连 304 验证都不用发”。Chrome、Firefox 都支持，能省一笔 RTT。

5.3 一个常见的混淆

很多人分不清 no-cache 和 no-store：

// ❌ 想"不缓存"但写错了
Cache-Control: no-cache  // 实际是"缓存但每次都验证"

// ✅ 真的不想缓存
Cache-Control: no-store

六、CDN 实战配置

6.1 一个 Node.js Express 静态资源服务示例

下面是一个最小可运行示例，演示如何为不同类型的资源配置合适的响应头，让 CDN 缓存策略正确生效。

环境：Node.js 18+，依赖 express@4。

// server.js
const express = require('express');
const path = require('path');

const app = express();

// 1. 带 hash 的静态资源 - 长期缓存
app.use('/static', express.static(path.join(__dirname, 'dist/static'), {
  maxAge: '1y',
  immutable: true,
  setHeaders(res) {
    // 显式声明 public，CDN 才会缓存
    res.setHeader('Cache-Control', 'public, max-age=31536000, immutable');
  }
}));

// 2. HTML 入口 - 不缓存（保证新版本立刻生效）
app.get('/', (req, res) => {
  res.setHeader('Cache-Control', 'public, max-age=0, must-revalidate');
  res.sendFile(path.join(__dirname, 'dist/index.html'));
});

// 3. API 接口 - 用户私有数据
app.get('/api/user', (req, res) => {
  res.setHeader('Cache-Control', 'private, no-cache');
  res.json({ id: 1, name: 'niroli' });
});

// 4. 半动态接口 - 边缘缓存 60 秒
app.get('/api/hot-list', (req, res) => {
  // s-maxage 仅对 CDN 生效，浏览器仍然不缓存
  res.setHeader('Cache-Control', 'public, max-age=0, s-maxage=60');
  res.json({ list: ['item1', 'item2'] });
});

app.listen(3000, () => {
  console.log('Server running at http://localhost:3000');
});

预期效果：

  • /static/app.a1b2c3.js 在 CDN 和浏览器都缓存一年
  • / 永远拉最新（但用 must-revalidate 走 304 验证，避免重复传输）
  • /api/user 不进 CDN
  • /api/hot-list 在 CDN 缓存 60 秒，相当于源站每分钟最多被请求一次

6.2 文件版本化策略

为什么我反复强调”带 hash 的文件名”？看下面对比：

// ❌ 反面案例：靠 query 参数破缓存
<script src="/app.js?v=1.0.1"></script>
// 问题：发版后需要刷 CDN 缓存；CDN 配置不当时版本号被忽略

// ✅ 正面案例：文件名带 hash
<script src="/app.a1b2c3d4.js"></script>
// 优势：新文件就是新 URL，CDN 直接命中新缓存，无需刷新

主流构建工具（Webpack、Vite、Rspack）都支持自动生成 hash 文件名：

// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        entryFileNames: 'assets/[name].[hash].js',
        chunkFileNames: 'assets/[name].[hash].js',
        assetFileNames: 'assets/[name].[hash].[ext]'
      }
    }
  }
};

6.3 HTTPS 配置

CDN 上配置 HTTPS，不能只理解成“把证书传到控制台”。它实际分成两段：

用户浏览器  ← HTTPS →  CDN 边缘节点  ← HTTP/HTTPS →  源站

常见模式：

模式 描述 适用场景
半链路 HTTPS 用户↔CDN 用 HTTPS，CDN↔源站走 HTTP 源站暂时不支持 HTTPS 时的过渡方案
全链路 HTTPS 用户↔CDN↔源站全程加密 推荐的标准配置

我的建议很明确：生产环境优先用全链路 HTTPS。半链路模式看起来“用户访问是 HTTPS”，但 CDN 到源站这一段仍然是明文，运营商劫持、内网窃听、中间人篡改的风险都还在。

HTTPS 配置里有几个容易被忽略的点：

配置项 作用 踩坑点
边缘证书 用户访问 CDN 时使用的证书 证书过期会导致全站 HTTPS 失败，一定要开到期告警
SNI 同一个 IP 上托管多个 HTTPS 域名 老旧客户端不支持 SNI 时可能握手失败
源站证书校验 CDN 回源 HTTPS 时校验证书是否合法 只加密不校验证书，安全性是不完整的
HSTS 强制浏览器后续只用 HTTPS 访问 配错后回滚成本高，建议先短时间灰度
HTTP/2 多路复用，减少连接开销 对大量小资源有收益，但要配合合理的资源拆分
HTTP/3 / QUIC 基于 UDP，弱网和移动网络下更有优势 需要客户端、CDN、网络链路共同支持，不要默认假设全量生效
OCSP Stapling CDN 在握手时附带证书状态 能减少浏览器额外查询证书状态的延迟

源站 HTTPS 还有一个细节：CDN 回源时要不要校验证书域名。

比如 CDN 回源地址是 origin.example.com，但源站证书只签了 www.example.com，有些 CDN 如果开启严格校验，会直接回源失败；如果关闭校验，虽然链路加密了，但 CDN 没有确认“对面真的是目标源站”。

我的实战建议：

  1. 边缘证书开启自动续期和到期告警
  2. CDN 到源站固定走 HTTPS，不用协议跟随
  3. 源站证书尽量使用和回源 Host 匹配的域名
  4. HSTS 先用短 max-age 灰度，确认没问题再拉长
  5. HTTP/3 可以开，但要用监控验证收益，不要为了“先进”而开

6.4 哪些场景不适合 CDN 缓存

CDN 很强，但不是所有请求都应该缓存。我的判断标准很简单：只要内容和具体用户强相关，或者要求强一致，就要非常谨慎。

场景 是否适合缓存 原因
带 hash 的 JS/CSS/图片 适合 URL 不变内容就不变，可以长期缓存
HTML 入口文件 谨慎 发布后要尽快更新，通常短缓存或回源验证
商品详情、新闻详情 适合短缓存 内容相对稳定，可以用秒级/分钟级缓存
用户资料、订单、账户余额 不适合 用户私有数据，缓存错就是严重事故
登录态接口 不适合 依赖 Cookie、Token、Authorization
支付、交易、库存扣减 不适合 强一致要求高，不能返回旧数据
后台管理接口 通常不适合 权限复杂，误缓存风险大
搜索结果 视情况 热门搜索可以短缓存，个性化搜索不适合

几个红线配置要特别小心：

Authorization: Bearer xxx
Cookie: sessionid=xxx
Set-Cookie: sessionid=xxx
Cache-Control: private

看到这些信号时，默认应该认为这个响应不适合被共享缓存。如果确实要缓存，也要明确拆分公共内容和用户私有内容，不要把登录态响应直接丢给 CDN。

还有一个容易忽略的 CORS 场景：

Access-Control-Allow-Origin: https://a.example.com
Vary: Origin

如果源站按请求的 Origin 动态返回 Access-Control-Allow-Origin，但 CDN 的 Cache Key 没有区分 Origin，就可能把 A 站的跨域响应缓存给 B 站，导致跨域异常甚至安全问题。这个时候要么让响应固定，要么把 Origin 纳入缓存变化维度。

七、CDN 进阶话题

7.1 动态加速

传统 CDN 只缓存静态资源，但动态请求（API、登录态相关）也能加速。原理是：

  1. 用户就近接入 CDN 边缘节点
  2. CDN 通过自建的优化骨干网把请求转发到源站
  3. 利用专线、TCP 优化、智能路由等手段降低延迟

我的看法：动态加速本质上是用 CDN 的网络替代公网，对跨国、跨运营商场景效果明显，国内同地域加速效果有限。

7.2 边缘计算（Edge Computing）

新一代 CDN 普遍支持在边缘节点跑代码，比如 Cloudflare Workers、AWS Lambda@Edge、阿里云 EdgeRoutine。

典型场景：

  • A/B 测试分流
  • 鉴权和限流
  • 简单的 API 聚合
  • 个性化内容生成

代码示例（Cloudflare Workers 风格）：

// 边缘节点上运行的代码
export default {
  async fetch(request) {
    const url = new URL(request.url);

    // 边缘鉴权
    const token = request.headers.get('Authorization');
    if (!token) {
      return new Response('Unauthorized', { status: 401 });
    }

    // 根据用户地理位置返回不同内容
    const country = request.cf?.country || 'CN';
    if (country === 'CN') {
      url.hostname = 'cn-origin.example.com';
    } else {
      url.hostname = 'global-origin.example.com';
    }

    return fetch(url.toString(), request);
  }
};

7.3 安全防护

主流 CDN 都集成了基础的安全能力：

  • 防 DDoS：边缘节点天然分布广，能吸收大流量攻击
  • WAF（Web 应用防火墙）：在边缘拦截 SQL 注入、XSS 等攻击
  • CC 防护：识别并限制异常的高频请求
  • 盗链防护：基于 Referer、Token 鉴权，防止资源被外部站点盗用

防盗链一个简单实战配置：

# 仅允许特定 Referer 访问
allowed_referers:
  - "*.example.com"
  - "example.com"

# 空 Referer 直接拒绝
deny_empty_referer: true

7.4 多 CDN 与容灾

单 CDN 架构简单，但它有一个天然问题：你把全站可用性押在了一家厂商身上。大部分中小业务没必要一开始就上多 CDN，但如果是大促、游戏更新包、音视频、核心官网，至少要提前设计容灾方案。

常见多 CDN 架构：

              ┌──────────────┐
用户请求  →    │  DNS / GSLB   │
              └──────┬───────┘
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
   CDN 厂商 A     CDN 厂商 B     CDN 厂商 C
       │             │             │
       └─────────────┼─────────────┘
                     ▼
                   源站

几种常见策略：

策略 做法 适用场景
主备 CDN 平时走 A，故障时切到 B 成本可控，适合多数业务
权重分流 A 70%，B 30% 平滑验证多家 CDN 质量
地域分流 国内走 A，海外走 B 海外访问质量差异明显的业务
运营商分流 电信、联通、移动走不同厂商 对国内链路质量要求高的业务
URL 级分流 图片走 A，视频走 B，下载包走 C 不同资源类型成本和能力不同

多 CDN 真正难的不是“把流量分出去”，而是配置一致性：

  1. 缓存规则要一致：TTL、忽略参数、状态码缓存策略不能互相打架
  2. HTTPS 证书要一致：每家 CDN 都要有证书续期和告警
  3. 回源 Host 要一致：否则切过去后可能全站 404
  4. 刷新预热要一致：发布系统要能同时刷新多家 CDN
  5. 日志口径要统一：否则排查时很难对齐命中率和错误率

我的建议：如果你还没有自动化发布和监控，不要轻易上复杂的多 CDN。先做主备 CDN + 一键切流预案，收益最大，复杂度最低。

八、CDN 监控指标

CDN 上线后不能只看“能不能访问”，真正要盯的是命中率、回源、延迟和错误率。

8.1 命中率指标

最核心的两个指标：

指标 含义 容易误解的点
请求命中率 命中 CDN 缓存的请求数 / 总请求数 小文件多时容易看起来很高
字节命中率 命中 CDN 缓存的流量 / 总流量 更能反映源站带宽是否被保护

举个例子：

10000 个小图标请求都命中 CDN，每个 2KB
10 个视频请求都回源，每个 1GB

这时请求命中率可能很好看，但字节命中率会很差，因为大头流量都打回源站了。所以排查源站带宽压力时，字节命中率比请求命中率更关键。

8.2 回源指标

回源相关指标直接决定源站压力：

指标 说明
回源请求数 CDN 向源站发起了多少请求
回源带宽 CDN 从源站拉走了多少流量
回源状态码 源站返回给 CDN 的 2xx/3xx/4xx/5xx 分布
回源延迟 CDN 到源站的响应时间
回源失败率 超时、连接失败、TLS 握手失败等异常比例

如果用户访问报 502/504，第一反应不要只看边缘节点，也要看回源是否超时、源站是否拒绝了 CDN IP、源站证书是否异常。

8.3 用户体验指标

用户侧建议重点看：

  • 首包时间（TTFB）
  • 下载耗时
  • P95 / P99 延迟
  • 4xx / 5xx 错误率
  • 各地域、各运营商访问质量
  • HTTP/2、HTTP/3 协议占比

平均值意义有限，P95/P99 更能反映真实体验。比如平均 100ms，但 P99 是 3s，说明少数用户体验已经很差了。

8.4 运维操作指标

刷新和预热也要监控：

操作 要看什么
刷新 是否成功、多久生效、是否超过额度
预热 成功率、失败 URL、预热耗时
配置变更 是否全网生效、是否有灰度失败
证书续期 是否即将过期、是否部署成功

我的经验是：CDN 故障很多不是“节点坏了”，而是发布、刷新、证书、配置变更这些操作环节出了问题。

九、CDN 成本模型

CDN 的技术方案最后一定会落到成本上。一个缓存策略如果命中率很低，本质上就是“花 CDN 的钱，又没省源站的钱”。

常见计费项：

成本项 说明 优化方向
下行流量 CDN 返回给用户的流量 压缩、图片格式优化、减少无效资源
峰值带宽 按带宽峰值计费 削峰、预热、错峰发布
请求数 按 HTTP/HTTPS 请求量计费 合并小资源、合理使用 HTTP/2
HTTPS 请求 部分厂商对 HTTPS 请求单独计费 关注小文件高频请求
回源流量 CDN 从源站拉取内容的流量 提升命中率，减少不必要回源
刷新/预热 超出免费额度后收费或限频 用文件 hash 替代频繁刷新
边缘函数 Workers、EdgeRoutine 等调用费用 把复杂逻辑留在源站，边缘只做轻逻辑
日志服务 实时日志、离线日志投递费用 只保留必要字段和周期

几个比较实用的省钱思路：

  1. 静态资源文件名带 hash，少用刷新
  2. 图片开启 WebP/AVIF、自适应裁剪和压缩
  3. 大文件提前预热，避免活动开始时集中回源
  4. 对低价值资源设置更长 TTL，提高命中率
  5. 对无意义查询参数做忽略，避免缓存碎片
  6. 定期看 TOP URL，优先优化最耗流量的资源
  7. 边缘函数只做轻逻辑，不要把复杂业务搬到边缘

我的判断是：CDN 成本优化不要一上来抠小请求，先看TOP 流量资源、字节命中率、回源带宽，这三个通常决定了大头成本。

十、常见问题与排查

10.1 命中率上不去怎么办

排查思路：

  1. 看 Cache Key 配置：是否包含了不必要的查询参数或 Header
  2. 看响应头：源站是否返回了 Cache-Control: private 或 no-store
  3. 看 URL 模式：是不是大量带时间戳的请求
  4. 看缓存时间：是否设置过短（比如 60 秒）导致频繁失效

10.2 用户访问到旧版本

通常是发布时 CDN 缓存没刷新。最佳实践：

  • 静态资源用 hash 文件名，不靠刷新
  • HTML 入口必须刷新（或者直接不让 CDN 缓存）
  • 在控制台设置好刷新规则的灰度

10.3 回源风暴

现象：某个热点资源缓存过期的瞬间，全网节点同时回源，把源站打爆。

原因：缓存同时过期（”缓存雪崩”的 CDN 版本）。

解决：

  • 开启 CDN 的”回源合并”功能（同一时刻同一 URL 只回源一次）
  • 用预热提前把新版本推到边缘
  • 配置中间层节点，减少直接回源的请求数

10.4 调试 CDN 是否命中

最常用的排查手段是看响应头里的 X-Cache 字段（不同厂商字段名略有差异）：

X-Cache: HIT from Edge.Beijing
X-Cache: MISS from Edge.Shanghai
X-Cache: REVALIDATED from Edge.Guangzhou

# 用 curl 看一眼
curl -I https://static.example.com/app.a1b2c3.js

# 多请求几次，第一次 MISS，后续应该是 HIT

小结

  1. CDN 本质是分布式多级缓存系统，核心价值是把内容放到离用户最近的地方
  2. 一次 CDN 请求的关键流程：DNS 调度 → 边缘节点缓存判断 → 命中直接返回 / 未命中回源
  3. DNS 调度、HTTP 302 调度、Anycast 是三种主流调度方式，商业 CDN 多用 DNS + 302 组合
  4. Cache Key 决定了”什么是同一个资源”，是 CDN 命中率的关键，要小心查询参数、Cookie、Origin 带来的缓存污染
  5. 回源类型选择：静态资源回 OSS/COS，动态业务回域名，IP 回源仅在特殊场景用
  6. 回源 Host 是最容易踩坑的配置，必须和源站的虚拟主机配置（或对象存储域名）严格匹配
  7. 多源站务必配置健康检查；启用回源合并和中间层节点，是控制源站压力的关键手段
  8. 静态资源用版本化文件名 + 长期缓存，HTML 入口用 must-revalidate，私有数据默认不要进 CDN 缓存
  9. 生产环境优先使用全链路 HTTPS，源站证书校验、HSTS、HTTP/2、HTTP/3 都要结合监控逐步开启
  10. 多 CDN 的核心难点是配置一致性，建议先从主备 CDN + 一键切流预案做起
  11. CDN 监控要同时看请求命中率和字节命中率，排查源站压力时后者更关键
  12. 成本优化优先看 TOP 流量资源、字节命中率和回源带宽，不要一上来抠小请求
  13. 大流量活动前必须做缓存预热；生产环境建议配置回源熔断，防止源站故障污染全网缓存
  14. 命中率上不去优先排查 Cache Key、响应头、查询参数和缓存时间
  15. 边缘计算让 CDN 从”内容分发”演进到”边缘代码执行”，但复杂业务逻辑不要轻易搬到边缘
