组件库的国际化与移动端适配

发表于2026|更新于2026|工程化
|字数总计:2.2k|阅读时长:8分钟

前言：一个要给多团队、多产品用的组件库，绕不开两个横切需求：国际化和移动端适配。它们不是某个组件的功能，而是整个库都要考虑的能力。这一篇讲组件库层面（不是应用层面）怎么设计 i18n 和适配——组件库的 i18n 和你在业务项目里配 vue-i18n 是两回事，它要解决的是「库自带的文案怎么让用户换语言、怎么按需只加载用到的语言包」。

组件库为什么需要「自己的」i18n

先澄清一个常见困惑：业务项目做 i18n 用 vue-i18n / react-intl 就行，为什么组件库还要单独搞一套？

因为组件库里有自带文案。比如：

  • 表格的「暂无数据」；
  • 分页的「上一页 / 下一页」；
  • 日期选择器的月份、星期名；
  • 上传组件的「点击上传」；
  • 表单的默认校验提示。

这些文案是组件库内置的，用户没法通过自己的 i18n 去改（他们的 i18n 不认识你组件内部的文案）。所以组件库必须提供自己的多语言机制，让用户能整体切换这些内置文案的语言。

关键认知：组件库的 i18n 只管「库自带的那部分文案」，用户业务里的文案还是走用户自己的 i18n。两者不冲突，各管各的。

组件库 i18n 的基本结构

主流做法是：定义一套语言包（locale）结构，通过一个全局的 Provider / Config 注入当前语言。

先定义语言包类型和内容：

// locale/lang/zh-cn.ts
export default {
  name: 'zh-cn',
  table: { emptyText: '暂无数据' },
  pagination: { prev: '上一页', next: '下一页' },
  datepicker: {
    months: ['一月', '二月', '三月', /* ... */],
    weeks: ['日', '一', '二', '三', '四', '五', '六'],
  },
}

// locale/lang/en.ts
export default {
  name: 'en',
  table: { emptyText: 'No Data' },
  pagination: { prev: 'Previous', next: 'Next' },
  datepicker: {
    months: ['January', 'February', /* ... */],
    weeks: ['Sun', 'Mon', 'Tue', 'Wed', 'Thu', 'Fri', 'Sat'],
  },
}

组件通过一个组合式函数读取当前语言的文案（以 Vue 为例）：

// composables/use-locale.ts
import { inject, computed } from 'vue'
import zhCn from '../locale/lang/zh-cn'

export const localeKey = Symbol('myui-locale')

export function useLocale() {
  const locale = inject(localeKey, computed(() => zhCn))
  // t('table.emptyText') 这样取文案
  const t = (path: string) => {
    return path.split('.').reduce((obj, key) => obj?.[key], locale.value as any)
  }
  return { locale, t }
}

组件里用：

const { t } = useLocale()
// 模板里：{{ t('table.emptyText') }}

用户在应用根部通过 Provider 提供语言：

import { ConfigProvider } from '@my-ui/components'
import en from '@my-ui/components/locale/en'

// <ConfigProvider :locale="en"> ...整个应用... </ConfigProvider>

这就是 Element Plus、Ant Design 的 ConfigProvider + locale 模式。核心是用依赖注入把语言往下传，组件按需取文案。

按需加载语言包：别把几十种语言全打进去

这是组件库 i18n 的深水区。如果你的库支持 40 种语言，全量打包会让用户的 bundle 白白背上几十份语言文案——而用户可能只用中英两种。

解决按需加载有几个层次：

1. 语言包独立成 subpath，用户按需 import

配合前面讲的 subpath exports，每种语言是一个独立入口：

{
  "exports": {
    "./locale/zh-cn": "./dist/locale/zh-cn.mjs",
    "./locale/en": "./dist/locale/en.mjs",
    "./locale/ja": "./dist/locale/ja.mjs"
  }
}

用户只 import 自己要的：

import zhCn from '@my-ui/components/locale/zh-cn'
import en from '@my-ui/components/locale/en'
// 没 import 的语言，一个字节都不会进 bundle

这是最基础也最有效的按需——用户 import 哪个语言，就只打包哪个。

2. 动态导入实现运行时懒加载

如果用户要做「切到日语时才下载日语包」，用动态 import()（原理见「Tree Shaking、副作用与代码分割」那篇的代码分割）：

async function loadLocale(lang: string) {
  // 每种语言被打成独立 chunk，切到时才下载
  const mod = await import(`@my-ui/components/locale/${lang}`)
  return mod.default
}

打包器会把每个语言包拆成独立 chunk，运行时按需下载。适合语言多、且用户会动态切换的国际化产品。

3. 文案里的复数、日期、数字格式

比 UI 文案更难的是「和语言强相关的格式」：复数（英语 1 item / 2 items）、日期格式、数字千分位、货币。不要自己造轮子，用平台内置的 Intl：

// 日期格式：Intl 自动按 locale 输出
new Intl.DateTimeFormat('en-US').format(new Date())   // 7/6/2026
new Intl.DateTimeFormat('zh-CN').format(new Date())   // 2026/7/6

// 数字/货币
new Intl.NumberFormat('de-DE', { style: 'currency', currency: 'EUR' }).format(1234.5)
// 1.234,50 €

Intl 是浏览器和 Node 内置的，零依赖、零体积、覆盖全球 locale。组件库涉及日期、数字展示时，优先用 Intl 而不是引入 moment/dayjs 的一堆 locale 文件。

移动端适配：rem 与 vw

移动端适配的本质问题是：设计稿是按某个固定宽度（如 375px）画的，但手机屏幕宽度各不相同，怎么让页面按屏幕宽度等比缩放。两种主流方案：rem 和 vw。

rem 方案

rem 是相对于根元素（html）字体大小的单位。适配思路是：**用 JS 根据屏幕宽度动态设置 html 的 font-size**，这样所有用 rem 的尺寸都会跟着屏幕缩放。

// 以 375px 设计稿、根字号 = 屏宽/10 为例
function setRootFontSize() {
  const width = document.documentElement.clientWidth
  document.documentElement.style.fontSize = width / 10 + 'px'
}
setRootFontSize()
window.addEventListener('resize', setRootFontSize)

写样式时，把设计稿 px 换算成 rem。手动换算太累，用 PostCSS 插件自动做——postcss-pxtorem：

// postcss.config.js
module.exports = {
  plugins: {
    'postcss-pxtorem': {
      rootValue: 37.5,      // 375 设计稿 / 10
      propList: ['*'],
      selectorBlackList: ['.norem'],  // 不想转的类
    },
  },
}

这样你在 CSS 里写 width: 75px，构建后自动变成 width: 2rem，运行时再根据屏宽换算成实际像素。

vw 方案

vw 是视口宽度的百分比，1vw = 视口宽度的 1%。它比 rem 更直接——不需要 JS 动态设根字号，纯 CSS 就能等比缩放。

同样用 PostCSS 插件自动换算，postcss-px-to-viewport（或 @vituum/postcss-px-to-viewport 等维护版本）：

module.exports = {
  plugins: {
    'postcss-px-to-viewport': {
      viewportWidth: 375,   // 设计稿宽度
      unitPrecision: 5,
    },
  },
}

写 width: 75px（375 设计稿），自动变成 width: 20vw。

rem vs vw 怎么选

维度 rem vw
是否要 JS 要（动态设根字号） 不要，纯 CSS
兼容性 极好 现代浏览器都支持
大屏限制 容易（限制 font-size 最大值） 需配合 max-width 容器
心智 稍绕（多一层根字号） 直观

新项目优先考虑 vw，纯 CSS、更简单、不需要那段设根字号的 JS；只有要兼容很老的环境，或需要精细控制大屏上限时，才用 rem。

作为组件库作者，这里有个重要取舍：通用组件库通常不应该硬编码某种移动端适配方案。因为你不知道用户用 rem 还是 vw、设计稿是 375 还是 750。更好的做法是组件内部用相对单位或让尺寸走 CSS 变量（token），把 px→rem/vw 的转换交给用户的构建配置。如果是专门的移动端组件库（如 Vant），才在库内部统一用 vw/rem 方案。

一个真实的坑：如果组件库产物里已经把 px 转成了 vw，用户又在自己项目里再跑一遍 postcss-px-to-viewport，可能二次转换出问题。所以组件库产物要么保持 px（让用户转），要么明确文档说明「产物已按 xxx 设计稿转成 vw，请勿重复转换」。

小结

  1. 组件库要有自己的 i18n，只管库内置文案（表格空数据、分页、日期等），用户业务文案仍走用户自己的 i18n。
  2. i18n 结构靠 ConfigProvider + 依赖注入把当前语言往下传，组件通过 useLocale 按需取文案。
  3. 语言包要能按需：独立成 subpath exports 让用户 import 哪个打哪个，语言多时用动态 import() 运行时懒加载。
  4. 复数、日期、数字、货币格式优先用内置 Intl，零依赖零体积，别引 moment/dayjs 的 locale。
  5. 移动端适配两方案：rem 需 JS 动态设根字号，vw 纯 CSS 等比缩放；新项目优先 vw。
  6. px 到 rem/vw 的换算用 PostCSS 插件（postcss-pxtorem / postcss-px-to-viewport）自动做，别手算。
  7. 通用组件库不要硬编码适配方案，把转换交给用户构建；专门的移动端组件库才在库内统一方案，并注意避免二次转换。
