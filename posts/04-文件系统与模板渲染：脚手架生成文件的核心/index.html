文件系统与模板渲染：脚手架生成文件的核心

发表于2026|更新于2026|工程化
|字数总计:2.5k|阅读时长:9分钟

前言：脚手架问完一圈问题，最终要落地的就是一件事——往磁盘上生成一堆文件。这一篇讲清楚脚手架的核心能力：用 node:fs 读写/复制文件、递归拷贝模板目录、把模板里的占位符替换成用户的真实信息。这是「create-xxx」这类工具的发动机。

脚手架生成文件的两种思路

把模板变成项目，业界主要有两种做法：

思路 做法 代表
静态模板拷贝 准备一份完整模板目录，整体复制到目标位置，再替换少量占位符 create-vite 风格
动态拼装 按用户选项，用代码逐个生成/拼接文件内容 选项极多、组合爆炸的工具

绝大多数脚手架用第一种：拷贝 + 替换。它简单、可维护、模板本身就是一个能直接跑的项目，改模板不用改代码。这一篇主要讲这种思路。

node:fs：现代写法用 fs/promises

Node 的文件操作在 node:fs 模块里。现在写工具一律用 Promise 版本 node:fs/promises，配合 async/await，比回调和同步版清爽得多。

import { readFile, writeFile, mkdir, readdir, stat, cp, rm } from 'node:fs/promises'
import { existsSync } from 'node:fs'
import path from 'node:path'

注意一个小细节：existsSync 在 node:fs 里（同步判断存在），而读写操作在 node:fs/promises 里。判断「目录在不在」用 existsSync 很方便，不必硬转成 promise。

几个最常用的操作：

// 读文件内容
const content = await readFile('package.json', 'utf-8')

// 写文件（目录不存在会报错，所以先确保目录在）
await mkdir('dist', { recursive: true }) // recursive 让多级目录一次建好
await writeFile('dist/index.js', 'console.log(1)')

// 列出目录内容
const entries = await readdir('src')

// 删除（recursive + force 类似 rm -rf）
await rm('dist', { recursive: true, force: true })

fs-extra：更顺手的文件系统工具库

如果你觉得原生 fs/promises 写起来还是有点散，脚手架里还有一个很常见的第三方库：fs-extra。它可以理解成 fs 的增强版，补了一些工程里高频但原生 API 不够顺手的方法。

npm i fs-extra

import fs from 'fs-extra'

// 目录不存在就创建，多级目录也能一次处理
await fs.ensureDir('dist/assets')

// 复制文件或目录，目录会自动递归
await fs.copy('template', 'my-app')

// 判断路径是否存在，返回 boolean
const exists = await fs.pathExists('my-app/package.json')

// 写文件前自动确保父目录存在
await fs.outputFile('my-app/src/index.js', 'console.log(1)')

// 删除文件或目录，效果类似 rm -rf
await fs.remove('my-app/dist')

它的好处是语义更贴近脚手架场景：ensureDir、copy、remove、pathExists 这些名字一看就知道在干什么。早些年 Node 原生没有 fs.cp、fs.rm 的时候，fs-extra 基本是标配。

不过现在 Node 原生文件系统能力已经补得很齐了，所以我的建议是：**简单脚手架优先用 node:fs/promises；如果项目里大量出现复制、清空、确保目录、读写 JSON 这类操作，再引入 fs-extra**。这样既不滥加依赖，也能在复杂场景里少写很多样板代码。

路径处理：永远用 node:path

跨平台是脚手架绕不开的坑。Windows 用 \，类 Unix 用 /，绝对不要手写字符串拼路径。一律用 node:path：

import path from 'node:path'

// ✅ 正面案例：跨平台安全
const target = path.join(process.cwd(), 'my-app', 'src', 'index.ts')

// ❌ 反面案例：Windows 上会出问题
const bad = process.cwd() + '/my-app/src/index.ts'

还有一个 ESM 下的高频问题：拿「当前文件所在目录」。CJS 里有 __dirname，ESM 里没有，要这样还原（这点在模块系统篇也提过）：

import { fileURLToPath } from 'node:url'
import path from 'node:path'

const __dirname = path.dirname(fileURLToPath(import.meta.url))

// 脚手架里常用它定位「打包进工具里的模板目录」
const templateDir = path.resolve(__dirname, '../templates/vue')

这个 templateDir 很关键：脚手架的模板一般和代码一起发布，运行时要靠 import.meta.url 算出模板的真实位置，而不能假设用户在哪个目录跑命令。

递归拷贝模板目录

把模板目录整个复制到目标位置，是拷贝式脚手架的第一步。Node 16.7+ 提供了 fs.cp，可以直接递归拷贝，省去自己写递归：

import { cp } from 'node:fs/promises'

await cp(templateDir, targetDir, { recursive: true })

但实际项目里，你往往需要边拷贝边处理：跳过某些文件、重命名（比如模板里放 _gitignore，生成时改名为 .gitignore）、对文本文件做占位符替换。这时候手写递归更可控：

import { readdir, mkdir, copyFile, readFile, writeFile } from 'node:fs/promises'
import path from 'node:path'

// 模板里以 _ 开头的特殊文件，生成时还原成 . 开头
const renameMap = {
  _gitignore: '.gitignore',
  _npmrc: '.npmrc',
}

async function copyTemplate(srcDir, destDir, data) {
  await mkdir(destDir, { recursive: true })
  const entries = await readdir(srcDir, { withFileTypes: true })

  for (const entry of entries) {
    const srcPath = path.join(srcDir, entry.name)
    const destName = renameMap[entry.name] ?? entry.name
    const destPath = path.join(destDir, destName)

    if (entry.isDirectory()) {
      // node_modules 这类目录直接跳过
      if (entry.name === 'node_modules') continue
      await copyTemplate(srcPath, destPath, data) // 递归
    } else {
      await copyFileWithRender(srcPath, destPath, data)
    }
  }
}

为什么模板里要用 _gitignore 而不是直接 .gitignore？不是因为 .gitignore 自己会被 Git 忽略，它完全可以被 Git 跟踪；也不要简单理解成“npm 发布一定会忽略 .gitignore”。更准确地说，.gitignore 对 npm 打包有特殊语义：当没有 .npmignore 时，npm 会读取 .gitignore 的内容作为发布忽略规则，历史上也出现过 .gitignore 被工具链改名或特殊处理的问题。为了避免模板文件被当成包管理工具的控制文件，社区常见做法是：模板里存成 _gitignore，生成项目时再还原成 .gitignore。create-vite 就是这么做的。

占位符替换：从简单到模板引擎

拷贝时要把模板里的占位符换成用户的真实数据，比如把 package.json 里的项目名、把 README 里的标题替换掉。

方案一：字符串替换（最简单）

模板里用一个约定的占位符，比如 {{projectName}}：

{
  "name": "{{projectName}}",
  "version": "0.0.0"
}

替换逻辑：

async function copyFileWithRender(srcPath, destPath, data) {
  // 只对文本文件做替换，二进制文件（图片等）直接拷
  const textExt = ['.json', '.js', '.ts', '.md', '.html', '.vue', '.css']
  if (!textExt.includes(path.extname(srcPath))) {
    await copyFile(srcPath, destPath)
    return
  }

  let content = await readFile(srcPath, 'utf-8')
  // 把所有 {{key}} 替换成 data[key]
  content = content.replace(/\{\{(\w+)\}\}/g, (_, key) => data[key] ?? '')
  await writeFile(destPath, content)
}

这种方案够应付大部分场景：项目名、作者、版本号这类「填空」。

方案二：EJS 模板引擎（需要逻辑时）

当模板里需要条件和循环——比如「选了 TypeScript 才写某段配置」「根据选中的插件生成不同 import」——简单字符串替换就不够了，这时候上模板引擎。ejs 是 Node 脚手架里最常用的一个。

npm i ejs

模板 package.json.ejs：

{
  "name": "<%= projectName %>",
  "scripts": {
    "dev": "vite"<% if (useTs) { %>,
    "typecheck": "tsc --noEmit"<% } %>
  }
}

渲染：

import ejs from 'ejs'
import { readFile, writeFile } from 'node:fs/promises'

const tpl = await readFile('templates/package.json.ejs', 'utf-8')
const output = ejs.render(tpl, { projectName: 'my-app', useTs: true })
await writeFile('my-app/package.json', output)

ejs 语法：<%= value %> 输出值，<% if/for %> 写逻辑。它让模板具备了「根据选项生成不同内容」的能力。

我的建议：先用字符串替换，不够了再上 EJS。很多脚手架其实不需要模板引擎，纯拷贝 + 填空就够。引入 EJS 是为了处理真正的条件/循环逻辑，别为了「显得专业」过早引入。

安全细节：覆盖前先确认

生成项目前，目标目录可能已经存在。直接覆盖会丢用户数据，这是个严重的坑。正确做法是先检查、再交互确认：

import { existsSync } from 'node:fs'
import { readdir, rm } from 'node:fs/promises'

async function ensureTargetDir(targetDir, force) {
  if (!existsSync(targetDir)) return

  const files = await readdir(targetDir)
  if (files.length === 0) return // 空目录，可以用

  if (!force) {
    // 实际项目里这里应该用上一篇的 confirm 交互询问
    throw new Error(`目录 ${targetDir} 非空，加 --force 可清空后重建`)
  }

  await rm(targetDir, { recursive: true, force: true })
}

create-vite 这类工具就是这么处理的：目标目录非空时，会明确问你「是清空、还是取消」，而不是默默覆盖。

小结

  1. 脚手架生成文件主流是「拷贝模板 + 替换占位符」，模板本身就是可运行项目，改模板不改代码。
  2. 文件操作优先用 node:fs/promises 配合 async/await，复杂场景可以引入 fs-extra 减少样板代码。
  3. 路径一律用 node:path，ESM 下用 fileURLToPath(import.meta.url) 还原 __dirname 来定位模板目录。
  4. 递归拷贝可用 fs.cp 或 fs-extra.copy，但需要跳过文件/重命名/替换时，手写递归更可控。
  5. 模板里的点文件可以存成 _gitignore，生成时还原成 .gitignore，避免被 npm 打包规则的特殊语义影响。
  6. 占位符先用字符串替换，需要条件/循环逻辑时再上 ejs，不要过早引入模板引擎。
  7. 覆盖已存在的非空目录前，必须检查并交互确认，绝不静默覆盖。
