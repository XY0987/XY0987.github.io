Babel、SWC 与 Oxc：编译链、polyfill 策略与取舍

发表于2026|更新于2026|工程化
|字数总计:2.8k|阅读时长:10分钟

前言：构建工具负责打包，但「把新语法转成老浏览器能跑的代码」这件事，是另一条独立的链路——编译/转译。这条链路里 Babel 是老大哥，SWC 是 Rust 写的快速替代，Oxc 则是 Vite 8 这类新工具链正在押注的下一代基础设施。这一篇把编译链讲清楚：AST 是什么、preset-env 和 browserslist 怎么联动、polyfill 到底怎么注入，最后说 Babel、SWC 和 Oxc 怎么选。

转译的本质：源码 → AST → 源码

Babel、SWC、Oxc 这类工具，干的都是同一件事：把一段代码转成另一段代码。中间的核心是 AST（抽象语法树）。

源码字符串
   │ parse（解析）
   ▼
  AST（抽象语法树，代码的结构化表示）
   │ transform（遍历 + 修改节点）
   ▼
  新 AST
   │ generate（生成）
   ▼
新源码字符串

为什么要转成 AST 再处理，而不是直接字符串替换？因为代码是有结构的。比如你想把箭头函数 () => {} 转成普通函数，光靠正则替换根本处理不了嵌套、作用域、this 绑定这些语义。AST 把代码变成一棵可遍历的树，每个节点是一个语法结构，转换才能精确。

举个直观的例子，const a = 1 解析后大致是这样一棵树：

VariableDeclaration (kind: const)
└── VariableDeclarator
    ├── id: Identifier (name: a)
    └── init: NumericLiteral (value: 1)

Babel 的转换插件，本质就是「遍历这棵树，遇到某种节点就改写它」。比如把所有 const/let 改成 var 来降级。

Babel 编译链：preset、browserslist、polyfill

Babel 自己只是个「parse → transform → generate」的引擎，真正干活的是插件。一堆插件打包成一套，就是 preset（预设）。

最重要的预设是 @babel/preset-env。它解决一个核心问题：我不想手动列出要转哪些语法，你帮我根据目标浏览器自动决定。

preset-env 和 browserslist 的联动

preset-env 怎么知道要转哪些语法？答案是看 browserslist 配置——你声明要支持哪些浏览器，它就只转那些浏览器不支持的语法。

// package.json
{
  "browserslist": [
    "> 0.5%",
    "last 2 versions",
    "not dead"
  ]
}

// babel.config.js
module.exports = {
  presets: [
    ['@babel/preset-env', {
      // 不写 targets 时，preset-env 会自动读 browserslist
    }],
  ],
}

这套联动的价值在于：如果你的目标浏览器都支持箭头函数，preset-env 就不会去转它，产物更小、更现代。反之目标包含老浏览器，它才降级。

我的理解：browserslist 是「需求声明」（我要支持谁），preset-env 是「执行者」（那我就转到这个程度）。它不光给 Babel 用，Autoprefixer、esbuild、Lightning CSS 等很多工具都读同一份 browserslist，所以它是整个工程的「兼容性单一事实源」。

语法转换 ≠ API polyfill

这是最容易混淆的点，必须分清：

  • 语法（syntax）：箭头函数、解构、可选链 ?.、class 等。这些是写法，Babel 能直接转成等价的老写法。
  • API：Promise、Array.prototype.includes、Object.assign 等。这些是运行时方法，老浏览器里压根不存在这个函数，光靠语法转换无能为力，必须注入实现——这就是 polyfill。
// 语法降级：箭头函数 → 普通函数，Babel 直接转
const fn = () => 1
// 转成：var fn = function () { return 1 }

// API：Promise 在老浏览器没有，转语法没用，得 polyfill 补一个 Promise 实现
const p = Promise.resolve(1)

这里要额外提醒一句：core-js 主要补的是 ECMAScript 标准 API，像 fetch 这种 Web API 不在它的覆盖范围里。如果要兼容老浏览器的 fetch，通常要单独引入 whatwg-fetch 这类 polyfill，或者在 Node 侧用 undici 这类运行时方案。

polyfill 策略：core-js 与 useBuiltIns

polyfill 的实现来自 core-js 这个库。preset-env 通过 useBuiltIns 选项控制怎么注入 core-js：

useBuiltIns 行为 评价
false（默认） 不自动注入，要你手动 import 容易漏
entry 在入口按 browserslist 注入「目标浏览器缺的全部 polyfill」 全但可能偏大
usage 只注入「代码里实际用到、且目标浏览器缺」的 polyfill 推荐，最省

推荐配置：

// babel.config.js
module.exports = {
  presets: [
    ['@babel/preset-env', {
      useBuiltIns: 'usage', // 按需注入
      corejs: '3.37',        // 指定 core-js 版本，必须装 core-js 依赖
    }],
  ],
}

npm i core-js

usage 模式下，你代码里写了 [].includes()，且 browserslist 里有不支持它的浏览器，Babel 才会自动 import 'core-js/modules/es.array.includes'。没用到的就不注入，产物最小。

坑：用 useBuiltIns: 'usage' 必须指定 corejs 版本并安装 core-js，否则要么报错要么注入的 polyfill 和你装的版本对不上。

SWC：Babel 的 Rust 替代

SWC（Speedy Web Compiler）做的事和 Babel 一样——parse / transform / generate，转 TS、JSX、降级语法。区别是它用 Rust 写、大量并行，速度比 Babel 快一个数量级。

npm i -D @swc/core @swc/cli

// .swcrc
{
  "jsc": {
    "parser": { "syntax": "typescript", "tsx": true }
  },
  "env": {
    "targets": "> 0.5%, last 2 versions, not dead",
    "mode": "usage",
    "coreJs": "3.37"
  }
}

可以看到 SWC 也支持 env（对应 preset-env 的思路）、读 browserslist 风格的 targets、按 usage 注入 core-js polyfill。注意不要同时配置 jsc.target 和 env，二者是两条目标环境配置路径；另外 coreJs 最好写具体 minor 版本，比如 "3.37"，不要只写 "3"，否则容易因为版本解析导致较新的 polyfill 没被注入。

还要说清楚一个取舍：SWC 的 usage 模式虽然概念上类似 Babel，但复杂用法下的 polyfill 识别不如 Babel 稳。如果你的项目要兼容很多老环境，且 polyfill 准确性比速度更重要，Babel 的 preset-env + core-js 仍然更稳。

Oxc：Vite 8 背后的新编译基础设施

Oxc（Oxidation Compiler）也是 Rust 写的 JS/TS 工具链，但它的定位不只是「又一个 Babel 替代品」。它更像是一组共享底层能力的工具集合：parser、transformer、resolver、minifier、linter、formatter 都围绕同一套基础设施演进。

放到 Vite 8 里看会更直观：Vite 8 官方迁移文档里明确说，Vite 8 使用 Rolldown + Oxc 这套 Rust 工具链替代过去的 Rollup + esbuild 路线，其中 JS transform 由 Oxc 负责，esbuild 配置会被兼容转换到 oxc 配置，但 esbuild 入口已经是迁移期方案。

// vite.config.ts
import { defineConfig } from 'vite'

export default defineConfig({
  oxc: {
    jsx: {
      runtime: 'automatic',
      importSource: 'react',
    },
  },
})

我的理解是：Babel、SWC、Oxc 不是简单的「谁淘汰谁」。Babel 强在生态和可定制转换；SWC 强在成熟快速的常规转译；Oxc 更强调和 Rolldown、Vite 这类新工具链的深度协同。比如 Oxc 的语义分析能力可以被 Rolldown 用来做更激进的 tree-shaking，这就不只是「把代码转快一点」了，而是整个构建链路一起提速。

但 Oxc 也不是所有场景的银弹。比如 Vite 8 迁移文档里提到，Oxc transformer 当前还不支持 lowering 原生 decorators；如果项目依赖复杂 Babel 插件、宏、非常规语法转换，短期内仍然要留 Babel，或者通过 @rolldown/plugin-babel 这类方式补上。

Babel、SWC 和 Oxc 怎么选

维度 Babel SWC Oxc
速度 慢（纯 JS） 快（Rust，约 10-20 倍） 快（Rust，面向整套工具链协同）
生态/插件 极其丰富，几乎所有转换都有插件 较少，常见需求够用，冷门转换可能缺 还在快速发展，重点服务 Vite/Rolldown 等新链路
配置稳定性 非常成熟 成熟但偶有边界 case 新，迁移期要关注兼容差异
polyfill 策略 preset-env + core-js 最成熟 支持类似 usage，但复杂场景不如 Babel 稳 主要负责语法/JS transform，不是 polyfill 方案的核心
典型使用方 老项目、需要特殊 Babel 插件 Next.js 默认、追求速度的新项目 Vite 8、Rolldown 生态、新一代 Rust 工具链

我的实战建议：

  1. 新项目、追求速度：优先 SWC（或干脆用内置了快引擎的 Vite/Next.js，不用自己配）。
  2. 存量项目、依赖某个 Babel 专属插件（比如某些装饰器、宏、特定框架的转换）：留在 Babel，别硬迁。
  3. Vite 8 项目：默认跟着 Oxc/Rolldown 走，旧的 esbuild 配置能兼容一段时间，但新配置应该往 oxc 迁。
  4. 大多数前端应用：其实你不需要直接配 Babel/SWC/Oxc——Vite 8 用 Oxc，Next.js 用 SWC，框架已经把转译这层封好了。只有做库、做特殊转换、维护老配置时才需要直接面对它们。

如果你是在写 npm 库，还要和应用区分开：应用可以按目标浏览器注入全局 polyfill，因为运行环境由你控制；库则要谨慎污染全局环境，通常不要在库里直接注入 core-js 全局 polyfill。更常见的做法是只做语法转译，把 API 兼容交给使用方，或者用 @babel/plugin-transform-runtime / core-js-pure 这类不污染全局的方案。

关键认知：Babel/SWC/Oxc 是「转译层」，它和打包器（Rollup/Webpack/Rolldown）是配合关系，不是竞争关系。你可能在 Webpack 里用 babel-loader 或 swc-loader，在 Rollup 里用 @rollup/plugin-babel，在 Vite 8 里默认走 Oxc——它们都是被构建链路调用的转译引擎。

一个能看到效果的最小示例

mkdir babel-demo && cd babel-demo
npm init -y
npm i -D @babel/core @babel/cli @babel/preset-env
npm i core-js

// package.json 里加
{ "browserslist": ["ie 11"] }

// babel.config.js
module.exports = {
  // corejs 要带上 minor 版本（与上文一致），否则新 API 的 polyfill 可能对不上
  presets: [['@babel/preset-env', { useBuiltIns: 'usage', corejs: '3.37' }]],
}

// src/index.js
const arr = [1, 2, 3]
console.log(arr.includes(2))
const fn = () => 'hi'

npx babel src/index.js

因为 browserslist 写了 ie 11，你会看到输出里：箭头函数被转成了普通函数（语法降级），并且自动 require('core-js/...') 注入了 includes 的 polyfill（API 补丁）。把 browserslist 改成 last 1 chrome version 再跑一次，会发现几乎不转——这就是 preset-env + browserslist 联动的直接体感。

小结

  1. 转译的本质是「源码 → AST → 转换 → 源码」，AST 让转换能感知代码结构而非盲目字符串替换。
  2. Babel 靠插件干活，preset 是插件集合，@babel/preset-env 根据 browserslist 自动决定转译程度。
  3. browserslist 是整个工程的兼容性单一事实源，被 Babel、Autoprefixer 等多个工具共享。
  4. 语法降级和 API polyfill 是两回事：前者改写法，后者靠 core-js 补缺失的运行时方法。
  5. useBuiltIns: 'usage' + 指定 corejs 版本是最省的 polyfill 策略，按实际使用注入。
  6. SWC 是 Babel 的 Rust 快速替代，概念相通；Oxc 则是 Vite 8/Rolldown 这类新工具链背后的 Rust 编译基础设施。
  7. 新项目追速度优先跟框架默认走；依赖专属插件或 polyfill 准确性的老项目留 Babel；Vite 8 项目关注 esbuild 配置向 oxc 的迁移。
