Commitlint、Husky 与 lint-staged 提交约束

发表于2026|更新于2026|工程化
|字数总计:1.4k|阅读时长:5分钟

前言：如果团队规范只写在文档里，最后一定会变成“新人不知道，老人懒得管”。提交约束的价值就是把规范放到 Git 流程里，让问题在进入仓库前就被拦住。

为什么需要提交前检查

一个真实项目里，代码进入仓库前至少应该回答三个问题：

  1. 格式是否统一；
  2. 基础 lint 是否通过；
  3. 提交信息是否能被人和工具读懂。

如果这些都靠 Code Review 处理，Review 很快就会变味。

原本 Review 应该关注：

  • 业务逻辑是否正确；
  • 模块设计是否合理；
  • 复杂变更是否有测试；
  • 是否引入长期维护风险。

结果最后变成：

  • 这里少了空格；
  • commit message 不规范；
  • 这个文件没格式化；
  • 这个变量没用。

我的建议是：低级、重复、确定的问题交给工具，Review 留给真正需要人判断的问题。

三个工具分别负责什么

提交约束里最常见的是这三个工具：

工具 作用 触发时机
Husky 管理 Git Hooks pre-commit、commit-msg 等
lint-staged 只处理暂存区文件 通常在 pre-commit
Commitlint 检查提交信息 通常在 commit-msg

它们不是替代关系，而是配合关系。

git commit
  │
  ├── pre-commit
  │     └── lint-staged 检查暂存文件
  │
  └── commit-msg
        └── commitlint 检查提交信息

接入 Husky

安装：

pnpm add -D husky

初始化：

pnpm exec husky init

初始化后通常会生成 .husky/pre-commit，可以写入：

pnpm lint-staged

同时在 package.json 里保留：

{
  "scripts": {
    "prepare": "husky"
  }
}

prepare 的作用是团队成员安装依赖后自动初始化 Husky。否则有些人本地不会启用 hooks，规范就会漏。

接入 lint-staged

安装：

pnpm add -D lint-staged

在 package.json 中配置：

{
  "lint-staged": {
    "*.{js,jsx,ts,tsx}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{css,scss,vue}": [
      "stylelint --fix",
      "prettier --write"
    ],
    "*.{json,md,yml,yaml}": [
      "prettier --write"
    ]
  }
}

这里的重点是：lint-staged 只处理暂存区文件。

比如你只 git add src/user.ts，那么它不会扫描整个项目。这对大型项目很重要，否则每次提交都跑全量 lint，开发体验会很差。

但也要注意一个坑：lint-staged 只能保证这次提交的文件没问题，不能替代 CI 的全量检查。

我的建议是：

阶段 检查范围
pre-commit 暂存文件，反馈要快
CI 全量项目，保证主干质量

接入 Commitlint

安装：

pnpm add -D @commitlint/cli @commitlint/config-conventional

创建 commitlint.config.mjs：

export default {
  extends: ['@commitlint/config-conventional'],
}

新增 .husky/commit-msg：

pnpm exec commitlint --edit "$1"

然后提交信息需要符合 Conventional Commits：

feat: add user profile page
fix: handle token expired error
docs: update engineering guide
refactor: simplify request client

如果写成：

update code

Commitlint 会拦截，因为这个提交信息对人和工具都没什么价值。

Conventional Commits 不只是格式好看

Conventional Commits 的基本结构是：

<type>(optional scope): <description>

常见 type：

type 含义
feat 新功能
fix 修复 bug
docs 文档
style 不影响逻辑的格式调整
refactor 重构
test 测试
chore 工程杂项
ci CI 配置
build 构建系统或依赖

它的价值不只是“看起来规范”，而是后续可以接上自动化：

  • 自动生成 changelog；
  • 自动判断版本升级类型；
  • 自动筛选发布内容；
  • 更容易追踪某类变更。

但我也不建议把它神化。提交信息不能替代 Changesets 这类显式发布说明，尤其是 monorepo 里，一个 commit 可能影响多个包，单靠 commit message 推断版本很容易不准。

更稳的方式是：

Conventional Commits
  └── 保证提交历史可读

Changesets
  └── 显式声明哪些包要怎么发版

不要在 pre-commit 里做太重的事情

一个常见错误是把所有检查都放进 pre-commit：

pnpm lint
pnpm typecheck
pnpm test
pnpm build

看起来很严格，实际很容易适得其反。

如果每次提交都要等几分钟，团队最后会开始频繁使用：

git commit --no-verify

这就说明工具链设计失败了。

我的建议是：

Hook 适合放什么
pre-commit lint-staged、快速格式化、轻量 lint
commit-msg commitlint
CI typecheck、test、build、全量 lint

本地 hook 要快，CI 要完整。二者不是一个职责。

一份可落地的配置组合

package.json：

{
  "scripts": {
    "prepare": "husky",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "lint:style": "stylelint \"src/**/*.{css,scss,vue}\"",
    "format": "prettier . --write",
    "check": "pnpm lint && pnpm lint:style && pnpm format:check",
    "format:check": "prettier . --check"
  },
  "lint-staged": {
    "*.{js,jsx,ts,tsx}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{css,scss,vue}": [
      "stylelint --fix",
      "prettier --write"
    ],
    "*.{json,md,yml,yaml}": [
      "prettier --write"
    ]
  }
}

.husky/pre-commit：

pnpm lint-staged

.husky/commit-msg：

pnpm exec commitlint --edit "$1"

commitlint.config.mjs：

export default {
  extends: ['@commitlint/config-conventional'],
}

这套配置不复杂，但已经能覆盖大多数团队项目的提交入口治理。

小结

  1. Husky 负责管理 Git Hooks，lint-staged 负责处理暂存文件，Commitlint 负责检查提交信息。
  2. pre-commit 要快，不适合放全量构建和完整测试。
  3. CI 才是最终质量闸口，本地 hook 只是提前反馈。
  4. Conventional Commits 让提交历史更可读，也方便后续自动化。
  5. 提交约束的目标不是为难开发者，而是减少低级问题进入仓库。
