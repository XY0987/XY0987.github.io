Vue 3 renderer 源码解析：render 和 patch 如何驱动挂载更新

发表于2026|更新于2026|Vue框架及周边库
|字数总计:3.6k|阅读时长:14分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：上一篇看了 createApp(App).mount('#app') 如何创建根 VNode 并调用 render(vnode, container)。这一篇继续往下看 renderer.ts：render 如何进入 patch，patch 又如何根据 VNode 类型分发到元素、组件、Fragment、Teleport、Suspense 等不同处理流程。

先给结论

Vue 运行时渲染主线可以简化成：

render(vnode, container)
  │
  ▼
patch(oldVNode, newVNode, container)
  │
  ├─ Text / Comment / Static
  ├─ Fragment
  ├─ Element
  │    ├─ mountElement
  │    └─ patchElement
  ├─ Component
  │    ├─ mountComponent
  │    └─ updateComponent
  ├─ Teleport
  └─ Suspense

render 是根入口，patch 是核心分发器。真正的 DOM 创建、组件挂载、组件更新，都是从 patch 分发出去的。

renderer 为什么能跨平台

runtime-core 的 renderer 不直接操作 DOM。它先从外部传入的 options 中拿到一组宿主环境操作：

  // renderer 不直接操作 DOM，而是把平台操作从 options 中解构成 hostXXX。
  // 对 runtime-dom 来说这些就是 DOM API；对自定义渲染器来说可以是任意宿主环境操作。
  const {
    insert: hostInsert,
    remove: hostRemove,
    patchProp: hostPatchProp,
    createElement: hostCreateElement,
    createText: hostCreateText,
    createComment: hostCreateComment,
    setText: hostSetText,
    setElementText: hostSetElementText,
    parentNode: hostParentNode,
    nextSibling: hostNextSibling,
    setScopeId: hostSetScopeId = NOOP,
    insertStaticContent: hostInsertStaticContent,
  } = options

这就是 Vue 渲染器可跨平台的关键。

对浏览器来说，hostCreateElement 最终是 document.createElement 一类 DOM API。对自定义渲染器来说，它可以是创建 Canvas 节点、小程序节点，或者其他宿主对象。

所以 runtime-core 只关心“创建节点、插入节点、更新属性”这些抽象动作，不关心具体平台是什么。

render：根渲染入口

render 是 app.mount 最终调用的入口。

  let isFlushing = false
  const render: RootRenderFunction = (vnode, container, namespace) => {
    if (vnode == null) {
      // render(null, container) 表示卸载整棵树。
      if (container._vnode) {
        unmount(container._vnode, null, null, true)
      }
    } else {
      // render(vnode, container) 表示挂载或更新：旧树保存在 container._vnode 上。
      patch(
        container._vnode || null,
        vnode,
        container,
        null,
        null,
        null,
        namespace,
      )
    }
    // 保存本次渲染的根 VNode，下一次 render 时作为旧树参与 patch。
    container._vnode = vnode
    if (!isFlushing) {
      isFlushing = true
      flushPreFlushCbs()
      flushPostFlushCbs()
      isFlushing = false
    }
  }

这里有三个重点。

第一，render(null, container) 表示卸载。

第二，render(vnode, container) 表示挂载或更新。到底是挂载还是更新，取决于 container._vnode 是否存在。

第三，渲染完成后会把当前 vnode 保存到 container._vnode，下一次 render 时就能拿它作为旧树参与 patch。

可以理解成：

第一次 render:
  container._vnode = undefined
  patch(null, vnode, container)  // mount

第二次 render:
  container._vnode = oldVNode
  patch(oldVNode, newVNode, container) // update

卸载:
  render(null, container)
  unmount(container._vnode)

patch：核心分发器

patch 是 renderer 最核心的函数。

  // Note: functions inside this closure should use `const xxx = () => {}`
  // style in order to prevent being inlined by minifiers.
  // patch 是渲染器的核心分发函数：n1 为旧 VNode，n2 为新 VNode。
  // n1 为 null 表示首次挂载；n1/n2 同类型表示更新；不同类型则先卸载旧节点再挂载新节点。
  const patch: PatchFn = (
    n1,
    n2,
    container,
    anchor = null,
    parentComponent = null,
    parentSuspense = null,
    namespace = undefined,
    slotScopeIds = null,
    optimized = __DEV__ && isHmrUpdating ? false : !!n2.dynamicChildren,
  ) => {
    if (n1 === n2) {
      return
    }

    // 新旧 VNode 类型不同，无法复用旧节点：先找到旧节点之后的锚点，再卸载旧树，后续按首次挂载处理。
    if (n1 && !isSameVNodeType(n1, n2)) {
      anchor = getNextHostNode(n1)
      unmount(n1, parentComponent, parentSuspense, true)
      n1 = null
    }

    // BAIL 表示退出优化路径，后续走完整 diff。
    if (n2.patchFlag === PatchFlags.BAIL) {
      optimized = false
      n2.dynamicChildren = null
    }

它先做三个基础判断：

  1. 新旧 VNode 完全相同，直接返回。
  2. 新旧 VNode 类型不同，旧节点不能复用，先卸载旧树。
  3. 如果新节点要求退出优化路径，就走完整 diff。

这里的 n1 和 n2 很重要：

参数 含义
n1 旧 VNode，首次挂载时为 null
n2 新 VNode
container 宿主容器
anchor 插入锚点
optimized 是否走编译优化路径

patch 如何按 VNode 类型分发

接下来，patch 会根据 VNode 的 type 和 shapeFlag 分发。

这里先区分一下：

字段 作用 例子
type VNode 的原始类型 'div'、组件对象、Text、Fragment
shapeFlag 根据 type 和 children 预先算好的分类标记 ELEMENT、COMPONENT、TEXT_CHILDREN、ARRAY_CHILDREN

为什么有了 type 还要 shapeFlag？因为 type 只能告诉我们“原始类型是什么”，但 renderer 需要频繁判断“它是不是元素、是不是组件、children 是文本还是数组”。如果每次都重新用 isString(type)、isObject(type)、isFunction(type) 判断，会比较分散。

所以 Vue 在创建 VNode 时先把这些结果压成 shapeFlag，后面 patch 阶段就可以用位运算快速判断：

shapeFlag & ShapeFlags.ELEMENT
shapeFlag & ShapeFlags.COMPONENT
shapeFlag & ShapeFlags.TEXT_CHILDREN

简单说：type 是原始信息，shapeFlag 是运行时为了快速分发提前做好的标签。

    const { type, ref, shapeFlag } = n2
    switch (type) {
      case Text:
        processText(n1, n2, container, anchor)
        break
      case Comment:
        processCommentNode(n1, n2, container, anchor)
        break
      case Static:
        if (n1 == null) {
          mountStaticNode(n2, container, anchor, namespace)
        } else if (__DEV__) {
          patchStaticNode(n1, n2, container, namespace)
        }
        break
      case Fragment:
        // Fragment 没有真实包裹元素，需要用起止锚点管理一组子节点。
        processFragment(
          n1,
          n2,
          container,
          anchor,
          parentComponent,
          parentSuspense,
          namespace,
          slotScopeIds,
          optimized,
        )
        break
      default:
        if (shapeFlag & ShapeFlags.ELEMENT) {
          // 普通元素走 processElement：内部会根据 n1 是否为空决定 mountElement 或 patchElement。
          processElement(
            n1,
            n2,
            container,
            anchor,
            parentComponent,
            parentSuspense,
            namespace,
            slotScopeIds,
            optimized,
          )
        } else if (shapeFlag & ShapeFlags.COMPONENT) {
          // 组件走 processComponent：内部会根据 n1 是否为空决定 mountComponent 或 updateComponent。
          processComponent(
            n1,
            n2,
            container,
            anchor,
            parentComponent,
            parentSuspense,
            namespace,
            slotScopeIds,
            optimized,
          )
        } else if (shapeFlag & ShapeFlags.TELEPORT) {
          // Teleport/Suspense 自带 process 实现，但仍复用当前 renderer internals。

可以看到，patch 本身不做所有细节，而是根据 VNode 类型转交给不同处理函数。

这也是 renderer 代码庞大但结构清晰的原因：patch 是总入口，各类节点各自处理自己的挂载和更新。

最后，patch 会统一处理 ref：

    // ref 在 VNode 本体 patch 完成后统一处理，确保 ref 指向最新 DOM 或组件实例。
    if (ref != null && parentComponent) {
      setRef(ref, n1 && n1.ref, parentSuspense, n2 || n1, !n2)
    } else if (ref == null && n1 && n1.ref != null) {
      setRef(n1.ref, null, parentSuspense, n1, true)
    }

普通元素会先进入 processElement：

n1 == null 表示首次挂载，于是进入 mountElement。

mountElement 的核心流程是：

    const { props, shapeFlag, transition, dirs } = vnode

    // 1. 创建宿主元素。对 runtime-dom 来说，这里就是 document.createElement。
    el = vnode.el = hostCreateElement(
      vnode.type as string,
      namespace,
      props && props.is,
      props,
    )

    // 2. 先挂载子节点，再处理 props。某些 DOM 属性依赖子内容已经存在，例如 <select value>。
    if (shapeFlag & ShapeFlags.TEXT_CHILDREN) {
      hostSetElementText(el, vnode.children as string)
    } else if (shapeFlag & ShapeFlags.ARRAY_CHILDREN) {
      mountChildren(
        vnode.children as VNodeArrayChildren,
        el,
        null,
        parentComponent,
        parentSuspense,
        resolveChildrenNamespace(vnode, namespace),
        slotScopeIds,
        optimized,
      )
    }

    if (dirs) {
      invokeDirectiveHook(vnode, null, parentComponent, 'created')
    }
    // 3. 设置 scoped CSS id。
    setScopeId(el, vnode, vnode.scopeId, slotScopeIds, parentComponent)
    // 4. 挂载 props，具体如何设置 class/style/event/attribute 由 hostPatchProp 决定。
    if (props) {
      for (const key in props) {
        if (key !== 'value' && !isReservedProp(key)) {
          hostPatchProp(el, key, null, props[key], namespace, parentComponent)
        }
      }

后面会把元素插入容器：

    // 5. 把创建好的元素插入容器。到这里，真实 DOM 才进入页面结构。
    hostInsert(el, container, anchor)
    if (
      (vnodeHook = props && props.onVnodeMounted) ||
      needCallTransitionHooks ||
      dirs
    ) {
      queuePostRenderEffect(() => {
        vnodeHook && invokeVNodeHook(vnodeHook, parentComponent, vnode)
        needCallTransitionHooks && transition!.enter(el)
        dirs && invokeDirectiveHook(vnode, null, parentComponent, 'mounted')
      }, parentSuspense)

所以元素首次挂载的流程可以概括为：

createElement
  │
  ├─ mount children
  ├─ directive created
  ├─ set scope id
  ├─ patch props
  ├─ transition beforeEnter
  ├─ insert into container
  └─ queue mounted hooks

子节点挂载：递归 patch

数组子节点会走 mountChildren：

  const mountChildren: MountChildrenFn = (
    children,
    container,
    anchor,
    parentComponent,
    parentSuspense,
    namespace: ElementNamespace,
    slotScopeIds,
    optimized,
    start = 0,
  ) => {
    for (let i = start; i < children.length; i++) {
      // 子节点可能是字符串、数字、数组等，这里统一规范化成 VNode，再递归交给 patch 挂载。
      const child = (children[i] = optimized
        ? cloneIfMounted(children[i] as VNode)
        : normalizeVNode(children[i]))
      patch(

这里很关键：挂载子节点不是单独写一套逻辑，而是把每个子节点规范化成 VNode，再递归调用 patch(null, child, container)。

这说明 patch 是整个渲染树递归展开的统一入口。

元素更新：patchElement

元素更新时会进入 patchElement：

  const patchElement = (
    n1: VNode,
    n2: VNode,
    parentComponent: ComponentInternalInstance | null,
    parentSuspense: SuspenseBoundary | null,
    namespace: ElementNamespace,
    slotScopeIds: string[] | null,
    optimized: boolean,
  ) => {
    // 更新元素时复用旧 VNode 对应的真实元素，只在它上面打补丁。
    const el = (n2.el = n1.el!)
    if (__DEV__ || __FEATURE_PROD_DEVTOOLS__) {
      el.__vnode = n2
    }
    // patchFlag 由编译器生成，标记哪些部分是动态的，用于跳过不必要的全量 diff。
    let { patchFlag, dynamicChildren, dirs } = n2

这里的核心是复用真实 DOM：

const el = (n2.el = n1.el!)

也就是说，新 VNode 不创建新 DOM，而是继承旧 VNode 的 el，然后只更新变化的部分。

如果有动态子节点，会走 block tree 优化路径：

    if (dynamicChildren) {
      // block tree 优化路径：只 patch 编译器收集到的动态子节点。

        n1.dynamicChildren!,
        dynamicChildren,
        el,
        parentComponent,
        parentSuspense,
        resolveChildrenNamespace(n2, namespace),
        slotScopeIds,
      )
      if (__DEV__) {
        // necessary for HMR
        traverseStaticChildren(n1, n2)
      }
    } else if (!optimized) {
      // 没有动态子节点优化时，回退到完整 children diff。
      patchChildren(

如果有 patchFlag，说明编译器已经告诉运行时哪些部分是动态的：

      // 有 patchFlag 说明这段 render 代码由编译器生成，可以根据动态标记走快速路径。
      // 这里假设新旧节点结构稳定，只更新被标记为动态的部分。

        // element props contain dynamic keys, full diff needed

这就是 Vue 3 编译优化和运行时配合的核心：编译器提前标记动态部分，运行时根据标记减少 diff 范围。

为什么响应式状态变化会更新组件

关键在这里：

    // 为组件渲染创建 ReactiveEffect：render 中读取的响应式状态会被收集，状态变化后触发组件更新。
    instance.scope.on()
    const effect = (instance.effect = new ReactiveEffect(componentUpdateFn))
    instance.scope.off()

    const update = (instance.update = effect.run.bind(effect))
    const job: SchedulerJob = (instance.job = effect.runIfDirty.bind(effect))
    job.i = instance
    job.id = instance.uid
    // 响应式状态变化时不直接同步更新组件，而是把 job 放入调度队列。
    effect.scheduler = () => queueJob(job)

组件 render 函数执行时，如果读取了响应式状态，会被响应式系统收集到当前 ReactiveEffect 中。

RendererInternals：给内置特性复用 renderer 能力

Teleport、Suspense、hydration 等特性需要复用 renderer 的内部能力，但又不能和主流程强耦合，所以 renderer 会构造一个 internals 对象：

  // 暴露给 Teleport/Suspense/Hydration 等特性的内部能力集合，避免这些特性和 renderer 主流程强耦合。
  const internals: RendererInternals = {
    p: patch,
    um: unmount,
    m: move,
    r: remove,
    mt: mountComponent,
    mc: mountChildren,
    pc: patchChildren,
    pbc: patchBlockChildren,
    n: getNextHostNode,
    o: options,
  }

这也是为什么 Teleport 和 Suspense 可以有自己的 process，但仍然复用当前 renderer 的 patch、move、unmount 等能力。

render、patch、createApp 的闭环

baseCreateRenderer 最后返回：

  return {
    render,
    hydrate,
    // createApp 由 renderer 注入 render/hydrate 后生成，app.mount 最终会回到这里的 render/hydrate。
    createApp: createAppAPI(render, hydrate),
  }

这就形成了完整闭环：

createRenderer(options)
  │
  ▼
生成 render / hydrate / createApp
  │
  ▼
createApp(App)

  │

  │
  ▼

小结

  1. renderer 通过 hostXXX 操作实现平台无关，DOM 能力由 runtime-dom 注入。
  2. render 是根入口，container._vnode 保存旧树，用于下一次 patch。
  3. patch 是核心分发器，根据 VNode 类型分发到元素、组件、Fragment、Teleport、Suspense 等处理逻辑。
  4. 元素挂载会创建宿主元素、挂载子节点、设置 props，最后插入容器。
  5. 元素更新会复用旧 DOM，并根据 patchFlag / dynamicChildren 走优化路径。
  6. 组件挂载会创建组件实例，执行 setupComponent，再通过渲染 effect 挂载子树。
  7. 组件响应式更新依赖 ReactiveEffect + scheduler + patch(prevTree, nextTree) 这条链路。
