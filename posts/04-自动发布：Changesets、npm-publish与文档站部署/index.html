自动发布：Changesets、npm publish 与文档站部署

发表于2026|更新于2026|工程化
|字数总计:2.4k|阅读时长:8分钟

前言：《npm 包发布全流程》那篇讲过 SemVer、dist-tag 和发版的手动流程。这一篇把发布这件事自动化并接进 CI——用 Changesets 管理版本和 changelog，让「发版」从「手动敲一串命令、容易出错」变成「合并 PR 就自动发」。同时讲文档站的自动部署，让工程化真正覆盖到「产出物上线」这一步。

手动发版的痛点

回想手动发布一个（尤其是 Monorepo 里的）包要做几件事：确定哪些包变了、每个包该升 major/minor/patch、更新版本号、写 changelog、npm publish、打 tag、推送。步骤多、顺序不能错，还特别容易出这些问题：

  • 忘了升版本号，发了个和上次一样的版本（npm 直接拒绝）
  • changelog 靠记忆手写，漏掉改动
  • Monorepo 里 A 依赖 B，B 升级了忘了同步 A 的依赖范围
  • 多人协作时，谁该在这次发版里、升什么级别，说不清

Changesets 就是来解决这套问题的。它的核心思想是：把「这次改动该怎么影响版本」这件事，在写代码的时候就记录下来，而不是等发版时凭记忆重建。

Changesets 的核心模型

Changesets 的工作流分两个动作，理解这两个就懂了它：

① 开发阶段：每个 PR 附带一个 changeset 文件
   「我改了 @my-ui/button，这是个 minor 变更，因为加了新 prop」
   → 一个个小的 markdown 意图文件，攒在 .changeset/ 目录

② 发版阶段：把攒着的 changeset 消费掉
   → 自动计算每个包该升到什么版本
   → 自动更新 package.json 版本号
   → 自动生成/追加 CHANGELOG.md
   → 自动处理 Monorepo 内部依赖联动

关键点：版本决策被拆散到每个改动发生的时刻。你改完代码顺手记一句「这是 minor，因为加了新功能」，发版时机器把这些意图汇总，算出最终版本。没有人需要在发版那一刻回忆「这三周都改了啥、该升几位」。

初始化：

pnpm add -D @changesets/cli
pnpm changeset init      # 生成 .changeset/config.json

开发阶段：加 changeset

改完代码，跑一条命令交互式地记录这次变更：

pnpm changeset

它会问你：这次改了哪些包？每个包是 major / minor / patch？变更说明是什么？回答完，生成一个像这样的文件：

---
"@my-ui/button": minor
"@my-ui/theme": patch
---

Button 新增 loading 属性；同步修正 theme 的一处 token 拼写

这个文件跟着 PR 一起提交、一起 review。好处是变更意图在 PR 里就是可见、可讨论的——reviewer 能质疑「这明明是 breaking change，为什么标 minor？」。

可以在 CI 里加一道检查：PR 如果动了源码却没带 changeset，就提醒（Changesets 官方有对应的 GitHub Action / bot）：

      # 检测 PR 是否缺少 changeset（用官方 changeset bot 或 action）
      - run: pnpm changeset status --since=origin/main

changeset status 会列出「相比主干，当前有哪些待发布的变更」，没有就非零退出。这能拦住「改了功能忘了记 changeset」。

发版阶段：version 与 publish

发版时两条命令：

# 1. 消费所有 changeset：升版本号 + 写 changelog + 删掉已消费的 changeset 文件
pnpm changeset version

# 2. 发布到 npm（构建产物要先准备好）
pnpm changeset publish

changeset version 做的事：读 .changeset/ 下所有变更文件，按 SemVer 规则算出每个包的新版本（同一个包有多条时，取最高级别），改 package.json，把变更说明追加进各包的 CHANGELOG.md，然后删掉这些已消费的 changeset。这一步产生的改动本身应该作为一个 commit / PR。

changeset publish 做的事：对比 npm 上已有版本，只发布版本号变了的包（Monorepo 里没变的包自动跳过），并打好 git tag。

一个细节：changeset publish 之前一定要先 build。发布的是 dist/ 里的产物，不是源码。顺序错了会把没构建的包发上去。

接进 CI：合并即发布

手动跑上面两条命令还是有心智负担。Changesets 官方的 changesets/action 把整个流程自动化成一个非常顺手的模式：

# .github/workflows/release.yml
name: Release

on:
  push:
    branches: [main]      # 主干有新提交就触发

concurrency: release      # 发布串行，避免并发发版打架

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write     # 允许推送 version 提交、打 tag
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm
          registry-url: https://registry.npmjs.org  # 配好 registry 才能发

      - run: pnpm install --frozen-lockfile
      - run: pnpm build       # 发布前必须构建

      - uses: changesets/action@v1
        with:
          # 有 changeset 时：开一个「Version Packages」PR
          # 没有 changeset 时：如果版本已更新，执行 publish
          publish: pnpm changeset publish
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}

这个 action 的巧妙之处在于它的两态行为，形成一个闭环：

主干上攒了几个带 changeset 的 PR
   │
   ▼
action 检测到有待发布变更
   │
   ▼
自动开/更新一个 "Version Packages" PR
   （里面是 changeset version 的结果：版本号 + changelog）
   │
   ▼
维护者 review 这个 PR，确认版本和 changelog 无误后合并
   │
   ▼
合并触发主干再次运行 action
   │
   ▼
这次没有待发布 changeset 了 → 执行 publish 发到 npm + 打 tag

好处：发版变成一次「点合并」的动作，而且版本号和 changelog 在合并前都能被人 review。既自动化，又保留了人工确认的关口——比「push 就直接发 npm」更可控。

预发布通道：把 dist-tag 接进流水线

稳定版本走 latest，但组件库和工具库经常还需要 next / beta / canary 这些预发布通道。它们解决的是同一个问题：让一部分用户先试新版本，但不影响默认安装的稳定版本。

npm install @my-ui/button          → 默认拿 latest
npm install @my-ui/button@next     → 拿下一代预览版
npm install @my-ui/button@beta     → 拿 beta 测试版
npm install @my-ui/button@canary   → 拿每次提交生成的金丝雀版本

自动化发布时，我更建议把发布通道和触发条件绑定清楚：

通道 常见触发 适用
latest 合并 Version Packages PR 后发布 稳定版本
next next 分支 / 下一大版本分支 下一代版本提前试用
beta 打 beta tag 或 release 分支 功能基本稳定，发布前验证
canary 主干每次合并或手动触发 高频内部验证，不承诺稳定

最关键的一点：预发布版本必须发到非 latest 的 tag。否则用户执行不带版本号的 npm install 时，会直接装到还没稳定的新版本。手动命令是：

npm publish --tag next

如果用 Changesets，可以用 pre mode 进入预发布状态，再发布到指定 tag：

pnpm changeset pre enter beta
pnpm changeset version
pnpm changeset publish --tag beta
pnpm changeset pre exit

这块不用一开始就做得很复杂。我的建议是：普通项目先只做 latest 自动发布；组件库 / SDK 这类被别人依赖的包，再补 next 或 beta 通道。canary 成本最高，因为版本很多、清理和沟通都要跟上，适合内部消费或成熟团队。

文档站的自动部署

组件库/工具库通常配套一个文档站（VitePress、Storybook——见《文档工程化》那篇）。文档站也该自动部署，不然文档永远滞后于代码。

以 VitePress 部署到 GitHub Pages 为例：

# .github/workflows/docs.yml
name: Deploy Docs

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }

      - run: pnpm install --frozen-lockfile
      - run: pnpm docs:build          # 产出静态站点到 docs/.vitepress/dist

      - uses: actions/upload-pages-artifact@v3
        with:
          path: docs/.vitepress/dist
      - uses: actions/deploy-pages@v4  # 部署到 GitHub Pages

思路对任何静态文档站都通用：构建出静态产物 → 上传 → 部署到托管平台（GitHub Pages / Vercel / 对象存储 + CDN，具体见下一阶段「部署与发布形态」）。把它接到主干 push 上，文档就永远跟代码同步。

一个协作上的实践：文档站也值得有 PR 预览。每个改文档的 PR 部署一个临时预览地址，reviewer 直接点开看渲染效果，而不是凭 Markdown diff 想象。PR Preview 这个话题下一阶段专门讲。

npm 发布的两个安全点

自动发布把 NPM_TOKEN 放进了 CI，有两个安全实践要提（详细的供应链安全在安全篇展开）：

  1. 用粒度最小的自动化 token：npm 支持创建「Automation」类型、限定包范围的 token，别用你账号的全权限 token。
  2. 开启发布来源校验 / provenance：npm 支持 --provenance，让包携带「由哪条 CI 构建发布」的可验证来源信息，用户能确认这个包确实来自你的官方流水线，而不是被人冒名发的。
      - run: pnpm changeset publish
        # 或直接 npm publish --provenance --access public

小结

  1. Changesets 的核心是「把版本决策拆到每个改动发生时记录」，发版时汇总计算，避免凭记忆重建版本和 changelog。
  2. 开发阶段 pnpm changeset 生成意图文件随 PR 提交，CI 用 changeset status 拦住「改了功能忘记记」。
  3. 发版阶段 changeset version 升版本+写 changelog，changeset publish 只发版本变了的包；publish 前必须先 build。
  4. changesets/action 的两态行为形成闭环：先开「Version Packages」PR 供 review，合并后再自动 publish，兼顾自动化与人工确认。
  5. 预发布通道用 dist-tag 管理：稳定版走 latest，预览版走 next / beta / canary，避免默认安装拿到未稳定版本。
  6. 文档站按「构建静态产物 → 上传 → 部署」接到主干 push，让文档永远跟代码同步。
  7. 自动发布用最小权限的 automation token，并开启 provenance 校验发布来源。
