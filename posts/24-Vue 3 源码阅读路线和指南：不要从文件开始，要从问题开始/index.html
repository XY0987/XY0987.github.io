Vue 3 源码阅读路线和指南：不要从文件开始，要从问题开始

发表于2026|更新于2026|Vue框架及周边库
|字数总计:3.3k|阅读时长:12分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：前面已经把响应式、运行时、编译器、diff、SSR 的主线过了一遍。这一篇不继续分析某个函数，而是整理一条更适合长期阅读的路线。我的建议是：不要从“我要读完 Vue 源码”开始，而要从“我要回答哪些问题”开始。

先给结论

读 Vue 3 源码可以分成五个阶段：

阶段 阅读目标 重点目录
0. 建立地图 知道各模块边界，不急着看细节 packages/*
1. 响应式系统 理解数据变化如何通知副作用 packages/reactivity
2. 运行时主线 理解组件如何挂载、更新、卸载 packages/runtime-core、packages/runtime-dom
3. 编译器主线 理解 template 如何变成 render packages/compiler-core、packages/compiler-dom
4. 高阶能力 理解 diff、内置组件、编译时优化、SSR、SFC runtime-core、compiler-core、server-renderer、compiler-sfc
5. 设计哲学 从实现里抽象出可迁移的框架设计原则 全局回看

最重要的一点是：阅读路线不应该按文件大小排序，而应该按心智模型排序。

准备工作：先跑起来，再读源码

源码阅读最忌讳只看静态代码。Vue 这种框架有大量运行时状态，只看文件很容易漏掉调用关系。

这个仓库的环境要求可以先看 package.json：

"engines": {
  "node": ">=18.12.0"
},

常用脚本也在这里：

我的建议是先准备三个东西：

  1. 一个最小用例，比如 reactive + effect、createApp + mount、template -> render。
  2. 一个源码入口，比如 reactive.ts、runtime-dom/src/index.ts、compiler-core/src/compile.ts。
  3. 一条调用链记录，不要一开始就试图看完整个文件。

源码阅读不是考古，最好让代码在断点里跑起来。

阶段一：先读响应式系统

推荐顺序：

01 reactive 创建 Proxy
02 get / set 连接 track 和 trigger
03 依赖收集与触发
04 effect 执行、调度与清理
05 ref 为什么需要 .value
06 computed 缓存、脏值、惰性求值
07 watch 监听调度与 cleanup

这一阶段要回答的问题是：

问题 对应源码
为什么 reactive(obj) === reactive(obj) reactive.ts 的 WeakMap 缓存
为什么读取属性会收集依赖 baseHandlers.ts 的 get
为什么修改属性会触发更新 baseHandlers.ts 的 set 和 dep.ts
为什么 effect 需要 cleanup effect.ts 的依赖清理
为什么 computed 默认不立刻执行 computed.ts 的脏值和缓存
为什么 watch 需要 cleanup apiWatch.ts / watch 的失效回调

不要把响应式只理解成 Proxy。Proxy 只是入口，真正值得看的，是依赖关系如何被表示、清理和重新建立。

effect 里有一个很重要的全局状态：

// 当前正在执行并允许收集依赖的订阅者。
// ReactiveEffect.run / refreshComputed 会在执行用户函数前设置它，track 会读取它来建立依赖关系。
export let activeSub: Subscriber | undefined

这说明 Vue 的依赖收集不是提前扫描出来的，而是在函数执行过程中动态建立的。这个模型非常关键。

阶段二：再读运行时主线

推荐顺序：

08 createApp 创建与挂载
09 render 与 patch 驱动挂载更新
10 组件实例创建与 setup
11 props 与 emits 规范化
12 模板变量和 this.xxx 如何访问状态
13 slots 插槽系统
14 scheduler 异步批量执行
15 keyed diff 五阶段最小移动
16 KeepAlive / Teleport / Suspense 内置组件

这一阶段要回答的问题是：

问题 对应源码
createApp(App).mount('#app') 到底做了什么 runtime-dom/src/index.ts、apiCreateApp.ts
为什么 Vue 可以跨平台渲染 createRenderer(options)
组件实例里保存了哪些状态 component.ts
props / emits 如何划分通信边界 componentProps.ts、componentEmits.ts
setup 返回值如何暴露给模板 componentPublicInstance.ts
slots 为什么是函数 componentSlots.ts、renderSlot.ts
状态变化为什么不是立刻同步更新 DOM scheduler.ts
列表更新为什么能尽量少移动 DOM renderer.ts 的 patchKeyedChildren
内置组件为什么要接入 renderer internals KeepAlive.ts、Teleport.ts、Suspense.ts

读运行时时不要一上来打开整个 renderer.ts 从头看到尾。这个文件很大，更适合按问题切片阅读。

阶段三：进入编译器主线

推荐顺序：

17 template 变成 render 函数
18 模板字符串变成 AST
19 AST 生成 render 函数
20 指令 transform 转换
21 编译时优化
22 .vue 文件拆分、编译、组装

编译器不要一开始就纠结所有 AST 节点类型。先抓住三段式：

parse
  -> transform
  -> codegen

入口很直接：

const resolvedOptions = extend({}, options, {
  prefixIdentifiers,
})
// 1. parse：模板字符串先解析成 AST；如果传入的已经是 RootNode，则直接复用。
const ast = isString(source) ? baseParse(source, resolvedOptions) : source
// 2. 准备 transform 预设：节点转换 + 指令转换。
const [nodeTransforms, directiveTransforms] =
  getBaseTransformPreset(prefixIdentifiers)

if (!__BROWSER__ && options.isTS) {
  const { expressionPlugins } = options
  if (!expressionPlugins || !expressionPlugins.includes('typescript')) {
    options.expressionPlugins = [...(expressionPlugins || []), 'typescript']
  }
}

// 3. transform：遍历 AST，处理 v-if/v-for/v-bind 等语法，并为后续 codegen 准备 codegenNode。
transform(
  ast,
  extend({}, resolvedOptions, {
    nodeTransforms: [
      ...nodeTransforms,
      ...(options.nodeTransforms || []), // user transforms
    ],
    directiveTransforms: extend(
      {},
      directiveTransforms,
      options.directiveTransforms || {}, // user transforms
    ),
  }),
)

// 4. codegen：把转换后的 AST 生成 render 函数字符串。
return generate(ast, resolvedOptions)

编译器阅读有一个技巧：拿一个极小模板反推源码。

<div :id="id">{{ msg }}</div>

你可以按下面的顺序追：

  1. baseParse 生成什么 AST。
  2. transformElement 给元素节点补了什么 codegenNode。
  3. transformExpression 如何处理 _ctx.msg。
  4. generate 最终输出什么 render 字符串。
  5. render 执行后返回什么 VNode。

这样比直接读完整个 parser 更有效。

阶段四：补齐高阶能力

高阶能力不建议太早读，因为它们依赖前面的主线。

能力 建议阅读时机 先理解什么
scheduler 组件更新主线之后 render effect 是如何入队的
keyed diff patchChildren 之后 VNode 的 type 和 key 如何判断复用
内置组件 renderer 主线之后 KeepAlive / Teleport / Suspense 如何复用 renderer 能力
编译时优化 compiler-core 之后 PatchFlags / Block Tree 如何让运行时少做 diff
SSR createApp / renderer 之后 服务端和客户端如何共享 VNode 语义
hydration SSR 之后 客户端为什么要认领 DOM 而不是重建 DOM
SFC 编译 compiler-core 之后 script / template / style 如何分别编译再组装

比如 scheduler 里，核心不是“用了 Promise”，而是它保证了去重、排序、父子组件更新顺序和后置任务时机：

export function queueJob(job: SchedulerJob): void {
  // 同一个 job 在同一轮 flush 中只允许入队一次。
  if (!(job.flags! & SchedulerJobFlags.QUEUED)) {
    const jobId = getId(job)
    const lastJob = queue[queue.length - 1]
    if (
      !lastJob ||
      // fast path when the job id is larger than the tail
      (!(job.flags! & SchedulerJobFlags.PRE) && jobId >= getId(lastJob))
    ) {
      queue.push(job)
    } else {
      queue.splice(findInsertionIndex(jobId), 0, job)
    }

    job.flags! |= SchedulerJobFlags.QUEUED

    queueFlush()
  }
}

function queueFlush() {
  if (!currentFlushPromise) {
    // 通过 Promise 微任务异步 flush，实现同一轮同步状态变更的批量更新。
    currentFlushPromise = resolvedPromise.then(flushJobs)
  }
}

阅读源码时的三个动作

1. 用问题牵引

不要问“这个文件写了什么”，而要问：

  • reactive 为什么要缓存代理对象？
  • computed 为什么要懒执行？
  • watch 为什么需要 cleanup？
  • runtime-core 为什么不直接依赖 DOM？
  • keyed diff 为什么先从头尾同步？
  • hydration mismatch 为什么要修正而不是直接报错退出？

问题越具体，调用链越清晰。

2. 用最小例子验证

每次只验证一个机制。

import { reactive, effect } from '@vue/reactivity'

const state = reactive({ count: 0 })

effect(() => {
  console.log(state.count)
})

state.count++

这个例子只适合看响应式，不要同时拿它去研究组件更新。研究组件更新时换成 createApp；研究编译器时换成 baseCompile。

3. 用数据结构做笔记

Vue 源码里很多逻辑，本质是在维护数据结构。

数据结构 作用
WeakMap 缓存原始对象到代理对象，避免重复代理
Dep 表示一个响应式属性对应的依赖集合
ReactiveEffect 表示一个可重新执行的副作用
VNode 表示 UI 的平台无关描述
ComponentInternalInstance 表示组件运行时实例
queue 表示等待异步执行的更新任务
AST 表示模板的结构化描述

如果你能画出这些结构之间的关系，比记住函数名更有价值。

常见误区

误区一：从最大文件开始读

renderer.ts 很重要，但不适合作为第一站。它同时包含挂载、更新、卸载、组件、元素、Teleport、Suspense、diff 等逻辑，第一次读很容易迷路。

更好的方式是先读入口，再沿着一条链路深入。

误区二：只看正常路径

源码里大量判断不是多余代码，而是在处理边界：

  • 参数非法怎么办？
  • 组件卸载中又触发更新怎么办？
  • 父组件更新时子组件已经卸载怎么办？
  • hydration 时服务端 DOM 和客户端 VNode 不一致怎么办？
  • 用户在 watch 回调里再次修改状态怎么办？

框架源码的价值，很多时候就在这些边界条件里。

误区三：把源码当标准答案背

源码会随着版本变化。比如内部依赖结构、优化策略、flag 设计都可能调整。

更稳定的是这些问题背后的约束：

  1. 怎么让用户写法简单？
  2. 怎么让运行时更新可预测？
  3. 怎么把平台差异隔离出去？
  4. 怎么在正确性和性能之间做取舍？
  5. 怎么给高级场景留下扩展口？

这些约束才是读源码真正应该沉淀下来的东西。

读完一段源码后如何判断自己真的懂了

可以用下面几个问题自测：

  1. 能不能用一句话说清这个模块解决什么问题？
  2. 能不能画出输入和输出？
  3. 能不能说出它依赖哪些模块，又不应该依赖哪些模块？
  4. 能不能举出至少一个边界场景？
  5. 能不能说出这里的设计如果放到自己的框架里有什么启发？

如果只能复述代码流程，还不算真正读懂。能解释设计约束，才说明这段源码变成了自己的知识。

小结

  1. Vue 源码阅读应该按问题推进，不应该按文件顺序硬啃。
  2. 第一阶段读响应式，第二阶段读运行时，第三阶段读编译器，最后再读 SSR 和高阶能力。
  3. 每次阅读都应该配一个最小例子，避免只看静态代码。
  4. 记录数据结构和模块边界，比记录函数名更重要。
  5. 真正有价值的不是“记住 Vue 怎么写”，而是理解它为什么这样设计。
