资源优化：图片、字体子集化与现代格式

发表于2026|更新于2026|工程化
|字数总计:2.2k|阅读时长:7分钟

前言：上一篇用性能门禁守住了「别越来越胖」。这一篇讲怎么主动「减肥」——资源优化。对绝大多数网站来说，图片和字体是体积的绝对大头，往往占了页面总下载量的一大半。JS 优化大家谈得多，但一张没压缩的 banner 图可能就抵得上你辛苦 tree-shaking 省下的所有 JS。这一篇讲图片和字体的工程化优化：压缩、现代格式、字体子集化，以及怎么把它们自动化进构建。

先搞清楚「大头在哪」

优化前先量。打开 DevTools 的 Network 面板，按资源类型排序，你大概率会看到：图片 > 字体 ≈ JS > CSS。很多团队花大力气优化 JS，却对一堆几 MB 的图片视而不见——这是典型的「在错误的地方使劲」。

整个排查顺序：先啃图片（体积大、优化立竿见影），再处理字体（中文字体尤其肥），最后才是 JS 的精细优化。按投入产出比排序，别一上来就钻进 JS 分包的细节。

图片优化：压缩 + 现代格式 + 响应式

图片优化有三个层次，效果叠加：

1. 压缩（无脑该做的）

未经压缩的 PNG/JPG 通常有大量冗余。用工具压一遍，肉眼几乎无损但体积能砍掉一半甚至更多。常用工具：

工具 定位
sharp Node 里的高性能图片处理库，构建时批处理首选
imagemin 老牌图片压缩，插件生态丰富
Squoosh Google 的在线/CLI 压缩工具，可视化调参

构建时用 sharp 批量压缩的示例：

import sharp from 'sharp'

// 把一张图压缩并转成多种格式
await sharp('src/hero.png')
  .resize(1200)                       // 限制最大宽度，别用原图 4000px
  .toFormat('webp', { quality: 80 })  // 转 WebP，质量 80 通常肉眼无损
  .toFile('dist/hero.webp')

2. 现代格式：WebP / AVIF

比压缩更狠的是换格式。相比传统 JPG/PNG：

  • WebP：比 JPG 小约 25-35%，兼容性极好（现代浏览器全支持）。默认首选。
  • AVIF：比 WebP 还小（同质量再省 20% 左右），但编码慢、兼容性稍差（较老的浏览器不支持）。

用 <picture> 做优雅降级——浏览器支持新格式就用新的，不支持自动回退：

<picture>
  <source srcset="/hero.avif" type="image/avif" />
  <source srcset="/hero.webp" type="image/webp" />
  <img src="/hero.jpg" alt="首图" width="1200" height="600" />
</picture>

浏览器从上往下挑第一个它支持的 source，都不支持就用兜底的 <img>。**注意 <img> 上写死了 width/height**——这是为了防 CLS（布局偏移，见性能指标篇），给图片预留好尺寸，加载完不会把布局撑得跳一下。

3. 懒加载与响应式

  • 懒加载：视口外的图片先不加载，<img loading="lazy"> 一个属性搞定，浏览器原生支持。
  • 响应式：手机不该下载给桌面准备的大图。用 srcset 让浏览器按屏幕挑合适尺寸：
<img
  srcset="/hero-400.webp 400w, /hero-800.webp 800w, /hero-1200.webp 1200w"
  sizes="(max-width: 600px) 400px, 800px"
  src="/hero-800.webp"
  loading="lazy"
  width="800" height="400"
/>

字体优化：中文字体的重灾区

英文字体几十 KB，无伤大雅。但中文字体动辄好几 MB——一个完整的中文字库有几万个字。直接引一个 3MB 的中文字体，能把首屏体验彻底拖垮。字体优化有几招：

1. 字体子集化（Subsetting）——中文优化的核心

你的页面根本用不到几万个汉字。字体子集化就是从完整字库里只抽出你实际用到的字，生成一个极小的子集字体。一个只含常用几千字或页面实际用字的子集，可能从 3MB 降到几十 KB。

工具：fonttools（Python，pyftsubset 命令）、subset-font（Node）等。

# 用 fonttools 抽取子集：只保留 text.txt 里出现的字符
pyftsubset full-font.ttf \
  --text-file=used-chars.txt \
  --flavor=woff2 \
  --output-file=subset.woff2

难点在于「怎么知道用了哪些字」。对内容固定的页面（官网、文档），可以扫描文本收集用字。对内容动态的应用，子集化就没那么好做——这时更适合用系统字体或按需分包字体。中文字体优化的关键认知：能子集化就子集化，这是数量级的收益。

2. woff2 格式

字体也有现代格式。woff2 是目前压缩率最好的字体格式，兼容性也好。有 ttf/otf 就转成 woff2，白省一截体积。

3. font-display 防止文字闪烁/隐身

字体加载有个体验坑：字体还没下载完，文字怎么显示？两种糟糕情况——FOIT（文字先隐身，字体到了才出现，一片空白）和 FOUT（先用后备字体显示，字体到了闪一下换掉）。用 font-display 控制：

@font-face {
  font-family: 'MyFont';
  src: url('/subset.woff2') format('woff2');
  font-display: swap;   /* 先用后备字体显示文字，字体到了再换，避免空白 */
}

swap 让文字先用系统后备字体显示出来（用户马上能读），自定义字体到了再替换。对内容型页面，「先能读」比「等到完美字体」重要。代价是会有一次字体切换的重排，可能贡献一点 CLS——用尺寸接近的后备字体能缓解。

把资源优化自动化进构建

手动优化每张图、每个字体不现实，也守不住——总有人会忘。要把它固化进构建流程，成为默认行为：

图片：用构建插件在打包时自动压缩/转格式。Vite 生态有 vite-plugin-image-optimizer（基于 sharp/svgo）等：

// vite.config.ts
import { ViteImageOptimizer } from 'vite-plugin-image-optimizer'

export default defineConfig({
  plugins: [
    ViteImageOptimizer({
      png: { quality: 80 },
      jpeg: { quality: 80 },
      webp: { quality: 80 },
    }),
  ],
})

这样开发者只管把图片放进项目，构建时自动压缩，不依赖任何人「记得手动压一下」。

字体：子集化通常作为一个独立的构建脚本，处理设计资产时跑一次生成子集，产物入库。动态内容的字体子集化可以做成服务端按需生成。

核心思路：优化要成为「系统默认」，而不是「个人自觉」。这和整个工程化的哲学一致——靠自觉的东西迟早会破防，能自动化的就自动化。上一篇的性能预算门禁是「守住底线」，这一篇的自动优化是「主动降低」，两者配合：自动优化把体积压下去，门禁防止它反弹。

一个真实的坑：优化了源图，没优化「按需生成」的图

现象：构建产物里的图都压得好好的，但用户上传的头像、CMS 里的运营图还是又大又慢。

原因：构建时的图片优化只覆盖了代码库里的静态图。用户上传、后台配置的动态图片走的是另一条路，构建插件管不着。

解决：动态图片要在服务端/CDN 层做实时优化——很多 CDN 和图床支持「URL 带参数实时裁剪/压缩/转格式」（如 ?w=800&format=webp），或者用专门的图片处理服务在上传时/访问时处理。别以为构建时优化了就万事大吉，动态图片是另一个战场，而且往往是线上真正的大头。

小结

  1. 优化前先量，大头通常是图片 > 字体 ≈ JS，按投入产出比排序，别死磕 JS 而放着几 MB 的图不管。
  2. 图片三层优化：压缩（sharp/imagemin/squoosh）、现代格式（WebP 默认、AVIF 更小但兼容性稍差，用 <picture> 降级）、懒加载 + 响应式 srcset。
  3. 图片一定写死 width/height 预留尺寸，防止 CLS 布局偏移。
  4. 中文字体是重灾区，核心手段是子集化（只抽实际用字，可从 MB 降到几十 KB）+ woff2 格式 + font-display: swap。
  5. 把图片压缩用构建插件自动化，让优化成为系统默认而非个人自觉。
  6. 自动优化（主动降体积）和性能预算门禁（防反弹）配合使用。
  7. 构建时优化只管静态图，用户上传/CMS 的动态图要在服务端/CDN 层实时优化，这往往是线上真正的大头。
