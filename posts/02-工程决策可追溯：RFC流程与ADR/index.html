工程决策可追溯：RFC 流程与 ADR

发表于2026|更新于2026|工程化
|字数总计:2.2k|阅读时长:6分钟

前言：前面所有篇都在讲「怎么做」——测试、CI、部署、监控、安全。这一篇讲一个更软但同样重要的问题：工程决策怎么被记录、被追溯。团队做技术选型、定架构方向时，如果决策过程和理由不留痕，半年后就会有人问「当初为什么选它、为什么不用那个」，而没人答得上来，甚至重复踩同一个坑。RFC 和 ADR 就是解决这个问题的两个轻量实践，让工程决策可讨论、可追溯。

为什么要记录决策

先说清痛点。任何有点规模的团队都会经历这些场景：

「我们为什么用 pnpm 不用 npm？」        → 没人记得当初的权衡
「这个奇怪的构建配置能删吗？」          → 不敢删，不知道当初为什么加
「上次不是讨论过要不要上微前端吗？结论呢？」→ 讨论散在群里，翻不到
「新人问为什么这么设计」               → 每次都要一个老人口头重讲一遍

共同的问题是：决策的「结论」和「理由」丢失了。代码只记录了「最终怎么做的」，没记录「为什么这么做、当时考虑过哪些方案、否决了什么」。而恰恰是「为什么」，才是判断「现在还该不该这么做」的依据。

一句话概括：代码告诉你「是什么」，RFC/ADR 告诉你「为什么」。

ADR：架构决策记录

ADR（Architecture Decision Record，架构决策记录）是最轻量的决策记录实践。它就是一份份小的 markdown 文档，每份记录一个重要决策，放在代码仓库里（通常 docs/adr/ 目录），跟代码一起版本管理。

一份 ADR 的结构非常简单，通常就这几段：

# ADR-0007: 采用 pnpm 作为包管理器

## 状态
已采纳（2026-03-15）

## 背景
项目是 Monorepo，有 12 个包。npm/yarn 的 node_modules 体积大、
安装慢，且幽灵依赖问题在多包场景下频繁出现。

## 决策
采用 pnpm 作为统一包管理器，用 workspace 管理 Monorepo。

## 理由
- 硬链接 + 内容寻址，磁盘占用和安装速度明显优于 npm/yarn
- 严格的依赖隔离，杜绝幽灵依赖
- 对 Monorepo workspace 支持成熟

## 后果
- 团队需统一用 pnpm，CI 和文档都要相应调整
- 少数只兼容 npm 的工具需额外处理
- 通过 Corepack 锁定 pnpm 版本保证一致性

ADR 的几个要点：

  1. 一个决策一份文档，编号递增（ADR-0001、ADR-0002…），不可删除。
  2. 状态字段：提议中（Proposed）、已采纳（Accepted）、已废弃（Deprecated）、被取代（Superseded by ADR-xxx）。决策变了不是删掉旧 ADR，而是标记为「被取代」并新写一份——保留决策的演变历史。
  3. 重点在「背景」和「理由」：记录当时的约束和权衡。这是未来判断「这个决策还成不成立」的关键——如果当初的约束不存在了，决策就该重新评估。
  4. 放进代码仓库：跟代码一起 review、一起演进，而不是丢在某个文档平台无人维护。

ADR 的精髓是极低成本——写一份就十几分钟，markdown 而已。它不追求完美，追求的是「重要决策有个能查到的落点」。我的建议：从今天起，团队里每个「以后可能有人问为什么」的技术决策，就顺手写一份 ADR。 成本极小，回报在半年后显现。

RFC：面向未落地决策的讨论流程

如果说 ADR 是「记录已经做的决策」，RFC（Request for Comments，请求评议）更偏向「一个还没定的重大提案，走一遍公开讨论、收集反馈、达成共识的流程」。

RFC 用于影响面大、需要多人达成一致的决策，比如：要不要引入微前端、要不要换状态管理方案、设计一个新的公共 API、重大的架构调整。这类决策不该由一个人拍板，也不该在群里聊两句就定，而值得走一个正式点的流程。

RFC 的典型流程：

1. 提案人写一份 RFC 文档（问题、方案、备选方案、影响、风险）
2. 提交为 PR / 专门的 RFC 仓库 issue，公开可见
3. 团队相关方评审、在文档上评论、讨论权衡
4. 达成共识 → RFC 被接受 → 落地实施
   有分歧 → 继续迭代方案，或记录「暂不采纳」及原因
5. RFC 归档，成为这个决策的永久记录

一份 RFC 通常包含比 ADR 更充分的论证：

  • 动机：要解决什么问题，为什么现在要解决。
  • 详细方案：具体怎么做。
  • 备选方案：还考虑过哪些，为什么不选它们（这部分极其重要）。
  • 影响与风险：对现有系统、团队、迁移成本的影响。
  • 未解决的问题：暂时没想清楚的点，开放讨论。

React、Vue、TC39（JS 标准）、Rust 等都用 RFC 流程管理重大变更——你能在它们的 RFC 仓库里看到每个重大特性「为什么这么设计、讨论过什么、否决过什么」。这就是 RFC 的价值：把重大决策的思考过程沉淀成公开、可追溯的资产。

RFC 和 ADR 的关系与配合

两者不是二选一，而是配合使用，覆盖决策的不同阶段：

RFC ADR
阶段 决策之前（提案、讨论） 决策之后（记录结论）
目的 达成共识 留档追溯
篇幅 较长（充分论证） 简短（结论 + 理由）
触发 重大、有争议的决策 任何值得记录的决策
过程 公开评审、多轮讨论 写下来即可

典型配合：重大决策走 RFC 讨论达成共识，落地后用一份 ADR 记录最终结论。小决策不必走 RFC，直接一份 ADR 就够。

一个实用的判断标准——这个决策要不要走 RFC：

影响面大 + 有多个可选方案 + 需要多人认同 + 改错代价高  → 走 RFC
局部的、方案明确的、影响小的                          → 直接 ADR 或不记录

别把所有事都上 RFC（流程会拖垮效率），也别所有事都不记录（决策全靠口口相传）。分寸感是关键。

落地建议：从小处开始

RFC/ADR 最大的敌人不是「不会写」，而是「建立了但没人维护」——写了两份就荒废了。几条让它活下去的建议：

  1. 从 ADR 开始，别一上来搞重流程。先养成「重要决策写一份 ADR」的习惯，成本低、见效快。RFC 流程等团队有需要（出现了该讨论却没讨论清楚的重大决策）再引入。
  2. 放进代码仓库，跟 PR 走。ADR/RFC 作为 markdown 进仓库，改动走 PR review。别用一个没人看的 wiki。
  3. 模板化、降低门槛。给个固定模板，填空即可。门槛越低越有人写。
  4. 在 PR/文档里引用。做某个改动时，PR 描述里链到对应的 ADR/RFC，让决策和代码关联起来。
  5. 接受它不完美。ADR 写得糙没关系，「有记录」远胜于「没记录」。追求完美只会让人不敢写。

我的核心观点：工程化不只是工具和流水线，也包括「决策的可追溯性」。前面十几篇讲的所有技术选型——用 Vitest 还是 Jest、GitHub Flow 还是 Trunk-Based、上不上 SSR——每一个背后都有权衡。把这些权衡记下来，团队才能在未来「知道为什么」，而不是对着一堆「不知道能不能动」的历史决策战战兢兢。这是工程成熟度的一个隐性标志。

小结

  1. 代码只记录「是什么」，RFC/ADR 记录「为什么」——决策的理由和权衡不留痕，团队就会重复踩坑、不敢改历史设计。
  2. ADR 是轻量的架构决策记录，一个决策一份 markdown（背景/决策/理由/后果），编号递增、放进代码仓库、用状态字段管理演变。
  3. ADR 精髓是极低成本，重点在「背景」和「理由」，让未来能判断决策是否还成立。
  4. RFC 是面向未落地重大决策的公开讨论流程（动机/方案/备选/影响/风险），用于影响面大、需多人共识的决策。
  5. RFC 的「备选方案及否决理由」最有价值，把重大决策的思考过程沉淀成可追溯资产。
  6. 两者配合：重大决策走 RFC 达成共识、落地后用 ADR 记录；小决策直接 ADR；用「影响面/方案数/改错代价」判断要不要走 RFC。
  7. 从 ADR 起步、放进仓库跟 PR 走、模板化降门槛、接受不完美——「有记录」远胜「没记录」。
