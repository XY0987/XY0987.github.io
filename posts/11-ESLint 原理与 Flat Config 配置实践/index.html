ESLint 原理与 Flat Config 配置实践

发表于2026|更新于2026|工程化
|字数总计:1.8k|阅读时长:6分钟

前言：阶段一解决的是项目能不能稳定跑起来，阶段二要解决的是代码能不能稳定写下去。我的理解是，代码规范不是让大家背规则，而是把容易出错的地方交给工具提前拦住。

ESLint 到底在检查什么

很多人第一次接触 ESLint，会把它理解成“检查分号、缩进、单双引号的工具”。这其实是早期印象。

现在我更愿意这样理解：

ESLint 是一个把源码解析成 AST，再用规则检查代码结构的静态分析工具。

它不是简单地按字符串查找，而是会先把代码解析成抽象语法树。

const count = 1
console.log(count)

在 ESLint 眼里，它看到的不是两行文本，而是类似这样的结构：

Program
├── VariableDeclaration
│   └── VariableDeclarator
│       ├── Identifier(count)
│       └── Literal(1)
└── ExpressionStatement
    └── CallExpression
        ├── MemberExpression(console.log)
        └── Identifier(count)

所以 ESLint 能做的事情远不止格式检查：

检查类型 例子 价值
语法风险 未使用变量、重复声明 提前发现低级错误
代码质量 复杂条件、无意义赋值 降低维护成本
框架约束 React Hooks 调用规则 避免运行时 bug
TypeScript 规则 禁止滥用 any 提升类型可信度
团队约定 禁止跨层级 import 固化架构边界

这也是我认为 ESLint 必须接入团队项目的原因：它能把“代码应该怎么写”变成可执行的规则。

ESLint 的工作流程

一次 eslint src 大致会经历下面几个步骤：

读取配置
  │
  ▼
匹配需要检查的文件
  │
  ▼
用 parser 把源码解析成 AST
  │
  ▼
按规则遍历 AST
  │
  ▼
输出问题或执行自动修复

这里有几个关键词要分清楚。

概念 作用
parser 决定 ESLint 如何理解源码，比如 TypeScript 需要 typescript-eslint
plugin 提供一批规则，比如 eslint-plugin-react-hooks
rule 具体检查项，比如 no-unused-vars
config 组合 parser、plugin、rule、ignore 的配置文件

一个常见误区是：以为安装了插件就会自动生效。

实际上不是。插件只是“规则仓库”，配置里启用了对应规则，它才会参与检查。

Flat Config 和 .eslintrc 的核心差异

ESLint v9 已经把 eslint.config.js 作为默认配置格式，传统 .eslintrc 已经进入 legacy 状态。

二者最大的差异不是文件名，而是配置模型变了。

对比点 .eslintrc Flat Config
配置文件 .eslintrc.* eslint.config.js
配置模型 层层级联、自动查找 一个数组，从上到下匹配
插件使用 字符串引用 直接 import 对象
ignore .eslintignore 或配置字段 通常放在配置数组中
JavaScript 能力 有限 天然使用 ESM/CJS 能力

以前 .eslintrc 更像“声明一个配置文件，然后让 ESLint 自己去合并”。

Flat Config 更像“我明确给 ESLint 一组配置对象，你按顺序执行”。

eslint.config.js
├── 全局忽略规则
├── JS 推荐规则
├── TS 文件规则
├── React 文件规则
└── 测试文件特殊规则

这种模型对大型项目更友好，因为配置来源更明确，不容易出现“这个规则到底从哪里来的”这种问题。

一个最小可用的 Flat Config

下面是一个 TypeScript 项目里比较常见的最小配置。

环境说明：

  • Node.js 18.18 及以上；
  • ESLint 9；
  • TypeScript 项目；
  • 使用 pnpm。

安装依赖：

pnpm add -D eslint @eslint/js typescript typescript-eslint

创建 eslint.config.js：

import js from '@eslint/js'
import tseslint from 'typescript-eslint'

export default [
  {
    ignores: ['dist/**', 'coverage/**', 'node_modules/**'],
  },
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    files: ['**/*.{ts,tsx}'],
    rules: {
      '@typescript-eslint/no-unused-vars': [
        'error',
        {
          argsIgnorePattern: '^_',
          varsIgnorePattern: '^_',
        },
      ],
    },
  },
]

再在 package.json 里加脚本：

{
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint . --fix"
  }
}

执行：

pnpm lint

如果代码里有未使用变量，就会看到类似输出：

error  'name' is assigned a value but never used  @typescript-eslint/no-unused-vars

TypeScript 项目为什么不要只用默认规则

TypeScript 项目里有一个很常见的坑：同时开启 ESLint 自带的 no-unused-vars 和 TypeScript 版的 @typescript-eslint/no-unused-vars。

这样会出现重复报错，甚至对类型声明判断不准确。

我的建议是：只要进入 TypeScript 文件，就优先使用 TypeScript ESLint 提供的同名规则。

{
  files: ['**/*.{ts,tsx}'],
  rules: {
    'no-unused-vars': 'off',
    '@typescript-eslint/no-unused-vars': 'error',
  },
}

原因很简单：TypeScript 的语法比 JavaScript 多，普通 ESLint 规则不一定理解类型空间。

比如：

type User = {
  id: string
}

const user: User = {
  id: '1',
}

这里的 User 是类型使用，不是运行时代码使用。规则如果不理解 TypeScript，就容易误判。

是否要开启类型感知规则

typescript-eslint 里有些规则需要读取 tsconfig.json，这类规则通常叫 type-aware linting。

它能检查更深的问题，比如：

async function getUser() {
  return { id: '1' }
}

// 没有 await，也没有处理 Promise
getUser()

这类问题普通语法规则不一定能准确判断，因为它需要知道 getUser() 的返回类型。

但类型感知规则也有代价：它会启动 TypeScript Program，速度明显慢于普通 lint。

我的建议是分层：

场景 建议
本地保存时 用普通 ESLint 规则，保证反馈快
pre-commit 只检查暂存文件，避免卡顿
CI 跑完整 ESLint + 类型检查
大型 monorepo 按 package 分区检查

不要一开始就把所有最重的规则塞进本地提交钩子里，否则团队最后会想办法绕过工具。

规则配置要有边界

ESLint 规则不是越多越好。

我通常会把规则分成三类：

规则类型 是否强制 例子
明确 bug 风险 必须强制 React Hooks 规则、未处理 Promise
团队一致性 适度强制 import 顺序、命名约定
个人偏好 尽量交给格式化工具 分号、缩进、换行

尤其要避免把 ESLint 配成“个人审美工具”。代码质量工具一旦掺入太多审美争论，就会失去团队信任。

一个更贴近团队项目的脚本设计

我更推荐把检查命令拆开：

{
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "typecheck": "tsc --noEmit",
    "check": "pnpm lint && pnpm typecheck"
  }
}

这样做有两个好处：

  1. 本地可以单独跑 lint:fix；
  2. CI 可以统一跑 check。

如果项目变大，还可以继续拆：

{
  "scripts": {
    "lint:src": "eslint src",
    "lint:test": "eslint tests",
    "typecheck": "tsc -p tsconfig.json --noEmit"
  }
}

工具链设计的目标不是命令越少越好，而是每个命令的职责清楚。

小结

  1. ESLint 的核心是基于 AST 的静态分析，不只是格式检查。
  2. ESLint v9 默认使用 Flat Config，新项目建议直接使用 eslint.config.js。
  3. TypeScript 项目要优先使用 typescript-eslint 的规则，避免普通 JS 规则误判。
  4. 类型感知规则更强但更慢，适合放到 CI 或完整检查里。
  5. 团队规则要优先约束 bug 风险和协作边界，不要把个人审美塞满配置。
