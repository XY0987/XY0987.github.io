Vue 3 源码系统总览：从响应式到渲染闭环

发表于2026|更新于2026|Vue框架及周边库
|字数总计:2.7k|阅读时长:9分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：这一篇不急着钻进某个函数，而是先建立一张 Vue 3 源码地图。我的理解是，读 Vue 源码最重要的不是记住每个函数怎么写，而是先知道这些模块为什么被拆开、它们如何协作，以及每一层在系统里解决什么问题。

先给结论

Vue 3 的核心链路可以概括成一条闭环：

template / render
  │
  ├─ compiler：template -> render function
  │
  ▼
render function
  │
  ▼
VNode
  │
  ▼
runtime-core renderer
  │
  ├─ component：组件实例、setup、props、slots、生命周期
  ├─ scheduler：异步批量更新
  └─ patch：把新旧 VNode 差异应用到宿主环境
        │
        ▼
runtime-dom / custom renderer
  │
  └─ DOM 操作、属性更新、事件绑定

reactivity
  │
  ├─ reactive / ref / computed / watch
  ├─ track：读数据时收集依赖
  └─ trigger：写数据时通知 effect
        │
        ▼
组件 render effect 重新执行，生成新的 VNode

所以 Vue 不是一个单点系统，而是一组互相配合的子系统：

子系统 核心问题 主要目录
响应式系统 数据变化如何被感知 packages/reactivity
运行时核心 组件如何创建、更新、卸载 packages/runtime-core
浏览器运行时 平台 DOM 能力如何注入 packages/runtime-dom
编译器核心 模板如何变成 render 函数 packages/compiler-core
DOM 编译器 浏览器模板语法如何转换 packages/compiler-dom
SFC 编译器 .vue 文件如何拆分和组装 packages/compiler-sfc
SSR 渲染器 服务端字符串如何生成并被接管 packages/server-renderer

这张表比某一个函数更重要。因为函数会改，目录结构和边界背后的设计约束更稳定。

Vue 解决的不是一个问题，而是三类问题

读 Vue 源码时，我建议一直带着三类问题看。

第一类是响应式问题：

用户改了一个变量，框架怎么知道谁该更新？

这对应 reactive、ref、effect、computed、watch。它们的主线是“读时收集，写时触发”。

第二类是渲染问题：

状态变化后，框架怎么把变化更新到页面上？

这对应组件实例、render effect、scheduler、VNode、patch、diff。它们的主线是“状态变了，不立刻粗暴操作 DOM，而是重新生成 VNode，再做最小必要更新”。

第三类是编译问题：

为什么模板可以写得像 HTML，但运行时却能高效更新？

这对应 parse、transform、codegen。它们的主线是“把模板中的静态信息提前分析出来，让运行时少猜一点”。

包分层：Vue 的第一层设计哲学

Vue 源码里很重要的一条线是：核心逻辑尽量平台无关，平台能力从外部注入。

runtime-core 不直接调用 document.createElement，而是接收一组 host 操作：

export function createRenderer<
  HostNode = RendererNode,
  HostElement = RendererElement,
>(options: RendererOptions<HostNode, HostElement>): Renderer<HostElement> {
  return baseCreateRenderer<HostNode, HostElement>(options)
}

// Separate API for creating hydration-enabled renderer.
// Hydration logic is only used when calling this function, making it
// tree-shakable.
export function createHydrationRenderer(
  options: RendererOptions<Node, Element>,
): HydrationRenderer {
  return baseCreateRenderer(options, createHydrationFunctions)
}

// overload 1: no hydration
function baseCreateRenderer<
  HostNode = RendererNode,
  HostElement = RendererElement,
>(options: RendererOptions<HostNode, HostElement>): Renderer<HostElement>

// overload 2: with hydration
function baseCreateRenderer(
  options: RendererOptions<Node, Element>,
  createHydrationFns: typeof createHydrationFunctions,
): HydrationRenderer

// implementation
function baseCreateRenderer(
  options: RendererOptions,
  createHydrationFns?: typeof createHydrationFunctions,
): any {
  // compile-time feature flags check
  if (__ESM_BUNDLER__ && !__TEST__) {
    initFeatureFlags()
  }

  const target = getGlobalThis()
  target.__VUE__ = true
  if (__DEV__ || __FEATURE_PROD_DEVTOOLS__) {
    setDevtoolsHook(target.__VUE_DEVTOOLS_GLOBAL_HOOK__, target)
  }

  // renderer 不直接操作 DOM，而是把平台操作从 options 中解构成 hostXXX。
  // 对 runtime-dom 来说这些就是 DOM API；对自定义渲染器来说可以是任意宿主环境操作。

    remove: hostRemove,
    patchProp: hostPatchProp,
    createElement: hostCreateElement,
    createText: hostCreateText,
    createComment: hostCreateComment,
    setText: hostSetText,
    setElementText: hostSetElementText,
    parentNode: hostParentNode,
    nextSibling: hostNextSibling,
    setScopeId: hostSetScopeId = NOOP,
    insertStaticContent: hostInsertStaticContent,
  } = options

这一层分离带来三个结果：

  1. runtime-core 可以复用在不同平台。
  2. runtime-dom 只负责浏览器差异，不污染核心渲染逻辑。
  3. 自定义渲染器有可能存在，因为核心算法不绑定 DOM。

这就是框架设计里非常关键的能力：把变化大的部分隔离出去，把稳定的部分沉淀成核心。

响应式：把“谁依赖谁”变成运行时图结构

响应式系统最容易被误解成“Proxy 魔法”。但 Proxy 只负责拦截读写，真正重要的是依赖图。

ReactiveEffect 是订阅者抽象，执行期间会设置当前活跃订阅者：

// 当前正在执行并允许收集依赖的订阅者。
// ReactiveEffect.run / refreshComputed 会在执行用户函数前设置它，track 会读取它来建立依赖关系。
export let activeSub: Subscriber | undefined

当 effect 运行时，它打开依赖收集窗口：

// 执行副作用函数，并在执行期间打开依赖收集窗口。(清理旧依赖、准备新依赖)
run(): T {
  // TODO cleanupEffect

  if (!(this.flags & EffectFlags.ACTIVE)) {
    // 已 stop 的 effect 再执行 runner 时，只调用原函数，不再收集依赖。
    return this.fn()
  }

  this.flags |= EffectFlags.RUNNING
  // 执行前先调用上一次注册的 cleanup，避免旧副作用残留。
  cleanupEffect(this)
  // 把旧依赖标记为待确认；本轮执行中再次访问到的依赖会被重新激活。
  prepareDeps(this)
  const prevEffect = activeSub
  const prevShouldTrack = shouldTrack
  // 设置全局 activeSub，后续响应式属性 get 时，track 就能收集到当前 effect。
  activeSub = this
  shouldTrack = true

这背后的设计不是“监听所有数据”，而是“只记录实际读过的数据”。这让响应式有了精确更新的基础。

调度器：把多次变化合并成一次更新

响应式数据变化后，如果每次都同步更新组件，性能和稳定性都会出问题。Vue 的调度器做的事情是：把同一轮同步代码里的多次更新合并到一个微任务里。

export function queueJob(job: SchedulerJob): void {
  // 同一个 job 在同一轮 flush 中只允许入队一次。
  if (!(job.flags! & SchedulerJobFlags.QUEUED)) {
    const jobId = getId(job)
    const lastJob = queue[queue.length - 1]
    if (
      !lastJob ||
      // fast path when the job id is larger than the tail
      (!(job.flags! & SchedulerJobFlags.PRE) && jobId >= getId(lastJob))
    ) {
      queue.push(job)
    } else {
      queue.splice(findInsertionIndex(jobId), 0, job)
    }

    job.flags! |= SchedulerJobFlags.QUEUED

    queueFlush()
  }
}

function queueFlush() {
  if (!currentFlushPromise) {
    // 通过 Promise 微任务异步 flush，实现同一轮同步状态变更的批量更新。
    currentFlushPromise = resolvedPromise.then(flushJobs)
  }
}

这里能看到 Vue 的另一个设计取向：不是追求每一次变化都立刻更新，而是追求在用户可感知前完成稳定、可预测、去重后的更新。

编译器：让运行时少做判断

模板编译的主入口是 baseCompile，主线很清楚：parse、transform、codegen。

const resolvedOptions = extend({}, options, {
  prefixIdentifiers,
})
// 1. parse：模板字符串先解析成 AST；如果传入的已经是 RootNode，则直接复用。
const ast = isString(source) ? baseParse(source, resolvedOptions) : source
// 2. 准备 transform 预设：节点转换 + 指令转换。
const [nodeTransforms, directiveTransforms] =
  getBaseTransformPreset(prefixIdentifiers)

if (!__BROWSER__ && options.isTS) {
  const { expressionPlugins } = options
  if (!expressionPlugins || !expressionPlugins.includes('typescript')) {
    options.expressionPlugins = [...(expressionPlugins || []), 'typescript']
  }
}

// 3. transform：遍历 AST，处理 v-if/v-for/v-bind 等语法，并为后续 codegen 准备 codegenNode。
transform(
  ast,
  extend({}, resolvedOptions, {
    nodeTransforms: [
      ...nodeTransforms,
      ...(options.nodeTransforms || []), // user transforms
    ],
    directiveTransforms: extend(
      {},
      directiveTransforms,
      options.directiveTransforms || {}, // user transforms
    ),
  }),
)

// 4. codegen：把转换后的 AST 生成 render 函数字符串。
return generate(ast, resolvedOptions)

编译器的价值不只是“把字符串变成函数”。更重要的是，它能提前知道哪些节点是静态的、哪些属性是动态的、哪些 children 是 keyed 的。运行时拿到这些信息，就不用完全靠猜。

这也是 Vue 3 和“纯运行时框架”很不一样的地方：Vue 不是只在运行时做优化，而是让编译期和运行时共同完成优化。

源码总览真正要看什么

我的看法是，读源码至少要分三层。

第一层是 API 怎么实现。比如 reactive 怎么创建 Proxy，computed 怎么缓存，watch 怎么 cleanup。

第二层是模块怎么协作。比如响应式系统如何触发组件更新，调度器如何保证父子组件更新顺序，编译器如何给运行时提供 patch flag。

第三层是设计取舍。比如为什么 runtime-core 不直接依赖 DOM，为什么 ref 必须通过 .value 访问，为什么 scheduler 默认异步批量执行，为什么 SSR hydration 选择复用 DOM 而不是重建。

只停留在第一层，很容易变成“背源码”。真正有价值的是第二层和第三层，因为它们能迁移到你以后设计自己的框架、业务架构和工具链里。

小结

  1. Vue 3 源码可以按响应式、运行时、编译器、SSR 四条主线理解。
  2. runtime-core 和 runtime-dom 的分离体现了平台无关核心 + 平台能力注入的设计。
  3. 响应式系统的本质是维护依赖图，不只是使用 Proxy。
  4. 调度器通过微任务和去重机制，把多次状态变化合并成稳定更新。
  5. 编译器提前分析模板信息，让运行时更新更精确。
  6. 读源码的终点不是“知道代码怎么写”，而是理解背后的系统边界和设计取舍。
