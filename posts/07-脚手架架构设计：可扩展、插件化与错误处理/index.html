脚手架架构设计：可扩展、插件化与错误处理

发表于2026|更新于2026|工程化
|字数总计:3.1k|阅读时长:11分钟

前言：前面几篇把 CLI 的各个零件都讲了：参数解析、交互、文件生成、子进程、模板管理。这一篇把它们组装起来，谈架构——一个能长期维护、能扩展的脚手架该怎么分层？怎么做插件化？错误和日志体验怎么设计？零件会写不等于会造车，架构是把工具从「能跑」做到「好维护」的关键。

先分层：把流程和能力拆开

很多人写脚手架，所有逻辑堆在一个 index.ts 的 action 回调里，几百行下来谁也不敢动。问题不在代码量，在于没有分层。一个清晰的脚手架，至少分三层：

┌─────────────────────────────────────┐
│  CLI 层：参数解析、命令注册            │  commander/cac
│  （只负责"接收用户意图"）             │
├─────────────────────────────────────┤
│  交互层：补全缺失参数、确认           │  clack/prompts
│  （把参数 + 交互合并成完整的 context）│
├─────────────────────────────────────┤
│  核心层：根据 context 执行业务         │  fs / execa / giget
│  （拷模板、装依赖、init git）         │
└─────────────────────────────────────┘

核心原则：CLI 层不写业务逻辑，核心层不碰 process.argv。CLI 层把用户输入整理成一个干净的 context 对象，往下传；核心层只认 context，不关心这些值是命令行传的还是交互问出来的。

这样做的直接好处是核心逻辑可测试、可复用：

// context 是唯一的"输入契约"
interface CreateContext {
  projectName: string
  targetDir: string
  template: string
  useTs: boolean
  install: boolean
  git: boolean
}

// 核心层只依赖 context，完全不知道 CLI 的存在
async function runCreate(ctx: CreateContext) {
  await copyTemplate(ctx.template, ctx.targetDir, ctx)
  if (ctx.install) await installDeps(ctx.targetDir)
  if (ctx.git) await initGit(ctx.targetDir)
}

再拆包：用 monorepo 管理 CLI 能力

上面的分层解决的是「代码职责」问题。如果脚手架继续变大，还会遇到另一个问题：很多能力会被多个命令复用，比如路径处理、日志、下载、权限校验、模板缓存、包管理器检测。这个时候就可以把 CLI 拆成多个 npm 包，用 monorepo 管理。

典型结构长这样：

my-cli/
├── package.json
├── pnpm-workspace.yaml
├── packages/
│   ├── cli/              # 命令入口：只负责注册命令和组合流程
│   ├── core/             # 核心编排：create、init、upgrade 等业务流程
│   ├── utils/            # 通用工具：路径、文件、日志、环境检测
│   ├── downloader/       # 下载能力：giget/degit/git/npm 包下载
│   ├── template-cache/   # 模板缓存：缓存目录、版本判断、更新确认
│   ├── permission/       # 权限能力：登录态、token、私有仓库权限校验
│   └── plugin-api/       # 插件接口：PluginApi、生命周期、上下文类型
└── templates/

pnpm-workspace.yaml 很简单：

packages:
  - "packages/*"

每个包都是独立的 npm 包，只是暂时放在同一个仓库里开发：

{
  "name": "@my-cli/downloader",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./dist/index.js"
  }
}

我的建议是：拆包按能力边界拆，不要按文件类型拆。不要拆成 @my-cli/types、@my-cli/helpers、@my-cli/constants 这种泛泛的包，而是拆成「下载」「缓存」「权限」「插件 API」这种能独立说清楚职责的包。

包之间怎么依赖

拆包之后，最重要的是别让依赖关系乱掉。一个比较健康的依赖方向是：

@my-cli/cli
  └── @my-cli/core
        ├── @my-cli/template-cache
        │     ├── @my-cli/downloader
        │     └── @my-cli/utils
        ├── @my-cli/permission
        │     └── @my-cli/utils
        ├── @my-cli/plugin-api
        └── @my-cli/utils

这里有几个原则：

  1. cli 只依赖 core，不要直接依赖一堆底层包，否则命令入口会重新变胖。
  2. core 负责业务编排，可以依赖缓存、下载、权限、插件 API。
  3. utils 是底层包，只能被别人依赖，自己不要反过来依赖 core。
  4. plugin-api 尽量只放类型和接口，避免引入具体实现。

代码里看起来就是这样：

// packages/cli/src/index.ts
import { runCreate } from '@my-cli/core'

program
  .command('create [name]')
  .option('-t, --template <template>')
  .action(async (name, options) => {
    await runCreate({ name, ...options })
  })

// packages/core/src/create.ts
import { ensureTemplateCache } from '@my-cli/template-cache'
import { checkTemplatePermission } from '@my-cli/permission'
import { copyDir } from '@my-cli/utils'

export async function runCreate(ctx) {
  await checkTemplatePermission(ctx.template)
  const templateDir = await ensureTemplateCache(ctx.template)
  await copyDir(templateDir, ctx.targetDir)
}

这样 core 只描述业务流程：校验权限 → 准备模板 → 复制文件。具体怎么鉴权、怎么下载、缓存放哪，都交给对应的包。

什么时候值得拆包

不是所有脚手架一开始都要 monorepo。我的判断是：

阶段 建议
只有一个 create 命令、两三个模板 单包就够了
有多个命令，共用下载、日志、缓存逻辑 可以拆 core、utils、downloader
有私有模板、权限系统、插件 API 建议 monorepo
多个工具共用同一套能力 必须拆包，否则复制粘贴会失控

拆包的收益是复用和边界清晰，代价是构建、发布、版本管理都会变复杂。所以不要一上来就把项目拆成十几个包，先让业务长出来，再按复用点拆出去。

参数与交互的合并：有就用，没有就问

上面 context 怎么来？这是脚手架体验的核心：命令行给了的用命令行，没给的交互式补全。这样既能 mycli create app -t vue --no-install（全自动、可脚本化），又能 mycli create（一步步引导）。

import { text, select, confirm, isCancel, cancel } from '@clack/prompts'

async function resolveContext(cliArgs): Promise<CreateContext> {
  // 1. 命令行没给项目名才问
  let projectName = cliArgs.name
  if (!projectName) {
    const r = await text({ message: '项目名称？', placeholder: 'my-app' })
    if (isCancel(r)) { cancel('已取消'); process.exit(0) }
    projectName = r
  }

  // 2. 命令行没给模板才问
  let template = cliArgs.template
  if (!template) {
    const r = await select({
      message: '选择模板',
      options: [
        { value: 'vue', label: 'Vue' },
        { value: 'react', label: 'React' },
      ],
    })
    if (isCancel(r)) { cancel('已取消'); process.exit(0) }
    template = r
  }

  return {
    projectName,
    targetDir: path.resolve(process.cwd(), projectName),
    template,
    useTs: cliArgs.ts ?? true,
    install: cliArgs.install ?? true,
    git: cliArgs.git ?? true,
  }
}

这个「有就用，没有就问」的模式，是所有好用脚手架的共同点。把它独立成一个函数，CLI 层和核心层就彻底解耦了。

插件化：让能力可插拔

当脚手架功能变多——支持加 ESLint、加 Router、加测试框架——把所有逻辑写死在核心层会越来越臃肿。这时候引入插件化：把每个「可选能力」做成一个独立单元，按用户选择动态加载。

最朴素也最实用的插件模型，就是约定一个统一接口：

interface ScaffoldPlugin {
  name: string
  // 该插件要往 context 注入的依赖、文件改动等
  apply(ctx: CreateContext, api: PluginApi): Promise<void> | void
}

interface PluginApi {
  // 给插件提供的能力：写文件、改 package.json、加依赖
  addDependency(name: string, version: string): void
  renderTemplate(from: string, to: string): Promise<void>
  extendPackageJson(patch: Record<string, unknown>): void
}

一个 ESLint 插件大概长这样：

const eslintPlugin: ScaffoldPlugin = {
  name: 'eslint',
  apply(ctx, api) {
    api.addDependency('eslint', '^9.0.0')
    api.extendPackageJson({
      scripts: { lint: 'eslint .' },
    })
    return api.renderTemplate('plugins/eslint/eslint.config.js', 'eslint.config.js')
  },
}

核心层把插件串起来执行：

async function applyPlugins(ctx, plugins, api) {
  for (const plugin of plugins) {
    await plugin.apply(ctx, api)
  }
  // 所有插件改完后，统一写一次 package.json
  await api.flushPackageJson()
}

这样新增能力 = 新增一个插件文件，不用动核心流程。Vue CLI、很多企业内部脚手架都是这个思路。

提醒：插件化是「功能复杂到一定程度」才值得引入的。如果你的脚手架就两三个固定模板，老老实实写在核心层更简单。不要为了架构而架构——过早插件化只会增加心智负担。等到「每次加功能都要改一大坨核心代码」时，再重构成插件不迟。

错误处理：区分致命与可降级

脚手架运行中会遇到各种错误，关键是分清两类：

类型 例子 处理方式
致命错误 模板不存在、目标目录冲突、磁盘写失败 终止流程，给清晰提示，非 0 退出码
可降级错误 git init 失败、自动装依赖失败 警告 + 跳过，让用户手动补，正常退出

致命错误用「自定义错误 + 顶层捕获」统一处理，避免到处 process.exit：

class ScaffoldError extends Error {}

async function main() {
  try {
    const ctx = await resolveContext(parseArgs())
    await runCreate(ctx)
  } catch (err) {
    if (err instanceof ScaffoldError) {
      // 可预期的业务错误：只给用户看友好提示
      console.error(red(`✖ ${err.message}`))
    } else {
      // 非预期错误：打完整堆栈，方便用户提 issue
      console.error(red('✖ 发生未知错误：'))
      console.error(err)
    }
    process.exit(1) // 非 0 退出码，CI 才能感知失败
  }
}

main()

这里有几个工程要点：

  1. 退出码很重要。失败必须 process.exit(1)，否则在 CI 或脚本里调用你的工具，它检测不到失败。
  2. **区分”给用户看的提示”和”给开发者看的堆栈”**。业务错误（如模板不存在）只显示一句人话；未知错误才打完整堆栈让人能定位。
  3. 可降级的错误别往上抛。在它发生的地方 try/catch 掉、警告一句、继续跑，就像上一篇 git init 的处理那样。

处理用户中途取消

用户按 Ctrl+C 是高频操作，尤其在交互过程中。前面讲过 clack 用 isCancel 处理 prompt 内的取消。但如果用户在「装依赖」这种长任务中按 Ctrl+C，要保证不留下半成品的烂摊子：

process.on('SIGINT', () => {
  console.log('\n操作已取消')
  // 如果已经创建了目录但还没完成，可以在这里清理
  process.exit(1)
})

是否要回滚已生成的文件，看产品取舍。create-vite 的做法是「目录已建则提示用户自行清理」，不强制回滚——回滚逻辑本身也可能出错。简单可靠优先。

日志体验：让用户始终知道发生了什么

好工具的日志有节奏感。把前面几篇的交互、loading、颜色组合成清晰的反馈：

import { intro, outro } from '@clack/prompts'
import { green, dim, cyan } from 'kolorist'

intro(cyan('create-my-app'))
// ...交互、生成...
outro(
  green('项目创建完成！') +
  '\n' +
  dim(`  cd ${ctx.projectName}\n  npm run dev`),
)

日志设计的几条原则：

  1. 每个阶段有明确反馈：开始做什么、做完了没、成功还是失败。
  2. **结尾给”下一步指引”**：告诉用户 cd xxx && npm run dev，别让人创建完一脸茫然。
  3. 错误信息要可行动：不只是「失败了」，而是「失败了，因为 X，你可以 Y」。
  4. 克制：颜色和符号服务于「快速辨识状态」，不是为了花哨。

一张整体架构图

把这一阶段所有零件按职责归位：

                用户命令
                   │
          ┌────────▼─────────┐
          │ @my-cli/cli       │  CLI 层：解析命令/选项
          └────────┬─────────┘
                   │ cliArgs
          ┌────────▼─────────┐
          │ @my-cli/core      │  交互 + 核心编排
          └────────┬─────────┘
                   │ context
          ┌────────▼─────────┐
          │  能力包            │
          │  ├ template-cache │  模板缓存 / 版本判断
          │  ├ downloader     │  giget / degit / npm
          │  ├ permission     │  登录态 / token / 权限
          │  ├ plugin-api     │  插件接口
          │  └ utils          │  文件 / 路径 / 日志
          └──────────────────┘

这套分层不复杂，但能让脚手架从「一坨 action 函数」进化成「可维护、可扩展、可测试」的工具。下一篇讲怎么给它写测试、发布到 npm。

小结

  1. 脚手架要分层：CLI 层只接收意图，交互层补全成 context，核心层只认 context 执行业务。
  2. CLI 层不写业务、核心层不碰 process.argv，用一个 context 对象解耦，核心逻辑才可测可复用。
  3. CLI 变大后可以用 monorepo 拆成多个 npm 包，按下载、缓存、权限、插件 API、utils 这些能力边界拆。
  4. 「命令行有就用、没有就交互问」是好用脚手架的共同模式，把它独立成函数。
  5. 功能复杂时引入插件化，把可选能力做成统一接口的插件，但不要为架构而架构、过早插件化。
  6. 错误分致命和可降级：致命错误终止 + 非 0 退出码 + 友好提示，可降级错误警告后跳过。
  7. 区分给用户的提示和给开发者的堆栈；失败务必 exit(1)，否则 CI 感知不到。
  8. 日志要有节奏：每阶段有反馈、结尾给下一步指引、错误信息可行动、整体克制。
