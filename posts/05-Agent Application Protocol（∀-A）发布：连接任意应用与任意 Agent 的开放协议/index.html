Agent Application Protocol（∀/A）发布：连接任意应用与任意 Agent 的开放协议

发表于2026|更新于2026|AI相关
|字数总计:4.7k|阅读时长:17分钟

前言：MCP 解决的是“Agent 怎么接工具和上下文”，但很多团队还有另一个更现实的问题：业务应用怎样接入一个可替换、可远程部署的 Agent？刚发布的 Agent Application Protocol（AAP，符号写作 ∀/A）想标准化的，正是这一层。

一句话看懂 AAP

AAP 是应用和 Agent 之间的标准接口：应用管界面与业务工具，Agent 管推理、上下文和通用能力。

它的名字 ∀/A 很直白：Any Application / Any Agent。只要两端实现同一份协议，理论上一个游戏引擎、CAD 软件、企业后台或微服务，都可以连接同一个远程 Agent；而应用也不必绑定某个 Agent 框架或模型供应商。

把它和常见概念放在一起会更清楚：

协议/能力 主要连接谁 解决的问题
Function Calling 模型 API 与调用方 模型如何描述一次函数调用
MCP Agent 与外部工具/资源 Agent 如何发现、调用外部能力
ACP IDE 与编码 Agent IDE 如何驱动本地优先的编码 Agent
AAP 应用与 Agent 任意应用如何接入远程、可替换的 Agent 服务

所以别把 AAP 当成“又一个 MCP 替代品”。先看一个具体场景：假设你在做一个 3D 建模软件，用户在软件里说：“把当前选中的角色放大 20%，再给它生成一个赛博朋克风格的配色方案。”

┌────────────── 3D 建模软件（Application）──────────────┐
│ 用户输入：把选中角色放大 20%，给我一套赛博朋克配色      │
│                                                          │
│ 应用独有能力：get_selected_model、scale_model、apply_color│
└────────────────────────┬───────────────────────────────┘
                         │
                         │  AAP：把“消息 + 工具定义”发给 Agent
                         │  POST /sessions/:id/turns（HTTP + SSE）
                         ▼
┌──────────────── 远程设计 Agent（Agent）─────────────────┐
│ 理解任务、维护对话、决定调用哪些工具、生成配色建议       │
│                                                          │
│ 需要放大模型 → 发 tool_call(scale_model) 给 3D 软件      │
└────────────────────────┬───────────────────────────────┘
                         │
                         │  MCP（可选）：给 Agent 接通用外部能力
                         ▼
              联网搜索 / 图片分析 / 代码执行 / 记忆服务

这里 AAP 就是中间那根线：它约定 3D 软件怎样发现远程 Agent、怎样创建会话、怎样发送用户消息，以及 Agent 想调用 scale_model 时如何把请求交还给软件执行。它不规定 3D 软件内部怎么改模型，也不规定 Agent 内部用哪家模型、哪个框架。

我的理解是：MCP 更像 Agent 的“USB 接口”；AAP 则更像把整台 Agent 机器接进业务应用的“网络协议”。如果你的应用只是在内部调一次 LLM API，AAP 反而会显得重。但当 Agent 要被多个应用复用、独立扩缩容、按量计费时，分层就开始有价值。

它拆开的，到底是哪一层耦合

今天不少 Agent 产品的结构是：前端、领域逻辑、Prompt、Agent Loop、模型调用、工具执行都塞进一个应用。起步很快，但后续通常会遇到两个问题：

  • 每个业务团队都要重复实现对话历史、上下文压缩、工具循环、模型重试和安全策略。
  • 想把底层 Agent 从框架 A 换成框架 B，或者把本地 Agent 换成远程 SaaS，往往要改应用层代码。

AAP 的边界划分非常明确：

归属 负责什么 为什么应该归它
Application（客户端） UI/UX、用户输入、领域数据、领域工具 它最了解“当前场景”“当前订单”“哪些操作允许执行”
Agent（服务端） Agent Loop、会话历史、LLM 交互、Guardrail、通用工具 它最了解如何推理、何时调用工具、怎样管理上下文窗口

这不是简单的前后端分层。AAP 把 Agent 当作一个独立的、远程优先的服务：应用不需要知道它内部用 Vercel AI SDK、LangChain 还是其他框架；Agent 也不必了解应用的 UI 和私有业务实现。

这层隔离还有一个常被忽略的好处：双方不必互相暴露实现细节。应用可以只暴露必要的工具 schema，Agent 可以保留自己的系统提示词、记忆实现和模型路由策略。

AAP 的核心：Agent 负责思考，应用负责动手

这句话是理解 AAP 最简单的方式：Agent 可以远程运行并提出“怎么做”，但真正操作业务数据和业务软件的，始终是应用这一侧。

应用侧工具：把“能做什么”告诉 Agent

还是用 3D 建模软件举例。用户说：“把当前选中的角色放大 20%。”

远程 Agent 并没有运行在 3D 软件进程里，它既看不到当前选中了什么，也没有权限直接改模型。于是软件先把自己能安全提供的动作告诉 Agent，例如：

{
  name: "scale_selected_model",
  description: "将当前选中的 3D 模型按指定比例缩放",
  parameters: {
    type: "object",
    properties: {
      percent: { type: "number", description: "缩放百分比，例如 120 表示放大 20%" }
    },
    required: ["percent"]
  }
}

这里的“工具”可以先把它理解成：软件给 Agent 的一张受限操作菜单。Agent 只能从菜单里请求动作，不能自行操作软件，更不能调用菜单上没有的能力。

完整过程其实就是一次“请求 → 执行 → 回报”的接力：

用户：把当前选中的角色放大 20%
  │
  ▼
3D 软件（Application）──把用户消息和“工具菜单”发给──→ 远程 Agent
                                                        │
                                                        │ Agent 判断：
                                                        │ 要完成任务，需要调用
                                                        │ scale_selected_model({ percent: 120 })
                                                        ▼
3D 软件 ←── Agent 发回“请执行这个动作”── Agent 暂停等待
  │
  │ 软件检查：当前用户有编辑权限吗？参数 120 合法吗？
  │ 检查通过后，软件在应用侧真正修改模型
  │
  └──把结果“角色已放大 20%”发回给 Agent──────────────→
                                                        │
                                                        ▼
                                      Agent：已完成，当前角色已放大 20%

协议中的 tool_call 就是图中的“请执行这个动作”；stopReason: "tool_use" 的意思是“我已经提出了操作请求，现在等应用把执行结果交回来”。名称虽然偏技术，但本质并不复杂：Agent 负责下指令，应用负责决定是否执行和实际执行。

这个“暂停等待”很重要。应用仍然握有自己业务工具的最终执行权，因此可以做参数校验、权限检查、二次确认和审计。Agent 只是提出意图，不是绕过业务边界的超级管理员。

Agent 侧工具：应用选择是否授权

Agent 也可以在 GET /meta 中公开自己支持的服务端工具，例如联网搜索、代码执行或持久记忆。应用创建会话时可选择启用哪些工具。

其中 trust: true 是一个值得谨慎使用的开关：它表示应用信任 Agent 在服务端直接执行该工具。此时 Agent 会连续推送 tool_call、tool_result 和后续文本，应用不用参与中间往返。

工具位置 谁执行 是否需要应用回传 典型用途
应用侧工具 Application 需要：提交 tool 结果 修改文档、读取当前场景、操作企业业务数据
未信任的 Agent 侧工具 Agent（获准后） 需要：提交许可决定 用户想先确认的外部操作
trust: true 的 Agent 侧工具 Agent 不需要 低风险的搜索、内部记忆检索

把 trust: true 当成授权策略，而不是性能优化按钮。会产生外部副作用、涉及付费或敏感数据的能力，默认不信任更稳妥。

协议长什么样：标准 HTTP 资源 + SSE

AAP 当前协议版本是 3。服务端先用 GET /meta 发布可用 Agent、能力、可配置选项和可启用的服务端工具。随后客户端围绕 session 操作：

方法 路径 用途
GET /meta 发现服务端的 Agent 与能力
POST /sessions 创建会话，但不运行 Agent
POST /sessions/:id/turns 发送用户消息或工具结果，并运行一轮 Agent
GET /sessions/:id/history 在支持时读取会话历史，用于恢复
DELETE /sessions/:id 删除会话和关联历史

一次“放大模型”的完整请求流程

继续使用前面的 3D 建模软件。用户输入“把当前选中的角色放大 20%”后，应用与远程 Agent 的正常交互如下。示例省略了每个请求都应携带的 Authorization: Bearer <api-key>，把注意力放在流程本身。

3D 建模软件（Application）                         远程 Agent 服务
          │                                               │
1. 发现   │ GET /meta                                     │
          │──────────────────────────────────────────────>│
          │<── 200 { version: 3, agents: [design-agent] } │
          │                                               │
2. 建会话 │ POST /sessions                                │
          │ { agent: design-agent,                         │
          │   tools: [scale_selected_model] }              │
          │──────────────────────────────────────────────>│
          │<──────────── 201 { sessionId: "sess_123" } ───│
          │                                               │
3. 发任务 │ POST /sessions/sess_123/turns                  │
          │ { stream: "delta", messages: [用户指令] }      │
          │──────────────────────────────────────────────>│
          │<── SSE：tool_call(scale_selected_model, 120) ─│
          │<── SSE：turn_stop(tool_use) ──────────────────│
          │                                               │
4. 应用执行│ 校验权限后，在自己的进程中放大模型             │
          │                                               │
5. 交结果 │ POST /sessions/sess_123/turns                  │
          │ { messages: [tool 结果：已放大 20%] }           │
          │──────────────────────────────────────────────>│
          │<── SSE：text_delta("已完成，角色已放大 20%") ─│
          │<── SSE：turn_stop(end_turn) ──────────────────│

对应到真实 HTTP 请求，关键的第 2、3、5 步大致如下：

POST /sessions
Content-Type: application/json

{
  "agent": { "name": "design-agent" },
  "tools": [{
    "name": "scale_selected_model",
    "description": "按百分比缩放当前选中的 3D 模型",
    "parameters": {
      "type": "object",
      "properties": { "percent": { "type": "number" } },
      "required": ["percent"]
    }
  }]
}

POST /sessions/sess_123/turns
Content-Type: application/json

{
  "stream": "delta",
  "messages": [{
    "role": "user",
    "content": "把当前选中的角色放大 20%"
  }]
}

Agent 通过 SSE 返回的并不是“它已经改好了”，而是一张待执行的操作单：

event: tool_call
data: {
  "toolCallId": "call_001",
  "name": "scale_selected_model",
  "input": { "percent": 120 }
}

event: turn_stop
data: { "stopReason": "tool_use" }

应用执行后，再把结果作为 tool 消息提交到同一个 sessionId，Agent 才会继续：

{
  "stream": "delta",
  "messages": [{
    "role": "tool",
    "toolCallId": "call_001",
    "content": "当前选中的角色已按 120% 缩放"
  }]
}

GET /sessions/:id/history 不在每一轮的正常链路里，主要用于应用重启、SSE 断线等恢复场景；DELETE /sessions/:id 则在用户结束对话或需要清理数据时调用。

请求 POST /sessions/:id/turns 可以指定三种返回方式：

  • delta：SSE 增量事件，适合聊天界面逐字输出。
  • message：仍然是 SSE，但按完整消息推送。
  • none：等待 Agent 完成后返回一份 JSON，适合后端服务调用。

服务端可以保持无状态地横向扩展，因为会话历史可以存到外部数据库或缓存中，而不是绑在某条常驻连接上。这里要准确一点：HTTP 服务器无状态，不等于会话没有状态。sessionId 对应的历史、工具配置和 Agent 配置仍需要持久化，只是任意实例都能从共享存储恢复它们。

最小可运行示例：一个应用怎样接入 AAP Agent

先说清这段代码的角色：它不是在实现 Agent，也不是在训练模型；它模拟的是“文档编辑器”这类业务应用。 远程 Agent 已经由 AAP 服务商部署好了，应用只需要按协议与它对话。

下面代码把上一节的流程真正串起来：

代码中的步骤 对应的协议动作 用人话说
request("/meta") 发现 Agent 问远程服务：“你提供哪些 Agent？”
POST /sessions 创建会话 选定一个 Agent，并告诉它应用有哪些可调用操作
POST /turns 发送用户任务 把“总结当前文档”交给 Agent
readSse() 接收流式回应 一边显示 Agent 的回答，一边监听它是否要求调用工具
executeApplicationTool() 应用侧执行工具 Agent 要读当前文档时，应用自己读取并回传结果

因此，读代码时只需要抓住一条主线：应用发任务 → Agent 请求工具 → 应用执行并回传 → Agent 给最终回答。

代码不依赖第三方包，要求 Node.js 20+（内置 fetch、ReadableStream）。它会发现 Agent、创建会话、发送一轮消息，并处理 SSE 中的文本和工具调用。

先设置服务地址和 API Key；如果服务端公开了 /meta，读取元数据时可以不带 Key，但这里统一带上：

export AAP_BASE_URL="https://api.example.com/v1"
export AAP_API_KEY="your-api-key"
node aap-client.mjs

/**
 * 应用端代码
 * 
 * 它模拟一个文档编辑器如何：
 *  连接远程 AAP Agent 服务；
 *  创建会话、发送用户任务；
 *  接收 Agent 的文本或工具调用请求；
 *  在应用侧执行 get_current_document；
 *  将结果回传给远程 Agent
*/
// aap-client.mjs

// 1. 应用配置：远程 AAP 服务的地址和访问凭证。
const baseUrl = process.env.AAP_BASE_URL;
const apiKey = process.env.AAP_API_KEY;

if (!baseUrl || !apiKey) {
  throw new Error("请设置 AAP_BASE_URL 和 AAP_API_KEY");
}

const headers = {
  Authorization: `Bearer ${apiKey}`,
  "Content-Type": "application/json",
};

// 2. 所有 AAP 请求都经过这里：补齐地址、认证头，并统一处理 HTTP 错误。
async function request(path, options = {}) {
  const response = await fetch(`${baseUrl}${path}`, {
    ...options,
    headers: { ...headers, ...options.headers },
  });

  if (!response.ok) {
    throw new Error(`${options.method ?? "GET"} ${path} 失败：${response.status}`);
  }
  return response;
}

// 3. 这是“文档编辑器应用”自己的能力，不属于远程 Agent。
//    真实项目中应在这里读取真实文档，并完成权限校验。
async function executeApplicationTool(name, input) {
  if (name === "get_current_document") {
    return JSON.stringify({ title: "方案草稿", selectedText: "AAP 协议评估" });
  }
  throw new Error(`应用不支持工具：${name}`);
}

// 4. Agent 的流式响应会从 SSE 到达。
//    遇到文本就显示；遇到 tool_call 就让应用执行对应工具，收集结果。
async function readSse(response) {
  const reader = response.body
    .pipeThrough(new TextDecoderStream())
    .getReader();
  let buffer = "";
  const toolResults = [];

  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += value;

    // SSE 事件以空行分隔；本示例只解析 AAP 所需的 event/data 字段。
    const chunks = buffer.split("\n\n");
    buffer = chunks.pop();

    for (const chunk of chunks) {
      const event = chunk.match(/^event: (.+)$/m)?.[1];
      const data = chunk.match(/^data: (.+)$/m)?.[1];
      if (!event || !data) continue;

      const payload = JSON.parse(data);
      if (event === "text_delta") process.stdout.write(payload.delta);
      if (event === "text") console.log(payload.text);
      if (event === "tool_call") {
        console.log(`\nAgent 请求工具：${payload.name}`);
        toolResults.push({
          role: "tool",
          toolCallId: payload.toolCallId,
          content: await executeApplicationTool(payload.name, payload.input),
        });
      }
      if (event === "turn_stop") return { stopReason: payload.stopReason, toolResults };
    }
  }

  throw new Error("SSE 流意外结束，未收到 turn_stop");
}

// 5. 发现远程服务提供的 Agent，并选用第一个。
const meta = await (await request("/meta")).json();
const agent = meta.agents[0];
if (!agent) throw new Error("服务端没有可用 Agent");

// 6. 创建会话，同时告诉 Agent：本应用允许它请求 get_current_document。
const { sessionId } = await (await request("/sessions", {
  method: "POST",
  body: JSON.stringify({
    agent: { name: agent.name },
    tools: [{
      name: "get_current_document",
      description: "读取当前编辑器中打开文档的必要上下文",
      parameters: { type: "object", properties: {} },
    }],
  }),
})).json();

// 7. 把用户任务交给 Agent；readSse 会实时打印它的文本或接收工具请求。
let result = await readSse(await request(`/sessions/${sessionId}/turns`, {
  method: "POST",
  body: JSON.stringify({
    stream: "delta",
    messages: [{ role: "user", content: "总结当前文档，并给出三个改进建议。" }],
  }),
}));

// 8. 如果 Agent 请求了应用侧工具，它会暂停。
//    现在把第 4 步收集到的工具执行结果提交回去，让它继续完成回答。
if (result.stopReason === "tool_use") {
  result = await readSse(await request(`/sessions/${sessionId}/turns`, {
    method: "POST",
    body: JSON.stringify({ stream: "delta", messages: result.toolResults }),
  }));
}

console.log(`\n\n本轮结束：${result.stopReason}`);

运行时，如果 Agent 不需要读取文档，你会直接看到它输出最终回答；如果它发出 get_current_document 请求，终端会先输出“Agent 请求工具：get_current_document”，应用回传文档摘要后，Agent 再继续生成回答。

这个示例故意把 executeApplicationTool 留在应用侧：协议不该替你跳过权限判断。生产环境还要补上 schema 校验、超时、工具结果大小限制、鉴权续期，以及 SSE 断线后的会话恢复。

AAP 与 MCP、ACP：该怎么选

AAP 官方把 ACP 定位为“IDE 连接本地编码 Agent”的协议；AAP 面向任何应用和远程 Agent，传输使用 HTTP + SSE。两者的目标并不冲突。

场景 更合适的选择 原因
给 Cursor、VS Code 一类 IDE 接本地编码 Agent ACP 协议目标就是 IDE 与 coding agent
给 Agent 接数据库、GitHub、文件系统、企业 API MCP 工具和资源互操作是它的核心职责
给业务后台、游戏引擎、设计软件接远程 Agent 服务 AAP 应用与 Agent 的职责边界最匹配
自己的单一 Web 产品里调用一个固定模型 直接调用模型 API 引入协议层未必有收益

实践里三者可以叠加：应用通过 AAP 调远程 Agent；Agent 通过 MCP 连接通用工具；如果应用本身是 IDE，再在适合的边界使用 ACP。关键不是“协议越多越先进”，而是每一层的替换和复用需求是否真实存在。

采用前要问的三个问题

第一，你真的需要“可替换 Agent”吗？如果 Agent 永远和单个产品同仓、同进程、同团队维护，直接调用 SDK 往往更低成本。AAP 的收益来自边界稳定后的复用，不来自第一天的代码量。

第二，应用侧工具是否足够小且明确？不要把“执行任意 SQL”“读取整个用户库”包装成一个万能工具。领域工具应该表达具体意图，例如 get_invoice_summary、create_draft_contract，并在应用侧执行授权。

第三，会话数据归谁、保存多久？AAP 提供会话接口，但不会替你解决数据保留、租户隔离、删除权和审计要求。远程 Agent 服务化之后，这些反而会成为上线前最先要厘清的边界。

小结

  1. AAP 连接的是 Application 与 Agent，不是替代 MCP 的工具协议。
  2. 应用保留 UI、领域工具与最终执行权；Agent 专注推理循环、上下文与通用能力。
  3. 应用侧工具通过 tool_call 停止并回传结果，服务端工具可按 trust 策略内联执行。
  4. AAP 基于 HTTP + SSE，使用 session 保存对话上下文，服务端可做无状态横向扩展。
  5. 适合远程、可复用的 Agent 服务；单体应用调用固定模型时，直接用模型 API 往往更简单。
