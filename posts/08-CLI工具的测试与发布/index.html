CLI 工具的测试与发布

发表于2026|更新于2026|工程化
|字数总计:2k|阅读时长:8分钟

前言：工具写好了、本地 npm link 也跑通了，最后一步是把它交出去：怎么测试保证它真能用，怎么发布到 npm 让别人 npm install -g 或 npm create 就能用。这一篇收尾整个阶段，讲 CLI 的测试策略和发布全流程，以及发布里那些一不小心就翻车的坑。

CLI 怎么测：分层测，别只测整体

CLI 测试最容易犯的错是「只想着端到端跑一遍命令」。端到端测试有用，但慢、脆、定位难。更好的策略是分层，这也呼应上一篇的分层架构：

层 测什么 怎么测
核心逻辑 纯函数：路径计算、占位符替换、包管理器识别 单元测试，最多最快
文件生成 给定 context，生成的目录/文件对不对 在临时目录跑核心函数，断言产物
端到端 完整命令跑通 子进程执行真实命令，断言退出码和输出

核心逻辑能拆成纯函数测，正是上一篇「核心层只认 context」的回报。下面用 vitest 举例（前面工程化篇用的测试框架，这里直接复用）。

单元测试：纯函数

把不依赖文件系统的逻辑抽成纯函数，测起来最爽：

// src/utils.ts
export function detectPackageManager(ua = process.env.npm_config_user_agent || '') {
  if (ua.startsWith('pnpm')) return 'pnpm'
  if (ua.startsWith('yarn')) return 'yarn'
  return 'npm'
}

export function render(tpl: string, data: Record<string, string>) {
  return tpl.replace(/\{\{(\w+)\}\}/g, (_, k) => data[k] ?? '')
}

// src/utils.test.ts
import { describe, it, expect } from 'vitest'
import { detectPackageManager, render } from './utils'

describe('detectPackageManager', () => {
  it('识别 pnpm', () => {
    expect(detectPackageManager('pnpm/9.0.0 npm/?')).toBe('pnpm')
  })
  it('默认 npm', () => {
    expect(detectPackageManager('')).toBe('npm')
  })
})

describe('render', () => {
  it('替换占位符', () => {
    expect(render('name: {{name}}', { name: 'app' })).toBe('name: app')
  })
})

文件生成测试：用临时目录

测「生成文件」时，关键是用系统临时目录，每次测完清理，别污染项目：

import { describe, it, expect, afterEach } from 'vitest'
import { mkdtemp, rm, readFile } from 'node:fs/promises'
import { tmpdir } from 'node:os'
import path from 'node:path'
import { runCreate } from './core'

let dir: string
afterEach(async () => {
  if (dir) await rm(dir, { recursive: true, force: true })
})

it('生成 package.json 且项目名正确', async () => {
  // 在系统临时目录建一个隔离的测试目录
  dir = await mkdtemp(path.join(tmpdir(), 'mycli-'))

  await runCreate({
    projectName: 'demo',
    targetDir: dir,
    template: 'vue',
    useTs: true,
    install: false, // 测试里别真去装依赖，太慢
    git: false,
  })

  const pkg = JSON.parse(await readFile(path.join(dir, 'package.json'), 'utf-8'))
  expect(pkg.name).toBe('demo')
})

注意 install: false：单测里绝不真跑 npm install，又慢又依赖网络。子进程相关的逻辑要么 mock 掉，要么留给端到端测试。

端到端测试：跑真实命令

最外层验证「构建产物能不能跑」，用 execa 调用打包后的 CLI：

import { execa } from 'execa'

it('--version 输出版本号', async () => {
  const { stdout } = await execa('node', ['dist/index.js', '--version'])
  expect(stdout).toMatch(/\d+\.\d+\.\d+/)
})

端到端测试要测的是构建产物（dist/），不是源码——因为用户最终跑的是产物。所以这类测试要在 build 之后跑。

发布前：package.json 关键字段

发布翻车，十有八九是 package.json 没配对。逐个过一遍发布相关的关键字段：

{
  "name": "create-my-app",
  "version": "1.0.0",
  "type": "module",
  "bin": {
    "create-my-app": "dist/index.js"
  },
  "files": ["dist", "templates"],
  "engines": {
    "node": ">=18"
  },
  "publishConfig": {
    "access": "public"
  }
}

逐个说清楚每个字段的坑：

  • **bin**：命令名 → 入口产物。这里指向 dist/index.js（构建产物），不是 src。入口文件第一行必须有 shebang（第一篇讲过），否则装上后敲命令没反应。
  • files：白名单，决定哪些文件被打进 npm 包。模板目录 templates 必须列进来，否则用户装了却没有模板。dist 同理。这是发布后「本地能跑、装了用户那报找不到模板」的头号原因。
  • **engines**：声明支持的 Node 版本，用户 Node 太旧时给警告。
  • **publishConfig.access**：发布 scoped 包（@org/xxx）时，要显式设 public 才能公开发布，否则默认私有会报错。
  • **type: module**：ESM 工具必写，和构建产物格式对齐。

用 npm pack 预演，别盲发

发布前一定要确认「到底打了哪些文件进去」。npm pack --dry-run 不真发布，只列出会被打包的文件：

npm pack --dry-run

npm notice 📦  create-my-app@1.0.0
npm notice Tarball Contents
npm notice 1.2kB  dist/index.js
npm notice 3.4kB  templates/vue/package.json
npm notice ...

盯着这个列表看：模板在不在？有没有误打 src、测试文件、.env？这一步能拦下绝大多数发布事故。

坑点：files 字段和 .npmignore / .gitignore 的关系很容易搞混。优先用 files 白名单（明确列要发什么），比 .npmignore 黑名单更可控、更不容易漏。无论哪种，发布前都用 npm pack --dry-run 实际验证一遍，别凭感觉。

发布流程

确认无误后，标准发布流程：

# 1. 构建产物
npm run build

# 2. 登录（首次）
npm login

# 3. 发布
npm publish

如果发布的是 scoped 包又想公开：

npm publish --access public

发布前自动构建，可以挂在 prepublishOnly 钩子上，避免忘记 build 就发了空壳包：

{
  "scripts": {
    "build": "tsup src/index.ts --format esm --clean",
    "prepublishOnly": "npm run build && npm test"
  }
}

prepublishOnly 会在 npm publish 前自动执行——构建 + 跑测试都过了才允许发布，这是一道很值的保险。

版本管理：用 changesets 而不是手改

发布不是一锤子买卖，后续要持续迭代。手动改 version、写 CHANGELOG 很容易乱，尤其多人协作或 monorepo。社区主流方案是 changesets：

npm i -D @changesets/cli
npx changeset init

工作流大致是：

# 开发完一个改动，记录一条 changeset（选 patch/minor/major + 写说明）
npx changeset

# 发布时：根据累积的 changeset 自动升版本号 + 生成 CHANGELOG
npx changeset version

# 再发布
npx changeset publish

changesets 的价值在于把「这次改动该升什么版本」这件事，从「发布时拍脑袋」变成「开发时就记录」，版本号和 CHANGELOG 都自动算出来。monorepo 里管理多个包发布时尤其离不开它。单包小工具可以先手动管版本，包变多了再上 changesets。

版本号遵循语义化版本（SemVer）：major.minor.patch。破坏性变更升 major，加功能升 minor，修 bug 升 patch。CLI 工具的「破坏性变更」包括改命令名、删选项、改默认行为——这些都会影响用户脚本，别当小改动随便发。

让用户能 npm create 使用

最后一个实用知识点：npm create xxx / npm init xxx 其实是 npx create-xxx 的语法糖。只要你的包名叫 create-xxx，用户就能用：

npm create my-app
# 等价于 npx create-my-app

所以做项目初始化类脚手架，包名约定用 create- 前缀（如 create-vite、create-next-app），用户用起来最自然。这是个命名约定，不是技术限制，但遵守它体验会好很多。

小结

  1. CLI 测试要分层：纯函数单测最多最快，文件生成用临时目录隔离，端到端跑真实产物命令。
  2. 单测里别真跑 npm install / git，mock 或跳过子进程，留给端到端测试。
  3. 发布前过一遍 package.json：bin 指向产物且带 shebang，files 务必包含 templates。
  4. 发布前用 npm pack --dry-run 预演，确认打包内容，拦下「漏发模板」这类事故。
  5. 用 prepublishOnly 钩子自动构建 + 测试，避免发出空壳或没测过的包。
  6. 版本管理用 changesets，开发时记录改动、发布时自动升版本和生成 CHANGELOG，遵循 SemVer。
  7. 项目初始化类工具包名用 create- 前缀，用户即可通过 npm create xxx 使用。
