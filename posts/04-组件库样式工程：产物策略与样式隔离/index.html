组件库样式工程：产物策略与样式隔离

发表于2026|更新于2026|工程化
|字数总计:2.3k|阅读时长:7分钟

前言：CSS 方案怎么选（CSS Modules、Sass、原子化、CSS-in-JS）在「CSS 工程化」那两篇讲过，那是站在「写应用」的角度。这一篇换个角度：站在「发一个组件库」的角度，样式该怎么产出、怎么让用户拿到、怎么保证不污染用户的页面。同样是 CSS-in-JS，用在自己应用里和打包进组件库发出去，考量是完全不同的。

组件库的样式，难在「发出去」

写应用时，样式就在自己项目里，构建工具全权处理，你不太需要操心「样式最终长什么样」。但组件库不一样——你的样式要打包成产物，装进别人的项目，在你无法预知的构建环境里跑。

这带来几个应用开发不会遇到的问题：

  • 用户可能用 Vite，也可能用 webpack，还可能不用构建工具；
  • 用户可能想要全量样式，也可能想按需只要用到的组件样式；
  • 你的类名不能和用户页面的类名撞车；
  • 用户想换主题色、切暗色，你得留出口子。

所以组件库的样式工程，核心是两件事：产物策略（样式以什么形态交付）和样式隔离（怎么不污染、能定制）。

样式产物策略：四种交付形态

用户拿到你的组件库样式，无非这么几种形态，各有取舍。

策略一：全量 CSS 单文件

最简单：把所有组件样式打成一个 dist/style.css，用户手动引一次。

import '@my-ui/components/style.css'
import { Button } from '@my-ui/components'
优点 缺点
实现简单，用户一行引入 用一个组件也加载全部样式
不依赖用户构建能力 无法按需
兼容任何环境 首屏 CSS 偏大

适合：组件不多的小型库、追求接入简单、或用户本来就会用到大部分组件的场景。

策略二：按组件 CSS

每个组件一个独立 CSS 文件，配合上一篇的 subpath exports 和 sideEffects，实现样式也按需。

dist/
├── button/style.css
├── table/style.css
└── ...

用户通过 unplugin 自动引入，或库内部在组件模块里 import './style.css'（靠 sideEffects 保留用到的那份）。这是主流组件库的做法，样式随组件按需，产物最优。

代价是构建复杂度上来了：要拆分样式产物、要保证每个组件的样式文件独立、要处理组件间共享的基础样式（如 reset、公共变量）单独成一份。

策略三：运行时 CSS-in-JS

styled-components、Emotion 这类，样式写在 JS 里，运行时生成类名注入 <style>。

用在应用里争议就不小（性能、SSR 成本，见 CSS 进阶那篇）。用在组件库里，问题被放大：

  • 用户被迫接受运行时开销和 styled-components 的运行时依赖；
  • SSR 场景下样式抽取更复杂，用户还得配你的 SSR 集成；
  • 用户想覆盖样式，得懂你的 CSS-in-JS 方案。

我的判断很直接：新做组件库，不建议用运行时 CSS-in-JS。它把运行时成本强加给了所有用户，而组件库恰恰应该尽量「零运行时」。

策略四：零运行时 CSS（推荐方向）

零运行时 CSS-in-JS 既保留了「用 JS/TS 写样式、类型安全、和 token 联动」的开发体验，又在构建时把样式编译成静态 CSS，用户拿到的就是普通 CSS 文件，没有任何运行时。代表方案：

方案 特点
Vanilla Extract 用 TS 写样式（.css.ts），构建时生成静态 CSS 和类名，类型安全、和 token 强联动
PandaCSS 零运行时，支持原子化 + 语义 token，配方（recipe）能力强

以 Vanilla Extract 为例，感受一下：

// button.css.ts
import { style } from '@vanilla-extract/css'
import { vars } from '../theme/vars.css.ts'   // 主题 token

export const button = style({
  padding: '8px 16px',
  borderRadius: vars.radius.md,
  color: vars.color.textOnPrimary,
  backgroundColor: vars.color.primary,
})

import { button } from './button.css.ts'
export const Button = (props) => <button class={button}>{props.children}</button>

这里的 button.css.ts、vars.css.ts 都是 TypeScript 文件，不是普通 CSS 文件。.css.ts 是 Vanilla Extract 的约定：开发时写 TS，构建时再生成真实的静态 CSS。

构建后，button.css.ts 变成一段静态 CSS + 一个哈希类名，运行时零成本。它同时解决了作用域隔离（类名哈希，和 CSS Modules 一样）、类型安全（token 是 TS 常量，写错编译报错）、按需（跟着组件模块走）。

我的判断：如果做一个偏「设计系统」的现代组件库，Vanilla Extract / PandaCSS 这类零运行时方案是当前最优解；如果做通用业务组件库、要兼容各种老环境，「按组件 CSS（Sass/CSS Modules 编译产出）」更稳、接入门槛更低。

样式隔离：不污染 + 可定制的平衡

样式隔离在组件库里是个矛盾体：隔离得太死，用户没法定制；不隔离，又会污染用户页面。好的方案要在两者间找平衡。

类名前缀 + scope class

最基础也最有效的隔离手段：所有类名带统一前缀（BEM 风格的命名空间）。

.myui-button { /* ... */ }
.myui-button--primary { /* ... */ }
.myui-button__icon { /* ... */ }

前缀（如 myui-）保证不和用户的 .button 撞车。这是 Element Plus、Ant Design 的做法。前缀最好可配置，方便用户在多套组件库共存时避免冲突。

如果用 CSS Modules 或零运行时方案，类名本身就是哈希的，天然隔离，但代价是用户没法通过类名覆盖样式——所以纯哈希方案通常要配合 CSS 变量留定制口子（下面讲）。

CSS Variable Token：隔离与定制的最佳结合点

这是组件库样式工程里最关键的设计：用 CSS 变量（自定义属性）承载可定制的值，用固定类名承载结构样式。

.myui-button {
  /* 结构样式：固定，不给改 */
  display: inline-flex;
  align-items: center;
  padding: var(--myui-button-padding, 8px 16px);
  border-radius: var(--myui-radius-md, 6px);

  /* 主题相关：走 CSS 变量，用户可覆盖 */
  color: var(--myui-color-text-on-primary, #fff);
  background: var(--myui-color-primary, #1677ff);
}

这样设计的好处是巨大的：

  1. 用户定制不需要覆盖你的类名，只要重定义 CSS 变量：
:root {
  --myui-color-primary: #7c3aed;   /* 换成品牌紫 */
  --myui-radius-md: 12px;          /* 圆角调大 */
}
  1. 暗色模式、多主题只是换一组变量值，组件代码一行不用改（下一篇设计系统会展开）；
  2. 样式仍然隔离，因为用户改的是变量值，不是你的选择器，不会破坏组件内部结构。

组件库所有和主题相关的值（颜色、圆角、间距、字号、阴影）都走 CSS 变量，结构性样式用固定类名。这是现代组件库（Ant Design 5 的 CSS 变量模式、Radix、shadcn 体系）的共识，也是和主题系统对接的地基。

:where() 降低选择器权重，让用户好覆盖

一个进阶但很实用的技巧：组件库的基础样式用 :where() 包一层，把选择器权重降到 0，用户覆盖时不用打权重仗。

/* 权重为 0，用户一个普通类就能覆盖 */
:where(.myui-button) {
  background: var(--myui-color-primary);
}

不用 :where() 时，用户想覆盖你的样式常常得写更高权重的选择器甚至 !important，体验很差。:where() 让「库提供默认、用户轻松覆盖」成为默认体验。这是近几年组件库样式设计的一个明显趋势。

一个务实的组件库样式方案

把上面的取舍收敛成一个我认为稳妥的默认组合：

写法      →  Sass + CSS Modules  或  Vanilla Extract（偏设计系统时）
隔离      →  统一类名前缀 + :where() 降权
定制      →  主题相关值全部走 CSS 变量（token）
产物      →  按组件拆分 CSS + 一份全量 style.css 兜底
副作用    →  sideEffects 里保留 *.css（见上一篇）

两份产物都提供：让能按需的用户按需（按组件 CSS + unplugin），让图省事的用户一行全量引入（style.css）。用户体验和工程灵活性都照顾到。

小结

  1. 组件库样式的核心难点是「发出去」：要打包成产物、进别人项目、在未知构建环境跑。
  2. 产物策略四选：全量 CSS（简单不按需）、按组件 CSS（主流、可按需）、运行时 CSS-in-JS（不推荐进库）、零运行时 CSS（Vanilla Extract/PandaCSS，现代设计系统优选）。
  3. 运行时 CSS-in-JS 会把运行时成本强加给所有用户，组件库应尽量零运行时。
  4. 样式隔离靠统一类名前缀，避免和用户页面撞车，前缀最好可配置。
  5. 主题相关值全部走 CSS 变量（token），结构样式用固定类名——这是隔离与定制的最佳结合点，也是对接主题系统的地基。
  6. 用 :where() 给基础样式降权，让用户不用打权重仗就能覆盖，是现代组件库的默认体验。
  7. 务实默认：Sass+CSS Modules（或 Vanilla Extract）+ 类名前缀 + CSS 变量定制 + 按组件拆分 CSS 并附一份全量兜底。
