Claude Code Settings 全解析：个人、项目、团队、企业配置怎么分层

发表于2026|更新于2026|AI相关
|字数总计:3.6k|阅读时长:14分钟

前言：前面我写过 CLAUDE.md、权限系统、Hooks、Skills、MCP，但这些能力真正落地时，最后都会回到一个问题：配置到底放哪里？个人配置、项目配置、团队配置、企业配置怎么分层？ 这篇就专门把 Claude Code 的 Settings 配置体系讲清楚。

为什么要单独讲 Settings

很多人第一次用 Claude Code，会把所有规则都往 CLAUDE.md 里塞。

比如：

- 不要读取 .env
- 不要执行 git push
- 默认用中文回答
- 保存前运行 npm test
- 使用某个 MCP server

这其实混在一起了。

CLAUDE.md 是写给模型看的“工作说明书”，而 Settings 是 Claude Code 客户端真正执行的“运行配置”。

两者区别很关键：

维度 CLAUDE.md Settings
本质 提示词上下文 客户端配置
作用对象 影响 Claude 怎么想 控制 Claude Code 怎么运行
是否强制 不强制，模型可能忘 更强制，客户端执行
适合内容 项目规范、开发习惯、上下文 权限、环境变量、Hooks、MCP、插件、企业策略
风险控制 提醒为主 管控为主

我的判断是：**CLAUDE.md 管“认知”，Settings 管“行为边界”。**

如果你要告诉 Claude：“这个项目用 pnpm”，写进 CLAUDE.md 很合适。

如果你要禁止 Claude 读取 .env，就应该写进 Settings 的 permissions.deny。

Claude Code 的四层配置作用域

Claude Code 官方文档把配置分成几个 scope。理解这个 scope，是理解 Settings 的第一步。

Scope 典型位置 影响范围 是否适合提交 Git
Managed 企业托管配置 / MDM / 系统目录 机器上所有用户 由企业 IT 管理
User ~/.claude/settings.json 当前用户所有项目 不提交
Project .claude/settings.json 当前仓库所有协作者 可以提交
Local .claude/settings.local.json 当前仓库当前用户 不提交

可以这样理解：

企业策略 Managed
  │ 最高优先级，用户不能覆盖
  ▼
命令行参数
  │ 当前会话临时覆盖
  ▼
本地项目 Local
  │ 当前项目里自己的私有偏好
  ▼
项目共享 Project
  │ 团队共享配置
  ▼
用户全局 User
     最低优先级，个人默认配置

它解决的是一个很现实的问题：同一套 Claude Code，既要支持个人自由定制，也要支持团队协作，还要支持企业安全管控。

User Settings：个人全局配置

个人配置放在：

~/.claude/settings.json

适合放这些东西：

  • 个人默认语言；
  • 默认权限模式；
  • 常用环境变量；
  • 个人常用 MCP；
  • 个人常用插件；
  • UI 偏好；
  • 是否开启某些功能。

一个典型例子：

{
  "language": "chinese",
  "permissions": {
    "defaultMode": "acceptEdits",
    "deny": [
      "Read(//**/.env)",
      "Bash(git push *)"
    ]
  },
  "env": {
    "CLAUDE_CODE_ENABLE_AWAY_SUMMARY": "1"
  }
}

这里有两个点值得注意。

第一，~/.claude/settings.json 是个人所有项目都生效的，所以不要写太具体的项目路径。

第二，全局 deny 规则会影响所有项目。比如你全局禁止 git push，那每个项目里 Claude 都不能直接 push，这通常是好事。

Project Settings：团队共享配置

项目配置放在：

.claude/settings.json

它适合提交到仓库，让团队成员共享。

适合放：

  • 项目级权限规则；
  • 项目级 Hooks；
  • 项目级插件；
  • 团队认可的 MCP 配置入口；
  • 项目需要的环境变量默认值；
  • 团队统一的工作流开关。

例如：

{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(git push *)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npm run lint -- --fix",
            "timeout": 120
          }
        ]
      }
    ]
  }
}

这个配置表达的意思是：

  1. Claude 可以直接跑 npm run lint；
  2. Claude 可以跑带参数的测试命令；
  3. Claude 不允许读 .env 和 secrets；
  4. Claude 不允许直接 git push；
  5. 每次编辑文件后自动跑 lint fix。

这类配置适合团队共享，因为它体现的是项目工程约定。

Local Settings：项目里的个人私有配置

本地配置放在：

.claude/settings.local.json

它通常会被 git ignore，不应该提交。

适合放：

  • 本机路径；
  • 个人测试环境；
  • 临时实验配置；
  • 当前项目里自己的权限偏好；
  • 不适合团队共享的本地工具。

比如：

{
  "env": {
    "LOCAL_API_BASE": "http://localhost:3000"
  },
  "permissions": {
    "allow": [
      "Bash(open http://localhost:3000)",
      "Bash(npm run dev)"
    ]
  }
}

这里的 LOCAL_API_BASE、open 命令都很依赖个人机器，放进团队配置就不合适。

我的建议是：凡是“换一台机器可能就不能用”的配置，都放 Local。

Managed Settings：企业级管控

企业级配置是 Claude Code Settings 里最容易被个人开发者忽略，但在团队落地时最重要的一层。

它可以来自：

  • Anthropic 服务端下发的 server-managed settings；
  • macOS MDM / plist；
  • Windows Registry / Group Policy / Intune；
  • 系统目录下的 managed-settings.json；
  • Linux / WSL 的 /etc/claude-code/managed-settings.json；
  • macOS 的 /Library/Application Support/ClaudeCode/managed-settings.json；
  • Windows 的 C:\Program Files\ClaudeCode\managed-settings.json。

Managed 的关键特点是：优先级最高，用户和项目不能覆盖。

例如企业可以统一禁止绕过权限模式：

{
  "permissions": {
    "disableBypassPermissionsMode": "disable",
    "deny": [
      "Read(//**/.env)",
      "Read(//**/id_rsa)",
      "Bash(git push --force *)"
    ]
  }
}

也可以禁止动态工作流：

{
  "disableWorkflows": true
}

或者要求只允许企业批准的 MCP server：

{
  "allowManagedMcpServersOnly": true,
  "allowedMcpServers": [
    { "serverName": "github" },
    { "serverName": "jira" }
  ]
}

这不是给个人玩家准备的，而是给“公司要让几百个工程师用 AI Coding 工具”准备的。

配置优先级怎么理解

官方文档里的优先级大致是：

Managed settings
  > 命令行参数
  > Local project settings
  > Shared project settings
  > User settings

比如你有三个配置：

// ~/.claude/settings.json
{
  "language": "english"
}

// .claude/settings.json
{
  "language": "chinese"
}

// .claude/settings.local.json
{
  "language": "japanese"
}

最终当前项目里生效的是 local 里的 japanese。

但如果企业 Managed 写了：

{
  "language": "chinese"
}

那 Managed 优先，用户不能覆盖。

这里要注意一个细节：不是所有配置都是“高优先级覆盖低优先级”。

很多数组配置会合并，比如：

  • permissions.allow；
  • permissions.deny；
  • sandbox 的路径配置；
  • 某些 allowlist / denylist。

更准确地说：

配置类型 行为
标量值 高优先级覆盖低优先级
对象 深度合并或按字段覆盖
数组 通常拼接、去重
权限规则 deny -> ask -> allow，deny 优先

所以看到 Settings 不生效时，不要只想“是不是被覆盖了”，也要考虑“是不是被合并了”。

Settings 里最常用的几类配置

Claude Code 的 Settings 项非常多，不需要一开始全背。

我建议先掌握这几类。

1. permissions：权限边界

这是最重要的一类。

{
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "Bash(npm run test *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Read(./.env)",
      "Bash(git push *)"
    ]
  }
}

核心规则：

deny > ask > allow

也就是说，只要某个操作被 deny 命中，就不能靠 allow 放回来。

我的建议是：

  • 对危险操作用 deny；
  • 对常用安全操作用 allow；
  • 对“可能需要但要看情况”的操作用 ask。

2. env：环境变量

env 会注入到 Claude Code 会话和它启动的子进程中。

{
  "env": {
    "NODE_ENV": "development",
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1"
  }
}

适合放项目级默认环境变量，但不建议放密钥。

密钥更应该走系统 keychain、专门的 credential helper，或者 MCP server 自己的认证机制。

3. hooks：生命周期自动化

Hooks 可以让 Claude Code 在某些事件发生时自动执行逻辑。

比如编辑文件后跑格式化：

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "npm run format",
            "timeout": 120
          }
        ]
      }
    ]
  }
}

但 Hooks 有副作用，放团队配置前要谨慎。

我的建议是：

  • 检查类 Hook 可以团队共享；
  • 自动修改类 Hook 先放 local 验证；
  • 会访问网络或密钥的 Hook 不要随便进仓库。

4. disableWorkflows：关闭动态工作流

动态工作流很强，但也可能带来 token 和资源消耗。

如果团队暂时不想启用：

{
  "disableWorkflows": true
}

或者用环境变量：

CLAUDE_CODE_DISABLE_WORKFLOWS=1

这个配置很适合企业或团队早期试点阶段使用。

5. skillOverrides：控制 Skill 可见性

当项目里 Skill 很多时，Skill 列表本身也会占上下文。

可以用 skillOverrides 控制：

{
  "skillOverrides": {
    "legacy-deploy": "off",
    "old-review": "name-only",
    "dangerous-prod-deploy": "user-invocable-only"
  }
}

常见值包括：

值 含义
on 正常可见可调用
name-only 只保留名字，减少描述占用
user-invocable-only 只能用户手动调用
off 关闭

这对大型团队很有价值，因为 Skill 多了之后，治理比创建更重要。

6. worktree：并行开发隔离

Claude Code 的后台 Agent、动态工作流、子 Agent 隔离都可能用到 worktree。

常见配置：

{
  "worktree": {
    "baseRef": "head",
    "symlinkDirectories": ["node_modules"],
    "sparsePaths": ["packages/app", "shared"],
    "bgIsolation": "worktree"
  }
}

含义：

  • baseRef：新 worktree 从哪里分支；
  • symlinkDirectories：哪些大目录用软链，避免重复复制；
  • sparsePaths：大仓库里只 checkout 部分目录；
  • bgIsolation：后台任务是否用 worktree 隔离。

这块后面可以单独写一篇，因为它关系到 AI 并行改代码的工程安全。

Settings、CLAUDE.md、Rules、Skills 怎么分工

这几个概念很容易混。

我的建议是按下面这张表分工：

需求 放哪里
项目怎么启动、怎么测试 CLAUDE.md 或 .claude/rules/
代码风格、目录约定 CLAUDE.md 或 .claude/rules/
禁止读 .env Settings permissions.deny
禁止执行危险命令 Settings permissions.deny 或 Hook
编辑后自动 lint Settings hooks
某类任务的操作手册 Skills
外部工具和数据源 MCP 配置
企业统一安全策略 Managed Settings
个人偏好 User Settings
本机私有路径 Local Settings

一句话总结：

规则写给 Claude 看，配置写给 Claude Code 执行。

一个推荐的项目配置结构

如果我是从零给一个团队项目接入 Claude Code，我会这么组织：

project/
├── CLAUDE.md
├── .claude/
│   ├── settings.json
│   ├── rules/
│   │   ├── code-style.md
│   │   ├── testing.md
│   │   └── security.md
│   ├── skills/
│   │   ├── review-pr/
│   │   │   └── SKILL.md
│   │   └── run-app/
│   │       └── SKILL.md
│   └── workflows/
│       └── triage-issues.js
├── .mcp.json
└── .gitignore

其中：

  • CLAUDE.md 放最核心的项目说明；
  • .claude/rules/ 拆分具体规则；
  • .claude/settings.json 放团队共享的权限、Hook、插件设置；
  • .claude/settings.local.json 不提交，给个人覆盖；
  • .mcp.json 放项目共享 MCP server；
  • .claude/skills/ 放团队复用工作流；
  • .claude/workflows/ 放可复用动态工作流。

这样结构清晰，也方便团队 Review。

一个比较完整的团队配置示例

下面这个示例适合前端项目做起步配置：

{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)",
      "Bash(npm run typecheck)",
      "Read(./package.json)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Bash(git push *)",
      "Bash(rm -rf *)"
    ]
  },
  "env": {
    "NODE_ENV": "development"
  },
  "worktree": {
    "bgIsolation": "worktree",
    "symlinkDirectories": ["node_modules"]
  },
  "skillOverrides": {
    "deploy-production": "user-invocable-only"
  }
}

这里我的取舍是：

  1. 测试、lint、typecheck 直接允许；
  2. commit 需要确认；
  3. push 和危险删除禁止；
  4. .env 和 secrets 禁止读取；
  5. 后台任务默认 worktree 隔离；
  6. 生产部署 Skill 只能用户手动调用。

这就是一个比较稳的团队起点。

常见误区

误区一：把安全要求写进 CLAUDE.md

比如：

不要读取 .env 文件

这只是提醒，不是强制。

更可靠的写法是：

{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)"]
  }
}

如果是企业环境，还应该放到 Managed Settings。

误区二：把本地配置提交到团队仓库

比如：

{
  "env": {
    "DATABASE_URL": "postgres://localhost:5432/mydb"
  }
}

如果这是你个人机器的数据库，就不应该进 .claude/settings.json。

应该放：

.claude/settings.local.json

误区三：全局 allow 太宽

比如：

{
  "permissions": {
    "allow": ["Bash"]
  }
}

这等于给所有 Bash 命令开绿灯，不建议。

更好的方式是按命令白名单：

{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git diff *)",
      "Bash(git status *)"
    ]
  }
}

误区四：忽略项目级配置的供应链风险

.claude/settings.json 是仓库里的文件。

如果你 clone 一个陌生仓库，它可能带着自己的 Claude Code 配置。

因此对项目级配置要有 trust 意识，尤其是：

  • hooks；
  • MCP server；
  • plugin；
  • dynamic command；
  • skill 里的 shell execution。

我的建议是：陌生仓库先用 plan mode 或默认权限，不要一上来 bypass。

我的配置建议

如果你是个人开发者：

  1. 在 ~/.claude/settings.json 里放通用偏好；
  2. 全局 deny .env、私钥、危险 git 操作；
  3. 每个项目用 CLAUDE.md 写清启动、测试、风格；
  4. 本地私有东西放 .claude/settings.local.json。

如果你是团队负责人：

  1. 把 .claude/settings.json 纳入代码评审；
  2. 权限规则尽量最小化；
  3. 高风险 Hooks 不要直接共享；
  4. 团队共享 Skill 要有 owner；
  5. MCP server 尽量区分 project 和 user scope。

如果你是企业管理员：

  1. 用 Managed Settings 定义不可突破的安全边界；
  2. 禁用 bypassPermissions 或限制使用环境；
  3. 管控 MCP server 和 plugin marketplace；
  4. 对 Hooks、Skills、Agents、MCP 做供应链治理；
  5. 配合用量统计和审计能力看整体使用情况。

小结

  1. CLAUDE.md 是提示词上下文，Settings 是 Claude Code 的运行配置，两者职责不同。
  2. Claude Code Settings 分为 Managed、User、Project、Local 四层，Managed 优先级最高。
  3. 个人偏好放 User，团队共享规则放 Project，本机私有配置放 Local，企业强制策略放 Managed。
  4. 安全边界不要只写进 CLAUDE.md，应使用 permissions.deny、Hooks、Sandbox 或 Managed Settings。
  5. Settings 的核心价值不是“多几个配置项”，而是让 AI Coding 从个人工具变成可治理的工程系统。
