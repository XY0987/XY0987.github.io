性能门禁：Lighthouse CI 与 Performance Budget

发表于2026|更新于2026|工程化
|字数总计:3.6k|阅读时长:11分钟

前言：上一篇讲清了性能指标。但指标如果只是「偶尔手动测一下」，性能一定会慢慢劣化——每个人都加一点点代码、一张图，日积月累就胖了，谁也说不清是哪次变慢的。这一篇讲怎么把性能变成流水线里的自动门禁：Web 应用可以用 Lighthouse CI 和 Performance Budget，小程序、跨端、原生应用也要有自己的首屏、包体积、帧率、崩溃率门禁，让「性能倒退」像「测试失败」一样被自动拦住。

性能会「熵增」，所以需要门禁

一个残酷的现实：性能是会自然劣化的。没有约束的话，代码库的性能几乎总是随时间变差——因为「加功能」有明确的推动力，「保持轻快」没人负责。每个 PR 加一个库、一张图、几个组件，单看都无所谓，累积起来就是首屏从 1.5s 变成 5s。

而且性能倒退很难在 review 时发现——diff 里看不出「这个 import 会让包大 300KB」。等用户投诉慢了再回头查，已经积重难返，根本定位不到是哪次改动引入的。

解法和代码质量一样：把它变成自动化门禁，卡在合并入口。这和《CI 流水线与质量强约束闸口》是同一个哲学——靠自觉守不住，得靠机器在 PR 上自动拦。

Web 应用最常见的门禁分两层：Lighthouse CI（跑综合评分和实验室指标）和 Performance Budget（卡具体的体积/资源阈值）。其他端也类似，只是工具换了：小程序看启动和包体积，跨端看首帧和掉帧，原生看冷启动、帧率、崩溃和 ANR。

Lighthouse CI：把性能评分接进流水线

Lighthouse 就是 Chrome DevTools 里那个「跑一下给你打分」的工具。Lighthouse CI（@lhci/cli）是它的自动化版本——在 CI 里对构建产物跑 Lighthouse，拿到性能/可访问性/最佳实践/SEO 的分数和各项指标，不达标就让流水线失败。

pnpm add -D @lhci/cli

配置 lighthouserc.js：

export default {
  ci: {
    collect: {
      staticDistDir: './dist',   // 对构建产物起本地服务跑
      numberOfRuns: 3,           // 跑多次取中位数，减少波动
    },
    assert: {
      assertions: {
        // 分类总分门槛
        'categories:performance': ['error', { minScore: 0.9 }],
        'categories:accessibility': ['error', { minScore: 0.9 }],
        // 具体指标门槛（实验室数据）
        'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
        'cumulative-layout-shift': ['warn', { maxNumericValue: 0.1 }],
      },
    },
    upload: { target: 'temporary-public-storage' },  // 报告存到临时公共空间
  },
}

接进 CI：

      - run: pnpm build
      - run: npx lhci autorun    # collect → assert → upload

几个关键设计点：

numberOfRuns: 3 取中位数：Lighthouse 单次跑波动不小（CI 机器负载、网络抖动都影响）。跑多次取中位数是标配，否则门禁会因为随机波动误报，很快被团队当成「又抽风了」而忽略。

error vs warn 分级：核心指标（性能总分、LCP）用 error（挂了阻断合并），次要的用 warn（只提醒不阻断）。这个分级和依赖 audit 的分级思路一样——门禁只在真正重要的地方卡死，否则噪音多了大家就学会无视它了。

LCP/INP 的局限：上一篇说过，Lighthouse 是实验室数据，INP/CLS 测不准。所以 Lighthouse CI 门禁重点卡 LCP、总分、包体积这些实验室能稳定测的，INP/CLS 的真实情况靠 RUM 监控盯（监控篇）。别指望 Lighthouse CI 帮你守住 INP。

Performance Budget：给资源设「预算」

Lighthouse 给的是「综合评分」，比较宏观。更直接、更好守的是 Performance Budget（性能预算）——给具体的资源指标设硬阈值：

JS 总体积      ≤ 300 KB (gzip)
CSS 总体积     ≤ 80 KB
单张图片       ≤ 200 KB
请求总数       ≤ 50
首屏字体       ≤ 2 个

预算的价值在于它是具体、可执行、好定位的。「性能分低了」很抽象，「JS 超了 300KB 预算」很具体——一看就知道是这次 PR 加的某个大依赖，改起来有明确目标。

Lighthouse CI 支持直接配预算文件 budget.json：

[
  {
    "resourceSizes": [
      { "resourceType": "script", "budget": 300 },
      { "resourceType": "stylesheet", "budget": 80 },
      { "resourceType": "total", "budget": 500 }
    ],
    "resourceCounts": [
      { "resourceType": "third-party", "budget": 10 }
    ]
  }
]

（budget 单位是 KB。）超预算就告警/阻断。

产物体积回归报警：盯住「增量」

比「绝对阈值」更敏感的一招是盯增量——不只看「现在多大」，更看「这个 PR 让它大了多少」。因为绝对阈值往往设得比较宽松（怕误伤），而「一个 PR 突然让包大了 300KB」即使还没超总阈值，也值得警惕。

Web / H5 场景，社区常用 size-limit 做这件事：

pnpm add -D size-limit @size-limit/preset-app

package.json 里声明每个入口的体积上限：

{
  "size-limit": [
    { "path": "dist/assets/index.*.js", "limit": "200 KB" }
  ],
  "scripts": {
    "size": "size-limit"
  }
}

配合 CI，size-limit 能在 PR 上评论出「这个 PR 让包从 180KB 变成了 195KB（+15KB）」。把体积变化摆到 PR 上，让每个人对自己引入的体积负责——这比一个遥远的总阈值有效得多。很多「顺手 import 了整个 lodash / moment」的问题，就是被这种增量报警当场抓住的。

但一换到小程序、跨端、原生 App，「包体积」就不只是 JS bundle 了，要盯的是最终交付给用户的那份产物：

场景 需要盯的增量 常见问题
小程序 主包、分包、图片、字体、WXML/WXSS/JS 资源 图片没压缩、公共依赖进主包、分包拆得不合理
WebView / Hybrid H5 bundle、离线包、内置资源、桥接 SDK 离线包持续膨胀、重复内置公共库
React Native JS bundle、Hermes bytecode、图片资源、Native SDK npm 依赖变大、图片资源进包、Native SDK 体积上涨
Flutter Dart AOT 产物、Asset、字体、图片、Plugin 引入的原生依赖 图片和字体过大、插件带入大体积 Native 库
原生 App APK / AAB / IPA、动态库、资源包、ABI 切分产物 SDK 堆叠、so 库重复、未做资源压缩和架构裁剪

工程实现上不一定非要找一个通吃的工具。更现实的做法是：构建完成后产出一份体积清单，和基线清单做 diff。

当前 PR:
  app-release.apk        42.3 MB  (+1.8 MB)
  assets/images          8.1 MB   (+900 KB)
  lib/arm64-v8a          12.6 MB  (+700 KB)
  miniapp/main-package   1.7 MB   (+220 KB)

规则:
  单次 PR 总产物增量 > 1 MB       → warn
  主包 / 首页关键包增量 > 200 KB  → error
  单张图片 > 300 KB              → error

这个思路对跨端尤其重要。比如 React Native 的 JS bundle 没怎么变，但新增了一个 Native SDK，最终 APK / IPA 变大很多；Flutter 的 Dart 代码没多少变化，但资源目录塞了几张大图，安装包一样会涨。用户下载的是最终产物，不是某一个技术栈的局部 bundle。

Web 之外：小程序、跨端、原生怎么设门禁

Lighthouse CI 主要服务 Web 页面，但性能门禁的思想不是 Web 专属。换到小程序、React Native、Flutter、原生 App，本质还是同一件事：先定义预算，再在 PR、构建、发布前自动验证。

可以先用这张表定口径：

应用类型 适合卡什么 常见门禁位置 说明
Web / H5 Lighthouse 分数、LCP、资源体积、请求数 PR CI、预览环境 实验室数据可复现，适合防止明显倒退
小程序 主包体积、分包体积、启动耗时、页面首屏、接口耗时 构建 CI、体验版、发布前检查 平台限制强，包体积和启动速度非常关键
WebView / Hybrid H5 体积、离线包大小、WebView 初始化、JSBridge 耗时 App 构建、离线包发布、灰度流程 只测 H5 不够，还要看容器层耗时
React Native / Flutter 包体积、首帧时间、FPS、掉帧率、页面切换耗时 真机自动化、集成测试、灰度前 性能问题常出在渲染线程、JS 线程或桥通信
原生 App 冷启动、热启动、帧率、卡顿、崩溃率、ANR 真机测试、发布流水线、灰度监控 既要卡性能，也要卡稳定性

小程序门禁

小程序最应该先卡两类东西：包体积和启动/首屏耗时。

包体积很好理解：平台本身就有主包、分包大小限制，超过了可能直接发不了版；即使没超过，包越大下载越慢、启动越慢。所以小程序 CI 里至少应该有这些检查：

主包体积      ≤ 设定阈值
单个分包体积  ≤ 设定阈值
图片资源体积  ≤ 设定阈值
未使用资源    不允许持续增长

启动和首屏就更接近上一篇讲的「用户看见了吗」。我的建议是不要一上来追求很复杂的指标，先把页面分成关键路径和普通路径：

首页 / 核心交易页 / 核心列表页  → 阻断门禁
低频设置页 / 活动页              → 提醒门禁

小程序平台通常会提供自己的开发者工具、质量面板和性能数据能力，具体字段要以微信、支付宝等平台官方文档为准。工程上要做的是把这些数据接进流水线或发布检查，而不是只在开发者工具里手动看一眼。

跨端应用门禁

跨端应用的麻烦在于：它既不像纯 Web 那样只有浏览器，也不像纯原生那样全是 Native。React Native 有 JS 线程、UI 线程、Native Bridge；Flutter 有 Dart 层、渲染管线和平台通道。门禁要盯的不是 Lighthouse 分数，而是这些更贴近运行时的指标：

首帧时间
页面切换耗时
FPS / 掉帧率
长任务 / 主线程阻塞
桥通信或平台通道耗时
图片解码和列表渲染耗时

这里最好上真机或稳定的模拟器跑自动化用例。比如打开首页、进入列表、滚动 10 秒、进入详情页，记录首帧和掉帧。如果这次 PR 让核心路径掉帧明显变多，就算功能测试全绿，也应该拦一下。

原生 App 门禁

原生应用的性能门禁更接近「性能 + 稳定性」一起守。因为用户感知里的「慢」经常和「卡死、闪退、白屏」混在一起。可以从这几项起步：

冷启动耗时
热启动耗时
核心页面首帧
滑动 FPS / 卡顿率
崩溃率
ANR / 卡死率
安装包体积

原生端还有一个特点：机型差异非常大。高端机测出来没问题，不代表低端机也没问题。所以门禁最好有固定设备池，至少覆盖一台中低端设备。没有设备池时，也要把低端机型的灰度数据单独看，别用全量平均值把问题盖掉。

非 Web 门禁的核心原则

非 Web 场景不要照搬 Lighthouse 的指标名，而要照搬它的治理思路：

  1. 先卡可重复的指标：包体积、启动耗时、首帧、核心路径耗时，比复杂的线上体验分更适合做 CI 阻断。
  2. 真机数据优先：跨端和原生的卡顿、掉帧、启动，更依赖设备性能，模拟环境只能做参考。
  3. 核心路径更严：首页、登录、支付、下单、列表滚动这些路径可以阻断；低频页面先提醒。
  4. CI 防倒退，线上监控看真实体验：门禁负责守住不要明显变差，真实用户数据负责发现长尾问题。

门禁怎么设才不会被架空

性能门禁最大的失败模式不是「没配」，而是「配了但被无视」——阈值太严天天误报，团队要么天天加白名单，要么直接把它设成非阻断然后没人看。几条让门禁活下去的经验：

  1. 阈值从「当前值 + 少量余量」开始，而不是理想值。比如现在 JS 是 280KB，就把预算设成 300KB，守住「别再涨」。等优化下去了再收紧。一上来就设个够不着的理想值，只会天天红。
  2. 区分「阻断」和「提醒」：只有最核心的少数几项用阻断（error），其余用提醒（warn）。宁可少卡几项但每次卡都当真，也别卡一堆然后大家全忽略。
  3. 门禁要能定位：报警得能说清「哪个资源超了、超了多少、大概是什么引入的」。只说「性能不达标」的门禁没人改得动。
  4. 和真实数据对齐：门禁用的实验室阈值，要偶尔和 RUM、灰度、真机测试数据对一对，别守着一个和用户真实体验脱节的实验室数字。

我的核心判断：性能门禁的目标是「防止倒退」，不是「追求满分」。守住「别越来越慢」这条线，比偶尔冲一次高分有用得多。它和覆盖率门禁是一个哲学——看趋势、设够用的线、别当 KPI 刷。

小结

  1. 性能会自然熵增，且倒退很难在 review 时发现，必须靠自动门禁卡在合并入口，和质量闸口同一哲学。
  2. Web 应用可以用 Lighthouse CI 在 PR 上跑实验室指标，用 assert 设分数和指标门槛。
  3. Performance Budget 给 JS/CSS/图片/请求数设具体阈值，体积回归要盯最终产物增量，而不只是 Web 的 JS bundle。
  4. Lighthouse 是实验室数据，门禁重点卡 LCP/总分/体积，INP/CLS 的真实情况靠 RUM。
  5. 小程序重点卡主包/分包体积、启动耗时、页面首屏和核心接口耗时。
  6. 跨端和原生应用重点卡首帧、页面切换、FPS、掉帧、冷启动、崩溃率和 ANR。
  7. 阈值从「当前值 + 少量余量」起步、分阻断/提醒、能定位、和真实数据对齐；门禁目标是防倒退不是刷满分。
