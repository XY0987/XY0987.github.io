Nginx 从入门到精通：一篇讲透静态服务、反向代理、负载均衡和 HTTPS

发表于2026|更新于2026|全栈
|字数总计:5.5k|阅读时长:23分钟

本文从这个心智模型讲起，再给一套可以直接跑的 Docker + Nginx + Node.js 实战项目，把静态服务、反向代理、负载均衡、gzip、SSE、HTTPS 常见配置一次讲清楚。

本文主要参考 Nginx 官方文档：Beginner's Guide、ngx_http_core_module、ngx_http_proxy_module、ngx_http_upstream_module、ngx_http_gzip_module、ngx_http_ssl_module。不确定的线上安全参数，我不会硬编，生产环境请结合公司安全基线再做加固。

先说结论：Nginx 到底解决什么问题

一句话：Nginx 是站在用户和后端服务之间的高性能流量入口。

它最常见的工作有四类：

能力 做什么 典型场景
静态资源服务 直接返回 HTML、CSS、JS、图片 前端打包产物部署
反向代理 把请求转发给后端服务 /api 转发到 Node / Java / Go 服务
负载均衡 在多个后端实例之间分发请求 多实例部署、扩容、容灾
TLS 终止 在 Nginx 层处理 HTTPS 后端只跑 HTTP，证书集中管理

我的理解是：如果把一个 Web 系统比作商场，Nginx 就像入口大厅。静态资源可以在大厅直接发，复杂业务再转给后面的柜台，柜台多了还要排队分流。

Nginx 的核心心智模型

先不要背指令，先把配置层级记住：

nginx.conf
├── main                 # 全局配置，例如 worker_processes
├── events               # 连接事件配置，例如 worker_connections
└── http                 # HTTP 服务配置
    ├── upstream         # 后端服务组
    └── server           # 一个虚拟主机
        └── location     # 一组 URI 匹配规则

官方文档里有两个概念很重要：

  • directive：指令，比如 listen 80;、root /usr/share/nginx/html;
  • context：上下文，比如 http {}、server {}、location {}

Nginx 配置不是随便写的，每个指令都有自己能出现的位置。比如 upstream 要写在 http 里，listen 要写在 server 里，proxy_pass 通常写在 location 里。

一个可以直接运行的完整项目

下面这个案例会跑起来：

  • 一个 Nginx 容器，监听 http://localhost:8080
  • 两个 Node.js 后端实例：app1、app2
  • Nginx 提供静态页面
  • /api/ 反向代理到 Node 后端，并做负载均衡
  • /stream 代理 SSE 流式接口
  • 开启 gzip 和静态资源缓存

环境要求

我本地按下面环境验证过：

工具 建议版本
Docker Desktop 4.x 或以上
Docker Compose v2
curl macOS / Linux 自带即可

不需要本地安装 Nginx，也不需要本地安装 Node.js，因为都跑在 Docker 里。

services:

    image: nginx:1.27-alpine
    container_name: nginx-playground
    ports:
      - "8080:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro

    depends_on:
      - app1
      - app2

  app1:
    image: node:20-alpine
    working_dir: /app
    volumes:
      - ./app:/app:ro
    environment:
      - INSTANCE=app-1

  app2:

    volumes:

创建 app/server.js，这里不用任何第三方依赖：

const http = require("http");

const instance = process.env.INSTANCE || "app";

function sendJson(res, data) {
  res.writeHead(200, {
    "Content-Type": "application/json; charset=utf-8",
    "Cache-Control": "no-store",
  });
  res.end(JSON.stringify(data, null, 2));
}

const server = http.createServer((req, res) => {
  if (req.url === "/hello") {
    return sendJson(res, {
      instance,
      message: "hello from Node.js backend",
      url: req.url,
      host: req.headers.host,
      realIp: req.headers["x-real-ip"] || null,
      forwardedFor: req.headers["x-forwarded-for"] || null,
      forwardedProto: req.headers["x-forwarded-proto"] || null,
      time: new Date().toISOString(),
    });
  }

  if (req.url === "/slow") {
    setTimeout(() => {
      sendJson(res, { instance, message: "slow response done" });
    }, 1500);
    return;
  }

  if (req.url === "/sse") {
    res.writeHead(200, {
      "Content-Type": "text/event-stream; charset=utf-8",
      "Cache-Control": "no-cache",
      Connection: "keep-alive",
    });

    let count = 0;
    const timer = setInterval(() => {
      count += 1;
      res.write(`data: ${JSON.stringify({ instance, count })}\n\n`);

      if (count === 5) {
        clearInterval(timer);
        res.end();
      }
    }, 1000);

    req.on("close", () => clearInterval(timer));
    return;
  }

  res.writeHead(404, { "Content-Type": "text/plain; charset=utf-8" });
  res.end(`not found from ${instance}\n`);
});

server.listen(3000, "0.0.0.0", () => {
  console.log(`${instance} listening on 3000`);
});

创建核心配置 nginx/nginx.conf：

worker_processes auto;

error_log /var/log/nginx/error.log notice;
pid /var/run/nginx.pid;

events {
    worker_connections 1024;
}

http {
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    log_format main '$remote_addr - $host "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" upstream=$upstream_addr '
                    'request_time=$request_time upstream_time=$upstream_response_time';

    access_log /var/log/nginx/access.log main;

    sendfile on;
    keepalive_timeout 65s;

    gzip on;
    gzip_min_length 256;
    gzip_comp_level 5;
    gzip_types
        text/plain
        text/css
        application/json
        application/javascript
        application/xml
        text/xml;

    upstream node_backend {
        least_conn;
        server app1:3000 max_fails=3 fail_timeout=10s;
        server app2:3000 max_fails=3 fail_timeout=10s;
        keepalive 16;
    }

    server {
        listen 80;
        server_name localhost;

        root /usr/share/nginx/html;
        index index.html;

        location = /health {
            access_log off;
            return 200 "ok\n";
        }

        location /assets/ {
            alias /usr/share/nginx/html/assets/;
            expires 7d;
            add_header Cache-Control "public";
        }

        location / {
            try_files $uri $uri/ /index.html;
        }

        location /api/ {
            proxy_pass http://node_backend/;
            proxy_http_version 1.1;
            proxy_set_header Connection "";

            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            proxy_connect_timeout 5s;
            proxy_send_timeout 60s;
            proxy_read_timeout 60s;
            proxy_next_upstream error timeout http_502 http_503 http_504;
        }

        location = /stream {
            proxy_pass http://node_backend/sse;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host $host;
            proxy_buffering off;
            proxy_cache off;
            proxy_read_timeout 3600s;
        }
    }
}

静态资源：root、alias、try_files 怎么选

静态资源是 Nginx 最基础也最常用的能力。

root：把 URI 拼到目录后面

location / {
    root /usr/share/nginx/html;
}

请求：

/index.html

实际查找：

/usr/share/nginx/html/index.html

root 的规则很简单：文件路径 = root 路径 + 请求 URI。

alias：把匹配前缀替换成目录

location /assets/ {
    alias /usr/share/nginx/html/assets/;
}

请求：

/assets/style.css

实际查找：

/usr/share/nginx/html/assets/style.css

alias 的心智模型是：把 /assets/ 这段 URI 替换成指定目录。

最容易踩坑的是结尾斜杠：

# ✅ 正面案例：location 和 alias 都以 / 结尾
location /assets/ {
    alias /usr/share/nginx/html/assets/;
}

# ❌ 反面案例：路径容易拼错
location /assets/ {
    alias /usr/share/nginx/html/assets;
}

我的建议：普通站点根目录用 root，特殊路径映射用 alias。如果 location 最后一段和目录最后一段一样，优先用 root，这也是官方文档里的建议方向。

try_files：前端 SPA 部署的关键

location / {
    try_files $uri $uri/ /index.html;
}

它的意思是：

  1. 先找 $uri 对应文件
  2. 再找 $uri/ 对应目录
  3. 都没有就返回 /index.html

这就是 Vue / React SPA 部署后刷新子路由不 404 的核心。

比如访问：

/user/profile

服务器上并没有这个真实文件，Nginx 会 fallback 到 /index.html，再交给前端路由接管。

location 匹配规则：不用背，但要知道优先级

常见 location 写法：

写法 含义 示例
location = / 精确匹配 只匹配 /
location /api/ 普通前缀匹配 匹配 /api/users
location ^~ /assets/ 优先前缀匹配 命中后不再检查正则
location ~ \.png$ 区分大小写正则 匹配 .png
location ~* \.jpg$ 不区分大小写正则 匹配 .jpg、.JPG

优先级可以简化记成：

精确匹配 =
  ↓
最长前缀匹配，若带 ^~ 则直接使用
  ↓
按配置顺序检查正则 location
  ↓
没有正则命中，则使用之前记录的最长前缀

实战里我最常用三种：

location = /health { ... }
location /api/ { ... }
location / { try_files $uri $uri/ /index.html; }

够用了，别一上来写一堆正则，把自己绕进去。

反向代理：proxy_pass 是最容易踩坑的指令

反向代理的最小配置是：

location /api/ {
    proxy_pass http://node_backend/;
}

这行看着简单，真正容易出问题的是：**proxy_pass 后面有没有 URI，尤其是有没有最后那个 /**。

三种写法对比

假设请求是：

/api/users?id=1
配置 后端收到的路径 说明
proxy_pass http://backend; /api/users?id=1 保留原始 URI
proxy_pass http://backend/; /users?id=1 去掉 /api/ 前缀
proxy_pass http://backend/v1/; /v1/users?id=1 把 /api/ 替换成 /v1/

本文示例里：

location /api/ {
    proxy_pass http://node_backend/;
}

所以浏览器请求 /api/hello，后端 Node 实际收到的是 /hello。

这也是我写项目时最常见的坑：前端明明请求 /api/users，后端却一直 404，最后发现是 Nginx 把路径前缀改了。

代理时建议带上的请求头

proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;

这几行的作用：

Header 作用
Host 把用户访问的域名传给后端
X-Real-IP 传递客户端 IP
X-Forwarded-For 追加代理链路 IP
X-Forwarded-Proto 告诉后端原始协议是 HTTP 还是 HTTPS

注意一个细节：proxy_set_header 有继承规则。如果你在某个层级写了任意一个 proxy_set_header，上层的其他 proxy_set_header 不一定会继续继承。为了少踩坑，我更倾向于在代理的 location 里把关键 header 写全。

负载均衡：upstream 不只是把机器列出来

在示例里我们写了：

upstream node_backend {
    least_conn;
    server app1:3000 max_fails=3 fail_timeout=10s;
    server app2:3000 max_fails=3 fail_timeout=10s;
    keepalive 16;
}

upstream 定义的是一个后端服务组，proxy_pass http://node_backend/; 才是真正引用它。

三种常用分发策略

策略 配置 适合场景
加权轮询 默认行为，或配置 weight 通用场景
最少连接 least_conn; 请求耗时差异大
IP 哈希 ip_hash; 后端本地存 session，需要会话保持

默认是加权轮询：

upstream backend {
    server app1:3000 weight=3;
    server app2:3000 weight=1;
}

大致表示 app1 接收更多流量。

请求耗时差异大时，用 least_conn 更稳：

upstream backend {
    least_conn;
    server app1:3000;
    server app2:3000;
}

如果后端 session 放在本机内存里，可以用 ip_hash 让同一个客户端尽量打到同一台机器：

upstream backend {
    ip_hash;
    server app1:3000;
    server app2:3000;
}

但我的建议是：能不用 sticky session 就不用。更好的方式是把 session 放到 Redis 这类共享存储里，这样后端实例才是真正无状态的。

max_fails 和 fail_timeout 不等于完整健康检查

server app1:3000 max_fails=3 fail_timeout=10s;

这表示：在 10s 内失败达到 3 次，就暂时认为这个后端不可用。这里的失败通常由 proxy_next_upstream 这类指令配合判断。

但要注意：开源 Nginx 这里不是主动定时探测健康检查，它更像是请求过程中发现失败后临时摘除。如果你需要更完整的主动健康检查，要考虑 Nginx Plus、网关层能力，或者在 Kubernetes 里交给 readinessProbe / livenessProbe。

gzip：别迷信压缩等级 9

示例配置：

gzip on;
gzip_min_length 256;
gzip_comp_level 5;
gzip_types
    text/plain
    text/css
    application/json
    application/javascript
    application/xml
    text/xml;

几个点说人话：

指令 作用 我的建议
gzip on 开启 gzip 大多数 Web 站点都应该开
gzip_min_length 小于这个大小不压缩 太小的响应压缩意义不大
gzip_comp_level 压缩等级 1-9 通常 4-6 就够了
gzip_types 额外压缩哪些类型 JS、CSS、JSON、XML 常见

为什么不建议无脑 gzip_comp_level 9？因为压缩率提升有限，但 CPU 消耗会增加。我的实战习惯是先用 5，除非有非常明确的压缩率要求。

SSE / 流式响应：一定注意 proxy_buffering

很多 AI 流式输出、消息推送会用 SSE。这个场景下，Nginx 默认缓冲可能让你看到一个现象：

后端明明一秒返回一段，浏览器却等到最后一次性收到。

原因通常是代理层把上游响应缓冲了。

示例里我们专门写了：

location = /stream {
    proxy_pass http://node_backend/sse;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
}

重点是：

proxy_buffering off;

我的判断：只要是 SSE、AI token 流式输出、长轮询这种实时响应，先检查 proxy_buffering 和 proxy_read_timeout，这两个配置非常容易被忽略。

HTTPS：Nginx 做 TLS 终止

线上一般不会让每个后端服务自己处理证书，而是在 Nginx 层做 TLS 终止：

用户浏览器
  ↓ HTTPS
Nginx
  ↓ HTTP 或内网 HTTPS
后端服务

最小骨架：

server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate /etc/nginx/ssl/example.com.crt;
    ssl_certificate_key /etc/nginx/ssl/example.com.key;

    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 10m;

    location / {
        proxy_pass http://backend;
    }
}

本地自签名证书也能跑。先生成证书：

mkdir -p nginx/certs
openssl req -x509 -nodes -days 365 \
  -newkey rsa:2048 \
  -keyout nginx/certs/localhost.key \
  -out nginx/certs/localhost.crt \
  -subj "/CN=localhost"

把 docker-compose.yml 的 Nginx 端口和挂载补上：

services:
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"
      - "8443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/certs:/etc/nginx/certs:ro
      - ./public:/usr/share/nginx/html:ro

再在 nginx.conf 的 http {} 里增加一个 HTTPS server：

server {
    listen 443 ssl;
    server_name localhost;

    ssl_certificate /etc/nginx/certs/localhost.crt;
    ssl_certificate_key /etc/nginx/certs/localhost.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 10m;

    location / {
        proxy_pass http://node_backend/;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

重启：

docker compose down
docker compose up --build

测试：

curl -k https://localhost:8443/hello

如果按上面的 HTTPS 配置走 proxy_pass http://node_backend/;，这里后端收到的路径就是 /hello。预期返回 JSON，并且 forwardedProto 是 https。

生产环境别直接用自签名证书，要用正式 CA 证书。证书链文件顺序也要注意：通常是服务器证书在前，中间证书在后。

配置变更：先 nginx -t，再 reload

修改配置后不要直接重启，先检查语法：

docker compose exec nginx nginx -t

预期：

nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

再平滑重载：

docker compose exec nginx nginx -s reload

Nginx 的 master 进程会读取新配置，如果配置没问题，就启动新的 worker，并让旧 worker 优雅退出。这个能力在线上很重要，因为它通常不会粗暴中断正在处理的请求。

常见坑位

坑 1：前端刷新路由 404

现象：/ 可以打开，但刷新 /user/profile 直接 404。

原因：Nginx 去磁盘找 /user/profile 这个文件，当然找不到。

解决：

location / {
    try_files $uri $uri/ /index.html;
}

坑 2：接口路径多了一段或少了一段

现象：前端请求 /api/users，后端日志里却是 /users 或 /api/users，和预期不一致。

原因：proxy_pass 有没有尾部 / 会改变 URI 转发规则。

解决：先明确后端到底要不要 /api 前缀，再固定写法：

# 后端需要 /api/users
location /api/ {
    proxy_pass http://backend;
}

# 后端只需要 /users
location /api/ {
    proxy_pass http://backend/;
}

坑 3：上传文件报 413

现象：小文件能上传，大文件报 413 Request Entity Too Large。

原因：client_max_body_size 默认值比较小，官方文档中默认是 1m。

解决：

location /upload/ {
    client_max_body_size 100m;
    proxy_pass http://backend;
}

坑 4：SSE 不流式输出

现象：后端一秒一条，前端最后一次性收到。

原因：代理缓冲。

解决：

location /stream {
    proxy_pass http://backend/sse;
    proxy_buffering off;
    proxy_read_timeout 3600s;
}

坑 5：真实 IP 丢失

现象：后端拿到的 IP 永远是 Nginx 容器或内网 IP。

原因：没有传递 X-Forwarded-For / X-Real-IP，或者后端没有信任代理头。

解决：Nginx 传头，后端按框架要求开启 trust proxy。比如 Express 里通常要配置：

app.set("trust proxy", true);

一份偏生产的配置骨架

下面这份不是让你直接复制上线，而是给一个“配置应该长什么样”的参考。为了不让它变成一坨看不懂的配置，我把关键说明直接写在注释里：

# worker 进程数，auto 表示按 CPU 核心数自动设置，通常比手写数字更稳
worker_processes auto;

# events 负责连接事件模型，worker_connections 表示每个 worker 最多处理多少连接
events {
    worker_connections 4096;
}

http {
    # 引入 MIME 类型映射，否则 CSS / JS 可能会被当成普通二进制返回
    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    # 自定义访问日志格式，重点记录请求、状态码、上游地址、总耗时、上游耗时
    log_format main '$remote_addr - $host "$request" '
                    '$status $body_bytes_sent upstream=$upstream_addr '
                    'request_time=$request_time upstream_time=$upstream_response_time';

    # access_log 看流量和耗时，error_log 看错误和告警
    access_log /var/log/nginx/access.log main;
    error_log /var/log/nginx/error.log warn;

    # sendfile 让 Nginx 更高效地发送静态文件
    sendfile on;

    # 客户端 keep-alive 连接保持时间，减少频繁建连成本
    keepalive_timeout 65s;

    # 请求体大小限制，上传接口经常需要按业务调大
    client_max_body_size 20m;

    # gzip 压缩：适合文本类资源，比如 HTML / CSS / JS / JSON
    gzip on;
    gzip_min_length 1024;
    gzip_comp_level 5;
    gzip_types text/plain text/css application/json application/javascript application/xml text/xml;

    # 后端服务组，Nginx 会把请求转发到这里面的实例
    upstream backend {
        # 请求耗时不均时，用 least_conn 比简单轮询更稳
        least_conn;

        # weight 是权重，max_fails + fail_timeout 控制失败后的临时摘除
        server 10.0.0.11:3000 weight=1 max_fails=3 fail_timeout=30s;
        server 10.0.0.12:3000 weight=1 max_fails=3 fail_timeout=30s;

        # 缓存到后端的空闲长连接，减少 Nginx 到后端的建连成本
        keepalive 32;
    }

    # HTTP 入口：只负责跳转到 HTTPS
    server {
        listen 80;
        server_name example.com;

        # 保留原始 host 和 URI，统一跳转到 HTTPS
        return 301 https://$host$request_uri;
    }

    # HTTPS 入口：真正承载静态资源和 API 代理
    server {
        listen 443 ssl;
        server_name example.com;

        # TLS 证书和私钥，生产环境换成真实证书路径
        ssl_certificate /etc/nginx/ssl/example.com.crt;
        ssl_certificate_key /etc/nginx/ssl/example.com.key;

        # 只启用较新的 TLS 协议版本
        ssl_protocols TLSv1.2 TLSv1.3;

        # TLS 会话复用，降低重复握手成本
        ssl_session_cache shared:SSL:10m;
        ssl_session_timeout 10m;

        # 前端静态资源根目录
        root /usr/share/nginx/html;
        index index.html;

        # 健康检查接口，给负载均衡器或发布系统探活用
        location = /health {
            access_log off;
            return 200 "ok\n";
        }

        # 静态资源目录，通常带长期缓存
        location /assets/ {
            alias /usr/share/nginx/html/assets/;
            expires 30d;
            add_header Cache-Control "public, immutable";
        }

        # API 反向代理，/api/users 会转发成后端的 /users
        location /api/ {
            proxy_pass http://backend/;

            # 使用 HTTP/1.1 并清理 Connection，便于 upstream keepalive 复用连接
            proxy_http_version 1.1;
            proxy_set_header Connection "";

            # 把原始请求信息传给后端，方便后端拿域名、真实 IP、协议
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            # 三类超时：连接后端、向后端发送请求、读取后端响应
            proxy_connect_timeout 5s;
            proxy_send_timeout 60s;
            proxy_read_timeout 60s;

            # 当前后端异常时，允许切到下一个 upstream 实例
            proxy_next_upstream error timeout http_502 http_503 http_504;
        }

        # 前端 SPA 兜底：真实文件不存在时回退到 index.html
        location / {
            try_files $uri $uri/ /index.html;
        }
    }
}

如果把上面的配置再压缩成一张说明表，大概是这样：

配置块 / 指令 主要作用 实战关注点
worker_processes 控制 worker 进程数 通常用 auto
worker_connections 控制单个 worker 的连接上限 高并发时需要结合系统文件句柄一起看
log_format 定义访问日志字段 建议记录 $upstream_addr 和耗时
sendfile 提升静态文件发送效率 静态资源服务建议开启
keepalive_timeout 客户端长连接超时 过短会频繁建连，过长会占连接
client_max_body_size 限制请求体大小 上传接口常见 413 就看它
gzip 压缩文本响应 压缩等级别无脑拉满
upstream 定义后端实例组 负载均衡和容错都从这里开始
least_conn 最少连接负载均衡 适合接口耗时不均的服务
server 80 HTTP 入口 通常只做 HTTPS 跳转
server 443 ssl HTTPS 入口 配证书、静态资源、代理规则
ssl_session_cache TLS 会话复用 降低重复握手成本
location /assets/ 静态资源缓存 文件名带 hash 时适合长期缓存
location /api/ 反向代理 API 注意 proxy_pass 尾部 /
proxy_set_header 传递原始请求信息 后端拿真实 IP、协议会用到
proxy_*_timeout 控制代理超时 慢接口、长连接接口要单独调
try_files 静态文件查找和兜底 SPA 刷新 404 的关键

我的实战建议：不要一开始就把配置写得特别花。先把静态资源、反向代理、日志、HTTPS、超时、上传大小这些基础项跑稳，再逐步加缓存、限流、灰度、WAF 等高级能力。

小结

  1. Nginx 的核心模型是 http → server → location，先理解层级再记指令。
  2. 静态服务优先搞懂 root、alias、try_files，SPA 刷新 404 基本靠 try_files 解决。
  3. 反向代理最容易踩坑的是 proxy_pass 的尾部 /，它会影响后端收到的 URI。
  4. 负载均衡通过 upstream 配置，通用场景用默认轮询，请求耗时不均可以用 least_conn。
  5. SSE 和 AI 流式输出要重点检查 proxy_buffering off 和超时配置。
  6. 线上变更配置先 nginx -t，再 nginx -s reload，不要直接盲目重启。
  7. 真正的生产配置不是堆指令，而是把流量路径、超时、日志、证书、回源策略都讲清楚。
