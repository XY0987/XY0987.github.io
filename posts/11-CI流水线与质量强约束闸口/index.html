CI 流水线与质量强约束闸口

发表于2026|更新于2026|工程化
|字数总计:1.9k|阅读时长:6分钟

前言：前面几篇把 ESLint、Prettier、Stylelint、提交约束、类型检查都讲了一遍。但有个问题一直没解决：这些本地约束，开发者其实都能绕过。真正让规范”无法被绕过”的那一层，是 CI 加分支保护。这篇就补上这个闸口。

本地 hook 不是强约束

前面讲提交约束时我反复强调”本地 hook 要快”，但要承认一个现实：

本地的 pre-commit、commit-msg，开发者一行命令就能跳过。

git commit --no-verify -m "skip checks"
git push --no-verify

--no-verify 会跳过所有 Git Hooks。这不是 bug，是 Git 故意留的口子。

所以本地 hook 的定位应该想清楚：

层级 能不能被绕过 定位
编辑器保存格式化 能（关掉插件即可） 提升体验
pre-commit / commit-msg 能（--no-verify） 提前反馈
CI + 分支保护 不能（合并入口卡死） 真正的强约束

我的理解是：**本地工具是”善意提醒”，CI 才是”硬性门禁”**。如果只配了 Husky 没配 CI，团队规范本质上还是靠自觉。

CI 在质量体系里的定位

CI 的价值不是”再跑一遍 lint”，而是它处在一个开发者无法跳过的位置——代码必须经过 CI 才能合并进主干。

开发者本地
  │  （hook 可被 --no-verify 跳过）
  ▼
push 到远程分支
  │
  ▼
开 Pull Request
  │
  ▼
CI 自动运行 ← 这里跑的检查没人能跳过
  │
  ├── 通过 → 允许合并
  └── 失败 → 阻止合并

注意：CI 跑通本身不会自动阻止合并。是否阻止，取决于后面要讲的分支保护配置。很多团队配了 CI 却没配分支保护，结果 CI 红了照样能点合并——那 CI 就只是个摆设。

一份最小可用的 GitHub Actions

延续前面几篇的脚本设计，假设 package.json 里已经有这些命令：

{
  "scripts": {
    "format:check": "prettier . --check",
    "lint": "eslint .",
    "lint:style": "stylelint \"src/**/*.{css,scss,vue}\"",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "build": "vite build"
  }
}

创建 .github/workflows/ci.yml：

name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      # 用 --frozen-lockfile，lockfile 和 package.json 对不上时直接失败
      - run: pnpm install --frozen-lockfile

      - run: pnpm format:check
      - run: pnpm lint
      - run: pnpm lint:style
      - run: pnpm typecheck
      - run: pnpm test
      - run: pnpm build

这里有两个细节值得说：

第一，cache: pnpm 让 setup-node 自动缓存 pnpm store。没有缓存的话，每次 CI 都要重新下载所有依赖，团队很快会嫌慢——而工具一旦慢，就会有人想办法绕开它。

第二，**一定要用 --frozen-lockfile**。它表示：如果 pnpm-lock.yaml 和 package.json 对不上，直接报错而不是默默更新。这能拦住”本地改了依赖但忘了提交 lockfile”这类问题，正好衔接上一篇依赖治理里说的 lockfile 可复现。

检查顺序：越便宜的越早跑

上一篇类型检查里提过这个原则，这里再强调一次，因为它直接影响 CI 体验。

install → format:check → lint → typecheck → test → build
   快                                              慢

格式和 lint 几秒就能跑完，失败也最容易修；build 和 test 更耗时。把便宜的放前面，开发者能更快拿到失败反馈，不用等五分钟才发现是少了个分号。

分支保护才是真正的闸口

这是这篇最关键的一节。前面的 CI 只是”跑了检查”，要让它变成”无法被绕过的约束”，必须配分支保护。

以 GitHub 为例，在仓库 Settings → Branches → Add branch ruleset（或旧版 Branch protection rules）里，对 main 开启：

配置项 作用
Require a pull request before merging 禁止直接 push 主干，必须走 PR
Require status checks to pass CI 不通过不能合并
勾选具体的 check（如 check） 指定哪个 job 必须通过
Require branches to be up to date 合并前必须基于最新主干，避免”分别通过、合起来挂”
Require approvals 至少 N 人 Review 通过
Do not allow bypassing the above settings 管理员也不能跳过

配完之后，效果是这样的：

PR 的 CI 失败
  └── 合并按钮置灰，谁都点不了（包括管理员，如果勾了禁止绕过）

到这一步，”靠工具约束”才算真正成立。在此之前，所有 lint、typecheck 都只是”建议”。

一个常见误区：以为加了 ci.yml 就万事大吉。其实没勾 required status checks，CI 红了照样能合并。文件存在 ≠ 约束生效，这两件事要分开看。

一个容易踩的坑：被跳过的必需检查

如果你为了加速，给 job 加了路径过滤，比如只在改了 src/** 时才跑：

on:
  pull_request:
    paths:
      - 'src/**'

然后又把这个 job 设成了 required check——这时如果某个 PR 只改了文档，这个 job 根本不会运行。而 GitHub 会一直等这个”必需但从未开始”的检查，PR 就卡死在那里永远合不了。

解决方式有两种：

  1. 不要给 required check 的 job 加 paths 过滤，让它每次都跑（内部再用条件跳过具体步骤）；
  2. 或者用一个”汇总 job”做最终的 required check，它依赖其他 job 但自己总会执行。

我的建议是中小项目直接用第一种，简单不容易出错。别为了省那点时间，引入一个能让所有 PR 卡死的隐患。

把依赖和 a11y 检查也接进来

前面两篇讲的依赖治理和 a11y，也应该在 CI 里有落点，否则同样是”靠自觉”。

安全和 license 检查：

      - run: pnpm audit --audit-level high
      - run: pnpm license:check

a11y 的运行时扫描（需要先起服务，再跑 Playwright）：

      - run: pnpm build
      - run: pnpm preview &
      - run: pnpm test:a11y

这里 pnpm audit --audit-level high 对应上一篇说的分级策略——只在 high 及以上失败，避免低危漏洞天天阻塞合并、最后被团队忽略。

Renovate / Dependabot 与 CI 的衔接

上一篇说过依赖升级要配合 CI 和人工评审。这里补一份 Dependabot 的最小配置 .github/dependabot.yml：

version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
    groups:
      # 把 minor 和 patch 合并成一个 PR，减少噪音
      minor-and-patch:
        update-types:
          - minor
          - patch

关键点不在配置本身，而在于：自动升级的 PR 也必须过同一套 required checks。

Dependabot 提 PR
  │
  ▼
跑完整 CI（lint / typecheck / test / build）
  │
  ├── patch 且 CI 通过 → 可考虑自动合并
  └── minor / major → 人工 Review 再合并

只有这样，自动升级才是”可控”的——升级如果引入问题，CI 会先红，而不是直接进主干。

非 GitHub 平台怎么对应

如果团队用工蜂（TGit）、GitLab 或其他平台，概念是相通的，只是叫法不同：

GitHub GitLab / 工蜂 作用
GitHub Actions GitLab CI（.gitlab-ci.yml）/ 流水线 跑检查
Branch protection Protected Branches 保护主干
Required status checks Pipelines must succeed CI 不过不能合
Required approvals Merge Request Approvals 强制 Review
CODEOWNERS Code Owners / 审批规则 指定评审人

核心思路完全一致：把检查放到一个开发者绕不过去的合并入口上。平台只是实现细节。

小结

  1. 本地 Git Hook 能被 --no-verify 跳过，不是强约束，只是提前反馈。
  2. CI 的价值在于它处在无法绕过的合并入口，但 CI 跑通不等于自动阻止合并。
  3. 真正的强约束是 CI 加分支保护（required status checks），缺一不可。
  4. required check 的 job 不要加路径过滤，否则可能让 PR 永远卡死。
  5. 依赖升级、audit、a11y 检查都应接入 CI，自动升级 PR 也必须过同一套检查。
