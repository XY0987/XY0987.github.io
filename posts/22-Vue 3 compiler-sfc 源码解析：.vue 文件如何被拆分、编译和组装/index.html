Vue 3 compiler-sfc 源码解析：.vue 文件如何被拆分、编译和组装

发表于2026|更新于2026|Vue框架及周边库
|字数总计:1.6k|阅读时长:7分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：compiler-core 负责通用模板编译，compiler-dom 面向浏览器 DOM，compiler-sfc 则面向 .vue 单文件组件。它的核心任务不是“单独编译模板”，而是把 <template>、<script setup>、<style scoped> 等块拆开，并协调它们之间的信息流。

compiler-sfc 对外暴露什么

入口文件很直观：

export { parse } from './parse'
export { compileTemplate } from './compileTemplate'
export { compileStyle, compileStyleAsync } from './compileStyle'
export { compileScript } from './compileScript'

常见工具链中的使用方式大致是：

.vue source
  -> parse() 得到 SFCDescriptor
  -> compileScript() 处理 <script setup>
  -> compileTemplate() 编译 <template>
  -> compileStyle() 编译 <style>
  -> 由打包插件组装成最终模块

parse：把 .vue 拆成 descriptor

SFCDescriptor 是后续所有编译阶段的共享数据结构：

export interface SFCDescriptor {
  filename: string
  source: string
  template: SFCTemplateBlock | null
  script: SFCScriptBlock | null
  scriptSetup: SFCScriptBlock | null
  styles: SFCStyleBlock[]
  customBlocks: SFCBlock[]
  cssVars: string[]
  slotted: boolean
  shouldForceReload: (prevImports: Record<string, ImportBinding>) => boolean
}

parse() 会先用 DOM 编译器以 parseMode: 'sfc' 解析整份 .vue：

export function parse(source: string, options: SFCParseOptions = {}): SFCParseResult {
  const ast = compiler.parse(source, {
    parseMode: 'sfc',
    prefixIdentifiers: true,
    ...templateParseOptions,
    onError: e => {
      errors.push(e)
    },
  })
}

然后遍历根节点，根据 tag 分配到不同 block：

ast.children.forEach(node => {
  if (node.type !== NodeTypes.ELEMENT) return
  switch (node.tag) {
    case 'template':
      descriptor.template = createBlock(node, source, false) as SFCTemplateBlock
      templateBlock.ast = createRoot(node.children, source)
      break
    case 'script':
      const scriptBlock = createBlock(node, source, pad) as SFCScriptBlock
      const isSetup = !!scriptBlock.attrs.setup
      if (isSetup) descriptor.scriptSetup = scriptBlock
      else descriptor.script = scriptBlock
      break
    case 'style':
      descriptor.styles.push(createBlock(node, source, pad) as SFCStyleBlock)
      break
    default:
      descriptor.customBlocks.push(createBlock(node, source, pad))
  }
})

这里的关键不是编译，而是保留每个 block 的：

  • content：块内源码。
  • attrs：例如 setup、lang、scoped、module。
  • loc：在原始 .vue 文件中的位置。
  • map：source map。

compileScript：script setup 的核心

compileScript 需要整个 SFCDescriptor，因为 <script setup> 不是孤立编译的：它可能要和普通 <script> 合并，也要知道模板中是否使用了导入变量。

/**
 * Compile `<script setup>`
 * It requires the whole SFC descriptor because we need to handle and merge
 * normal `<script>` + `<script setup>` if both are present.
 */
export function compileScript(sfc: SFCDescriptor, options: SFCScriptCompileOptions): SFCScriptBlock {

1. 处理两种 script 的关系

const { script, scriptSetup, source, filename } = sfc
const scriptLang = script && script.lang
const scriptSetupLang = scriptSetup && scriptSetup.lang

if (script && scriptSetup && scriptLang !== scriptSetupLang) {
  throw new Error(`<script> and <script setup> must have the same language type.`)
}

if (!scriptSetup) {
  const ctx = new ScriptCompileContext(sfc, options)
  return processNormalScript(ctx, scopeId)
}

如果没有 <script setup>，基本就是处理普通 script。如果两者同时存在，则必须语言一致，因为后面要合并成一个模块。

2. 提升 import，去重并记录绑定

for (const node of scriptSetupAst.body) {
  if (node.type === 'ImportDeclaration') {
    hoistNode(node)
    for (let i = 0; i < node.specifiers.length; i++) {
      const specifier = node.specifiers[i]
      const local = specifier.local.name
      const imported = getImportedName(specifier)
      registerUserImport(source, local, imported, isType, true, !options.inlineTemplate)
    }
  }
}

<script setup> 中的 import 需要提升到模块顶层，同时记录到 ctx.userImports。这些信息后续用于：

  • 判断导入是否在模板中使用。
  • 去除重复 import。
  • 识别从 vue 导入的编译宏。

3. 识别编译宏

if (node.type === 'ExpressionStatement') {
  const expr = unwrapTSNode(node.expression)
  if (
    processDefineProps(ctx, expr) ||
    processDefineEmits(ctx, expr) ||
    processDefineOptions(ctx, expr) ||
    processDefineSlots(ctx, expr)
  ) {
    ctx.s.remove(node.start! + startOffset, node.end! + startOffset)
  } else {
    processDefineModel(ctx, expr)
  }
}

defineProps、defineEmits、defineModel 等不是运行时 API，而是编译宏。它们会被编译器消费掉，然后生成组件选项、setup 参数或运行时代码。

4. 分析 binding metadata

// `defineProps` & `defineModel` also register props bindings
if (scriptAst) {
  Object.assign(ctx.bindingMetadata, analyzeScriptBindings(scriptAst.body))
}
for (const key in scriptBindings) {
  ctx.bindingMetadata[key] = scriptBindings[key]
}
for (const key in setupBindings) {
  ctx.bindingMetadata[key] = setupBindings[key]
}

bindingMetadata 会被模板编译使用。例如 v-model 要判断一个变量是不是 ref，模板表达式要判断是否需要 _ctx. 前缀。

5. 生成 setup 和默认导出

const genDefaultAs = options.genDefaultAs
  ? `const ${options.genDefaultAs} =`
  : `export default`

ctx.s.prependLeft(
  startOffset,
  `\n${genDefaultAs} /*@__PURE__*/${ctx.helper(`defineComponent`)}({${def}${runtimeOptions}\n  ${hasAwait ? `async ` : ``}setup(${args}) {\n${exposeCall}`,
)
ctx.s.appendRight(endOffset, `})`)

最终，<script setup> 会被包进组件的 setup() 中。

compileTemplate：在模板编译外层加 SFC 能力

入口：

export function compileTemplate(options: SFCTemplateCompileOptions): SFCTemplateCompileResults {
  const { preprocessLang, preprocessCustomRequire } = options
  const preprocessor = preprocessLang
    ? preprocessCustomRequire
      ? preprocessCustomRequire(preprocessLang)
      : consolidate[preprocessLang as keyof typeof consolidate]
    : false
  if (preprocessor) {
    return doCompileTemplate({ ...options, source: preprocess(options, preprocessor), ast: undefined })
  } else {
    return doCompileTemplate(options)
  }
}

compileTemplate 主要处理：

  • 模板预处理器，例如 pug。
  • asset URL 转换，例如 <img src="./logo.png">。
  • scoped id 注入。
  • SSR 模式切换。
  • source map 和错误位置回映射。

真正调用编译器在 doCompileTemplate：

let { code, ast, preamble, map } = compiler.compile(inAST || source, {
  mode: 'module',
  prefixIdentifiers: true,
  hoistStatic: true,
  cacheHandlers: true,
  scopeId: scoped ? longId : undefined,
  slotted,
  sourceMap: true,
  hmr: !isProd,
  nodeTransforms: nodeTransforms.concat(compilerOptions.nodeTransforms || []),
  filename,
  onError: e => errors.push(e),
  onWarn: w => warnings.push(w),
})

所以 compiler-sfc 并不重复实现模板编译，而是把 SFC 相关信息转换成 compiler-dom 或 compiler-ssr 的选项。

compileStyle：PostCSS 插件链

样式编译入口：

export function doCompileStyle(options: SFCAsyncStyleCompileOptions) {
  const preprocessor = preprocessLang && processors[preprocessLang]
  const preProcessedSource = preprocessor && preprocess(options, preprocessor)
  const plugins = (postcssPlugins || []).slice()
  plugins.unshift(cssVarsPlugin({ id: shortId, isProd }))
  if (trim) plugins.push(trimPlugin())
  if (scoped) plugins.push(scopedPlugin(longId))
}

样式编译的核心是 PostCSS 插件链：

插件 / 处理 作用
cssVarsPlugin 处理 v-bind() CSS 变量
trimPlugin 清理样式首尾空白
scopedPlugin 把选择器重写为带 data-v-xxx 的 scoped 样式
postcssModules 生成 CSS Modules 映射
preprocessor 处理 Sass / Less / Stylus 等

SFC 编译的关键协作

compiler-sfc 最值得关注的是跨 block 协作：

信息来源 被谁使用 用途
<script setup> binding metadata template compile 表达式前缀、ref 判断、导入使用检查
<style scoped> id template compile / style compile 模板节点注入 scopeId，样式选择器重写
CSS vars script / style 生成运行时 CSS 变量注入逻辑
template AST compileScript 判断 import 是否在模板中被使用
source map template / style 输出 把错误映射回 .vue 原文件

小结

compiler-sfc 可以理解为 .vue 文件的协调层：

  1. parse 负责拆块，产出 SFCDescriptor。
  2. compileScript 负责处理 <script setup>、编译宏和 binding metadata。
  3. compileTemplate 负责把 SFC 信息传给模板编译器。
  4. compileStyle 负责预处理、scoped、CSS vars 和 CSS Modules。

它本身不替代 compiler-core，而是把 SFC 这种文件格式拆成多个编译任务，再把这些任务需要共享的信息串起来。
