自动检查流水线：lint、typecheck、test 与 build

发表于2026|更新于2026|工程化
|字数总计:1.9k|阅读时长:7分钟

前言：上一篇讲了 CI 的核心模型。这一篇落到最实际的问题：一条 PR 提上来，CI 到底该自动跑哪些检查？顺序怎么排？失败了怎么给出人能看懂的反馈？把 lint、typecheck、test、build 这四件事组织成一条高效的自动检查流水线，是持续交付的第一道关。

四道检查各自在防什么

先想清楚每道检查的职责，别把它们混成一锅粥。它们防的是不同层次的问题：

检查 防的问题 快慢 失败好不好修
format / lint 风格不统一、低级错误、坏味道 很快 很好修（多数可自动修）
typecheck 类型不匹配、字段拼错、null 漏判 快 好修
test 逻辑回归、行为变了 中～慢 看情况
build 打包报错、产物出不来 慢 看情况

这四道从上到下，越来越贵、越来越慢，但也越来越接近「真的能跑」。format/lint 是格式和低级问题，build 成功才意味着「至少能打出包来」。它们互不替代——lint 过了不代表类型对，类型对了不代表逻辑对，逻辑对了不代表打得出包。

检查顺序：越便宜的越早跑

这是自动检查流水线最重要的一条原则，之前在类型检查和 CI 闸口篇都提过，这里正式定下来：

install → format:check → lint → typecheck → test → build
  快 ─────────────────────────────────────────────► 慢

为什么？因为快速失败（fail fast）给开发者最好的反馈体验。一个少写分号的低级错误，应该 10 秒内就红给你看，而不是等 5 分钟 build 完才告诉你「其实第一步就挂了」。把便宜的检查放前面，绝大多数问题在几十秒内暴露，开发者改起来也最轻松。

对应的 package.json 脚本（延续前面几个阶段的约定）：

{
  "scripts": {
    "format:check": "prettier . --check",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:coverage": "vitest run --coverage",
    "build": "vite build"
  }
}

一份完整可用的检查流水线

把四道检查串成一个 GitHub Actions workflow：

# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

# 同一 PR 新 push 时，取消还在跑的旧运行，省资源也更快
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with: { version: 9 }

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm             # 缓存 pnpm store，二次跑快很多

      - run: pnpm install --frozen-lockfile

      # 从便宜到贵，快速失败
      - run: pnpm format:check
      - run: pnpm lint
      - run: pnpm typecheck
      - run: pnpm test:coverage
      - run: pnpm build

几个值得说的细节：

**concurrency + cancel-in-progress**：开发时一个 PR 会连续 push 好几次，没这个配置的话每次 push 都排队跑一遍旧的没意义的 CI。加上它，新 push 自动取消旧运行——省 CI 额度，也让最新提交更快出结果。这是个几乎零成本、收益很大的配置。

**--frozen-lockfile**：lockfile 和 package.json 对不上就直接失败，而不是默默改 lockfile。拦住「本地改了依赖忘了提交 lockfile」的问题，保证 CI 装的依赖和本地一致。

串行一个 job 还是拆成多个 job

上面把所有检查塞进一个 check job，命令串行跑。另一种做法是每道检查一个独立 job，并发跑：

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile
      - run: pnpm format:check
      - run: pnpm lint

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile
      - run: pnpm typecheck

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile
      - run: pnpm test:coverage

  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 9

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile
      - run: pnpm build

两种各有取舍：

单 job 串行 多 job 并发
总耗时 各步骤相加 取最慢的那个
依赖安装 装一次 每个 job 都要装（可缓存）
失败定位 看日志 每个检查独立红/绿，一眼看清
配置复杂度 简单 略复杂（重复的 setup）
适合 中小项目 大项目 / 检查耗时长

中小项目用单 job 串行，简单够用；检查加起来超过三五分钟、或者想让「哪个检查挂了」在 PR 上一目了然时，再拆成并发多 job。别一上来就过度拆分——每个 job 重装依赖的开销，可能比省下的并行时间还多。

让失败反馈「人能看懂」

CI 挂了，开发者第一反应是「哪挂了、为啥挂」。如果只能去翻几百行日志，体验很差。几个提升反馈质量的做法：

1. 覆盖率 / 检查结果贴到 PR 上

用 reporter 或社区 action 把测试覆盖率、lint 结果以评论形式贴到 PR，不用点进 CI 详情页翻日志。比如测试报告可以生成 GitHub 能识别的格式：

      - run: pnpm test:coverage
      # 覆盖率/测试结果可用社区 action 贴成 PR 评论或 Job Summary

2. 用 $GITHUB_STEP_SUMMARY 输出摘要

GitHub Actions 支持往一个特殊文件写 Markdown，会渲染成 Job 的摘要页：

      - run: echo "### 构建产物大小" >> "$GITHUB_STEP_SUMMARY"
      - run: du -sh dist >> "$GITHUB_STEP_SUMMARY"

3. 保留失败现场的产物

测试/E2E 失败时，把截图、trace、日志作为 artifact 传上去，方便下载排查（上一篇 Playwright 的 trace 就靠这个）：

      - uses: actions/upload-artifact@v4
        if: failure()          # 只在失败时上传，省空间
        with:
          name: playwright-report
          path: playwright-report/

if: failure() 是个好习惯——成功时没必要传这些排查用的东西。

这条流水线怎么变成「强约束」

要强调一点：这条检查流水线本身不会阻止合并。CI 红了，如果没配分支保护，照样能点 merge。让它成为「无法绕过的闸口」，必须在仓库设置里开启分支保护 + required status checks——这块在《CI 流水线与质量强约束闸口》那篇讲透了，这里不重复。

一个衔接点：如果你把检查拆成了多个并发 job，required status checks 要把每个都勾上，或者用一个「汇总 job」（needs: [lint, typecheck, test]）作为唯一的 required check。后者更省心——加检查时不用回设置里改 required 列表。

  # 汇总 job：只有它当 required check，其他检查都是它的依赖
  ci-passed:
    needs: [lint, typecheck, test, build]
    runs-on: ubuntu-latest
    steps:
      - run: echo "所有检查通过"

小结

  1. lint、typecheck、test、build 防的是不同层次的问题，互不替代，别混成一步。
  2. 检查顺序从便宜到贵（format→lint→typecheck→test→build），快速失败给最好的反馈体验。
  3. concurrency + cancel-in-progress 自动取消同一 PR 的旧运行，几乎零成本的提速。
  4. --frozen-lockfile 保证 CI 依赖和本地一致，拦住忘提交 lockfile 的问题。
  5. 中小项目单 job 串行就够，检查耗时长或想清晰定位失败再拆并发多 job。
  6. 用 Job Summary、PR 评论、失败时上传 artifact，让失败反馈人能看懂、能排查。
  7. 检查流水线本身不阻止合并，配合分支保护 + required checks 才是强约束；多 job 建议用汇总 job 当唯一 required check。
