接口契约、Mock 与请求层工程化基础

发表于2026|更新于2026|工程化
|字数总计:1.7k|阅读时长:6分钟

前言：阶段一不需要把数据层做得很深，但至少要先搭好框架：接口类型从哪里来、Mock 放在哪里、请求错误怎么统一处理、缓存层应该归谁管。这些问题不提前约定，后面业务代码会越来越散。

数据层工程化要解决什么

很多项目一开始会在页面里直接写请求：

const res = await fetch('/api/users')
const users = await res.json()

写 Demo 没问题，业务项目很快会遇到这些问题：

  • 每个页面都在拼接口地址；
  • token 处理散落各处；
  • 错误码处理不统一；
  • 请求取消、重试、缓存没人管；
  • 后端字段变了，前端到运行时才发现；
  • 本地开发依赖后端环境，联调效率低。

所以数据层工程化至少要回答三件事：

接口契约：前后端如何约定请求和响应结构
Mock：后端没好或测试场景下如何模拟接口
请求层：业务代码如何稳定调用接口

接口契约：不要靠口头约定字段

接口契约的核心是：请求参数、响应结构、错误结构，要有可追踪的来源。

常见方案：

方案 说明 适合场景
OpenAPI / Swagger 标准接口描述文件 前后端协作、自动生成类型
Apifox 接口设计、调试、Mock、文档一体 团队协作和接口管理
手写类型 前端自己维护 TS 类型 小项目或后端无规范时

我的建议是：只要接口数量开始变多，就尽量推动 OpenAPI 或类似契约工具，不要长期靠手写类型硬撑。

从 OpenAPI 生成 TypeScript 类型

比如使用 openapi-typescript，可以把 OpenAPI schema 转成 TypeScript 类型。

openapi-typescript ./openapi.yaml -o ./src/services/schema.d.ts

生成后可以这样使用：

import type { paths } from './schema'

type ListUsersResponse =
  paths['/users']['get']['responses'][200]['content']['application/json']

openapi-typescript 的特点是偏“只生成类型”，运行时代码很少，适合你想自己封装请求层的场景。

如果想生成更完整的 SDK，可以考虑：

工具 特点
openapi-typescript 生成 TS 类型，轻量，适合自定义请求层
orval 可生成类型安全客户端，支持 React Query、SWR 等生态
@hey-api/openapi-ts 插件化生成类型、SDK、客户端，适配多种 HTTP 客户端

工具不是重点，重点是：接口类型应该从契约生成，而不是散落在每个页面里手写。

Mock 方案怎么选

MSW

MSW，也就是 Mock Service Worker，核心思路是在网络层拦截请求。浏览器里通过 Service Worker，Node.js 测试环境里也有对应拦截能力。

它的优势是：同一套 mock handler 可以复用在：

  • 本地开发；
  • 组件测试；
  • 集成测试；
  • Storybook；
  • Demo 演示。

目录可以这样放：

src/
├── mocks/
│   ├── handlers/
│   │   └── user.ts
│   ├── browser.ts
│   └── server.ts

示例 handler：

import { http, HttpResponse } from 'msw'

export const userHandlers = [
  http.get('/api/users', () => {
    return HttpResponse.json([
      { id: '1', name: 'Tom' }
    ])
  })
]

我的看法是：如果你希望开发和测试复用同一套 Mock，优先考虑 MSW。

vite-plugin-mock

vite-plugin-mock 更偏开发期插件，适合 Vite 项目快速模拟接口。

优点：

  • 接入简单；
  • 对 Vite 项目友好；
  • 适合本地开发快速出数据。

缺点：

  • 和测试环境复用能力不如 MSW；
  • 更依赖构建工具插件体系。

独立 Mock Server

独立 Mock Server 可以用 Express、Koa、Fastify 或专门平台实现。

适合：

  • 多端共用同一套 Mock；
  • Mock 逻辑复杂；
  • 需要权限、状态、场景切换；
  • 前端项目不想绑定某个构建工具。

缺点是维护成本更高，需要有人把 Mock Server 当成一个小服务维护。

请求层应该封装什么

一个基础请求层至少包含：

1. baseURL
2. 请求头注入
3. token / 鉴权处理
4. 统一错误码处理
5. 超时处理
6. 请求取消
7. 重试策略
8. 响应数据解包

目录可以这样组织：

src/services/
├── http.ts              # axios/fetch 实例
├── errors.ts            # 错误类型和错误码
├── sdk/                 # OpenAPI 生成或手写接口函数
└── query/               # React Query / VueQuery / SWR 封装

一个简化的请求封装：

export class HttpError extends Error {
  constructor(
    message: string,
    public status: number,
    public code?: string
  ) {
    super(message)
  }
}

export async function request<T>(url: string, init?: RequestInit): Promise<T> {
  const res = await fetch(url, {
    ...init,
    headers: {
      'Content-Type': 'application/json',
      ...init?.headers
    }
  })

  if (!res.ok) {
    throw new HttpError(res.statusText, res.status)
  }

  return res.json() as Promise<T>
}

真实项目里你可能用 axios，也可能用 fetch。工具不是重点，重点是业务组件不要直接处理底层细节。

请求取消和重试不要散写

比如搜索框输入时，旧请求应该取消；网络抖动时，部分查询可以重试。

这些逻辑不要散在每个组件里。

如果用原生 fetch，可以用 AbortController：

const controller = new AbortController()

request('/api/users', {
  signal: controller.signal
})

controller.abort()

如果用 React Query、SWR、VueQuery，取消、重试、缓存、失效刷新都应该放在数据查询层统一处理，而不是组件里到处写。

缓存层放在哪里

以 React Query 为例，我不建议组件直接拼 query key 和请求函数。

// ❌ 组件里散写 query key 和请求细节
useQuery({
  queryKey: ['users', page],
  queryFn: () => request(`/api/users?page=${page}`)
})

更推荐封一层：

import { useQuery } from '@tanstack/react-query'
import { userApi } from '../sdk/user'

export function useUsers(page: number) {
  return useQuery({
    queryKey: ['users', page],
    queryFn: () => userApi.list({ page })
  })
}

组件只关心业务数据：

const { data, isLoading } = useUsers(1)

这样 query key、缓存策略、重试策略都集中在 services/query 或业务模块自己的 query 层。

一个推荐的数据层结构

我比较推荐的基础结构：

src/
├── services/
│   ├── http.ts
│   ├── errors.ts
│   ├── schema.d.ts
│   ├── sdk/
│   │   └── user.ts
│   └── query/
│       └── user.ts
├── mocks/
│   ├── handlers/
│   │   └── user.ts
│   ├── browser.ts
│   └── server.ts
└── features/
    └── user/
        └── components/

依赖方向是：

features -> services/query -> services/sdk -> services/http
mocks    -> 契约类型 / mock 数据

不要让 services 反过来依赖 UI 组件，也不要让 Mock 逻辑侵入真实请求层。

小结

  1. 数据层工程化先解决接口契约、Mock 和请求封装三件事。
  2. 接口多起来后，优先推动 OpenAPI / Swagger / Apifox 这类契约来源。
  3. MSW 适合开发和测试复用 Mock，vite-plugin-mock 适合 Vite 项目快速开发，独立 Mock Server 适合多端共用。
  4. 请求层要统一处理鉴权、错误、取消、重试和响应解包，不要散在页面里。
  5. React Query、SWR、VueQuery 这类缓存层应该有固定工程位置，组件只消费业务 Hook。
