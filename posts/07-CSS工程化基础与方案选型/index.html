CSS 工程化基础与方案选型

发表于2026|更新于2026|工程化
|字数总计:1.9k|阅读时长:6分钟

前言：CSS 工程化不是为了把样式写得更复杂，而是为了让样式在多人协作、组件复用、主题扩展时不互相污染。选方案前，先要分清每个工具解决的到底是什么问题。

CSS 为什么也需要工程化

很多项目初期写 CSS 都很轻松：

.button {
  padding: 8px 12px;
  color: #fff;
  background: #1677ff;
}

但随着项目变大，问题会越来越明显：

  • class 名冲突；
  • 选择器层级越来越深；
  • 全局样式影响范围不可控；
  • 主题色到处硬编码；
  • 重复样式越来越多；
  • 删除组件时不知道 CSS 能不能删；
  • 移动端、暗色主题、国际化布局难维护。

所以 CSS 工程化要解决的不是“怎么写出炫酷样式”，而是下面几个问题：

问题 目标
作用域 样式不要随便污染全局
复用 公共样式和设计 token 可复用
维护 样式和组件关系清楚
构建 能自动补前缀、压缩、转换语法
约束 命名、嵌套、复杂度有规则

PostCSS：CSS 处理管线

PostCSS 本身不是 Sass，也不是 Tailwind。

我的理解是：PostCSS 是一个 CSS 转换平台。

它把 CSS 解析成 AST，然后交给插件处理。

CSS 源码
  │
  ▼
PostCSS Parser
  │
  ▼
插件处理
  │
  ├── autoprefixer
  ├── postcss-preset-env
  └── 其他插件
  │
  ▼
输出 CSS

最常见的例子是自动补浏览器前缀。

输入：

.container {
  user-select: none;
}

经过 Autoprefixer 后，可能输出：

.container {
  -webkit-user-select: none;
  user-select: none;
}

项目里通常不需要直接操作 PostCSS，但你要知道很多工具背后都依赖它。

比如 Vite、Tailwind、Autoprefixer、一些 CSS 压缩工具，都可能参与 PostCSS 管线。

Sass：增强 CSS 表达能力

Sass 解决的是 CSS 写法增强问题。

它提供：

  • 变量；
  • 嵌套；
  • mixin；
  • 函数；
  • 模块化导入。

示例：

$primary-color: #1677ff;

@mixin card {
  border-radius: 8px;
  box-shadow: 0 2px 8px rgb(0 0 0 / 8%);
}

.user-card {
  @include card;

  &__title {
    color: $primary-color;
  }
}

Sass 的优点是学习成本低，适合传统样式体系和复杂页面。

但它也有一个常见风险：嵌套滥用。

.page {
  .content {
    .list {
      .item {
        .title {
          color: #333;
        }
      }
    }
  }
}

这种写法会让选择器越来越重，后期覆盖非常痛苦。

所以如果使用 Sass，一定要配合 Stylelint 限制嵌套深度。

CSS Modules：解决局部作用域

CSS Modules 解决的是样式作用域问题。

Button.module.css：

.root {
  padding: 8px 12px;
  color: #fff;
  background: #1677ff;
}

组件里使用：

import styles from './Button.module.css'

export function Button() {
  return <button className={styles.root}>Submit</button>
}

构建后 class 名会被转换成带 hash 的名字，避免全局冲突：

Button_root__a1b2c

CSS Modules 很适合组件化项目，尤其是：

  • React/Vue 组件；
  • 中后台页面；
  • 不想引入原子化 CSS；
  • 希望样式和组件文件靠近。

它的缺点是跨组件复用样式不如原子化 CSS 方便，设计 token 仍然需要额外体系管理。

Tailwind：原子化 CSS 的代表

Tailwind 的思路是用大量原子类组合样式。

export function Card() {
  return (
    <div className="rounded-lg bg-white p-4 shadow-sm">
      <h2 className="text-lg font-medium text-slate-900">Title</h2>
    </div>
  )
}

它的优点很明显：

  • 不需要频繁起 class 名；
  • 样式和结构在同一个地方；
  • 设计 token 可以集中配置；
  • 重复样式更容易通过组件抽象解决；
  • 产物可以按使用情况裁剪。

但它也有争议：

  • JSX/模板里的 class 很长；
  • 对不熟悉的人可读性差；
  • 设计不统一时会写成“行内样式升级版”；
  • 复杂交互状态下 class 组合容易膨胀。

我的看法是：Tailwind 很适合组件化程度高、设计体系稳定的项目。

如果团队还没有设计 token，也没有组件抽象习惯，直接上 Tailwind 可能会变成另一种混乱。

UnoCSS：更灵活的原子化引擎

UnoCSS 也是原子化 CSS 工具，但它和 Tailwind 的本质区别值得说清楚。

先澄清一个常见误解：「按需生成」不是 UnoCSS 相对 Tailwind 的优势。Tailwind 从 v3 的 JIT 引擎起也是按需生成的，只产出你代码里真正用到的类。所以「按需」是两者共有的，不是区分点。

真正的区别在于定位：

  • Tailwind 是一套写好的原子类库：色阶、间距、命名都由它规定好，你主要是「用」这套现成的类，开箱即用。
  • UnoCSS 是一个可编程的原子类引擎：它本身不内置任何类名，类名到 CSS 的映射规则由你通过 preset / rules 定义。你看到 bg-blue-500 能用，是因为装了 presetUno()（它模拟了 Tailwind 风格）。

所以它的特点是：

  • 本质是引擎，类名规则可完全自定义；
  • 预设（preset）可组合，presetUno 能模拟 Tailwind；
  • 支持自定义规则、快捷方式、设计体系映射；
  • 同样按需生成，速度快；
  • 适合需要高度定制原子化体系的团队。

最小配置（只用 presetUno，效果几乎等同 Tailwind）：

import { defineConfig, presetUno } from 'unocss'

export default defineConfig({
  presets: [presetUno()],
})

使用方式和原子化 CSS 类似：

<button class="rounded bg-blue-500 px-3 py-2 text-white">
  Submit
</button>

而它真正灵活的地方，是可以自己定义「类名 → CSS」的规则：

import { defineConfig, presetUno } from 'unocss'

export default defineConfig({
  presets: [presetUno()],
  rules: [
    // 静态规则：写 text-huge 就生成 font-size: 64px
    ['text-huge', { 'font-size': '64px' }],
    // 动态规则：m-数字 → margin
    [/^m-(\d+)$/, ([, d]) => ({ margin: `${d}px` })],
  ],
})

这种「自定义规则」在 Tailwind 里要靠改配置或写插件，而 UnoCSS 把它当成一等公民。

如果团队只是想用 Tailwind 生态，直接用 Tailwind 更稳。

如果团队希望自己定义大量规则、快捷方式、设计体系映射，UnoCSS 会更灵活。

怎么选型

我通常按项目类型判断。

场景 推荐方案
小型页面或传统项目 Sass + Stylelint
React/Vue 中后台 CSS Modules + Sass
组件库 CSS Modules / Vanilla Extract / 原子化方案
设计体系成熟的应用 Tailwind
高度定制原子化体系 UnoCSS
需要构建转换能力 PostCSS 作为底层管线

如果你问我一个保守默认值：

中后台业务项目可以优先选择 CSS Modules + Sass + Stylelint，等设计体系成熟后再考虑 Tailwind 或 UnoCSS。

原因是这套方案学习成本低，局部作用域明确，对大多数团队比较稳。

和规范工具怎么配合

CSS 工程化不是只选一个写法，还要配合工具约束。

最低配置我建议包含：

{
  "scripts": {
    "lint:style": "stylelint \"src/**/*.{css,scss,vue}\"",
    "lint:style:fix": "stylelint \"src/**/*.{css,scss,vue}\" --fix",
    "format": "prettier . --write"
  }
}

再配合：

  • Stylelint 限制嵌套深度；
  • Prettier 统一格式；
  • 设计 token 管理颜色、间距、字号；
  • CSS Modules 或原子化工具控制作用域；
  • CI 跑样式检查。

CSS 最怕“先随便写，后面再治理”。样式一旦失控，重构成本通常比 JS 更高。

小结

  1. PostCSS 是 CSS 转换管线，常用于自动补前缀、语法转换和工具集成。
  2. Sass 增强 CSS 表达能力，但要控制嵌套深度。
  3. CSS Modules 解决局部作用域，适合组件化业务项目。
  4. Tailwind 适合设计体系成熟、组件抽象稳定的项目。
  5. UnoCSS 更灵活，适合需要自定义原子化规则的团队。
