Vue 3 组件渲染上下文解析：模板变量和 this.xxx 如何访问到 setupState、props 和 data

发表于2026|更新于2026|Vue框架及周边库
|字数总计:2.8k|阅读时长:12分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：前面看了组件实例如何创建、setup 如何执行。这一篇继续看模板和 render 函数里的属性访问：为什么模板里可以直接写 count、msg、$attrs？这些名字最终是怎么从 setupState、props、data、ctx 中解析出来的？

先给结论

组件渲染上下文主要由两部分组成：

模块 职责
componentPublicInstance.ts 处理组件公开实例代理，也就是模板变量、_ctx.xxx、this.xxx 的统一访问入口
componentRenderUtils.ts 执行组件 render，处理 attrs 透传，判断组件是否需要更新

这里的 this.xxx 要分清两层含义：

场景 用户写法 运行时形态
模板 {{ count }} 编译成 render 后通常访问 _ctx.count
用户手写 render render() { return h('div', this.count) } Vue 调用 render 时把 this 绑定到组件代理
Options API 方法等 methods: { inc() { this.count++ } } 方法执行时的 this 也会绑定到组件代理
runtime compile {{ count }} 可能通过 with (_ctx) 在组件代理上查找 count

所以这篇讲的不是“模板里一定写 this.count”，而是讲这些访问最后如何进入同一套组件公开实例代理。

访问普通属性的优先级是：

setupState -> data -> props -> ctx -> publicPropertiesMap -> globalProperties

也就是说，模板里写：

{{ count }}

运行时不是直接访问某个普通对象，而是走组件代理 PublicInstanceProxyHandlers.get。

publicPropertiesMap：$xxx 从哪里来

组件实例上常见的 $attrs、$slots、$emit、$nextTick 等公共属性，来自 publicPropertiesMap：

// 组件公开实例上的 $xxx 属性映射表。
// 模板或 this.$attrs/this.$emit 等访问会通过 PublicInstanceProxyHandlers 转到这里。
export const publicPropertiesMap: PublicPropertiesMap =
  // Move PURE marker to new line to workaround compiler discarding it
  // due to type annotation
  /*@__PURE__*/ extend(Object.create(null), {
    $: i => i,
    $el: i => i.vnode.el,
    $data: i => i.data,
    $props: i => (__DEV__ ? shallowReadonly(i.props) : i.props),
    $attrs: i => (__DEV__ ? shallowReadonly(i.attrs) : i.attrs),
    $slots: i => (__DEV__ ? shallowReadonly(i.slots) : i.slots),
    $refs: i => (__DEV__ ? shallowReadonly(i.refs) : i.refs),
    $parent: i => getPublicInstance(i.parent),
    $root: i => getPublicInstance(i.root),
    $host: i => i.ce,
    $emit: i => i.emit,
    $options: i => (__FEATURE_OPTIONS_API__ ? resolveMergedOptions(i) : i.type),
    $forceUpdate: i =>
      i.f ||
      (i.f = () => {
        queueJob(i.update)
      }),
    $nextTick: i => i.n || (i.n = nextTick.bind(i.proxy!)),
    $watch: i => (__FEATURE_OPTIONS_API__ ? instanceWatch.bind(i) : NOOP),
  } as PublicPropertiesMap)

所以 $attrs 不是实例上的普通字段，而是通过映射函数从内部实例取出来的。

accessCache：为什么模板访问要缓存来源

组件 render 时会频繁访问变量。如果每次都按顺序查 setupState、data、props、ctx，成本会很高。

Vue 用 accessCache 记录某个 key 上次从哪里解析出来：

// accessCache 中保存 key 的来源，避免每次 render 访问 this.xxx 都重复判断。
enum AccessTypes {
  OTHER,
  SETUP,
  DATA,
  PROPS,
  CONTEXT,
}

export interface ComponentRenderContext {
  [key: string]: any
  _: ComponentInternalInstance
}

export const isReservedPrefix = (key: string): key is '_' | '$' =>
  key === '_' || key === '$'

const hasSetupBinding = (state: Data, key: string) =>
  state !== EMPTY_OBJ && !state.__isScriptSetup && hasOwn(state, key)

第一次访问 count 时，Vue 会判断它来自哪里；后续再访问 count，就能直接从缓存路径读取。

举个简单例子：

export default {
  data() {
    return {
      count: 1,
    }
  },
}

模板里多次访问：

<div>{{ count }} {{ count + 1 }} {{ count + 2 }}</div>

第一次访问 count 时，Vue 会按 setupState -> data -> props -> ctx 的顺序查，发现它在 data 里，于是记录：

accessCache.count = AccessTypes.DATA

后面再访问 count，就可以直接读 data.count，不用再重复判断来源。

注意这里缓存的不是 count 的值，而是 count 的来源。

PublicInstanceProxyHandlers.get：模板变量和 this.xxx 的解析顺序

组件公开实例代理的核心是 get：

// 组件公开实例代理：模板/render 中的 this.xxx、用户拿到的组件实例属性访问都会进入这里。
export const PublicInstanceProxyHandlers: ProxyHandler<any> = {
  get({ _: instance }: ComponentRenderContext, key: string) {
    if (key === ReactiveFlags.SKIP) {
      return true
    }

    const { ctx, setupState, data, props, accessCache, type, appContext } =
      instance

    // for internal formatters to know that this is a Vue instance
    if (__DEV__ && key === '__isVue') {
      return true
    }

    // 普通 key 的访问优先级是 setupState -> data -> props -> ctx。
    // This getter gets called for every property access on the render context
    // during render and is a major hotspot. The most expensive part of this
    // is the multiple hasOwn() calls. It's much faster to do a simple property
    // access on a plain object, so we use an accessCache object (with null
    // prototype) to memoize what access type a key corresponds to.
    let normalizedProps
    if (key[0] !== '$') {
      const n = accessCache![key]
      if (n !== undefined) {
        switch (n) {
          case AccessTypes.SETUP:
            return setupState[key]
          case AccessTypes.DATA:
            return data[key]
          case AccessTypes.CONTEXT:
            return ctx[key]
          case AccessTypes.PROPS:
            return props![key]
          // default: just fallthrough
        }
      } else if (hasSetupBinding(setupState, key)) {
        accessCache![key] = AccessTypes.SETUP
        return setupState[key]
      } else if (data !== EMPTY_OBJ && hasOwn(data, key)) {
        accessCache![key] = AccessTypes.DATA
        return data[key]
      } else if (
        // only cache other properties when instance has declared (thus stable)
        // props
        (normalizedProps = instance.propsOptions[0]) &&
        hasOwn(normalizedProps, key)
      ) {
        accessCache![key] = AccessTypes.PROPS
        return props![key]
      } else if (ctx !== EMPTY_OBJ && hasOwn(ctx, key)) {
        accessCache![key] = AccessTypes.CONTEXT
        return ctx[key]
      } else if (!__FEATURE_OPTIONS_API__ || shouldCacheAccess) {
        accessCache![key] = AccessTypes.OTHER
      }
    }

    const publicGetter = publicPropertiesMap[key]
    let cssModule, globalProperties
    // $ 开头的公开属性从 publicPropertiesMap 中读取，例如 $attrs/$slots/$emit/$nextTick。
    if (publicGetter) {

核心优先级就是：

setupState
  ↓
data
  ↓
props
  ↓
ctx
  ↓
$xxx public properties
  ↓
css modules
  ↓
globalProperties

这解释了为什么如果 setup 和 props 中有同名字段，模板会优先访问 setupState。

PublicInstanceProxyHandlers.set：为什么 props 不能改

写入代理时也有规则：

  set(
    { _: instance }: ComponentRenderContext,
    key: string,
    value: any,
  ): boolean {
    const { data, setupState, ctx } = instance
    // 写入同样遵循 setupState -> data -> ctx 的方向；props 和 $xxx 公共属性禁止直接写。
    if (hasSetupBinding(setupState, key)) {
      setupState[key] = value
      return true
    } else if (
      __DEV__ &&
      setupState.__isScriptSetup &&
      hasOwn(setupState, key)
    ) {
      warn(`Cannot mutate <script setup> binding "${key}" from Options API.`)
      return false
    } else if (data !== EMPTY_OBJ && hasOwn(data, key)) {
      data[key] = value
      return true
    } else if (hasOwn(instance.props, key)) {
      __DEV__ && warn(`Attempting to mutate prop "${key}". Props are readonly.`)
      return false
    }

所以 props 不能直接修改，是代理层主动拦截的结果。

runtime compiled render 为什么需要特殊代理

运行时编译的模板 render 可能使用 with(ctx)。这时需要额外的 has trap 控制变量查找：

// runtime compiler 生成的 render 会使用 with(ctx)，因此需要额外的 has trap 控制作用域查找。
export const RuntimeCompiledPublicInstanceProxyHandlers: ProxyHandler<any> =
  /*@__PURE__*/ extend({}, PublicInstanceProxyHandlers, {
    get(target: ComponentRenderContext, key: string) {
      // fast path for unscopables when using `with` block
      if ((key as any) === Symbol.unscopables) {
        return
      }
      return PublicInstanceProxyHandlers.get!(target, key, target)
    },
    has(_: ComponentRenderContext, key: string) {
      const has = key[0] !== '_' && !isGloballyAllowed(key)
      if (__DEV__ && !has && PublicInstanceProxyHandlers.has!(_, key)) {
        warn(
          `Property ${JSON.stringify(
            key,
          )} should not start with _ which is a reserved prefix for Vue internals.`,
        )
      }
      return has
    },
  })

这是 full build 下运行时模板编译才会涉及的路径。

renderComponentRoot：组件 render 的统一入口

组件更新 effect 中会调用 renderComponentRoot(instance) 得到组件子树。

export function renderComponentRoot(

attrs 透传是怎么处理的

renderComponentRoot 得到 root VNode 后，会处理 attrs 透传：

  // attr merging
  // 处理 attrs 透传：能透传时 clone 根 VNode 合并 attrs，不能透传时开发环境给出警告。
  // in dev mode, comments are preserved, and it's possible for a template
  // to have comments along side the root element which makes it a fragment
  let root = result
  let setRoot: SetRootFn = undefined
  if (
    __DEV__ &&
    result.patchFlag > 0 &&
    result.patchFlag & PatchFlags.DEV_ROOT_FRAGMENT
  ) {
    ;[root, setRoot] = getChildRoot(result)
  }

  if (fallthroughAttrs && inheritAttrs !== false) {
    const keys = Object.keys(fallthroughAttrs)
    const { shapeFlag } = root
    if (keys.length) {
      if (shapeFlag & (ShapeFlags.ELEMENT | ShapeFlags.COMPONENT)) {
        if (propsOptions && keys.some(isModelListener)) {
          // If a v-model listener (onUpdate:xxx) has a corresponding declared
          // prop, it indicates this component expects to handle v-model and
          // it should not fallthrough.
          // related: #1543, #1643, #1989
          fallthroughAttrs = filterModelListeners(
            fallthroughAttrs,
            propsOptions,
          )
        }
        // 克隆根 VNode 并合并 attrs，避免直接修改可能被 hoist/cache 的原始 VNode。
        root = cloneVNode(root, fallthroughAttrs, false, true)

如果组件根节点是普通元素或组件，attrs 会合并到根 VNode 上。

如果根节点是 Fragment、Text、Teleport 等不能安全透传的类型，开发环境会提示警告。

shouldUpdateComponent：子组件是否需要更新

父组件更新时，不一定要重新渲染所有子组件。Vue 会用 shouldUpdateComponent 判断子组件是否需要更新：

export function shouldUpdateComponent(
  prevVNode: VNode,
  nextVNode: VNode,
  optimized?: boolean,
): boolean {
  // 父组件更新到子组件 VNode 时，用这个函数判断子组件实例是否真的需要重新渲染。
  const { props: prevProps, children: prevChildren, component } = prevVNode
  const { props: nextProps, children: nextChildren, patchFlag } = nextVNode
  const emits = component!.emitsOptions

  // Parent component's render function was hot-updated. Since this may have
  // caused the child component's slots content to have changed, we need to
  // force the child to update as well.
  if (__DEV__ && (prevChildren || nextChildren) && isHmrUpdating) {
    return true
  }

  // force child update for runtime directive or transition on component vnode.
  if (nextVNode.dirs || nextVNode.transition) {
    return true
  }

  if (optimized && patchFlag >= 0) {
    // 编译器优化路径：根据 patchFlag 只检查动态 slots/props。
    if (patchFlag & PatchFlags.DYNAMIC_SLOTS) {
      // slot content that references values that might have changed,
      // e.g. in a v-for
      return true
    }

优化路径下，Vue 会借助 patchFlag 只检查动态 props 或动态 slots。

非优化路径通常来自手写 render，会更保守：

  } else {
    // 非优化路径通常来自手写 render，需要更保守地比较 children 和 props。
    // this path is only taken by manually written render functions
    // so presence of any children leads to a forced update
    if (prevChildren || nextChildren) {
      if (!nextChildren || !(nextChildren as any).$stable) {
        return true
      }
    }
    if (prevProps === nextProps) {
      return false
    }
    if (!prevProps) {
      return !!nextProps
    }
    if (!nextProps) {
      return true
    }
    return hasPropsChanged(prevProps, nextProps, emits)
  }

这里也会排除 emits listener，因为事件监听变化不一定意味着 props 变化。

小结

  1. 模板里的变量访问、编译后的 _ctx.xxx、Options API 中的 this.xxx，最终都会进入 PublicInstanceProxyHandlers.get。
  2. 普通属性访问优先级是 setupState -> data -> props -> ctx。
  3. $attrs、$slots、$emit 等来自 publicPropertiesMap。
  4. accessCache 用于缓存 key 的来源，是 render 热路径优化。
  5. renderComponentRoot 执行组件 render 并返回规范化后的子树 VNode。
  6. attrs 默认会透传到组件根节点，不能透传时开发环境会警告。
  7. shouldUpdateComponent 用于判断父组件更新时子组件是否需要重新渲染。
