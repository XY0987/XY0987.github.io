环境矩阵与配置注入：dev/test/staging/pre/prod 的产物隔离

发表于2026|更新于2026|工程化
|字数总计:2.2k|阅读时长:6分钟

前言：《环境变量与多环境配置治理》那篇（第五阶段）讲过 .env 文件和多环境变量的组织。这一篇站在部署的角度往深里走一层，回答上一篇容器化留下的问题：一套代码要跑遍 dev / test / staging / pre / prod 好几个环境，产物怎么隔离、配置怎么注入，才能既安全又能做到「一次构建、多处运行」。这是让部署体系不出乱子的关键一环。

环境矩阵：为什么要这么多环境

先说清楚这几个环境各自的角色，别把它们当成「一样的东西复制几份」：

环境 别名 用途 数据
dev 开发 本地/联调开发 假数据 / 开发库
test 测试 QA 功能测试 测试库
staging 预发 尽量接近生产的验收 生产同构数据（脱敏）
pre 预发布/灰度 用生产数据做最后验证 生产数据
prod 生产 真实用户 生产数据

越往右越接近真实、越危险。关键差异是 staging/pre 和 prod 在配置和数据上要严格隔离——最怕的就是测试环境的代码连到了生产数据库，或者生产的密钥泄漏到了测试环境。环境矩阵的本质是用「配置隔离」把同一份代码安全地放到不同危险等级的场景里。

不是每个团队都需要全部五个。小团队常见 dev/test/prod 三个就够；有严格发布流程的大团队才需要 staging/pre 这些额外的验证关卡。按需设，别盲目照搬。

两种配置注入方式：构建期 vs 运行时

前端多环境最核心的技术抉择是：环境配置在什么时候、以什么方式进入产物。两种范式：

构建期注入（Build-time）
  每个环境构建一次，配置编译进产物
  dev 一个包、test 一个包、prod 一个包

运行时注入（Runtime）
  只构建一次，产物里留占位，运行时才填入配置
  一个包跑遍所有环境

它们的取舍很关键：

构建期注入 运行时注入
构建次数 每个环境一次 一次
「测过的包 = 上线的包」 否（每环境重新构建） 是（同一个产物一路验证到生产）
配置改动 要重新构建部署 改配置即可，不重新构建
实现复杂度 简单（Vite import.meta.env） 稍复杂（要留注入机制）
适合 环境少、配置稳定 容器化、环境多、要求产物一致

构建期注入：简单直接的默认方案

Vite 的 import.meta.env 就是构建期注入。.env.production 里的 VITE_ 变量在 vite build 时被静态替换进代码：

// 代码里这么写
const apiBase = import.meta.env.VITE_API_BASE

// 构建后，被替换成字面量
const apiBase = "https://api.prod.example.com"

配合不同的 mode 构建不同环境：

vite build --mode staging     # 读 .env.staging
vite build --mode production  # 读 .env.production

这个方案的优点是简单、零运行时开销、tree-shaking 友好。缺点上一篇说过——配置被焊死进产物，一个包只对应一个环境。改个接口地址得重新走一遍构建。而且它破坏了「测过的那个包就是上线的那个包」这个理想：staging 验证的包和 prod 上线的包是两次不同的构建产物。

环境少、配置稳定的项目，构建期注入完全够用，别过度设计。

运行时注入：一次构建，多处运行

当你想「同一个镜像/产物验遍所有环境再上生产」时，就需要运行时注入。前端做运行时配置有几种常见手法：

手法一：占位 + 启动时替换（容器场景最常用）

产物里放一个配置文件占位，容器启动时用环境变量替换。比如产物里放 config.js：

// public/config.js —— 打进产物，但值是占位符
window.__APP_CONFIG__ = {
  apiBase: '__API_BASE__',
}

HTML 里引用它（在业务 JS 之前）：

<script src="/config.js"></script>

容器启动时用一段脚本把占位符替换成真实环境变量，再启动 Nginx：

#!/bin/sh
# docker-entrypoint.sh
# 用环境变量替换产物里的占位符
sed -i "s|__API_BASE__|${API_BASE}|g" /usr/share/nginx/html/config.js
nginx -g "daemon off;"

这样同一个镜像，docker run -e API_BASE=https://api.test... 跑测试环境，换个环境变量就跑生产。镜像不变，配置在启动时注入，完美契合上一篇容器化「一次构建、多处运行」的目标。

手法二：接口下发配置

页面启动时先请求一个 /api/config 接口，由后端根据环境返回配置。更灵活（能动态改），但多一次请求、且要处理这个请求本身的失败。

容器化部署优先用「占位 + 启动替换」，它简单、无额外请求、配置在部署时就定了。接口下发适合「配置需要动态调整、不重启就生效」的场景。

产物隔离：别让环境串味

不管哪种注入方式，都要保证不同环境的产物和配置严格隔离，这是安全底线。几条规则：

  1. 生产密钥绝不进前端产物。前端代码是公开的，任何编译进去的东西用户都能看到。真正的密钥（数据库密码、第三方 secret）只能在后端/网关。前端的「配置」只该有公开信息（接口地址、公开的 key、开关）。
  2. 产物按环境+版本归档（呼应静态部署篇）：releases/prod/v1.3.0/、releases/staging/v1.3.0/，别让不同环境的产物混在一个目录互相覆盖。
  3. .env.production 等文件不提交敏感值：.env 只放非敏感默认值和占位，真实的敏感配置走 CI secrets / 部署平台的环境变量注入。

一个真实的坑：开发时为了方便，把测试环境的 token 硬编码在代码里，然后跟着构建进了生产包。表现是生产环境莫名其妙带着测试凭证，甚至被人从打包文件里扒出来。根因就是「把不该进前端的东西编译进了产物」。判断标准很简单：这个值能不能让全世界看到？不能，就不该出现在前端产物里。

CI 里怎么组织多环境

把上面的落到 CI，一个清晰的多环境流水线是这样：

构建期注入方案：
  按分支/tag 触发不同环境的构建部署
  merge 到 main       → 构建 staging 产物 → 部署 staging
  打 v* tag           → 构建 prod 产物    → 部署 prod

运行时注入方案（更优）：
  构建一次，产出一个「环境无关」的产物/镜像
  ├─► 注入 staging 配置 → 部署 staging → 验证
  ├─► 注入 pre 配置     → 部署 pre     → 用生产数据验证
  └─► 注入 prod 配置    → 部署 prod（就是刚才验过的那个产物）

运行时注入方案的漂亮之处：从 staging 到 prod，产物字节级一致，你在 staging 验证过的就是最终上生产的东西，中间没有「重新构建可能引入变化」的风险。这也是为什么我倾向于在多环境、容器化的项目里用运行时注入——它让「环境矩阵」真正成为「同一产物的不同配置视图」，而不是「几个可能有差异的独立构建」。

小结

  1. 环境矩阵（dev/test/staging/pre/prod）的本质是用配置隔离，把同一份代码安全地放进不同危险等级的场景；按需设，别盲目照搬五个。
  2. 配置注入两种范式：构建期注入（每环境构建一次，配置编译进产物）和运行时注入（构建一次，运行时填配置）。
  3. 构建期注入用 Vite import.meta.env + --mode，简单够用，适合环境少、配置稳定的项目。
  4. 运行时注入用「占位 + 启动时替换」最契合容器化，同一镜像换环境变量跑遍所有环境，保证「测过的包 = 上线的包」。
  5. 产物隔离是安全底线：生产密钥绝不进前端产物，产物按环境+版本归档，敏感值走 CI secrets 而非提交进 .env。
  6. 判断某个值该不该进前端产物，就问「能不能让全世界看到」。
  7. 多环境、容器化项目优先运行时注入，让环境矩阵成为「同一产物的不同配置视图」，从 staging 到 prod 产物字节一致。
