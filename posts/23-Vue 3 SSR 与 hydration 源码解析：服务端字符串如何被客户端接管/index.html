Vue 3 SSR 与 hydration 源码解析：服务端字符串如何被客户端接管

发表于2026|更新于2026|Vue框架及周边库
|字数总计:2.2k|阅读时长:9分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：SSR 的目标不是只在服务端生成 HTML，还要让客户端在已有 DOM 上恢复交互能力。服务端负责把组件树渲染成字符串，客户端 hydration 负责让 VNode 认领这些 DOM，并在不一致时修正。

整体链路

服务端：
createSSRApp(App)
  -> renderToString(app)
  -> renderComponentVNode(rootVNode)
  -> renderVNode / renderElementVNode
  -> SSRBuffer
  -> HTML string

客户端：
createSSRApp(App).mount(container)
  -> hydrate(rootVNode, container)
  -> hydrateNode(container.firstChild, vnode)
  -> hydrateElement / hydrateChildren / mountComponent
  -> 绑定事件、ref、指令 hooks

服务端渲染和客户端接管是两条不同链路，但它们共享 VNode、组件实例、render 结果这些核心结构。

服务端入口：renderToString

export async function renderToString(input: App | VNode, context: SSRContext = {}): Promise<string> {
  if (isVNode(input)) {
    return renderToString(createApp({ render: () => input }), context)
  }

  const vnode = createVNode(input._component, input._props)
  vnode.appContext = input._context
  input.provide(ssrContextKey, context)
  const buffer = await renderComponentVNode(vnode)

  const result = await unrollBuffer(buffer as SSRBuffer)
  await resolveTeleports(context)
  return result
}

renderToString 做了几件事：

  1. 如果传入的是裸 VNode，先包成 App。
  2. 创建根组件 VNode，并继承 app context。
  3. 通过 provide 把 SSR context 注入组件树。
  4. 调用 renderComponentVNode 得到 buffer。
  5. 展开 buffer，得到最终 HTML 字符串。

为什么 SSR 使用 Buffer

这里的 Buffer 不是 Node.js 的二进制 Buffer，而是 Vue SSR 自己用的一个临时收集容器。

可以简单理解成：服务端渲染时，Vue 不会一开始就把所有内容拼成最终 HTML 字符串，而是先把普通 HTML 片段、子组件渲染结果、异步组件结果都放进一个数组里。这个数组就是 SSRBuffer。

比如它内部可能长这样：

[
  '<div>',
  '<span>hello</span>',
  Promise.resolve(['<p>async component</p>']),
  '</div>',
]

最后 Vue 再把这个 buffer 展开成最终 HTML：

<div><span>hello</span><p>async component</p></div>

服务端渲染不是简单同步拼接字符串，因为组件里可能有：

  • async setup()
  • serverPrefetch
  • 异步组件
  • Teleport

所以 Vue 先收集为 SSRBuffer：

export function createBuffer() {
  let appendable = false
  const buffer: SSRBuffer = []
  return {
    getBuffer(): SSRBuffer {
      return buffer
    },
    push(item: SSRBufferItem): void {
      const isStringItem = isString(item)
      if (appendable && isStringItem) {
        buffer[buffer.length - 1] += item as string
        return
      }
      buffer.push(item)
      appendable = isStringItem
      if (isPromise(item) || (isArray(item) && item.hasAsync)) {
        buffer.hasAsync = true
      }
    },
  }
}

这个 buffer 可以包含三类内容：

内容 含义
string 普通 HTML 片段
SSRBuffer 子组件 / 子树的嵌套 buffer
Promise<SSRBuffer> 异步组件或异步 setup 的结果

appendable 是一个小优化：连续字符串会合并，减少数组项数量。

renderComponentVNode：SSR 中也会创建组件实例

export function renderComponentVNode(vnode: VNode, parentComponent: ComponentInternalInstance | null = null): SSRBuffer | Promise<SSRBuffer> {
  const instance = (vnode.component = createComponentInstance(vnode, parentComponent, null))
  const res = setupComponent(instance, true /* isSSR */)
  const hasAsyncSetup = isPromise(res)
  let prefetches = instance.sp
  if (hasAsyncSetup || prefetches) {
    const p = Promise.resolve(res).then(() => {
      if (hasAsyncSetup) prefetches = instance.sp
      if (prefetches) return Promise.all(prefetches.map(prefetch => prefetch.call(instance.proxy)))
    })
    return p.then(() => renderComponentSubTree(instance, slotScopeId))
  } else {
    return renderComponentSubTree(instance, slotScopeId)
  }
}

SSR 不会挂载真实 DOM，但仍然需要组件实例，因为：

  • setup() 要执行。
  • props / slots / attrs 要初始化。
  • 组件上下文和依赖注入要可用。
  • serverPrefetch 要收集并等待。

renderVNode：把 VNode 写成 HTML

export function renderVNode(push: PushFn, vnode: VNode, parentComponent: ComponentInternalInstance, slotScopeId?: string): void {
  const { type, shapeFlag, children, dirs, props } = vnode
  if (dirs) {
    vnode.props = applySSRDirectives(vnode, props, dirs)
  }

  switch (type) {
    case Text:
      push(escapeHtml(children as string))
      break
    case Comment:
      push(children ? `<!--${escapeHtmlComment(children as string)}-->` : `<!---->`)
      break
    case Fragment:
      push(`<!--[-->`)
      renderVNodeChildren(push, children as VNodeArrayChildren, parentComponent, slotScopeId)
      push(`<!--]-->`)
      break
    default:
      if (shapeFlag & ShapeFlags.ELEMENT) renderElementVNode(push, vnode, parentComponent, slotScopeId)
      else if (shapeFlag & ShapeFlags.COMPONENT) push(renderComponentVNode(vnode, parentComponent, slotScopeId))
  }
}

可以看到，Fragment 在 SSR 中会被渲染为注释锚点：

<!--[-->
  ...children
<!--]-->

这些锚点对客户端 hydration 很重要，因为 Fragment 没有真实包裹元素，客户端需要靠锚点知道它的边界。

客户端入口：createHydrationFunctions

hydration.ts 位于 runtime-core，但它强依赖 DOM renderer 的 host 操作，所以会接收 rendererInternals：

export function createHydrationFunctions(rendererInternals: RendererInternals<Node, Element>) {
  const {
    mt: mountComponent,
    p: patch,
    o: { patchProp, createText, nextSibling, parentNode, remove, insert, createComment },
  } = rendererInternals
}

根 hydrate 函数：

const hydrate: RootHydrateFunction = (vnode, container) => {
  if (!container.hasChildNodes()) {
    patch(null, vnode, container)
    flushPostFlushCbs()
    container._vnode = vnode
    return
  }

  hydrateNode(container.firstChild!, vnode, null, null, null)
  flushPostFlushCbs()
  container._vnode = vnode
}

如果容器为空，就退化为普通 mount。否则从第一个 DOM 节点开始，让根 VNode 认领 DOM。

hydrateNode：按 VNode 类型认领 DOM

const hydrateNode = (node, vnode, parentComponent, parentSuspense, slotScopeIds, optimized = false): Node | null => {
  optimized = optimized || !!vnode.dynamicChildren
  const isFragmentStart = isComment(node) && node.data === '['
  const onMismatch = () => handleMismatch(node, vnode, parentComponent, parentSuspense, slotScopeIds, isFragmentStart)
  const { type, ref, shapeFlag, patchFlag } = vnode
  let domType = node.nodeType
  vnode.el = node
}

hydrateNode 的核心动作是：

  1. 把 vnode.el 指向浏览器中由服务端 HTML 解析出来的现有 DOM。
  2. 根据 VNode 类型检查 DOM 类型是否匹配。
  3. 匹配则继续 hydrate 子树。
  4. 不匹配则进入 handleMismatch。

文本节点 mismatch

case Text:
  if (domType !== DOMNodeTypes.TEXT) {
    nextNode = onMismatch()
  } else {
    if ((node as Text).data !== vnode.children) {
      warn(`Hydration text mismatch in`, node.parentNode, ...)
      logMismatchError()
      ;(node as Text).data = vnode.children as string
    }
    nextNode = nextSibling(node)
  }
  break

文本不一致时，Vue 会告警并把 DOM 文本修正为客户端期望值。

元素节点 hydration

const hydrateElement = (el, vnode, parentComponent, parentSuspense, slotScopeIds, optimized) => {
  const { type, props, patchFlag, shapeFlag, dirs, transition } = vnode
  const forcePatch = type === 'input' || type === 'option'

  if (shapeFlag & ShapeFlags.ARRAY_CHILDREN && !(props && (props.innerHTML || props.textContent))) {
    let next = hydrateChildren(el.firstChild, vnode, el, parentComponent, parentSuspense, slotScopeIds, optimized)
    while (next) {
      remove(next)
      next = next.nextSibling
    }
  } else if (shapeFlag & ShapeFlags.TEXT_CHILDREN) {
    if (el.textContent !== clientText) {
      el.textContent = vnode.children as string
    }
  }

  if (props) {
    patchProp(el, key, null, props[key], undefined, parentComponent)
  }

  return el.nextSibling
}

元素 hydration 主要做三类工作：

工作 说明
hydrate children 让子 VNode 继续认领子 DOM
检查文本 / children mismatch 服务端多出来的删掉，少了的挂载
patch 必要 props 事件监听、表单值、.prop、自定义元素等需要客户端补丁

注意：大部分静态属性并不会重新 patch，因为服务端 HTML 已经包含它们。客户端重点补的是事件监听，以及 hydration 时发现和客户端 VNode 不一致、必须修正的 DOM 状态。

这里的“必须修正”主要包括几类：

场景 为什么要修正
文本内容不一致 以客户端 VNode 计算结果为准，直接更新 textContent
子节点数量不一致 服务端多出来的节点要删除，少了的节点要补挂载
表单状态 value、checked、indeterminate 等需要以客户端运行时状态为准
事件监听 HTML 里没有真正绑定 JS 函数，必须客户端重新绑定

children 不匹配时如何处理

const hydrateChildren = (node, parentVNode, container, parentComponent, parentSuspense, slotScopeIds, optimized): Node | null => {
  const children = parentVNode.children as VNode[]
  for (let i = 0; i < children.length; i++) {
    const vnode = optimized ? children[i] : (children[i] = normalizeVNode(children[i]))
    if (node) {
      node = hydrateNode(node, vnode, parentComponent, parentSuspense, slotScopeIds, optimized)
    } else {
      patch(null, vnode, container, null, parentComponent, parentSuspense, getContainerType(container), slotScopeIds)
    }
  }
  return node
}

如果服务端 DOM 比客户端 VNode 少，Vue 会用 patch(null, vnode, ...) 挂载缺失节点。

如果服务端 DOM 比客户端 VNode 多，则在 hydrateElement 中继续删除多余 DOM：

while (next) {
  logMismatchError()
  const cur = next
  next = next.nextSibling
  remove(cur)
}

mismatch 的兜底：handleMismatch

handleMismatch 的思路是：当前 DOM 无法被当前 VNode 认领，那就移除错误 DOM，并按客户端 VNode 重新 patch。

const handleMismatch = (node, vnode, parentComponent, parentSuspense, slotScopeIds, isFragment): Node | null => {
  warn(`Hydration node mismatch`, ...)
  logMismatchError()
  vnode.el = null
  // 后续移除旧 DOM，并调用 patch(null, vnode, container, next, ...)
}

这也是 hydration 的底线：尽量复用服务端 DOM，但一致性比复用更重要。

SSR 与 hydration 的关键设计

设计 作用
SSRBuffer 同时容纳同步字符串和异步子树
Fragment 注释锚点 让无包裹节点的片段在客户端可定位
vnode.el = node 让客户端 VNode 认领服务端 DOM
mismatch 修正 保证最终 DOM 与客户端 VNode 一致
props 选择性 patch 避免重复设置静态属性，只补事件和必须状态
flushPostFlushCbs hydration 完成后执行 mounted / directive 等后置副作用

小结

SSR 负责在服务端把组件输出成 HTML，hydration 负责在客户端复用这份 HTML 对应的 DOM，让 VNode 和真实 DOM 对齐，并恢复事件、组件实例和响应式更新能力，最终让页面获得和 SPA 类似的交互体验。

SSR 与 hydration 可以分成两句话理解：

  1. 服务端：组件树先渲染成 SSRBuffer，再展开成 HTML 字符串。
  2. 客户端：VNode 不重新创建 DOM，而是认领现有 DOM；不一致时再修正或重新挂载。

所以 hydration 不是“再渲染一遍”，而是“在服务端 DOM 基础上恢复 VNode、事件、ref 和组件副作用”。这正是 Vue 3 SSR 能兼顾首屏性能和客户端交互的关键。
