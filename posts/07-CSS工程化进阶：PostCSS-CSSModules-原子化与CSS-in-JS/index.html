CSS 工程化进阶：PostCSS、CSS Modules、Sass 与原子化、CSS-in-JS 的取舍

发表于2026|更新于2026|工程化
|字数总计:2k|阅读时长:6分钟

前言：在构建工具链里，CSS 是个常被低估的部分。基础篇我们聊过 CSS 方案选型，这一篇站在构建的角度往深里走：CSS 是怎么被打包工具处理的——PostCSS 插件链怎么跑、CSS Modules 怎么做局部作用域、Sass 和原子化 CSS、CSS-in-JS 各自在工程上的代价。重点是「构建时发生了什么」和「怎么选」。

CSS 也要经过一条编译链

很多人以为 CSS 是直接拿来用的，其实在现代构建里，一段 CSS 从源码到产物，要经过和 JS 类似的处理链：

源 CSS（可能是 .scss / .css）
   │ 预处理器（Sass/Less，可选）：变量、嵌套、mixin → 标准 CSS
   ▼
标准 CSS
   │ PostCSS 插件链：autoprefixer、嵌套、压缩等
   ▼
处理后的 CSS
   │ 打包器：提取成文件 or 注入 JS、加 hash、按需生成/清理
   ▼
产物 CSS

理解这条链，你才知道每个工具卡在哪一环、为什么需要它。

PostCSS：CSS 界的 Babel

PostCSS 本身不做任何转换，它只做一件事：把 CSS 解析成 AST，交给插件去改，再生成 CSS。这和 Babel 对 JS 的处理是一个套路——所以我常说 PostCSS 是「CSS 界的 Babel」。

它的能力完全取决于装了哪些插件，插件按顺序组成一条链：

// postcss.config.js
module.exports = {
  plugins: [
    require('postcss-import'),       // 1. 处理 @import，合并文件
    require('postcss-nested'),       // 2. 支持嵌套语法
    require('autoprefixer'),         // 3. 自动加浏览器前缀
    require('cssnano'),              // 4. 压缩（一般只在生产）
  ],
}

链条从上往下执行。最常用的插件是 autoprefixer——它根据 browserslist（对，又是它，和 Babel 共享同一份兼容性声明）自动补 -webkit-、-moz- 等前缀：

/* 你写 */
.box { display: flex; user-select: none; }

/* autoprefixer 根据 browserslist 自动补全 */
.box { display: flex; -webkit-user-select: none; user-select: none; }

关键认知：Vite、Next.js 等工具默认就内置了 PostCSS，你放一个 postcss.config.js 就能扩展插件链，不用自己接管整个流程。browserslist 配一份，Babel 和 autoprefixer 都读它。

CSS Modules：构建时做局部作用域

CSS 全局作用域是老大难——两个组件都写 .title，就会互相覆盖。CSS Modules 在构建时解决这个问题：把类名编译成全局唯一的哈希名。

/* Button.module.css */
.title { color: red; }

// Button.jsx
import styles from './Button.module.css'
// styles.title 在构建后变成类似 'Button_title_a1b2c' 的唯一类名
export default () => <h1 className={styles.title}>Hi</h1>

构建后产物大致是：

.Button_title_a1b2c { color: red; }

<h1 class="Button_title_a1b2c">Hi</h1>

原理就是构建工具把 .title 这个类名替换成「文件名 + 类名 + hash」的组合，保证不同文件的同名类不冲突。Vite 里只要文件名带 .module.css 就自动启用，零配置。

CSS Modules 的好处是：作用域隔离、依然是纯 CSS（学习成本低）、构建时完成无运行时开销。我的看法是，它是「样式隔离」这个需求里性价比最高的方案之一。

Sass：预处理器解决「写起来麻烦」

Sass（.scss）解决的是另一类问题——原生 CSS 写起来啰嗦：没有变量（CSS 变量出现前）、不能嵌套、没有 mixin 复用。

// 变量、嵌套、mixin
$primary: #3498db;

@mixin center {
  display: flex;
  justify-content: center;
}

.card {
  color: $primary;
  .title { @include center; } // 嵌套
}

Sass 在构建时被编译成标准 CSS（Vite 里装 sass 依赖就能用 .scss）。它和 CSS Modules 不冲突——你完全可以写 Button.module.scss，同时享受作用域隔离和 Sass 语法。

注意取舍：现在原生 CSS 已经有了自定义属性（--var）、原生嵌套等能力，Sass 的部分价值被削弱。新项目如果只用变量和嵌套，可以先评估原生 CSS 够不够，不一定非上 Sass。

原子化 CSS：换一种写样式的思路

原子化 CSS（以 Tailwind、UnoCSS 为代表）是近几年的主流方案。它的思路是：不写自定义类，而是用大量「单一职责的工具类」组合：

<!-- 不写 .card 类，直接用工具类拼 -->
<div class="flex justify-center p-4 text-blue-500 rounded">原子化</div>

工程角度，原子化的核心优势在构建产物：因为类是预定义的、可复用的，构建工具能扫描你实际用到的类，只生成这些类的 CSS。所以无论项目多大，CSS 体积都趋于收敛，不会像传统写法那样线性膨胀。

传统 CSS：组件越多 → 自定义类越多 → CSS 越大
原子化：  组件越多 → 复用同一批工具类 → CSS 趋于稳定

这里说的不是 JS 那种严格意义上的 Tree Shaking。普通 CSS 很难安全判断某个选择器一定没被用到，因为类名可能来自模板、运行时字符串、CMS 内容。原子化 CSS 的优势更准确地说是「按扫描结果生成用到的工具类」，PurgeCSS 这类方案则是「扫描后清理看起来没用到的选择器」，二者都要注意动态类名的 safelist 配置。

代价是 HTML 里类名很长、可读性见仁见智、有一定学习成本。我的判断：团队项目、追求一致性和最终体积，原子化很香；但它需要团队达成共识，不然「一半人写 Tailwind 一半人写自定义类」反而更乱。

CSS-in-JS：把样式写进 JS

CSS-in-JS（styled-components、Emotion 等）把样式直接写在组件里：

import styled from 'styled-components'

const Button = styled.button`
  color: ${(props) => props.primary ? 'white' : 'black'};
  padding: 8px 16px;
`

它的卖点是：天然作用域隔离、样式能用 JS 变量/props 动态计算、组件和样式同文件。但工程上它有明确的代价，必须分清两种实现：

类型 代表 代价
运行时（runtime） styled-components、Emotion 运行时解析样式、生成类名，有性能开销，SSR 也更复杂
零运行时（zero-runtime） 编译期方案 构建时把样式抽成静态 CSS，无运行时开销

我的实战感受：传统运行时 CSS-in-JS 在大型应用里的性能和 SSR 成本，让它这几年明显降温。现在的趋势是要么用原子化 CSS，要么用零运行时的 CSS-in-JS（构建期把样式编译成静态 CSS）。如果选运行时方案，要清楚它的开销在哪。

怎么选：一张取舍表

方案 作用域隔离 运行时开销 学习成本 适合
原生 CSS + 约定 无（靠命名约定如 BEM） 无 低 小项目、landing page
CSS Modules 有（构建时） 无 低 大多数组件化项目
Sass + CSS Modules 有 无 中 需要复杂样式逻辑
原子化（Tailwind/UnoCSS） 不需要（工具类） 无 中 团队项目、控制体积
运行时 CSS-in-JS 有 有 中 强动态样式、能接受开销

我的默认选择：组件化项目用 CSS Modules（需要复杂逻辑就配 Sass），团队追求一致性和体积用原子化。运行时 CSS-in-JS 除非有强需求，否则要谨慎评估开销。

小结

  1. CSS 在构建里也走一条编译链：预处理器 → PostCSS 插件链 → 打包器提取/注入，理解这条链才知道每个工具的位置。
  2. PostCSS 是「CSS 界的 Babel」，本身不转换，能力全靠插件链；autoprefixer 最常用，和 Babel 共享 browserslist。
  3. CSS Modules 在构建时把类名哈希成全局唯一，零运行时解决作用域隔离，性价比高。
  4. Sass 解决「写起来啰嗦」，但原生 CSS 已有变量和嵌套，新项目要先评估是否真的需要。
  5. 原子化 CSS 的工程优势在产物体积趋于收敛，适合团队项目，但需要团队共识。
  6. CSS-in-JS 要分清运行时和零运行时：运行时方案有性能和 SSR 代价，近年降温，慎选。
