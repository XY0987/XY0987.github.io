i18n 国际化工程化与质量治理

发表于2026|更新于2026|工程化
|字数总计:3.8k|阅读时长:14分钟

前言：很多项目一开始把 i18n 理解成“把中文抽成变量”。这个理解没错，但只停在第一层。真正进入团队协作后，i18n 要解决的是：文案不能漏、语言包不能乱、格式不能靠手写、上线前要能被工具拦住。

i18n 不只是翻译字符串

入门时可以把 i18n 理解成：

// ❌ 反面案例
export function SubmitButton() {
  return <button>提交</button>
}

改成：

// ✅ 正面案例
export function SubmitButton() {
  return <button>{t('common.submit')}</button>
}

这个理解是对的，但不完整。

真正的问题是：项目里所有和语言、地区、书写习惯有关的假设，都不能散落在业务代码里。

常见例子包括：

类型 反面写法 问题
文案 暂无数据 切语言时不会变
日期 2026-07-11 不同地区展示习惯不同
金额 ￥99.00 货币符号、分隔符、位置都可能不同
复数 1 items 英文复数规则错误
布局方向 默认从左到右 阿拉伯语、希伯来语等 RTL 场景会出问题

我的理解是：i18n 工程化不是让页面“能翻译”，而是让语言环境差异变成可配置、可检查、可测试的工程能力。

i18n 要处理哪些差异

这里要分清两个概念：哪些差异属于 i18n 问题，以及哪些内容应该放进语言包。

i18n 要处理的范围比语言包更大：

差异类型 应该怎么处理 例子
文案 放进语言包 提交 / Submit
语序 整句放进语言包，不要拆词拼接 张三创建了订单 / Order was created by Tom
复数 交给 i18n 框架或消息函数处理 1 message / 2 messages
日期、时间、金额 用 Intl 或统一格式化工具 2026年7月11日 / Jul 11, 2026
方向 用 dir、CSS 逻辑属性、组件布局适配 LTR / RTL

所以 i18n 不是只有语言包。语言包主要解决自然语言表达问题，而格式和方向更适合交给格式化 API、样式体系和组件布局处理。

哪些内容应该放进语言包

不是所有和 i18n 有关的东西都要丢进语言包。

通常这样区分：

内容 是否放进语言包 原因
按钮、提示、标题 是 用户可见文案
表单校验信息 是 不同语言表达差异很大
空状态、错误状态 是 直接影响用户理解
带变量的整句文案 是 不同语言语序可能不同
复数文案 是，但要用复数规则处理 不能简单拼 s
日期、时间、金额格式 否，用格式化 API 格式规则比字符串替换复杂
LTR / RTL 方向 否，用布局和样式处理 方向不是一句文案
埋点字段、接口枚举 否 给系统消费，不是给用户看
CSS class、测试 id 否 工程标识，不是展示内容

一个常见误区是：把所有字符串都抽出去。

这样会让语言包变成垃圾桶：

export const zhCN = {
  buttonClassName: 'primary-button',
  orderStatusPaid: 'PAID',
  submitText: '提交',
}

这里 submitText 应该国际化，但 buttonClassName 和 PAID 不应该。

判断标准很简单：这个字符串是不是直接展示给用户看的自然语言。如果是，优先纳入 i18n；如果不是，先别急着抽。

语言包结构要稳定

小项目最容易写成这样：

export const zhCN = {
  submit: '提交',
  cancel: '取消',
  userName: '用户名',
}

短期看没问题，但项目大了以后会很快失控：

  • key 不知道属于哪个模块；
  • 不同页面命名风格不一致；
  • 删除页面后不知道语言包能不能删；
  • 英文包漏 key 只能上线后才发现。

更推荐按业务域分层：

export const zhCN = {
  common: {
    submit: '提交',
    cancel: '取消',
    loading: '加载中',
  },
  user: {
    title: '用户管理',
    create: '新建用户',
    deleteConfirm: '确认删除该用户吗？',
  },
  order: {
    title: '订单管理',
    empty: '暂无订单',
  },
} as const

英文包保持同样结构：

export const enUS = {
  common: {
    submit: 'Submit',
    cancel: 'Cancel',
    loading: 'Loading',
  },
  user: {
    title: 'User Management',
    create: 'Create User',
    deleteConfirm: 'Are you sure you want to delete this user?',
  },
  order: {
    title: 'Orders',
    empty: 'No orders',
  },
} as const

语言包的结构一旦稳定，后面才能做类型约束和自动检查。

用 TypeScript 约束 key

如果 t 函数接收任意字符串，这种错误很难提前发现：

export function UserPage() {
  return <h1>{t('user.tilte')}</h1>
}

title 拼成了 tilte，运行时可能只会显示 key，甚至直接空白。

可以先写一个类型工具，把嵌套对象转换成点路径。

环境说明：

  • Node.js 18 及以上；
  • TypeScript 5；
  • 使用 pnpm。

安装：

pnpm add -D typescript

示例文件 i18n.ts：

const zhCN = {
  common: {
    submit: '提交',
    cancel: '取消',
  },
  user: {
    title: '用户管理',
    create: '新建用户',
  },
} as const

type DotPrefix<T extends string> = T extends '' ? '' : `.${T}`

type DotNestedKeys<T> = {
  [K in keyof T & string]: T[K] extends Record<string, unknown>
    ? `${K}${DotPrefix<DotNestedKeys<T[K]>>}`
    : K
}[keyof T & string]

type MessageKey = DotNestedKeys<typeof zhCN>

function t(key: MessageKey) {
  return key
}

t('user.title')
t('common.submit')

// 取消下面这行注释，TypeScript 会报错
// t('user.tilte')

执行类型检查：

pnpm tsc i18n.ts --noEmit

这段代码的价值不是实现一个完整 i18n 框架，而是说明一个原则：翻译 key 应该尽量从“运行时字符串”变成“编译期可检查的类型”。

实际项目里可以基于 vue-i18n、react-intl、i18next 做封装，但思路一样：不要让业务代码随便写裸字符串 key。

这些 i18n 库的底层思路其实很接近。

可以先把它们理解成一个“运行时查表系统”：

当前语言 locale
  │
  ▼
选择对应语言包
  │
  ▼
根据 key 找到模板
  │
  ▼
把变量、复数、日期格式等规则填进去
  │
  ▼
返回最终展示文案

比如业务代码调用：

t('user.deleteConfirm', { name: '张三' })

i18n 库内部大致会做几件事：

  1. 读取当前语言，比如 zh-CN；
  2. 到 zh-CN 语言包里找到 user.deleteConfirm；
  3. 拿到类似 确认删除用户 {name} 吗？ 的模板；
  4. 把 {name} 替换成 张三；
  5. 返回 确认删除用户 张三 吗？。

vue-i18n、react-intl、i18next 的差别主要在接入方式和生态：

库 常见使用场景 核心特点
vue-i18n Vue 项目 和 Vue 响应式、组件上下文结合紧密
react-intl React 项目 基于 ICU MessageFormat，适合处理复数、日期、数字
i18next 多框架项目 框架无关，插件生态丰富，可配合 React、Vue、Node 使用

但从工程治理角度看，重点不是选哪个库，而是把这几件事管住：

  • 语言包结构要稳定；
  • key 要尽量可类型检查；
  • 缺失翻译要能在 CI 里暴露；
  • 业务代码不要绕过 t 直接写死文案；
  • 日期、金额、复数不要靠手动字符串拼接。

检查语言包是否缺 key

类型只能约束调用方，语言包之间是否对齐，还需要额外检查。

比如中文包有 order.empty，英文包漏了：

const zhCN = {
  order: {
    title: '订单管理',
    empty: '暂无订单',
  },
}

const enUS = {
  order: {
    title: 'Orders',
  },
}

这种问题适合写脚本在 CI 里拦。

创建 scripts/check-i18n-keys.mjs：

const zhCN = {
  common: {
    submit: '提交',
    cancel: '取消',
  },
  order: {
    title: '订单管理',
    empty: '暂无订单',
  },
}

const enUS = {
  common: {
    submit: 'Submit',
    cancel: 'Cancel',
  },
  order: {
    title: 'Orders',
  },
}

function flattenKeys(obj, prefix = '') {
  return Object.entries(obj).flatMap(([key, value]) => {
    const path = prefix ? `${prefix}.${key}` : key

    if (value && typeof value === 'object' && !Array.isArray(value)) {
      return flattenKeys(value, path)
    }

    return path
  })
}

const baseKeys = new Set(flattenKeys(zhCN))
const targetKeys = new Set(flattenKeys(enUS))

const missingKeys = [...baseKeys].filter((key) => !targetKeys.has(key))
const extraKeys = [...targetKeys].filter((key) => !baseKeys.has(key))

if (missingKeys.length || extraKeys.length) {
  console.error('i18n key check failed')

  if (missingKeys.length) {
    console.error('Missing keys:', missingKeys)
  }

  if (extraKeys.length) {
    console.error('Extra keys:', extraKeys)
  }

  process.exit(1)
}

console.log('i18n keys are aligned')

执行：

node scripts/check-i18n-keys.mjs

预期输出：

i18n key check failed
Missing keys: [ 'order.empty' ]

真实项目里不要把语言包直接写在脚本里，可以从 src/locales/zh-CN.ts、src/locales/en-US.ts 读取。核心逻辑不变：以一个基准语言为准，检查其他语言是否缺 key、是否多了废弃 key。

检查硬编码文案

i18n 项目里最常见的问题不是框架不会用，而是开发时顺手写了中文：

export function EmptyOrder() {
  return <div>暂无订单</div>
}

这类问题可以通过 ESLint 自定义规则做得很精细，也可以先用简单脚本兜底。

创建 scripts/check-hardcoded-zh.mjs：

import { readdirSync, readFileSync, statSync } from 'node:fs'
import { join } from 'node:path'

const root = 'src'
const fileExtensions = new Set(['.ts', '.tsx', '.js', '.jsx', '.vue'])
const chineseRegExp = /[\u4e00-\u9fa5]/

function walk(dir) {
  return readdirSync(dir).flatMap((name) => {
    const fullPath = join(dir, name)
    const stat = statSync(fullPath)

    if (stat.isDirectory()) {
      return walk(fullPath)
    }

    return fullPath
  })
}

function getExtension(file) {
  const match = file.match(/\.[^.]+$/)
  return match ? match[0] : ''
}

const files = walk(root).filter((file) => fileExtensions.has(getExtension(file)))
const violations = []

for (const file of files) {
  const lines = readFileSync(file, 'utf8').split('\n')

  lines.forEach((line, index) => {
    if (chineseRegExp.test(line) && !line.includes('i18n-ignore')) {
      violations.push(`${file}:${index + 1} ${line.trim()}`)
    }
  })
}

if (violations.length) {
  console.error('Found hardcoded Chinese text:')
  console.error(violations.join('\n'))
  process.exit(1)
}

console.log('No hardcoded Chinese text found')

这个脚本很粗糙，但对很多团队已经够用，尤其适合早期治理。

可以允许少量例外：

const brandName = '飞书' // i18n-ignore

注意不要把这个脚本当成银弹。它只能发现“源码里出现中文”，不能判断这段中文是不是应该翻译，也不能识别服务端返回的文案。更严肃的项目可以进一步接入 ESLint 自定义规则，按 AST 判断 JSX 文本、字符串字面量、模板字符串。

格式化不要靠拼字符串

很多 i18n 问题不是翻译错，而是格式写死了。

比如日期：

// ❌ 反面案例
const text = `${year}年${month}月${day}日`

更合理的做法是使用 Intl.DateTimeFormat：

const date = new Date('2026-07-11T00:00:00Z')

const zhText = new Intl.DateTimeFormat('zh-CN', {
  dateStyle: 'medium',
  timeZone: 'UTC',
}).format(date)

const enText = new Intl.DateTimeFormat('en-US', {
  dateStyle: 'medium',
  timeZone: 'UTC',
}).format(date)

console.log(zhText)
console.log(enText)

数字和金额也一样：

const price = 123456.78

console.log(
  new Intl.NumberFormat('zh-CN', {
    style: 'currency',
    currency: 'CNY',
  }).format(price),
)

console.log(
  new Intl.NumberFormat('en-US', {
    style: 'currency',
    currency: 'USD',
  }).format(price),
)

文案走 i18n，日期、数字、金额优先走 Intl API，不要自己手写格式规则。

这样做的好处是，把地区差异交给标准 API，而不是在业务代码里堆一堆 if (locale === 'zh-CN')。

复数和变量插值要提前设计

中文里很多时候不关心复数：

1 条消息
2 条消息

英文就不一样：

1 message
2 messages

所以不要这样写：

// ❌ 反面案例
const text = `${count} messages`

更好的方式是让语言包表达复数规则。

一个最小示例：

const messages = {
  en: {
    inbox(count: number) {
      return count === 1 ? `${count} message` : `${count} messages`
    },
  },
  zh: {
    inbox(count: number) {
      return `${count} 条消息`
    },
  },
}

console.log(messages.en.inbox(1))
console.log(messages.en.inbox(2))
console.log(messages.zh.inbox(2))

真实项目里通常会交给 i18n 框架处理，比如 ICU MessageFormat。这里想强调的是：不要把变量顺序、复数规则写死在组件里。

因为不同语言的语序不一样。

中文可以是：

张三 创建了订单 1001

英文可能是：

Order 1001 was created by Tom

如果组件里写成固定拼接：

`${userName} 创建了订单 ${orderId}`

后面翻译会很痛苦。应该把整句交给语言包，而不是只翻译几个单词。

RTL 不能等上线后再想

如果项目只面向中文和英文，很多团队会忽略 RTL。

但只要未来可能支持阿拉伯语、希伯来语，就要尽早避免写死方向。

常见问题包括：

场景 问题
margin-left / margin-right RTL 下方向相反
左箭头、右箭头 翻页、返回图标可能需要镜像
文本对齐 默认 left 不一定合理
弹层位置 从左展开还是从右展开可能不同

现代 CSS 可以优先使用逻辑属性：

.card {
  padding-inline: 16px;
  margin-block: 12px;
  text-align: start;
}

少写：

.card {
  padding-left: 16px;
  padding-right: 16px;
  text-align: left;
}

这部分和前面的 CSS 工程化、a11y 是有关联的：方向、阅读顺序、焦点流转都会影响真实用户体验。

i18n 在 CI 里怎么落地

i18n 检查不要只靠人工 Review。

可以在 package.json 里加脚本：

{
  "scripts": {
    "check:i18n-keys": "node scripts/check-i18n-keys.mjs",
    "check:i18n-hardcoded": "node scripts/check-hardcoded-zh.mjs",
    "check:i18n": "pnpm check:i18n-keys && pnpm check:i18n-hardcoded"
  }
}

CI 里执行：

pnpm check:i18n

如果项目已经有完整质量流水线，可以放在 lint 之后、测试之前：

format:check
  │
  ▼
lint
  │
  ▼
check:i18n
  │
  ▼
typecheck
  │
  ▼
test

为什么放在这里？

因为 i18n key 和硬编码文案检查通常很快，失败也容易修。越便宜的检查越早跑，能减少开发者等待时间。

Code Review 里看什么

自动化检查之外，Review 还要关注这些问题：

  • 新增用户可见文案有没有走 t；
  • 语言包 key 命名是否属于正确业务域；
  • 是否把整句放进语言包，而不是拆成几个词拼接；
  • 日期、金额、数字是否使用 Intl 或统一格式化工具；
  • 表单校验、空状态、错误提示有没有覆盖；
  • 是否引入了不可翻译的图片文案；
  • 样式是否写死 left、right，未来是否影响 RTL。

工具能拦住漏 key 和硬编码，但判断“这句话是不是可翻译、翻译后语序是否合理”，还是需要人。

小结

  1. i18n 的第一层是文案变量化，更深一层是把语言和地区差异纳入工程体系。
  2. 语言包结构要稳定，按业务域组织，避免 key 变成全局垃圾桶。
  3. 翻译 key 应尽量类型化，减少运行时才发现拼错的问题。
  4. 缺 key、硬编码文案适合接入脚本和 CI，不要只靠人工 Review。
  5. 日期、数字、金额、复数、RTL 都是 i18n 的一部分，不能只靠字符串替换解决。
