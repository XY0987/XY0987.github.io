Claude Code Agent View 与 Background Agents 解析：后台多任务怎么跑

发表于2026|更新于2026|AI相关
|字数总计:3.9k|阅读时长:13分钟

前言：Dynamic Workflows 是“让 Claude 写脚本编排一堆子 Agent”，而 Agent View / Background Agents 是另一条路线：让多个完整 Claude Code 会话在后台并行跑，用户只在需要介入时回来处理。 这篇讲清楚它解决什么问题、怎么工作、和 Subagents / Workflows 有什么区别。

Agent View 是什么

Agent View 是 Claude Code 用来管理多个后台会话的界面。

官方入口是：

claude agents

它会打开一个列表视图，每一行是一个 background session，也就是一个完整的 Claude Code 会话。

这些会话可以：

  • 在后台继续工作；
  • 独立读代码、改代码、跑命令；
  • 需要权限或用户输入时暂停；
  • 完成后等待你审查；
  • 你可以随时 attach 进去继续对话；
  • 也可以 detach 回到总览界面。

用一句话说：

Agent View 是 Claude Code 的“后台任务管理器”。

它有点像：

  • IDE 的任务面板；
  • GitHub Actions 的运行列表；
  • tmux 里的多窗口；
  • 加上一个可以随时接管的 AI Agent。

它解决的核心问题

普通 Claude Code 是一个前台会话。

你让它修一个 bug，它就在当前终端里跑。它没完成前，你基本就在等。

但真实开发中，经常有很多互不相关的任务：

  • 一个任务调查 flaky test；
  • 一个任务修文档；
  • 一个任务审 PR；
  • 一个任务跑依赖升级；
  • 一个任务重构小模块；
  • 一个任务分析线上日志。

这些任务不一定需要你一直盯着。

Agent View 的价值就是：把 Claude Code 从“单会话助手”变成“多后台任务系统”。

传统单会话：

你 ──▶ Claude Code ──▶ 等待完成 ──▶ 下一个任务

Agent View：

              ┌─▶ 后台 Agent A：修测试
你 ──▶ 调度面板 ├─▶ 后台 Agent B：审 PR
              ├─▶ 后台 Agent C：查日志
              └─▶ 后台 Agent D：更新文档

你只处理：需要输入、需要权限、需要审查的节点

这就是它的定位。

Background Agent 不是 Subagent

这点很容易混。

Claude Code 里现在有好几种“多个 Agent”的形态：

能力 本质 适合场景
Subagent 主会话临时派出的子任务 Agent 快速研究、隔离上下文、返回摘要
Background Agent 完整 Claude Code 会话在后台运行 多个独立任务并行推进
Agent Teams 多个 Claude Code 会话组成团队协作 需要通信、任务列表、协作分工
Dynamic Workflows JavaScript workflow 编排大量 subagents 大规模、可重复、强编排任务

Subagent 更像“派一个同事去查一下，回来汇报”。

Background Agent 更像“开一个独立项目分支，让一个人自己推进，之后我再来看结果”。

关键差异：

维度 Subagent Background Agent
是否完整 Claude Code 会话 否 是
是否在后台持续存在 通常不是 是
是否可 attach 进去继续聊 通常不行 可以
是否适合长任务 一般 适合
是否适合多任务面板管理 不适合 适合
文件修改隔离 依赖配置 通常可用 worktree 隔离

我的理解是：Subagent 是上下文隔离工具，Background Agent 是任务并行工具。

怎么启动后台任务

官方文档里主要有三种方式。

方式一：从 Agent View 里启动

先打开：

claude agents

然后在底部输入任务，比如：

investigate why the checkout test is flaky

按回车后，它会创建一个新的后台 Claude Code 会话。

注意：在 Agent View 底部输入的每条 prompt，通常是 dispatch 一个新后台任务，而不是给当前某个任务发 follow-up。

方式二：把当前会话后台化

在已有 Claude Code 会话里：

/bg

或者：

/background

也可以顺便补一条任务：

/bg run the related tests and fix any failures

这适合当前任务跑久了，你想先把它放后台，继续做别的事。

方式三：从 Shell 直接启动

claude --bg "investigate the flaky checkout test"

还可以指定名字：

claude --bg --name "flaky-checkout" "investigate the flaky checkout test"

也可以指定 Agent：

claude --agent code-reviewer --bg "review PR 1234"

这就很适合脚本化、批量任务、命令行调度。

Agent View 里能看到什么

Agent View 本质上是一个状态面板。

它会显示每个后台 session 的状态。

常见状态包括：

状态 含义
Working Claude 正在工作，可能在读文件、跑命令或生成响应
Needs input 等待用户输入或权限确认
Idle 当前空闲，等待下一条 prompt
Completed 任务完成
Failed 会话因错误结束
Stopped 会话被用户停止

这里最重要的是 Needs input。

因为后台任务的理想使用方式不是让你一直看输出，而是：

  1. 你派发多个任务；
  2. 它们自己跑；
  3. 哪个需要你介入，哪个进入 Needs input；
  4. 你只处理阻塞点。

这很像“管理队列”，而不是“盯着一个终端”。

Peek、Reply、Attach、Detach

Agent View 的交互方式可以拆成四个动作。

Peek：快速看一眼

选中某个后台任务，按 Space，可以打开 peek panel。

它适合看：

  • 最近输出；
  • 当前阻塞问题；
  • Claude 想让你批准什么；
  • 任务是否完成；
  • 有没有 PR 或结果摘要。

Peek 的特点是轻量，不需要完整进入这个会话。

Reply：直接回复

如果 peek panel 里 Claude 在等你回答，你可以直接输入回复。

比如：

Use the second approach, but do not change the public API.

如果要发送 shell 命令，可以用 ! 前缀。

Attach：进入完整会话

选中会话后按 Enter，进入完整 Claude Code 会话。

Attach 后就像普通 Claude Code：

  • 可以继续对话；
  • 可以输入 slash command；
  • 可以查看完整上下文；
  • 可以批准权限；
  • 可以要求它改方向。

Detach：回到面板

从 attached 会话返回 Agent View，就是 detach。

它不会停止后台任务，只是你不再盯着它。

这套交互很像：

Agent View 总览
  ├─ Peek：看一眼
  ├─ Reply：轻量回复
  ├─ Attach：进入完整会话
  └─ Detach：回到总览

Worktree 隔离：后台 Agent 为什么不容易互相打架

多个后台 Agent 同时改代码，最怕什么？

不是慢，而是互相覆盖。

比如：

  • Agent A 在改 src/user.ts；
  • Agent B 也在改 src/user.ts；
  • 两个人都以为自己改得对；
  • 最后工作区一团乱。

Claude Code 为后台 session 设计了 worktree 隔离。

典型路径类似：

.claude/worktrees/

后台 session 在需要编辑文件前，可以进入独立 Git worktree。

这样每个后台任务都有自己的工作副本：

主工作区
  │
  ├── background-agent-A-worktree
  │     └── 修 flaky test
  │
  ├── background-agent-B-worktree
  │     └── 更新文档
  │
  └── background-agent-C-worktree
        └── 重构组件

好处是：

  • 多个 Agent 可以并行改代码；
  • 不会直接污染主 working copy；
  • 你可以审查每个 worktree 的 diff；
  • 不满意可以丢弃；
  • 满意再 merge / cherry-pick / commit。

但也有风险：如果你在 Agent View 里删除某个 session，相关 worktree 可能也会被删除，未提交修改可能丢失。

所以我的建议是：删除后台任务前，先确认 worktree 里的改动是否要保留。

怎么配置后台 worktree 行为

官方 Settings 里有 worktree 相关配置。

例如：

{
  "worktree": {
    "bgIsolation": "worktree",
    "baseRef": "head",
    "symlinkDirectories": ["node_modules"],
    "sparsePaths": ["packages/app", "shared"]
  }
}

几个字段的意思：

字段 作用
bgIsolation 后台任务是否用 worktree 隔离，常见值是 worktree 或 none
baseRef 新 worktree 从哪个 ref 创建，如远端默认分支或当前 HEAD
symlinkDirectories 大目录用软链，避免重复复制，比如 node_modules
sparsePaths 大仓库只 checkout 部分目录

如果你不想后台 Agent 自动进入 worktree，可以设置：

{
  "worktree": {
    "bgIsolation": "none"
  }
}

但我不建议团队项目这么做。

除非你非常确定后台任务不会并行改同一批文件，否则 worktree 隔离是更安全的默认值。

Supervisor：后台会话为什么能持续存在

后台 session 不是简单的 shell 子进程。

官方文档里提到，它由本地的 per-user supervisor process 管理。

可以理解成：

Agent View
   │
   ▼
Supervisor 进程
   ├── Background Session A
   ├── Background Session B
   └── Background Session C

Supervisor 负责：

  • 管理后台会话；
  • 持久化状态；
  • 让 session 在 detach 后继续运行；
  • 在需要时重新 attach；
  • 在空闲太久后停止进程以节省资源；
  • Claude Code 更新后重新连接会话。

相关本地状态大致会放在：

~/.claude/daemon.log
~/.claude/daemon/roster.json
~/.claude/jobs/<id>/state.json
~/.claude/jobs/<id>/tmp/

这些文件通常不需要手动编辑。

我的理解是：Agent View 不只是 UI，它背后有一个本地任务运行时。

后台 Shell Job：不一定每个后台任务都是 AI

Agent View 还支持后台 shell job。

比如在 Agent View 里输入：

! npm test

或者从 shell 启动：

claude --bg --exec 'npm test'

这种任务不调用模型，只是跑命令。

它适合：

  • 长时间测试；
  • 构建任务；
  • lint；
  • benchmark；
  • 本地服务启动。

这点很实用，因为你可以把 AI 任务和普通工程任务放在一个面板里看。

权限模式怎么继承

后台任务不是没有权限边界。

它会读取运行目录里的 Settings。

不同启动方式权限来源略有不同：

启动方式 权限来源
/bg 把当前会话后台化 继承当前会话权限模式
claude agents 面板 dispatch 使用该目录 Settings 的默认权限模式
claude --bg 使用该目录 Settings 的默认权限模式
指定 subagent 可使用 subagent frontmatter 里的 permissionMode

需要注意：auto 和 bypassPermissions 这类高风险模式，通常需要你先在交互式场景里确认，不能让后台任务无感越权。

我的建议是：

  • 后台任务默认用 default 或 acceptEdits；
  • 高风险项目用 plan；
  • 不要轻易给后台任务 bypassPermissions；
  • 涉及外部输入的后台任务更要谨慎。

适合哪些场景

场景一：并行修多个互不相关的小问题

比如：

Agent A：修登录页文案
Agent B：补 Button 组件测试
Agent C：更新 README
Agent D：调查一个 flaky test

这些任务互不依赖，适合放后台并行跑。

你不需要盯着每个任务，只需要最后看结果。

场景二：PR 审查和问题跟进

可以给每个 PR 一个后台 Agent：

claude --agent code-reviewer --bg --name "review-pr-1024" "review PR 1024"

它可以：

  • 看 diff；
  • 找风险；
  • 总结变更；
  • 生成 review comment；
  • 等你最终确认。

这比在一个大对话里连续审多个 PR 清晰得多。

场景三：长时间测试和修复

比如：

run the test suite, investigate failures, and propose fixes

这类任务可能跑很久。

放前台，你只能等。

放后台，你可以继续做别的事，等它进入 Needs input 或 Completed 再处理。

场景四：多方向调查

比如一个线上 bug，有多个可能原因：

  • 最近代码变更；
  • 数据异常；
  • 依赖升级；
  • 环境变量变更；
  • flaky test。

你可以派多个后台 Agent 分别调查。

这和 Dynamic Workflows 有点像，但差别是：Agent View 更像你手动管理多个独立调查任务，而不是让 JavaScript workflow 自动编排。

不适合哪些场景

Agent View 不是万能的。

不适合：

场景 原因
强顺序依赖任务 并行意义不大
多个任务都要改同一文件 容易冲突，即使用 worktree 也要合并成本
简单小修改 后台化反而麻烦
token 预算很紧 多个 session 会并行消耗额度
本机不能长时间运行 后台 Agent 仍然跑在本机，不是云端托管
不可信仓库 后台任务更容易放大权限风险

一句话：适合并行、独立、可审查的任务，不适合强耦合任务。

和 Dynamic Workflows 怎么选

这两个能力很容易放在一起比较。

维度 Agent View / Background Agents Dynamic Workflows
编排方式 人手动派发多个后台会话 Claude 生成 workflow 自动编排
任务规模 多个独立任务 数十到数百子 Agent
中间状态 每个 session 自己保存 workflow 脚本变量保存
可控性 人更容易逐个接管 自动化程度更高
适合场景 并行开发、PR 审查、长任务 大规模扫描、研究、迁移、验证
风险 多 session 消耗额度、worktree 删除 token 黑洞、资源并发、自动编排不可控

我的使用建议是：

  • 你能明确说出“这几个任务互不相关” → 用 Agent View；
  • 你需要“一个大任务自动拆成很多小任务” → 用 Dynamic Workflows；
  • 你需要“多个 Agent 互相讨论协作” → 用 Agent Teams；
  • 你只是想查一小块上下文 → 用 Subagent。

一个推荐工作流

假设我要处理一个复杂项目的多项维护任务，我会这样用：

claude agents

然后派发：

@frontend fix the layout regression in the dashboard page

@code-reviewer review the latest diff for security and API compatibility risks

investigate why npm test is flaky on checkout.spec.ts

/update-docs summarize recent API changes and update README

之后我只关注：

  • 哪些任务 Needs input；
  • 哪些任务产生了 diff；
  • 哪些任务完成后值得合并；
  • 哪些任务应该直接丢弃。

这比一个会话里来回切换上下文舒服很多。

使用时最容易踩的坑

坑一：并行开太多 Agent

每个后台 session 都消耗 Claude Code 额度。

并行 10 个 Agent，就接近 10 倍速度消耗。

我的建议：一开始 2 到 4 个就够了。

坑二：忘记后台 Agent 在本机运行

Background Agents 不是云任务。

如果你的机器睡眠、断电、重启，正在运行的任务会受影响。

所以别把它当成长期云端 worker。

坑三：删除 session 前没保存 worktree 改动

Agent View 里删除 session，可能会连相关 worktree 一起删除。

如果里面有未提交修改，可能直接没了。

我的习惯是：

  1. 先 attach；
  2. 看 git diff；
  3. 需要就 commit 或 copy；
  4. 再删除 session。

坑四：后台任务权限给太大

后台任务最大的问题是“无人看守”。

所以更要保守：

  • 不要随便 bypassPermissions；
  • 不要让它读敏感文件；
  • 不要让它自动 push；
  • 涉及外部输入时要隔离。

我的判断

我觉得 Agent View 是 Claude Code 从“工具”走向“工作台”的关键能力。

以前我们使用 AI Coding 工具，更多是：

我提出任务 → AI 执行 → 我等待 → 我反馈

Agent View 之后更像：

我派发任务 → 多个 AI 在后台推进 → 我处理阻塞点和最终审查

这对开发者角色的改变很明显：你不只是写 prompt 的人，而更像一个任务调度者。

但它也带来了新要求：

  • 你要会拆任务；
  • 你要会设置权限；
  • 你要会审 diff；
  • 你要会管理 worktree；
  • 你要能判断哪些任务适合并行。

所以它不是让人完全不用管，而是把人的注意力从“过程等待”转移到“任务设计和结果验收”。

小结

  1. Agent View 是 Claude Code 的后台任务管理界面，入口是 claude agents。
  2. Background Agent 是完整 Claude Code 会话，适合长时间、独立、可并行的任务。
  3. 它和 Subagent 不同：Subagent 偏上下文隔离，Background Agent 偏任务并行和可接管。
  4. Worktree 隔离是后台多任务安全修改代码的关键，但删除 session 前要确认改动是否保留。
  5. 不要盲目开太多后台 Agent，token、权限、本机资源和文件冲突都需要管理。
  6. 我的建议是：能手动拆成多个独立任务时用 Agent View，需要自动大规模编排时再用 Dynamic Workflows。
