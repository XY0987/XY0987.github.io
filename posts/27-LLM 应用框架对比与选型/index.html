LLM 应用框架对比与选型：LangChain / LangGraph / AutoGen / CrewAI / Eino 怎么选

发表于2026|更新于2026|AI相关
|字数总计:4.1k|阅读时长:14分钟

行业时间线

行业核心节点 事件
2022-10 LangChain 发布，开启 LLM 应用框架时代
2023-09 微软开源 AutoGen，主打多 Agent 对话协作
2024-01 LangGraph 从 LangChain 独立，主打状态机式编排
2024-03 CrewAI 开源，主打”角色扮演式”多 Agent 协作

先把”LLM 框架”这个词说清楚

市面上叫”Agent 框架””LLM 框架”的东西混得很乱，很多根本不是一个层级的产品。我自己的分法是四层：

┌──────────────────────────────────────────────────┐
│  第四层：无代码 Agent 平台                         │
│  Dify / Coze / n8n / FastGPT                     │
│  定位：拖拽式编排，给非程序员用                      │
└──────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────┐
│  第三层：Agent 编排框架                            │
│  LangGraph / AutoGen / CrewAI / Agents SDK       │
│  定位：流程控制、多 Agent 协作、状态管理            │
└──────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────┐
│  第二层：LLM 应用组件库 / SDK                      │
│  LangChain / LlamaIndex / Eino                   │
│  定位：Model、Prompt、Tool、Memory、RAG 等原子能力  │
└──────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────┐
│  第一层：底层协议与模型 SDK                         │
│  OpenAI SDK / MCP / Function Calling 原生协议     │
│  定位：最底层的能力接入                             │
└──────────────────────────────────────────────────┘

本文聚焦第二层和第三层。一个经常被问的问题是「LangChain 和 LangGraph 什么关系」，这里先说清楚：

  • LangChain 是第二层的组件库，提供 Model / Prompt / Tool / Memory / RAG 这些原子能力
  • LangGraph 是第三层的编排引擎，用来把这些组件按状态图的方式组织起来
  • 官方定位：**LangChain 做”能力砖块”，LangGraph 做”建筑图纸”**，二者是上下游关系，不是竞争关系

Eino 同时具备组件库和编排能力，所以它在两层里都出现，下文放到组件库那一节讲。

六大框架定性

先用一句话给每个框架定性，后面再展开：

框架 层级 一句话定位 典型比喻
LangChain 组件库 LLM 应用的瑞士军刀 一大堆乐高积木
LangGraph 编排 基于状态图的 Agent 编排引擎 用有向图写业务流程
AutoGen 编排 微软出品，多 Agent 对话式协作 一群 AI 在会议室里开会
CrewAI 编排 角色扮演式多 Agent 协作 组一个”AI 剧组”干活
Eino 组件+编排 字节出品，Go 生态的 LLM 应用框架 Go 版的 LangChain
OpenAI Agents SDK 编排 OpenAI 官方的轻量 Agent SDK 官方亲儿子，简单直接

逐个拆解

LangChain：最”基础”的选择

核心思想：把 LLM 应用拆成一堆可组合的组件（Model、Prompt、Tool、Retriever、Memory、Parser），用 LCEL（LangChain Expression Language）把这些组件用管道串起来。它不负责复杂的流程控制，只负责把砖头做好。

import { ChatOpenAI } from "@langchain/openai";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { StringOutputParser } from "@langchain/core/output_parsers";

const prompt = ChatPromptTemplate.fromMessages([
  ["system", "你是一个平实直接的技术编辑"],
  ["human", "用一段话讲清楚：{topic}"],
]);

const model = new ChatOpenAI({ model: "gpt-4o-mini" });

// LCEL：用管道把组件串起来
const chain = prompt.pipe(model).pipe(new StringOutputParser());

const result = await chain.invoke({ topic: "什么是 LangChain" });

优点：

  • 生态最大：几乎所有主流模型、向量库、工具都有现成集成，遇到问题 Google 一搜有答案
  • 组件化程度最高：RAG、Memory、Tool 这些原子能力的抽象是业界事实标准，很多其他框架都在复用它的抽象
  • LCEL 表达力强：管道式写法简洁，天然支持流式、异步、批处理
  • 上下游生态完整：LangSmith（可观测）、LangServe（部署）、LangGraph（编排）一条龙

缺点：

  • 不擅长复杂流程：循环、条件分支、多 Agent 协作等复杂流程用 LCEL 写很别扭，这正是 LangGraph 诞生的原因
  • 抽象层多，调试偏麻烦：一个简单调用底层可能套了四五层 Runnable，栈追踪看着头大
  • 版本迭代激进：早期 v0.0.x 到 v0.1 到 v0.2 API 变过几次，老代码升级有阵痛（现在稳定多了）
  • 我的实战感受：做简单 LLM 调用 / RAG 管道用 LangChain 够了；一旦流程里出现循环、分支、人工介入，就该上 LangGraph

LangGraph：最”工程化”的选择

核心思想：把 Agent 流程抽象成一个有向状态图（StateGraph）。每个节点是一个函数或 Agent，边是状态转移条件。

import { StateGraph, END, Annotation } from "@langchain/langgraph";

// 1. 定义状态
const AgentState = Annotation.Root({
  messages: Annotation<string[]>({ reducer: (a, b) => a.concat(b) }),
  done: Annotation<boolean>(),
});

// 2. 定义节点
const planner = async (state: typeof AgentState.State) => { /* ... */ };
const executor = async (state: typeof AgentState.State) => { /* ... */ };
const reviewer = async (state: typeof AgentState.State) => { /* ... */ };

// 3. 构建图
const workflow = new StateGraph(AgentState)
  .addNode("planner", planner)
  .addNode("executor", executor)
  .addNode("reviewer", reviewer)
  .addEdge("__start__", "planner")
  .addEdge("planner", "executor")
  // 4. 条件边
  .addConditionalEdges("executor", (s) => (s.done ? "reviewer" : "executor"), {
    reviewer: "reviewer",
    executor: "executor",
  })
  .addEdge("reviewer", END);

const app = workflow.compile();

优点：

  • 流程可见可控：每个节点、每条边都明确写出，debug 时一眼看清走到哪一步
  • 支持循环和分支：天然支持 ReAct、Reflection、Plan-and-Execute 等所有经典模式
  • 生态完善：LangChain 全家桶能直接复用，工具、RAG、Memory 全有
  • LangSmith 可观测性一流：每步的输入输出、Token 消耗、延迟都能可视化

缺点：

  • 上手门槛偏高：得理解状态图、reducer、条件边等概念
  • 写多 Agent 协作偏啰嗦：节点和边要手写，Agent 多了图会很复杂
  • JS 版略滞后 Python 版：@langchain/langgraph 核心功能都有，但部分新特性（如高级 checkpointer、某些预置 Agent 模板）要等 Python 先发

AutoGen：最”会议感”的选择

核心思想：把多个 Agent 放进一个”对话群聊”，通过消息传递协作。像人类开会一样，谁该说话、什么时候结束由策略决定。

from autogen import AssistantAgent, UserProxyAgent, GroupChat, GroupChatManager

user = UserProxyAgent("user", human_input_mode="NEVER")
coder = AssistantAgent("coder", system_message="你是资深工程师，负责写代码")
reviewer = AssistantAgent("reviewer", system_message="你是代码审查员")
tester = AssistantAgent("tester", system_message="你负责写测试用例")

group = GroupChat(
    agents=[user, coder, reviewer, tester],
    max_round=10
)
manager = GroupChatManager(groupchat=group)

user.initiate_chat(manager, message="实现一个链表反转函数")

优点：

  • 多 Agent 协作表达最自然：每个 Agent 只管自己的角色，协作逻辑由 Manager 统一调度
  • Conversable Agent 范式：所有 Agent 都能收发消息，灵活
  • 微软背书：社区活跃度高，Research 更新快

缺点：

  • 流程不可控：群聊谁发言、什么时候停，全是 LLM 决策，生产环境很难调试
  • Token 消耗大：每个 Agent 都带完整上下文，成本蹭蹭涨
  • 版本切换频繁：v0.2 到 v0.4 API 大改，旧项目升级成本高
  • **更像”研究玩具”**：我在生产项目里用过，最后都换掉了——流程不确定性太大

CrewAI：最”直觉”的选择

核心思想：把多 Agent 协作建模成一个剧组——每个 Agent 有角色（role）、目标（goal）、背景故事（backstory），任务（Task）分配给合适的 Agent，按顺序或层级执行。

from crewai import Agent, Task, Crew

researcher = Agent(
    role="市场研究员",
    goal="调研 AI Agent 框架的市场格局",
    backstory="你有 10 年技术咨询经验，擅长分析技术趋势",
    tools=[search_tool]
)

writer = Agent(
    role="技术编辑",
    goal="把研究结果写成博客",
    backstory="你是资深技术写作者，文风平实"
)

task1 = Task(description="调研主流 Agent 框架", agent=researcher)
task2 = Task(description="基于调研结果写一篇对比文章", agent=writer)

crew = Crew(agents=[researcher, writer], tasks=[task1, task2])
result = crew.kickoff()

优点：

  • 心智模型最直观：角色 + 任务 + 团队，任何人五分钟能理解
  • 代码量极少：同样功能比 LangGraph 少一半代码
  • 自带几种协作模式：sequential、hierarchical，常见场景开箱即用

缺点：

  • 抽象太高，定制化难：想改一点底层逻辑就得翻源码
  • 复杂流程表达力不足：条件分支、循环、错误重试等工程化需求得绕着写
  • 工具生态相对弱：不如 LangChain 丰富
  • 不适合强 SLA 场景：我的实战感受是，做 demo / 内部工具合适，做面向 C 端的线上服务要慎重

Eino：最”Go 生态”的选择

核心思想：字节开源的 Go 语言 LLM 应用框架，借鉴 LangChain 的 LCEL 思想，但更强调类型安全和流式处理。

// 构建一个简单的 Chain
chain := compose.NewChain[string, string]().
    AppendChatTemplate(promptTemplate).
    AppendChatModel(chatModel).
    AppendLambda(parseOutput)

result, err := chain.Compile(ctx).Invoke(ctx, "你好")

优点：

  • Go 原生：Go 后端项目接入 LLM 不用再调 Python 服务
  • 类型安全：编译期就能发现链路错误，不像 Python 运行时才报
  • 性能好：Go 的并发模型写 Agent 的 parallel tool call 非常自然
  • 字节内部大规模使用：豆包、扣子等产品的底层就是它

缺点：

  • 生态刚起步：工具、模板、示例远不如 LangChain 丰富
  • 社区主要是中文：英文圈知名度低
  • 高级 Agent 模式（Reflection、Multi-Agent）需要自己拼装

OpenAI Agents SDK：最”官方”的选择

核心思想：OpenAI 官方在 2025 年推出的轻量 Agent SDK，继承了 Swarm 的 handoff 理念，但更生产就绪。

import { Agent, run } from "@openai/agents";

const billingAgent = new Agent({
  name: "Billing",
  instructions: "处理账单问题",
});

const techAgent = new Agent({
  name: "Tech",
  instructions: "处理技术问题",
});

const triage = new Agent({
  name: "Triage",
  instructions: "判断用户问题属于哪个领域，交给对应 Agent",
  handoffs: [billingAgent, techAgent],
});

const result = await run(triage, "我账单多了 100 块");

优点：

  • 极简 API：核心概念就三个——Agent、Handoff、Tool
  • 官方维护：跟 OpenAI 模型特性跟得最紧（Structured Output、Parallel Tool Call 等）
  • 内置 Tracing：每一步自动记录，直接在 OpenAI Platform 看

缺点：

  • 只支持 OpenAI 及兼容协议：用国产模型要绕
  • 功能还在补齐：比 LangGraph 少一截
  • 多 Agent 协作只有 Handoff 一种模式

我的实战建议

不同场景我会做不同的推荐：

场景0：简单 LLM 调用 / RAG 管道

首选：LangChain

就是一个”用户问问题 → 检索 → 让 LLM 回答”的线性流程，没必要上 LangGraph。LangChain 的 LCEL 几行代码就能把 Retriever、Prompt、Model、Parser 串起来，天然支持流式输出。先看清需求是不是真的需要编排，不是所有 LLM 应用都叫 Agent。

判断标准：如果你画流程图画出来是一条直线（或者最多一个固定分支），LangChain 就够了；一旦要循环、回退、多 Agent 协作，再升级 LangGraph。

场景1：C 端线上 Agent 产品

首选：LangGraph

C 端产品对可观测性、可控性、稳定性的要求极高。LangGraph 的状态图让流程一清二楚，LangSmith 的 Trace 能直接定位线上问题，这两点目前其他框架都做不到这个水准。

坑提醒：LangGraph.js 常用能力已经跟得上 Python 版，但部分新特性发布有滞后。Node.js 项目接入前，先确认依赖的高级特性在 JS 版是否就绪。

场景2：企业内部工具 / 效率类应用

首选：CrewAI

内部工具优先拼开发速度，出点问题可以快速改。CrewAI 用”角色 + 任务”的模型让需求方都能参与讨论（”这个 Agent 应该是什么角色？”），协作效率高。

场景3：Go 后端团队

首选：Eino

别为了用 LangGraph 硬起一个 Python 服务。Eino 在字节内部经过大规模验证，类型系统 + 并发模型很适合 Go 生态。不足是生态还在补，常见场景能覆盖，冷门需求可能要自己造轮子。

场景4：OpenAI 单一生态 + 简单分流

首选：OpenAI Agents SDK

如果你就是做客服分流、简单多 Agent 调度，又深度绑定 OpenAI 模型，没必要上 LangGraph 这么重的东西。Agents SDK 几十行代码搞定。

场景5：学术研究 / 探索新协作模式

首选：AutoGen

AutoGen 的群聊模型非常适合探索”多 Agent 怎么交互更好”这类开放性问题。但研究归研究，生产千万别用 AutoGen 的纯群聊模式——概率性输出叠加概率性对话终止，线上出问题你根本查不出来是哪环的问题。

几个常见选型误区

踩过 / 见过的坑：

误区1：一上来就选”最火”的

见过团队只因为”LangGraph 在 HackerNews 热度高”就上。结果团队 Python 基础薄弱，一堆 async / generator / TypedDict 把人劝退。选型首先看团队基础，其次看生态，最后才看热度。

误区2：把多 Agent 当万能钥匙

多 Agent 协作听着很美，实际 80% 的场景单 Agent + 多工具就够了。多 Agent 意味着：Token 成本 ×N、出错概率 ×N、调试难度 ×N。没有非多 Agent 不可的硬需求，别轻易上。

误区3：忽视可观测性

线上 Agent 最怕的是”黑盒调用”——用户说不对，你不知道是哪一步出的问题。选型必须把 Tracing 放进核心评估项。LangGraph + LangSmith、OpenAI Agents SDK 自带 Tracing，这方面领先。其他框架要自己搭，成本不低。

误区4：框架不对齐 Function Calling 协议

有些”伪 Agent 框架”底层不用原生 Function Calling，而是用正则解析 LLM 输出。这种方式在弱模型上凑合能跑，上 GPT-4 / Claude 立刻浪费了模型能力。选型时一定确认底层走的是 LLM 原生 Function Calling / Tool Use 协议。

不要框架也是一种选型

最后补一点：手写 Agent Loop 也是一种正当选型。在以下场景我会选择不用框架：

  • 团队需要极致的控制粒度（限频、重试、上下文管理每一处都要自己管）
  • 业务逻辑特殊（比如推送意图检测、多层兜底），框架抽象反而束手束脚
  • 只做单 Agent + 一个简单的 ReAct 循环，框架反而是过度工程

小结

  1. LLM 应用框架分四层——底层 SDK、组件库、编排框架、无代码平台，搞清楚你选的是哪一层
  2. LangChain 和 LangGraph 是上下游而非竞品——LangChain 做砖头，LangGraph 做图纸
  3. 简单线性流程（普通对话、RAG）用 LangChain 就够，不要硬上 Agent 框架
  4. LangGraph 是复杂 Agent 的生产首选，状态图 + LangSmith 的组合目前无人能敌
  5. CrewAI 胜在”直觉”——角色+任务的模型让需求方也能参与，内部工具首选
  6. AutoGen 适合研究，不适合生产——群聊模式的不确定性太高
  7. Eino 是 Go 生态的最优解，字节大规模验证过
  8. OpenAI Agents SDK 是 OpenAI 单一生态下的最轻量选择
  9. 选型优先看团队基础和可观测性，最后才看热度
  10. 不用框架也是选项——控制粒度要求极高时，手写 Loop 反而简单可控
