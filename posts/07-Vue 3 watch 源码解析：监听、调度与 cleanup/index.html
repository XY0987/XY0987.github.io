Vue 3 watch 源码解析：监听、调度与 cleanup

发表于2026|更新于2026|Vue框架及周边库
|字数总计:3.2k|阅读时长:13分钟

源码说明：本文分析的源码基于 vue@3.5.21，对应官方仓库为 vuejs/core，本文所在学习仓库为 XY0987/vue_ori_learning。

前言：watch 是响应式系统里最贴近业务使用的 API。它不像 computed 那样返回一个派生值，而是在依赖变化时执行回调。我的理解是，watch 的本质是：把不同类型的监听源统一成 getter，再用 ReactiveEffect 跑这个 getter，最后通过 scheduler 控制回调什么时候执行。

先给结论

watch 的核心链路可以拆成五步：

步骤 做什么
标准化 source 把 ref、reactive、getter、数组源统一成 getter
创建 effect 用 new ReactiveEffect(getter) 收集依赖
构造 job 比较新旧值，决定是否执行回调
接入 scheduler 控制回调同步执行、入队执行或首次立即执行
cleanup 下一次回调前或 stop 时执行清理逻辑

如果用一句话概括：

watch 不是单独发明了一套响应式机制，它是基于 ReactiveEffect、getter、scheduler 和 cleanup 组合出来的监听 API。

watch 和 watchEffect 的区别

先从使用方式看：

watch(source, (newValue, oldValue, onCleanup) => {
  // source 变化后执行
})

watchEffect(onCleanup => {
  // 立即执行，并自动收集函数内部读取到的依赖
})

二者底层都走 watch 这套基础逻辑，但语义不同：

API 是否有 cb 是否比较新旧值 依赖来源
watch(source, cb) 有 会比较 显式 source
watchEffect(effect) 无 不比较 effect 函数内部自动收集

在 @vue/reactivity 层，二者的差异主要体现在 cb 是否存在。

cleanup 的存储结构

watch 的 cleanup 不是直接挂在全局变量上，而是挂在具体 watcher effect 上：

// 初始占位值，用于区分“第一次运行”与真实的 undefined 旧值。
const INITIAL_WATCHER_VALUE = {}

export type WatchScheduler = (job: () => void, isFirstRun: boolean) => void

// 每个 watcher effect 对应一组 cleanup，下一次执行回调前或 stop 时会统一调用。
const cleanupMap: WeakMap<ReactiveEffect, (() => void)[]> = new WeakMap()
// 当前正在执行回调的 watcher，用于 onWatcherCleanup 绑定 cleanup 所属 effect。
let activeWatcher: ReactiveEffect | undefined = undefined

onWatcherCleanup 注册 cleanup 时，会找到当前正在执行的 watcher：

export function onWatcherCleanup(
  cleanupFn: () => void,
  failSilently = false,
  owner: ReactiveEffect | undefined = activeWatcher,
): void {
  if (owner) {
    // cleanup 绑定到具体 watcher effect，而不是全局变量。
    // 这样同一个 watcher 多次注册 cleanup 时，可以在下一轮回调前按批次清理。
    let cleanups = cleanupMap.get(owner)
    if (!cleanups) cleanupMap.set(owner, (cleanups = []))
    cleanups.push(cleanupFn)
  } else if (__DEV__ && !failSilently) {
    warn(
      `onWatcherCleanup() was called when there was no active watcher` +
        ` to associate with.`,
    )
  }
}

这解释了为什么 onCleanup 必须在 watch 回调或 watchEffect 函数执行期间调用：只有这段时间里，activeWatcher 才能指向正确的 watcher。

第一步：把 source 标准化成 getter

watch 支持很多 source 类型：

  • ref
  • reactive 对象
  • getter 函数
  • 多 source 数组
  • watchEffect 的副作用函数

源码会把它们统一成 getter：

  if (isRef(source)) {
    // watch(ref, cb)：getter 只读取 .value，依赖收集发生在 ref 自己的 dep 上。
    getter = () => source.value
    forceTrigger = isShallow(source)
  } else if (isReactive(source)) {
    // watch(reactiveObj, cb)：通过遍历对象属性来收集依赖。
    getter = () => reactiveGetter(source)
    forceTrigger = true
  } else if (isArray(source)) {
    // watch([a, b, getter], cb)：多源监听会把每个 source 标准化成一个数组结果。
    isMultiSource = true
    forceTrigger = source.some(s => isReactive(s) || isShallow(s))
    getter = () =>
      source.map(s => {
        if (isRef(s)) {
          return s.value
        } else if (isReactive(s)) {
          return reactiveGetter(s)
        } else if (isFunction(s)) {
          return call ? call(s, WatchErrorCodes.WATCH_GETTER) : s()
        } else {
          __DEV__ && warnInvalidSource(s)
        }
      })
  } else if (isFunction(source)) {
    if (cb) {
      // watch(getter, cb)：source 自身就是 getter。
      getter = call
        ? () => call(source, WatchErrorCodes.WATCH_GETTER)
        : (source as () => any)
    } else {
      // watchEffect(effect)：没有 cb，source 就是需要立即执行并自动收集依赖的副作用函数。
      getter = () => {
        if (cleanup) {
          pauseTracking()
          try {
            cleanup()
          } finally {
            resetTracking()
          }
        }
        const currentEffect = activeWatcher
        activeWatcher = effect
        try {
          return call
            ? call(source, WatchErrorCodes.WATCH_CALLBACK, [boundCleanup])
            : source(boundCleanup)
        } finally {
          activeWatcher = currentEffect
        }
      }
    }
  } else {
    getter = NOOP
    __DEV__ && warnInvalidSource(source)
  }

这里有一个关键点：watch 真正监听的不是 source 本身，而是执行 getter 过程中读取到的响应式依赖。

例如：

watch(countRef, cb)

会变成：

getter = () => countRef.value

再比如：

watch(() => state.count, cb)

getter 就是用户传入的函数。底层 effect 执行 getter 时，读取 state.count，自然会被 track 收集。

deep 的本质：主动遍历以读取属性

深度监听不是魔法，本质是主动递归读取属性，让这些属性都被依赖收集。

watch 内部有一个 reactiveGetter：

  // 根据 deep 配置决定 reactive 对象要遍历到什么深度。
  // watch 监听 reactive 对象时，需要通过主动读取属性来建立依赖。
  const reactiveGetter = (source: object) => {
    // deep 为 true/数字时，后面会再包一层 traverse，这里先返回原对象。
    if (deep) return source
    // deep: false/0 或 shallow reactive 只遍历根层属性。
    if (isShallow(source) || deep === false || deep === 0)
      return traverse(source, 1)
    // 默认监听 reactive 对象时做深度遍历，让嵌套属性变化也能触发 watcher。
    return traverse(source)
  }

如果显式配置了 deep，还会再包装一层：

  if (cb && deep) {
    const baseGetter = getter
    const depth = deep === true ? Infinity : deep
    // 显式 deep 会在 getter 结果上继续 traverse，确保深层属性都被读取并收集依赖。
    getter = () => traverse(baseGetter(), depth)
  }

traverse 的作用就是递归访问对象、数组、Map、Set、ref 等内部值：

// 用于递归遍历对象/集合的核心工具函数，深度访问对象属性以建立依赖关系。
export function traverse(
  value: unknown,
  depth: number = Infinity,
  seen?: Map<unknown, number>,
): unknown {
  // 非对象、超过深度、或被 markRaw 跳过的对象，不需要继续遍历。
  if (depth <= 0 || !isObject(value) || (value as any)[ReactiveFlags.SKIP]) {
    return value
  }

  // seen 用于处理循环引用，同时记录已遍历到的最大深度，避免重复遍历。
  seen = seen || new Map()
  if ((seen.get(value) || 0) >= depth) {
    return value
  }
  seen.set(value, depth)
  depth--
  if (isRef(value)) {
    traverse(value.value, depth, seen)
  } else if (isArray(value)) {
    for (let i = 0; i < value.length; i++) {
      traverse(value[i], depth, seen)
    }
  } else if (isSet(value) || isMap(value)) {
    value.forEach((v: any) => {
      traverse(v, depth, seen)
    })
  } else if (isPlainObject(value)) {
    for (const key in value) {
      traverse(value[key], depth, seen)
    }
    for (const key of Object.getOwnPropertySymbols(value)) {
      if (Object.prototype.propertyIsEnumerable.call(value, key)) {
        traverse(value[key as any], depth, seen)
      }
    }
  }
  return value
}

所以 deep: true 的成本是实打实的：它需要递归读取对象结构。对象越大，遍历成本越高。

第二步：创建 ReactiveEffect

source 标准化成 getter 后，watch 会创建一个 ReactiveEffect：

  // watch 底层仍然是一个 ReactiveEffect，只是 effect 的 fn 是标准化后的 getter。
  effect = new ReactiveEffect(getter)

  effect.scheduler = scheduler
    ? () => scheduler(job, false)
    : (job as EffectScheduler)

  // 绑定到当前 watcher effect 的 cleanup 注册函数，会作为第三个参数传给 watch 回调。
  boundCleanup = fn => onWatcherCleanup(fn, false, effect)

这说明 watch 和 effect 的底层机制是一致的：都是通过 ReactiveEffect 执行函数、收集依赖、在依赖变化时被调度。

区别在于：普通 effect 的 fn 通常就是用户传入的副作用函数；而 watch(source, cb) 创建的 ReactiveEffect，它的 fn 是标准化后的 getter，用来读取 source、收集依赖、拿到新值。真正的 cb(newValue, oldValue, cleanup) 不在 effect.run() 里直接执行，而是在 job 里完成。

还要区分首次执行：

  • 非 immediate 的 watch：初始化时只执行 effect.run()，收集依赖并保存 oldValue，不会执行回调。
  • immediate: true 的 watch：初始化时执行 job(true)，job 内部会先 effect.run() 拿到新值，然后立即执行回调。
  • 后续依赖变化：调度器触发 job，再由 job 决定是否执行回调。

第三步：job 负责比较新旧值并执行回调

job 是 watch 的核心调度任务：

  const job = (immediateFirstRun?: boolean) => {
    // effect 已停止，或依赖没变且不是 immediate 首次运行时，直接跳过。
    if (
      !(effect.flags & EffectFlags.ACTIVE) ||
      (!effect.dirty && !immediateFirstRun)
    ) {
      return
    }
    if (cb) {
      // watch(source, cb)：先运行 getter 拿到新值，同时完成依赖收集。
      const newValue = effect.run()
      if (
        deep ||
        forceTrigger ||
        (isMultiSource
          ? (newValue as any[]).some((v, i) => hasChanged(v, oldValue[i]))
          : hasChanged(newValue, oldValue))
      ) {
        // 回调再次执行前，先执行上一轮注册的 cleanup。
        if (cleanup) {
          cleanup()
        }
        const currentWatcher = activeWatcher
        activeWatcher = effect
        try {
          const args = [
            newValue,
            // 首次触发时 oldValue 对外表现为 undefined；多源首次触发时为 []。
            oldValue === INITIAL_WATCHER_VALUE
              ? undefined
              : isMultiSource && oldValue[0] === INITIAL_WATCHER_VALUE
                ? []
                : oldValue,
            boundCleanup,
          ]
          oldValue = newValue
          call
            ? call(cb!, WatchErrorCodes.WATCH_CALLBACK, args)
            : // @ts-expect-error
              cb!(...args)
        } finally {
          activeWatcher = currentWatcher
        }
      }
    } else {
      // watchEffect：没有新旧值比较，依赖变化后直接重新执行 effect。
      effect.run()
    }
  }

watch(source, cb) 的执行逻辑是：

  1. 先判断 effect 是否还活着、是否真的脏了。
  2. 运行 getter 得到 newValue。
  3. 根据 deep、forceTrigger、hasChanged 判断是否需要执行回调。
  4. 执行上一轮 cleanup。
  5. 调用回调，传入 newValue、oldValue、onCleanup。
  6. 更新 oldValue。

而 watchEffect 没有新旧值比较，依赖变了就重新执行 effect。

immediate、once 和初始运行

初始运行逻辑在这里：

  // initial run
  if (cb) {
    if (immediate) {
      // immediate: true 时立即执行 job，回调会收到当前值和 undefined 旧值。
      job(true)
    } else {
      // 非 immediate 时先运行 getter 收集依赖，并把结果保存为 oldValue，不触发回调。
      oldValue = effect.run()
    }
  } else if (scheduler) {
    // watchEffect + 自定义 scheduler：首次执行交给 scheduler 决定。
    scheduler(job.bind(null, true), true)
  } else {
    effect.run()
  }

这里解释了 immediate 的行为：

watch(source, cb, { immediate: true })

会立刻执行 job(true)，因此回调立即触发，并且第一次的 oldValue 是 undefined。

once 则通过包装回调实现：

  if (once && cb) {
    const _cb = cb
    // once 通过包装回调实现：第一次回调执行后立即 stop watcher。
    cb = (...args) => {
      _cb(...args)
      watchHandle()
    }
  }

第一次回调执行完，直接调用 watchHandle() 停止 watcher。

scheduler：运行时如何控制 watch 执行时机

@vue/reactivity 层只提供 scheduler 选项。真正的 flush: 'pre' | 'post' | 'sync' 是 runtime-core 包装出来的。

在 runtime-core/src/apiWatch.ts 里，doWatch 会根据 flush 配置 scheduler：

  // scheduler
  let isPre = false
  if (flush === 'post') {
    baseWatchOptions.scheduler = job => {
      queuePostRenderEffect(job, instance && instance.suspense)
    }
  } else if (flush !== 'sync') {
    // default: 'pre'
    isPre = true
    baseWatchOptions.scheduler = (job, isFirstRun) => {
      if (isFirstRun) {
        job()
      } else {
        queueJob(job)
      }
    }
  }

可以这样理解：

flush 行为
sync 不额外包装 scheduler，同步执行
pre 默认行为，更新前进入组件调度队列
post 组件渲染后执行

watch.ts 本身并不关心组件，它只知道：如果传了 scheduler，就把 job 交给 scheduler。

  effect.scheduler = scheduler
    ? () => scheduler(job, false)
    : (job as EffectScheduler)

这就是响应式包和运行时包的职责边界：

  • @vue/reactivity 负责监听机制。
  • @vue/runtime-core 负责结合组件更新时机调度 watcher。

stop、pause、resume

watch 返回的不是普通函数，而是带控制方法的 handle：

  watchHandle.pause = effect.pause.bind(effect)
  watchHandle.resume = effect.resume.bind(effect)
  watchHandle.stop = watchHandle

  return watchHandle

前面构造 watchHandle 时，它的核心就是停止底层 effect：

  const scope = getCurrentScope()
  const watchHandle: WatchHandle = () => {
    // stop 时停止底层 ReactiveEffect，并从当前 effectScope 中移除。
    effect.stop()
    if (scope && scope.active) {
      remove(scope.effects, effect)
    }
  }

所以：

const stop = watch(source, cb)
stop()

本质就是 effect.stop()。

pause 和 resume 则复用 ReactiveEffect 自己的暂停/恢复能力。暂停期间依赖变化不会立即执行，恢复时如果期间被触发过，会补一次触发。

cleanup 的执行时机

cleanup 有两个执行时机。

第一，下一次回调执行前：

        // 回调再次执行前，先执行上一轮注册的 cleanup。
        if (cleanup) {
          cleanup()
        }

第二，watcher stop 时：

  cleanup = effect.onStop = () => {
    const cleanups = cleanupMap.get(effect)
    if (cleanups) {
      if (call) {
        call(cleanups, WatchErrorCodes.WATCH_CLEANUP)
      } else {
        for (const cleanup of cleanups) cleanup()
      }
      cleanupMap.delete(effect)
    }
  }

这就是为什么常见的异步请求取消可以这样写：

watch(id, async (newId, oldId, onCleanup) => {
  const controller = new AbortController()

  onCleanup(() => {
    controller.abort()
  })

  await fetch(`/api/${newId}`, {
    signal: controller.signal,
  })
})

当 id 再次变化时，上一次请求会先被 abort，再发起新请求。

一个完整流程

以这个例子为例：

const count = ref(0)

watch(count, (newValue, oldValue, onCleanup) => {
  console.log(newValue, oldValue)
})

count.value++

初始化：

watch(count, cb)
  │
  ▼
source 是 ref
  │
  ▼
getter = () => count.value
  │
  ▼
new ReactiveEffect(getter)
  │
  ▼
非 immediate：effect.run()
  │
  ├─ 读取 count.value，收集依赖
  └─ oldValue = 0

更新：

count.value++
  │
  ▼
count.dep.trigger()
  │
  ▼
effect.scheduler()
  │
  ▼
job()
  │
  ├─ effect.run() 得到 newValue
  ├─ hasChanged(newValue, oldValue)
  ├─ cleanup()
  ├─ cb(newValue, oldValue, onCleanup)
  └─ oldValue = newValue

小结

  1. watch 的第一步是把各种 source 标准化为 getter。
  2. watch 底层仍然依赖 ReactiveEffect 收集依赖和响应变化。
  3. job 负责执行 getter、比较新旧值、调用 cleanup 和回调。
  4. deep 的本质是递归读取属性，让深层属性也被依赖收集。
  5. immediate 决定是否初始化时立即执行回调，once 通过回调后 stop 实现。
  6. scheduler 让运行时可以控制 watch 回调的执行时机。
  7. cleanup 会在下一次回调前和 stop 时执行，适合清理异步任务。

到这里，响应式系统的核心 API 主线基本完整了：reactive、ref、computed、effect、watch。后续可以进入运行时主线，从 createApp 和 renderer 开始看组件如何挂载和更新。
