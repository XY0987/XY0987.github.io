新一代构建工具链趋势：Rolldown、Rspack、OXC、Biome、Bun / Deno

发表于2026|更新于2026|工程化
|字数总计:2.4k|阅读时长:8分钟

前言：这一篇不要求你精通任何一个新工具，目标是建立一张「坐标系」——知道 Rolldown、Rspack、OXC、Biome、Bun、Deno 各自站在什么位置、要替代谁、迁移成本如何。这样以后看到这些名字不慌，能快速判断它和你已有的工具栈是什么关系。本篇涉及的版本节点变化很快，具体请以各项目官方文档为准。

一句话先把坐标系定下来

这几年新工具的共同主题就一个字：Rust 重写。把原来用 JavaScript 写的慢工具，用 Rust 重写成快工具。先用一张表定位：

工具 要替代/对标 语言 角色
Rolldown Rollup（+ esbuild 在 Vite 里的角色） Rust 打包器
Rspack Webpack Rust 打包器
Rsbuild / Rslib Webpack 上层方案 / 库构建 Rust 应用/库构建框架
OXC（oxlint/oxfmt） 部分 Babel / ESLint / Prettier 能力 Rust 解析 + lint + 格式化
Biome ESLint + Prettier 二合一 Rust lint + 格式化
Bun Node.js + npm + 打包器 + 测试 Zig 全能运行时工具链
Deno Node.js Rust 安全优先的运行时

记住一个分类：Rolldown/Rspack 是打包层的替代，OXC/Biome 是质量工具层的替代，Bun/Deno 是运行时层的替代。它们分别在我前面讲的「坐标系」三层里各占一块。

Rolldown：Vite 的下一代底层

Rolldown 是 Vite 团队（现在叫 VoidZero）用 Rust 写的打包器，定位是「Rust 版的 Rollup」——保持 Rollup 的插件 API 和产物形态，但快一个数量级。

它解决的是 Vite 的一个历史包袱。前面讲过，Vite 2~6 是双引擎：开发用 esbuild、构建用 Rollup。这套设计的代价是开发和构建两套引擎、偶尔行为不一致，而且 Rollup 是 JS 写的、构建大项目慢。

Rolldown 的目标就是用一个 Rust 引擎统一这两个角色：

旧（Vite ≤7）：  esbuild（dev） + Rollup（build）  ← 两套引擎
新（Vite 8+）：  Rolldown（dev + build）           ← 一套 Rust 引擎

按官方发布信息，Rolldown 已经成为 Vite 8（2026 年 3 月发布）的默认底层，Rolldown 1.0 也在 2026 年 5 月稳定。对普通 Vite 用户来说，这个切换基本是无感的——配置和 Rollup 风格插件大多兼容，你只是「免费」拿到了更快的构建。

和你的关系：如果你用 Vite，迁移到 Vite 8 大概率不需要改代码，享受构建提速即可。CommonJS 重度依赖、Yarn PnP 等少数场景需要测一下兼容性。这也是为什么我前面说「学 Rollup 插件机制不过时」——Rolldown 兼容它。

Rspack / Rsbuild / Rslib：字节系的 Webpack 替代

如果说 Rolldown 是「Vite 阵营」的 Rust 化，那 Rspack 系就是「Webpack 阵营」的 Rust 化，由字节跳动主导。

  • Rspack：Rust 写的打包器，主打和 Webpack 高度兼容——配置、loader、plugin 大部分能直接复用，但不承诺 100% 兼容。
  • Rsbuild：架在 Rspack 之上的开箱即用构建框架，类比「Webpack 阵营的 Vite」，提供合理默认配置。
  • Rslib：基于 Rspack 的库构建方案，类比 tsup/unbuild 的角色。

它的核心卖点是迁移成本低。一个跑了多年的大型 Webpack 项目，换 Vite 可能要大改（bundle → no-bundle 思路不同、某些 Webpack 专属 loader 没有对应），但换 Rspack 往往只需要改少量配置，就能拿到 Rust 的速度。

Webpack 项目想提速：
  → 换 Vite：思路不同，迁移成本高，但开发体验最好
  → 换 Rspack：配置兼容，迁移成本低，平滑提速

和你的关系：维护存量 Webpack 大项目、又嫌它慢，优先评估 Rspack（迁移成本低）；如果是能接受重写、追求极致开发体验的新项目或中型项目，Vite 仍是首选。

实操上不要只看「兼容」两个字就直接替换。Rspack 官方维护了常见社区插件的兼容列表，常规 loader/plugin 大多能迁，但如果项目里有自研 Webpack 插件、冷门 loader、深度依赖 compiler 内部细节的逻辑，一定要单独验证。

OXC：Rust 的解析 / lint 工具链

OXC（The Oxidation Compiler）是一套用 Rust 写的 JavaScript/TypeScript 底层工具集合，目标是重写解析、lint、格式化这些能力。它旗下你会听到：

  • oxlint：极快的 linter，对标 ESLint 的常用规则。常被当作「预检」——在 ESLint 之前先用 oxlint 跑一遍，毫秒级抓出大部分问题。
  • oxfmt：Prettier 兼容的格式化器。
  • OXC 的解析器本身也被 Rolldown、Rspack 等工具当作底层引擎使用。

它的现状（截至 2026 年中）是：oxlint 已经不是实验品，下载量很大，很多团队用「oxlint 做快速预检 + ESLint 做深度规则」的组合。但 OXC 还没有完全覆盖 ESLint 的插件生态，复杂、冷门的规则仍要靠 ESLint。

和你的关系：OXC 不一定要立刻全量替换你的 ESLint。一个低风险的用法是把 oxlint 加进 pre-commit 或 CI 第一道闸口做秒级预检，ESLint 留作深度检查。这呼应了「CI 流水线与质量闸口」那篇的分层思路。

Biome：ESLint + Prettier 二合一

Biome（前身 Rome）走的是另一条路：不是只做 linter 或只做 formatter，而是一个工具同时干 lint 和格式化，用 Rust 写，零依赖、极快。

它和现有规范栈的取舍很清晰：

维度 ESLint + Prettier Biome
工具数量 两个（还要协调边界） 一个
速度 较慢 快很多
配置 两套配置 + 协调 一份配置
插件生态 极其丰富 较少，框架专用规则有限
迁移 — biome migrate 辅助迁移

Biome 最大的吸引力是「一个工具、一份配置、还快」，消除了 ESLint 和 Prettier 之间那些恼人的边界协调（这块痛点在「Prettier 与 Stylelint 的边界」那篇专门讲过）。代价是插件生态不如 ESLint，一些 React/安全类的专用规则可能缺。

和你的关系：新项目、追求低配置和速度、规则需求不复杂 → Biome 很合适。重度依赖 ESLint 特定插件（安全、框架专属规则）的成熟项目 → 继续 ESLint，或用 oxlint 做预检。

Bun / Deno：运行时层的搅局者

前面几个都在「构建/质量」层，Bun 和 Deno 则在更底层的运行时层，是 Node.js 的挑战者。

Bun

Bun 主打全家桶：一个二进制同时是运行时、包管理器、打包器、测试运行器。官方当前仍把 Bun 描述为用 Zig 编写、底层基于 JavaScriptCore；如果后续出现 Rust 迁移进展，可以当作实现层演进关注，但不要把它作为今天选型的核心依据。

bun install   # 替代 npm install，快很多
bun run dev   # 跑脚本
bun build     # 打包
bun test      # 测试
bun --hot     # 热重载

它的卖点是「一个工具搞定一切」，对 Node.js API 兼容度很高（约 98%）。短板是那剩下的 2%——一些用 node-gyp 编译的原生 C++ 模块（老版本 bcrypt、sharp 等）可能跑不起来，企业级、依赖复杂的存量项目迁移要谨慎做依赖审计。

Deno

Deno 是 Node.js 作者 Ryan Dahl 重新设计的运行时，主打安全（默认沙箱，权限要显式授予）和原生 TS 支持（直接跑 TS、能做类型检查）。Deno 2 大幅补齐了 Node.js / npm 兼容性，支持 node_modules 和 package.json，还有 npm: 说明符和自家的 JSR 注册表。

// Deno 直接跑 TS，权限需显式授予
// deno run --allow-net server.ts

怎么看 Bun / Deno

我的判断（保持坐标系思维，不盲目跟风）：

场景 倾向
企业级、依赖复杂的存量后端 仍以 Node.js 为主，稳
新项目、想要全家桶 + 速度 可以试 Bun
脚本、CLI、追求快冷启动 + 安全 Deno 很合适
边缘计算 / 安全敏感场景 Deno 的权限模型有优势

现在更像「稳定的多元化」：Node 主打稳定、Deno 主打安全、Bun 主打性能和一体化。不存在一个赢家通吃，按场景选。

怎么建立你自己的坐标系

最后给一套不焦虑的方法论，面对层出不穷的新工具：

看到一个新工具，先问三个问题：
1. 它在哪一层？（打包层 / 质量工具层 / 运行时层）
2. 它要替代谁？（对标的旧工具是什么）
3. 迁移成本多大？（配置兼容？思路是否相同？）

回答完这三个问题，你就能把任何新工具放进坐标系，而不是被一堆名字淹没。

我的总体态度：新工具大多是「更快地做同一件事」，而不是「做一件全新的事」。所以底层原理（打包、转译、模块图、Tree Shaking 那些）才是真正长期有效的知识，工具会换，原理不变。建立坐标系、理解原理，比追每个新工具重要得多。

小结

  1. 新工具的共同主题是 Rust 重写，本质是「更快地做同一件事」，按层分类就不乱。
  2. Rolldown 是 Rust 版 Rollup，已成为 Vite 8 默认底层，统一了原来的 esbuild + Rollup 双引擎，对用户基本无感提速。
  3. Rspack/Rsbuild/Rslib 是字节系的 Webpack 兼容替代，迁移成本低，适合存量 Webpack 项目提速。
  4. OXC（oxlint/oxfmt）是 Rust 解析/lint 工具链，适合做 ESLint 之前的秒级预检，暂不完全替代 ESLint 生态。
  5. Biome 是 ESLint + Prettier 二合一，配置少且快，适合新项目；重度插件需求仍留 ESLint。
  6. Bun（全家桶、性能）和 Deno（安全、原生 TS）是 Node.js 的运行时挑战者，现状是「稳定的多元化」，按场景选。
  7. 面对新工具问三件事：在哪一层、替代谁、迁移成本多大；原理比工具更值得投入。
